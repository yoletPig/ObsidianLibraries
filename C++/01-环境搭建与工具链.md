## 1. 为什么语音/推理引擎是 C++ 写的

先建立动机。你迟早会碰到这几个名字：**whisper.cpp**（OpenAI Whisper 的纯 C/C++ 实现）、**onnxruntime**（微软推理引擎，核心 C++，Python 只是外壳）、**Kaldi / k2、webrtcvad、portaudio**（语音圈老牌 C/C++ 库）。

为什么不是 Python？一句话：**这些库干的是"每个样本都要算一遍"的活，对性能和内存布局有硬要求，Python 解释器本身的开销承担不起。**

- 一段 16kHz 音频，1 秒就是 16000 个样本；模型推理是几百万次乘加。C++ 编译成机器码直接跑；numpy、torch 说白了也是"C++ 内核 + Python 遥控器"。
- C++ 的另一个关键是**确定性**：没有 GC 停顿，对象何时死亡由作用域决定——这在 10ms 一帧的实时音频处理里是刚需。
- 现实分工：**算法实验用 Python，工程落地（引擎、插件、嵌入式端）用 C++**。你的目标就是去开遥控器后面那台机器，代价是内存要自己管——本系列的主线。

## 2. `g++ main.cpp` 到底做了什么：编译四阶段

Python 是"解释执行"，C++ 是"先把人话翻译成机器码"。翻译分四个阶段：

```
main.cpp ──① 预处理──> main.i ──② 编译──> main.s ──③ 汇编──> main.o ──④ 链接──> a.out
          (文本替换)        (C++ → 汇编)      (汇编 → 机器码)      (多份 main.o 拼起来)
```

1. **预处理（Preprocess）**：纯文本操作。把 `#include` 的头文件原样粘贴进来，展开宏，删注释。产物还是 C++ 源码。
2. **编译（Compile）**：真正的语言层翻译——语法检查、类型检查、优化，生成汇编。
3. **汇编（Assemble）**：把汇编翻成二进制**目标文件**（`.o`）。此时函数还只有名字，没有最终地址。
4. **链接（Link）**：把你所有 `.o` 和用到的库拼成可执行文件，填上所有地址。你 90% 的 "undefined reference" 报错发生在这一步。

g++ 可以让任何一步停下来给你看中间产物：

```bash
g++ -E main.cpp -o main.i   # 停在 ①：看看 #include 到底粘进来了多少行
g++ -S main.cpp -o main.s   # 停在 ②：阅读人类可读的汇编
g++ -c main.cpp -o main.o   # 停在 ③：得到目标文件
g++ main.o -o app           # 只做 ④：链接
g++ main.cpp -o app         # 四步全做（平时用这个就行）
```

试一下第一条，`#include <cstdio>` 一行会被展开成几千行——头文件的本质就是**声明清单**，不是魔法。

### 第一个可执行程序

```cpp
// hello.cpp
#include <cstdio>

int main() {
    std::printf("hello, speech!\n");
    return 0;
}
```

```bash
g++ -std=c++17 -Wall -Wextra -pedantic -o hello hello.cpp
./hello
```

预期输出：

```
hello, speech!
```

> Python 里 `print` 是现成的；C++ 里 `printf` 来自 C 标准库，要先 `#include <cstdio>` 告诉编译器"有这么个函数"。C++ 自家的 `std::cout`（`<iostream>`）也行，本书两不排斥，音频代码里 `printf` 更常见。

## 3. g++ 常用旗子速查

| 旗子 | 作用 | 什么时候用 |
|---|---|---|
| `-std=c++17` | 指定语言标准（默认可能偏旧，必须显式写） | 永远写 |
| `-O0` / `-O2` / `-O3` | 优化级别：O0 不优化（最好调试），O2 日常发布 | 开发期 O0，测性能 O2/O3 |
| `-g` | 把变量名、行号等调试信息塞进可执行文件 | 要用 gdb / ASan 时 |
| `-Wall -Wextra -pedantic` | 全开警告，最严格的三档 | 永远写，警告当错误对待 |
| `-I 目录` | 告诉编译器去哪找 `#include "xxx.h"` | 头文件不在当前目录时 |
| `-L 目录` + `-l 名字` | 告诉链接器去哪找库；`-laudio` 找 `libaudio.a/.so` | 链接第三方库时 |
| `-fsanitize=address,undefined` | 插入运行时检查，抓内存错误 | 调试（见第 5 节） |

警告不是装饰。看这个例子：

```cpp
// warn_demo.cpp
#include <cstdio>
#include <vector>

int main() {
    std::vector<float> samples = {0.1f, -0.2f, 0.3f};
    for (int i = 0; i < samples.size(); ++i) {   // 有符号 vs 无符号比较
        std::printf("%f\n", samples[i]);
    }
    return 0;
}
```

`samples.size()` 是无符号的 `size_t`，拿 `int i` 去比，极端长度下会出错。加警告编译 `g++ -std=c++17 -Wall -Wextra -pedantic -c warn_demo.cpp -o /dev/null`，编译器立刻指出：

```
warn_demo.cpp:7:23: warning: comparison of integer expressions of different
signedness: 'int' and 'std::vector<float>::size_type' {aka 'long unsigned int'}
    7 |     for (int i = 0; i < samples.size(); ++i) {
      |                     ~~^~~~~~~~~~~~~~~~
```

修正方法（第 02 篇细讲）是换成 `std::size_t` 或用范围 for。**肌肉记忆：编译命令永远带 `-Wall -Wextra -pedantic`，出现警告当编译失败处理。**

### 头文件目录与库：`-I -L -l` 实战

把第 6 节的 `audio_utils` 编译成静态库再链接（库命名规则：`lib<名字>.a`，用 `-l<名字>` 引用；假设 `audio_utils.h` 在 `include/`、源码在 `src/`）：

```bash
g++ -std=c++17 -Wall -Wextra -pedantic -Iinclude -c src/audio_utils.cpp -o build/audio_utils.o
ar rcs build/libaudio.a build/audio_utils.o      # ar 把 .o 打包成静态库
g++ -std=c++17 -Wall -Wextra -pedantic -Iinclude -c main.cpp -o build/main.o
g++ build/main.o -Lbuild -laudio -o build/app    # -Iinclude 找头文件，-Lbuild -laudio 找库
./build/app
```

预期输出：

```
last=-2
```

将来调用 onnxruntime 时，`-Ionnxruntime/include -Lonnxruntime/lib -lonnxruntime` 就是同样的三板斧。下一节的 CMake 会把它们从命令行里解放出来。

## 4. CMake 最小工程

**为什么需要 CMake**：上面的链接命令把源文件、目录、库全写死在命令行里；文件一多、还想跨平台，手敲就崩了。CMake 的思路是**用一份 `CMakeLists.txt` 描述"工程里有什么"，它替你在任何平台生成构建脚本**。whisper.cpp、onnxruntime 全用 CMake 构建，学会它你才能亲手编译这些项目。

最小工程两个文件。`main.cpp`：

```cpp
// main.cpp
#include <cstdio>
#include <string_view>

constexpr float kGain = 1.5f;   // 编译期常量

int main() {
    std::string_view name = "whisper";
    std::printf("building %s demo, gain=%g\n", name.data(), kGain);
    return 0;
}
```

`CMakeLists.txt`：

```cmake
cmake_minimum_required(VERSION 3.16)   # 最低要求的 CMake 版本
project(speech_demo LANGUAGES CXX)     # 工程名，语言是 C++

set(CMAKE_CXX_STANDARD 17)             # 对应 g++ 的 -std=c++17
set(CMAKE_CXX_STANDARD_REQUIRED ON)    # 不允许悄悄退回旧标准
set(CMAKE_CXX_EXTENSIONS OFF)          # 用 -std=c++17 而不是 gnu++17

add_executable(speech_demo main.cpp)   # 目标名 + 源文件列表

target_compile_options(speech_demo PRIVATE -Wall -Wextra -pedantic)
```

构建与运行（现代 CMake 惯例：在 `build/` 目录里构建，产物不污染源码目录）：

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release   # 读 CMakeLists.txt，生成构建脚本
cmake --build build                              # 实际编译（内部调 make / ninja）
./build/speech_demo
```

预期输出：

```
building whisper demo, gain=1.5
```

三点说明：① `CMAKE_BUILD_TYPE=Release` 相当于 `-O2 -DNDEBUG`，`Debug` 相当于 `-g -O0`；**不指定类型时默认无优化无调试信息，两头不讨好**——新手最常见的坑之一。② `cmake --build build` 是跨平台的"编译一下"，进去直接 `make` 也行。③ 以后加库就是加 `add_library` + `target_link_libraries`，`-I -L -l` 全由它接管；编译 whisper.cpp 时你写的其实就是 `cmake -B build && cmake --build build -j`。

## 5. 出错了怎么查：gdb 与 AddressSanitizer

程序崩溃（段错误 Segfault）时，默认只有一句冷冰冰的 `Segmentation fault`。两个工具能看到真相。

### 5.1 gdb：崩溃现场停尸间

gdb 是命令行调试器，最小工作流：

```bash
g++ -std=c++17 -g -O0 -o app main.cpp   # -g 带调试信息，-O0 别优化（否则行号乱跳）
gdb ./app
```

常用命令：`run` 跑到崩溃自动停下；`bt`（backtrace）打印崩溃时的函数调用链，精确到文件和行号；`print 变量` 看值；`break 5` 在第 5 行下断点；`next`/`step` 单步（后者会进函数内部）。

### 5.2 AddressSanitizer：让内存错误自己招供

比 gdb 更省事的是**给编译器加运行时检查器**。同样的崩溃，ASan 编译再运行：

```cpp
// gdb_segfault.cpp —— 一个典型的空指针崩溃
#include <cstdio>

void apply_gain(float* buf, int n, float gain) {
    for (int i = 0; i < n; ++i) {
        buf[i] *= gain;    // buf 是空指针，这里崩溃
    }
}

int main() {
    float* buffer = nullptr;   // 假装忘了分配
    apply_gain(buffer, 3, 1.5f);
    return 0;
}
```

```bash
g++ -std=c++17 -g -fsanitize=address -o seg_asan gdb_segfault.cpp
./seg_asan
```

真实输出（关键行）：

```
=================================================================
==4485==ERROR: AddressSanitizer: SEGV on unknown address 0x000000000000
==4485==The signal is caused by a READ memory access.
==4485==Hint: address points to the zero page.
    #0 ... in apply_gain(float*, int, float) gdb_segfault.cpp:6
    #1 ... in main gdb_segfault.cpp:12
```

不用单步、不用猜：**崩溃类型（SEGV 空指针）、出错行（第 6 行）、完整调用链**全有了。

ASan 更强的场景是"程序没崩、但内存悄悄写坏了"。经典的越界：

```cpp
// oob_asan.cpp
#include <vector>
#include <cstdio>

int main() {
    std::vector<int> frame{1, 2, 3};   // 3 个样本
    std::printf("%d\n", frame[3]);     // 越界！只有下标 0..2
    return 0;
}
```

```bash
g++ -std=c++17 -g -Wall -Wextra -pedantic -fsanitize=address,undefined -o oob_asan oob_asan.cpp
./oob_asan
```

真实输出（关键行）：

```
==4238==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x50200000001c ...
READ of size 4 at 0x50200000001c thread T0
    #0 ... in main oob_asan.cpp:7
0x50200000001c is located 0 bytes to the right of 12-byte region [...]
```

注意两件事：

- 这个程序**不开 ASan 时大概率正常打印一个垃圾值然后若无其事地退出**——越界在 release 版往往"看起来没事"，直到某天在客户机器上随机崩溃。ASan 的价值就是把静默腐坏变成当场爆炸。
- `heap-buffer-overflow ... 0 bytes to the right of 12-byte region` 连"你越到了合法内存右边 0 字节处"都说出来了。

`undefined`（UBSan）部分抓有符号溢出、除零等未定义行为。日常组合拳：

```bash
# 调试版：带检查
g++ -std=c++17 -g -O0 -Wall -Wextra -pedantic -fsanitize=address,undefined -o app_debug main.cpp
# 发布版：优化 + 去掉检查
g++ -std=c++17 -O2 -Wall -Wextra -pedantic -o app main.cpp
```

第 03 篇用 ASan 演示泄漏检测；第 04 篇的智能指针会从根上消灭大部分这类问题。

## 6. 头文件与源文件分离

Python 里 `import utils` 就完事；C++ 的模型是两层的：

- **头文件（`.h`）**：放**声明**——"有这么个函数，长这样"，接口清单。
- **源文件（`.cpp`）**：放**定义**——函数体。是四阶段翻译的基本单位（编译单元）。

```cpp
// audio_utils.h —— 声明（接口）
#pragma once            // 现代写法：防止头文件被重复包含
#include <cstddef>      // std::size_t

// 把一段样本整体乘以增益，返回处理后的最后一个样本
float apply_gain(float* samples, std::size_t n, float gain);
```

```cpp
// audio_utils.cpp —— 定义（实现）
#include "audio_utils.h"

float apply_gain(float* samples, std::size_t n, float gain) {
    for (std::size_t i = 0; i < n; ++i) {
        samples[i] *= gain;
    }
    return n > 0 ? samples[n - 1] : 0.0f;
}
```

```cpp
// main_split.cpp —— 只 include 声明，链接时才找到函数体
#include <cstdio>
#include "audio_utils.h"   // 声明在这里，定义在 audio_utils.cpp

int main() {
    float frame[3] = {0.5f, 0.25f, -1.0f};
    float last = apply_gain(frame, 3, 2.0f);
    std::printf("last=%g\n", last);   // 预期 last=-2
    return 0;
}
```

编译运行：

```bash
g++ -std=c++17 -Wall -Wextra -pedantic -c audio_utils.cpp -o audio_utils.o
g++ -std=c++17 -Wall -Wextra -pedantic -c main_split.cpp -o main_split.o
g++ audio_utils.o main_split.o -o split_demo && ./split_demo
```

预期输出：

```
last=-2
```

**`#pragma once` 是干嘛的**：头文件会被层层 include（main 同时 include A 和 B，A、B 都 include C 时，C 的内容会被粘两次）。同名声明两次没事，但**定义**两次就违反规则了。`#pragma once` 让头文件内容只粘贴一次；传统等价写法是 include guard（见自测题）。现代编译器都支持前者，认识两种、写一种即可。

**ODR（One Definition Rule，单一定义规则）一句话**：整个程序里，任何函数、变量、类型的定义最多出现一次（内联函数/模板等特例除外）。你以后碰到的 `multiple definition of ...` 链接错误就是 ODR 被违反的现场——典型原因是在头文件里写了非内联的函数定义。

> 顺带一提：`using namespace std;` 在小练习里图省事可以，但**不要写进头文件**——它会把整个 std 暴露给所有 include 它的人，极易造成重名冲突。本书全程用 `std::` 前缀。

## 常见坑

1. **忘了 `-std=c++17`**：默认标准偏旧，结构化绑定等直接编译失败，你会以为是自己写错了。
2. **Release 和 Debug 行为不一样**：不带 `-g` 的程序 gdb 里全是 `??`；`-O2` 优化后行号乱跳、变量被优化掉。调试请用 `-O0 -g`。
3. **警告视而不见**：`-Wsign-compare` 这类警告背后往往是真实的越界/死循环隐患。
4. **`undefined reference to ...`**：链接期错误，声明了但没链接它的 `.o` 或库——检查 `-L` `-l` 或 CMake 的 `target_link_libraries`。
5. **头文件里写函数定义**（非模板/非内联）：被两个 `.cpp` include 后违反 ODR，链接报 `multiple definition`。

## 小结

- 语音/推理引擎选 C++ 是为了性能与确定性；你的目标是读懂并使用这类代码库。
- 编译四阶段：预处理（粘贴/展开）→ 编译（翻译+检查）→ 汇编（生成 .o）→ 链接（拼装+填地址）。
- 日常命令：`g++ -std=c++17 -Wall -Wextra -pedantic`；调试加 `-g -O0`，测性能加 `-O2`。
- CMake 用一份文本描述工程，`cmake -S . -B build && cmake --build build` 走天下。
- 崩溃定位：gdb `run + bt`，或 `-fsanitize=address,undefined` 让错误自己报行号。
- 头文件放声明、源文件放定义；`#pragma once` 防重复包含；ODR = 定义全局唯一。

## 自测题

1. `#include <cstdio>` 在哪个阶段被处理？它把什么粘进了你的源码？
2. `undefined reference to apply_gain(...)` 大概率是哪个阶段的错误？两个最常见原因？
3. `-O0` 和 `-O2` 各适合什么场景？为什么调试要用 `-O0`？
4. `frame[3]` 越界但程序没崩、只输出了怪数字。为什么 ASan 能抓到而普通编译抓不到？
5. 为什么函数定义不要写在头文件里？写出与 `#pragma once` 等价的 include guard。
6. CMake 里 `CMAKE_BUILD_TYPE=Release` 大致等价于哪几个 g++ 旗子？

<details><summary>答案</summary>

1. 预处理阶段。它把 `<cstdio>` 头文件的**内容**（printf 等函数的声明）原样粘贴进源码，所以一行 include 展开成几千行。
2. 链接阶段。原因：① 忘了编译/链接定义该函数的 `.cpp`（或没加 `-l库名`）；② 声明与定义的签名不一致（比如一个用 `size_t` 一个用 `int`），C++ 名字修饰后的名字对不上。
3. `-O0` 编译快、不优化，行号变量与源码一致，适合开发调试；`-O2` 性能好，适合发布和性能测试。调试用 `-O0` 是因为优化会重排语句、把变量放进寄存器，单步和打印都失真。
4. 越界读是"未定义行为"：不开 ASan 时只是读到堆上相邻的垃圾数据，程序照常跑；ASan 在每次内存访问插入检查、分配区周围布置"毒药区"，一访问立刻报告类型、行号和分配位置。
5. 头文件被多个 `.cpp` include 后会产生多份定义，链接时违反 ODR 报 multiple definition。等价写法：`#ifndef AUDIO_UTILS_H` / `#define AUDIO_UTILS_H` / 头文件内容 / `#endif`。
6. 大致等价于 `-O2 -DNDEBUG`（NDEBUG 会关闭 `assert`）；对应地 `Debug` 等价于 `-g`（常配 `-O0`）。
</details>
