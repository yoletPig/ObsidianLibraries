## 一、为什么推理引擎必然多线程

一个典型的语音识别流水线，本质上是三条速度完全不同的流水线在同时工作：

```
采集线程(麦克风回调, 10ms 级实时性) ──环形缓冲区──→ 推理线程(几十~几百 ms/帧) ──结果队列──→ 输出线程
```

如果只用一个线程顺序执行：采集 → 推理 → 解码 → 输出，那么推理的 100ms 里，麦克风新来的音频就没人接——**音频是实时流，错过就永远丢了**。所以采集必须独立线程（回调不能被推理阻塞），推理独立线程（从队列里取帧慢慢算），线程之间靠线程安全的队列/环形缓冲区交接数据（第 13 篇实战就写一个）。Python 里 `threading` 受 GIL 限制，很多人靠多进程绕开；C++ 的 `std::thread` 是真正的操作系统线程，没有 GIL，这也是推理引擎都用 C++ 写的重要原因之一。

## 二、std::thread 基础：join 与 detach

启动线程就是把"可调用对象 + 参数"交给 `std::thread` 构造函数（本篇全部示例都用 `g++ -std=c++17 -Wall -pthread xxx.cpp -o xxx` 编译，**`-pthread` 必须加**）：

```cpp
#include <iostream>
#include <thread>

void work(int id) { std::cout << "线程 " << id << " 工作中\n"; }

int main() {
    std::thread t(work, 1);  // 启动新线程，立即返回
    std::cout << "主线程继续做自己的事\n";
    t.join();                // 等待 t 结束，才能销毁 t
    return 0;
}
```

三条铁律：

1. **`std::thread` 对象销毁前，必须已经 `join()` 或 `detach()`**，否则程序直接 `std::terminate()`。这和 RAII 的思想一脉相承——只不过 `std::thread` 自己不是 RAII 的，需要你保证。
2. **`join()` 是"等它干完"**：主线程阻塞直到子线程结束。
3. **`detach()` 是"撒手不管"**：线程变成后台精灵线程，和 `std::thread` 对象断开联系。

### detach 为什么危险

detach 之后，你就**失去了对这个线程的一切控制**：无法等待、无法取消、也不知道它是否还在跑。如果线程还引用着某个已经析构的局部变量或成员，就是悬空引用——比悬空指针更难查，因为它可能"大多数时候恰好没炸"。实战建议：**推理引擎里几乎不用 `detach()`**。采集、推理、解码线程的生命周期和引擎一样长，用成员变量持有 `std::thread`，在析构函数里设置停止标志后 `join()`；想"启动一个异步任务然后拿结果"，用后面的 `std::async` 或线程池。

## 三、数据竞争：一个真实的错误示例

两个线程对同一个 `int` 各自 `++` 100000 次，直觉上结果应该是 200000。先看代码（**警告：这是未定义行为，仅供演示，不要这样写**）：

```cpp
// race.cpp
#include <iostream>
#include <thread>

int counter = 0; // 两个线程共享，且没有任何保护

void increment_100k() {
    for (int i = 0; i < 100000; ++i) {
        ++counter; // 数据竞争：读-改-写 三步可能被打断
    }
}

int main() {
    std::thread t1(increment_100k), t2(increment_100k);
    t1.join(); t2.join();
    std::cout << "期望值 200000，实际值 " << counter << '\n';
    return 0;
}
```

用 **`-O0`** 编译运行（不加优化），在本文作者的机器上真实跑出的几组结果：

```
期望值 200000，实际值 110321
期望值 200000，实际值 113625
期望值 200000，实际值 100000
```

结果通常 **远小于 200000**。原因：`++counter` 在 CPU 层面是"读 → 加 1 → 写回"三步，两个线程可能同时读到同一个旧值，各自加 1 后写回——两次加法只生效了一次（丢失更新）；一旦两个线程开始以纳秒级步调交错，成片的更新都会被吞掉（所以才会低到 100000）。两个附注：其一，这是**未定义行为（UB）**，标准不保证任何结果——恰好在 `-O2` 下作者机器上多次都得到 200000，**测试通过不代表没有竞争，只代表这次没炸**；其二，推理引擎里这绝不是理论问题，丢帧计数器、会话状态、特征缓存……任何被多线程碰的普通变量都是这颗雷。下面两节给出两种正规修法：加锁，或用原子变量。

## 四、std::mutex + RAII 锁：lock_guard 与 unique_lock

`std::mutex` 的语义很朴素：同一时刻只有一个线程能持有它，别人 `lock()` 会阻塞。但手动配对 `lock()/unlock()` 会重蹈手动 `new/delete` 的覆辙（忘记解锁、异常路径漏解锁），所以**永远用 RAII 包装**（复习第 03 篇）：

```cpp
// mutex_demo.cpp
#include <iostream>
#include <mutex>
#include <thread>

int counter = 0;
std::mutex mtx; // 保护 counter 的互斥量

void increment_100k() {
    for (int i = 0; i < 100000; ++i) {
        std::lock_guard<std::mutex> lock(mtx); // 构造加锁，析构解锁
        ++counter;
    } // lock 离开作用域自动解锁，即使中途抛异常也不会忘记解锁
}

int main() {
    std::thread t1(increment_100k), t2(increment_100k);
    t1.join(); t2.join();
    std::cout << "期望值 200000，实际值 " << counter << '\n';
    return 0;
}
```

输出（稳定不变）：

```
期望值 200000，实际值 200000
```

两者的分工：**`std::lock_guard`** 构造即锁、析构即解锁，不能中途开/关，最轻量，临界区一杆子插到底就用它；**`std::unique_lock`** 稍重，但可以中途 `lock()/unlock()`、支持延迟加锁、可以移动，**条件变量 `wait()` 只接受它**——wait 内部要"解锁 → 睡眠 → 被唤醒后重新加锁"。性能提示：临界区越短越好，推理线程拿到锁只该做"取走一帧数据"，矩阵乘法放到锁外做。

## 五、std::atomic：无锁的简单计数

如果共享的只是一个变量（计数器、标志位、序号），动用互斥量有点杀鸡用牛刀。`std::atomic` 让对这个变量的**单个读-改-写操作整体不可分割**：

```cpp
// atomic_demo.cpp
#include <atomic>
#include <iostream>
#include <thread>

std::atomic<int> counter{0}; // 原子变量：并发访问不需要加锁

void increment_100k() {
    for (int i = 0; i < 100000; ++i) {
        ++counter; // 原子的读-改-写，整体不可分割
    }
}

int main() {
    std::thread t1(increment_100k), t2(increment_100k);
    t1.join(); t2.join();
    std::cout << "期望值 200000，实际值 " << counter.load() << '\n';

    // compare_exchange 的直觉：CAS——"如果它还是旧值，就换成新值"
    int expected = 200000;
    bool ok = counter.compare_exchange_strong(expected, 0);
    std::cout << "compare_exchange 是否成功: " << std::boolalpha << ok
              << "（成功时 counter 被写为 0），失败时 expected 保存当前实际值: "
              << counter.load() << '\n';
    return 0;
}
```

输出：

```
期望值 200000，实际值 200000
compare_exchange 是否成功: true（成功时 counter 被写为 0），失败时 expected 保存当前实际值: 0
```

要点：

- `++counter`、`counter.load()`、`counter.store(v)` 都是原子操作，结果精确。**`compare_exchange_strong`（CAS）一句话**："如果当前值等于 expected，就写成新值并返回 true；否则什么都不写，把当前值回填到 expected 并返回 false"——无锁数据结构的积木，本教程只用到这层直觉。
- 常用场景：`std::atomic<bool> stop_flag_` 让推理线程优雅退出（第 13 篇会见到姊妹版 `closed_`）；`std::atomic<int> frames_dropped_` 统计丢帧。
- **`atomic` 只解决"单个操作"的原子性**，需要"同时更新两个变量"或"保护一整段逻辑"时仍要 mutex。

## 六、条件变量：生产者-消费者（音频流水线的骨架）

计数器可以无锁，但**队列不行**：容器是多步修改的复合状态，必须 mutex 保护；而"队列空时消费者怎么办"则要条件变量 `std::condition_variable`——它让线程**睡眠等待某个条件成立，被别人唤醒后再检查**，而不是空转轮询烧 CPU。

一个完整可运行的音频帧生产者-消费者示例（16kHz 采样、480 样本一帧 = 30ms）：

```cpp
// prodcons.cpp
#include <cmath>
#include <condition_variable>
#include <deque>
#include <iostream>
#include <mutex>
#include <thread>
#include <vector>

constexpr int kSampleRate = 16000;
constexpr int kFrameSize = 480; // 30 ms @ 16kHz
constexpr int kNumFrames = 8;   // 生产者总共产 8 帧

std::deque<std::vector<float>> queue_; // 已就绪的音频帧队列
std::mutex mtx_;
std::condition_variable cv_;
bool producer_done_ = false; // 生产者收工标志

// 生产者：把每个音频帧推进队列，就像音频采集回调往里送数据
void producer() {
    for (int f = 0; f < kNumFrames; ++f) {
        std::vector<float> frame(kFrameSize);
        for (int i = 0; i < kFrameSize; ++i) {
            frame[i] = 0.5f * std::sin(2.0f * 3.14159f * 440.0f *
                                       (f * kFrameSize + i) / kSampleRate);
        }
        {
            std::lock_guard<std::mutex> lock(mtx_);
            queue_.push_back(std::move(frame)); // 移动，避免拷贝大块样本
        }
        cv_.notify_one(); // 通知消费者：有新帧了
    }
    {
        std::lock_guard<std::mutex> lock(mtx_);
        producer_done_ = true;
    }
    cv_.notify_all(); // 让所有还在等待的消费者醒来看收工标志
}

// 消费者：像推理线程一样，一帧一帧取出来"处理"（这里只算峰值）
void consumer() {
    int frame_id = 0;
    while (true) {
        std::vector<float> frame;
        {
            std::unique_lock<std::mutex> lock(mtx_); // 等条件要用 unique_lock
            // wait 的第二步（lambda）防止虚假唤醒和收工漏判
            cv_.wait(lock, [] { return !queue_.empty() || producer_done_; });
            if (queue_.empty()) {
                break; // 队列空且生产者已收工：干净退出
            }
            frame = std::move(queue_.front());
            queue_.pop_front();
        } // 在锁外处理数据，尽量缩短临界区
        float peak = 0.0f;
        for (float s : frame) peak = std::max(peak, std::abs(s));
        std::cout << "[消费者] 处理第 " << frame_id++ << " 帧，峰值 = "
                  << peak << '\n';
    }
}

int main() {
    std::thread p(producer), c(consumer);
    p.join(); c.join();
    std::cout << "所有帧处理完毕\n";
    return 0;
}
```

输出（8 帧全部处理，帧序号固定；每次运行帧与帧之间的真实时序可能不同，但结果一致；第 1~6 帧输出相同，此处省略）：

```
[消费者] 处理第 0 帧，峰值 = 0.5
[消费者] 处理第 7 帧，峰值 = 0.5
所有帧处理完毕
```

读懂三个关键机制：

1. **`wait(lock, pred)`** 等价于 `while (!pred()) cv.wait(lock);`，谓词必不可少，原因有二：**虚假唤醒**——OS 允许 wait 在没人 notify 时醒来，必须重新检查条件；**收工竞争**——消费者检查完"队列空"到进入 wait 之间，生产者可能刚好推入数据并 notify，不重查条件这次通知就永远丢了。带谓词的 wait 把"检查 + 睡眠"原子地放在锁的保护下，两个问题一起解决。
2. **改状态必须先拿锁**：先 `push_back` 再 `notify_one`；收工标志同理，改完 `notify_all`。**收工协议**：光靠"队列空"不能退出（可能下一秒就有新帧），必须加"生产者已收工"标志，两者结合才是安全退出条件。

## 七、死锁与避免

死锁的教科书场景：线程 1 拿了锁 A 想要锁 B，线程 2 拿了锁 B 想要锁 A，互相等到天荒地老。有两条系统性防线：

**防线一：统一加锁顺序。** 只要所有线程都以相同顺序获取多把锁（比如永远先 A 后 B），循环等待就构不成。

**防线二：`std::scoped_lock`（C++17）。** 需要一次拿多把锁时，用它一把抓，内部算法保证不死锁：

```cpp
// scoped_lock_demo.cpp
#include <chrono>
#include <iostream>
#include <mutex>
#include <thread>

std::mutex mtx_a, mtx_b;

// 正确做法：统一锁顺序（两边都先 a 后 b）
void worker_fixed(int id) {
    std::lock_guard<std::mutex> la(mtx_a);
    std::this_thread::sleep_for(std::chrono::milliseconds(1)); // 制造交错窗口
    std::lock_guard<std::mutex> lb(mtx_b);
    std::cout << "线程 " << id << " 同时持有 a 和 b，无死锁\n";
}

// 另一种正确做法：std::scoped_lock 一次性锁住多把锁，内部避免死锁
void worker_scoped(int id) {
    std::scoped_lock lock(mtx_a, mtx_b); // C++17，构造时全拿，析构时全放
    std::cout << "scoped_lock 线程 " << id << " 完成\n";
}

int main() {
    std::thread t1(worker_fixed, 1), t2(worker_fixed, 2);
    t1.join(); t2.join();
    std::thread t3(worker_scoped, 3), t4(worker_scoped, 4);
    t3.join(); t4.join();
    return 0;
}
```

输出：

```
线程 1 同时持有 a 和 b，无死锁
线程 2 同时持有 a 和 b，无死锁
scoped_lock 线程 3 完成
scoped_lock 线程 4 完成
```

另外两条工程习惯：**锁内绝不调用未知代码**（回调、虚函数、别的模块接口——它可能反过来再拿你的锁）；一把 mutex 只保护一个明确的数据结构，用注释写清楚"这把锁保护谁"。

## 八、std::async / std::future / std::promise 快速一览

这一家子解决"把一个任务扔到后台，稍后拿结果"：**`std::async(std::launch::async, f, args...)`** 启动 `f`，立刻返回 `std::future<R>`；**`std::future`** 是"未来才会有值"的占位符，`get()` 阻塞到结果就绪（只能调用一次）；**`std::promise`** 是 future 的写端，当"结果就绪的时刻"由你自己的代码决定时，在工作线程里 `set_value()`，另一端 `get()`。

```cpp
// async_demo.cpp
#include <chrono>
#include <future>
#include <iostream>
#include <mutex>
#include <thread>

// ---------- 1. std::async：把任务丢到后台，用 future 收结果 ----------
double simulate_inference(int n) { // 模拟一段耗时的推理
    double sum = 0.0;
    for (int i = 0; i < n; ++i) sum += 0.001 * i;
    return sum;
}
// ---------- 2. std::promise：手动在某个时点"塞"结果给等待者 ----------
void worker_with_promise(std::promise<int> p) {
    std::this_thread::sleep_for(std::chrono::milliseconds(10));
    p.set_value(42); // 结果就绪的时刻由这里决定
}
// ---------- 3. std::call_once：无论多少线程，只初始化一次 ----------
std::once_flag model_flag;
void load_model(const char* name) { std::cout << "加载模型: " << name << '\n'; }
void thread_body() { std::call_once(model_flag, load_model, "asr-cn-v1"); }

int main() {
    std::future<double> f = std::async(std::launch::async, simulate_inference, 1000);
    std::cout << "主线程可以先干别的……\n";
    std::cout << "async 结果 = " << f.get() << '\n'; // get() 只能调用一次

    std::promise<int> p;
    std::future<int> pf = p.get_future();
    std::thread t(worker_with_promise, std::move(p)); // promise 只能移动
    std::cout << "promise 结果 = " << pf.get() << '\n';
    t.join();

    std::thread t1(thread_body), t2(thread_body), t3(thread_body);
    t1.join(); t2.join(); t3.join(); // "加载模型"只会打印一次
    return 0;
}
```

输出：

```
主线程可以先干别的……
async 结果 = 499.5
promise 结果 = 42
加载模型: asr-cn-v1
```

三个一句话备忘：`std::async` 用 `std::launch::async` 显式要求"新线程执行"，不写的话实现可以延迟到 `get()` 时同步执行，容易踩坑；`future.get()` 只能调一次，`promise` 只能 `set_value` 一次且**只能移动**（回忆第 05 篇：它独占"设置结果"的权利）；**`std::call_once` 一句话**——多个线程同时到达时，`call_once(flag, f, ...)` 保证 `f` 在整个程序里只被执行一次，适合"模型只加载一次"这类懒初始化。

## 常见坑

1. **忘记 `-pthread`**：能编译（甚至能链接），但运行时表现怪异或崩溃。凡用了 `<thread>`/`<mutex>` 一律加上。
2. **忘 join 导致 `std::terminate`**；**detach + 引用局部变量**则造成偶发悬空崩溃，两类都是最难的 bug。
3. **wait 不带谓词**：虚假唤醒或通知丢失，消费者永久睡眠。永远写 `cv.wait(lock, pred)` 两参数版。
4. **改共享状态没拿锁**：状态修改必须在锁内，否则存在"检查-睡眠"窗口丢通知；同理**临界区不做重活**，推理计算放锁外。
5. **认为"测试通过 = 没有竞争"**：竞争是 UB，`-O2` 下可能恰好不发作（见第三节真实数据）；**用 `atomic` 保护复合操作**同理——两个 atomic 变量的更新合在一起不是原子的，该上锁还是要上锁。

## 小结

- 推理引擎 = 采集线程 + 推理线程 + 后处理线程，靠线程安全队列交接数据；音频实时流不容许单线程串行。
- `std::thread` 销毁前必须 `join()` 或 `detach()`；引擎生命周期线程用成员变量 + 析构时 join，不用 detach。
- 多线程共享的普通变量并发写是 UB；单变量计数用 `std::atomic`，复合逻辑用 `std::mutex` + RAII 锁（`lock_guard` / `unique_lock`）。
- 生产者-消费者：mutex 保队列，`wait(lock, pred)` 保等待，"队列空 + 收工标志"保退出；多锁场景统一顺序或用 C++17 `std::scoped_lock`。`async/future/promise` 是"后台任务 + 取结果"三件套，`call_once` 保证一次初始化；第 13 篇将把这些与模板、RAII 组装成真正的 `RingBuffer`。

## 自测题

1. `std::thread` 对象析构前既没有 `join()` 也没有 `detach()`，会发生什么？
2. `race.cpp` 在 `-O2` 下多次运行都输出 200000，能否断定程序没有数据竞争？
3. `std::lock_guard` 和 `std::unique_lock` 怎么选？条件变量的 `wait` 只接受哪一个？
4. `cv.wait(lock, pred)` 中谓词 `pred` 的两个作用是什么？
5. 生产者改完共享队列后调用 `notify_one`，若消费者恰好在"检查条件"和"进入睡眠"之间，通知会丢吗？为什么带谓词的 wait 不怕？
6. 两个线程分别先拿 A 后拿 B、先拿 B 后拿 A，写出两种 C++17 的修法。
7. `counter.compare_exchange_strong(expected, v)` 返回 false 时，`expected` 的值发生了什么？
8. `std::async(f)` 不指定 launch 策略有什么隐患？怎么写才稳妥？

### 答案

1. 程序直接调用 `std::terminate()` 终止。
2. 不能。数据竞争是未定义行为，"恰好得到正确结果"恰恰是 UB 的典型表现，随时可能换环境后发作。
3. 临界区一锁到底用 `lock_guard`（更轻）；需要中途解锁/重锁、延迟加锁或配合条件变量时用 `unique_lock`；`wait` 只接受 `unique_lock`。
4. 防虚假唤醒（醒来无条件重查）和防通知丢失（检查与睡眠在锁保护下原子进行）。
5. 会丢——但这正是谓词的作用：wait 内部在持有锁的状态下重新求值 `pred`，只要状态已在锁内改过，重新检查就能看到，不会睡死。
6. 方法一：让两个线程都统一"先 A 后 B"；方法二：改用 `std::scoped_lock lock(mtx_a, mtx_b);` 一次性获取两把锁。
7. `counter` 保持原值，函数把 counter 的当前实际值写回 `expected`，返回 false。
8. 不指定时实现可选择推迟执行，任务可能拖到 `get()`/析构时才在当前线程跑，破坏"并发执行"预期；应显式写 `std::launch::async`。
