## 1. 为什么 RAII 需要标准化的指针

03 篇说过：把资源包进一个类的析构函数里，就永远不会忘记释放。那么问题来了——

```cpp
void process() {
    float* data = new float[48000];  // 想用 RAII，谁来调用 delete[]？
    // ... 中间任何一处 return / throw 都会跳过 delete[]
    delete[] data;
}
```

裸指针自己不是 RAII：它没有析构函数。你必须**手工**记住在哪里释放，而函数一旦有多个出口、或者异常会向上传播，手工释放必然出错。

解决思路很直接：**造一个很小的类，里面只有一个指针，析构函数负责释放**。这就是智能指针。C++ 标准库提供了两种性格截然不同的：

| | `unique_ptr` | `shared_ptr` |
|---|---|---|
| 所有权 | 独占，同一时刻只有一个主人 | 共享，计数归零才释放 |
| 可拷贝 | 否（只能移动） | 是 |
| 额外开销 | 零（不比裸指针大） | 一个控制块 + 原子计数 |
| 心智模型 | "这块资源是我的" | "这块资源我们共用" |

## 2. `std::unique_ptr`：独占所有权

### 为什么先学它

语音引擎里大多数资源天然是**独占**的：一条音频管道上一个环节处理完的 `AudioBlock`，要么归下一个环节，要么销毁，不存在"两个环节同时拥有"的合法状态。这类场景用 `unique_ptr`，让编译器替你执行"只能有一个主人"的规矩。

### 怎么写

```cpp
#include <memory>
auto block = std::make_unique<AudioBlock>(48000, 1024);  // 永远别写 new AudioBlock(...)
```

- **创建用 `std::make_unique`**（C++14 起）：一行完成分配 + 构造，且不会把裸指针短暂暴露出来。
- **所有权转移用 `std::move`**：`unique_ptr` 禁止拷贝，把"转移所有权"变成一个显式的、在代码里看得见的动作。
- **按值传入 `unique_ptr` 参数 = 声明"我要接管它"**；按引用或传裸指针/引用 = "我只借用"。

### 可运行示例：音频块在函数间转移

```cpp
#include <iostream>
#include <memory>
#include <utility>
#include <vector>

// 一个音频数据块：这里用两个成员代表"真实音频数据"，先不碰裸指针
class AudioBlock {
public:
    AudioBlock(int sample_rate, int frames)
        : sample_rate_(sample_rate), frames_(frames) {
        std::cout << "  AudioBlock 构造: " << frames_ << " 帧\n";
    }
    ~AudioBlock() { std::cout << "  AudioBlock 析构: " << frames_ << " 帧\n"; }

    int sample_rate() const { return sample_rate_; }
    int frames() const { return frames_; }

private:
    int sample_rate_;
    int frames_;
};

// 接收方"接管"所有权：参数按值传 unique_ptr，签名就写明了"我要拿走它"
void consume(std::unique_ptr<AudioBlock> block) {
    std::cout << "  处理 " << block->frames() << " 帧 @ "
              << block->sample_rate() << " Hz\n";
}  // block 离开作用域，AudioBlock 自动释放

std::unique_ptr<AudioBlock> produce() {
    // 局部 unique_ptr 返回时自动"上浮"为移动，不需要写 std::move
    return std::make_unique<AudioBlock>(48000, 1024);
}

int main() {
    auto block = std::make_unique<AudioBlock>(48000, 1024);
    // auto b2 = block;          // 编译错误：unique_ptr 不可拷贝，所有权不能复制
    consume(std::move(block));   // 转移所有权出去
    std::cout << "  转移后 block 是否为空: " << std::boolalpha
              << (block == nullptr) << '\n';

    auto from_factory = produce();
    std::cout << "  工厂产物: " << from_factory->frames() << " 帧\n";

    // unique_ptr 可以放进容器：音频块队列天然是"独占"语义
    std::vector<std::unique_ptr<AudioBlock>> queue;
    queue.push_back(std::make_unique<AudioBlock>(16000, 256));
    queue.push_back(produce());
    std::cout << "  队列长度: " << queue.size() << '\n';
    return 0;
}  // 队列析构 -> 所有块自动释放，全程没有出现 new/delete
```

预期输出（注意每个对象恰好构造一次、析构一次）：

```text
  AudioBlock 构造: 1024 帧
  处理 1024 帧 @ 48000 Hz
  AudioBlock 析构: 1024 帧
  转移后 block 是否为空: true
  AudioBlock 构造: 1024 帧
  工厂产物: 1024 帧
  AudioBlock 构造: 256 帧
  AudioBlock 构造: 1024 帧
  队列长度: 2
  AudioBlock 析构: 256 帧
  AudioBlock 析构: 1024 帧
  AudioBlock 析构: 1024 帧
```

三个要点：

1. **零开销不是口号**：默认删除器下，`sizeof(std::unique_ptr<T>) == sizeof(T*)`，解引用也不再额外间接——它就是"会自动析构的裸指针"，所以语音热路径上随便用。
2. **返回值不用 `std::move`**：`produce()` 里的返回是隐式移动，写了 `std::move(return xxx)` 反而会禁用编译器的返回值优化。
3. **自定义删除器一句话**：`std::unique_ptr<FILE, decltype(&fclose)> f(fp, &fclose);`——把"怎么释放"作为第二个模板参数（或构造参数）传进去即可，管理 C 接口资源（音频设备句柄、`FILE*`）时用。`shared_ptr` 版本运行一下看看：

```cpp
#include <cstdio>
#include <iostream>
#include <memory>

int main() {
    // 管理 C 接口资源（比如音频设备句柄）时，告诉 shared_ptr "怎么关"
    std::shared_ptr<std::FILE> file(
        std::fopen("/tmp/cpp_verify_456/demo_out.txt", "w"),
        [](std::FILE* f) {  // 自定义删除器：析构时自动调用
            if (f != nullptr) std::fclose(f);
            std::cout << "  自定义删除器：文件已关闭\n";
        });

    if (file) { std::fputs("hello from shared_ptr\n", file.get()); }
    std::cout << "  main 即将结束\n";
    return 0;
}  // 离开作用域时自动调用上面的 lambda，不需要手写 fclose
```

预期输出（关闭动作发生在 `main` 之后、程序退出之前）：

```text
  main 即将结束
  自定义删除器：文件已关闭
```

## 3. `std::shared_ptr`：共享所有权

### 为什么需要它

有些资源确实要共享：ASR 模型的权重加载要几秒，十几个推理任务应该共用同一份，而不是各自加载。**"最后一个用完的人负责释放"**——这正是引用计数的语义。

### 控制块与开销（必须心里有数）

`shared_ptr` 比裸指针多两个东西，合称**控制块**：

- **强引用计数**：有多少个 `shared_ptr` 共享这个对象；
- **弱引用计数**：有多少个 `weak_ptr` 在观察（下一节）。

每次拷贝/析构 `shared_ptr` 都要对计数做**原子操作**（加减 + 内存屏障）。所以：

- 拷贝不是免费的，在极热的循环里按 `const&` 传 `shared_ptr`；
- `make_shared<T>(...)` 把对象和控制块放进**同一次分配**，比 `shared_ptr<T>(new T(...))` 少一次分配、对缓存也更友好，**永远优先用它**。

### 线程安全性（准确表述，面试高频）

- **引用计数本身是原子的**：多个线程同时拷贝/析构**各自持有的** `shared_ptr` 副本，计数不会乱，对象不会提前释放也不会泄漏。
- **同一个 `shared_ptr` 对象不是线程安全的**：两个线程同时读写**同一个** `shared_ptr` 变量（一个赋新值、一个拷贝）是数据竞争，需要加锁或用 `std::atomic<std::shared_ptr<T>>`（C++20）。
- **被管理的对象完全不受保护**：`shared_ptr<ModelWeights>` 只保证"权重在你用的时候活着"，两个线程同时读权重没问题，但一读一写照样要自己加锁。

一句话：**shared_ptr 保护"这个对象还存在吗"，不保护"这个对象的内容"**。

### 可运行示例

```cpp
#include <iostream>
#include <memory>
#include <string>
#include <utility>

// 模型权重：加载昂贵，多个推理任务想共享同一份
class ModelWeights {
public:
    explicit ModelWeights(std::string name) : name_(std::move(name)) {
        std::cout << "  加载模型权重: " << name_ << "（昂贵的 I/O 只发生这一次）\n";
    }
    ~ModelWeights() { std::cout << "  释放模型权重: " << name_ << '\n'; }
    const std::string& name() const { return name_; }

private:
    std::string name_;
};

// 只"借用"权重参与推理：按 const 引用传 shared_ptr，引用计数不变
// （注意参数类型要与实参一致，若写成 shared_ptr<const ModelWeights> 会临时 +1，见"常见坑"）
void infer(const std::shared_ptr<ModelWeights>& weights) {
    std::cout << "  推理任务借用权重: " << weights->name()
              << "，当前引用计数 = " << weights.use_count() << '\n';
}

int main() {
    auto shared = std::make_shared<ModelWeights>("whisper-tiny");
    std::cout << "  创建后 use_count = " << shared.use_count() << '\n';

    {
        auto reader = shared;  // 拷贝 shared_ptr：计数 +1，权重本身没有复制
        std::cout << "  拷贝一份后 use_count = " << shared.use_count() << '\n';
        infer(shared);
    }  // reader 析构：计数 -1，权重仍然活着

    std::cout << "  离开作用域后 use_count = " << shared.use_count() << '\n';
    std::cout << "  主流程继续使用权重: " << shared->name() << '\n';
    return 0;
}  // 最后一个 shared_ptr 析构，权重才真正释放
```

预期输出：

```text
  加载模型权重: whisper-tiny（昂贵的 I/O 只发生这一次）
  创建后 use_count = 1
  拷贝一份后 use_count = 2
  推理任务借用权重: whisper-tiny，当前引用计数 = 2
  离开作用域后 use_count = 1
  主流程继续使用权重: whisper-tiny
  释放模型权重: whisper-tiny
```

`use_count` 随拷贝 +1、随析构 -1，归零时权重才析构——这就是"最后一个走的人关灯"。

## 4. `std::weak_ptr`：打破循环引用

### 泄漏现场

引用计数有个著名盲区：**两个对象用 `shared_ptr` 互相指着，计数就永远到不了 0**。下面这个例子真的会泄漏（本节两个示例都编译运行验证过，泄漏版还用 AddressSanitizer 确认了 `160 byte(s) leaked in 2 allocation(s)`）：

```cpp
#include <iostream>
#include <memory>
#include <string>
#include <utility>

// 声学场景树：parent 与 child 互相指向，且都用 shared_ptr
// 运行后你会发现：看不到任何析构输出 —— 两个结点互相扣留，内存泄漏了
struct Node {
    std::string name;
    std::shared_ptr<Node> parent;  // 指向父结点
    std::shared_ptr<Node> child;   // 指向子结点

    explicit Node(std::string n) : name(std::move(n)) {
        std::cout << "  构造 " << name << '\n';
    }
    ~Node() { std::cout << "  析构 " << name << '\n'; }
};

// 作用域结束后深调用一层，冲刷栈上陈旧指针，LeakSanitizer 才能确认"不可达"（见正文）
__attribute__((noinline)) void scrub() {
    volatile int buf[512];
    for (volatile int& x : buf) {
        x = 0;
    }
}

void run() {
    auto parent = std::make_shared<Node>("parent");
    auto child = std::make_shared<Node>("child");
    parent->child = child;   // child 的引用计数变为 2
    child->parent = parent;  // parent 的引用计数变为 2
}  // 局部变量 parent/child 析构：计数各自减回 1，但永远到不了 0

int main() {
    std::cout << "进入作用域\n";
    run();
    scrub();
    std::cout << "main 结束 —— 注意：上面没有出现任何析构输出，泄漏了\n";
    return 0;
}
```

预期输出——**没有任何"析构"字样**，这就是泄漏的直接证据：

```text
进入作用域
  构造 parent
  构造 child
main 结束 —— 注意：上面没有出现任何析构输出，泄漏了
```

用 `g++ -std=c++17 -fsanitize=address -g` 编译运行，LeakSanitizer 通常会报告 `160 byte(s) leaked in 2 allocation(s)`（本例为此特意加了冲刷栈的 `scrub()`）。如果你的环境没报，也不矛盾——栈上残留的陈旧指针可能让对象"看似仍可达"而漏报；**该跑的析构没跑，才是泄漏的铁证**。

### `weak_ptr` 修复版

修复原则只有一句话：**所有权方向用 `shared_ptr`，回指方向用 `weak_ptr`**。`weak_ptr` 观察对象但不增加计数，用之前通过 `lock()` 尝试"升级"成 `shared_ptr`：

```cpp
#include <iostream>
#include <memory>
#include <string>
#include <utility>

// 与泄漏版唯一的区别：回指方向（child -> parent）改用 weak_ptr
// 规则："拥有"用 shared_ptr，"知道对方在哪"用 weak_ptr
struct Node {
    std::string name;
    std::weak_ptr<Node> parent;    // 弱引用：不增加引用计数
    std::shared_ptr<Node> child;   // 强引用：拥有子结点

    explicit Node(std::string n) : name(std::move(n)) {
        std::cout << "  构造 " << name << '\n';
    }
    ~Node() { std::cout << "  析构 " << name << '\n'; }
};

int main() {
    std::cout << "进入作用域\n";
    {
        auto parent = std::make_shared<Node>("parent");
        auto child = std::make_shared<Node>("child");
        parent->child = child;   // child 计数 = 2
        child->parent = parent;  // parent 计数不变（weak 不计数）
        std::cout << "离开作用域\n";
    }
    std::cout << "main 结束 —— 两个结点都正常析构了\n";
    return 0;
}
```

预期输出——两个析构都出现了：

```text
进入作用域
  构造 parent
  构造 child
离开作用域
  析构 parent
  析构 child
main 结束 —— 两个结点都正常析构了
```

`lock()` 的用法：`if (auto p = child->parent.lock()) { /* p 是临时 shared_ptr，安全使用 */ }`——对象可能已被销毁，`lock()` 返回空指针，绝不会出现悬空访问。语音系统里"推理任务 → 模型权重"的回指、"回调注册者 → 引擎"的引用，都是 `weak_ptr` 的典型位置。

## 5. 所有权设计经验法则

1. **默认 `unique_ptr`，有理由才升级 `shared_ptr`**。`unique_ptr` 可以隐式转换成 `shared_ptr`（反过来不行），先独占后共享的路是通的。
2. **判断问题只有一个："这个资源要不要多个主人？"** 不需要，就 `unique_ptr`。语义上"转移"（音频块沿管道流动）是 `unique_ptr` + `std::move`。
3. **接口签名泄露所有权设计**：
   - `void sink(std::unique_ptr<T> p)` —— 接管；
   - `T* borrow(...)` / `const T& borrow(...)` —— 只借用，不拥有；
   - `void share(std::shared_ptr<T> p)` —— 分享一份所有权（按值才计数）。
4. **函数内部临时计算用 `std::vector`/值语义即可**，不必事事上智能指针。
5. **看到 `shared_ptr` 要问一句"这真的需要共享吗"**——很多代码库里一半的 `shared_ptr` 其实只是作者不敢用 `unique_ptr`；管理 C 接口句柄（如 `pa_simple*`、`FILE*`）时给智能指针配自定义删除器，让 RAII 覆盖非内存资源。

## 6. 常见坑

- **`shared_ptr` 参数类型不完全一致会偷偷计数**：本篇示例里 `infer` 若声明为 `const std::shared_ptr<const ModelWeights>&`，传入 `shared_ptr<ModelWeights>` 会因隐式转换生成一个临时 `shared_ptr`，`use_count` 凭空 +1（实测如此）。要么类型写一致，要么直接按值传。
- **循环引用不报错、不崩溃，只是安静泄漏**：ASan 的 LeakSanitizer 通常能报出来，但它依赖"对象不可达"判定——栈上残留指针可能让对象"看起来仍可达"而漏报（本篇泄漏示例因此加了一个冲刷栈的 `scrub()`）。最可靠的证据永远是：**析构函数该跑没跑**。
- **`use_count()` 在多线程下只是近似值**：别的线程可能随时增减计数，它适合调试和日志，不适合做业务判断。
- **`make_shared` 的一个副作用**：对象和控制块同一块内存，只要有 `weak_ptr` 活着，整块内存都不能还——大对象 + 长命 `weak_ptr` 场景要留意。
- **`get()` 拿到的裸指针交给别人管理就等于双份所有权**：两个主人各自 delete，必然 double-free；`shared_ptr<T> a(raw); shared_ptr<T> b(raw);` 同理会造出两个独立控制块，双重释放。

## 7. 小结

- RAII 的"自动释放"需要载体，智能指针就是标准化的载体：`unique_ptr` 独占且零开销，`shared_ptr` 共享但带控制块与原子计数。
- `unique_ptr` 表达"转移"，`shared_ptr` 表达"共用"，`weak_ptr` 表达"知道但不拥有"，接口签名应当如实反映这三者。
- `shared_ptr` 只保证对象存活期，不保护对象内容；引用计数原子，同一个 `shared_ptr` 变量仍需同步。
- 循环引用是 `shared_ptr` 的结构性盲区：所有权单向，回指用 `weak_ptr`。

## 自测题

1. 为什么 `unique_ptr` 不能拷贝却可以放进 `std::vector` 并 `push_back`？
   <details><summary>答案</summary>
   `push_back` 接收的是右值（临时对象或 `std::move` 的结果），走的是**移动**而非拷贝；容器元素的所有权转移是移动语义，不违反"独占"。直接写 `v.push_back(ptr)`（`ptr` 是左值）才会编译报错，需要 `std::move(ptr)`。
   </details>

2. `shared_ptr` 的引用计数是原子的，那两个线程同时写"同一个 `shared_ptr` 变量"安全吗？
   <details><summary>答案</summary>
   不安全。原子性保护的是计数，不保护 `shared_ptr` 变量本身：一个线程赋值、另一个线程同时拷贝它属于数据竞争（未定义行为）。各线程只操作自己持有的副本则完全安全。
   </details>

3. 下面的代码泄漏吗？为什么？
   `auto w = std::make_shared<int>(42); std::weak_ptr<int> obs = w; w.reset();`
   <details><summary>答案</summary>
   不泄漏。`weak_ptr` 不维持强计数，`w.reset()` 后强计数归零，`int` 的析构函数立即运行、对象宣告死亡，`obs.expired()` 变为 `true`；但注意 `make_shared` 把对象和控制块放在同一块内存里，这块内存要等 `obs` 也析构、弱计数归零后才真正归还。
   </details>

4. 音频处理管道中，"采集线程产出的 `AudioBlock` 交给识别线程，处理完销毁"应该用哪种指针？接口签名怎么写？
   <details><summary>答案</summary>
   `std::unique_ptr<AudioBlock>`，队列用 `std::vector<std::unique_ptr<AudioBlock>>`（或加锁的队列），投递接口 `void enqueue(std::unique_ptr<AudioBlock> block)`——按值传参表明接管所有权。任何时候不需要两个环节同时"拥有"同一块数据。
   </details>
