## 1. 第一性原理：为什么需要"消息集"

上周的收尾悬念：V2X 广播的是"我在哪、多快、朝哪"，但这些信息要用**双方都认识的编码**才能被理解。设想路侧 RSU 的感知栈（Stage 1-5 的全部产出）输出了一个目标：

```
track_id=101, cls=car, pos=(63.20 m, -12.45 m), vel=(11.30, 0.45) m/s, L=4.6 m, W=1.9 m, conf=0.94
```

隔壁车道的车收到这段话——然后呢？`pos` 是相对哪个原点的坐标？`conf` 是 0~1 还是 0~100？`track_id` 明天还是同一个意思吗？**消息集（message set dictionary）标准要解决的就是这个问题：把感知/交通信息编码成一组字段名、分辨率、取值范围、更新频率全部公开固定的结构，让陌生节点无需协商即可互译。**

三份最重要的消息集标准：

| 标准 | 出身 | 覆盖消息 |
| --- | --- | --- |
| **SAE J2735**（美国，V2X Communications Message Set Dictionary，ASN.1 编写） | DSRC 时代起步，现用于两国阵营的北美部署 | BSM（基本安全消息）、SPAT、MAP、SRM、EM 等 |
| **T/CSAE 53-2020**《合作式智能运输系统 车用通信系统应用层及应用数据交互标准（第一阶段）》（中国汽车工程学会，2017 年初版、2020 年修订） | 中国 C-V2X 应用层事实标准（第一阶段 17 个场景） | BSM、**RSM**（路侧安全消息）、RSI（路侧信息）、SPAT、MAP 等 |
| **ETSI TR 103 562**（欧洲，2019，CPS 分析报告） | 欧洲协同感知路线 | 定义 **CPM**（Collective Perception Message，协同感知消息）的分析基础——让每个节点广播"我**看到的目标**列表"（后续规范性文档为 ETSI TS 103 324） |

一张图记住分工：BSM 说"**我自己**在哪"，RSM/CPM 说"**我看见的东西**在哪"。前者是车自我陈述，后者正是路侧感知系统的输出接口——你做的每一个 3D 框，最终都以 RSM/CPM 类消息的形式离开机房。

**接口思维**是本周的核心方法论：消息集就是感知系统与外部世界之间的 API。写 API 的规矩在这里全部适用——字段语义要文档化、单位分辨率要写死、版本要管理、向后兼容要考虑。区别只在于：这个 API 的"调用方"是素不相识的路过车辆，出错时你无法回滚、无法发补丁，**字段定义错一个分辨率，纠错成本是全城所有 RSU 的固件升级**。

## 2. 打开 J2735：BSM Part I 逐字段解读

BSM（Basic Safety Message，基本安全消息）是 J2735 中最核心的消息：车辆以 **10 Hz** 广播自己的状态。Part I（coreData）是必选的核心字段：

| 字段 | 含义 | 分辨率/范围 | 为什么是它 |
| --- | --- | --- | --- |
| `msgCnt` | 消息计数器 | 0~127 循环 | 接收端据此识别"丢了几条/是否乱序" |
| `id` | 临时车辆 ID | 4 字节（随机分配，非车牌） | 跨消息关联同一辆车；随机性防跟踪隐私攻击 |
| `secMark` | 分钟内毫秒标记 | 0~60999 ms | 与 msgCnt 一起确定消息的精确时刻 |
| `lat`, `lon` | 纬度/经度 | 0.1 微度（1e-7 度） | 绝对位置；1e-7 度 ≈ 1.1 cm，够用 |
| `elev`, `accuracy` | 高程与定位精度 | — | 告诉接收方"我的 GPS 多可信" |
| `speed` | 标量速度 | **0.02 m/s** 步长 | 时延外推补偿的速度来源 |
| `heading` | 航向 | **0.0125°** 步长 | 区分方向（速度是标量，没方向） |
| `angle` | 方向盘转角 | 1.5° 步长 | 预判转向 |
| `size`（width/length） | 车辆宽/长 | cm | 接收端算碰撞余量 |

（Part II 是可选扩展：事件标志、路径预测、RTK 高精位置等，本系列不展开。）

### 2.1 为什么到处都是"定点数"而不是浮点

J2735 用**定点量化**（fixed-point encoding）：真实值 = 存储整数 × 分辨率。`speed = 565` 表示 11.30 m/s。三个理由：

1. **省字节**：speed 范围 0~163.83 m/s，用 0.02 m/s 步长只需 13 bit；float32 要 32 bit。10 Hz 广播 × 道路上每辆车，每个字节都是信道负载（上周第 3 节：信道是共享稀缺资源）。
2. **误差有界且可解析**：定点数的量化误差上界就是半个步长——speed 最大 ±0.01 m/s，heading 最大 ±0.00625°，lat/lon 最大 ±0.05 微度 ≈ ±5.5 mm。接收方**精确知道**消息里每个数坏了多少。
3. **无符号解释歧义**：浮点跨平台/跨语言解析没有字节序陷阱（ASN.1 编码下尤其如此）。

选择分辨率的逻辑是统一的：**分辨率 ≈ 传感器噪声的一半到四分之一**——量化误差要小于测量误差才有意义，也没必要细到噪声以下（纯属浪费比特）。0.02 m/s 的速度分辨率对应 GNSS 测速的典型精度量级；0.1 微度位置分辨率（≈1.1 cm）低于车道级定位需求一个数量级，留足了余量。

### 2.2 中国侧：RSM 才是路侧感知的出口

T/CSAE 53 沿用了 J2735 的风格并做了本土化（坐标系、枚举值等），其中与路侧感知直接相关的是 **RSM（Roadside Safety Message，路侧安全消息）**：RSU 把**自己感知到的目标**（车辆/行人/非机动车，含位置、速度、航向、尺寸、TrackID 等）广播出去——字段风格与 BSM 的 coreData 高度同构。RSM 与 RSI（路侧信息，如限速、事故提示等交通事件）、SPAT（信号灯相位与配时）、MAP（路口地图）共同构成中国 V2X 第一阶段的消息家族。**工程对应**：路侧感知栈的输出适配层，就是"TrackID/类别/位置/速度/尺寸/置信度 → RSM 字段"的映射器；而车端收到 RSM 后的适配层，则是第 3 周的协同融合入口。

欧洲的 CPM（ETSI TR 103 562 分析、后续 TS 103 324 规范化）走的同一条路但更系统：它规定了"哪些目标值得广播、多久广播一次"的**生成规则**（management container / perception container / per-object container 的分层结构），本质是上周"信道稀缺"问题的标准化解法。

### 2.3 消息家族其余成员：SPAT、MAP、RSI

路侧设备不止广播目标，第一阶段的完整消息家族各司其职（路侧感知工程师迟早都要对接）：

| 消息 | 全称 | 内容 | 典型频率 |
| --- | --- | --- | --- |
| **SPAT** | Signal Phase and Timing（信号灯相位与配时） | 当前红绿灯相位 + 倒计时 | 10 Hz（相位变化时必须立即更新） |
| **MAP** | Map Data（路口地图） | 路口拓扑：车道连接关系、停止线、转向约束 | 静态，启动时发/低频重发 |
| **RSI** | Road Side Information（路侧信息） | 交通事件（事故、施工、逆行、异常行人）、标志标牌 | 事件驱动 + 低频 |
| **RSM** | Roadside Safety Message（路侧安全消息） | 路侧感知到的动态目标列表 | 10 Hz |

SPAT + MAP 是一对搭档：MAP 告诉你"这个路口有几条车道、怎么连接"，SPAT 告诉你"哪条车道现在是绿灯还有几秒"——两者合成"绿波引导/红灯预警"类应用。**对感知系统的隐含要求**：RSM 里的目标要能关联到 MAP 的车道编号（"在进口道 3 上逆行的那辆车"），这需要感知输出带上车道级语义——Stage 2 的语义分割与 BEV（Stage 5）在这里再次兑现价值。

### 2.4 编码与字节：ASN.1 一句话

J2735 与 T/CSAE 53 的消息都用 **ASN.1**（Abstract Syntax Notation One）语言编写字段定义，线上传输用 UPER（非对齐紧凑编码）打包。你不需要会写 ASN.1，只需要知道三件事：① 字段定义是**标准原文可查的**（不用猜）；② 编码是**紧凑二进制**（教学版脚本用 Python 字典模拟的是"语义层"，真实系统编码后更小）；③ 存在成熟的开源 ASN.1 编译器（如 `asn1c`）能把标准文件直接编译成 C/Python 编解码代码——工程上**手写字段解析是大忌**，以标准原文为唯一事实源。

## 3. 可运行实验：感知输出 → 简化 BSM → 解码还原（w2）

把 Stage 4 融合跟踪器输出的目标列表，编码成简化 BSM 风格消息（字段名与分辨率对齐 J2735 coreData），再解码回来测误差，最后做 100 ms 时延到达实验。

```python
# w2_bsm_roundtrip.py —— 第 2 周：把融合跟踪输出序列化成简化 BSM 风格消息并解析回来
# 简化依据 SAE J2735 BSM Part I coreData 的字段名与定点分辨率：
#   位置 0.1 微度(1e-7 deg)、速度 0.02 m/s、航向 0.0125 deg、尺寸 cm、msgCnt 0~127、secMark 分钟内毫秒
import numpy as np

np.random.seed(20)

LAT0, LON0 = 39.99850, 116.32450           # 北京某路口附近（演示用局部 ENU 原点）
M_PER_DEG_LAT = 111320.0                    # 纬度方向 1 度的米数（近似）
M_PER_DEG_LON = 111320.0 * np.cos(np.radians(LAT0))

# ---- Stage 4 融合跟踪器在 t = 612.45 s 输出的目标列表（世界 ENU 坐标，米）----
TRACKS = [
    {"track_id": 101, "cls": "car",   "p": (63.20, -12.45), "v": (11.30,  0.45), "L": 4.60, "W": 1.90, "conf": 0.94},
    {"track_id": 107, "cls": "truck", "p": (-45.10,  38.22), "v": (-0.20, -3.80), "L": 9.80, "W": 2.55, "conf": 0.88},
    {"track_id": 112, "cls": "ped",   "p": ( 8.75,  21.60), "v": ( 1.40,  0.30), "L": 0.45, "W": 0.45, "conf": 0.76},
]
T_CAPTURE = 612.45                          # 感知时刻（s），来自路侧时钟

def enu2llh(x, y):
    return LAT0 + y / M_PER_DEG_LAT, LON0 + x / M_PER_DEG_LON

def llh2enu(lat, lon):
    return (lon - LON0) * M_PER_DEG_LON, (lat - LAT0) * M_PER_DEG_LAT

# ---- 编码：目标列表 -> 简化 BSM/RSM 风格消息（模拟传输就绪的字典）----
MSG_CNT = 87
def encode(tracks, t_capture):
    msgs = []
    sec_mark = int(round((t_capture % 60) * 1000))          # 分钟内毫秒 0~60999
    for tr in tracks:
        lat, lon = enu2llh(*tr["p"])
        speed = float(np.hypot(*tr["v"]))                    # 标量速度
        heading = np.degrees(np.arctan2(tr["v"][0], tr["v"][1])) % 360  # 0=北,顺时针
        msgs.append({
            "msgCnt":  MSG_CNT % 128,                        # 0~127 循环计数
            "id":      f"{tr['track_id']:04x}",              # 4 字节临时 ID
            "secMark": sec_mark,
            "lat":     int(round(lat  / 1e-7)),              # 0.1 微度定点
            "lon":     int(round(lon  / 1e-7)),
            "speed":   int(round(speed / 0.02)),             # 0.02 m/s 定点
            "heading": int(round(heading / 0.0125)),         # 0.0125 deg 定点
            "size_L_cm": int(round(tr["L"] * 100)),
            "size_W_cm": int(round(tr["W"] * 100)),
            "cls":     tr["cls"],
            "conf":    tr["conf"],
        })
    return msgs

# ---- 解码：消息 -> 目标列表（回到局部 ENU 米制）----
def decode(msgs):
    out = []
    for m in msgs:
        lat, lon = m["lat"] * 1e-7, m["lon"] * 1e-7
        x, y = llh2enu(lat, lon)
        out.append({
            "track_id": int(m["id"], 16),
            "p": (x, y),
            "speed": m["speed"] * 0.02,
            "heading": m["heading"] * 0.0125,
            "L": m["size_L_cm"] / 100, "W": m["size_W_cm"] / 100,
        })
    return out

# ---- roundtrip：量化误差有多大？----
msgs = encode(TRACKS, T_CAPTURE)
print(f"编码得到 {len(msgs)} 条消息（msgCnt={msgs[0]['msgCnt']}，secMark={msgs[0]['secMark']}）")
print(f"track 101 的消息: {msgs[0]}")

back = decode(msgs)
print("\n==== roundtrip 位置/速度还原误差 ====")
for tr, bk in zip(TRACKS, back):
    dx, dy = bk["p"][0] - tr["p"][0], bk["p"][1] - tr["p"][1]
    err_p = np.hypot(dx, dy)
    v_enc = np.hypot(*tr["v"])
    err_v = bk["speed"] - v_enc
    print(f"track {tr['track_id']}: 位置误差 = {err_p*100:6.2f} cm   速度误差 = {err_v:+7.3f} m/s")
    assert err_p < 0.05 and abs(err_v) < 0.011

# ---- 时戳的意义：消息到得太晚怎么办 ----
T_NOW = 612.45 + 0.10                        # 接收时刻 = 感知时刻 + 100 ms 传输时延
msg1 = msgs[0]
t_msg = T_CAPTURE + msg1["secMark"] / 1000 - (T_CAPTURE % 60)   # 还原感知时刻
age = T_NOW - t_msg
speed = msg1["speed"] * 0.02
heading_rad = np.radians(msg1["heading"] * 0.0125)
v_vec = np.array([speed * np.sin(heading_rad), speed * np.cos(heading_rad)])
stale_pos = np.array(decode([msg1])[0]["p"])
extrap_pos = stale_pos + v_vec * age        # 按消息自带的速度外推补偿
true_pos = np.array(TRACKS[0]["p"]) + np.array(TRACKS[0]["v"]) * 0.10
print(f"\n==== 时延 100 ms 到达时 ====")
print(f"消息年龄 age = {age*1000:.0f} ms，速度 = {speed:.2f} m/s")
print(f"不做补偿直接用: 位置误差 = {np.linalg.norm(stale_pos - true_pos):.3f} m")
print(f"按速度外推补偿后: 位置误差 = {np.linalg.norm(extrap_pos - true_pos):.3f} m")
```

**预期输出**（固定种子实测）：

```
编码得到 3 条消息（msgCnt=87，secMark=12450）
track 101 的消息: {'msgCnt': 87, 'id': '0065', 'secMark': 12450, 'lat': 399983882, 'lon': 1163252411, 'speed': 565, 'heading': 7018, 'size_L_cm': 460, 'size_W_cm': 190, 'cls': 'car', 'conf': 0.94}

==== roundtrip 位置/速度还原误差 ====
track 101: 位置误差 =   0.45 cm   速度误差 =  -0.009 m/s
track 107: 位置误差 =   0.52 cm   速度误差 =  -0.005 m/s
track 112: 位置误差 =   0.39 cm   速度误差 =  +0.008 m/s

==== 时延 100 ms 到达时 ====
消息年龄 age = 100 ms，速度 = 11.30 m/s
不做补偿直接用: 位置误差 = 1.131 m
按速度外推补偿后: 位置误差 = 0.005 m
```

三个数字的解读：

- **roundtrip 位置误差 0.4~0.5 cm**：来自经纬度 0.1 微度定点（1.1 cm 步长，量化误差上界 ±0.55 cm，实测 0.45 cm 在界内）。对比传感器本身的分米级噪声，编码误差可以忽略——**消息集不背感知误差的锅**。注意三条误差各不相同（0.45/0.52/0.39 cm）但都在上界内：量化误差不是系统偏差，是"最后一个有效数字的舍入"，逐目标独立。
- **速度误差 ±0.009 m/s**：0.02 m/s 步长的量化误差上界 ±0.01 m/s，三条全部贴着上界内。注意 `speed` 是**标量**，方向单独存在 `heading` 里——所以解码端能重建速度矢量 `v_vec`。
- **1.131 m vs 0.005 m**：上周 v·Δt 公式的实证。11.30 m/s × 100 ms = 1.13 m 的错位，靠消息自带的 secMark + speed + heading 三个字段就修到了 5 mm（残余来自定点量化）。**这就是"每个看似不起眼的字段都有存在理由"的最好例证**——没有 secMark 你连"消息有多旧"都不知道。

> **动手验证**：把 T_CAPTURE 改成 613.45（跨分钟：613.45 % 60 = 13.45，secMark 会回到 13450）。理解 secMark 只有"分钟内毫秒"精度，跨分钟边界时**接收端需要自己的分钟计数 + msgCnt 连续性**才能定位绝对时刻——这也是真实 BSM 接收机的做法。

### 3.1 适配器视角：感知字段 → 消息字段映射表

把 w2 脚本的 encode() 抽象成一张工程映射表——这就是真实 RSU 项目里"感知算法组"与"通信协议组"之间的接口文档骨架：

| 感知输出（Stage 4 融合器） | 消息字段（简化 BSM/RSM） | 转换 | 坑 |
| --- | --- | --- | --- |
| track_id | `id` | 十进制 → 4 字节十六进制 | ID 漂移（Stage 4）直接毁掉此字段语义 |
| p（世界 ENU，m） | `lat` / `lon` | ENU→大地坐标，再 × 1e7 取整 | 忘乘 cos(纬度) 处理经度米数 |
| v（速度矢量） | `speed` + `heading` | 矢量 → 标量+角度分解 | 只有标量时方向信息已丢，无法重建矢量 |
| L/W（尺寸） | `size_L_cm` / `size_W_cm` | m → cm 取整 | 3D 高度与 yaw 在 coreData 之外 |
| conf（置信度） | `conf` | 直传（语义需双方约定） | 校准前后概率混用 |
| — | `msgCnt` / `secMark` | 由发送时钟生成 | 时钟不同步则下游补偿全错 |

表中"坑"一列就是第 5 节失效模式的预告：**适配器是感知误差与通信误差的交界层，两类错误都会在这里现形**。联调时打印这张表的每一格，是定位"目标对不上"问题的第一动作。

## 4. 时戳与同步：呼应 Stage 1 的时间对齐

上节的 roundtrip 能精确补偿时延，隐含了一个前提：**发端和收端的时钟在同一根时间轴上**。回顾 Stage 1/3 讲过的传感器时间同步问题，V2X 场景把它放大到了"设备与设备"之间：

- 路侧感知栈的时戳来自路侧时钟（GPS 授时，PPS/PTP 同步到 UTC），车端时钟同样来自 GNSS——两端共享同一绝对时基，secMark 才有意义。
- 若某端时钟漂了 50 ms，上节的补偿公式就会**系统性**多补/少补 50 ms × 11.3 m/s ≈ 0.57 m——时戳错误不是"消息没用了"，而是更隐蔽的"消息很自信地错了"。
- 工程检查项（真实联调每周都做）：① 校验 secMark 与本地到达时刻的差是否稳定（漂移的时钟表现为该差值持续增长）；② 用 msgCnt 的连续性算丢包率（10 Hz 广播下，每秒计数应 +10，缺多少补多少）。

```
丢包检测（msgCnt 循环 0~127）：
  收到 ... 85, 86, 89, 90 ...
               └─ 87、88 丢了（或乱序）→ 丢包率 = 2/10/s
  处理：不重传（广播无回程），直接用当前 KF 预测顶上（Stage 4 的预测步就是为这一刻设计的）
```

这正是广播与单播的哲学差异：单播靠重传与确认保证到达，广播**默认会丢**、把兜底责任交给接收端的运动模型——Stage 4 那句"漏检几帧椭圆会变大但轨迹不丢"，在 V2X 场景下从性质变成了日常。第 4 周仿真里 5% 丢包被 KF 无声吸收，就是这个设计的实验证明。

## 5. 本周小结

- 消息集标准解决"陌生节点互译"问题：SAE J2735（BSM 说"我自己在哪"）+ T/CSAE 53-2020（**RSM 说"我看见的东西在哪"——路侧感知的官方出口**）+ ETSI CPM（欧洲协同感知消息，含生成规则）。
- BSM Part I 核心七字段：msgCnt（0~127 循环）、id（4 字节临时 ID）、secMark（分钟内毫秒）、lat/lon（0.1 微度）、speed（0.02 m/s）、heading（0.0125°）、size（cm）；**全部定点量化**——省带宽、误差有界、无解释歧义。
- roundtrip 实测：位置编码误差 ≤0.55 cm（解析上界内）、速度 ≤±0.01 m/s——**消息集不背感知误差的锅**，排查时先跑 roundtrip 排除编码层。
- secMark + speed + heading 三字段合力把 100 ms 时延的 1.13 m 错位修到 5 mm——**时间戳不是元数据，是补偿公式的输入**。
- 时钟同步是隐含前提：50 ms 时钟差 × 11.3 m/s = 0.57 m 系统性偏差，用"消息年龄漂移监控 + msgCnt 丢包统计"两根探针盯住。

## 6. 工程权衡与失效模式

1. **编码超范围（overflow）**：真实值超出定点范围（如 speed > 163.83 m/s 不可能，但 heading 在 359.99° 边界、lat/lon 在范围边界）会被截断成完全错的值。**症状**：某个方向的个别目标位置突变到地球另一侧；**修复**：编码前 clamp + 测试用例覆盖边界值。
2. **坐标系没写进消息**：RSM 有参考点定义，但自研私有消息常常"忘了说原点在哪"。**症状**：两端各自能跑，联调时目标整体平移/旋转了固定量；**修复**：消息里显式携带参考坐标系定义或双方约定配置版本号。
3. **conf（置信度）语义不统一**：0.94 是 softmax 概率还是校准后的概率？车端如果直接拿它当概率用会翻车。**症状**：车端融合权重异常；**修复**：接口文档明确定义并做校准（Stage 2 讲过概率校准）。
4. **TrackID 漂移的直接损失**：本地融合器 ID 不稳定（Stage 4 的 ID switch），广播后对端把同一辆车关联成新目标，重复计入碰撞风险。**症状**：对端目标数量虚高、轨迹抖动；**修复**：确认态轨迹才广播 + ID 保持策略（min_hits/确认机制），呼应《后融合.md》笔记。
5. **拿 secMark 当绝对时间戳用**：secMark 只在分钟内单调，跨分钟必须配合本地分钟计数。**症状**：每小时出现一次 59.999→0.000 的"时间倒流"误判；**修复**：用 msgCnt 连续性做跨分钟消歧。
6. **频率错配**：感知跑 25 Hz 相机、融合器 10 Hz、消息 10 Hz，若未对齐帧率，同一目标的消息时间戳抖动 ±50 ms，下游补偿跟着抖。**症状**：速度估计的 zigzag、融合残差异常；**修复**：接口层显式声明频率并做最近邻/插值时间对齐（Stage 1 异步时延问题的通信版）。

## 7. 延伸思考题（含解析）

**Q1**：BSM 的 `id` 是 4 字节随机临时 ID 且会定期更换，为什么不用车牌号/VIN？
**A**：隐私。安全应用只需要"这几条消息是不是同一辆车"，不需要知道它是谁。固定 ID 会让路侧设备能长期追踪任何人——欧盟 GDPR 与各国隐私法都不允许。定期换 ID（pseudonym）进一步限制追踪窗口。代价是 ID 换新瞬间对端要做轨迹接力（又回到 TrackID 一致性）。

**Q2**：0.1 微度的经度分辨率，在赤道和在北京（40°N）对应的米数一样吗？
**A**：不一样。0.1 微度纬度恒为 1.11 cm；经度 1 度对应 111.32 km × cos(纬度)，北京 40°N 时 0.1 微度经度 ≈ 1.11 cm × cos40° ≈ 0.85 cm。所以同样的定点格式，经向误差略小——w2 脚本里 `M_PER_DEG_LON` 乘 `cos(LAT0)` 就是在做这个换算。

**Q3**：路侧感知有 3D 尺寸（长宽高）和朝向（yaw），RSM/BSM 风格消息里只有长宽，朝向信息怎么传？
**A**：J2735 coreData 只有 width/length（Part I 尽量小）；3D 属性属于扩展部分（Part II 或 CPM 的 per-object container，含 height、yaw、参考点）。教学版脚本只传 L/W 是有意简化——真实工程里目标级消息的字段完整度是"带宽 vs 信息量"权衡的直接体现，CPM 为此设计了一整套可选字段。

**Q4**：为什么说"消息集不背感知误差的锅"？编码误差和感知误差怎么区分？
**A**：编码误差有解析上界（半个步长，本例 ≤0.55 cm），感知误差是传感器/算法噪声（分米~米级），两者差两个数量级以上。排查位置误差时先用解析上界排除编码（跑一遍 roundtrip 断言），剩下的全部归因于感知链路——这就是"每层误差可分离"的工程意义。

**Q5**：路侧感知在隧道/高架下 GNSS 拒止，消息还能用吗？
**A**：绝对坐标（lat/lon）会漂，但消息结构照样有效——工程对策是把"位置参考点"换掉：RSU 部署时预先标定自己在已知地图坐标系的精确位置（一次性，Stage 3 的标定思想），感知输出走"参考点 + 相对坐标"，GNSS 只需兜住路侧一台设备而不是每个目标。车端同理可以走车道级相对定位。原则：**时间同步可以靠共享时基，空间同步要靠"一个精心标定的锚点"而不是"每帧都准的绝对定位"**。
