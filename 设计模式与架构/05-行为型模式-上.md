# 05 - 行为型模式（上）：策略、观察者、命令、模板方法

## 本篇目标

行为型模式（GoF 共 11 个）解决"**对象之间如何分配职责与通信**"。本篇讲日常出现频率最高的四个：策略、观察者、命令、模板方法。下篇（06）讲状态、迭代器、中介者、责任链等并做模式滥用反思。

## 1. 策略模式（Strategy）

**动机**：同一件事有多种做法，且做法会切换/扩展。把每种做法封装成独立类，让它们**可互相替换**（02 篇 OCP 的落地形态）。

```python
from abc import ABC, abstractmethod

class RouteStrategy(ABC):
    @abstractmethod
    def route(self, a, b) -> list: ...

class Fastest(RouteStrategy): ...
class Cheapest(RouteStrategy): ...
class AvoidHighway(RouteStrategy): ...

class Navigator:
    def __init__(self, strategy: RouteStrategy):
        self.strategy = strategy
    def navigate(self, a, b):
        return self.strategy.route(a, b)   # 算法可整体替换

nav = Navigator(Fastest())
nav.strategy = Cheapest()      # 运行时切换
```

三个工程要点：

1. **策略由外部注入**——`Navigator` 不 `if-else` 选择，选择权在调用方。如果模式内部自己选策略，就退化成了"带多态的 if-else"，收益减半；
2. **Python 的轻量形态**：函数即策略。`Navigator(route_fn)` 直接传函数即可，不必造类——模式的价值在"可替换的抽象"，不在类的仪式感；
3. **辨识信号**：一个方法里长满 `if method == ...` 分支、分支内容会继续膨胀 → 提取策略。若分支数封顶且稳定（如固定的 2 种），保持 if-else 更简单（01 篇 YAGNI）。

## 2. 观察者模式（Observer）

**动机**：一个对象状态变化，**多个**对象需要知情，且不希望主题类知道具体是谁。

```python
class EventBus:
    def __init__(self):
        self._subs: dict[str, list] = {}

    def subscribe(self, topic, fn): self._subs.setdefault(topic, []).append(fn)
    def publish(self, topic, event):
        for fn in self._subs.get(topic, []):
            fn(event)

# 订单系统：支付完成后，库存、通知、积分各自订阅
bus.subscribe("order.paid", lambda e: inventory.deduct(e.order))
bus.subscribe("order.paid", lambda e: notify.send(e.order))
bus.subscribe("order.paid", lambda e: points.award(e.user))
# 此后新增"发送优惠券"只需要再加一行订阅——主题侧零修改（OCP）
```

GoF 原版是 Subject/Observer 抽象类对；现代工程几乎都简化为**事件总线/发布订阅**（上例）。两者严格说有差别：发布订阅中间多一层 broker，发布者与订阅者互不相知；GoF 观察者中 Subject 仍持有 Observer 列表。

**必须正视的两个坑**（Observer 的经典代价）：

1. **执行顺序不确定**：订阅者的回调顺序没有保证——**不要让业务正确性依赖回调顺序**；
2. **失控的副作用链**：一次 publish 触发一串同步回调，哪个抛异常都会打断后续（除非总线和 listener 各自兜异常），排查问题时"谁触发的"变得难追。工程对策：回调统一 try/except + 记日志；重副作用场景改用**持久化事件表 + 异步消费**（事件驱动架构的雏形，08 篇展开）。

## 3. 命令模式（Command）

**动机**：把"一次请求"封装成对象，从而可以**存储、排队、撤销、重放**。

```python
@dataclass
class Command(ABC):
    @abstractmethod
    def execute(self): ...
    @abstractmethod
    def undo(self): ...

class Deposit(Command):
    def __init__(self, account, amount):
        self.account, self.amount = account, amount
        self.done = False
    def execute(self):
        self.account.balance += self.amount; self.done = True
    def undo(self):
        if self.done: self.account.balance -= self.amount

# 历史 = 可撤销的操作序列（编辑器 undo/redo 的骨架）
history: list[Command] = []
cmd = Deposit(acc, 100); cmd.execute(); history.append(cmd)
...
history.pop().undo()   # 撤销
```

命令 vs 策略（又一个高频混淆）：

| | 策略 | 命令 |
| --- | --- | --- |
| 封装什么 | 一**种做法**（怎么算） | 一**次请求**（做了什么） |
| 对象用途 | 被选择、被替换 | 被排队、被记录、被撤销 |
| 典型场景 | 算法切换 | undo/redo、任务队列、宏录制 |

现代形态：MQ 队列里的**消息**（可序列化的"请求对象"）、CQRS 中的 Command 对象，都是命令模式的规模化应用。

## 4. 模板方法模式（Template Method）

**动机**：流程骨架固定，个别步骤可变。父类定骨架（final 方法），子类填空。

```python
class DataPipeline(ABC):
    def run(self):                 # 模板方法：骨架固定
        raw = self.extract()
        cleaned = self.transform(raw)
        self.load(cleaned)

    @abstractmethod
    def extract(self): ...         # 可变步骤交给子类

    def transform(self, raw):      # 也可提供默认实现（钩子）
        return [r.strip() for r in raw]

    @abstractmethod
    def load(self, rows): ...

class CsvPipeline(DataPipeline):
    def extract(self): ...         # 只填自己的空
    def load(self, rows): ...
```

识别信号：多个类流程相同、只有个别环节不同——正在用复制粘贴同步这些流程。Java 标准库 `AbstractList`、Spring 的 `JdbcTemplate`、本仓库 Agent 系列 02 篇里"ReAct 主循环"（循环骨架固定、每步动作可变）都是模板方法形状。

**代价**：继承是静态绑定——骨架变更要动所有子类的父类，且"填空"被迫继承。现代替代是**回调/高阶函数**（把可变步骤作为参数传入）：`pipeline.run(extract=my_fn)`。Python/JS 中高阶函数常比模板方法更轻；Java 8+ 可用 `Consumer`/`Function` 参数替代部分场景。

## 小结对照表

| 模式 | 一句话 | 识别信号 | 主要代价 |
| --- | --- | --- | --- |
| 策略 | 可替换的做法 | 多分支且会膨胀 | 类增殖 |
| 观察者 | 一变多知，互不相知 | "改了 A 还要记得改 B" | 顺序不定、副作用链 |
| 命令 | 请求对象化 | 需要撤销/排队/重放 | 每命令一类 |
| 模板方法 | 骨架固定填空 | 复制粘贴同步流程 | 继承绑定 |
