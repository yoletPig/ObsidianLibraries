# 03 - 创建型模式

## 本篇目标

创建型模式把"**对象怎么创建**"这件事从使用代码中剥离。本篇覆盖 GoF 五个创建型模式中的四个（单例、工厂方法+抽象工厂、建造者、原型），每个都讲：动机 → 实现 → 代价 → 现代语言的替代/简化。

先给一个总判断，帮你校准学习投入：**日常工作中最常用的是工厂类与建造者；单例最常用但争议最大；原型在现代语言中往往被浅拷贝 API 或序列化取代**。

## 1. 单例模式（Singleton）

**动机**：全局只需要一个实例——配置中心、连接池、日志器。

```python
# Python 经典实现：模块级单例最简单
# config.py 里直接创建实例，Python 模块天然只 import 一次
class Config: ...
config = Config()   # 全局唯一的实例
```

```java
// Java 经典双重检查锁（DCL）实现
public class Config {
    private static volatile Config instance;
    private Config() {}
    public static Config getInstance() {
        if (instance == null) {                       // 第一次检查（无锁）
            synchronized (Config.class) {
                if (instance == null) instance = new Config();  // 第二次检查
            }
        }
        return instance;
    }
}
```

三个必须知道的工程事实：

1. **`volatile` 不能省**（Java）：`instance = new Config()` 不是原子操作（分配→构造→赋值三步），无 volatile 时另一线程可能拿到"已赋值但未构造完"的半成品实例。这是并发面试的经典考点，也对应本仓库 C++ 系列 12 篇的主题；
2. **C++11 起有更优雅的写法**（Meyers' Singleton，C++11 保证局部 static 初始化线程安全）：
   ```cpp
   Config& Config::instance() {
       static Config c;   // C++11: 首次调用时构造，且线程安全
       return c;
   }
   ```
3. **单例的代价**：隐藏的全局状态（调用方看不出函数依赖了它）→ 测试难以隔离；往往沦为"优雅的全局变量"。

**现代替代**：多数场景用**依赖注入容器**（一个受控的全局）或框架提供的 application context。经验法则：单例留给真正无状态、且生命周期=进程生命周期的对象。

## 2. 工厂方法与简单工厂

**动机**：调用方不应该 `new` 具体类——一旦写死，换实现就要改调用方（OCP，02 篇）。

```python
from abc import ABC, abstractmethod

# 产品抽象
class Exporter(ABC):
    @abstractmethod
    def export(self, data) -> bytes: ...

class CsvExporter(Exporter): ...
class ExcelExporter(Exporter): ...

# 简单工厂：一个静态方法按条件创建（严格说不是 GoF 23 模式之一，
# 而是工厂思想的入门形态，见《设计模式之禅》的分类）
def create_exporter(fmt: str) -> Exporter:
    return {"csv": CsvExporter, "excel": ExcelExporter}[fmt]()

# 工厂方法（GoF 正式版）：把"决定创建什么"下放给子类
class ReportJob(ABC):
    @abstractmethod
    def make_exporter(self) -> Exporter: ...   # 工厂方法：子类决定产品

    def run(self, data):                        # 模板方法（05 篇）
        exp = self.make_exporter()              # 父类只依赖抽象
        ...process(exp.export(data))...

class CsvReportJob(ReportJob):
    def make_exporter(self): return CsvExporter()
```

**代价与辨析**：工厂类会增殖——产品种类少（≤3）且稳定时，直接 `new` 更直白。工厂的价值出现在：创建过程复杂（多步、需配置）、需要按运行时条件选择实现、或需要统一替换所有实现（如测试时换假实现）。

## 3. 抽象工厂（Abstract Factory）

**动机**：需要**一族**相关产品保持配套。例：UI 库要整套切换——Light 风格的 Button+Input+Dialog，或 Dark 风格的一整套。若用三个独立工厂，可能出现 Light 按钮配 Dark 对话框。

```python
class WidgetFactory(ABC):
    @abstractmethod
    def make_button(self) -> Button: ...
    @abstractmethod
    def make_input(self) -> Input: ...

class LightFactory(WidgetFactory): ...   # 生产的组件保证风格配套
class DarkFactory(WidgetFactory): ...
```

**辨析**：工厂方法生产**一种**产品、靠子类扩展；抽象工厂生产**一族**产品、强调配套约束。族的数量少时，抽象工厂的类数量膨胀很快（每族一个工厂类），这是它最大的代价。

## 4. 建造者模式（Builder）

**动机**：对象有很多可选参数。Java 的"重叠构造器"（telescoping constructor）是经典痛点——参数一多，调用处全靠位置记参数，可读性灾难。

```java
// 建造者：分步构建 + 链式调用，可选参数显式命名
HttpClient client = HttpClient.newBuilder()
        .version(HttpClient.Version.HTTP_2)
        .connectTimeout(Duration.ofSeconds(10))
        .followRedirects(HttpClient.Redirect.NORMAL)
        .build();
```

两个关键区分（面试常考）：

- **建造者 vs 工厂**：工厂关心"创建**哪种**对象"（一步完成）；建造者关心"如何**分步**组装一个复杂对象"（多步，且步骤可控）；
- **经典 GoF 建造者**还包含 Director（指挥者，固化构建步骤顺序）；现代语言中 Builder 多简化为"链式 setter + build()"（Effective Java 第 2 版第 2 条推广的形态）。Java 标准库的 `Stream.Builder`、`StringBuilder`，Lombok 的 `@Builder` 都是此形态。

## 5. 原型模式（Prototype）

**动机**：创建对象的成本高（如要查库初始化），或只有"从现有实例出发改一改"才自然。

```python
import copy
proto = Invoice(template_params)     # 昂贵的初始化只做一次
inv1 = copy.deepcopy(proto)          # 基于原型克隆
inv1.number = "INV-001"
```

**现代简化**：多数语言的标准库/序列化机制覆盖了此需求（Python 的 `copy`、`dataclasses.replace`；JS 对象的字面克隆 `structuredClone`）。GoF 原型的**clone 接口约定**（深/浅拷贝的显式控制）在语言层面各有实现，需要理解的只剩"深浅拷贝的区别"——深拷贝复制引用链上的所有对象，浅拷贝只复制最外层、内部引用共享。

## 小结与选用决策

```
需要全局唯一？ → 单例（先考虑 DI 容器）
创建方式复杂/需按条件选择？ → 工厂（一族产品配套 → 抽象工厂）
可选参数多？ → 建造者
克隆现有实例更自然？ → 原型（多用语言内建拷贝）
```
