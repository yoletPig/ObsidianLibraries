# 04 - 结构型模式

## 本篇目标

结构型模式解决"**类与对象如何组合成更大的结构**"。本篇重点讲四个高频模式（适配器、装饰器、代理、外观），辨析其中两对最易混淆的组合（装饰器 vs 代理、适配器 vs 外观），末尾速览低频的桥接、组合、享元。

## 1. 适配器模式（Adapter）

**动机**：已有的接口和需要的接口**对不上**，而旧接口的代码不能改（第三方库、遗留系统）。

```python
# 旧系统只会这个接口
class LegacyPayment:
    def make_payment(self, cents: int): ...

# 新代码期望的接口
class PaymentGateway(ABC):
    @abstractmethod
    def charge(self, amount: Decimal, currency: str): ...

# 适配器：把旧接口"翻译"成新接口
class LegacyPaymentAdapter(PaymentGateway):
    def __init__(self, legacy: LegacyPayment):
        self.legacy = legacy
    def charge(self, amount: Decimal, currency: str) -> None:
        if currency != "CNY":
            raise ValueError("legacy 网关只支持 CNY")
        self.legacy.make_payment(int(amount * 100))   # 单位换算 + 转发
```

适配器是"**补救性**"模式——它不创造新设计，而是让**既成事实的两端**协作。看到适配器，通常意味着系统里有"不想动的历史"。

## 2. 装饰器模式（Decorator）

**动机**：给对象**动态叠加**职责，又不想为每种组合建子类（继承组合爆炸：加密+压缩+日志三个维度，继承要 7 个子类；装饰器只要 3 个）。

```python
class DataSource(ABC):
    @abstractmethod
    def read(self) -> bytes: ...
    @abstractmethod
    def write(self, data: bytes): ...

class FileSource(DataSource):          # 被装饰的核心
    def __init__(self, path): self.path = path
    def read(self): return Path(self.path).read_bytes()
    def write(self, d): Path(self.path).write_bytes(d)

class DataSourceDecorator(DataSource):  # 装饰器基类：实现接口 + 持有同接口对象
    def __init__(self, inner: DataSource): self.inner = inner
    def read(self): return self.inner.read()
    def write(self, d): self.inner.write(d)

class Compress(DataSourceDecorator):
    def write(self, d): self.inner.write(gzip.compress(d))
    def read(self): return gzip.decompress(self.inner.read())

class Audit(DataSourceDecorator):
    def write(self, d):
        log(f"write {len(d)} bytes")   # 叠加新职责，再转发
        self.inner.write(d)

# 关键能力：运行时自由叠加、顺序即语义
src = Audit(Compress(FileSource("data.bin")))
```

结构特征（记忆锚点）：**装饰器与被装饰者实现同一接口，且持有同接口的引用**——所以对调用方完全透明，可以一层套一层。

> 你早就在用了：Python 的 `@decorator` 语法、Java 的 `java.io` 流（`new BufferedInputStream(new FileInputStream(f))`）、本仓库 C++ 系列里 `std::unique_ptr` 包装裸指针的思路，都是装饰器形状。

## 3. 代理模式（Proxy）

**动机**：在访问真实对象前**插入控制**——延迟加载、权限检查、缓存、远程调用。

```python
class Image(ABC):
    @abstractmethod
    def render(self): ...

class HeavyImage(Image):                     # 加载成本极高
    def __init__(self, path): self.path = path
    def render(self): print(f"渲染 {self.path}")

class LazyImageProxy(Image):                 # 虚代理：推迟昂贵操作
    def __init__(self, path):
        self.path, self._real = path, None
    def render(self):
        if self._real is None:
            self._real = HeavyImage(self.path)   # 第一次用时才加载
        self._real.render()
```

代理家族按用途分：**虚代理**（延迟加载，上例）、**保护代理**（权限检查）、**远程代理**（RPC stub——调用远程对象像调用本地）、**缓存代理**。现代基础设施里它无处不在：数据库连接池、RPC 框架的客户端 stub、AOP 切面，本质都是代理。

### 关键辨析：装饰器 vs 代理

两者结构**几乎一样**（同接口 + 持有同接口引用），区别全在**意图**：

| | 装饰器 | 代理 |
| --- | --- | --- |
| 意图 | **增强**功能（加行为） | **控制**访问（管行为） |
| 客户端感知 | 知道自己在叠加行为，主动组合 | 通常不知道代理存在 |
| 典型问题 | "我要多几种能力组合" | "我不想/不能直接访问真身" |

## 4. 外观模式（Facade）

**动机**：子系统太复杂，客户端需要一条**简化入口**。

```python
class OrderFacade:      # 客户端只看这个类
    def place_order(self, cart, user):
        inventory.reserve(cart)     # 实际协调 4 个子系统
        payment = payments.charge(user, cart.total)
        shipping.schedule(cart, user.address)
        notifier.sent(user, payment.receipt)
```

要点：外观**不消灭**子系统——高级客户端仍可绕过外观直接用子系统精细控制。它是"默认入口"而非"唯一入口"。与适配器的辨析：**适配器是接口不兼容时的翻译层（一对一转换），外观是接口太复杂时的简化层（多对一收敛）**。

## 5. 低频三兄弟速览

- **桥接（Bridge）**：把两个**独立变化维度**拆开，用组合连接。例：形状（圆/方）× 绘制 API（矢量/位图），继承要 4 个类且加一维翻一倍；桥接拆成 Shape 持有 Renderer，两边独立演化。形状与颜色、消息类型与发送渠道，都是"两个维度"的信号；
- **组合（Composite）**：树形结构中"个体与容器同接口"。文件系统中**文件**与**目录**统一为 Node、目录可含 Node，是标准案例；
- **享元（Flyweight）**：海量对象中抽离共享的内部状态以省内存。文字编辑器中"字形"（共享）与"位置"（每处不同）的分离是教科书案例；现代语境下，"内部状态共享 + 外部状态传入"的思想广泛见于对象池、字符串驻留（`String.intern`）。

## 选用决策

```
接口不兼容要桥接？ → 适配器    接口太复杂要收敛？ → 外观
要叠加可选职责？  → 装饰器    要控制访问/延迟？  → 代理
两个维度独立变化？→ 桥接      树形同构？        → 组合
海量对象省内存？  → 享元
```
