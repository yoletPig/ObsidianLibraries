# 10 - 架构实战：演进一个系统

## 项目目标

用一个虚构但真实的场景——"图书电商平台"——走一遍从 **0 到模块化单体再到局部服务化** 的完整推演。重点不是最终形态，而是**每一步决策的依据、被放弃的方案、以及决策被推翻时怎么改**。07–09 篇的所有工具（trade-off、ADR、质量属性 Scenario、绞杀者模式）都会用到。

> 方法论说明：本篇是"教学推演"，数据为示意量级；真实系统中每个决策都应以你自己的度量数据为准。

## 0. 起点：一个 50 行的脚本

```
v0: books.py —— 单文件脚本
    Flask 路由 + sqlite3 直查 + 邮件用 print 代替
```

**此刻的正确决策：什么都不做。** 01 篇 YAGNI、08 篇"系统很小别过度设计"。架构始于问题，不始于流行词。

## 1. 第一次演进：分层（触发器：3 个人协作）

**信号**：团队 3 人，git 冲突高发，改一个 SQL 要同时读懂 Flask 和业务逻辑。

**决策**：引入三层（08 篇分层架构）——`routers/`（协议）→ `services/`（业务）→ `repositories/`（SQL）。同时约定：service 层不出现 SQL，router 层不出现业务规则。

**ADR-001 要点**：否决"直接上微服务"——理由：3 人团队的服务化运维成本 > 协作收益；单体分层已解决冲突问题。

## 2. 第二次演进：模块化（触发器：边界开始模糊）

**信号**：半年后，"下单扣库存"的逻辑在 service 层里到处出现；有人从 billing 模块直接 import 了 inventory 的内部函数，改库存表结构时 billing 悄悄崩了。

**决策**：按业务能力切模块（08 篇模块化单体）：

```
app/
  orders/    {api.py, service.py, repo.py}   ← 只暴露 api.py
  inventory/ ...
  billing/   ...
  shared/    （真正的公共件：日志、配置）
```

配套纪律（08 篇的三条，缺一不可）：

1. 模块间只准 import 对方的 `api.py`；
2. 每个模块私有数据表，**禁止跨模块 join**（billing 想要订单数据？调用 orders 的接口或订阅其事件）；
3. 用 import-linter 在 CI 里固化上述规则。

**被否决的方案**：按技术层切模块（所有 service 一堆、所有 repo 一堆）——否决理由：这会让"改一个业务"仍然跨多个目录，边界没有对应业务概念。

## 3. 第三次演进：局部事件驱动（触发器：多下游联动）

**信号**：支付成功后要联动 4 个下游（库存、通知、积分、发票），orders.service 里 `if` 越来越多；产品还要加第 5 个下游。

**决策**：引入进程内事件总线（05 篇观察者的工程化），orders 只发布 `order.paid`，下游各自订阅。**不上 Kafka**——当前 QPS（<100）与团队规模撑不起独立中间件的运维成本，进程内总线可事后替换为消息中间件（07 篇可逆性视角：把接口抽象成 `EventPublisher`，进程内实现换 Kafka 实现时业务代码不动）。

**质量属性 Scenario（09 篇五要素）固化此决策**：

```
刺激源   │ 新增下游"发票服务"
刺激     │ 订阅 order.paid 事件
环境     │ 生产
响应度量 │ orders 模块代码 0 行改动；接入耗时 < 1 天
响应     │ 新下游正常工作
```

## 4. 第四次演进：服务化拆分（触发器：规模数据）

**信号**（三个一起来才考虑，08 篇）：

- 部署耦合成为真实痛点：发票模块的 bug 让整个商城回滚；
- 计算负载不均：商品搜索吃掉 80% CPU，拖慢下单（无法独立扩缩）；
- 搜索团队 5 人，想要独立的技术栈与发布节奏。

**决策**：**只拆搜索**成独立服务，其余保持单体。这是本篇最重要的一条纪律：

> **拆分的单位是"痛"，不是"代码量"。** 一次只拆最痛的那块，其他不动。

拆分手法（09 篇绞杀者模式）：新搜索服务上线 → 网关按比例路由流量（5% → 50% → 100%）→ 单体内旧搜索代码枯萎删除。全程可回滚：路由开关切回去就行。

**拆分时刻的新增账单**（必须预先列出，09 篇取舍公理）：

| 新问题 | 对策 |
| --- | --- |
| 搜索服务挂了 → 整站搜索不可用 | 降级：返回缓存的热门列表（有损服务优于不可用） |
| 数据一致性：商品改名后搜索晚几秒更新 | 接受最终一致 + 商品服务发布 `product.updated` 事件 |
| 调用链路变长，排障困难 | 全链路 trace-id（从网关生成，服务间透传） |
| 独立部署 → 环境配置漂移 | 容器化 + 统一配置中心 |

## 5. 全程决策地图回顾

```
v0 脚本 ──(3人协作)──→ v1 分层单体
      ──(边界模糊/跨模块改坏)──→ v2 模块化单体
      ──(多下游联动/加下游成本高)──→ v3 单体+事件驱动
      ──(部署耦合/负载不均/团队规模)──→ v4 单体+事件+1个服务
```

三条贯穿始终的元原则：

1. **每次演进都由真实信号触发**，从不"为了先进而演进"；
2. **每次演进都写 ADR**，包括被否决的方案（07 篇）；
3. **每次演进都可回滚**——不可逆的架构动作要拆成一系列可逆的小动作。

## 6. 反面教材：如果当初直接上微服务

对照练习（面试与评审高频题）：如果 v0 阶段就把系统拆成 8 个微服务，会发生什么——

- 3 人团队维护 8 份 CI/CD、8 份监控、8 份服务发现配置；
- 一次"下单"跨 4 个服务的分布式事务（Saga/补偿逻辑）取代了一个本地事务；
- 本地起完整环境需要 Docker 编排十几个容器，新人上手周期从半天变一周；
- 换来的"独立部署/扩缩"收益：当时毫无用处。

这个练习的目的：**架构决策的对错不在于方案本身，在于方案与当前约束的匹配**。

## 自测

1. v0 阶段"什么都不做"是哪条原则？为什么不矛盾于"架构思维"？
2. 模块化单体的三条纪律？哪条决定未来能否顺利拆分？
3. "拆分的单位是痛不是代码量"——举出本案例中的三个"痛"。
4. 绞杀者模式的流量切换为什么"全程可回滚"？

## 系列完结

十篇回顾：01-02 建立判断尺（变化、SOLID）→ 03-06 模式词汇表（含滥用反思）→ 07-09 架构思维（取舍、风格、质量属性）→ 10 完整演进。接下来建议：找你自己正在维护的项目做一次"架构审计"——画出模块依赖图，找出违反依赖方向的 import，写第一份 ADR。
