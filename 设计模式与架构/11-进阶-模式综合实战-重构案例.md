# 11 - 进阶：模式综合实战——重构一个真实模块

> 进阶篇第 1 章。基础篇按"动机→结构→代价"逐个学模式；本章反过来：**从一个真实的烂模块出发，一步步应用 6 个模式 + SOLID 完成重构**。重点展示真实的重构决策过程——包括"判断哪个模式不该用"。

## 1. 起点：一段真实的"进化产物"

业务背景：一个导出模块，两年间经过 7 次需求变更，长成了这样（Python 示例，真实代码库中极常见）：

```python
# before/exporter.py —— 412 行，此处截取骨架
class Exporter:
    def export(self, data, fmt, dest, compress, encrypt, notify, batch_id, retries=3):
        t0 = time.time()
        rows = []
        for r in data:
            if fmt == "csv":
                line = ",".join(self._esc_csv(str(v)) for v in r)
            elif fmt == "json":
                line = json.dumps(dict(r))          # 每行一个 JSON 对象
            elif fmt == "excel":
                raise ValueError("excel 需要整表对象，不支持行迭代")   # 半成品功能
            rows.append(line)

        body = "\n".join(rows)
        if compress:
            body = gzip.compress(body.encode())      # 隐含约定：compress 与 excel 冲突
        if encrypt and not compress:
            body = self._encrypt(body)               # 顺序耦合：先压缩后加密
        elif encrypt:
            raise ValueError("encrypt 需与 compress 同开")  # 又一处隐含约定

        if dest.startswith("s3://"):
            self._s3_put(dest, body, retries)
        elif dest.startswith("file://"):
            Path(dest[7:]).write_bytes(body if isinstance(body, bytes) else body.encode())
        elif dest.startswith("ftp://"):
            self._ftp_put(dest, body, retries)       # 没人记得这功能还能不能用

        if notify:
            if notify == "email":
                send_email(self.admin, f"导出 {batch_id} 完成，耗时 {time.time()-t0:.1f}s")
            elif notify == "webhook":
                requests.post(self.hook, json={"batch": batch_id, "ok": True})
```

先用 02 篇的 SOLID 给它"验伤"（这一步在任何重构里都该先做）：

| 症状 | 违反 | 证据 |
| --- | --- | --- |
| 一个类知道格式、压缩、加密、存储、通知五件事 | SRP | 5 个变化原因 |
| 加一种格式/存储/通知都要改 `export` 本体 | OCP | if-elif 链是扩展点 |
| `excel` 分支 raise、隐含的"压缩与加密顺序"约定 | LSP/契约缺失 | 行为约定散落在分支间 |
| `fmt`/`dest`/`notify` 用裸字符串传参 | ISP/类型缺失 | 调用方无法枚举合法值 |
| `Exporter` 直接 new S3/FTP/SMTP 依赖 | DIP | 单测必须 mock 网络 |

## 2. 重构路线图：先测后拆，先数据后行为

### 步骤 0：特征测试（characterization test）

重构的安全网。在**不改变行为**的前提下，用现有输入/输出固化现状（Feather《Working Effectively with Legacy Code》的核心手法：先给烂代码补上"记录现状"的测试，哪怕现状是错的）：

```python
def test_current_csv_gzip_file_output():
    # 用小样本数据跑现有 export，把输出字节存为 golden file
    # 重构后必须逐字节一致，才允许合并
```

### 步骤 1：裸字符串 → 枚举（最小改动，立即收益）

```python
class Fmt(StrEnum):
    CSV = "csv"; JSON = "json"; EXCEL = "excel"   # EXCEL 暂保留并显式标注未支持
class Destination(NamedTuple):
    uri: str           # 保留字符串（协议多样），但解析收进工厂
```

这一步没有引入任何模式，却是纯收益：调用方在类型层面就无法传 "jso"。

### 步骤 2：按"变化轴"拆策略（SRP + OCP）

识别出三根独立变化轴：**格式（行序列化）**、**存储（写到哪里）**、**通知（完成后告知谁）**。每轴一个抽象：

```python
class RowSerializer(Protocol):
    def serialize_row(self, row: Mapping) -> str: ...
    def content_type(self) -> str: ...

class CsvSerializer:
    def serialize_row(self, row): return ",".join(escape(str(v)) for v in row.values())
    def content_type(self): return "text/csv"

class Sink(Protocol):
    def write(self, payload: bytes, meta: ExportMeta) -> None: ...

class FileSink:
    def __init__(self, path: Path): self.path = path
    def write(self, payload, meta): self.path.write_bytes(payload)   # 原子写见 §4

class Notifier(Protocol):
    def notify(self, meta: ExportMeta) -> None: ...

class WebhookNotifier:
    def __init__(self, url: str, client: httpx.Client): ...
    def notify(self, meta): ...    # 超时/重试策略收在类内，不再是 retries 裸参数
```

`export` 主流程坍缩为编排：

```python
def export(self, data, serializer: RowSerializer, sink: Sink,
           pipeline: DataTransform = Identity(), notifier: Notifier | None = None):
    body = "\n".join(serializer.serialize_row(r) for r in data).encode()
    sink.write(pipeline.apply(body), ExportMeta(batch_id=self.next_id()))
    if notifier:
        notifier.notify(...)
```

注意：**`retries=3` 这类裸参数消失了**——它属于各 Sink/Notifier 的内部策略（构造时注入），不再由最顶层函数签名一路透传（参数钻井，parameter drilling，是坏味道目录中的 overhead）。

### 步骤 3：压缩/加密的组合 → 装饰器（04 篇）

压缩与加密是"对字节流的叠加变换"，且需求必然继续叠加（签名？分块？）。继承组合爆炸的信号再次出现：

```python
class Transform(Protocol):
    def apply(self, data: bytes) -> bytes: ...

class Gzip:      ...
class Encrypt:   ...
class Sign:      ...

# 组合即管道，顺序显式化（原来藏在 elif 里的隐含约定变成类型外的显式组装）
pipeline = Encrypt(key, Gzip())        # 先压缩后加密 —— 与旧行为一致
# pipeline = Sign(kms, Encrypt(key, Gzip()))   # 新需求：零改动现有类
```

旧代码"encrypt 需与 compress 同开"的隐含约束随之消解：顺序由组装处显式决定，冲突由组装校验（工厂函数里一条断言），不再是分支间的暗契约。

### 步骤 4：存储选择 → 简单工厂 + DIP

```python
def make_sink(uri: str) -> Sink:
    if uri.startswith("file://"): return FileSink(Path(uri[7:]))
    if uri.startswith("s3://"):   return S3Sink(boto3.client("s3"), uri)
    raise ValueError(f"不支持的协议: {uri.split('://')[0]}")
```

- `Exporter` 只依赖 `Sink` 协议（DIP）：单测注入 `InMemorySink`，不再 mock 网络；
- 刻意**不引入**注册表/插件机制：三个实现用 if-工厂足够（01 篇 YAGNI；等实现超过 5~6 个再考虑 entry-points 注册）。

### 步骤 5：FTP 遗留功能 → 显式降级

对"没人记得还能不能用"的 FTP 分支，正确的重构动作不是纳入新抽象，而是**特征测试 + 标记弃用**：留一个 `FtpSink` 实现 + golden test 锁行为 + 文档标注 deprecation。**重构的职责是让现状显式，不是替业务做删除决定。**

## 3. 重构前后对比：量化验收

| 维度 | 前 | 后 |
| --- | --- | --- |
| `export` 签名 | 8 个参数、3 个裸字符串 | 4 个有类型参数 |
| 新增一种存储 | 改核心函数 | 新增一个 Sink 类 + 工厂一行 |
| 单测依赖 | mock S3/SMTP/FTP | 注入 InMemory 假实现 |
| 隐含约定 | 2 处（分支间） | 0 处（组装处显式） |
| 行数 | 412 | ~340（含协议定义） |

行数几乎没变——**重构的价值从来不是行数，而是变化成本**（01 篇的核心命题）。用 07 篇（架构篇）的话说：每根变化轴都拿到了独立演化的边界。

## 4. 复盘：本次重构用掉/没用掉的模式

**用掉**：策略（格式/存储/通知三轴）、装饰器（变换管道）、简单工厂（sink 构造）、依赖注入（测试替代）。

**没用掉且要说明为什么**：

- **抽象工厂**：没有"一族配套产品"需求（格式与存储正交），硬套会造出 `CsvFileFactory/CsvS3Factory/...` 组合爆炸；
- **观察者/事件总线**：只有一个通知场景且同步即可；等"多个下游各自反应"真实出现再上（08 篇事件驱动的判别信号）；
- **模板方法**：主流程没有稳定的"骨架+填空"结构，编排函数（组合）比继承骨架更直白。

这半节是本章真正想教的东西：**重构者对"不用哪个模式"的论证，与"用了哪个模式"同样重要**。

## 5. 迁移策略：大爆炸式重写 vs 绞杀者式替换

即便模块只有 400 行，也建议绞杀者式落地（09 篇手法）：新旧 `export` 并存 → 调用方逐个迁移到新签名 → golden test 保证逐字节等价 → 旧类删除。任何时候都可以安全回退到旧实现。
