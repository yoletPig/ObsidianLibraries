# 13 - 进阶：数据架构与一致性

> 进阶篇第 3 章。架构决策中**最不可逆**的一类是数据决策（07 篇可逆性分级：改存储 ≈ 心脏手术）。本章四条主线：存储选型的决策框架、事务与隔离级别的准确理解、跨服务一致性的工程手段、缓存与派生数据的治理。

## 1. 存储选型：从"要什么保证"倒推

选型正确的思考顺序不是"用什么数据库"，而是**先写下数据必须满足的保证，再倒推**：

| 你需要的保证 | 候选方向 | 典型代表 |
| --- | --- | --- |
| 强一致事务、复杂查询 | 关系型 | PostgreSQL、MySQL |
| 海量写入、按分区键查询、水平扩展 | 分片/宽列 | Cassandra 类、TiDB 类 |
| 文档形状多变、读多写少 | 文档库 | MongoDB、DynamoDB |
| 全文检索/倒排 | 搜索引擎 | Elasticsearch/OpenSearch |
| 对象/大文件 | 对象存储 | S3/OSS |
| 高频低延迟 KV | 内存 KV | Redis |
| 事件流持久化 | 日志型 | Kafka |
| 分析型聚合（列存） | OLAP | ClickHouse/StarRocks 类 |

两条元纪律比表格本身重要：

1. **默认关系型**：绝大多数业务数据需要事务与关联查询，PostgreSQL/MySQL 能覆盖到团队忘记还有其他选项的规模。**"数据量大"不等于"关系型不行"**（分库分表前还有索引优化/读写分离/缓存三层，09 篇阶梯）；
2. **多存储 = 多一致性难题**：每多一种存储，就多一份"两处数据如何对齐"的长期税（§3）。一个系统里 5 种存储通常意味着 5 倍的运维与对账工作，**每引入一种都要能回答"它替代了什么、放弃了什么"**。

## 2. 事务与隔离：把四个隔离级别读准

### 2.1 并发异常速查

| 异常 | 定义 | RU | RC | RR | SER |
| --- | --- | --- | --- | --- | --- |
| 脏读 | 读到未提交数据 | 可能 | 避免 | 避免 | 避免 |
| 不可重复读 | 同事务两次读同一行结果不同 | 可能 | 可能 | 避免 | 避免 |
| 幻读 | 同条件两次查询行集不同 | 可能 | 可能 | 视实现* | 避免 |
| 丢失更新 | 两事务读-改-写，后者覆盖前者 | 可能 | 可能 | 可能** | 避免 |

*SQL 标准的 RR 只防"纯幻读"，PostgreSQL 的 RR 实际提供快照隔离（MVCC，每个事务看到一致的快照），防住多数幻读但仍存在写偏斜（write skew）；**MySQL InnoDB 的 RR 通过间隙锁（next-key locking）在多数场景防幻读与丢失更新，但读后写仍需显式加锁（`SELECT ... FOR UPDATE`）才稳妥。各家实现与 SQL 标准有差异——**以所用数据库的官方文档为准，别背教科书表格**。

### 2.2 工程要点

1. **锁的最小化**：事务要短；事务里不做 RPC/HTTP 调用（把网络延迟变成锁持有时间，是连接池耗尽的头号原因）；
2. **乐观并发优先**：用版本号列（`UPDATE ... WHERE version=n`）做冲突检测，多数读多写少场景比悲观锁吞吐高；冲突率真高再上悲观锁；
3. **死锁的最小化**：多行更新按统一顺序（如按主键排序）访问——消灭"互相等待"的结构性成因。

## 3. 跨服务一致性：放弃幻想，选择模式

微服务拆分后（08 篇 v4 阶段），跨服务的本地事务不存在了。诚实的选项只有两类：

### 3.1 编排式 Saga：把长事务写成补偿链

```
下单 Saga：
  1. 订单服务：创建订单(pending)          ← 本地事务
  2. 库存服务：预占库存                    ← 失败 → 补偿 1：取消订单
  3. 支付服务：扣款                        ← 失败 → 补偿 2：释放库存 → 补偿 1
  4. 订单服务：订单置 confirmed
```

要点：

- **每步必须同时定义补偿动作**；补偿本身也要幂等（重试安全，Agent 系列 12 篇同款纪律）；
- **中间态可见**：Saga 执行中订单是 pending——业务流程（客服、报表）必须理解中间态；
- **补偿不可能时**（如已发货无法"取消发货"）：设计上避免——把不可补偿步骤尽量放最后，或改为人工处理流程；
- 编排（orchestration，中心 Saga 协调器）vs 协同（choreography，事件链各自响应）：前者流程显式可观测，后者少一个组件但流程散落。**步骤超过 3 个选编排**。

### 3.2 事务性发件箱（Transactional Outbox）：本地事务 + 可靠投递

跨服务事件的经典难题：**"更新数据库"与"发事件"是两个系统，无法原子**。直接发，崩溃点在中间就丢事件；先更新后发，同样。

解法：**同一个本地事务里写业务表 + outbox 表**，由独立的 relay 轮询/订阅 outbox 投递事件：

```sql
BEGIN;
  UPDATE orders SET status='confirmed' WHERE id=$1;
  INSERT INTO outbox(topic, payload, created_at)
       VALUES ('order.confirmed', '{"order_id":1}', now());
COMMIT;   -- 业务与事件同生共死
-- relay: SELECT ... FROM outbox ORDER BY id LIMIT n → 发布到 Kafka → 标记已发
```

代价与正确预期：投递是**至少一次**——消费方必须幂等（按事件 ID 去重）。这个模式与量化 08 篇的"标签工程"无关，但与 Agent 12 篇的事件日志是同一个思想：**先落盘、再传播、消费端幂等**。

### 3.3 一致性级别的诚实声明

跨服务数据必然出现不一致窗口。工程上的正确做法不是消灭它，而是**声明并管理它**：

- 对外接口文档写明哪些读是"可能陈旧"的；
- 关键读操作提供一致性锚点（读自己的写：读路由到主库，或读前先确认事件已消费）；
- 对账任务（reconciliation）：定期比对两处数据，差异告警——**对账不是丢人的补丁，是最终一致系统的标准组成部分**（金融系统叫"日切对账"）。

## 4. 缓存与派生数据：一致性的日常战场

### 4.1 缓存失效的策略选择

| 模式 | 流程 | 适用 |
| --- | --- | --- |
| Cache-aside（旁路） | 读：miss 则查库回填；写：更库 + 删缓存 | 默认选择 |
| Write-through | 写穿透缓存与库 | 一致性要求高、写少 |
| TTL-only | 只靠过期 | 可容忍陈旧窗口的统计类数据 |

经典问题"先删缓存还是先更新库"：cache-aside 标准做法是**先更新库，再删缓存**（配合 TTL 兜底）。为什么是"删"不是"改"：改缓存需要保证与库的一致（并发写会交错出旧值覆盖新值），删是幂等的、让下次读自然回填。残余风险窗口（删后、回填前读到旧值）用短 TTL 或延迟双删缓解——**没有零窗口的方案，只有与业务容忍度匹配的方案**。

### 4.2 击穿/穿透/雪崩（面试三连，也是真事故）

- **穿透**（查不存在的 key，每次都打到库）：空值缓存 + 布隆过滤器前置；
- **击穿**（热点 key 过期瞬间并发回填打垮库）：互斥回填（单飞 singleflight——同 key 只放一个请求去查库，其余等待）；
- **雪崩**（大量 key 同时过期）：过期时间加随机抖动。

### 4.3 派生数据的管理原则

缓存之外的派生数据（搜索索引、报表表、物化视图）遵循同一原则：**必须能从源头重建**。重建能力（replay 源数据重灌索引）是派生层的最后保险——丢失不可重建的派生数据，等于把派生层当成了真相源（违反单一事实来源，Single Source of Truth）。

## 5. 数据架构的演进预埋

1. **迁移脚本纳入版本控制**（schema 迁移工具如 Flyway/Alembic 的语义），每次变更是可回放的迁移步——schema 与代码同版本发布；
2. **扩列不缩列**：废弃字段先停写、观察、再删除（与 API 12 篇的破坏性变更流程同构）；
3. **大表变更先评估锁影响**：加列有默认值在部分数据库是全表重写（如 MySQL 8 前的某些 DDL）——大表的 DDL 是高危操作，变更前查清所用引擎的行为；
4. **备份要演练恢复**：没有做过恢复演练的备份等于没有备份。
