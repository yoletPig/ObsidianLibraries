# 08 - 核心架构模式

## 本篇目标

掌握四个最常用的架构风格：分层、模块化单体、微内核、事件驱动。每个讲清楚：结构 → 适用条件 → 代价。微服务放在 10 篇（演进案例）中结合拆分时机讨论，避免"一听微服务就上"的初学者陷阱。

## 1. 分层架构（Layered Architecture）

**结构**：代码按职责切层，**依赖只能自上而下**。经典四层：

```
表现层（API/UI）      ← 只关心协议与格式
业务层（Service）     ← 业务规则
持久层（Repository）  ← 数据存取
数据库
```

- **优点**：概念简单、团队分工天然按层、关注点分离；
- **代价一：分层泄漏**——为了省事把 Entity 直接传给 API 层，导致 DB 变更波及接口契约。对策：层间用 DTO 隔离（代价是要写转换代码——这本身就是取舍）；
- **代价二：业务逻辑被摊薄**——一个业务规则分散在 service/controller/repository 三层，改一个规则要动三层（业内称 "sinkhole anti-pattern"：请求穿过层层却没有任何一层真正加工业务，Richards & Ford 对此有专述）；
- **代价三：部署单体**——所有层必须整体部署，任何小改动都要全量回归。

**适用**：绝大多数中小型业务系统。它是默认起点，不是错误答案。

## 2. 模块化单体（Modular Monolith）

**结构**：**部署上是单体，代码内是边界清晰的模块**——模块之间只能通过公开接口调用，模块拥有自己的目录/包甚至独立数据库 schema：

```
monolith/
  orders/      ← 对外只暴露 orders/api.py，内部结构他人不可依赖
  inventory/
  billing/
```

关键纪律（Sam Newman《Monolith to Microservices》与社区共识）：

1. **模块间只走公开接口**，禁止 import 对方内部实现；
2. **（可选进阶）模块私有数据表**，禁止跨模块 join——这条纪律执行到位，未来的服务化拆分就是"搬代码"；执行不到位，拆分时面对的是解开几百处表级耦合；
3. 模块边界用**测试和静态检查固化**（如 import-linter 规则），靠口头约定必然失守。

**为什么它是当前的主流推荐**：微服务的收益（独立部署、独立扩缩、技术异构）在团队小、流量小的阶段**用不上**，而其成本（分布式事务、运维、网络延迟）**一分不少**。Martin Fowler 描述过这一模式及其代价（"MonolithFirst", 2015：多数成功微服务团队的起点都是妥善演化的单体）；"模块化单体"作为显式架构风格，近年已被广泛接受（如 Shopify 的模块化单体实践、《Modular Monoliths》相关著述）。

**要点**：模块化单体不是"微服务的妥协版"，而是**先收获边界、再按需收获部署独立性**的演进路径——10 篇实战将走这条路线。

## 3. 微内核架构（Microkernel / 插件架构）

**结构**：核心系统（最小业务能力）+ 插件（独立功能单元），核心通过注册机制与插件解耦：

```
┌─────────────────────────────────────┐
│ 核心系统（工作流调度/数据模型/注册表）   │
├─────────────────────────────────────┤
│ 插件A  插件B  插件C …（可独立增删）     │
└─────────────────────────────────────┘
```

- **典型案例**：VS Code（核心是编辑器外壳，语言支持/Lint/主题全是插件）、Eclipse、浏览器扩展、OSS 播放器；本仓库 Agent 系列 04 篇的 MCP 宿主 + Server 模式也是微内核形状；
- **判别信号**："同一个核心 + 多种可插拔能力，且能力集合会持续增长/由第三方扩展"；
- **代价**：插件与核心的**契约设计**是成败关键——契约太窄（插件做不了事）或太宽（核心被迫为个别插件改内部）；插件间通信与版本兼容（核心升级会不会 break 老插件）是长期税。

## 4. 事件驱动架构（Event-Driven Architecture, EDA）

**结构**：组件不直接调用彼此，而是**发布事件**/订阅事件，通过 broker（Kafka、RabbitMQ、云队列）解耦：

```
订单服务 ──publish──→ [order.paid] ──→ 库存服务(订阅)
                              └─────→ 通知服务(订阅)
                              └─────→ 积分服务(订阅)
```

- **得到**：发布者与消费者完全解耦（加消费者不动发布者）、削峰填谷、天然的审计流（05 篇观察者模式的规模化版本）；
- **必须付出的代价**（引用 Kafka/事件驱动社区的通行结论）：
  1. **最终一致**：库存扣减晚于支付成功，中间状态对外可见——业务上必须容忍或设计补偿；
  2. **消息语义要显式管理**：至少一次投递（at-least-once）意味着消费者必须**幂等**（同一消息处理两次结果不变）；Kafka 分区内有序、跨分区无序，需要顺序的业务要按 key 路由；
  3. **调试复杂**：一次业务流程的日志散落在多个异步消费者里，必须依赖 trace-id 贯穿。

**判别信号**："一个动作引发多个下游各自反应"“高峰流量需要缓冲"“下游允许延迟" → EDA；反之，调用方需要**立即拿到结果**的（下单要马上知道扣款成功），就该同步调用，硬套事件驱动只会自找补偿逻辑。

## 5. 四种风格的选择框架

按顺序问四个问题：

1. **系统很小、团队很小？** → 分层单体（甚至不分层）够用，别过度设计；
2. **需要清晰的模块边界、未来可能拆分？** → 模块化单体；
3. **能力集合持续增长、需要第三方扩展？** → 微内核（可与上两者叠加）；
4. **一动作多下游 / 需要削峰 / 能接受最终一致？** → 局部引入事件驱动（EDA 可以只用于系统的一部分，不必全盘）。

**注意：风格可以混合**——常见的成熟形态是"模块化单体 + 对外微内核 + 对内事件驱动"。
