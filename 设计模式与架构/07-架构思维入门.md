# 07 - 架构思维入门

## 本篇目标

从本篇起进入架构阶段。目标是完成三个思维转变：

1. 从"代码怎么写"到"**结构怎么定**"；
2. 从"正确性"到"**取舍**"（trade-off）；
3. 从"实现者"到"**决策者**"（会写架构决策记录）。

## 1. 架构是什么：一个可操作的定义

"架构"这个词被滥用得厉害。本系列采用 Richards & Ford 在《Fundamentals of Software Architecture》（O'Reilly, 2020）中的务实定义——他们把架构拆成两部分：

> **架构 = 系统的重要结构特性（structure）+ 需要艰难权衡的架构决策（architecture characteristics 与 decisions）。**

一个实用的判别法（同书提出）：**一个决策是架构级的，当它难以更改、且更改代价随时间剧增**。比如"单体还是微服务""用什么消息中间件""数据存哪"，改起来伤筋动骨，是架构决策；"这个函数放哪个文件""用哪个 JSON 库"，随时可换，不是。

架构师的核心工作因此不是"画框图"，而是：**识别质量属性 → 做可逆性分级 → 在相互冲突的质量属性之间做显式取舍 → 把决策写下来**。

## 2. 取舍思维：没有银弹，只有代价

架构的第一公理（Richards & Ford 的表述）：

> **Everything in software architecture is a trade-off.**（一切皆是取舍。）

推论：如果有人向你推荐一个架构方案却说不出它的代价，**这个方案还没被理解**。每个"好处"背后都对应一个"坏处"，例如：

| 方案 | 得到 | 付出 |
| --- | --- | --- |
| 微服务 | 独立部署、独立扩缩 | 分布式复杂度、运维成本、最终一致性 |
| 强一致数据库 | 数据永远正确 | 写入延迟、扩展受限 |
| 缓存 | 读性能暴涨 | 数据陈旧、缓存失效逻辑复杂 |
| 事件驱动 | 削峰、解耦 | 调试困难、最终一致、消息语义要管理 |

**"Atwood's Law"式的警惕**同理适用于架构：不要因为"可能用得上"而引入复杂度。架构决策的隐性成本是**认知负荷**——系统每多一种机制，每个后来者（包括三个月后的你自己）都要多学一样东西。

## 3. 康威定律：你的组织结构会变成你的架构

> **设计系统的组织，其产生的设计等价于该组织的沟通结构。**（Melvin Conway, 1968）

这不是讽刺而是工程规律：4 个团队合写的系统，天然会长出 4 个模块边界。架构师必须**同时设计两样东西**——技术结构与组织结构。反过来用：微服务的流行不只是技术原因，也是"让小团队各自拥有服务、独立部署"的组织原因（这正是 Amazon "two-pizza team" 与服务化绑定的逻辑）。

## 4. 架构决策记录（ADR）：把"为什么"写下来

架构决策最大的资产不是结论，而是**当时的理由与被否决的备选项**。半年后新人问"为什么用消息队列不用 RPC"，没人记得，于是要么盲从要么推翻重来。**ADR（Architecture Decision Record）**是轻量解法：每个重大决策一个短文档。

最小模板（Michael Nygard 2011 年提出的格式精简版）：

```markdown
# ADR-007: 订单通知改用事件总线

日期: 2026-11-06 | 状态: 已接受

## 背景
通知渠道已从 2 个增至 5 个，每加一个渠道都要改订单核心服务并回归测试。

## 决策
引入进程内事件总线，订单服务只发布 order.paid 事件，渠道各自订阅。

## 备选方案
1. 订单服务直接调用各渠道（维持现状）——否决：继续违反 OCP，核心服务耦合渠道数
2. 立即上 Kafka——否决：当前 QPS 下进程内总线足够，运维成本不匹配（YAGNI）

## 后果
+ 新增渠道零改动订单服务
- 回调顺序不确定（已约定：渠道间不依赖顺序，见 ADR-008）
- 事件消费失败需要重试机制（TODO: ADR-009）
```

ADR 的关键纪律：**记录被否决的方案及否决理由**——这是防止组织反复踩坑的核心价值。

## 5. 可逆性：架构决策的新视角

Richards & Ford 强调的一个现代视角：**优先做可逆（可低成本推翻）的决策**。

- 可逆：换一个 HTTP 框架、换一个 JSON 库、进程内总线换实现；
- 难逆：数据库选型、单体→微服务、对外 API 契约。

判断依据是"迁移成本 × 概率"，而不是"哪个更先进"。这也解释了一条经典工程路线的合理性：**先用最简单的方案，把演进的可能留好接缝，等规模证明需要时再升级**（08 篇"模块化单体优先"的立论基础）。

## 6. 从设计模式到架构：尺度变了，原则没变

| | 设计模式 | 架构 |
| --- | --- | --- |
| 尺度 | 类与对象 | 服务、模块、数据流 |
| 变化的时间尺度 | 需求迭代（天/周） | 组织与规模变化（月/年） |
| 核心手法 | 抽象 + 多态 | 边界划分 + 依赖方向 + 冗余/隔离 |
| 共同哲学 | **隔离变化，依赖稳定**（01 篇） | **完全相同** |

策略模式把"会变的算法"隔离进可替换实现；架构把"会变的服务"隔离进边界清晰的模块。**思想一脉相承，只是尺度放大**——这是本系列把两者编在一起的初衷。
