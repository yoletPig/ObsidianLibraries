# 01 - 为什么需要设计模式

## 本篇目标

在接触任何具体模式之前，先回答一个根本问题：**设计模式到底在解决什么问题？** 想清楚这个，后面学每个模式才有"钩子"可以挂。

## 1. 一切从"变化"开始

设想一个完全不会变的程序：读一个文件、算一个数、写出去。这样的程序不需要任何设计模式——直接写就行。

问题在于**真实需求会变**：

- 今天导出 CSV，下个月要导出 Excel；
- 今天日志打到控制台，明天要打文件、发网络；
- 今天付款用支付宝，明天要接微信支付。

软件工程里有一条经验规律（来自《代码大全》等经典著作对成本数据的长期观察）：**修改一个已有系统的成本，远高于当初写对它的成本**——需求变更、缺陷修复越到项目后期越贵。设计模式就是**为"将来会变的地方"预先留好接缝**的手法。

判断一个地方值不值得留接缝的标准：**它变过，或者你确信它会变**。没变过的代码不要抽象（YAGNI：You Aren't Gonna Need It，出自极限编程社区）。

## 2. 耦合：接缝的反面

看一段典型的"坏"代码：

```python
class ReportService:
    def export(self, data):
        # 直接 new 具体类 + 硬编码细节
        csv = CsvWriter()
        csv.open("report.csv")
        for row in data:
            csv.write(row.name + "," + row.value)
        csv.close()
```

`ReportService` 和 `CsvWriter` 之间存在**耦合**：导出格式改了，必须改 `ReportService`；想测试它还得真的写文件。变化的病毒沿着耦合传播——改一处，波及一片。

设计模式的共同目标一句话概括：

> **找到变化，把它封装起来，让系统里稳定的部分不依赖会变的部分。**

GoF 在《Design Patterns》（1994）第一章提出的两大原则正是这个意思：

1. **Program to an interface, not an implementation**（面向接口编程，而非面向实现）；
2. **Favor object composition over class inheritance**（优先使用对象组合而非类继承）。

## 3. 模式是什么、不是什么

GoF 的定义：

> A design pattern is a described solution to a recurring design problem——**在特定情境下，反复出现的设计问题的、被命名过的可复用解法**。

三个关键词拆解：

- **可复用**：不是某段具体代码，而是"解法形状"——一份代码不会出现在两个项目里，但同一个"形状"会；
- **命名过的**：模式的最大价值之一是**团队词汇表**。"这里加个观察者"一句话传达了结构、职责与预期行为，省掉半小时解释；
- **特定情境**：每个模式有适用条件。脱离情境谈模式，是模式学习第一大坑。

**模式不是**：

- 不是银弹：模式解决"结构"问题，不解决算法、性能、需求理解错误；
- 不是越多越好：一个模式就引入一层间接性（更多类、更多跳转）。**每个模式都有代价**，本系列每篇都会列出"代价"小节；
- 不是发明出来的新东西：模式是对**已有好代码的归纳**。GoF 的 23 个模式来自对面向对象代码库的总结提炼。

## 4. 23 个模式的地图

GoF 按**目的**把 23 个模式分三类（本系列按此展开）：

| 类别 | 解决的问题 | 包含的模式 |
| --- | --- | --- |
| **创建型**（5） | 对象怎么创建——把"创建"从使用处剥离 | 单例、工厂方法、抽象工厂、建造者、原型 |
| **结构型**（7） | 类与对象怎么组合成更大的结构 | 适配器、装饰器、代理、外观、桥接、组合、享元 |
| **行为型**（11） | 对象之间怎么分配职责、怎么通信 | 策略、观察者、命令、模板方法、状态、迭代器、中介者、责任链、备忘录、访问者、解释器 |

另一个关键维度是贯穿 23 个模式的**共同套路**（从 GoF 各模式的动机部分可归纳，也是教学者常用的概括）：**找一个变化点 → 设计一个抽象（接口）→ 让变化点实现它 → 让稳定部分依赖这个抽象**。后面每个模式都会回到这条主线。

## 5. 一个贯穿实例：通知系统

以后各篇会用同一个演进中的例子——一个订单通知系统——展示模式如何逐个登场：

```python
# 版本1：能跑
def notify(order):
    print(f"发送短信: 订单{order.id}已支付")

# 版本2：需求变了——还要发邮件。复制粘贴式扩展：
def notify(order):
    send_sms(order)
    send_email(order)      # 改了核心函数

# 版本3：需求又变——大客户走企业微信、夜里不发短信、测试时都不发……
def notify(order):          # ← 已经没人敢改这个函数了
    ...
```

版本 3 的函数就是典型的**需求墓地**：每次变化都往里堆 if，直到没人理解、没人敢动。从这个例子出发：

- **策略模式**（05 篇）：不同渠道 = 可替换的策略；
- **观察者模式**（05 篇）："订单已支付"是一个事件，关心的人自己订阅；
- **责任链**（06 篇）：夜间不发的规则 = 链上的一环；
- **外观模式**（04 篇）：把"通知"包装成一个稳定门面。

现在不需要看懂这些模式，只需要记住这个例子在"未设计"状态下的痛感——**模式的每一步引入都是为了消掉一种具体的痛**。
