# 06 - 行为型模式（下）：状态、迭代器、中介者、责任链

## 本篇目标

补齐常用的高价值行为型模式（状态、迭代器、中介者、责任链），然后做一件本系列最重要的反思：**什么时候不该用模式**。

## 1. 状态模式（State）

**动机**：对象行为随内部状态改变，且状态多、转换复杂——把每个状态封装成类，用多态替代状态相关的大 if-else。

```python
class OrderState(ABC):
    @abstractmethod
    def pay(self, order): ...
    @abstractmethod
    def ship(self, order): ...

class Pending(OrderState):
    def pay(self, order):
        order.state = Paid()          # 状态转换由状态类自己管理
        print("已支付")
    def ship(self, order):
        raise InvalidTransition("未支付不能发货")   # 非法转换显式拒绝

class Paid(OrderState):
    def pay(self, order): raise InvalidTransition("重复支付")
    def ship(self, order): order.state = Shipped()

class Order:
    def __init__(self): self.state: OrderState = Pending()
    def pay(self):  self.state.pay(self)
    def ship(self): self.state.ship(self)
```

与策略模式的辨析（最后一个高频混淆点）：两者结构几乎相同（接口 + 可替换实现），**意图不同**——策略是调用方**主动选择**算法且各算法互不知晓；状态是对象**自行流转**，且状态类之间**相互知道**（`Paid` 里 new 出 `Shipped`）。一句话：策略改的是"算法"，状态改的是"对象自身行为"。

状态机的现代形态：当状态多、转换复杂时，手写类会膨胀，工程上常用**显式状态机定义**（转换表或库，如 Python 的 `transitions`、Spring Statemachine），核心思想一致——**让非法转换显式失败，而不是隐式错乱**。

## 2. 迭代器模式（Iterator）

**动机**：顺序访问聚合对象的元素，**不暴露内部结构**。

```python
class Playlist:
    def __init__(self): self._songs = []
    def __iter__(self):               # Python 协议：返回迭代器
        return iter(self._songs)

class ShuffledPlaylist:               # 换一种遍历方式，调用方无感
    def __init__(self, songs): self._songs = list(songs)
    def __iter__(self):
        random.shuffle(self._songs)
        return iter(self._songs)

for song in playlist: ...             # 调用方完全不关心内部怎么存
```

这个模式已经被语言**内化**：Python 的 `__iter__`/`__next__` 协议、Java 的 `Iterable`/`Iterator`、C++ 的 iterator 概念、JS 的 `Symbol.iterator`。**今天你不需要"实现"它，只需要"遵守"它**——遍历算法（正序、倒序、随机、过滤）作为独立迭代器与容器解耦的思想，已经融进语言的 for 循环与生成器里。这是"模式被语言吸收"的最佳案例（03 篇的建造者也有同样趋势）。

## 3. 中介者模式（Mediator）

**动机**：N 个对象两两交互 → 耦合 O(N²)；引入中介者，全部只和中介说话 → O(N)。

```
两两交互:  A↔B A↔C A↔D B↔C B↔D C↔D   (6 条边)
经过中介:  A—M  B—M  C—M  D—M        (4 条边，且互不相知)
```

典型场景：对话框内按钮、输入框、列表的联动（GUI 圈的经典案例）；现代架构中，**消息中间件**（Kafka/RabbitMQ）让服务互不直连，是中介者思想的规模化。代价：中介者可能膨胀成新的"上帝对象"——它知道了太多细节。当联动规则超过一屏代码，考虑拆多个中介者或改用事件驱动。

## 4. 责任链模式（Chain of Responsibility）

**动机**：一个请求依次经过多个处理器，**每个处理器决定处理或传给下一个**，处理器之间互不感知。

```python
class Handler(ABC):
    def __init__(self, nxt: "Handler | None" = None): self.nxt = nxt
    @abstractmethod
    def handle(self, req): ...

class AuthHandler(Handler):
    def handle(self, req):
        if not req.user: return "401"
        return self.nxt.handle(req) if self.nxt else None

class RateLimitHandler(Handler):
    def handle(self, req):
        if req.exceeded(): return "429"
        return self.nxt.handle(req) if self.nxt else None

chain = AuthHandler(RateLimitHandler(BusinessHandler()))
```

现代落地比教科书版本多得多：**Web 中间件**（Express/Flask/Django 的 middleware 栈）、异常处理的 except 链、审批流。本仓库 Agent 系列 08 篇的"纵深防御"层层检查，也是一种责任链。

两个工程要点：**链的组装顺序即语义**（鉴权必须先于业务，组装处要显式且受审）；**注意断链**——某个处理器吞掉请求但忘了 return，是这类代码最常见的 bug。

## 6. 最重要的反思：模式滥用

学完模式清单，必须立刻补上解毒剂。三个常见的滥用信号：

1. **为未来而抽象**（违反 YAGNI）："以后可能有第二种实现，先抽个接口"——那个"以后"往往永远不来，抽象层却永远要维护。**等第一种变化真实出现时再抽象**（Rule of Three 的精神：重复出现三次再提取，出自 Martin Fowler《Refactoring》）；
2. **模式堆叠**：一个类套了工厂、装饰器、代理三层，没人读得懂。判断标准：**删掉这个模式，代码会更难懂吗？** 不会就删；
3. **模式即目标**："我们的设计里用了 15 个模式"不是优点。模式是手段，**可读性和可维护性**才是目标。GoF 原书副标题是 "Elements of **Reusable** Object-Oriented Software"——复用是目的，模式只是路径。

一个诚实的观察：现代语言与框架吸收了大量模式（迭代器进协议、建造者进流式 API、观察者进事件总线、代理进 AOP），**很多情况下"用好语言内建机制"比"手搓模式"更符合模式精神**。
