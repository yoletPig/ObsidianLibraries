## 1. 进阶算子：选 Softmax（含在线归约）

### 1.1 为什么进阶

第 5-6 周的 fused Add+RMSNorm 是"逐元素 + 简单归约"。Softmax 更难，因为：

$$
\text{softmax}(x_i) = \frac{e^{x_i}}{\sum_j e^{x_j}}
$$

需要**两次遍历数据**（先求最大值和指数和，再归一化），且为数值稳定要先减最大值：

$$
\text{softmax}(x_i) = \frac{e^{x_i - m}}{\sum_j e^{x_j - m}}, \quad m = \max_j x_j
$$

### 1.2 在线归约（online reduction）

若一行数据分多块处理，不能等所有块都来才归约——用**在线算法**边扫边更新：

```
初始化: m = -inf, d = 0        # m=最大值, d=指数和
每块:
    m_new = max(m, block_max)
    d = d * exp(m - m_new) + sum(exp(block - m_new))
    m = m_new
# 第二遍: out = exp(x - m) / d
```

关键技巧：当最大值更新时，用 `exp(旧m - 新m)` 缩放累积的 `d`，保持正确。这与 FlashAttention 的在线 softmax 是**同一个数学**（呼应你学过的注意力优化）。

### 1.3 跨核数据分块

若一行跨多个核（或按行分给不同核），要设计：
- **按行切**：每核独立处理完整的行 → 无跨核通信，优先选；
- **一行跨核**：需跨核归约通信 → 复杂，尽量避免。

**设计原则**：让归约维度（行）完整落在单核内，把并行度放在行数上。

## 3. Profiling 驱动优化（交付核心技能）

### 3.1 用 msprof 抓算子性能

```bash
msprof --application="python your_op_test.py" \
       --output=./prof_out \
       --aic-metrics=PipeUtilization,MemoryUsage
```

关注的指标：
- **Cube/Vector 利用率**：计算单元忙的时间占比；
- **流水气泡**：搬运与计算之间的空隙；
- **各阶段耗时**：CopyIn / Compute / CopyOut 的占比。

### 3.2 读懂利用率

| 现象 | 诊断 | 优化方向 |
| --- | --- | --- |
| Vector 利用率低、有明显空隙 | 流水没起来/搬运阻塞 | 双缓冲、预取 |
| 计算慢 | 算法/指令效率低 | 用更优算子接口、减少冗余 |
| 搬运占比过高 | 块太小、搬运频繁 | 加大块（若 UB 允许） |

### 3.3 优化前后对比（交付）

```
| 版本 | 延迟 | Vector 利用率 | 改动 |
| 初版（未优化流水） | | | |
| + double buffer | | | 流水并行 |
| + 块大小调优 | | | 减少搬运次数 |
| 最终 | | | |
```

每步改动对应一个指标变化——这就是"用数据说话"的优化报告。

## 4. 生态判断力（面试必答题）

### 4.1 什么时候用现成算子库

- 算子在 CANN 算子库**已有且性能可接受** → 直接用；
- 通用算子（GEMM、卷积、标准激活）→ 几乎都有现成优化的实现。

### 4.2 什么时候必须自研

1. **算子库没有**：模型用了新结构（如你学的某些新注意力变体）；
2. **性能不够**：现成算子是通用实现，你的场景能特化优化（如特定形状、可融合）；
3. **融合需求**：把多个小算子融合成一个大算子，减少访存往返（如你的 fused Add+RMSNorm）。

### 4.3 判断框架

```
是否有现成算子？ ──否──> 自研
    │是
现成性能够吗？ ──否──> 能否特化/融合优化？──> 自研
    │是
直接用
```

## 6. 工程权衡与失效模式

### 6.1 权衡

- **自研成本**：算子开发门槛高、周期长，仅在有明确收益时做；
- **特化程度**：越特化越快但越不通用；
- **融合粒度**：融合多省访存，但算子变大难调、复用性降。

### 6.2 失效模式

1. **在线归约错**：最大值更新时忘了缩放累积和。修复：严格按在线算法公式。
2. **跨核归约混乱**：一行跨核导致通信复杂。修复：按行切、避免跨核归约。
3. **接入后崩**：算子接口与框架约定不符。修复：严格按注册规范、先单算子后接入。
4. **优化无依据**：凭感觉改。修复：先 msprof 定位瓶颈再改，每步留数据。

## 7. 延伸思考题（含解析）

**Q1**：Softmax 的在线归约在解决什么问题？
**A**：数据分块处理时，不能等全部数据到位才求最大值和指数和。在线算法边扫边更新最大值与指数和，最大值变化时用 `exp(旧m-新m)` 缩放累积量保持正确。这与 FlashAttention 的在线 softmax 同一数学。

**Q2**：为什么归约维度（行）要尽量落在单核内？
**A**：跨核归约需要核间通信，代价高且复杂。按行切、让每核处理完整的行，可把并行度放在行数上、避免通信。这是数据分块设计的基本原则。

**Q3**：怎么用数据证明你的优化有效？
**A**：msprof 抓优化前后的延迟、Cube/Vector 利用率、各阶段耗时。每步改动对应指标变化（如加双缓冲后流水气泡消失、利用率上升）。有前后对比数据才算数。

**Q4**：什么场景必须自研算子？
**A**：① 算子库没有该算子；② 现成算子性能不够、可针对你的形状/场景特化；③ 需要融合多个小算子减少访存。否则优先用现成的。

**Q5**：fused 算子为什么通常比多个独立小算子快？
**A**：独立算子之间要经 HBM 读写中间结果，访存往返多；融合后中间结果留在片上（UB），一次搬入、算完一次搬出，大幅减少访存——这正是所有算子融合的核心收益。
