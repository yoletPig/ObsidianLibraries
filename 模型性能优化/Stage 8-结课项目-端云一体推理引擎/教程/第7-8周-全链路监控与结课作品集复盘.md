## 1. 全链路监控：端云协同的专属指标

### 1.1 在 Stage 7 大盘上增加的指标

端云协同引入了"分流"这个新维度，必须监控：

| 指标 | 含义 | 异常信号 |
| --- | --- | --- |
| **分流比例** | 端侧/云端/级联的请求占比 | 比例突变 = 分流逻辑或负载异常 |
| **级联触发率** | 端侧答不好升级的比例 | 升高 = 端侧能力不足或阈值问题 |
| **缓存命中率** | 端侧回填缓存的命中 | 低 = 缓存键设计差 |
| **端侧延迟** | 端侧推理耗时分布 | 升高 = 板端资源争用/降频 |
| **端云一致性** | 同类问题端云答案差异 | 分歧率升高 = 对齐失效 |

### 1.2 实现：路由层埋点

```python
from prometheus_client import Counter, Histogram

ROUTE_DECISION = Counter(
    "route_decision_total", "分流决策计数",
    ["decision"])   # edge/cloud/cascade/fallback
CASCADE_TRIGGER = Counter("cascade_trigger_total", "级联升级次数")
EDGE_LATENCY = Histogram("edge_latency_seconds", "端侧推理延迟")
CACHE_HIT = Counter("edge_cache_hit_total", "端侧缓存命中")

# 在路由层各处打点
@app.post("/route")
async def route(req, client):
    decision = classify(req)
    ROUTE_DECISION.labels(decision=decision).inc()
    # ...
```

### 1.3 为什么盯分流比例

分流比例是系统健康度的**综合信号**：
- 云端调用占比突然升高 → 级联阈值漂移 / 请求分布变化 / 端侧故障；
- 级联触发率升高 → 端侧模型能力跟不上请求难度；
- 端侧兜底次数升高 → 云端过载或不稳。

**一个比例数字的变化，往往是最早的故障征兆**——比延迟告警还早。

## 2. 端到端追踪：贯穿端侧→路由→云端

### 2.1 用 request_id 串全链路

第 3-4 周契约里的 `request_id` 在这里发挥价值：

```
端侧日志：[req-abc] edge infer, conf=0.42, 320ms
路由日志：[req-abc] cascade triggered -> cloud
云端日志：[req-abc] cloud infer, 1.2s
追踪后端：req-abc 的完整时间线（三段 span）
```

### 2.2 OpenTelemetry 跨服务

```python
# 路由层转发时把 trace context 传给云端
headers = {"traceparent": current_traceparent()}
await client.post(f"{CLOUD_URL}/infer", json=req, headers=headers)
```

云端与端侧接入同一个 trace 后端（Jaeger/Tempo），一条请求的完整时间线即可视化——**哪里慢、哪里卡，一眼看清**。

## 5. 工程权衡与失效模式

### 5.1 权衡

- **监控粒度**：端云指标多，全采成本高。核心指标全采，细粒度采样。
- **作品集广度**：15 个 Stage 都列会失焦。挑 3 个最硬的深挖，其余做索引。

### 5.2 失效模式

1. **分流比例无监控**：分流逻辑漂移无人知。修复：比例指标 + 突变告警。
2. **追踪断链**：request_id 没贯穿端云，问题定位难。修复：契约强制 + 全链路打点。
3. **作品集流水账**：罗列所有工作但无重点。修复：电梯陈述 + 3 个深挖点结构。
4. **演示翻车**：现场演示依赖网络/硬件。修复：录屏备份 + 降级演示路径。

## 6. 延伸思考题（含解析）

**Q1**：为什么分流比例本身要监控？
**A**：它是系统健康度的综合信号：云端调用占比突升（分流漂移/端侧故障）、级联率升高（端侧能力不足）、兜底增多（云端不稳）都会最先反映在比例上，常比延迟告警更早暴露问题。

**Q2**：端云协同的追踪怎么做？
**A**：用贯穿端云的 request_id 作关联键，各层日志带该 ID；进阶用 OpenTelemetry 传递 trace context，把端侧→路由→云端串成一条可视化时间线，定位慢在哪一段。

**Q3**：作品集为什么"挑 3 个深挖"而不是全列？
**A**：面试官注意力有限，全列 = 全浅。挑最硬的 3 个（如 Ascend C 算子、量化数学、端云架构）展示"能往下挖三层"的深度，其余做索引供追问。深度比广度更能证明能力。

**Q4**：现场演示最大的风险是什么？怎么防？
**A**：依赖实时网络/硬件，易翻车。防法：① 提前录屏备份；② 准备降级演示路径（如只演示端侧离线部分）；③ 演示前全链路预热检查。

**Q5**：这套系统如果继续演进，下一步做什么？
**A**：合理方向：① 真实多机部署验证（补模拟的差距）；② 端侧模型持续蒸馏（云端使用数据回流）；③ 分流决策升级为学习型（在线学习请求难度）；④ 扩展到多模态（Omni 模型端云协同）。展示演进思路 = 展示技术视野。
