## 1. 第一性原理：云端侧是"能力天花板"

### 1.1 云端在端云协同中的角色

端侧管隐私、低延迟、兜底；**云端管能力上限**——复杂推理、长文、知识密集问题都靠它。所以云端侧要用**最强配置**：最优量化模型 + 调优引擎 + 弹性编排。

### 1.2 三块积木的衔接

$$
\text{Stage 2 量化模型（AWQ-4bit 7B）} \;+\; \text{Stage 5 调优 vLLM} \;+\; \text{Stage 7 编排} \;=\; \text{云端服务}
$$

本周就是把这三块焊起来并压测定标。

## 2. 云端栈装配

### 2.1 量化模型 + 引擎

用 Stage 2 横评选出的最优量化模型（如 AWQ-4bit 7B），配 Stage 5 调优的引擎参数：

```bash
vllm serve <模型>-AWQ \
    --quantization awq \
    --max-model-len 8192 \
    --max-num-seqs 64 \                    # Stage 5 调优值
    --gpu-memory-utilization 0.9 \         # Stage 5 调优值
    --enable-chunked-prefill \
    --api-key $KEY
```

### 2.2 包一层服务层（供路由层调用）

引擎的 OpenAI 接口之上，包一个**业务服务层**，加路由层需要的字段：

```python
# cloud_service.py（FastAPI）
from fastapi import FastAPI
from openai import OpenAI

app = FastAPI()
engine = OpenAI(base_url="http://localhost:8000/v1", api_key=KEY)

@app.post("/infer")
async def infer(req: dict):
    resp = engine.chat.completions.create(
        model=req["model"],
        messages=req["messages"],
        max_tokens=req.get("max_tokens", 512),
        stream=False,
        extra_body={"request_id": req["request_id"]},   # 去重用
    )
    return {
        "request_id": req["request_id"],
        "text": resp.choices[0].message.content,
        "source": "cloud",                     # 标记来源（端云对比用）
        "latency_ms": ...,
    }
```

### 2.3 SSE 流式接口

供路由层把云端输出**边生成边转发**给用户：

```python
from fastapi.responses import StreamingResponse

@app.post("/infer/stream")
async def infer_stream(req: dict):
    def gen():
        stream = engine.chat.completions.create(
            model=req["model"], messages=req["messages"], stream=True)
        for chunk in stream:
            delta = chunk.choices[0].delta.content or ""
            yield f"data: {delta}\n\n"
        yield "data: [DONE]\n\n"
    return StreamingResponse(gen(), media_type="text/event-stream")
```

### 2.4 编排（复用 Stage 7）

把服务容器化，用 Stage 7 的 K8s（Kind 模拟）或 Ray Serve 编排，配自动扩缩。**云端侧 = 引擎 + 业务服务层 + 编排**，三层各司其职。

## 3. API 契约（本周交付核心二）

路由层与云端服务之间的接口约定，必须显式定义：

```
POST /infer
请求：
  request_id: string      # 全局唯一，去重 + 追踪
  messages: [...]         # OpenAI 格式
  model: string
  max_tokens: int
  timeout_ms: int         # 路由层的等待预算

响应：
  request_id: string
  text: string            # 完整回答
  source: "cloud"
  confidence: float       # 云端自评置信度（可选）
  latency_ms: int

流式：POST /infer/stream（SSE）
错误：503（过载）/ 504（超时）——路由层据此触发降级
```

**关键约定**：
- `request_id` 贯穿端云，用于去重与全链路追踪；
- `timeout_ms` 让云端知道路由层的预算，避免白算；
- 过载返回 503（而非排队卡死），让路由层能切端侧兜底。

## 4. 压测定标（本周交付核心三）

### 4.1 要测出什么

压测不是为了好看，是给**路由层提供分流依据**：

```
路由层需要知道：
- 云端当前队列长度（是否过载 → 端侧兜底）
- 云端典型延迟（决定能接受的请求类型）
- 云端吞吐上限（容量规划）
```

### 4.2 标准压测报告

```bash
python benchmark_serving.py \
    --backend openai-chat --base-url http://<云端>:8080 \
    --model <模型> --dataset-name sharegpt \
    --num-prompts 200 --request-rate 8
```

报告模板：

```
《云端服务压测定标报告》
配置：AWQ-4bit 7B，vLLM 调优配置，K8s N 副本
负载：ShareGPT 200 条，request-rate 8
结果：
  吞吐：__ tokens/s（单副本 / 集群）
  TTFT P50/P99：__ / __ ms
  TPOT P50/P99：__ / __ ms
  满足 SLO 的最大并发：__
自动扩缩验证：负载翻倍时副本从 N → 2N，延迟回落
```

**这份报告的"满足 SLO 的最大并发"就是路由层判断"云端是否过载"的阈值依据**。

## 5. 工程权衡与失效模式

### 5.1 权衡

- **量化激进程度**：云端是能力天花板，量化别太狠伤质量（用横评结论）；
- **流式缓冲**：SSE 转发有缓冲延迟，调小提升体验但增网络开销；
- **副本数**：多则抗载但成本高，按定标的单副本能力算。

### 5.2 失效模式

1. **无 request_id 去重**：级联升级时重复请求重复计费。修复：全局 request_id + 云端去重。
2. **过载返回 200 排队**：路由层以为正常、用户干等。修复：过载明确返回 503 触发降级。
3. **timeout 不一致**：云端算得比路由层等得久，白算。修复：请求带 `timeout_ms`，云端尊重。
4. **流式断流**：网络抖动 SSE 中断。修复：客户端重连 + 断点续传（带已生成偏移）。

## 6. 延伸思考题（含解析）

**Q1**：云端侧为什么用"最强配置"而不是省钱配置？
**A**：云端承载的是端侧答不了的复杂请求，是能力天花板。这里省质量 = 系统上限降低。成本优化靠"把简单请求拦在端侧"，而不是削弱云端。

**Q2**：API 契约里为什么必须有 request_id？
**A**：① 去重——级联升级可能重复提交，云端据此幂等处理避免重复计费；② 全链路追踪——贯穿端侧→路由→云端的追踪标识。

**Q3**：云端过载为什么返回 503 而不是排队？
**A**：排队会让路由层误以为"正常处理中"，用户无限等待。明确 503 让路由层立即感知并触发降级（切端侧兜底），保住可用性。

**Q4**：压测定标对路由层有什么用？
**A**：定标给出"云端满足 SLO 的最大并发/队列阈值"，路由层用它判断云端是否过载、决定是否端侧兜底。没有定标，分流就是盲目的。

**Q5**：流式转发相比整句返回，端云链路多了什么复杂度？
**A**：要处理 SSE 的转发缓冲、断流重连、断点续传。换来的是首字延迟大幅降低（边生成边到用户）。体验收益通常值得这个复杂度。
