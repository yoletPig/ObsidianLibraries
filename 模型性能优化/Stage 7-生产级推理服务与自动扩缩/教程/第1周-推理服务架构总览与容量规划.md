## 1. 第一性原理：从"能跑"到"能扛"

### 1.1 单机推理与生产服务的差距

本地跑 `vllm serve` 只是起点。生产服务还要回答：

- 流量涨 10 倍怎么办？（**扩缩**）
- 一张卡挂了怎么办？（**容错**）
- 怎么知道服务健不健康？（**可观测性**）
- 每月账单能不能接受？（**成本**）

架构就是为这些问题准备的答案。

### 1.2 四层架构

```
┌─────────────────────────────────────────────┐
│ 接入层：网关、限流、鉴权、协议转换             │
├─────────────────────────────────────────────┤
│ 路由层：负载均衡、模型路由、灰度/AB           │
├─────────────────────────────────────────────┤
│ 推理层：引擎集群（vLLM/MindIE 实例 × N）      │
├─────────────────────────────────────────────┤
│ 存储层：模型仓库、结果缓存、日志               │
└─────────────────────────────────────────────┘
```

**为什么不能裸暴露引擎**：
- 没有限流 → 突发流量打垮服务；
- 没有负载均衡 → 单实例过载、其余闲置；
- 没有模型路由 → 无法灰度新版本；
- 没有监控 → 故障靠用户投诉发现。

### 1.3 每层的关键决策

| 层 | 核心决策 | 本周相关性 |
| --- | --- | --- |
| 接入 | 限流算法（令牌桶）、超时设置 | 容量规划的输入假设 |
| 路由 | 轮询/最少连接/一致性哈希 | 第 3 周 |
| 推理 | 实例数、机型、引擎配置 | **本周核心** |
| 存储 | 模型分发、缓存策略 | 第 5-6 周 |

## 2. 容量规划方法学（本周核心）

### 2.1 从业务量到资源量的换算链

$$
\text{峰值 QPS} \xrightarrow{\times \text{每请求 token 量}} \text{token/s 需求} \xrightarrow{\div \text{单卡能力}} \text{实例数}
$$

每一步都要有**实测或文献支撑**的数字，并写明假设。

### 2.2 完整计算书模板（交付）

**输入假设**（逐条写清）：

```
业务假设：
- 峰值 100 QPS（每秒 100 个请求）
- 平均输入 512 token、输出 256 token
- SLO: TTFT ≤ 500 ms, TPOT ≤ 50 ms/token
- 峰值持续 1 小时，其余时段 30% 负载

实测依据（来自你的 Stage 5 压测）：
- 单卡 A100 + Qwen2.5-7B：
  满足上述 SLO 时，单实例可持续吞吐 ≈ X tokens/s
  单实例可支撑并发 ≈ Y（KV cache 约束）
```

**推算**：

```
1. 每秒需要的输出 token 总量：
   100 QPS × 256 token/req = 25,600 tokens/s（输出）

2. Prefill 算力需求：
   100 QPS × 512 token/req = 51,200 tokens/s（prefill）

3. 实例数（按输出吞吐瓶颈）：
   ceil(25,600 / X) = N_decode 台

4. 实例数（按并发瓶颈）：
   同时在途请求数 ≈ 100 × 平均响应时间(秒)
   平均响应时间 ≈ 512 prefill时间 + 256 × 50ms ≈ 13 s
   在途 ≈ 1300，单实例并发 Y → ceil(1300 / Y) = N_concurrent 台

5. 取 max(N_decode, N_concurrent) × 1.3（余量）= 最终实例数

6. 机型：按显存需求（权重 + 目标并发的 KV）选卡型
```

**关键提醒**：
- **在途请求数**常被低估——LLM 响应时间长（秒级），100 QPS 下在途请求远不止 100 个；
- **余量 30%**：流量波动、故障切换、滚动更新都要余量；
- 所有 `X`、`Y` 必须来自你的实测，不能拍脑袋。

### 2.3 排队论直觉（面试加分）

利用率 $\rho$ 越高，排队延迟越爆炸。M/M/1 的平均等待时间：

$$
W_q = \frac{\rho}{\mu(1-\rho)}
$$

$\rho = 0.9$ 时等待是 $\rho = 0.5$ 时的 **9 倍**。这就是"容量设在拐点前 70-80%"的数学依据——**不是保守，是排队论必然**。

## 3. 负载分池：在线与离线分开

### 3.1 两类负载的诉求相反

| | 在线对话 | 离线批处理 |
| --- | --- | --- |
| 优化目标 | 低延迟（TTFT/TPOT） | 高吞吐 |
| 批大小 | 小（保延迟） | 大（保吞吐） |
| 到达模式 | 随机、突发 | 可调度 |
| 失败容忍 | 低（用户在等） | 高（可重试） |

### 3.2 混池的代价

混在一起时，离线大请求占住算力 → 在线请求排队 → 延迟超标；或反过来为保延迟牺牲批大小 → 离线吞吐崩。**分池部署**（独立实例组、独立扩缩策略）是标准解。

## 4. 实现：容量计算脚本（交付）

```python
import math

def capacity_plan(peak_qps, avg_in_tokens, avg_out_tokens,
                  single_instance_tps, single_instance_concurrency,
                  avg_response_time_s, headroom=1.3):
    """容量规划计算器：输入业务假设与实测单卡数据，输出实例数。"""
    # 1. 输出吞吐需求
    out_demand = peak_qps * avg_out_tokens
    n_decode = math.ceil(out_demand / single_instance_tps)

    # 2. 并发需求
    in_flight = peak_qps * avg_response_time_s
    n_concurrent = math.ceil(in_flight / single_instance_concurrency)

    # 3. 取大者 + 余量
    n = max(n_decode, n_concurrent)
    n_with_margin = math.ceil(n * headroom)

    return {
        "输出吞吐需求(tokens/s)": out_demand,
        "在途请求数": in_flight,
        "按吞吐需实例": n_decode,
        "按并发需实例": n_concurrent,
        "加余量后实例数": n_with_margin,
    }

# 用你的 Stage 5 实测数据填入
result = capacity_plan(
    peak_qps=100,
    avg_in_tokens=512, avg_out_tokens=256,
    single_instance_tps=3000,          # ← 换成你的实测
    single_instance_concurrency=64,    # ← 换成你的实测
    avg_response_time_s=13,
)
for k, v in result.items():
    print(f"{k}: {v}")
```

**预期**：打印出各维度推算值。把 `single_instance_tps` 与 `single_instance_concurrency` 换成你 Stage 5 的真实数据——这份计算书才是你的交付。

## 5. 工程权衡与失效模式

### 5.1 权衡

- **余量大小**：多 → 贵但稳；少 → 省钱但突发流量下崩。30% 是起点；
- **机型选择**：大卡（A100）吞吐高效率低（小负载浪费），小卡灵活但数量多运维重；
- **分池粒度**：完全分池隔离好但资源利用率低，共享池省资源但互相干扰。

### 5.2 失效模式

1. **低估在途请求**：只按 QPS 算实例、忽略响应时长 → 并发爆表排队。修复：用在途 = QPS × 响应时长。
2. **利用率设太高**：90% 利用率排队爆炸（排队论）。修复：容量留 20-30% 余量。
3. **在线离线混池**：互相拖累。修复：分池 + 独立扩缩。
4. **单点容量假设失真**：实测数据与生产负载分布不符。修复：用真实负载分布压测（Stage 5 已强调）。

## 6. 延伸思考题（含解析）

**Q1**：怎么估算一台机器能抗多少并发？
**A**：两条约束取小：① 显存——（总显存 - 权重 - 激活）÷ 单请求最大 KV；② 延迟——并发上去后每请求分到的算力变少，超 SLO 即止。实测时用压测找到满足 SLO 的最大并发。

**Q2**：为什么容量要设在拐点前 70-80%，而不是 95%？
**A**：排队论：等待时间随利用率趋 1 而爆炸（ρ=0.9 的等待是 ρ=0.5 的 9 倍）。且需余量应对波动、故障切换与滚动更新。95% 利用率 = 任何小波动都排队雪崩。

**Q3**：在线对话与离线批处理为什么分池？
**A**：优化目标相反：在线要低延迟（小批），离线要高吞吐（大批）。混池会互相拖累——离线大请求阻塞在线、或保延迟牺牲离线吞吐。分池各自优化。

**Q4**：容量计算书里最容易错的一步是什么？
**A**：低估在途请求数。LLM 响应以秒计，100 QPS 下在途远大于 100。必须用"在途 = QPS × 平均响应时长"算并发需求，而不是直接拿 QPS 当并发。

**Q5**：如果实测单卡数据与生产差异大怎么办？
**A**：生产上线后持续观测真实负载分布与单卡表现，滚动修订容量模型。容量规划不是一次性的，是"假设→实测→修订"的循环。
