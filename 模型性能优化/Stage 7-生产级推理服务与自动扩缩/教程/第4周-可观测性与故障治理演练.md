## 1. 第一性原理：推理服务的"健康"长什么样

### 1.1 普通服务看"活着"，推理服务看"够快"

Web 服务的核心指标是可用性（成功率）。推理服务即使 100% 成功，也可能慢到不可用——所以推理的可观测性围绕**延迟分布与排队**展开。

### 1.2 推理专属指标清单（本周交付的 6 个核心）

| 指标 | 含义 | 为什么重要 |
| --- | --- | --- |
| **TTFT** | 首 token 延迟 | 用户感知的响应速度 |
| **TPOT** | 每 token 间隔 | 流式输出的流畅度 |
| **吞吐** | tokens/s | 容量与成本效率 |
| **队列长度** | 排队请求数 | 过载的最早信号 |
| **抢占率** | 被抢占请求比例 | 显存压力指示 |
| **GPU 利用率/显存** | 资源水位 | 容量规划依据 |

**分位数而非均值**：延迟必须看 P50/P95/P99——均值掩盖长尾，而长尾才是用户投诉的来源。

## 2. Prometheus + Grafana 大盘（交付核心一）

### 2.1 指标采集

推理引擎通常暴露 Prometheus 格式的 `/metrics`。在模拟集群用 Prometheus 抓取：

```yaml
# prometheus 抓取配置（示意）
scrape_configs:
  - job_name: 'inference'
    static_configs:
      - targets: ['infer-service:8080']
```

自定义业务指标（如队列长度）用 Prometheus client 库暴露：

```python
from prometheus_client import Counter, Histogram, Gauge

REQUESTS = Counter("infer_requests_total", "总请求数")
TTFT = Histogram("infer_ttft_seconds", "首 token 延迟",
                 buckets=(0.05, 0.1, 0.2, 0.5, 1, 2, 5))
QUEUE_LEN = Gauge("infer_pending_requests", "排队请求数")
```

### 2.2 大盘与告警规则（交付 ≥6 指标 + 2 告警）

Grafana 大盘面板（PromQL 示意）：

```
# TTFT P99
histogram_quantile(0.99, rate(infer_ttft_seconds_bucket[1m]))

# 队列长度
infer_pending_requests

# 吞吐（每秒完成请求）
rate(infer_requests_total[1m])
```

告警规则（`prometheus/rules`）：

```yaml
groups:
- name: inference
  rules:
  - alert: HighQueueLength
    expr: infer_pending_requests > 50
    for: 1m
    labels: {severity: warning}
    annotations: {summary: "排队请求持续超过 50，可能过载"}
  - alert: HighTTFT
    expr: histogram_quantile(0.99, rate(infer_ttft_seconds_bucket[2m])) > 2
    for: 2m
    labels: {severity: critical}
    annotations: {summary: "TTFT P99 超 2 秒，体验劣化"}
```

**交付**：大盘截图 + 两条告警规则，并说明阈值怎么定（基于 SLO 反推：TTFT SLO 500ms，告警设在接近超标处）。

## 3. 分布式追踪：定位一条慢请求

### 3.1 全链路追踪

一条请求穿过 网关 → 路由 → 引擎 → 采样。用 **OpenTelemetry** 给请求打 trace：

```python
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider

trace.set_tracer_provider(TracerProvider())
tracer = trace.get_tracer("inference")

async def handle(req):
    with tracer.start_as_current_span("gateway"):
        with tracer.start_as_current_span("engine.prefill"):
            do_prefill(req)
        with tracer.start_as_current_span("engine.decode"):
            do_decode(req)
```

### 3.2 用 span 定位瓶颈

在追踪后端（Jaeger/Tempo）看这条慢请求的时间线：哪个 span 占了大头，瓶颈就在哪——是排队、是 prefill、还是 decode。**这是"延迟从哪来"的线上版答案**（呼应 Stage 5 的离线分析）。

## 4. 故障治理演练（交付核心二）

### 4.1 三种故障的注入与恢复

**故障一：GPU/内存 OOM**

```
注入：把负载打高 + 调低显存上限（或发超长上下文请求）
观察：实例重启、告警触发、服务短暂不可用
恢复：副本自愈重启；根因 → 限制最大上下文、降并发、加显存
```

**故障二：慢节点（长尾）**

```
注入：给某个副本人为限速（如限制 CPU/加人工延迟）
观察：部分请求延迟显著高于其他（P99 恶化、P50 正常）
恢复：健康检查剔除慢节点、流量重分配；根因 → 排查该节点资源争用
```

**故障三：队列爆满**

```
注入：压测流量远超容量（如 10× 正常）
观察：队列长度飙升、排队告警、吞吐不再增长
恢复：限流丢弃溢出请求 / 扩容；根因 → 容量不足，需扩容或降级
```

### 4.2 演练记录模板

```
故障：队列爆满
- 注入方式：locust 打到 10× 容量
- 告警触发：HighQueueLength（排队 > 50）在 12:03 触发
- 现象：队列从 5 → 300，吞吐封顶，TTFT 飙到 10s
- 恢复动作：开限流（丢弃溢出）+ 手动扩副本
- 恢复时间：2 分钟
- 结论：需在队列 > 50 时自动扩容，并设入口限流
```

**价值**：把"故障响应"从纸面流程变成肌肉记忆。真出事时，你做过演练的版本比没做过的快一个量级。

### 4.3 优雅降级策略

过载时的主动选择（按优先级）：
1. **丢弃低优请求**（保高优用户）；
2. **切更小模型**（牺牲质量保响应）；
3. **拒绝长上下文**（长请求占资源最多）。

这些要**预先配置好**，故障时一键生效，而不是临时想。

## 5. 工程权衡与失效模式

### 5.1 权衡

- **告警灵敏度**：太灵敏告警风暴（麻木），太迟钝发现晚。按 SLO 分级（warning 早、critical 准）。
- **追踪开销**：全量追踪有性能开销。采样率权衡，慢请求必采。
- **指标粒度**：太粗看不出问题，太细存储成本高。

### 5.2 失效模式

1. **只有均值没有分位数**：P99 爆了均值还正常，漏报。修复：所有延迟指标看分位数。
2. **告警疲劳**：低价值告警太多，真告警被忽略。修复：告警分级、定期清理无效告警。
3. **无追踪定位难**：慢请求不知道卡哪。修复：接入分布式追踪，关键路径全打 span。
4. **降级没预案**：过载时临时决策手忙脚乱。修复：预先配置降级策略并演练。

## 6. 延伸思考题（含解析）

**Q1**：推理服务要盯哪些普通服务不盯的指标？
**A**：TTFT、TPOT、吞吐、队列长度、抢占率、GPU 显存/利用率。普通服务盯可用性与 QPS，推理必须盯延迟分布与排队——因为推理的"失败"常表现为"太慢"而非"报错"。

**Q2**：为什么延迟指标必须看分位数而非均值？
**A**：推理延迟分布通常长尾。均值会被大量快请求拉低，掩盖少数超慢请求；而用户体验由最慢的那批决定。P99 才能反映真实最差体验。

**Q3**：线上 TTFT 突增，排查路径？
**A**：① 看是否过载（队列长度、并发）；② 看是否有超长请求拖慢（大 prompt 独占）；③ 看资源（显存、GPU 利用率）；④ 用分布式追踪定位慢在排队还是计算。分层定位，从最可能到最不可能。

**Q4**：慢节点为什么用健康检查剔除？
**A**：慢节点（资源争用/硬件退化）会让打到它的请求长尾。健康检查/慢请求检测能识别并把它移出负载均衡，流量切到健康节点，避免个别节点拖累整体延迟。

**Q5**：优雅降级为什么必须预先配置？
**A**：故障时认知带宽被占用、决策质量下降。预先配置好的降级策略（丢低优/切小模型/拒长请求）可一键执行，把"临场决策"变成"执行预案"，恢复更快更稳。
