## 1. 第一性原理：调度器是"显存、算力、延迟"三者的仲裁者

### 1.1 调度器要解决的问题

推理服务同时收到很多请求，每个请求有自己的生命周期（排队→prefill→decode→完成）。调度器要在每一步决定：

- **哪些请求进 GPU 跑**（受显存和算力限制）；
- **谁先谁后**（影响延迟公平性）；
- **显存不够时牺牲谁**（抢占策略）。

这本质是一个**在线资源分配问题**——请求到达不可预知，决策必须实时做。

### 1.2 批处理的演进（一条主线）

$$
\text{static batching} \to \text{continuous batching} \to \text{chunked prefill} \to \text{PD 分离}
$$

- **Static batching**：凑够一批一起跑，全批结束才接新请求。短请求等长请求，浪费严重；
- **Continuous batching**：每一步（每个 decode iteration）都可插入新请求、移出完成请求——**以 iteration 为粒度动态组批**。这是现代引擎的基石；
- **Chunked prefill**：把长 prefill 切块，与 decode 混在同一步执行，避免 prefill 阻塞 decode；
- **PD 分离**：prefill 与 decode 拆到不同机器池，各自优化。

每一步演进都在解决前一步暴露的**干扰**或**浪费**问题。

## 2. vLLM V1 调度器内部

### 2.1 两个队列

- **waiting**：已到达、还没开始（或等待显存）的请求；
- **running**：正在 GPU 上迭代的请求。

每步调度的核心动作：从 waiting 取请求**准入（admit）**进 running，前提是显存（KV 块）和预算够。

### 2.2 准入判断（能不能进）

一个新请求进 running 需要：

1. **有空闲 KV 块**容纳它的 prompt（prefill）+ 预留的生成空间；
2. **总 token 数**不超过 `max-num-batched-tokens`（单步算力预算）；
3. **并发数**不超过 `max-num-seqs`。

任一不满足，请求留在 waiting（排队）。

### 2.3 抢占（Preemption）

当 running 里的请求持续增长、显存耗尽，而又有更高优先级需求时，调度器会**抢占**某个请求，把它踢出 running。两种手段：

- **recompute（重算）**：直接丢弃该请求的 KV，之后重新 prefill。省显存（立即释放全部块），但浪费已算的计算；
- **swap（换出）**：把 KV 块换到 CPU 内存，之后换回。保留计算，但占 PCIe 带宽、有换入换出开销。

**选择逻辑**：序列短（重算便宜）→ recompute；序列长（重算贵）且 CPU 内存够 → swap。这呼应了启动参数 `--swap-space`（每卡预留的 CPU 换出空间）。

### 2.4 手写最小调度状态机（帮助理解）

```python
from collections import deque
from dataclasses import dataclass, field

@dataclass
class Req:
    req_id: int
    prompt_len: int
    max_gen: int
    gen_len: int = 0
    @property
    def total_len(self): return self.prompt_len + self.gen_len
    @property
    def done(self): return self.gen_len >= self.max_gen

class MiniScheduler:
    """连续批处理的最小状态机：准入 + 抢占。"""
    def __init__(self, max_blocks, block_tokens=16,
                 max_batched_tokens=2048, max_seqs=4):
        self.max_blocks = max_blocks
        self.block_tokens = block_tokens
        self.max_batched_tokens = max_batched_tokens
        self.max_seqs = max_seqs
        self.waiting = deque()
        self.running = []
        self.used_blocks = 0

    def blocks_for(self, req):
        return (req.total_len + self.block_tokens - 1) // self.block_tokens

    def submit(self, req):
        self.waiting.append(req)

    def admit(self):
        """从 waiting 准入到 running（受三重约束）。"""
        while self.waiting:
            cand = self.waiting[0]
            need = self.blocks_for(cand)
            if (self.used_blocks + need <= self.max_blocks
                    and len(self.running) < self.max_seqs):
                self.waiting.popleft()
                self.running.append(cand)
                self.used_blocks += need
            else:
                break     # 头部请求都进不去，后面的更不行（保序）

    def preempt_if_needed(self):
        """显存超限时抢占最长的请求（recompute）。"""
        while self.used_blocks > self.max_blocks and self.running:
            victim = max(self.running, key=lambda r: r.total_len)
            self.running.remove(victim)
            self.used_blocks -= self.blocks_for(victim)
            victim.gen_len = 0                 # recompute: 重置，重新 prefill
            self.waiting.appendleft(victim)

    def step(self):
        self.admit()
        self.preempt_if_needed()
        for r in self.running:
            r.gen_len += 1                     # 每步生成一个 token
        finished = [r for r in self.running if r.done]
        for r in finished:
            self.running.remove(r)
            self.used_blocks -= self.blocks_for(r)
        return finished

# ---- 验证：连续批处理让短请求先走 ----
sched = MiniScheduler(max_blocks=64, max_seqs=3)
sched.submit(Req(1, prompt_len=100, max_gen=50))    # 长
sched.submit(Req(2, prompt_len=10, max_gen=5))      # 短，应早完成
completion_order = []
for step in range(200):
    if step == 3:
        sched.submit(Req(3, prompt_len=20, max_gen=10))   # 中途插入
    for r in sched.step():
        completion_order.append(r.req_id)
    if not sched.waiting and not sched.running:
        break
print("完成顺序:", completion_order)
assert 2 in completion_order[:2], "短请求应在前两批完成（连续批处理特性）"
print("连续批处理：短请求未被长请求阻塞，先完成 ✓")
```

**预期**：短请求 2 先完成，中途插入的请求 3 也能及时进入——这正是连续批处理相对 static batching 的核心价值。

## 3. Chunked Prefill：把 prefill 切块

### 3.1 问题：长 prefill 阻塞 decode

一个 8k token 的 prefill 是算力密集的大矩阵乘，执行时间长（几百毫秒）。若整段执行，期间所有 decode 请求都在等——**TPOT 抖动、decode 长尾**。

### 3.2 解法：预算内切块

把长 prefill 切成小块（如每块 ≤ `max-num-batched-tokens` 的预算），每步只做一块，剩余下一步接着做。这样每步的 prefill 工作量被限制，**与 decode 共存**：

$$
\text{每步} = \underbrace{\text{decode tokens}}_{\text{所有 running 请求}} + \underbrace{\text{一块 prefill}}_{\le \text{预算}}
$$

### 3.3 收益与代价

- **收益**：TTFT 长尾改善（没有超长 prefill 独占）；decode 延迟更平稳；
- **代价**：长 prompt 的总 prefill 时间可能略增（被切多步、与 decode 抢算力）；预算调小 → 干扰少但 prefill 更慢。

`--enable-chunked-prefill` 与 `--max-num-batched-tokens` 共同控制。这是"延迟平滑度"与"prefill 吞吐"的权衡旋钮。

## 4. PD 分离（Disaggregated Serving）

### 4.1 Prefill vs Decode 的根本差异

| | Prefill | Decode |
| --- | --- | --- |
| 计算特性 | 大矩阵乘，**算力瓶颈** | 逐 token 生成，**访存瓶颈** |
| GPU 利用 | 算力打满 | 带宽打满、算力闲置 |
| 延迟敏感 | TTFT | TPOT |

两者**争抢的资源不同、优化方向相反**。混在同一卡上，互相干扰（prefill 吃算力拖慢 decode，decode 吃带宽拖慢 prefill）。

### 4.2 PD 分离的思路

把两类负载**拆到不同的机器池**：

- **Prefill 池**：算力优化（甚至用不同的批大小/引擎配置）；
- **Decode 池**：带宽优化；
- 中间通过**高速网络传 KV cache**（prefill 算完的 KV 传给 decode 池）。

代表工作：**DistServe**（按 goodput 优化分离）、**Mooncake**（KV cache 为中心的分离架构）。

### 4.3 收益与代价

- **收益**：两类负载各自最优，整体 goodput（满足 SLO 的吞吐）提升；
- **代价**：需要跨机传 KV（网络带宽/延迟成本）；运维复杂（两套池、调度协同）。

短 prompt 场景 KV 传输开销占比高，分离收益小；**长 prompt + 高并发**场景收益最大。

## 5. SGLang 调度器对照：RadixAttention 与 cache-aware

### 5.1 与 vLLM 的核心差异

第 1 周讲过：SGLang 用 **Radix Tree** 主动管理前缀，调度器 **cache-aware**——把共享前缀的请求排在一起，最大化 KV 复用。

### 5.2 调度差异的实际影响

- **多轮对话 / 共享系统提示词**场景：SGLang 的前缀命中率高，prefill 省、延迟低；
- **前缀完全随机**的场景：两者接近，差异主要在各自实现细节。

这是"什么负载选什么引擎"的关键判据之一（本周压测会量化）。

## 7. 工程权衡与失效模式

### 7.1 权衡

- **chunked prefill 预算**：小 → 干扰少但 prefill 慢；大 → 反之；
- **抢占策略**：recompute 省显存费算力，swap 反之；按序列长度与 CPU 内存选；
- **PD 分离**：长 prompt 高并发才划算，短场景传输开销不划算。

### 7.2 失效模式

1. **TTFT 长尾**：偶发超长 prefill 独占。修复：开 chunked prefill、限制单请求最大 prompt。
2. **TPOT 抖动**：decode 被 prefill 干扰。修复：调小 chunk 预算、或 PD 分离。
3. **排队雪崩**：显存耗尽后大量请求卡 waiting，吞吐骤降。修复：降 `max-num-seqs`、开 KV 量化、扩容。
4. **PD 分离网络瓶颈**：KV 传输打满网络。修复：高速互联（RDMA）、减少同时传输量。

## 8. 延伸思考题（含解析）

**Q1**：chunked prefill 为什么能改善 TTFT 长尾？代价是什么？
**A**：它把超长 prefill 切块，避免单个大 prefill 独占多步、阻塞后续请求的首次计算，从而平滑首包延迟。代价是长 prompt 的总 prefill 时间可能变长（被切多步、与 decode 抢算力），预算是权衡旋钮。

**Q2**：抢占时 recompute 和 swap 怎么选？
**A**：序列短 → recompute（重算便宜，立即释放显存）；序列长 → swap（重算太贵，换到 CPU 保留计算），前提是 CPU 内存与 PCIe 带宽够。`--swap-space` 决定能换出多少。

**Q3**：为什么 prefill 是算力瓶颈、decode 是访存瓶颈？
**A**：prefill 一次处理整个 prompt，是大矩阵乘，算术强度高、吃算力；decode 每步只算一个 token，但要加载整个模型权重和 KV，算术强度低、受显存带宽限制。

**Q4**：PD 分离什么场景最划算？
**A**：长 prompt + 高并发。此时 prefill 算力需求大、KV 大，分离后两池各自优化收益显著，且大 KV 传输的相对开销可被长生成摊薄。短 prompt 场景传输开销占比高，不划算。

**Q5**：vLLM 与 SGLang 调度差异在什么负载下体现？
**A**：共享前缀场景（多轮对话、统一系统提示词）。SGLang 的 RadixAttention + cache-aware 调度前缀命中率高，省 prefill、延迟低；前缀随机场景两者接近。（用你的压测数据佐证。）
