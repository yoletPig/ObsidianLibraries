### 阶段四：GGML / llama.cpp 与端侧推理——CPU 与 NPU 上的大模型（6 周）

**阶段核心目标**：拆解端侧推理事实标准 `llama.cpp`：GGUF 格式、CPU 量化内核（Q4_K/Q5_K）、采样器与 KV cache 管理、RPC/异构卸载机制，并联动你手上的 **RK3588 RKNN 部署**（含自定义算子）与 MTK NeuroPilot 工具链。本阶段直接服务你的语音结课项目（Stage 7 端侧助手）中的端侧 LLM 组件。

> 🔧 硬件配置：你已有 RK3588 与 MTK 板（两板都要实操）、x86 机器跑 GGML CPU 推理。本阶段无 GPU 依赖，全部可本地执行。

---

### 📅 逐周学习路线与 MVP 交付

#### 第 1 周：GGUF 格式与 llama.cpp 架构解剖

* **学习重点**：
* **GGUF 容器**：KV 元数据区 + tensor 目录 + 数据区的二进制布局；`gguf-py` 库读写实践。
* **量化类型全家福**：Q4_0/Q4_1 → Q4_K/Q5_K（K-quants：超块 + 二级缩放）→ IQ 系列（imatrix 重要性矩阵量化）；每种格式的位宽构成与精度排序。
* **llama.cpp 架构**：`ggml` 张量库（CPU/GPU 双后端）→ `llama` 模型层 → `llama-cli/server` 应用层三层结构；模型加载到推理的完整调用链。
* **imatrix 原理**：为什么「用校准数据统计每个通道重要性」能让 2-3 bit 量化可用。

* **推荐资料**：
* `ggerganov/llama.cpp` 源码：`ggml-quants.c`（量化内核）、`gguf` 规范文档
* 论文：*K-quants* 设计说明（见 llama.cpp PR #1684 讨论，第一手设计记录）

* **💡 第 1 周 MVP 交付**：
> ① 用 `gguf-py` 解析一个 GGUF 文件，打印全部元数据与每个 tensor 的量化类型/形状；② 手写 Q4_0 的解量化（dequantize_row_q4_0）C/Python 实现，与官方 `ggml-quants.c` 输出对齐；③ 图解 Q4_K 的超块结构（256 权重 = 8 子块 × 32，每子块独立 scale + min）。

#### 第 2 周：CPU 推理引擎——量化内核与采样器

* **学习重点**：
* **CPU 向量指令**：AVX2/AVX-512/ARM NEON 在量化 kernel 中的作用；为什么 llama.cpp 在 x86 与 ARM 都能打。
* **矩阵-向量乘优化**：decode 阶段的 GEMV 怎么吃满内存带宽（prefetch、unroll、SIMD 打包）。
* **采样器链**：temperature / top-k / top-p / min-p / repetition penalty 的实现位置与顺序。
* **KV Cache 管理**：连续批处理（contiguous batching）、KV 量化（Q8_0 KV cache）、上下文外推。
* **量化模型生产**：`llama-quantize` 的 `--imatrix` 流程，从 HF 权重到 GGUF 的完整转换链。

* **💡 第 2 周 MVP 交付**：
> ① 在你的 x86 机器上完成「HF 权重 → convert_hf_to_gguf → imatrix 校准 → Q4_K_M/Q3_K_S 双版本量化」全流程；② 对比两档量化在 CPU 上的 tokens/s、内存占用与生成质量（长文本连贯性测试）；③ 用 `perf` 抓一次推理火焰图，确认 GEMV kernel 占时比例。

#### 第 3 周：异构卸载与多设备——llama.cpp 的工程纵深

* **学习重点**：
* **GPU 卸载**：`-ngl` 层卸载、MMVQ/MMQ 量化 GEMM kernel 在 GPU 上的形态。
* **RPC 分布式**：llama.cpp 的 RPC 后端把层拆到远程机器——「局域网拼出大显存」的实现原理。
* **Vulkan/Metal/CANN 后端**：llama.cpp 的多后端抽象层（`ggml-backend`），**重点预读 CANN 后端**（与你的昇腾设备联动，Stage 6 深挖）。
* **llama-server**：OpenAI 兼容 API、continuous batching 的调度实现——端侧服务化的最小闭环。

* **💡 第 3 周 MVP 交付**：
> ① 在 x86 机器上起 `llama-server`，用 curl/Python 客户端压测并发 1/4/8 路的吞吐与延迟；② 研究你的本地环境（无 NVIDIA GPU）下可用的后端（Vulkan/远程 RPC），跑通一次跨机或跨后端推理并记录配置。

#### 第 4 周：RKNN 部署——RK3588 上的 NPU 推理

* **学习重点**：
* **RKNN-Toolkit2 全流程**：ONNX → RKNN（量化选项：非对称/动态范围、混合精度层指定）→ `.rknn` 模型；模拟器验证与板端部署。
* **精度调试**：逐层余弦相似度对比工具、量化敏感层回退策略。
* **性能调优**：NPU 核（RK3588 三核）绑定、多核并行推理、零拷贝内存（`rknn_create_mem`）。
* **端侧语音模型实战**：把你的语音方向成果搬上板——SenseVoice-Small / DeepFilterNet / VAD 的 RKNN 转换与推理（语音×性能的首次交叉）。

* **推荐资料**：
* `airockchip/rknn-toolkit2` 官方 examples（重点看 `onnx` 目录与 `dynamic_shape`）
* `airockchip/rknn-llm`（RK3588 上跑 LLM 的官方项目）

* **💡 第 4 周 MVP 交付**：
> ① 在 RK3588 上完成「ONNX → RKNN → 板端推理」三连：对象用一个语音相关模型（DeepFilterNet 或小型 VAD）；② 用 `rknn-llm` 在板上跑通一个 1-3B LLM（INT4/INT8），记录 tokens/s 与内存；③ 输出逐层精度对比报告，标出量化掉点最严重的层。

#### 第 5 周：RKNN 自定义算子 + MTK NeuroPilot

* **学习重点**：
* **RKNN C API 与自定义算子**：模型转换时自定义算子落 CPU、其余落 NPU 的混合执行；自定义算子的注册流程（`rknn_custom_op`）、内存格式（NCHW vs NHWC）与量化参数透传。
* **为什么需要自定义算子**：NPU 不支持的特殊结构（你的 ASR 里的 CIF、TTS 的 flow matching 组件都可能撞上）。
* **MTK NeuroPilot/AI Developer Option**：`.tflite` → MTK APU 的转换工具链（NeuroPilot Converter）、量化选项、APU 与 GPU/CPU 的异构调度；Genio 系列的 APU 算力分配。

* **推荐资料**：
* `rknn-toolkit2` 的 `custom_op` 示例；MediaTek NeuroPilot 官方文档与 `ai-devtool`

* **💡 第 5 周 MVP 交付**：
> ① 在 RKNN 上实现一个自定义算子（例如自定义激活函数或 RMSNorm），走「CPU 自定义算子 + NPU 主体」的混合部署并验证正确性；② 在 MTK 板上完成同一个语音模型的 NeuroPilot 转换与推理，输出「RK3588 vs MTK」同模型性能对比表。

#### 第 6 周：端侧推理全家桶整合 + 复盘

* **学习重点**：
* **端侧方案决策矩阵**：CPU(GGML) vs NPU(RKNN) vs APU(NeuroPilot) 在不同模型/精度/功耗下的选型。
* **功耗与热管理**：端侧推理的隐性天花板；DVFS 调频对 tokens/s 的影响实测。
* **对接语音结课项目**：确定 Stage 7 端侧助手中 LLM 组件的最终形态（rknn-llm / llama.cpp CPU / 混合）。

* **💡 第 6 周 MVP 交付**：
> 产出《端侧 LLM 部署选型报告》：同一 1.5B/3B 模型在 {x86 CPU GGML, RK3588 rknn-llm, RK3588 CPU, MTK APU} 四平台的 {tokens/s, 首 token 延迟, 内存, 功耗} 矩阵 + 选型结论。这份报告同时是你语音结课项目的技术决策书。
