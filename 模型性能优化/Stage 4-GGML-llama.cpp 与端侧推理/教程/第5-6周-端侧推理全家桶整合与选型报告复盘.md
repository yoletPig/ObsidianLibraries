## 1. 第一性原理：端侧选型 = 四维预算的联合优化

云端选型只看"精度-成本"，端侧要同时盯四个预算：**速度（延迟/吞吐）、内存、功耗、热量**。四者互相咬合：

$$
\text{提速} \xrightarrow{\text{加压提频}} \text{功耗} \uparrow \xrightarrow{\text{积热}} \text{降频} \xrightarrow{} \text{速度回落}
$$

这个闭环意味着：**端侧的峰值性能没有意义，可持续性能才是指标**。一块被动散热的板子，前 30 秒的 tokens/s 和第 5 分钟的可能是两个数字——本报告必须测"持续值"。

### 1.1 三条路线的本质差异

| 路线 | 算力来源 | 最强场景 | 先天短板 |
| --- | --- | --- | --- |
| CPU（GGML/llama.cpp） | SIMD + 内存带宽 | 灵活（任意模型结构、长上下文、完整采样器） | 带宽天花板低、功耗高 |
| NPU（RKNN/rknn-llm） | 专用 INT 阵列 | 固定结构的量化模型、低功耗持续推理 | 算子白名单、上下文受限 |
| APU（NeuroPilot） | MTK 专用单元 | TFLite 生态模型、与 MTK 多媒体管线协同 | 生态封闭、调试工具少 |

### 1.2 决策矩阵（本报告的骨架）

选型不是"谁快选谁"，而是按场景加权：

```
场景 → 瓶颈资源 → 路线：
端侧语音助手（实时对话）→ 首 token 延迟 + 持续功耗 → NPU 小模型 / CPU 中模型
离线批量转写        → 吞吐 + 内存          → CPU 大 batch / NPU 流水
多媒体联动（边录边推理）→ 总线与内存争用     → 独占核绑定 + 实测争用损耗
```

### 1.3 DVFS 与热管理实测方法

- **锁频测试**：把 CPU/NPU 频率锁定在若干档位（`cpufreq` 或厂商接口），各测 tokens/s——得到"频率-速度"曲线，识别收益递减点；
- **持续压测**：满速跑 10-15 分钟，每分钟记录一次 tokens/s 与温度——画出"降频悬崖"出现的时间点；
- **功耗读数**：板载功率计（若有）或 `power_supply` sysfs / 厂商节点，单位时间能耗换算 mJ/token——**mJ/token 才是端侧的可比单位**（比 W 更公平，因为它归一化了速度）。

```
└─ 内存 < 4GB？

```

### 2.4 DVFS 扫频测量脚本（表三的数据来源）

```bash
#!/bin/bash
# dvfs_sweep.sh —— 锁频扫档：画"频率-速度"曲线，找收益递减点
GOV=/sys/devices/system/cpu/cpufreq/policy0   # 按板子实际路径调整
MODEL=qwen2.5-1.5b-Q4_K_M.gguf

echo "freq_mhz,tokens_per_s,temp_c"
for freq in 600000 1008000 1416000 1800000 2208000; do
    sudo cpufreq-set -r -g performance -d $freq -u $freq 2>/dev/null || \
        echo $freq | sudo tee $GOV/scaling_max_freq > /dev/null
    sleep 2                                    # 等频率稳定
    tps=$(./build/bin/llama-cli -m $MODEL -p "$(cat prompt.txt)" \
          -n 128 -t 4 2>&1 | grep -oP 'eval time.*?=\s*\K[\d.]+' | head -1)

    echo "$((freq/1000)),$tps,$((temp/1000))"
done
# 预期曲线：低频段近似线性增长，高频段斜率放缓（带宽而非算力受限时更平缓）
# 交付：把扫频数据画成图，标出"每 +100MHz 收益 < 5%"的拐点——锁频就锁这里
```

### 2.5 内存预算四件套（OOM 预防表）

| 组成 | 估算公式 | 1.5B Q4_K 示例 |
| --- | --- | --- |
| 权重 | 参数量 × bpw / 8 | ~0.95 GB |
| KV cache | $2 \times L \times n_{kv} \times d_h \times seq \times bytes$ | 4K ctx ≈ 0.3-0.6 GB |
| 运行时 | 计算缓冲 + 线程栈 + 后端上下文 | ~0.2-0.5 GB |
| 系统预留 | OS + 图形栈 + 其他进程 | ≥ 0.5 GB |

$$
\text{总预算} \approx \text{四项之和} \times 1.2\ (\text{余量})
$$

板端内存 ≤ 4GB 时，这张表直接决定"能不能跑、跑多长上下文"——报告表一的"峰值内存"列必须与此表对账。

## 3. 工程权衡与失效模式

### 3.1 权衡

- **峰值 vs 持续**：端侧永远按持续值选型；峰值只在"突发短请求"场景（如唤醒词检测）有意义。
- **灵活 vs 高效**：NPU 快但封闭、CPU 慢但全能——工程上常见"双形态"：正常走 NPU，特殊请求回退 CPU。
- **报告的可复现性**：温度、后台进程、内存压力都会污染数字——每行数据注明环境（室温、锁频状态、后台负载），否则报告三个月后不可信。

### 3.2 失效模式

1. **用峰值速度拍板**：症状——产品上市后"越用越卡"；根因——热降频，峰值不可持续；修复——持续压测 10 分钟 + 降频悬崖记录（§2.2 表三）。
2. **内存预算漏算**：症状——板端跑大模型 OOM；根因——只算权重，忘了 KV cache + 系统 + 图形栈；修复——预算表四件套：权重 + KV + 运行时 + 系统预留。
3. **跨平台比 W 不比 mJ/token**：症状——得出"慢的平台更省电"的错误结论；根因——功率没归一化到每 token；修复——统一用 mJ/token（§1.3）。
4. **实验室温度失真**：症状——冬天测的数据夏天翻车；根因——被动散热对环境温度极敏感；修复——按产品实际工作温度区间复测（至少 25℃ 与 35℃ 两档）。

## 4. 延伸思考题（含解析）

**Q1**：为什么端侧要发明 "mJ/token" 这个指标？
**A**：端侧的真实约束是电池/散热预算（总能量），不是瞬时功率。快但费电与慢但省电，只有在"每个 token 花多少能量"上才可比。mJ/token = 功率 ÷ tokens/s，是速度与功耗的联合归一——选型报告用它一眼看穿"虚假的省电"。

**Q2**：降频悬崖出现后，是继续硬扛还是主动降档？
**A**：主动降档。悬崖后系统会自动在"过热-降频-恢复"间震荡，速度抖动且不可预测；锁定在一个可持续的频率档，换来平稳的 tokens/s——端侧体验要的是稳定而非峰值。这就是 §2.3 决策树里"锁频找收益递减点"的原因。

**Q3**：同一 1.5B 模型，为什么四平台首 token 延迟的排序可能和 tokens/s 不同？
**A**：首 token（prefill）吃算力，decode 吃带宽——两个阶段瓶颈不同。NPU 算力相对强、带宽相对弱时，可能"首字快、续写慢"。所以两个指标必须分开测、分开选型，只报一个必然踩坑。

**Q4**：语音结课项目为什么建议"混合形态"而不是单押一条路线？
**A**：语音助手是多组件系统：VAD/降噪是固定小模型（NPU 最优）、LLM 对话是变长复杂逻辑（CPU 灵活）、唤醒在极低功耗档。每个组件的最优路线不同——系统级选型天然是异构的，这恰好是本方向四平台的完整用武之地。

**Q5**："端侧跑 7B 现实吗？"——用本报告的框架回答。
**A**：按四预算回答：内存（7B Q4 ≈ 4GB + KV，16GB 板勉强）、速度（decode 带宽账：板级 ~30 GB/s → 个位数 tokens/s）、功耗/热（满速不可持续）。结论：**技术上能跑，产品上不现实**——端侧应选 1.5-3B + 云端级联（复杂请求上云），这正是 Stage 8 端云一体架构的端侧依据。

## 5. 本阶段面试速查（背下这组数字与结论）

### 5.1 必须脱口而出的数字

| 问题 | 答案锚点 |
| --- | --- |
| Q4_K 的位宽构成 | 超块 256 权重 = 8 子块×32；144 字节/超块 = 4.5 bpw |
| 7B decode 带宽上限 | 权重体积 ÷ 带宽：14GB/2TB/s ≈ 143 tokens/s（GPU）；板端带宽代入同理 |
| Q4_K_M 的 7B 体积 | ≈ 4.4 GB；加 KV 与运行时按 ×1.3 预算 |
| imatrix 的作用 | 激活平方均值加权误差预算，让 2-3 bit 可用 |
| 采样器顺序 | rep-penalty → temp → top-k → top-p → min-p → 归一化 |

### 5.2 必须讲清楚的四个机制

1. **K-quants 为什么比 Q4_0 准**：两级缩放（超块 FP16 × 子块 6-bit）= 同位宽更细粒度，隔离离群子块。
2. **llama.cpp 跨平台能打的原因**：块状自包含格式 + AVX2/NEON 手写内核 + GEMV 访存瓶颈本质（不依赖特殊硬件）。
3. **NPU 部署精度排查链**：逐层余弦对比 → 标 < 0.95 的层 → 混合精度回退 → 端到端指标复测。
4. **端侧选型四预算**：速度（持续值）、内存（四件套）、功耗（mJ/token）、热（降频悬崖）——峰值性能没有意义。
