## 1. 第一性原理：实验室指标与真实场景的差距从哪来

实验室里你控制了一切：安静、常温、短对话、干净电源。真实客厅有四个你没控制的变量：

| 变量 | 实验室 | 真实场景 | 击穿方式 |
| --- | --- | --- | --- |
| 声学环境 | 安静（>30 dB SNR） | 电视/多人（5~15 dB） | ASR 成功率跳水 |
| 温度 | 室温短跑 | 连续工作 2 小时 | 降频 → 延迟全线上涨 |
| 时长 | 10 次对话 | 连续待机 24 小时 | 内存泄漏、句柄耗尽 |
| 网络 | 无（离线设计） | 用户会问「联网吗」 | 离线边界必须可证明 |

本周的全部工作，就是把这四个变量的风险逐一测出来、写进报告。**能说出自己系统在哪里会坏，是工程师与调参者的分界线。**

## 2. 鲁棒性三板斧：离线验证、泄漏排查、高温测试

### 2.1 完全离线验证

方法：`sudo ip link set wlan0 down`（物理拔网线/关射频更彻底），跑完整测试集——唤醒、对话、打断全部通过才算「离线」。**检查清单**：

- TTS 无云端音色依赖；
- LLM 无在线词表/缓存回源；
- 时间戳不依赖 NTP（RTC 本地时钟）；
- 日志上报全部落本地文件（联网时才批量上传）。

任何一项失败，都说明「离线」只是当前没触发联网路径——写进风险清单并修复。

### 2.2 内存泄漏长跑

判定标准：连续 24 小时（至少 8 小时）混合负载（对话 + 待机 + 唤醒），RSS 增长 **<50 MB/小时且无单调趋势**才算通过。采样工具链：

```python
import time, resource

def rss_mb():
    """当前进程 RSS（MB），长跑监控用。"""
    return resource.getrusage(resource.RUSAGE_SELF).ru_maxrss / 1024

def leak_check(duration_h=8, interval_s=60):
    """每 interval 秒采一次全链路进程组内存，输出趋势。"""
    samples = []
    t_end = time.time() + duration_h * 3600
    while time.time() < t_end:
        samples.append((time.time(), rss_mb()))
        time.sleep(interval_s)
    growth = samples[-1][1] - samples[0][1]
    rate = growth / duration_h
    print(f"内存增长: {growth:.1f} MB / {duration_h} h = {rate:.1f} MB/h")
    assert rate < 50, "内存增速超红线，存在泄漏"
    return samples
```

**常见泄漏点**（按你链路的出现概率排序）：① 音频缓冲/队列只进不出（打断路径没清空）；② 会话历史列表无上限；③ ONNX Runtime session 反复创建不复用；④ 日志句柄。定位用 `pmap -x $(pidof assistant) | sort -k3 -n` 观察哪个映射段在涨。

### 2.3 高温降频

RK3588 满载结温到 85°C 后大核会降频（常见降到标称的 60~70%），**所有 CPU 侧延迟同比例变慢**——你的预算表是按冷机测的，热机可能全线破线。防法：

1. 压测时同时记录 `cat /sys/class/thermal/thermal_zone*/temp`，把延迟数据按温度分桶；
2. 主动散热（散热片+风扇）是端侧产品的标配，别省；
3. 预算表加一行「热机 P95」，与冷机并列报告——面试时主动讲这个，是系统成熟度的证明。

## 3. 质量压测：分信噪比矩阵

### 3.1 设计原则

成功率必须按**信噪比分层**报告，一个总数字没有意义。噪声类型也要覆盖三类真实场景：安静、电视背景（非平稳、含人声）、多人交谈（竞争性人声最难）。

| SNR | 安静 | 电视背景 | 多人场景 | 判定 |
| --- | --- | --- | --- | --- |
| 30 dB+（近场） | ✅ 目标 ≥98% | — | — | 基线 |
| 15 dB | 目标 ≥95% | 目标 ≥85% | ≥75% | 主力场景 |
| 5 dB | ≥85% | ≥60% | 记录即可 | 边界，报告不承诺 |

测试集：50 条固定指令 × 每档噪声 3 次重放 = 每档 150 次；噪声按目标 SNR 与指令信号混合（用 `pyloudnorm` 对齐响度）。

### 3.2 可运行的压测统计

```python
import numpy as np

def snr_matrix_report(results):
    """results: {(snr_db, noise_type): [bool, ...] 成功与否}。"""
    print(f"{'SNR':>6} | {'噪声类型':<8} | 成功率 | 95%置信区间")
    for (snr, noise), flags in sorted(results.items()):
        n, k = len(flags), sum(flags)
        p = k / n
        # Wilson 区间：小样本成功率比简单比例更可信
        z = 1.96
        lo = (p + z*z/(2*n) - z*np.sqrt(p*(1-p)/n + z*z/(4*n*n))) / (1 + z*z/n)
        hi = (p + z*z/(2*n) + z*np.sqrt(p*(1-p)/n + z*z/(4*n*n))) / (1 + z*z/n)
        print(f"{snr:>5}dB | {noise:<8} | {p:6.1%} | [{lo:.1%}, {hi:.1%}]")
        assert n >= 100, f"每档样本不足: {noise}@{snr}dB 只有 {n} 次"
    return results

# 交付：把板端真实压测结果喂进来；示例占位
demo = {(30, "安静"): [True]*148 + [False]*2,
        (15, "电视背景"): [True]*130 + [False]*20}
snr_matrix_report(demo)
print("压测统计框架就绪 ✓（置信区间让 150 次样本的结论站得住）")
```

**预期输出**：分档成功率 + Wilson 置信区间。**报告纪律**：成功率低于目标的档位不许藏——写明「该档位表现 + 改进方向（前端升级/换阵列）」，诚实的失败分析比虚假的 99% 更值钱。

### 3.3 与云端方案的对比评测

同 50 条指令，云端（同尺寸模型 + 云端 ASR）跑一遍，报告三维：**延迟**（端侧应显著更低）、**成功率**（允许损失，写明损失多少）、**可用性**（端侧离线可用）。这张表是你回答「为什么不用云端方案」面试问题的现成答案。

## 4. 可观测性：延迟埋点与火焰图

### 4.1 埋点规范

每个模块进出口打时间戳（第 1-2 周的 5 段埋点），落到结构化日志：

```python
import json, time

class Trace:
    """一次对话的延迟火焰图源数据。"""
    def __init__(self, session_id):
        self.sid = session_id
        self.events = []                       # (t_ms, module, phase)
    def mark(self, module, phase):
        self.events.append((time.monotonic() * 1000, module, phase))
    def spans(self):
        """把相邻 mark 转成 (模块, 耗时) 区间，供火焰图/条形图使用。"""
        out = []
        for (t0, m0, p0), (t1, m1, p1) in zip(self.events, self.events[1:]):
            out.append({"module": m0, "phase": p0, "ms": round(t1 - t0, 1)})
        assert out and all(s["ms"] >= 0 for s in out), "时间戳必须单调"
        return out

tr = Trace("s001")
for m, p in [("vad", "start"), ("asr", "decode"), ("llm", "prefill"),
             ("llm", "first_token"), ("tts", "first_chunk")]:
    tr.mark(m, p); time.sleep(0.01)
spans = tr.spans()
assert len(spans) == 4 and sum(s["ms"] for s in spans) > 0
print("埋点->区间转换验证通过 ✓")
```

把 100 次对话的 spans 聚合成「模块 × 耗时」堆叠条形图（matplotlib `barh` 堆叠即可）——**这就是你的延迟火焰图**：一眼看出哪个模块占了总延迟的大头、哪次对话在哪段异常。

### 4.2 归因优先顺序

P95 超标时的定位路径：① 先看分段分布哪段右尾长；② 该段内按输入长度/温度/核占用分桶；③ 找到最大单一因子再动手优化。**先归因后优化**，凭感觉调参数是压测阶段最大的时间黑洞。

## 6. 工程权衡与失效模式

### 6.1 权衡

- **压测覆盖度 vs 交付时间**：全矩阵（3 噪声 × 3 SNR × 150 次）约一天机时；砍不动的是 15 dB 主力档，可砍的是 5 dB 边界档（只记录不承诺）。
- **热机预算的取舍**：加散热成本 ~20 元 vs 软件降负载（牺牲响应速度）——产品选前者，演示项目两者都记录。
- **诚实报告的代价**：低成功率档位写出来「难看」，但藏着被面试官一问就穿——主动暴露 + 给改进方向才是加分项。

### 6.2 失效模式（压测阶段特有）

1. **长跑第 6 小时崩溃**：队列泄漏在低负载下不显形。修复：长跑必须混合负载（对话+打断+待机循环），不能只挂机。
2. **压测数据与演示不一致**：压测在安静房间、演示在展厅（嘈杂+回声）。修复：演示前在目标场地跑一遍快速矩阵，备好降噪档位参数。
3. **置信区间外的结论**：30 次样本就写「成功率 90%」。修复：每档 ≥100 次 + Wilson 区间（3.2 已内置断言）。
4. **埋点本身拖慢系统**：日志同步写盘占用大核。修复：埋点只写内存环形缓冲，异步落盘，压测时对比「埋点开/关」的延迟差确认 <5 ms。

## 7. 延伸思考题（含解析）

**Q1**：内存泄漏判定为什么用「增速 <50 MB/h 且无单调趋势」而不是「零增长」？
**A**：真实系统有合法的内存波动（glibc 内存池、音频缓冲随对话长度变化、模型缓存预热）。零增长标准会把正常波动误判为泄漏，也会逼人造假。「增速上限 + 趋势检验」区分的是「无界增长」（真泄漏）与「有界波动」（正常）——24 小时尺度上真泄漏必然露出单调趋势。

**Q2**：电视背景噪声为什么比同能量的白噪声难？
**A**：电视噪声是**非平稳 + 含人声**的：NS 靠统计平稳性估计噪声谱，人声与目标语音频谱高度重叠（都是语音，前端无法区分「哪个人声是主人」）。同能量白噪声反而容易减。这就是多人/电视档成功率天然更低的根因——也是「定向拾音（波束成形）+ 声纹门限」成为下一代前端方向的原因（接上你 Stage 4 的声纹知识）。

**Q3**：热机测试发现 ASR 段延迟 +40% 破预算，三个修复方向按成本排序？
**A**：① 加散热（硬件，最便宜，先做）；② ASR 迁 NPU（回填项，降 CPU 负载）；③ 热机时降级策略（如关闭 NS 高阶档）。原则：**先物理后算法，先固定项后牺牲体验项**。

**Q4**：「与云端对比」里端侧成功率低 8 个点，怎么向不懂技术的老板/面试官解释这是可接受的？
**A**：三个事实：① 离线可用（断网/隐私/无月租）是产品前提，云端方案该场景根本不可用，不是同一选项；② 8 个点集中在 5 dB 极端档，主力 15 dB+ 档差距 <3 个点；③ 差距的归因已定位（前端算力），有明确升级路径（NPU 回填）。**用「不可用对比」替代「优劣对比」是核心话术。**

**Q5**：如果重做一遍这个项目，最该提前到第 1-2 周做的是什么？
**A**：**埋点与预算校准器**。前四周大量时间花在「手工拼凑延迟数据」上——如果第 1 周就把 Trace 类 + 预算校验函数立起来，每周打通一段就自动进表，第 7-8 周的压测报告是自动聚合出来的而非补出来的。可观测性先行，是本项目最大的复盘教训。

## 8. 演示彩排清单（现场翻车预防）

演示是结课交付的最后一环，翻车点都有固定模式，逐项预防：

| 翻车点 | 预防措施 |
| --- | --- |
| 现场噪声比录屏环境大，识别率跳水 | 演示前在目标场地跑 10 条快速矩阵；备好指向性麦克风 |
| 演示时设备热机降频 | 演示前 30 分钟让设备空载散热，勿连续演示多轮 |
| 观众提问超出测试集范围 | 准备「超出能力边界」的话术：诚实说明边界 + 改进路径 |
| 打断演示失败（观众声音太小） | 彩排时按最坏音量测打断阈值，现场备手势降级方案 |
| 录屏与现场表现不一致 | 录屏注明录制条件；现场数据当场打印给评委看 |

**黄金法则**：现场演示**永远先演断网**——拔掉网线跑完一轮对话，这一动作比任何 PPT 都能证明「离线」二字的含金量。

## 9. 踩坑记录模板（博客素材，边测边写）

压测阶段的每个坑都是博客与面试素材，但**必须当场记录**——一周后细节就忘了。模板五段式：

```markdown
### 坑 #N：<一句话症状>
- **症状**：观察到什么（附日志/数字）
- **排查**：试过什么、排除了什么（走错的路也要写，体现方法论）
- **根因**：最终定位到什么（附证据）
- **修复**：改了什么、验证手段（前后对比数字）
- **预防**：加了什么断言/监控/契约防止复发
```

示例（真实发生级别）：「坑 #3：第 6 轮对话必崩——排查内存曲线发现 KV cache 线性增长无上限，根因是会话历史没截断；修复为 4 轮滑窗 + 硬上限，加了启动断言；压测表新增『第 8 轮内存』列防复发。」

**数量要求**：结课博客至少收录 5 个坑，其中至少 1 个与热机/泄漏/打断相关——这些才是系统能力的证明，比任何架构漂亮话都有说服力。

## 10. 结课面试一页纸（语音方向毕业答卷）

**问：你的助手延迟怎么做到 1.5 秒内的？**
答：预算先行——唤醒 50 / VAD 100 / ASR 200 / LLM 首 token 500 / TTS 首包 300，合计 1150 留 350 抖动余量。ASR 靠非自回归单步解码，LLM 靠 INT4 + 历史截断压 prefill，TTS 靠分句边生成边播，实测 P50/P95 各有数字支撑。

**问：这个项目里最难的部分是什么？**
答：选一个你真实踩过的坑深讲（推荐 AEC 参考回路或热机降频），按「症状→排查→根因→修复→预防」五步讲完。难点不在模型，在**跨模块的系统联调**。

**问：为什么不用云端方案？**
答：离线可用是产品前提（隐私/无网络场景/零月租）；短交互端侧延迟反而更低（省网络往返）；云端做对照评测，成功率差 8 个点集中在极端噪声档，主力档差 <3 个点且归因明确（前端算力，有升级路径）。

**问：真实用户场景和你测试场景差在哪？**
答：四个变量——噪声类型（竞争性人声最难）、温度（降频击穿预算）、时长（泄漏只有长跑显形）、交互习惯（用户会抢话/重复/半途改口）。压测矩阵就是逐个逼近这些变量，残余差距写进风险清单。
