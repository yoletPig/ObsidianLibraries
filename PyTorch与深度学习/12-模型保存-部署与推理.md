# 12 - 模型保存、部署与推理

## 本篇目标

读完本篇，你应该能做到：

1. 正确使用 `state_dict` 保存/加载模型，说清它和"整模型 pickle"的区别。
2. 写出**可断点续训**的 checkpoint（模型 + optimizer + epoch + RNG 状态）。
3. 把模型导出成 ONNX 并用 onnxruntime 做数值一致性验证。
4. 了解 `torch.compile` 的定位，掌握推理三件套：`eval()` / `inference_mode` / kv cache 概念。

训练只是模型生命周期的一半；"存得下、搬得走、跑得快"才是工程闭环。本篇也是《模型性能优化》系列的直接前置。

## 1. state_dict vs 整模型保存

### 1.1 两种方式的区别

```python
import torch
import torch.nn as nn

model = nn.Sequential(nn.Linear(784, 256), nn.ReLU(), nn.Linear(256, 10))

# 方式一(推荐): 只存参数字典
torch.save(model.state_dict(), "model.pt")          # 本质: {"0.weight": tensor..., "0.bias": ...}
sd = torch.load("model.pt", map_location="cpu")
model.load_state_dict(sd)                            # 需要先有结构一致的 model 对象

# 方式二(不推荐): pickle 整个模型对象
torch.save(model, "model_full.pt")
model2 = torch.load("model_full.pt")                 # 连结构一起恢复
```

为什么推荐 `state_dict`（PyTorch 官方文档 *Saving and Loading Models* 的立场）：

1. **可移植**：state_dict 只是一堆张量的字典，不依赖你的类定义文件路径；整模型 pickle 把"类的源码位置"也序列化了——重构目录后 `AttributeError: Can't get attribute 'MyModel'`；
2. **可控**：可以只存一部分（如只存骨干）、可以跨模型变体共享（预训练权重）、便于转ONNX/其他格式；
3. **稳定**：pickle 跨 PyTorch 版本与平台更脆。

`load_state_dict` 默认 `strict=True`——键名或形状不匹配立即报错，这**是特性**：升级模型结构时强制你显式确认兼容性（`strict=False` 会静默丢弃不匹配的键，慎用）。

### 1.2 常见的键名不匹配来源

- `nn.DataParallel`/DDP 包装会把键加前缀 `module.`（存的时候存 `model.module.state_dict()`，或加载时剥离前缀）；
- `nn.Sequential` 的键是位置编号 `0.weight`——**插入/删除一层后全部错位**，这也是"用命名子模块而非 Sequential 堆叠"的工程理由（经验做法）；
- torch.save 保存的是引用路径——移动 .pt 文件没事，但加载端要有相同 PyTorch 版本为佳。

## 2. checkpoint 与断点续训

### 2.1 为什么需要它

长训练会被中断：机器重启、显存 OOM、配额到期。没有 checkpoint 就从零开始。一个完整 checkpoint 保存**五件套**：

```python
ckpt = {
    "model": model.state_dict(),
    "optimizer": optimizer.state_dict(),   # momentum/Adam 的 m,v 状态! 不存则续训后前几百步震荡
    "epoch": epoch,
    "scheduler": scheduler.state_dict() if scheduler else None,   # lr 调度进度
    "rng": {                               # 复现训练随机流(04 章三件套的延续)
        "torch": torch.get_rng_state(),
        "cuda": torch.cuda.get_rng_state_all() if torch.cuda.is_available() else None,  # [GPU]
        "numpy": np.random.get_state(),
        "python": random.getstate(),
    },
    "best_val": best_val,                  # 早停进度(10 章)
}
torch.save(ckpt, f"ckpt_epoch{epoch}.pt")
```

### 2.2 恢复与续训

```python
ckpt = torch.load("ckpt_epoch42.pt", map_location="cpu")   # 先到 CPU, 再按需搬 GPU(跨机器兼容)
model.load_state_dict(ckpt["model"])
optimizer.load_state_dict(ckpt["optimizer"])
start_epoch = ckpt["epoch"] + 1
torch.set_rng_state(ckpt["rng"]["torch"])                  # 随机流精确衔接
# ... 然后从 start_epoch 继续训练循环
```

**最易被忽略的是 optimizer 状态**：Adam 的 $m, v$ 是训练过程的"动量记忆"。只恢复参数不恢复优化器状态，续训的头几百步等效于"冷启动的 Adam"，loss 常出现一个小跳变——这不是 bug，是你丢了状态（经验做法：对比续训前后 loss 曲线即可自检）。`map_location="cpu"` 是跨设备保存/加载的安全习惯：GPU 机器存、CPU 机器取不会报错。

## 3. ONNX 导出与验证

### 3.1 为什么需要它

PyTorch 模型要离开 Python 生态（C++ 服务、手机、WebAssembly、其他推理引擎）就需要中间表示。ONNX 是开放的计算图格式，onnxruntime 等引擎可在无 Python 环境执行它。

```python
import torch, torch.nn as nn

model = nn.Sequential(nn.Flatten(), nn.Linear(784, 256), nn.ReLU(), nn.Linear(256, 10))
model.eval()                                        # 导出前必须 eval(固定 BN/Dropout 行为)!
dummy = torch.randn(1, 1, 28, 28)                   # 示例输入: 形状+dtype 是导出的"模板"

torch.onnx.export(
    model, (dummy,), "model.onnx",
    input_names=["image"], output_names=["logits"],
    dynamic_axes={                                  # 声明 batch 维可变(不声明则固定 batch=1)
        "image": {0: "batch"},
        "logits": {0: "batch"},
    },
    opset_version=17,                               # 算子集版本, 新版本支持更多算子
)
```

导出原理一句话：**跑一遍前向，把实际执行的算子记录成静态图**（追踪式导出，trace）。这带来两个推论：① 控制流（if/while）会被"拍平"成当时走的那条路径，数据相关的动态逻辑要么避免要么用 scripting；② 导出前必须 `model.eval()`——否则 Dropout 的随机性被固化进图。

### 3.2 数值一致性验证（部署前的仪式）

```python
import onnxruntime as ort   # pip install onnxruntime
import numpy as np

x = torch.randn(8, 1, 28, 28)
with torch.inference_mode():                       # PyTorch 侧参考输出
    ref = model(x).numpy()

sess = ort.InferenceSession("model.onnx", providers=["CPUExecutionProvider"])
out = sess.run(None, {"image": x.numpy()})[0]

print(out.shape)                                   # (8, 10)
np.testing.assert_allclose(ref, out, rtol=1e-3, atol=1e-5)
print("数值一致 ✓   最大绝对误差:", np.abs(ref - out).max())   # 量级 1e-6 ~ 1e-7 属正常
```

为什么需要这一步：不同引擎的算子实现、融合策略、舍入顺序不同，输出**不可能逐位相同**，但应接近 fp32 精度极限（绝对误差 1e-6 量级）。误差到 1e-3 以上就要警惕（算子版本差异/某个层没转对）。这一步是《模型性能优化》量化工作的基线——**先确认 fp32 导出无损，再谈量化**，否则分不清误差来自量化还是导出。

## 4. torch.compile 概览

PyTorch 2.x 的编译加速（PyTorch 2 官方发布文档：https://pytorch.org/docs/stable/torch.compiler_api.html）：

```python
model = torch.compile(model)     # 一行包装, 训练/推理代码不变
# 首次调用会触发编译(慢, 几十秒), 之后每次前向走优化后的 kernel
# 取消包装: model = model._orig_mod (或重新构建)
```

它做三件事：**捕获动态图**（把 Python 执行的算子记录成图）、**图级优化**（算子融合：把 LN+残差+激活融合成更少 kernel，减少显存往返）、**代码生成**（为具体 shape 生成专用 kernel）。收益：典型模型 10%~30% 提速（官方基准口径；小模型/纯 Python 开销占比大时收益更明显）。

三个注意点（经验做法）：

1. 训练循环里频繁变 shape（变长序列每个 batch 的 T 不同）会反复触发重编译——设 `dynamic=True` 或统一 shape；
2. `torch.compile` 与 8 章的动态图**语义完全兼容**（这是它优于静态图框架的地方：失败的图会自动回退到 eager 执行）；
3. 本系列示例不默认编译（首次编译开销对教学代码是噪音），真实训练脚本值得加。

## 5. 推理优化常识

### 5.1 eval + inference_mode：免费的正确性

```python
model.eval()                          # BN 用 running stats, Dropout 关闭(03/06 章)
with torch.inference_mode():          # 比 no_grad 更快: 连版本计数都不维护(01 章)
    logits = model(x)
```

**漏掉任何一半的后果**：漏 `eval()` → dropout 开着，输出随机、精度掉；漏 `inference_mode/no_grad` → 建一张无用的 autograd 图，显存翻倍、速度下降。推理服务里这是第一行代码。

### 5.2 kv cache：生成式模型的记忆（概念预告）

自回归生成（8 章 3.3）每生成一个 token 都对**整个前缀**重新算注意力——生成第 1000 个 token 时，前 999 个 token 的 K/V 全部重算，是 $O(T^2)$ 的浪费。**KV cache** 把每层每个位置的 K、V 缓存下来，新 token 只算自己的 Q 与全量缓存的交互：每步从 $O(T^2)$ 降到 $O(T)$。

这是《VLM & VLA》里所有 LLM 推理的底层机制，也是《模型性能优化》显存优化的主角（cache 大小 = 2 × n_layer × n_kv_head × d_head × T × 精度字节数 × batch）。本系列只立概念，具体实现留给衔接系列。

### 5.3 其余常识一页

- **批量推理**：单条推理喂 batch=1 严重浪费并行度；服务端攒批（dynamic batching）是吞吐优化第一课（经验做法）；
- **量化**：fp32→int8 可省 4 倍显存带宽、多数模型精度损失 <1%——完整展开见《模型性能优化 Stage 1》，其数学合法性依赖 9 章的数值表示知识；
- **推理引擎**：ONNX Runtime / TensorRT / vLLM（LLM 专用，内置 kv cache + continuous batching）按场景选择；
- **Warmup**：首次推理有编译/内存分配开销，服务上线前预热若干请求（经验做法）。

## 6. 常见陷阱

1. **`torch.save(model)` 整模型保存**后重构代码目录，加载时 `Can't get attribute`（1.1）。
2. **checkpoint 只存模型不存 optimizer**：续训 loss 跳变，还以为模型坏了（2.1）。
3. **导出 ONNX 前忘了 `eval()`**：Dropout 被固化成"随机置零"写入静态图（更隐蔽：训练时图里带着 dropout 节点，部分算子集直接报不支持）。
4. **`dynamic_axes` 忘配 batch**：导出的模型只能跑 batch=1，服务端想攒批直接 shape 报错。
5. **加载 GPU 保存的 ckpt 不加 `map_location`**：CPU 机器上 `RuntimeError: Attempting to deserialize object on a CUDA device`。
6. **推理时误用 `requires_grad` 的输入**：输入张量默认 `requires_grad=False` 本无碍，但把 `model(x)` 的输出**再喂回模型**且保留了图，显存持续增长——服务进程内存缓慢上涨的经典病因，用 `inference_mode` 一了百了。
7. **用 `strict=False` 加载"大概齐"的权重**：静默跳过不匹配的键，模型"能跑但部分层是随机初始化"——精度问题排查的地狱级难度来源。

## 本篇小结

- 保存用 `state_dict`（张量字典，可移植），加载用 `load_state_dict(strict=True)`（键名不匹配立即暴露）。
- 断点续训五件套：model + **optimizer** + epoch + scheduler + RNG 状态；漏 optimizer 等于丢掉动量记忆。
- ONNX 导出 = 追踪式记录前向；导出前 eval、用 dynamic_axes 放开 batch；导出后必须做数值一致性验证（fp32 基线是量化工作的前提）。
- `torch.compile` 在不改变动态图语义的前提下做图优化与 kernel 生成，训练推理都能用。
- 推理三件套：`eval()` + `inference_mode()` + kv cache（概念）；量化与推理引擎见《模型性能优化》。

2. 构造键名不匹配实验：把 `nn.Sequential` 中间插入一层后加载旧 state_dict，观察 `strict=True` 的报错信息，理解错误提示如何帮你定位。
3. 把 6 章 MiniCNN 导出 ONNX 并验证数值一致性；尝试 batch=1 与 batch=16 各跑一次，确认 dynamic_axes 生效。
