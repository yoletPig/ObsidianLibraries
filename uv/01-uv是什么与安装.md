# 01 - uv 是什么与安装

## 本篇目标

1. 准确理解 uv 的定位：**不是"更快的 pip"这么简单**，而是把散装工具链收拢为单一工具；
2. 完成安装与首次验证；
3. 拿到一张"旧工具 → uv"的迁移对照表。

## 1. uv 的官方定位

uv 官方文档的自我描述（转述）："一个用 Rust 编写的极快的 Python 包与项目管理器"，并明确列出它的替代目标：

> **A single tool to replace pip, pip-tools, pipx, poetry, pyenv, twine, virtualenv, and more.**

拆开理解，uv 同时是：

| 角色 | 替代对象 | 对应 uv 能力 |
| --- | --- | --- |
| 包安装器 | pip | `uv pip install`（pip 兼容接口）/ `uv add`（项目接口） |
| 依赖锁定 | pip-tools | `uv lock` / `uv sync`（且是跨平台的 universal lockfile） |
| 虚拟环境管理 | virtualenv / venv | 自动管理 + `uv venv` |
| Python 解释器管理 | pyenv | `uv python install` / `uv python pin` |
| CLI 工具管理 | pipx | `uv tool install` / `uvx` |
| 项目/发布管理 | poetry / twine | `uv init` / `uv build` / `uv publish` |

两条设计上的重要事实：

1. **双接口并存**：`uv pip ...` 是 pip 兼容接口（老习惯无缝迁移，但**不写锁文件**）；`uv add/sync` 是项目接口（写 `uv.lock`，推荐日常使用）。哪个接口在什么场景用，02/03 篇展开；
2. **速度来自工程而非魔法**：Rust 实现 + 并行下载 + 全局缓存去重（同一 wheel 全机只存一份）。官方宣称较 pip 有 10~100 倍提速——量级可信，具体数字随场景浮动，不必当承诺。

## 2. 安装

三选一（官方文档列出的主流方式）：

```bash
# ① 官方独立安装脚本（macOS/Linux；不依赖已装 Python）
curl -LsSf https://astral.sh/uv/install.sh | sh

# ② 用已有的 pip 装（最不折腾）
pip install uv

# ③ 包管理器
brew install uv            # macOS
# Windows 官方提供 powershell 安装脚本与 winget/scoop 渠道，见官方文档
```

验证：

```bash
uv --version      # 输出版本号即成功
uv self update    # 自更新（独立安装方式才可用；pip 装的用 pip 升级）
```

> 安全提示：`curl | sh` 类安装脚本执行前先浏览其内容是基本素养；对安全敏感的环境选方式 ② 或系统包管理器。

## 3. 旧工具 → uv 对照表（速查）

| 你以前敲的 | 现在用 |
| --- | --- |
| `python -m venv .venv && source .venv/bin/activate` | `uv venv`（或干脆不手动建，`uv run/sync` 自动管理） |
| `pip install requests` | 项目内：`uv add requests`；临时：`uvx --from ...` 或 `uv pip install requests` |
| `pip freeze > requirements.txt` | `uv lock`（真正的解析锁，不是环境快照——03 篇讲区别） |
| `pip install -r requirements.txt` | `uv sync` |
| `pip-compile` | `uv lock` / `uv pip compile` |
| `pipx install ruff` | `uv tool install ruff` |
| `pipx run black` | `uvx black` |
| `pyenv install 3.12` | `uv python install 3.12` |
| `poetry add` / `poetry publish` | `uv add` / `uv publish` |

**一个重要的例外认知**：`uv pip` 接口是兼容层，适合"现有脚本/CI 改造成本要低"的过渡场景；**它不做锁与解析管理**。新项目一律用项目接口（`uv add`/`uv sync`）。

## 4. uv 与"激活虚拟环境"这件事

老工作流的仪式感来源：先 `venv`、再 `activate`、忘了激活就装错地方。uv 的默认哲学是**你不需要激活**：

- `uv run <cmd>` 在项目环境中执行命令（环境不存在会自动创建并同步依赖）；
- `uv add` / `uv sync` / `uvx` 同理——它们内部始终操作**正确的环境**，不存在"装错地方"；
- 真要在 shell 里手动激活（调试、老脚本）：`source .venv/bin/activate` 照旧可用——uv 默认在项目根创建 `.venv`，与既有习惯完全兼容。

这个转变的心智价值：**环境从"你要维护的状态"变成"uv 保证的不变量"**（`uv sync` 后环境必然与锁文件一致）。

## 5. 什么情况下不该（暂时）用 uv

保持诚实的工程判断：

1. **依赖 uv 私有扩展能力的生态约束**：个别旧项目使用 Poetry 的特定语法/插件，迁移要动 `[tool.poetry]` 段（08 篇给迁移路径）；
2. **极端离线/特殊网络环境**：uv 的一切都走 index 配置，自建镜像的配置量比 pip 多了解一点点（08 篇）；
3. **团队规范锁定**：团队统一用 Poetry 时，"个人换成 uv"制造的配置漂移比收益大——先推动团队决策（08 篇的落地清单）。

除此之外，个人项目从 uv 起步在 2024 年后已是合理默认。
