# 02 - 项目管理基础

## 本篇目标

走通 uv 的标准项目闭环：`init → add → sync → run`，并理解每一步在文件系统上**实际发生**了什么（本系列风格：不背命令，看懂机制）。

## 1. 建项目：uv init 的三种形态

```bash
uv init myapp              # ① 应用（默认）：可运行的项目
uv init --lib mylib        # ② 库：带 src 布局与构建配置
uv init                    # ③ 在当前目录初始化（已有目录补齐文件）
```

以默认应用形态为例，产出：

```text
myapp/
├── pyproject.toml     # 项目元数据与依赖声明（唯一的"事实来源"）
├── main.py            # 入口示例（uv run main.py 即可跑）
├── .python-version    # 声明本项目用的 Python 版本（04 篇展开）
└── README.md
```

生成的 `pyproject.toml`（PEP 621 标准格式，**不是** Poetry 的私有格式）：

```toml
[project]
name = "myapp"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
requires-python = ">=3.12"     # 最低 Python 版本约束
dependencies = []              # 依赖将出现在这里
```

三个值得注意的设计：

1. **`pyproject.toml` 是 PEP 621/518 的标准文件**——工具无关（pip/build 生态都认），换成别的工具迁移成本低；
2. **`.python-version` 是独立小文件**——它的存在让"这个项目要什么 Python"成为可提交、可版本化的事实（04 篇）；
3. `uv init --lib` 的 `src/` 布局是打包最佳实践（源码与构建产物分离，测试 import 的是安装后的包）。

## 2. 加依赖：uv add 做了五件事

```bash
cd myapp
uv add requests           # 加运行依赖
uv add --dev pytest       # 加开发依赖（进入 dependency-groups 的 dev 组，03/08 篇）
```

`uv add` 的幕后动作（每一步都可见可查）：

1. **解析**：计算满足版本约束与全部现有依赖的依赖图（解析器是 uv 的心脏，03 篇展开）；
2. **下载并缓存 wheel**（全局缓存去重）；
3. **更新 `pyproject.toml`** 的 `dependencies`；
4. **更新 `uv.lock`**（锁文件首次出现，03 篇的主角）；
5. **更新 `.venv` 环境**（不存在则先创建）。

```bash
uv remove requests        # 反向操作：五件事全部回滚
uv add "pandas>=2.2"      # 支持完整的版本规范语法（03 篇详解）
```

## 3. uv sync：环境与锁文件对齐

`uv sync` 的语义一句话：**让 `.venv` 精确等于 `uv.lock` 的内容**——多装的删掉、缺的补上、版本不对的换掉。

```bash
git pull 之后          → uv sync     # 拉了同事更新的 uv.lock，环境一键对齐
CI 里                  → uv sync     # 同样的一行
想连开发依赖都不要     → uv sync --no-dev
只想跑生产最小环境     → uv sync --no-dev（部署场景，08 篇）
```

这就是 01 篇说的"环境是 uv 保证的不变量"：**不要再用 pip 往 `.venv` 里零散装包**——那会让环境偏离锁文件，`uv sync` 会把你手装的包删掉（这是特性不是 bug：环境必须可复现）。

## 4. uv run：在正确环境里执行一切

```bash
uv run main.py            # 在项目环境中跑脚本
uv run pytest             # 在项目环境中跑任意命令
uv run python             # 交互解释器
uv run -v main.py         # -v 能看到它做了什么（排查环境问题的入口）
```

`uv run` 的决策逻辑：项目环境就绪（与锁一致）→ 直接执行；不就绪 → **先自动 sync 再执行**。所以新人上手的完整流程只有三行：

```bash
git clone <repo> && cd <repo>
uv sync        # 或直接 uv run ...
uv run pytest
```

**对比旧世界**：装 Python 版本（pyenv）→ 建环境（venv）→ 激活 → 装 pip 工具 → 装依赖 → 祈祷。每一行的消失都是有原因的（锁文件 + 解释器管理 + 缓存）。

## 5. 项目文件清单：哪些提交、哪些忽略

| 文件 | 提交进 Git？ | 理由 |
| --- | --- | --- |
| `pyproject.toml` | ✅ 必须 | 事实来源 |
| `uv.lock` | ✅ 必须（应用项目） | 可复现的依赖图（03 篇）；库项目可讨论（08 篇） |
| `.python-version` | ✅ 必须 | 团队解释器一致性 |
| `.venv/` | ❌ 永不 | 本地环境，可由 lock 重建（Git 02 篇"可重建的不入库"） |

（uv 不会自动生成 `.gitignore`，记得手写：`.venv/`。）

## 6. 一个最小工作日

```bash
# 早上拉代码
git pull && uv sync
# 开发：加个依赖试试
uv add httpx
# 跑测试
uv run pytest
# 收工：pyproject.toml 与 uv.lock 的改动随代码一起提交
git add pyproject.toml uv.lock src/ && git commit -m "feat: 接入 httpx"
```
