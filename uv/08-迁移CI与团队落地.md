# 08 - 迁移、CI 与团队落地

## 本篇目标（uv 系列收官）

三件事：把**老项目**迁到 uv（requirements.txt / Poetry 两条路径）、把 uv 装进 **CI**（含缓存与发布）、以及**团队**层面的落地决策清单。

## 1. 路径 A：requirements.txt 项目 → uv

最常见的存量形态。两步走：

```bash
# ① 生成 pyproject.toml（在项目根）
uv init --bare        # 只补最小元数据，不建 main.py（--bare 的语义见 uv init --help）

# ② 把存量 requirements 转为项目依赖
uv add -r requirements.txt        # 逐条解析并写入 pyproject + 生成 uv.lock
```

**迁移中的判断（不是无脑转换）**：

1. requirements.txt 里的**传递依赖**（当年 pip freeze 导出的快照）不该进 `pyproject.toml`——只挑你**直接 import** 的包；传递依赖交给解析器与锁（03 篇两个文件的角色分工）；
2. `uv add -r` 之后跑测试再提交——锁文件与旧环境可能有差异（旧锁来自旧解析），先验证再切换；
3. 过渡期可以**双轨**：CI 同时跑 `uv sync` 与旧流程一个迭代周期，稳定后删旧文件。

`uv pip compile` 的补充定位：如果项目要**继续用 pip**但想要跨平台锁，`uv pip compile requirements.in -o requirements.txt --universal` 可单独作为"更快的 pip-tools"使用——这是 01 篇说的 pip 兼容接口的正经用途。

## 2. 路径 B：Poetry 项目 → uv

Poetry 的 `[tool.poetry]` 段是私有格式，迁移 = 翻译成 PEP 621 标准：

```toml
# 迁移前（tool.poetry 格式）          # 迁移后（PEP 621 标准）
[tool.poetry.dependencies]           [project]
python = "^3.11"                     requires-python = ">=3.11"
requests = "^2.31"                   dependencies = ["requests>=2.31"]
[tool.poetry.group.dev.dependencies] [dependency-groups]
pytest = "*"                         dev = ["pytest"]
```

机械工作可以用社区转换脚本（如 `migrate-to-uv` 一类工具，以各自文档为准），但**迁移后必须人工核对**三处：版本约束的语义等价（`^3.11` → `>=3.11,<4` 是 uv 文档给出的对应）、extras 的转换、以及 `poetry.lock` → `uv.lock`（**重新生成而不是转换**——解析器不同，锁没有可比性）。

## 3. CI 集成：标准流水线模板

GitHub Actions 形态（GitLab/Jenkins 同理，改命令来源即可）：

```yaml
name: ci
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5          # 官方 action：装 uv + 内置缓存
        with:
          enable-cache: true                  # 缓存 uv 缓存目录（03 篇全局缓存的 CI 版）
      - run: uv sync --frozen                 # ⭐ frozen：锁与 pyproject 不一致即失败
      - run: uv run pytest
```

三个 CI 纪律（都是可复现性的收口）：

1. **`uv sync --frozen`**：CI 只许按锁装，**禁止在 CI 里隐式重解析**——锁过期就应该红，而不是悄悄解析出新版本；
2. **锁版本的解释器矩阵**：`uv python install 3.10 3.11 3.12` + 矩阵策略（04 篇库项目组合的兑现）；
3. **缓存键**用 `uv.lock` 的哈希——锁变了缓存自然失效（`setup-uv` 已内置该逻辑）。

## 4. 发布：uv build / uv publish

库项目的最后一步也收编了（替代 build/twine）：

```bash
uv build                     # 产出 sdist + wheel 到 dist/
uv publish                   # 发布到 PyPI（token 走 UV_PUBLISH_TOKEN 环境变量）
```

发布前自检三件套：`pyproject.toml` 元数据完整（description/readme/classifiers）、`requires-python` 与实际测试矩阵一致、版本号按 SemVer 升过（Git 09 篇的 tag 流程衔接：打 tag `v1.2.0` → CI 按 tag 构建 → `uv publish`）。

## 5. 私有源与镜像配置

企业内网/国内加速的标准配置（写在项目 `pyproject.toml`，随仓库分发）：

```toml
[[tool.uv.index]]
name = "internal"
url = "https://internal.example.com/simple/"   # 内部 PyPI / 国内镜像
default = true
```

- 环境变量方式：`UV_DEFAULT_INDEX`（替换旧 `UV_INDEX_URL` 的现代写法，具体以 uv 文档 ENV 页为准）；
- **凭据不进仓库**：走环境变量或 keyring（与 Git 04 篇凭据纪律同构）。

□ 迁移期双轨验证一个迭代 → 删旧 requirements/工具残留
