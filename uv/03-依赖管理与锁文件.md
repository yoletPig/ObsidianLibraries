# 03 - 依赖管理与锁文件

## 本篇目标

1. 区分两个"版本文件"的角色：`pyproject.toml`（声明意图）vs `uv.lock`（锁定事实）；
2. 看懂 uv 的解析行为与版本规范语法；
3. 掌握依赖分组（dependency groups）与可选依赖（extras），以及团队协作的锁纪律。

## 1. 两个文件，两种语义

| | `pyproject.toml` | `uv.lock` |
| --- | --- | --- |
| 谁写 | 人（`uv add` 修改） | 解析器（`uv lock` 生成） |
| 内容 | **直接依赖 + 版本约束**（意图） | **完整依赖图每个包的精确版本与哈希**（事实） |
| 类比 | 菜谱（"要牛肉，要辣"） | 采购单（"XX 品牌牛肉 500g，批次号…"） |

为什么两者都要？只看意图文件，`pip install` 每次解析都可能拿到不同结果（传递依赖的版本漂移）——"上周能装，今天装出 bug"。锁文件把**解析结果固化**，`uv sync` 不再解析、只按锁安装——"任何时候任何机器，环境完全一致"。这就是可复现性的机制。

**uv 的锁是 universal lockfile**：一份锁覆盖所有平台与 Python 版本（解析时把各平台的解都算出来），不再需要 per-OS 的锁文件——对比 pip-tools 时代"每个环境各自 compile"的碎片化，这是 uv 锁的架构级改进。

## 2. 解析：uv 在什么时候、按什么规则算

解析发生的时机：`uv add`（必须，因为依赖变了）、`uv lock --upgrade`（你主动要求全面升级）、`uv sync` **不解析**（只按锁装——快与稳的来源）。

解析器的目标（约束求解）：找到一组包版本，**同时满足**所有直接/传递依赖的版本要求。当"不可能满足"时你会看到 Conflict 报错（uv 会列出冲突链条）——这不是工具 bug，是依赖真的互斥（03 篇末给解法）。

版本规范语法速查（PEP 440 标准）：

```toml
dependencies = [
  "requests>=2.31",        # ≥ 2.31
  "pandas>=2.2,<3.0",      # 区间约束（跨大版本要小心！）
  "httpx==0.27.*",         # 锁定到次版本段
  "flask~=3.0",            # 等价 >=3.0, ==3.*（允许补丁级浮动）
  "torch>=2.0; sys_platform == 'linux'",   # 环境标记（PEP 508）
]
```

**约束写法的团队纪律**：应用项目**写宽**（`>=2.31` 即可——真正的锁死交给 `uv.lock`，意图文件里写死版本是"双重锁定"，只会让依赖树更难解）；**库项目更要写宽**（你的下游无法满足"必须是 2.31.0 整"的库）。错误写法的代价：约束过紧 → 解析器无解或被迫使用旧包。

## 3. 锁文件的协作纪律（Git 系列 02 篇的落地）

```bash
git pull
uv sync               # 拉同事更新过的 uv.lock 后：环境对齐，结束
```

1. **`uv.lock` 必须提交**（应用项目），且**与 `pyproject.toml` 同一个 commit**——否则 CI/同事会出现"意图与事实不一致"的中间状态；
2. **锁冲突的处理**：两人同时改依赖 → pull 时 uv.lock 冲突 → **不要手工合并锁文件**（它是生成物，合并生成物必错）：取一侧，重跑 `uv add` 补上另一侧的包，让 uv 重新生成；
3. **升级策略分离**：`uv sync` 永不升级（按锁装）；`uv lock --upgrade` 才升级（每周/每迭代跑一次的维护动作，配 CI 验证）。**把"装依赖"与"升级依赖"分成两个动作**，是稳定性纪律的核心。

## 4. 依赖分组：dev 依赖与其他场景

uv 支持 **PEP 735 dependency groups**（`[dependency-groups]` 表）——2024 年被 PyPA 接受的标准，取代各家私有的 dev 依赖写法：

```toml
[dependency-groups]
dev = [                     # uv 默认组：uv add --dev pytest 进这里
  "pytest>=8.0",
  "ruff>=0.6",
]
lint = ["ruff>=0.6"]        # 自定义组：按场景分组
docs = ["mkdocs>=1.6"]
```

```bash
uv sync --group lint        # 只装 lint 组
uv sync --no-group docs     # 排除某组
uv sync --no-dev            # 生产环境：不装 dev 组（08 篇部署用）
```

与 **extras（可选依赖）** 的分工：extras 是 `[project.optional-dependencies]`，**面向下游使用者**（`pip install mylib[plot]`）；dependency-groups 是**面向开发者自己**（测试/lint/文档工具）。混用的信号：下游开始装你的 "dev" 组——那它就该是 extras。

## 5. 解析失败的救援

```bash
uv add "a-package"          # error: Because ... conflict ...

# ① 看清冲突链：报错会列出"谁要求谁≥X，谁又要求<Y"
# ② 释放空间：放宽自己过紧的约束（§2 纪律）
# ③ 平台冲突（如某包无 Windows wheel）：
uv add "package" --optional gpu ...    # 或用环境标记限定平台
# ④ 真实的互斥：寻找替代包 / 联系上游放约束 / [tool.uv] override-dependencies
#    （覆盖传递依赖的约束——最后手段，会绕开上游的声明，写注释说明原因）
```

## 6. 缓存：为什么 uv 的安装快且省

全局缓存（默认 `~/.cache/uv`，Linux）按内容寻址存储 wheel：**同一 wheel 全机只存一份**，项目环境里放的是硬链接（同盘）——10 个项目用 torch，磁盘也只有一份。缓存相关的常用操作：

```bash
uv cache clean                # 清空
uv cache prune                # 清理未使用的缓存项
```

缓存损坏的排查思路：删除缓存重试永远是安全动作（它可再生——Git 02 篇"可重建的不入库"的 uv 版）。
