# 12 - 运维-备份与监控

## 本篇目标

- 会做容量规划：行大小估算到磁盘/内存/备份的换算。
- 配好慢查询日志与例行巡检，让问题在用户投诉前被发现。
- 建立监控指标分层（连接/命中率/延迟/磁盘），知道每层指标异常说明什么。
- 跑通备份恢复演练（sqlite/postgres 实测"备份→删库→恢复"），掌握双写/影子表迁移流程，最后以 25 道面试高频题收束全系列。

## 1. 容量规划：一张表到底占多少磁盘

容量规划的起点是**行大小估算**——不是拍脑袋"数据不大"，而是算出数字（数字才能外推到备份窗口、内存配比）：

```text
单行大小 ≈ Σ各列字节数 + 行头开销
  数值: INT 4B, BIGINT 8B, NUMERIC(12,4) ~8-12B, TIMESTAMP 8B
  文本: TEXT = 实际字节(UTF8 中文 ~3B/字) + 1B 长度前缀
  PG 行头: ~23B 对齐到 24B + NULL 位图; SQLite: 每列 1-2B 变长头

例: kline_1min(symbol TEXT 9B, ts 8B, 5×NUMERIC ~50B)
   ≈ 9+8+50 + 24(行头) + 12(索引条目×1.2) ≈ 100B/行
年数据: A股 5000 只 × 240 日 × 240 bar ≈ 2.9 亿行 ≈ 29 GB(表) + ~15 GB(主键索引)
```

外推三件套（经验做法）：

1. **磁盘**：表+索引+WAL（峰值写入 × 保窗时长）+ 临时空间（排序/hash 落盘）+ compaction 余量（LSM 引擎留 30-50%，06 章）。**水位 70% 报警**——文件系统在 90% 以上性能骤降且迁移无余地。
2. **内存**：shared_buffers（PG 惯例 25% 系统内存）+ 工作内存（sort/hash，每连接每操作）+ OS 页缓存（剩余大头，05 章 BUFFERS 命中率的来源）。
3. **备份体积与窗口**：全量 ≈ 数据体积 × 压缩比（PG dump -Fc 约 3-5x）；增量 = WAL 速率。**备份窗口必须小于业务低峰时长**，否则备份任务跨峰抢 IO。

验证手段：建 100 万行样例表后 `pg_total_relation_size('表名')` 实测再线性外推——估算与实测偏差 >20% 时说明行宽假设错了（通常是 TEXT 列没算够）。

## 2. 慢查询日志与例行巡检

**慢查询日志是第 05 章"定位"步的常开开关**：

```bash
# PostgreSQL: postgresql.conf
log_min_duration_statement = 500        # 超500ms的语句入日志
log_lock_waits = on                     # 锁等待入日志
# MySQL: slow_query_log=ON; long_query_time=0.5; log_queries_not_using_indexes=ON(谨慎,噪声大)
```

例行巡检清单（经验做法：每天自动化跑，输出一屏，异常才细看）：

```sql
-- PG 例行五连(逐条解释器: 看什么/阈值/异常说明什么)
SELECT count(*) FILTER (WHERE state='idle in transaction') FROM pg_stat_activity;
-- >0 且持续: 长事务冻结 vacuum(04 章) → 找到 pid 杀掉并修应用

SELECT relname, n_live_tup, n_dead_tup,
       round(n_dead_tup*100.0/NULLIF(n_live_tup+n_dead_tup,0),1) AS dead_pct
FROM pg_stat_user_tables ORDER BY dead_pct DESC LIMIT 5;
-- dead_pct > 20%: 表膨胀, 检查 autovacuum 是否被长事务卡住

SELECT total_exec_time, calls, query FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 5;
-- TOP SQL 是否都是认识的? 冒出来的陌生大查询 = 事故前兆

SELECT count(*) FROM pg_stat_activity WHERE wait_event_type='Lock';
-- 锁等待队列 >0: 查 pg_locks 找持锁者(DDL? 长事务?)

SELECT pg_size_pretty(pg_database_size(current_database()));
-- 库体积趋势: 周环比暴涨 → 找失控表(往往是日志/事件表忘了分区滚动)
```

SQLite 的巡检极简版：`PRAGMA integrity_check;`（文件完整性）、`PRAGMA wal_checkpoint(PASSIVE);`（WAL 大小）、`PRAGMA optimize;`（顺手刷统计）——个人项目每周跑一次脚本即可（经验做法）。

## 3. 监控指标分层：每层异常说明什么

监控不是指标越多越好，而是**分层定位**（四层金字塔，从外到内）：

```
L4 业务层:   核心接口成功率/P99延迟              ← 用户视角, 报警最先响
L3 应用层:   连接池等待数/获取连接耗时            ← 应用侧池(07章)排队=池太小或库慢
L2 数据库层: 活跃连接数/长事务数/锁等待/缓存命中率/
             主从复制延迟(repl lag 秒)            ← 数据库健康
L1 资源层:   CPU/内存/磁盘空间/磁盘IO利用率       ← 兜底, 涨到边界前要扩容
```

逐层速查表（每行都是"指标异常 → 第一嫌疑人"的映射）：

| 指标 | 健康区间（经验值） | 异常的第一嫌疑人 |
| --- | --- | --- |
| 活跃连接数 | < max_connections×70% | 连接池泄漏（应用忘还）；慢查询堆积 |
| 缓存命中率（缓冲池） | > 95% | 突然下跌：新查询形态/大范围扫描/内存被挤 |
| 主从延迟 | < 秒级 | 从库单线程回放追不上：大事务/DDL；网络 |
| 磁盘 IO util | < 80% | 全表扫描潮（05 章）；compaction 风暴（06 章） |
| 死元组比例 | < 20% | 长事务；autovacuum 调度不足 |
| WAL 产生速率 | 平稳 | 突增：批量任务未分批/未合并提交 |

报警设计原则（经验做法）：**L4 直接呼人（P0），L2/L3 工单处理（P1/P2），L1 趋势周报**；每个报警必须带"下一步看什么"的 runbook 链接——没有处置动作的报警只是噪音发生器。

## 4. 备份恢复演练：光备份不恢复 = 没备份

原则先行（本系列重复三次的守则）：**备份的可靠性由恢复演练定义**。演练脚本化、定期跑、结果留档。

SQLite 恢复演练（最简形态，30 秒跑完）：

```bash
# ① 备份(在线安全备份: 用 .backup 命令而非 cp, 避免拷到写一半的状态)
sqlite3 /tmp/app.db ".backup /tmp/app_backup.db"
# ② 灾难: 主库损坏(模拟误删)
mv /tmp/app.db /tmp/app.db.broken
# ③ 恢复 + 验证(行数对账)
cp /tmp/app_backup.db /tmp/app.db
sqlite3 /tmp/app.db "PRAGMA integrity_check; SELECT count(*) FROM users;"
# 输出: ok | 100  ← 演练通过的标准输出
```

PostgreSQL 恢复演练（逻辑备份路径，配合 07 章 pg_dump）：

```bash
# ① 全量备份
pg_dump "postgresql://yyl@localhost/dev" -Fc -f /backup/dev_$(date +%F).dump
# ② 灾难模拟: 删表
psql -c "DROP TABLE kline_1min"
# ③ 恢复到临时库对账(不直接覆盖生产, 先验证再切换)
createdb dev_restore && pg_restore -d dev_restore /backup/dev_*.dump
psql -d dev_restore -c "SELECT count(*) FROM kline_1min"      # 与生产对账
# ④ 通过后换库/改连接串。物理备份+PITR 恢复(任意时间点)流程见 07 章 6 节,
#    演练要点: 在恢复机上起实例 → recovery_target_time 定到"误删前 1 分钟" → 验证数据
```

演练检查单（经验做法）：恢复耗时（算 RTO 是否达标）、对账 SQL（行数 + 抽样内容 + 关键聚合）、演练周期（月度）、**演练记录归档**（谁、何时、耗时、结果）——"上次演练通过"是事故夜唯一的镇静剂。

## 5. 迁移流程：双写与影子表

换库/改表结构的迁移，风险的根源是**新旧两套系统在切换窗口内的行为差异**。两套主流流程：

**影子表（改表结构）**——同一库内的 schema 迁移：

```sql
-- ① 建新结构的影子表
CREATE TABLE orders_new (LIKE orders INCLUDING ALL);
-- ② 双写: 应用同时写新旧两表(或触发器兜底)
-- ③ 回填历史: 分批 UPDATE/INSERT ... SELECT (每批 1万行, 避免长事务, 04 章)
INSERT INTO orders_new SELECT * FROM orders WHERE id BETWEEN 1 AND 10000;
-- ④ 对账: 行数+校验和
SELECT count(*), sum(hashtext(id::text||qty::text)) FROM orders;      -- 与 orders_new 对比
-- ⑤ 切读 → 观察期 → 改名换位(原子):
ALTER TABLE orders RENAME TO orders_old;
ALTER TABLE orders_new RENAME TO orders;
-- ⑥ 观察一周无回滚需求后 DROP orders_old
```

**双写（换存储引擎）**——PG 迁 ClickHouse、加缓存层等跨系统迁移：

```text
① 写路径双写(先写老库成功为新真源, 新库失败只告警不阻断)
② 历史数据批量搬迁(分批+限速, 不抢业务 IO)
③ 双读比对: 灰度流量同时读两库, 日志记录差异(字段级 diff), 差异率→0 才继续
④ 切读新库(可回滚: 读开关拨回老库)
⑤ 停写老库, 老库转只读归档; 保留期后下线
```

两条铁律贯穿（经验做法）：**每一步可回滚**（切换点用开关/改名实现，不删任何东西）；**对账先于切换**（count/checksum/抽样 diff，数字不齐不切读）。时间换算：一次严肃迁移的 80% 工时在③④（比对与灰度），写迁移脚本只占 20%——预算别排反。

## 6. 面试高频问题清单（25 题带要点）

全系列浓缩成 25 题（标注所属章节，答案要点=答题骨架；展开能力靠前面章节的实验）：

**索引与查询（03/05 章）**

1. 索引失效的场景有哪些？——函数包裹列/隐式转换/前导 %LIKE/跳过最左列/低选择性优化器放弃/统计过期；每条配一个改法。
2. 为什么 B+树而不是红黑树/哈希/跳表？——页对齐 IO（3-4 层摸到千万行）；哈希无范围；跳表内存友好（Redis zset）；答介质与服务形态。
3. 聚簇索引与二级索引的区别？回表是什么？——InnoDB 主键即数据；二级叶存主键→回表；覆盖索引消灭回表。
4. 最左前缀原则的原理？——联合索引按 (a,b) 排序=先姓后名；等值在前范围收尾；书写顺序无关。
5. 什么是覆盖索引？什么场景值得做？——查询列全在索引里（Index Only Scan）；高频+列少+回表热点才做。
6. EXPLAIN 你看哪几个字段？——cost/rows(估算vs实际)/actual time×loops/扫描节点/Rows Removed；统计信息与 ANALYZE。
7. 三种 JOIN 算法与适用场景？——Nested Loop(小驱动大+索引)、Hash(大等值)、Merge(有序/范围)；驱动表选择。

**事务与 MVCC（04 章 + 分布式 07 章）**

8. ACID 分别靠什么实现？——undo/redo(WAL)/锁+MVCC/应用不变量；C 常被误解为数据库保证。
9. 三大并发异常与隔离级别对应？——脏读/不可重复读/幻读 × RC/RR；RR 是否有幻阅读实现（PG 出写偏斜，MySQL 间隙锁基本挡住）。
10. MVCC 的原理？——版本链/快照判定/读不加锁；PG xmin/xmax 堆内多版本 vs InnoDB undo 链。
11. 快照读和当前读的区别？——普通 SELECT 读快照；UPDATE/FOR UPDATE 读最新+加锁；丢更新的根源与修复。
12. 长事务有什么危害？——冻结旧版本回收：PG 膨胀+xid 回卷、InnoDB undo 膨胀；idle in transaction 监控。
13. 写偏斜是什么？怎么防？——两事务读对方要写的集合；SI 的残留异常；SSI/串行化+重试/应用层约束。

**存储引擎（06/10 章）**

14. B+树 vs LSM-Tree 的取舍？——读放大/写放大/空间放大三角；RocksDB/Cassandra 选 LSM 的负载特征。
15. WAL 的作用与流程？——先日志后数据、组提交、checkpoint；崩溃恢复=重放。
16. 为什么顺序写比随机写快？——寻道/页擦除；01 章存储层次数字；LSM 把随机写变顺序追加。
17. SQLite 的 WAL 模式解决了什么？——读写不互斥；单写者模型不变；checkpoint 语义。
18. 页是什么？为什么按页管理？——最小 IO 单元；缓冲池的单位；B+树节点=页。

**缓存与 Redis（08 章）**

19. 缓存穿透/击穿/雪崩与对策？——空值+布隆/单飞互斥/错峰 TTL+多级+熔断；各自成因一句话。
20. 先更新库还是先更新缓存？——先更新库再删缓存；双写窗口分析；延迟双删与 binlog 订阅兜底。
21. 分布式锁怎么正确实现？——SETNX+EX+token+Lua 释放+看门狗续期；Redlock 争议：效率锁 vs 正确性锁（fencing/幂等）。
22. Redis 持久化 RDB vs AOF？——checkpoint vs WAL 的内存版；everysec 丢 1s；混合持久化。
23. zset 为什么用跳表？——内存介质上实现简单/范围查询不弱/并发友好；与 B+树的介质差异。

**建模与运维（11/12 章）**

24. OLTP 与 OLAP 的区别？列存为什么快？——负载/事务模型；少列 IO+压缩+向量化；TP/AP 分库组合。
25. 线上数据库突然变慢，排查思路？——分层定位：业务监控→pg_stat_activity/slow log→EXPLAIN ANALYZE 三看→索引失效四因→资源层；带回滚预案与复盘文档。**答的是流程不是知识点**。

## 常见误区

1. **"备份=复制一份文件"**：在线库直接 cp 可能拷到写一半的页（SQLite 用 .backup、PG 用 pg_basebackup/dump）；更致命的是从不恢复验证——备份链路里唯一不可省的环节是演练。
2. **"监控装上就完事"**：没有 runbook 的报警=噪音发生器；指标异常要映射到"第一嫌疑人+下一步动作"（3 节速查表），否则值班只会关报警。
3. **"迁移=导出导入"**：迁移的难点在切换窗口的行为等价与可回滚，不在搬数据。没有对账与灰度读的迁移是赌博；每步开关化才谈得上流程。
4. **"容量规划=现在够用"**：要按增速外推到"下一次扩容决策点"（水位 70%），并给 WAL/compaction/备份留余量——磁盘打满的库连删除数据的操作都可能跑不动。
5. **"巡检是 DBA 的事"**：应用工程师写出的长事务、无索引大查询、忘分批的批量任务，都会在巡检指标上现形——指标异常的根因八成在应用代码里。

## 本篇小结

- 容量规划从行大小估算开始，外推到表/索引/WAL/备份四本账；估算必须用实测校准（pg_total_relation_size）。
- 慢查询日志常开 + 每日例行五连（长事务/死元组/TOP SQL/锁等待/库体积）——问题在投诉前被发现。
- 监控四层（业务/应用/数据库/资源），每层异常有"第一嫌疑人"映射；报警必须带处置动作。
- 备份恢复演练脚本化、月度化：sqlite .backup 与 pg_dump/pg_restore 全流程实测；"光备份不恢复=没备份"。
- 迁移两套流程：影子表（改结构）与双写（换引擎）；每步可回滚、对账先于切换，80% 工时在比对与灰度。
- 25 题清单是全系列的索引：每题要点都能在对应章节找到实验与出处——面试答的是"做过"而非"背过"。

## 练习

1. 容量估算实操：给自己的业务表做 1 节的行大小估算，建 100 万行样例后用 `pg_total_relation_size` 校验，写下偏差与修正（TEXT 列、NULL 位图往往是偏差源）。
2. 把 2 节巡检五连写成每日 cron 脚本，输出汇总一屏；人为制造一个 `idle in transaction`（BEGIN 后 sleep）验证第一条 SQL 能抓到它。
3. 完整演练：对测试库执行"pg_dump → DROP 表 → pg_restore 到新库 → count 对账 → 换连接串"全流程并计时；把你的 RTO（恢复耗时）与数据规模写成一行记录，作为第一份演练档案。
4. 影子表迁移实战：给已有 100 万行的表"新增一列并改主键"——按 5 节六步流程走完（含对账 SQL 与改名切换），记录每步耗时；思考哪一步最容易出事故。
