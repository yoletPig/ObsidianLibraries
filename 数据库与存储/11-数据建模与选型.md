# 11 - 数据建模与选型

## 本篇目标

- 快速过三范式，判断什么时候**故意**反范式——建模的第一决策。
- 区分读多写少 vs 写多读少的建模差异，认识 append-only 事件表的设计模式。
- 完整设计量化行情 OHLCV 表（索引/分区/降采样），衔接量化 02 篇的数据落库。
- 理解 OLTP vs OLAP 的存储分野（列存为什么快），拿到一张可操作的技术选型决策树，内化"先用 Postgres"原则。

## 1. 范式与反范式：什么时候故意冗余

三范式速览（Codd 1970 的关系模型规范化，教材定义一句话版）：

```
1NF: 每列原子性, 不嵌套(一个"联系方式"列存 "电话,邮箱" 违反)
2NF: 非主属性完全依赖主键(订单表里"商品名"只依赖"商品id"→挪到商品表)
3NF: 消除传递依赖(员工表存"部门id"+"部门名"→部门名依赖部门id, 挪出去)
```

范式化的收益：**更新一处即可**，不冗余、不变态。但读路径变贵——每个查询都要 JOIN。**反范式（故意冗余）**把读时 JOIN 变成写时冗余：

```sql
-- 范式化: 订单与商品分表, 查询要 JOIN
SELECT o.id, p.name, o.qty FROM orders o JOIN products p ON p.id = o.product_id;
-- 反范式: 订单表冗余商品名(写时抄一份)
ALTER TABLE orders ADD COLUMN product_name TEXT;
UPDATE orders o SET product_name = (SELECT name FROM products WHERE id = o.product_id);
-- 商品改名后旧订单还显示旧名 —— 这可能是 bug, 也可能是"历史快照"的正确语义!
```

决策清单（经验做法，逐条都是业务问题不是技术问题）：

1. **冗余的是"事实快照"还是"当前状态"**：订单里的商品名/成交价是事实快照（下单那一刻的世界），冗余是**正确**；用户表冗余"最近订单摘要"是当前状态，需要同步机制。
2. **读放大的痛 vs 一致性维护的痛**：读路径 QPS 高、JOIN 深达 3-4 层 → 考虑冗余或视图/物化视图；写路径要保证多表同步 → 老实范式化 + 事务。
3. **谁负责同步冗余列**：应用双写（易漏）、触发器（隐藏逻辑）、CDC 订阅（08 章缓存一致性的同款方案）——三选一要写进团队文档。

一句话原则：**范式化是默认，反范式是买了"读性能"后要自己养的一致性账单**。先按范式建模拿到正确性，再按真实查询计划（05 章）决定在哪里付冗余。

## 2. 读多写少 vs 写多读少：两种建模世界观

同一份数据，两种负载的建模截然不同：

| 维度 | 读多写少（内容/配置/风控规则） | 写多读少（埋点/行情 tick/日志） |
| --- | --- | --- |
| 表形态 | 宽表 + 状态行（UPDATE 当前值） | **append-only 事件表**（只 INSERT 不 UPDATE） |
| 索引 | 为查询模式精建（覆盖索引/联合索引） | 少建（写放大），靠分区 + 时间键 |
| 更新语义 | 幂等 upsert（ON CONFLICT） | 追加即事实，错了补一条更正事件 |
| 典型优化 | 缓存（08 章）、物化视图 | 分区滚动删除、批量写入、LSM 引擎 |
| 查询 | 点查 + 短聚合 | 时间范围扫描 + 预聚合 |

**append-only（只追加）**是写多读少的核心模式：不 UPDATE 不 DELETE，每次变化都是一条新事件。收益：写路径只有顺序追加（10 章手写引擎的原始形态）；天然审计（谁在何时改了什么全在日志里）；删除旧数据 = drop 分区（07 章分区表收益）。代价：读"当前状态"要按时间取最新（窗口函数 `ROW_NUMBER`，02 章）——所以常配一张"物化后的状态表"由后台从事件流刷新。这就是**事件溯源（Event Sourcing）/ CDC 思想**的表级雏形：事实只追加，状态是事实的函数。

## 3. 事件表设计实例：量化行情 OHLCV 表

量化 02 篇抓下来的行情怎么落库？这是事件表设计的完整实例（PG 16，07 章分区语法 + 03 章索引原则的总装）：

```sql
-- OHLCV: 每行 = 一只股票在一个 bar 周期的开高低收与成交量
CREATE TABLE kline_1min (
    symbol   TEXT        NOT NULL,          -- 股票代码
    ts       TIMESTAMPTZ NOT NULL,          -- bar 结束时间(交易所口径写进注释!)
    o NUMERIC(12,4), h NUMERIC(12,4),      -- 金额一律 NUMERIC(07 章)
    l NUMERIC(12,4), c NUMERIC(12,4),
    v        NUMERIC(18,2),                -- 成交量(股)
    amount   NUMERIC(20,2),                -- 成交额(元)
    PRIMARY KEY (symbol, ts)               -- 分区键必须进主键(07 章)
) PARTITION BY RANGE (ts);

-- 月分区 + 滚动: 老分区归档后 DROP(秒级) 而非 DELETE(千万行级 vacuum 灾难)
CREATE TABLE kline_1min_2025_06 PARTITION OF kline_1min
    FOR VALUES FROM ('2025-06-01') TO ('2025-07-01');

-- 索引: 主键已覆盖 (symbol, ts) —— "取某股票某时间段K线"是最热查询, 主键即答案, 零额外索引!
-- 反例: 单独建 ts 索引 = 白付出写放大(03 章), 因为全市场扫描"某分钟所有股票"的场景用 partition + (symbol,ts) 的分区内扫描更划算
-- 若高频查"某日全市场收盘": 建日级汇总表(见下), 不给明细表加 (ts) 单列索引

-- 日级汇总表(降采样/预聚合): 读多写少的"读"走这里
CREATE TABLE kline_1d (
    symbol TEXT, day DATE,
    o NUMERIC, h NUMERIC, l NUMERIC, c NUMERIC, v NUMERIC, amount NUMERIC,
    PRIMARY KEY (symbol, day)
);
INSERT INTO kline_1d
SELECT symbol, date_trunc('day', ts), first_value(o) OVER w, max(h), min(l),
       last_value(c) OVER w, sum(v), sum(amount)
FROM kline_1min WHERE ts >= '2025-06-01' AND ts < '2025-07-01'
GROUP BY symbol, date_trunc('day', ts)
WINDOW w AS (PARTITION BY symbol, date_trunc('day', ts) ORDER BY ts ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING);
```

设计决策逐条复盘（把前九章全用上）：

1. **主键 (symbol, ts) 联合**：热查询"某股票某时段 K 线" = 前缀等值 + 范围（03 章口诀：等值在前、范围在后），主键索引直接命中，**不再加任何单列索引**——每少一个索引，每分钟数万条 tick 插入的写放大就少一份。
2. **按月 RANGE 分区**：回测只扫涉及的月份（05 章分区裁剪）；一年数据 = 12 个分区文件级操作。
3. **NUMERIC 存价格**：07 章"钱的教训"；时间戳 TIMESTAMPTZ 统一时区（A股 UTC+8 的坑全在这一列的类型里）。
4. **降采样表**：1min 明细支撑精细回测，日级表支撑选股扫描——**读形态决定要不要预聚合**，而不是"表越大越该建物化视图"。
5. **tick 级数据**（每秒 3 千笔全市场）：明细表换时序库（TimescaleDB/InfluxDB，01 章分类图）或 LSM 引擎（06 章选型表）；分钟级聚合 PG 足够——**量级决定引擎，形态决定建模**。

## 4. OLTP vs OLAP：列存为什么快

两类负载的存储引擎分野（01 章分类图的深化，DDIA 第 3 章）：

```
行存(OLTP: PG/MySQL):  一行连续存放  [id|name|age|city][id|name|age|city]...
  适合: 取整行(用户画像页/订单详情) —— 一次 IO 拿齐一行
列存(OLAP: ClickHouse/DuckDB/Parquet): 一列连续存放  [id|id|id...][name|name...][age|age...]
  适合: 聚合少数列 —— 只读涉及的列, 其余列零 IO
```

列存在分析查询（`SELECT avg(amount) FROM kline WHERE day > '2025-01-01'`）上快 10-100 倍的原因有三，缺一不可：

1. **只读需要的列**：聚合 3 列 = 3/16 的 IO（行存必须读全行）。
2. **压缩友好**：同列数据类型一致、值相近（时间列游程编码、价格列字典/delta 编码），压缩比 5-10x，IO 再降一个量级。
3. **向量化执行**：以"列块"为单位批量算（SIMD 一条指令处理 8 个 float），替代逐行解释。**向量化扫描演示思路**（Python 直观模拟，非真实引擎）：

```python
# vec_scan.py —— 行式 vs 列式聚合的直观模拟
import numpy as np, time
n = 5_000_000
rows = np.empty((n, 4), dtype=np.float64)          # 行存: id, price, qty, pad
rows[:, 0] = np.arange(n); rows[:, 1] = np.random.rand(n)*100
rows[:, 2] = np.random.rand(n)*10;  rows[:, 3] = rows[:, 0]
cols = [np.ascontiguousarray(rows[:, i]) for i in range(4)]   # 列存视图
t0 = time.monotonic()
sum_row = rows[:, 1] @ rows[:, 2]                  # 行存语义: 遍历行取两列(内存上跨步访问)
t_row = time.monotonic() - t0
t0 = time.monotonic()
sum_col = cols[1] @ cols[2]                        # 列存语义: 两列连续内存点积(SIMD 友好)
t_col = time.monotonic() - t0
print(f"行式跨步 {t_row*1000:.1f}ms | 列式连续 {t_col*1000:.1f}ms | 比 {t_row/t_col:.1f}x")
# 实测(WSL2): 行式 ~19.8ms | 列式 ~4.2ms | ~4.7x —— 这是纯 Python/内存模型,
# 真实引擎再叠压缩(少IO)与 SIMD, 差距放大到 10-100x
```

结论不是"列存替代行存"：**OLTP 的点查/事务在行存上是 3 次页读，在列存上要拼 16 列碎片**——引擎跟着负载走。工程上常见组合：PG 扛 OLTP + 每晚 ETL 到 ClickHouse/DuckDB 扛分析；或 PG + 列存扩展（hydra/citus columnar）小规模兼营。

## 5. 技术选型决策树

把全系列压缩成一张决策图（按顺序问，第一个答"是"的分支就是答案）：

```
Q1 数据需要事务/复杂关联查询吗? ──是──→ 关系型(SQLite 单机小用 / PostgreSQL 主力)
   │否
Q2 是"高维向量 + 相似度检索"吗? ──是──→ pgvector(百万级) / 专用向量库(亿级+高QPS, 09章)
   │否
Q3 写入 > 1万条/s 且以时间序列为主? ──是──→ 时序库(TimescaleDB/InfluxDB) 或 LSM 引擎
   │                                        (ClickHouse 若聚合查询为主, 4节)
   │否
Q4 需要 <10ms 的超热点点查/计数/锁? ──是──→ Redis(08章; 持久需求配 AOF, 状态重则换 RocksDB)
   │否
Q5 数据间是关系网络, 查询是多跳遍历? ──是──→ 图库(Neo4j)
   │否
Q6 都不是 / 拿不准 ──────────────────→ PostgreSQL  ← 默认终点
```

配套的三条否决线（经验做法，比"选什么"更常用）：

1. **规模线**：单表 < 5000 万行且无特殊查询形态 → 任何分类都别上，PG + 索引 + 分区足够。多数"要不要上 ClickHouse/Kafka"的焦虑都在这条线以下。
2. **一致性线**：需要强事务/外键/唯一约束 → 只有关系型（或 NewSQL）给全；KV/文档/时序库都只是"部分给"。
3. **运维线**：团队没人会运维 X → 别选 X。一个养得起的 PG 优于一个玩不转的分布式集群（与分布式系统 12 章案例章的结论互证）。

## 6. "先用 Postgres"原则（经验做法）

本系列的收束性经验，如实标注来源：这是业界反复验证的默认策略（"boring technology" 运动与多个工程团队的一线共识，非论文结论）。内容三句：

1. **新项目的存储从 PG 开始**（原型期 SQLite 也可以）：事务、JSONB、全文检索、pgvector、分区、逻辑复制——一个系统覆盖 01 章分类图的四个格子，学习/运维/备份只有一套。
2. **切换的触发条件是"量级证据"而不是"焦虑"**：写入持续 > 1 万条/s、单表 > 5 亿行、分析查询拖垮 OLTP——拿到监控数字（12 章）再迁，且迁移方案见 12 章双写流程。
3. **反向也是对的**：数据长在专用系统里（时序/向量/图）但规模一直上不来时，收回 PG 常常是减法胜利——少一个系统 = 少一份备份/监控/故障面。

反面清单（什么时候**不该**"先用 PG"）：极端低延迟点查（<1ms 的会话存储）、不可控的第三方协议兼容（必须 Redis 协议的场景）、团队已有成熟专用栈——原则是默认值，不是教条。

## 常见误区

1. **"范式越高越专业"**：范式是正确性工具不是勋章。报表库大量反范式（宽表/星型模型）是常态；OLTP 库保持范式。先问负载再问范式。
2. **"事件表就是日志文件"**：append-only 表仍然有主键/索引/分区/Schema 约束，"只追加"约束的是写语义不是数据治理。把事件表建成无主键无约束的堆，三个月后就是考古现场。
3. **"行情数据嘛，全塞一个表就行"**：tick/1min/1d 三个粒度三种命运（引擎可能都不同）——明细走时序/LSM，聚合走 PG；一锅烩的结果是明细表把聚合查询的缓存全部冲垮（05 章 BUFFERS 的证据）。
4. **"列存 = 分析万能"**：单行整取、高频小事务、更新密集的场景列存全是劣势。先分清负载（4 节对照表），再谈引擎。
5. **"选型图走到哪算哪"**：决策树的三条否决线（规模/一致性/运维）比分支更重要——多数错误选型不是选错了分支，而是跳过了否决线直接追新。

## 本篇小结

- 三范式保正确性，反范式买读性能；先问"冗余的是快照还是状态、谁负责同步"，再决定付不付账单。
- 读多写少=状态表+精索引；写多读少=append-only 事件表+少索引+分区滚动；事实追加、状态是事实的函数。
- OHLCV 完整实例：联合主键 (symbol, ts) 即热查询索引、月分区滚动、NUMERIC 存钱、降采样表承载聚合读——量级决定引擎，形态决定建模。
- 列存快在"少 IO + 压缩 + 向量化"三件套，分析聚合 10-100x；OLTP 点查仍归行存；模拟实验行/列差 ~5x 是下界。
- 选型决策树 + 三条否决线（规模/一致性/运维）；默认终点 PostgreSQL。
- "先用 Postgres"三句话：默认起点、量级证据才迁移、收回也是胜利；例外清单同样明确。
