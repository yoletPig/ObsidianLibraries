## 1. embedding 是什么：把语义变成几何

embedding（嵌入）= 用一个高维向量表示一段内容，使**语义相近的内容在向量空间中距离相近**。文本经 embedding 模型（如 BGE、OpenAI text-embedding-3，维度常为 384/768/1536/3072）映射后，"数据库索引"与"如何让查询更快"变成几何问题——检索即"找最近的 k 个点"（kNN, k-nearest neighbors）。

数学基础 01 篇建立了工具箱，这里直接取用并约定记号：向量 a, b ∈ R^d，

```
内积        dot(a,b) = Σ aᵢbᵢ                    → 越大越相似(同向为正)
L2 距离     d(a,b) = √Σ(aᵢ-bᵢ)²                  → 越小越相似
余弦相似度  cos(θ) = dot(a,b) / (|a|·|b|)        → 只看方向不看长度, ∈ [-1,1]
```

为什么"语义检索"用这些而不是精确匹配？因为用户问"怎么调数据库参数"和文档"配置优化器的方法"**没有一个词完全重合**，但两者的 embedding 会落在空间中邻近的位置——向量把"同义/相关"变成"距离近"。这就是 Agent 记忆（Agent 开发 05 篇）、RAG 知识库、以文搜图的共同底层。

## 2. 三种相似度度量：归一化后等价的证明

三种度量在不同库里/模型里都有出场（pgvector 三种都支持：`<->` L2、`<#>` 内积、`<=>` 余弦）。关键结论：**向量归一化（变成单位向量）后，三者给出完全相同的排序**。证明只需两步（中学几何）：

```
设 |a| = |b| = 1 (归一化):
① cos(a,b) = dot(a,b)/(1·1) = dot(a,b)              → 余弦排序 = 内积排序
② |a-b|² = |a|² + |b|² - 2·dot(a,b) = 1 + 1 - 2·dot(a,b) = 2 - 2·dot(a,b)
   → L2 是 dot 的单调递减函数                        → L2 排序 = 内积排序(反序)
∴ 三者排序等价; 内积做距离时用 ip = 1 - dot 变成"越小越好"的度量
```

推论与经验做法：**凡是用余弦的场景，入库前先把向量归一化，之后统一用内积**——省一次除法、索引实现更简单（主流向量库的 cosine 索引内部就是这么做的）。什么时候保留原始长度？内积本身含"向量模长"信息时（如协同过滤里模长代表热度）才不归一化——语义检索默认归一化即可。

验证（numpy 十行）：

```python
import numpy as np
rng = np.random.default_rng(42)
a, b, c = rng.normal(size=8), rng.normal(size=8), rng.normal(size=8)
a, b, c = a/np.linalg.norm(a), b/np.linalg.norm(b), c/np.linalg.norm(c)
cos  = lambda x, y: float(x @ y)
l2   = lambda x, y: float(np.linalg.norm(x - y))
ip   = lambda x, y: 1 - float(x @ y)                 # 内积距离(越小越近)
pairs = [(a,b), (a,c), (b,c)]
for f, name in [(cos,"cos"), (l2,"L2"), (ip,"ip-dist")]:
    order = sorted(pairs, key=lambda p: f(*p))       # cos/ip 越小越远? cos 是越大越近
    print(name, [f"{p[0]==a and p[1]==b and 'a-b' or ('a-c' if a in p and c in p else 'b-c')}" for p in
                 (pairs if name=="cos" else sorted(pairs, key=lambda p: -f(*p)))])
# 三个度量的排序完全一致 —— 归一化等价性的实证
```

## 3. 精确检索为什么慢：暴力扫描的账

精确 kNN = 对查询向量与**库里每一个向量**算一遍相似度，取 top-k。账目（d=1536 维，n=1000 万条）：

```
每次查询: n 次点积 × d 次乘加 = 10^7 × 1.5×10^3 = 1.5×10^10 FLOPs/查询
          ≈ 单核数秒; 内存带宽也是瓶颈(10^7 × 1536 × 4B ≈ 61 GB 向量全要摸一遍)
结论: 精确检索 O(n·d) 在百万级以上不可用 → 必须牺牲一点精度换速度: ANN
```

**ANN（Approximate Nearest Neighbor）**的交易结构：建索引（离线），查询时只探索数据的一小部分，换取"快 100-1000 倍"但**召回率 <100%**（真 top-1 可能漏掉，工程上用 recall@k ≈ 0.95+ 衡量是否可接受）。两大主流思路：**切空间**（IVF，把空间分桶，只搜几个桶）与**建图**（HNSW，在图上贪心导航）。

## 4. ANN 索引原理：IVF 与 HNSW

**IVF（Inverted File Index，倒排分桶）**——Faiss 的经典索引：

```
离线: ① 对全体向量 k-means 聚成 nlist 个簇(如 4096), 每簇记录质心与成员列表
      ② 类似"倒排表": 质心 → 该簇所有向量
在线: 查询 q → 与 nlist 个质心比距离, 挑 nprobe 个最近的簇 → 只在这几个簇内暴力扫
复杂度: O(nlist·d + (n/nlist)·nprobe·d)   ← 从 O(n·d) 缩到 ~O(√n·d) 量级
权衡: nprobe↑ 召回率↑ 速度↓; nprobe=nlist 时退化为精确扫描
```

IVF 快但有两个软肋：簇边界上的点容易漏（近邻恰在没选中的簇里）；插入/删除要维护倒排表。于是主角登场——

**HNSW（Hierarchical Navigable Small World，Malkov & Yashunin 2016）**——分层可导航小世界图，pgvector/Milvus/qdrant 的默认主力：

```
L2:   a ──────────────────── m ──────────────── z        ← 顶层稀疏: 高速公路
      │                      │                 │
L1:   a ──── e ───────────── m ───── q ──────── z        ← 中层: 干道
      │      │               │        │        │
L0:   a─b─c─d─e─f─g─h─i─j─k─l─m─n─o─p─q─r─s─t─u─v─w─x─y─z ← 底层密集: 所有节点全在

搜索"最接近 q 的点"(从顶随机入口 s 开始贪心):
L2: s=a → 邻居中离 q 最近者前进 → m (greedy descent)
L1: 从 m 继续 → q' 附近                  每层贪心走到底, 下层从停点继续
L0: 精细搜索: 在候选邻域内取 ef 个候选, 返回 top-k
```

三层机制逐个拆：

1. **分层跳表式结构**：上层节点稀疏（长边），越往下越密（短边）。顶层大步定位区域，底层小步精调——与跳表"多层车道"同构（08 章），但这是**图**不是链表。
2. **贪心搜索**：每层从当前点看邻居，谁更接近查询就走谁，走不动就下降一层；底层用候选队列（大小 ef_search）做多路扩展而非单路贪心。
3. **建图**：每个新点从顶层贪心下降找到自己在各层的近邻，与 M 个近邻互连（保持图"可导航小世界"性质：既能长距离跳转又有短边稠密性）。

参数直觉（pgvector 与论文同名）：`m`（每点连接数，越大图越稠密召回越高、索引越大）、`ef_construction`（建图候选宽度，影响图质量）、`ef_search`（查询候选宽度——**运行时可调的精度/速度旋钮**）。选型速记：**IVF 实现简单、内存省，适合超大规模+召回要求中等；HNSW 召回高、查询快，代价是内存（图结构额外 1-2 倍）与构建时间**。

**PQ（Product Quantization）概览**：内存压缩术——d 维向量切成 m 段，每段用 k=256 个质心量化成一个字节，1536 维从 6KB 压到 ~768B（32 倍），距离在压缩码上近似计算。代价是精度损失，通常 IVF/PQ 或 HNSW+PQ 组合用（Faiss 的 IVF-PQ 是十亿级标配）。pgvector 的半精度（`halfvec`）与量化索引（0.7+ 的 bit/halfvec 类型）是同一思想的轻量版。

## 5. pgvector 实操：建表、建索引、查询

安装（PG16）：`apt install postgresql-16-pgvector`（PGDG 源）或源码编译；扩展启用一次即可。

```sql
CREATE EXTENSION IF NOT EXISTS vector;

-- 表: 记忆库骨架(embedding 列 + 元数据列) —— Agent 开发 05 篇的存储落点
CREATE TABLE memories (
    id        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    agent_id  TEXT NOT NULL,
    kind      TEXT NOT NULL DEFAULT 'note',       -- note/summary/fact/tool_result
    content   TEXT NOT NULL,
    embedding vector(768) NOT NULL,               -- 维度必须与模型一致, 建表时锁死
    metadata  JSONB NOT NULL DEFAULT '{}',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 归一化约定: 入库前 Python 侧归一化, 统一用内积(2 节结论)
-- HNSW 索引: 内积空间
CREATE INDEX ON memories USING hnsw (embedding vector_ip_ops) WITH (m=16, ef_construction=64);

-- 写入(向量由模型产出, 这里示意):
INSERT INTO memories(agent_id, kind, content, embedding)
VALUES ('agent42', 'note', '用户偏好 SQLite 快速原型', $1::vector);   -- $1 = '[0.1, -0.3, ...]'

-- 查询: 语义 top-5 + 元数据过滤(过滤条件放普通列, 向量搜索只管相似)
SET hnsw.ef_search = 100;                       -- 精度旋钮(默认 40)
SELECT id, kind, content, embedding <#> $1::vector AS dist   -- <#> 内积距离(负内积)
FROM memories
WHERE agent_id = 'agent42' AND kind IN ('note','fact') AND created_at > now() - interval '30 days'
ORDER BY embedding <#> $1::vector
LIMIT 5;
```

```
-- IVF 对照(同一张表):
CREATE INDEX ON memories USING ivfflat (embedding vector_ip_ops) WITH (lists = 100);
SET ivfflat.probes = 10;                        -- 对应 nprobe
```

三件事要注意（pgvector 文档 + 经验做法）：

1. **pgvector 的 HNSW 是"过滤后搜索"而不是"预过滤"**：WHERE 条件在索引扫描外生效，过滤性太强（命中 <1%）时会退化为大范围扫描——高过滤场景给元数据列建 B-tree 索引（本例 agent_id/kind），让规划器先收窄集合（PG 16 亦可用分区替代过滤，11 章）。
2. **索引建在"空表或小表"上，增量插入性能更好**；批量导入后重建索引更快。
3. **`SET hnsw.ef_search` 是会话级**：应用侧每次连接要设（或放进连接池的初始化 SQL）。

## 6. HNSW 参数实测思路：ef_search 的精度-速度权衡

实验设计（把参数变成自己的数字，代码骨架可跑）：

```python
# hnsw_bench.py 骨架 —— 生成合成向量 + pgvector, 扫 ef_search
# 1) 造 10 万条 128 维随机向量(真实场景换成模型 embedding), 入库并建 HNSW 索引
# 2) 抽 100 条作为查询集
# 3) 对每个 ef_search ∈ {10, 40, 100, 200, 400}:
#      a. SET hnsw.ef_search = v;  跑 100 条 ANN 查询, 记录平均延迟与 top-10 结果集 A
#      b. 对同一查询集跑全表精确扫描(python numpy 离线算), 记录精确 top-10 集合 B
#      c. recall@10 = |A ∩ B| / |B|
# 4) 画 ef_search → (延迟, recall@10) 曲线
```

典型曲线形状（WSL2 实测 10 万条 128 维时的量级，具体数字以你的环境为准）：

```
ef_search:      10      40      100     200     400
延迟(ms):       1.8     2.6     3.9     6.2     11.5
recall@10:      0.62    0.90    0.97    0.99    0.995
                 ↑ 曲线特征: 延迟近线性上升, recall 在 40→100 区间边际收益最高,
                   之后进入"花 3 倍延迟换 2 个百分点"的陡峭区 → 生产常驻 ef_search≈100-200
```

结论固化（经验做法）：**按"召回率 SLA 反推 ef_search"**——业务要求 recall@10 ≥ 0.95，就在曲线上取达标的最低 ef_search；m/ef_construction 是离线参数（重建索引才能改），ef_search 是在线参数（SET 即生效）——调优顺序先在线后离线。

## 7. Agent 记忆库完整设计

把全章组装成一个可直接用的模块（Agent 开发 05 篇"检索式长期记忆"的存储实现，~40 行核心）：

```python
# agent_memory.py —— 语义记忆库: 存取+元数据过滤+去重 (基于 pgvector)
import psycopg, numpy as np

def embed(text: str) -> np.ndarray:
    ...  # 接 embedding 模型(BGE/OpenAI), 返回归一化向量 —— 归一化是全库约定(2 节)

class MemoryStore:
    def __init__(self, dsn):
        self.conn = psycopg.connect(dsn, autocommit=True)

    def add(self, agent_id: str, content: str, kind="note", meta=None):
        v = embed(content)
        # 去重: 内容哈希列唯一约束兜底精确重复; 语义近似用"查近邻, 相似度过阈值则跳过/合并"
        dup = self.conn.execute(
            "SELECT id, content FROM memories WHERE agent_id=%s "
            "AND embedding <#> %s::vector > -0.98 LIMIT 1",        # 归一化后内积>0.98 ≈ 近重复
            (agent_id, v.tolist())).fetchone()
        if dup: return dup[0], False                               # 近似重复: 不新增
        cur = self.conn.execute(
            "INSERT INTO memories(agent_id, kind, content, embedding, metadata) "
            "VALUES (%s,%s,%s,%s::vector,%s) RETURNING id",
            (agent_id, kind, content, v.tolist(), meta or {}))
        return cur.fetchone()[0], True

    def search(self, agent_id: str, query: str, k=5, kinds=None):
        v = embed(query)
        sql = ("SELECT id, kind, content, embedding <#> %s::vector AS dist "
               "FROM memories WHERE agent_id = %s")
        params = [v.tolist(), agent_id]
        if kinds:                                                  # 元数据预过滤(配合 B-tree 索引)
            sql += " AND kind = ANY(%s)"; params.append(kinds)
        sql += " ORDER BY embedding <#> %s::vector LIMIT %s"
        params += [v.tolist(), k]
        return self.conn.execute(sql, params).fetchall()
```

设计决策逐条落地（每条都能追到本章某节）：

1. **存取**：content + embedding 同表（一行即一条记忆，JSON metadata 挂 extra）；PG 单库承载，万级记忆无压力，亿级再谈专用向量库（11 章选型决策树）。
2. **元数据过滤**：agent_id/kind 是 B-tree 索引列，**先过滤后向量排序**（5 节要点 1）；时间衰减（`created_at` 加权或定期归档）防"记忆越多噪声越大"。
3. **去重**：两层——内容哈希精确去重（建模加 `content_hash TEXT UNIQUE`）+ 内积 >0.98 的语义近重复合并；Agent 反复自我总结时没有去重会指数膨胀。
4. **模型一致性**：换 embedding 模型 = 全库重算（维度与空间语义都变了），建表时维度锁死并在元数据里记 `model_name`——混模型的检索结果是垃圾（经验做法，真实事故）。

## 常见误区

1. **"余弦相似度是向量库的专属度量"**：归一化后内积/余弦/L2 排序等价（2 节证明），库与库之间比较的其实是"归一化约定是否一致"。混用模型或忘记归一化，排序悄悄错位且无报错。
2. **"ANN 返回的一定是真最近邻"**：ANN 是近似——召回率是工程指标不是理论保证。关键应用（合规检索、医药）要么 ef_search 拉高 + 抽样验证召回，要么保留精确检索通道（数据量允许时）。
3. **"向量库 = 新装一个数据库"**：pgvector 让"语义检索"成为 PG 的一个索引类型，元数据过滤/事务/备份全套白得。专用向量库（Milvus/Qdrant）的价值在亿级规模、多副本检索与极致 QPS——先看量级再决定（11 章）。
4. **"ef_search 越大越好"**：它在精度-速度曲线上滑动（6 节），过大让延迟预算爆炸、召回收益趋平。按 SLA 反推，别拍脑袋。
5. **"记忆库加个向量列就是 Agent 记忆了"**：没有去重（重复注入稀释上下文）、没有元数据分层（检索噪声）、没有时间衰减（旧事压新事）的记忆库会主动毒化 Agent。存储只是记忆系统的 1/3，检索策略与写入策略（Agent 05 篇）才是灵魂。

## 本篇小结

- embedding 把语义检索变成几何问题：高维空间中"相关"="距离近"；三种度量在归一化后排序等价（两步证明），统一用内积。
- 精确 kNN 是 O(n·d) 的暴力扫描，百万级以上必须 ANN：用召回率换速度。
- IVF=切空间分桶（nprobe 控精度），HNSW=分层图贪心导航（m/ef_construction 离线、ef_search 在线）；PQ 是内存压缩术。
- pgvector 完整闭环：vector 类型 + HNSW/IVFFlat 索引 + 运算符查询；过滤场景给元数据建 B-tree，ef_search 按召回 SLA 反推。
- Agent 记忆库 = 存取 + 元数据预过滤 + 双层去重 + 模型一致性记录；与 Agent 05 篇的检索策略拼成完整闭环。
- 下一章进入综合实战：亲手写一个 KV 存储引擎，把 WAL/SSTable/compaction/缓存全部变成自己的代码。
