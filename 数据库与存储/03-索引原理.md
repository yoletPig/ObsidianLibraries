# 03 - 索引原理

## 本篇目标

- 用复杂度对比说清"为什么要索引"：全表扫描 O(n) vs 索引查找 O(log n)。
- 画出 B+树结构并**亲手推导阶数**，理解"为什么 3 层能存千万行"。
- 区分聚簇索引与二级索引（InnoDB 主键即数据），说清回表与覆盖索引。

## 1. 为什么要索引：一次对比实验

100 万行的表按 id 找一行，没有索引只能**全表扫描**——逐行看一遍，O(n)；有索引（B+树）从根走到底，O(log n)。数字差距大到没有讨论余地：n=10^7 时 log₂n≈23，即 **~43 万倍的比较次数差距**；落到 IO 上，全表扫描读所有数据页，索引查找只读 3-4 个页。

```python
# index_vs_scan.py —— 实测: 100万行, 索引查找 vs 全表扫描
import sqlite3, time
conn = sqlite3.connect("/tmp/idx_demo.db")
conn.execute("CREATE TABLE IF NOT EXISTS t(id INTEGER PRIMARY KEY, v INT, s TEXT)")
if conn.execute("SELECT count(*) FROM t").fetchone()[0] == 0:
    conn.executemany("INSERT INTO t(v, s) VALUES(?, ?)",
                     [(i, f"value-{i}") for i in range(1_000_000)])
    conn.commit()

t0 = time.monotonic()
row = conn.execute("SELECT s FROM t WHERE id = 999999").fetchone()      # 走主键索引(rowid)
print(f"索引查找 id=999999: {(time.monotonic()-t0)*1000:.3f} ms, {row}")

t0 = time.monotonic()
row = conn.execute("SELECT s FROM t WHERE v = 999999").fetchone()       # v 无索引 → 全表扫描
print(f"全表扫描 v=999999: {(time.monotonic()-t0)*1000:.3f} ms, {row}")
```

实测输出（WSL2/Ubuntu，数据已在操作系统页缓存中）：

```
索引查找 id=999999: 0.048 ms, ('value-999999',)
全表扫描 v=999999: 218.352 ms, ('value-999999',)
```

**~4500 倍**。数据全在内存里尚且如此，数据在盘上时差距更大（扫描要读 ~2 万个页，索引查找读 3-4 个页，每页一次随机 IO——回忆 01 章的存储层次）。本篇所有"快"都来自一个抽象：**索引 = 把"找数据"变成"在有序结构上找位置"**。

## 2. B+树结构详解

数据库索引的标准答案是 **B+树**。B 树由 Bayer & McCreight 1970 年提出（*Organization and Maintenance of Large Ordered Indices*），B+树是它的工程变体：**数据只存叶子节点，内部节点只存路由键，叶子之间用链表串起来**（B+树的精确起源有考证争议，通说为 1970 年代初 IBM 的实现，见 Knuth TAOCP 6.2.4 的批注）：

```
                         内部节点(页): [17 | 35]              ← 只存键+子页指针
                        /            \
              [3|10|17]                [35|42|58]           ← 再一层路由
              /   |   \                /   |   \
叶子: [1|3|5|10|12|17]→[18|21|35|39]→[35|42|50|58|61]→[70|...]   ← 全部数据+有序链表
        叶子之间双向链表 → 支持范围扫描 WHERE id BETWEEN 10 AND 40
```

为什么是 B+树而不是二叉树/红黑树/哈希表？逐个排除（DDIA 第 3 章）：

- **二叉树太瘦高**：100 万节点高约 20 层，每层一次页读取（磁盘随机 IO）= 20 次 IO；B+树把分叉做大（几百个分支），**矮胖**——100 万行 3 层，10 亿行 4 层。
- **哈希表不支持范围查询**：`WHERE id BETWEEN 10 AND 40`、`ORDER BY`、前缀匹配，哈希全废；B+树叶子上数据有序，范围扫描 = 定位起点 + 顺链表走。
- **跳表也可以**（Redis zset 用它，08 章），但跳表每层指针是随机内存访问，B+树以"页"为单位对齐磁盘 IO——数据库要的是"最少页读取"。

**阶数推导：为什么 3 层能存千万行。** 设页大小 P=4096B（SQLite 默认），内部节点存"键 + 子页号"。以 8B 整数键 + 4B 页号 ≈ 12B/条计，一个页容纳约 `4096/12 ≈ 341` 个分支（扣除页头/预留空间后常按 ~300-400 估）。叶子节点存"键 + 行数据"，假设整行 ~50B，每叶 ~80 行。则：

```
高度 2:  341 内部分支 × 80 行/叶        ≈   2.7 万行
高度 3:  341 × 341 × 80                ≈  930 万行     ← 3 层 ≈ 千万行
高度 4:  341 × 341 × 341 × 80          ≈ 31.7 亿行
```

这就是"千万行 3 层"的出处：**分支数 ~341，任何一层都是页级随机 IO，3 层 = 3 次 IO 摸到任何一行**；根节点常驻缓冲池，实际磁盘 IO 往往只剩 1-2 次。行更大（如 500B）时每叶行数降到 ~8，3 层也还有 ~90 万行，4 层 3 亿——所以 B+树高度几乎永远是 3-4 层，这是它对所有规模数据承诺的常数。

维护：插入找叶子，满则**分裂**（中点上提进父节点，父满继续向上分裂，根分裂则长高一层）；删除不足半满则**合并/重分布**。分裂导致键在物理页间搬家——07 章讲 UUID 主键时会回到这个细节（随机插入造成频繁分裂，这是自增 ID 的核心优势）。

## 3. 聚簇索引 vs 二级索引：主键即数据

B+树索引分两种用法（MySQL InnoDB 的术语，PostgreSQL 的堆表只有第二种，见本节末）：

- **聚簇索引（clustered index）**：叶子节点**就是数据行本身**，表即索引。InnoDB 强制如此——`PRIMARY KEY` 的 B+树就是整张表。
- **二级索引（secondary index）**：叶子存"索引键 + 主键值"。查二级索引拿到主键后，还要回聚簇索引查整行——这一步叫**回表（bookmark lookup / 回表）**。

```
聚簇索引(主键 id)                二级索引(列 v)
根 [50|100]                     根 [100|200]
叶: id=1→(整行)                 叶: v=5→id=3, v=9→id=1 ...
      ↓ 命中即返回                     ↓ 还差一步
                                回表: 拿 id=3 再走一遍聚簇索引
```

两个直接推论：

1. **主键查询走聚簇索引：1 棵树搞定，无回表**；二级索引查询：2 棵树，除非覆盖（下节）。
2. **二级索引的叶子存主键，所以主键越胖每页装得越少、树越高**——UUID(16B) 做主键比 BIGINT(8B) 的每棵二级索引都更占空间、更深，加上随机插入的分裂问题（07 章），就是"自增 ID 优先"的完整论证。

PostgreSQL 不搞聚簇：所有表是**堆表（heap）**，索引叶子存"键 + ctid（物理行位置）"。代价是同样要回表（回堆）；好处是更新主键外的列不搬家、二级索引与行的关系更松。`CLUSTER` 命令可一次性按索引重排物理顺序，但不会自动维持。两种路线没有绝对优劣，面试常考，答"MySQL 聚簇 = 表即主键索引，PG 堆表 = 表与索引分离"即可。

SQLite 与 InnoDB 同路：`INTEGER PRIMARY KEY` 就是 rowid 的别名，表数据按 rowid 聚簇存储（第 06 章 hexdump 可亲眼看）。**例外**：SQLite 的 `WITHOUT ROWID` 表按主键聚簇，此时非整数主键也可聚簇。

## 4. 最左前缀原则：联合索引 EXPLAIN 实验

联合索引 `(a, b)` 的排序规则：先按 a 排，a 相同再按 b 排——**本质上是一本"先姓氏后名字"的电话簿**。能查"姓王"（a=?），能查"姓王名强"（a=? AND b=?），不能直接查"名强"（b=?，得翻遍全本）。这就是**最左前缀原则**。用实验钉死（SQLite 的 `EXPLAIN QUERY PLAN`，MySQL 用 `EXPLAIN`，PostgreSQL 用 `EXPLAIN`，输出措辞不同、结论一致）：

```python
# leftmost.py —— 联合索引 (user_id, status) 的最左前缀实验
import sqlite3
conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders(id INTEGER PRIMARY KEY, user_id INT, amt REAL, status TEXT)")
conn.executemany("INSERT INTO orders(user_id, amt, status) VALUES(?,?,?)",
                 [(i % 1000, i * 1.0, "ok" if i % 3 else "paid") for i in range(100_000)])
conn.execute("CREATE INDEX ix_us ON orders(user_id, status)")

plan = lambda q: conn.execute("EXPLAIN QUERY PLAN " + q).fetchone()[3]
cases = [
    "SELECT * FROM orders WHERE user_id=42",                            # 最左列: 走索引
    "SELECT * FROM orders WHERE user_id=42 AND status='ok'",            # 全匹配: 走索引
    "SELECT * FROM orders WHERE status='ok'",                           # 缺最左列: 全表扫描!
    "SELECT * FROM orders WHERE status='ok' AND user_id=42",            # 顺序无关, 优化器重排
    "SELECT amt FROM orders WHERE user_id=42",                          # 只查 amt: 覆盖索引
]
for q in cases:
    print(f"{plan(q):<50} <- {q[:52]}")
```

实测输出：

```
SEARCH orders USING INDEX ix_us (user_id=?)                        <- SELECT * FROM orders WHERE user_id=42
SEARCH orders USING INDEX ix_us (user_id=? AND status=?)           <- ... user_id=42 AND status='ok'
SCAN orders                                                        <- SELECT * FROM orders WHERE status='ok'
SEARCH orders USING INDEX ix_us (user_id=? AND status=?)           <- ... status='ok' AND user_id=42
SEARCH orders USING COVERING INDEX ix_us (user_id=?)               <- SELECT amt FROM orders WHERE user_id=42
```

四条结论：

1. `user_id=42`：SEARCH（索引范围查找）。
2. `user_id AND status`：两列都用上，定位更窄。
3. **只查 status：SCAN（全表扫描）**——跳过最左列，索引失效。这不是 bug，是排序结构决定的（电话簿按姓排，只报名字没人帮你找）。
4. WHERE 里两列顺序写反了照样走索引——优化器会重排，**最左前缀约束的是索引定义顺序，不是 SQL 书写顺序**。

补充两条边界（经验做法）：

- **范围查询截断后续列**：`WHERE user_id=42 AND amt>100` 走索引但只用到 user_id（amt 是范围条件，其后的 status 若在索引中则用不上）。设计口诀：**等值列在前，范围列收尾**——`(user_id, status, amt)` 中 amt 放最后。
- **LIKE 的前缀例外**：`LIKE 'ABC%'` 等价于范围查询（>= 'ABC' AND < 'ABD'）可走索引；`LIKE '%ABC'` 从中间匹配，失效。

## 5. 覆盖索引：不回表的艺术

上面第 5 个用例的输出里藏着 `COVERING INDEX`：查询要的列（amt）恰好全在索引里（索引含 user_id 键），**跳过回表直接从索引出结果**。回表 = 再走一遍聚簇索引 = 再来几次 IO；数据量大时，覆盖索引是"二级索引查询"与"主键查询"拉平的杠杆：

```
无覆盖:  二级索引树(3次IO) → 回表聚簇树(1-3次IO)  =  4-6 次IO
有覆盖:  二级索引树(3次IO) → 叶子即答案            =  3 次IO, 且叶子页更密集缓存更友好
```

代价是索引更宽（把 amt 塞进索引）。取舍口诀（经验做法）：**高频查询 + 列很少 + 明显的回表热点，才值得做覆盖索引**；顺手把"多塞一列"当习惯则会让每条 INSERT 都付出代价（下一节实测）。MySQL 支持 `INCLUDE` 式的思路（其实用联合索引实现），PostgreSQL 11+ 有原生 `CREATE INDEX ... INCLUDE (col)`——把列附在叶子里但不参与排序键，专为此设计。SQLite 直接靠联合索引 + 查询列恰好被覆盖。

验证方法：`EXPLAIN QUERY PLAN` 出现 `USING COVERING INDEX`（SQLite）/ `Index Only Scan`（PostgreSQL）/ `Using index`（MySQL）即覆盖生效。

## 6. 索引什么时候反而慢：写放大实测

每个二级索引都是一棵**独立维护的 B+树**：INSERT/UPDATE 索引列时，数据树 + 每棵索引树都要更新（还可能页分裂）。索引把读的 O(n) 降成 O(log n)，同时把写的常数放大 1 倍多。实测（200 万行，含 1 个二级索引 vs 无索引，`executemany` 单事务批量插入）：

```python
# write_amp.py —— 建索引前后的插入速度对比(完整脚本见运行输出)
import sqlite3, time, os
def bench(path, with_index, n=200_000):
    if os.path.exists(path): os.remove(path)
    c = sqlite3.connect(path)
    c.execute("CREATE TABLE t(id INTEGER PRIMARY KEY, v INT, s TEXT)")
    if with_index: c.execute("CREATE INDEX ix_v ON t(v)")
    t0 = time.monotonic()
    c.executemany("INSERT INTO t(v,s) VALUES(?,?)", [(i % 100_000, f"row{i}") for i in range(n)])
    c.commit()
    dt = time.monotonic() - t0
    print(f"插入{n}行: {'带索引' if with_index else '无索引'} {dt:.2f}s "
          f"({n/dt/1e3:.0f} 千行/s), 文件 {os.path.getsize(path)/1e6:.1f} MB")
bench("/tmp/no_idx.db",  False)
bench("/tmp/with_idx.db", True)
```

实测输出（WSL2，SSD；无索引时也含主键聚簇树的维护）：

```
插入200000行: 无索引 0.14s (1428 千行/s), 文件 4.3 MB
插入200000行: 带索引 0.20s (1000 千行/s), 文件 6.9 MB
```

两个代价同时可见：**写慢 1.4 倍、文件大 60%**。注意这还是"单索引 + 小行 + 单事务"的温和场景；真实 OLTP 里每表三五个索引、行更宽，写入开销翻几倍很常见。单条自动提交的插入受每条 fsync 支配（分布式系统 07 章实验），索引差异会被落盘噪声掩盖——所以实验必须用同一事务批量插（经验做法：基准测试先固定事务边界，再谈别的变量）。

什么时候**不该**建索引（经验做法清单）：

1. **写多读少且查询模式覆盖不到的列**：日志表、行情 tick 表按 tick 序号建索引，几乎没人按序号查。
2. **低选择性列单列建索引**：性别/状态类列（基数 2-3），索引过滤不掉多少行，优化器宁愿全表扫描——不如做联合索引的尾列或前缀列。
3. **从不作为查询条件的列**：纯粹的存储负担。
4. **小表**：几百行的表全表扫描比树查找还快，优化器自己会放弃索引。

反过来，一个高频经验数字：**一个表 2-5 个精心设计的联合索引**通常是最优点；每加一个索引都问一句"哪个查询会用到它？写放大值吗？"

## 7. 哈希索引与位图索引：一句话带过

- **哈希索引**：键 → hash → 桶，点查 O(1)，但完全不支持范围/排序/前缀。主流 B+树数据库里只以"自适应"形式出现（InnoDB 自适应哈希索引自动给热点页加速）；PostgreSQL 支持哈希索引但少有人用（btree 几乎总能胜任）。记忆点：**点查专用、范围免谈**。
- **位图索引**：每个列值一个位向量，`性别=男` 的位图中第 i 位标记第 i 行。适合**基数极低 + 只读分析**（数据仓库），写入并发下锁整段位图，OLTP 别碰。PostgreSQL 里没有持久化位图索引，但执行计划里有位图扫描（Bitmap Index Scan，把 btree 结果先聚合成位图再回表，05 章会见到）。

本系列后续章节的索引主角仍是 B+树：05 章看优化器怎么"决定用不用它"，06 章 hexdump 亲手看 SQLite 的索引页，10 章手写引擎时再体会一次"为什么是 B+树"。

## 常见误区

1. **"建了索引查询就快"**：条件写法可以让索引失效——对列套函数（`WHERE upper(name)=...`）、隐式类型转换（字符串列 vs 数字字面量）、前导 `%` 的 LIKE、跳过最左列。05 章逐一复现。
2. **"索引越多越好"**：每多一棵树，写放大 +1，空间 +1 份，优化器选择面还变大（统计信息不准时可能选错）。索引是"读的预付款"，付的是写的账。
3. **"聚簇索引就是主键索引的名字"**：聚簇是"数据按索引物理组织"的属性。MySQL(InnoDB) 主键即数据；PG 没有聚簇（堆表 + 独立索引）；SQLite `INTEGER PRIMARY KEY` 即 rowid。同一个词在不同库里行为不同，答之前先问"哪个库"。
4. **"主键一定要用 UUID 才现代"**：UUID 随机 → 插入落点随机 → 页分裂频繁 + 缓存命中率低（07 章实测思路）。分布式 ID（雪花等，趋势递增）才是"全局唯一 + 顺序友好"的两全解。
5. **"EXPLAIN 的 rows 是准确值"**：它是**估计值**（基于统计信息），误差大时优化器会选错计划（05 章讲 ANALYZE 更新统计信息）。看计划要结合 `EXPLAIN ANALYZE` 的真实执行数据。

## 本篇小结

- 索引把查找从 O(n) 降到 O(log n)：百万行内存级实测差 ~4500 倍，盘上差距更大。
- B+树 = 矮胖多叉 + 叶子链表：以页为 IO 单位，341 分支 × 80 行/叶 → 3 层 ~930 万行，高度对规模近乎常数。
- 聚簇索引叶子即数据（InnoDB/SQLite rowid 表），二级索引叶子存主键、查询常需回表；PG 堆表索引叶子存 ctid。
- 最左前缀是联合索引的结构属性：等值列在前、范围列收尾、书写顺序无关；覆盖索引（COVERING/Index Only Scan）消灭回表。
- 索引不是免费的：实测写慢 1.4 倍、体积 +60%；按"读热查询反推索引"，2-5 个联合索引是常见最优区间。
- 哈希（点查 O(1) 无范围）与位图（低基数只读）是配角；主角永远是 B+树。
