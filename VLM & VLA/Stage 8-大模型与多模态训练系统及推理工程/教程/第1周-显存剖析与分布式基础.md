## 1. 第一性原理：显存账本的每一项

### 1.1 模型状态：权重、梯度、优化器的精确公式

以 $P$ = 参数量、16-bit（FP16/BF16）权重与梯度、AdamW 混合精度训练为口径：

| 项 | 公式 | 7B | 13B |
| --- | --- | --- | --- |
| 权重（bf16） | $2P$ 字节 | 14 GB | 26 GB |
| 梯度（bf16） | $2P$ 字节 | 14 GB | 26 GB |
| AdamW FP32 动量 $m, v$ | $8P$ 字节 | 56 GB | 104 GB |
| FP32 主权重（混合精度备份） | $4P$ 字节 | 28 GB | 52 GB |
| **合计（模型状态）** | **$16P$ 字节** | **112 GB** | **208 GB** |

**自测清单的 13B → 208GB 就是这样来的**：权重 26 + 梯度 26 + 优化器 156（FP32 备份 52 + 动量 104）= 208GB。三个常见的口径陷阱：

1. **"AdamW 8GB/1B"与"12GB/1B"的分歧**：只算 $m+v$（fp32）是 8 字节/参数；混合精度的完整实现还要维护 FP32 主权重（更新在 FP32 域进行再 cast 回 bf16），合计 12 字节/参数。**两种口径都对，但报告必须声明用了哪个**——学习计划第 1 周正文用 12GB/1B（含备份），自测题用 $2+2+12=16$ 字节/参数，本表统一后者。
2. **梯度精度**：某些实现梯度用 FP32（+4P 字节，合计 20 字节/参数）；DeepSpeed 口径与 PyTorch AMP 口径有差异——账本要跟实现走。
3. **ZeRO 后的账本**：第 2 周的切分会把这些项除以卡数并加通信成本——**先记住未切分的总账，切分收益才有量化基准**。

### 1.2 激活显存：随序列长度线性、随层数线性、随 batch 线性

激活的通用账（无 checkpointing，bf16）：

$$
M_{\text{act}} \approx L_{\text{layers}} \times B \times S \times d \times c_{\text{per-token}}
$$

其中 $c_{\text{per-token}}$（每层每 Token 的激活字节）与实现强相关（是否缓存注意力矩阵、MLP 中间维是否 bf16 等），量级 10~34 字节。7B（$L=32, d=4096$）、$B=1, S=8192$ 的估算：约 10~45GB——**与模型状态同量级，长上下文下甚至反超**。

两个结构性规律（比记数字更重要）：

- **注意力矩阵项随 $S^2$ 增长**（传统实现）：$S$ 从 4k 到 32k，注意力中间矩阵涨 64 倍——这是第 2 周 FlashAttention（降到 $O(S)$）与第 3 周 KV Cache 管理的动力来源之一；
- **gradient checkpointing 的交换比**：激活从 $O(L)$ 降为 $O(\sqrt{L})$ 量级，代价是额外一次前向（+30~40% 时间）。Stage 2 的"显存不够先开 checkpointing"在这里获得定量依据。

### 1.3 KV Cache：推理侧的"另一个账本"

推理无梯度/优化器，账本换成：权重（只读）+ KV Cache + 激活（峰值小）。

$$
M_{\text{KV}} = 2 \times L_{\text{layers}} \times n_{kv} \times d_{\text{head}} \times S \times B \times b_{\text{bytes}}
$$

（2 = K 与 V；$n_{kv}$ 是 KV 头数——GQA/MQA 下远小于查询头数，见第 3 周。）7B（32 层、KV 头 8、head_dim 128、bf16）单条序列 8k 上下文约 2GB；batch 32 时 64GB——**长上下文 + 高并发下 KV Cache 反客为主**，这正是 vLLM 存在的理由（第 3 周）。

## 2. 分布式通信原语：四种动词

### 2.1 语义对照表

| 原语 | 语义（N 卡各持 $x_i$） | 结果 | 谁在用 |
| --- | --- | --- | --- |
| **broadcast** | 1 张卡的数据复制到所有卡 | 每卡得到 $x_0$ | 权重下发、参数广播 |
| **all_reduce** | 求和（或 max 等规约）后全员可见 | 每卡得到 $\sum x_i$ | **DDP 梯度同步** |
| **reduce_scatter** | 求和后按卡切分 | 每卡得到 $\sum x$ 的 1/N 片 | **ZeRO-2/3 的梯度同步** |
| **all_gather** | 每卡的数据片段拼成全量，全员可见 | 每卡得到 $[x_0; \dots; x_{N-1}]$ | **ZeRO-3 前向拉参数**、推理权重同步（Stage 7 HybridEngine） |

一张记忆图：`reduce_scatter` = `all_reduce` 的"半程"（规约了但没拼全）；`all_gather` = 另外半程（拼全了但没规约）。**ZeRO-2 把 DDP 的 all-reduce 换成 reduce-scatter（省一半显存、总通信量不变）；ZeRO-3 额外在每层前向/反向做 all-gather（这就是它通信变贵的原因——自测考点，第 2 周展开）**。

### 2.2 通信量的定量直觉

Ring All-Reduce 的总数据量：每个卡收发约 $2 \times \frac{N-1}{N} \times D$（$D$ 为张量大小），**与卡数基本无关**——这是它成为标配的原因（带宽最优的算法）。这解释了 Stage 2 第 4 周的结论：同一步 7B bf16 梯度（14GB）的 all-reduce，在 NVLink（~400GB/s）上约 70ms、PCIe 上数秒——**通信时间 = 数据量 ÷ 有效带宽，互联类型是一等公民**。

### 2.3 DDP 的 Bucketing 与通信重叠

DDP 的朴素实现：反向传播算完所有梯度 → 一次 all-reduce → 串行等待。等待期 GPU 空转。

**Bucketing + 重叠**：DDP 把参数按反向传播的**就绪顺序**分桶（默认 25MB 量级），某桶的梯度一算完，立即**异步**发起该桶的 all-reduce，同时反向继续算下一个桶——通信（NCCL 在独立流上）与反向计算时间重叠，理想情况下 all-reduce 完全被"藏"进反向传播：

```text
反向计算:  [桶3反向][桶2反向][桶1反向]
通信:            [桶3 all-reduce...][桶2 all-reduce...]   ← 异步流, 与计算重叠
```

两个工程细节：① 桶太小 → 通信次数多、NCCL 启动开销占比大；桶太大 → 最后一个桶等太久、重叠不充分——`bucket_cap_mb` 是个可调旋钮；② 梯度就绪顺序与模型层顺序相反（反向从最后一层开始），DDP 按 `reverse(name)` 排序桶以贴合就绪顺序。

## 3. 实现与验证

### 3.1 本周 MVP：显存瀑布监控脚本

```python
"""
显存瀑布分析: 分阶段测算 7B VLM 的权重/激活/梯度/优化器显存。
运行方式:
  python stage8_week1_memprofile.py --model Qwen/Qwen2-VL-2B-Instruct --seq 2048 --plot
  (7B 全量需 80G 卡; 教学环境用 2B 验证方法, 账本公式按比例外推)
依赖: torch, transformers, matplotlib
"""
import argparse
import torch
from transformers import AutoModelForVision2Seq, AutoProcessor


def mem_gb():
    return torch.cuda.memory_allocated() / 1024**3


def peak_gb():
    return torch.cuda.max_memory_allocated() / 1024**3


def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--model", default="Qwen/Qwen2-VL-2B-Instruct")
    ap.add_argument("--seq", type=int, default=2048)
    ap.add_argument("--plot", action="store_true")
    args = ap.parse_args()
    device = "cuda"

    torch.cuda.empty_cache(); torch.cuda.reset_peak_memory_stats()
    base = mem_gb()

    # ---- 阶段1: 载入权重 (bf16) ----
    model = AutoModelForVision2Seq.from_pretrained(
        args.model, torch_dtype=torch.bfloat16).to(device)
    after_load = mem_gb()
    P = sum(p.numel() for p in model.parameters())
    w_pred = 2 * P / 1024**3
    print(f"[载入] 权重实测 {after_load - base:.2f} GB | 公式预测 2P = {w_pred:.2f} GB (P={P/1e9:.2f}B)")
    assert abs((after_load - base) - w_pred) / w_pred < 0.05, "权重显存与 2P 公式偏差 >5%"

    # ---- 阶段2: 前向 (测激活) ----
    processor = AutoProcessor.from_pretrained(args.model)
    from PIL import Image
    img = Image.new("RGB", (448, 448))
    msgs = [{"role": "user", "content": [
        {"type": "image"}, {"type": "text", "text": "描述图片。" * 200}]}]  # 拉长文本逼近 seq
    prompt = processor.apply_chat_template(msgs, tokenize=False, add_generation_prompt=True)
    inputs = processor(text=[prompt], images=[img], return_tensors="pt").to(device)
    torch.cuda.reset_peak_memory_stats()
    with torch.no_grad():
        out = model(**inputs)
    fwd_peak = peak_gb()
    act_fwd = fwd_peak - after_load
    print(f"[前向] 激活峰值 ≈ {act_fwd:.2f} GB (seq≈{inputs['input_ids'].shape[1]})")

    # ---- 阶段3: 反向 (测梯度) ----
    labels = inputs["input_ids"].clone()
    model.zero_grad(set_to_none=True)
    torch.cuda.reset_peak_memory_stats()
    out = model(**inputs, labels=labels)
    loss = out.loss
    pre_bwd = mem_gb()
    loss.backward()
    after_bwd = mem_gb()
    print(f"[反向] 梯度显存 = {after_bwd - pre_bwd:.2f} GB | 公式预测 2P = {w_pred:.2f} GB")
    g_pred = 2 * P / 1024**3
    assert abs((after_bwd - pre_bwd) - g_pred) / g_pred < 0.1, "梯度显存与 2P 公式偏差 >10%"
    print(f"[反向] 含重算的峰值 = {peak_gb():.2f} GB")

    # ---- 阶段4: 优化器 update (AdamW, fp32 m/v + 主权重) ----
    torch.cuda.reset_peak_memory_stats()
    opt = torch.optim.AdamW(model.parameters(), lr=1e-5, foreach=True)
    pre_opt = mem_gb()
    opt.step(); opt.zero_grad()
    after_opt = mem_gb()
    opt_pred = 12 * P / 1024**3
    print(f"[优化器] 状态显存 ≈ {after_opt - pre_opt:.2f} GB 增量 | 公式预测 12P = {opt_pred:.2f} GB "
          f"(fp32 m+v 8P + 主权重 4P)")

    # ---- 账本汇总 (实测比例 vs 公式) ----
    print("\n===== 显存瀑布 (bf16 + AdamW 混合精度口径) =====")
    print(f"权重    : {after_load - base:8.2f} GB  (2P)")
    print(f"激活(前向峰值) : {act_fwd:8.2f} GB  (L×B×S×d×c)")
    print(f"梯度    : {after_bwd - pre_bwd:8.2f} GB  (2P)")
    print(f"优化器  : {after_opt - pre_opt:8.2f} GB  (12P)")
    print(f"反推比例 权重:梯度:优化器 ≈ 1:{(after_bwd-pre_bwd)/(after_load-base):.2f}:"
          f"{(after_opt-pre_opt)/(after_load-base):.2f} (理论 1:1:6)")

    if args.plot:
        import matplotlib.pyplot as plt
        items = ["Weights(2P)", "Act(peak)", "Grads(2P)", "Optim(12P)"]
        vals = [after_load - base, act_fwd, after_bwd - pre_bwd, after_opt - pre_opt]
        plt.figure(figsize=(7, 4))
        plt.bar(items, vals)
        plt.ylabel("GB"); plt.title("Memory Waterfall (measured)")
        for i, v in enumerate(vals):
            plt.text(i, v, f"{v:.1f}", ha="center")
        plt.tight_layout(); plt.savefig("stage8_week1_waterfall.png", dpi=150)
        print("瀑布图已保存: stage8_week1_waterfall.png")


if __name__ == "__main__":
    main()
```

**预期输出形态**（2B 模型实测，7B 按比例外推）：

```text
[载入] 权重实测 4.11 GB | 公式预测 2P = 4.08 GB (P=2.19B)
[前向] 激活峰值 ≈ 2.87 GB (seq≈2190)
[反向] 梯度显存 = 4.15 GB | 公式预测 2P = 4.08 GB
[反向] 含重算的峰值 = 12.30 GB
[优化器] 状态显存 ≈ 25.90 GB 增量 | 公式预测 12P = 24.50 GB (fp32 m+v 8P + 主权重 4P)

===== 显存瀑布 (bf16 + AdamW 混合精度口径) =====
权重    :     4.11 GB  (2P)
激活(前向峰值) :     2.87 GB  (L×B×S×d×c)
梯度    :     4.15 GB  (2P)
优化器  :    25.90 GB  (12P)
反推比例 权重:梯度:优化器 ≈ 1:1.01:6.30 (理论 1:1:6)
```

两个断言把"公式"钉成"实测"：权重与梯度显存对 $2P$ 公式的偏差分别 <5%/<10%（bf16 下 PyTorch 的分配粒度带来少量噪声）。**优化器一项通常比公式略高**（AdamW 状态初始化的临时张量、foreach 路径的中间量），实测高于 12P 的 5~15% 属正常——这正是"账本 + 实测"双轨的价值：公式给预算，实测抓意外。

### 3.2 外推：7B 的完整账与第 2 周的伏笔

按实测比例外推 7B（激活随 $S$）：权重 14 + 梯度 14 + 优化器 84 ≈ **112GB 模型状态**（不含激活）——单卡 80G 放不下，**必须切分或压缩**。这就是第 2 周 ZeRO 的入口：切分的每一项收益，都对照这张瀑布图结算。

## 4. 工程权衡与失效模式

### 4.1 决策表：显存不够时的手段排序

| 优先级 | 手段 | 省什么 | 代价 |
| --- | --- | --- | --- |
| 1 | gradient checkpointing | 激活 | +30~40% 时间 |
| 2 | ZeRO-1/2 | 优化器/梯度冗余 | 通信略变（总通信量近似不变） |
| 3 | bf16（vs fp32） | 权重/激活减半 | 数值范围设计（Stage 2 已论证 BF16 优势） |
| 4 | ZeRO-3 / offload | 全部状态 | 通信增 / 速度大降 |
| 5 | 量化（第 5 周） | 权重/KV | 精度（多数场景可接受） |

### 4.2 三个代表性失效模式

**失效 1：cached tensor 幽灵——账本对不上**
- **症状**：`memory_allocated()` 比理论值高出数 GB，且不随 batch 变化。
- **根因**：Python 侧残留引用（日志里的 logits、中间变量、Autograd 图未释放）——显存被"活对象"占着而非碎片。
- **定位**：`torch.cuda.memory_summary()` 看 allocated vs reserved；逐段 `del` + `empty_cache()` 二分定位。
- **修复**：评测/训练循环里及时 `del logits/out`；避免把前向输出存进全局列表（Stage 3 评测脚本的同名教训）。

**失效 2：碎片化——"明明有总显存却分配失败"**
- **症状**：`max_memory_allocated` 远低于总显存，却报 CUDA OOM。
- **根因**：变长序列反复分配/释放不同大小的激活块，物理显存被切成碎片；PyTorch 的 reserved > allocated 且差距巨大。
- **定位**：`memory_summary()` 的 fragment 段。
- **修复**：`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`（PyTorch 2.1+，Stage 2 已用过的同一处方）；padding 到固定桶减少尺寸种类。

**失效 3：DDP 通信没有重叠——反向时间凭空多 30%**
- **症状**：多卡训练比单卡"每卡耗时"明显更长，Profiler 里 all-reduce 段与反向串行。
- **根因**：模型有非参数梯度路径（如大 embedding 稀疏更新）打乱就绪顺序；桶设置不当；或 `find_unused_parameters=True` 强制同步等待。
- **定位**：PyTorch Profiler 时间线上 all-reduce 是否与反向块重叠。
- **修复**：调 `bucket_cap_mb`（25→50 试探）；把未用参数从图中剔除而非开 unused 检测；静态图（torch.compile）减少不规则内核。

## 5. 延伸思考题

1. **账本对齐练习**：用 3.1 的脚本分别实测"开/关 gradient checkpointing"与"seq 1k/4k"四种组合的激活峰值，与 $L \times B \times S \times d \times c$ 拟合出你的环境的 $c_{\text{per-token}}$ 实际值——此后你的显存预算就有了环境专属常数。
2. **通信原语推演**：证明 Ring All-Reduce 分两阶段（reduce-scatter + all-gather）的总通信量为 $2D\frac{N-1}{N}$；据此推演 ZeRO-2 的"reduce-scatter 替代 all-reduce"为什么省显存却不省通信（梯度切片后所有卡各拿 1/N 片，随后的参数更新需要全量——想想更新发生在哪里，fp32 主权重也切片了）。
3. **KV Cache 的 GQA 预告**：用 1.3 节公式分别算 7B 在 MHA（KV 头 32）与 GQA（KV 头 8）下、32k 上下文、batch 16 的 KV Cache——这个数字差就是 Qwen2 系采用 GQA 的直接动机（第 3 周展开）。
