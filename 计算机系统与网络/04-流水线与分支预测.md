# 04 - 流水线与分支预测

## 本篇目标

- 用流水线的眼光重新理解"CPU 主频"：一条指令的延迟没变，吞吐为什么翻了数倍；时钟周期为什么由最慢一级决定。
- 认识三类流水线冒险（结构/数据/控制），重点吃透控制冒险：分支预测为什么"值得猜"、误预测惩罚 15~20 周期从哪来。
- 做分支预测实验：有序 vs 无序数组求和实测 3.4 倍差距，并理解 -O2 下编译器用 cmov 把整个效应抹掉的现场。
- 建立 SIMD 与乱序执行的正确直觉：一条指令算多个数、IPC 可以大于 1，以及 Python 代码为什么吃不到这些红利。

前置：01 章（抽象阶梯）、03 章（缓存延迟）；02 章的指令知识会在反汇编处用到。

## 1. 流水线思想：洗衣店给你的启示

洗一批衣服要走四道工序：洗（30 分钟）、烘（30）、叠（30）、放（30）。串行做 4 批要 8 小时；**流水线**做法是第 1 批洗完进烘干时，第 2 批立刻进洗衣机——4 批只要 3.5 小时（P&H 第 4 章的标准类比）：

```
时间 →  0   30   60   90   120  150  180 分钟
批1:   洗   烘   叠   放
批2:        洗   烘   叠   放
批3:             洗   烘   叠   放
批4:                  洗   烘   叠   放
第一件完成于 120 分（延迟没变！），之后每 30 分钟出一批（吞吐 ×4）
```

CPU 把"取指→译码→执行→访存→写回"当作五道工序（P&H 第 4.5 节的经典五级：IF/ID/EX/MEM/WB），同一时刻五条指令分别处在五级。关键账本：

- **单条指令延迟没变**（甚至因流水线寄存器开销略变长），变的是**吞吐率**：理想情况下每个周期都有一条指令"出炉"。
- **时钟周期由最慢一级决定**：若 EX 要 300ps、其他级 100ps，时钟就得起 300ps。这就是 01 章说"主频有物理上限"的另一半原因——级切得越细主频能越高，但级间寄存器开销占比越大，所以主频换 IPC 有个工程甜点区。
- 流水线的理想加速比 ≈ 级数（5 级理想 ×5）。现代 x86 流水线 **14~20 级**（Intel SDM/各家优化手册），理想吞吐 = 每周期完成接近 1 条——然后，现实立刻用"冒险"砸场子。

## 2. 冒险：流水线的三种"堵车"

**结构冒险（structural hazard）**：两条指令同一周期抢同一硬件。例：取指和访存都用一个指令/数据存储器——解决方案是分立 L1i/L1d（03 章你已在 lscpu 里见过这两个实例），现代主流 ISA 里结构冒险基本已被硬件预算消灭。

**数据冒险（data hazard）**：后一条指令需要前一条还没写完的结果。`add %rax,%rbx` 后紧接 `sub %rbx,%rcx`，按"写回后才读"的严格时序，sub 要空转 2 拍。解决方案是**转发（forwarding/bypassing）**：EX 结果一出来直接从流水线寄存器拉给下一级的输入端，不必等写回——

```
 add:  IF  ID  EX  MEM  WB
 sub:      IF  ID  EX*  ...        EX* 直接引用 add 的 EX 输出（转发）
 mul:          IF  ID  EX stall 1 拍   ← load-use 冒险：数据在 MEM 级才出现
```

只剩**load-use** 这一种典型停顿：load 的数据 MEM 级才可得，紧跟的使用者（即使转发）也要多等 1 拍。编译器靠**指令调度**（把无关指令填进这个洞）缓解——02 章说 -O2 会"改变程序形状"，这就是形状之一。

**控制冒险（control hazard）**：`je` 要到 EX/MEM 级才知道跳不跳，但流水线前端**早就**按顺序预取了后面的指令——若跳转成立，已取的 15~20 条指令全部作废。这是现代 CPU 最大的性能洞，下一节专门讲。

## 3. 分支预测：为什么"猜"是理性策略

先算账：现代流水线 ~20 级，分支结果要到第 4~6 级才确定，误预测要冲刷的指令窗口约 **15~20 周期**（Intel 优化手册给出典型分支误预测惩罚约 15~20 cycles）。典型代码里分支每 5~6 条指令出现一次——如果每次都停 15 周期，流水线约一半时间在空转。所以设计者选择**赌**：预测它不跳（或按历史跳），赌错再冲刷。

**为什么猜得准？** 因为分支行为有强规律。预测器进化史（P&H 4.8；Hennessy & Patterson《计算机体系结构：量化研究方法》第 3 章有完整综述）：

```
 1. 静态预测：向后跳 = 循环 → 猜跳；向前 = 猜不跳。准确率 ~65-85%
 2. 2-bit 饱和计数器：每分支一个计数器，连错 2 次才改主意
        00 强不跳 → 01 弱不跳 → 10 弱跳 → 11 强跳（循环边缘不再抖动）
 3. BTB（分支目标缓冲）：缓存"这个地址的分支上次跳去了哪"，取指级直接用
 4. 现代主力 TAGE/感知机混合：用长历史模式匹配，典型准确率 95~99%
```

预测的精度是以"历史会重复"为前提的。**分支可预测性的直觉**：错误检查、边界判断这类分支接近 50/50（不可预测）；循环、类型标签、热路径条件高度偏斜（可预测）。这也预告了 5 节实验的形状：把一个 50/50 的分支序列换成 100% 可预测序列，差的就是那 15~20 周期/次。

预测器的资源账（理解"为什么能猜这么准"的硬件视角）：2-bit 计数器通常以 2 的幂次规模成组放置（如 4K 个表项，用分支地址低位索引——**不同分支可能撞同一表项，别名干扰是预测精度的重要损失源**）；BTB 只缓存"跳过"的分支（不跳的分支不需要目标）；现代 TAGE 用多档历史长度（4~200+ 位）做模式匹配，长历史捕捉周期性模式、短历史兜底。由此得出可操作推论：**分支越少、行为越规律的代码对预测器越友好**；大量 switch/间接调用的解释器循环（Python 解释器本身就是！）是预测压力最大的负载——这也是 CPython 3.11 加"自适应专用解释器"（给热点字节码做特化）能提速 25% 的底层原因之一：把多态分派变成单一模式。

## 4. 实验：有序 vs 无序数组求和

经典实验（源自 McVoy/Stu 的 stackoverflow 名题"Why is processing a sorted array faster"）：随机数求和 vs 排序后求和，代码一字不改：

```c
// branch.c —— 同一段代码，只差"数组是否有序"
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
#define N 32768
double now(){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);return t.tv_sec+t.tv_nsec/1e9;}
int cmp(const void*x,const void*y){return *(int*)x-*(int*)y;}
int main(){
    static int data[N];
    srand(42);
    for(int i=0;i<N;i++) data[i]=rand()%256;      // 0~255，≥128 的概率约 50%
    long sum=0; double t0,t1;
    t0=now();
    for(int r=0;r<2000;r++){sum=0;
        for(int i=0;i<N;i++) if(data[i]>=128) sum+=data[i];}
    t1=now(); printf("unordered: %.4f s (sum=%ld)\n", t1-t0, sum);
    qsort(data,N,sizeof(int),cmp);                 // 排序：分支变可预测
    t0=now();
    for(int r=0;r<2000;r++){sum=0;
        for(int i=0;i<N;i++) if(data[i]>=128) sum+=data[i];}
    t1=now(); printf("sorted:    %.4f s (sum=%ld)\n", t1-t0, sum);
    return 0;
}
```

```bash
$ gcc -O0 branch.c -o branch_O0 && ./branch_O0
unordered: 0.2444 s (sum=3149529)
sorted:    0.0709 s (sum=3149529)        # 3.4 倍！
$ gcc -O2 branch.c -o branch && ./branch
unordered: 0.0298 s (sum=3149529)
sorted:    0.0296 s (sum=3149529)        # 差距消失了？！
```

两段结果都要会读：

- **-O0 的 3.4 倍**：随机数据让 `if (data[i]>=128)` 这条分支变成抛硬币，预测器理论上限 50%，每次错的代价 ~15-20 周期；排序后分支变成"前半永远不跳、后半永远跳"，预测器近乎 100%。差距 = 误预测次数 × 惩罚。
- **-O2 差距消失**：看反汇编（02 章技能）：

```bash
$ gcc -O2 -S branch.c -o - | grep -A3 "cmov\|cmove" | head -6
	movl	(%rax), %edx
	leal	(%rdx,%rcx), %eax      # sum+data[i] 先算好
	testl	%edx, %edx
	cmovns	%eax, %r8d             # 符号位为正才采纳，否则保留旧 sum
```

编译器把 `if (cond) sum += x` 改写成了**条件传送（cmov）**：两条路径都算好，用一条指令按条件挑选结果——**没有跳转就没有冲刷**，控制冒险被消灭。代价是"无条件多算了一次加法"，但换来确定性。这是"无分支编程"的核心思想：**误预测贵，就买确定**。注意 cmov 不是万能药（两侧计算都贵时反而亏、且可能引入除零等副作用风险），编译器只在收益明确时使用。**经验做法**：热循环里把"不可预测分支"改写成算术（`sum += data[i] >= 128 ? data[i] : 0` 是起点，但以编译器实际产物为准）或查表，先用反汇编确认分支真被消除了。

## 5. 乱序执行与超标量：流水线的现代形态

五级流水线是教学模型。真实 x86 核心是**超标量 + 乱序**（out-of-order）机器（P&H 4.10 与《量化研究方法》第 3 章）：

```
 前端（顺序）：取指 → 译码（每周期 4~6 条）→ 重命名（消除假依赖）
                                        ↓
 保留站：就绪的微操作乱序发射到多个执行端口（ALU×2~3、load×2、store、FP…）
                                        ↓
 重排序缓冲 ROB：按原始程序顺序提交结果（保持程序语义）
```

三个要点：① **乱序但不违法**——提交永远按程序序，指令间的真实数据依赖绝不被打破，乱序只是"找无关的活先干"；② **IPC 可以大于 1**：一周期发射/提交多条指令，`perf stat` 里的 IPC（instructions per cycle）超过 4 都常见（性能工程 03 篇教你读它）；③ **前端口径**：IPC 低不一定是执行慢，可能是前端取指/译码瓶颈（iCache 未命中、分支预测失败）或后端等待（缓存未命中停顿）——perf 的 topdown 分析法把 IPC 拆成 frontend-bound / backend-bound / bad-speculation（含分支误预测）/ retiring 四桶，这就是性能工程 03 篇"IPC 数字背后"的原理课。

乱序与分支预测是一对搭档：预测器赌一个方向让流水线继续灌（speculation），赌错了靠 ROB 撤销所有推测结果——**预测是油门，ROB 是安全气囊**。

## 6. SIMD：一条指令，一排数字

超标量之外还有一条并行维度：**SIMD（单指令多数据）**。x86 的向量扩展：SSE（128 位）/ AVX2（256 位）/ AVX-512（512 位）——一个 256 位寄存器装 **8 个 float**，一条 `vaddps %ymm1,%ymm0,%ymm2` 同时算 8 对加法（CSAPP 3.13 与《Optimization Manual》第 12~15 章）：

```
标量:  vaddss:  [a0]      + [b0]      → [c0]          1 个/条
向量:  vaddps:  [a0 a1 ... a7] + [b0 b1 ... b7] → [c0 ... c7]   8 个/条
       （AVX2 256bit = 8×float32）
```

这直接改写 03 章的算术强度账本：同样的访存次数，算力上限 ×8。NumPy/PyTorch 的底层 kernel 全靠它——`np.dot`、`torch.nn.Linear` 在 CPU 上跑的就是 AVX 指令。**ARM 注**：ARM 的对应物是 NEON（128 位）与 SVE/SVE2（可变长 128~2048 位），RK3588 的 4×A76 支持 NEON——端侧部署查算子速度时先确认 NEON 路径有没有走通。

那 Python 能吃到吗？**解释器本身吃不到**：`for i in range(n): s += a[i]` 每次迭代要执行上百条字节码/对象操作，算术只占其中几条——SIMD 加速的那部分被 Python 对象开销淹没（这就是 NumPy 存在的理由：把循环沉到底层 C/SIMD）。判断一段 C 代码有没有被自动向量化（**经验做法**）：`gcc -O2 -fopt-info-vec` 会打印哪些循环向量化成功；没成功时检查访问步长、条件分支（可用 cmov/掩码改写）和别名问题（`restrict` 关键字）。

## 7. 超线程与多核：流水线之后的并行层级

超标量+乱序把一个核内部填满了，但填满只是"理想态"——现实中 load 未命中停顿、分支冲刷都会让执行端口空转。**超线程（SMT，Simultaneous Multi-Threading）**的思路：一个物理核伪装成两个逻辑核，**共享**执行端口/缓存/分支预测器，只是各自维护一套架构状态（通用寄存器组、PC）——线程 A 等 load 时，线程 B 的指令填进空闲端口。本机 `lscpu` 的证据：

```
Thread(s) per core:  2      ← 每物理核 2 个逻辑线程（SMT 开启）
Core(s) per socket:  8      ← 8 个物理核（6P+4E 混合架构）
```

性能预期要摆正（P&H 4.10 与 Intel 优化手册的口径）：SMT 收益通常 **15~30%**，远不到"两个核"的 2 倍——因为执行资源是共享的，两个线程是**分时复用**流水线而非各占一半。两线程跑同一热点代码（抢同一资源）时 SMT 甚至可能负收益。**经验做法**：计算密集且互相独立的负载开 SMT 有收益；内存带宽已打满的负载（03 章的边界）开 SMT 几乎无收益；对延迟敏感的单线程任务，用 `taskset` 独占物理核（连同关闭其 SMT 兄弟）是推理服务的常见做法。

```
 并行的四个层级（本章视角的地图，从细到粗）：
 SIMD        一条指令 8 个数     （数据级并行，本篇 6 节）
 乱序/超标量  一个核一周期多条指令（指令级并行 ILP，本篇 5 节）
 SMT         一个核跑两个线程    （线程级并行 TLP 的资源共享版，本节）
 多核        多个独立核          （TLP 的完整版，OS 系列 02/11 篇）
```

层级越粗，程序员要操心的事越多：SIMD 与 ILP 基本由编译器+硬件自动兑现，SMT 由操作系统调度，多核才真正把"同步与一致性"推给程序员（OS 系列 11 篇的锁与内存序）。本系列 01–05 章的边界也在此画清：**03 章讲数据怎么被搬到核，04 章讲指令怎么在核里流动，多核协同属于 OS 系列**。

## 常见误区

1. **"流水线级数越多越快"**：级数提升主频（每级更短），但误预测惩罚 ≈ 级数 × 周期，级数越深赌错的代价越大；Pentium 4 的 31 级就是历史上为高主频付出的预测代价。级数是频率与误预测风险的平衡，不是越大越好。
2. **"只有 if 语句才有分支"**：循环回边（`jne`）、函数调用的间接目标（switch 表、虚函数、函数指针）都经过预测器；间接目标 BTB miss 的代价同样高昂。热路径上的多态虚函数调用是 C++ 常见坑（C++ 系列与 devirtualization 话题呼应）。
3. **"乱序执行会改变程序结果"**：不会。ROB 保证按程序序提交，数据依赖被尊重；只有可观察的副作用顺序保持不变，程序语义才成立。乱序只是调度，不是改写。
4. **"分支预测是编译器的事"**：预测器在硬件里，编译器帮不上"猜得准"，但能帮你"少猜"（cmov、查表、循环不变量外提）。两边分工，别混。
5. **"SIMD 自动向量化开了 -O2 就一定有"**：访问模式不规则、存在别名、循环内有依赖时自动向量化会放弃；显式 intrinsics 或编译指示（`#pragma omp simd`）是兜底。以 `-fopt-info-vec` 的输出为准，别靠信仰。

## 本篇小结

- 流水线不缩短单条延迟，只提升吞吐（每周期出一条）；时钟周期由最慢一级决定，主频与流水线深度是同一枚硬币的两面。
- 三类冒险：结构（用分立资源消灭）、数据（转发消灭，剩 load-use 停 1 拍靠编译器调度）、控制（预测器 + 冲刷，误预测 ~15-20 周期）。
- 预测器赌"历史重演"：2-bit 饱和计数器防抖、BTB 记目标、TAGE 长历史匹配，典型准确率 95-99%；分支越规律越好猜。
- 实验：-O0 下有序 vs 无序 3.4 倍；-O2 下编译器用 cmov 把分支变成无条件算术，差距归零——"误预测贵就买确定"（经验做法）。
- 现代核 = 超标量（多端口）+ 乱序（ROB 保序提交）+ SIMD（一次 8 个 float）；IPC>1 是常态，IPC 低要先分清前端/后端瓶颈（衔接性能工程 03 的 topdown）。
- Python 吃不到 SIMD 的原因：解释器开销淹没算术收益；把循环沉到 NumPy/C 层才有红利。
- 并行四层级：SIMD（数据级）→ 乱序超标量（指令级）→ SMT（一核双线程，共享执行资源，收益 15-30%）→ 多核（OS 系列接管）；层级越粗，越需要程序员操心同步。

## 练习

1. 用洗衣店模型算一笔账：4 级流水、每级 1 周期，处理 100 条指令的总周期是多少（含首次填充 3 拍）？若有 10 个分支各误预测 15 拍，总周期变成多少，吞吐下降百分比是多少？
2. 在 branch.c 里把 `data[i]>=128` 改成 `data[i]>=32`（阈值改变数据分布），-O0 下重测 unordered/sorted，解释为什么 sorted 的时间不变而 unordered 可能略有变化（数据分布 → 误预测次数）。
