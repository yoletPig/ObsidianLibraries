## 1. 延迟数字表：工程师必须背下来的数量级

来源：Jeff Dean《Latency Numbers Every Programmer Should Know》（2009 年 Build '10 演讲），Brendan Gregg 将其整理成著名可视化卡片；跨层数字在 03 章已给过一半，这里补全工程版并加上"换算"一栏——**光速与快递员的物理事实**：

| 事件 | 量级 | 直觉换算（1ns≈光走 30cm） |
| --- | --- | --- |
| L1 缓存访问 | ~1 ns | 房间里 |
| 内存往返（DRAM） | ~100 ns | 横穿一条街 |
| 同机房 RPC（含栈开销） | ~0.5 ms | 过一个街区 |
| 同城 RTT | ~1-5 ms | 跨城区 |
| 跨国/跨洲 RTT | ~150-300 ms | 北京↔洛杉矶光速直线 ~70ms，实际路径绕行 2-4 倍 |
| SSD 随机读 | ~20-100 µs | 比内存慢 1000 倍 |
| 一次 HTTPS 握手（1-RTT TLS1.3） | ≈ 2×RTT + 服务器处理 | 跨洲站点 ≈ 400ms 才能发第一个请求 |

**为什么必须背**：因为它是所有"该不该优化"的**分母**。例：接口耗时 120ms，其中 DB 查询 90ms——若 DB 在同城（RTT 1ms），90ms 是"真的在算"；若 DB 跨机房（RTT 40ms）且查了 2 次，80ms 可能只是**在路上**，加索引无效、搬机房立竿见影。分不清"计算时间"和"传输时间"，优化方向就是随机的。**经验做法**：给任何服务的延迟拆账时，第一刀切"本地计算/网络往返/磁盘 IO"三份，各占多少一目了然，再决定动哪刀。

## 2. 带宽×延迟积：BDP 与窗口

一条链路"同时能有多少数据在飞"由带宽和 RTT 共同决定：

```
BDP = 带宽 × RTT
例：100 Mbps 链路 × 50 ms RTT = 12.5 MB/s × 0.05 s = 625 KB 在途
例：10 Gbps 长肥网络 × 100 ms = 125 MB 在途！
```

要吃满带宽，**在途数据必须 ≥ BDP**（管道灌不满就没有满速可谈）。对 TCP，在途数据上限 = 接收窗口 rwnd（07 章），所以：**窗口 < BDP ⇒ 吞吐 = 窗口/RTT，与带宽无关**。常见场景的 BDP 速查（心算即可）：

| 场景 | 带宽 | RTT | BDP（在途需求） | 说明 |
| --- | --- | --- | --- | --- |
| 家宽到同城 CDN | 300 Mbps | 15 ms | ≈ 563 KB | 普通窗口即可吃满 |
| 机房间万兆 | 10 Gbps | 0.5 ms | ≈ 625 KB | 低 RTT 是朋友 |
| 跨洲 10G 专线 | 10 Gbps | 150 ms | ≈ 187 MB | **必须开窗口缩放+大缓冲** |
| 跨洲 100 Mbps | 100 Mbps | 150 ms | ≈ 1.9 MB | 带宽小 BDP 也小，窗口够 |

经典陷阱：带宽 1Gbps、RTT 50ms、窗口只有 256KB → 吞吐 = 256KB/50ms ≈ 5.2MB/s ≈ 42Mbps，**带宽利用率 4%**——加带宽无效，必须加窗口（这正是 07 章握手时 wscale 窗口缩放存在的理由：16 位字段最大 64KB，乘 2⁷ 才到 MB 级）。实测验证：

```bash
$ ss -tin dst :443 | grep -E 'rtt|send'
	rtt:45.2/0.1   send 4.5Mbps   unacked 38   cwnd 62
# 吞吐上限估计 = cwnd×MSS / RTT = 62×1460B / 45ms ≈ 2.0MB/s
```

**经验做法**：跨地域传输慢时先算 BDP 对账——若理论吞吐远高于实测且 `ss` 看到 cwnd 偏小，是拥塞控制保守（考虑 BBR）或丢包率作祟；若 cwnd 已很大仍慢，看接收端窗口与应用读速（所谓"服务端慢"经常是客户端读慢）。本系列的延迟表 + BDP 公式与 Linux 性能工程 07 章的实测工具是同一知识的一体两面。

BDP 的思维还可以超出 TCP，做任何"管道"的容量设计：消息队列的在途消息上限（消费速率 × 端到端延迟）、流水线的工位深度（03 章 GPU 流水线）、甚至并发爬虫的请求数（QPS × 平均响应）。凡"速率 × 延迟"决定"同时在飞多少"的场景，都是 BDP 换了个马甲——**见到"加并发没用/加了也白加"，先算这条管道的 BDP 对不对得上**。

## 3. 为什么"加机器不一定变快"

三类硬约束，每类一个现场：

**① 串行依赖**：流程 A→B→C 必须依次发生，并行只能压"同一环节内部的量"。用户登录要过：鉴权服务→风控服务→数据库——三跳串行，每跳 20ms，总延迟 60ms 与机器数无关；把三个服务各扩 10 倍，延迟还是 60ms（吞吐提高了，延迟没变）。**吞吐可并行，延迟看关键路径**。

**② 一致性强制的往返**：分布式一致性协议（共识/锁/主从复制）的代价就是**额外往返**。写一个"强一致跨机房"的数据：客户端→机房A主库（1 RTT）→同步复制到机房B（1 RTT 跨洲 150ms）→确认（回程）——写延迟 ≥ 300ms，**这是 CAP/共识的数学代价，不是实现差**。同一数据同城复制 30ms 就够——所以"多活"难就难在跨洲一致性延迟上（10 章调度、本章 7 节再回收）。

**③ 共享瓶颈**：03 章的内存带宽（8 核抢一条总线）、07 章的拥塞窗口（所有连接共享一条链路）、数据库连接池（100 个应用实例抢 2000 个连接）——加机器只是把瓶颈推到下一个共享点。**判断方法**：看目标资源是不是"全局共享且不可分割"（带宽、单库写、单实例缓存）；是，则先拆共享点（分片、本地缓存、读写分离）再加机器。

把三类约束放进一张算题（面试与架构评审通用）：一个下单接口的关键路径是"鉴权 10ms（本地）→ 风控 RPC 30ms（跨机房 RTT 20 + 处理 10）→ 强一致写主库 80ms（跨洲同步复制）→ 返回"。总延迟 120ms 里：本地计算只占 20ms，**100ms 是协议与距离给的**——加 10 台应用机器，这三段一毫秒都不会变；把风控 RPC 改批量/合并不了（串行依赖），把强一致写换同城（-50ms）或异步化（-80ms，牺牲强一致）才是有效杠杆。**先问每一段延迟的"物理成分"（距离/协议/计算），再谈加机器**——这个拆法同时覆盖 3 类约束的判断。

## 4. Amdahl 定律：并行收益的数学上限

系统有可并行比例 p 和不可并行的串行比例 (1-p)，用 n 个并行单元的加速比（Amdahl 1967）：

```
S(n) = 1 / ((1-p) + p/n)
```

推导一行：总时间 = 串行部分 (1-p)·T + 并行部分 (p·T)/n；加速比 = 原时间/新时间。数值表（背下形状）：

| p \ n | 2 | 4 | 16 | 100 | ∞ |
| --- | --- | --- | --- | --- | --- |
| 0.50 | 1.33 | 1.60 | 1.88 | 1.98 | **2.00** |
| 0.90 | 1.82 | 3.08 | 6.40 | 9.17 | **10.00** |
| 0.95 | 1.90 | 3.48 | 9.14 | 16.67 | **20.00** |
| 0.99 | 1.96 | 3.88 | 13.91 | 50.25 | **100.00** |

两个反直觉结论：① **上限由串行部分锁死**：p=0.95 时哪怕无限并行，最多快 20 倍（1/(1-0.95)）；p=0.50 永远最多 2 倍。② **边际收益递减**：p=0.9 时从 2 核到 4 核快 1.69 倍，从 50 到 100 核只快 1.11 倍——机器数翻倍不再带来翻倍。工程含义：**优化顺序是先提 p 再加 n**（串行的 10% 改并行，比再买 100 台机器值钱）；这也解释了推理服务里为什么"批量"优先于"扩容"（batch 内并行把 p 推高，而 GPU 已经是 n=几千并行的单元）。对照定律 Gustafson（1988）一句话区分：Amdahl 回答"固定工作量下并行能多快跑完"（降延迟视角），Gustafson 回答"固定时间下能多算多少"（扩工作量视角）——讨论降延迟用 Amdahl，讨论吞吐扩容用 Gustafson。

## 5. 延迟算题两例：把数字表用起来

**例一：一次 HTTPS 请求的握手预算**（把 1 节的表变成心算）。目标服务器 RTT=60ms（同城边缘），各阶段理论下限：

```
 DNS（本地解析器有缓存）        0 RTT        0 ms
 TCP 三次握手                  1 RTT       60 ms   （SYN→SYN+ACK 是半个往返？不：
                                          SYN 与 SYN+ACK 各半个，合并计 1 RTT）
 TLS 1.3 握手（与 TCP 合并计）  +0~1 RTT    60 ms   （TLS1.3 的 1-RTT 里 ClientHello
                                          可搭 TCP 第三个 ACK 的车，实际约 1 RTT）
 HTTP 请求+首字节响应          1 RTT       60 ms
 合计首字节                   ≈ 3 RTT     180 ms
 若 TLS1.2（2-RTT）且跨洲 150ms：≈ 4 RTT = 600ms —— 版本与距离都是 2 倍级杠杆
```

这张小账单解释了 08 章的 HTTP/3（把 TCP+TLS 两笔握手并成 1 RTT）、09 章的 0-RTT（复用会话再省一笔）、10 章的 Anycast（把 RTT 本身砍小）各自省的是哪一笔——**每一项优化都能在账单上找到自己的位置**。也解释了为什么"长连接+连接池"是所有客户端库（数据库/Redis/HTTP）的标配：连接建立成本是每个新连接都要重付的固定税。

**例二：Little's Law 做容量规划**（性能工程 01 篇的核心公式，这里补上网络语境的用法）：

```
L = λ × W        并发数 = 到达率 × 平均驻留时间
例：API 目标 QPS=1000，平均响应 200ms → 稳态并发 L = 1000 × 0.2 = 200
   → 至少 200 个"并发槽"（连接池、worker、线程），再加余量应对突发
```

两个直接应用：① **连接池 sizing 不再拍脑袋**——QPS 与单请求延迟一乘就出下限（DB 连接池给 200+缓冲，而不是"经验值 10"）；② **排队预警**——实测并发 > λ×W 持续增长，说明系统过饱和（吞吐封顶了），P99 会先爆炸（性能工程 01 篇的长尾）。**经验做法**：压测报告必须同时给 QPS、P99、并发数三个数，用 Little's Law 交叉验证一致性——三个数对不上，说明测量本身有坑（比如压测机瓶颈）。

## 6. RTT 敏感设计：对抗往返的四件工具

凡是"每一步都要等上一步的网络回应"的设计，延迟 ≈ 步数 × RTT，而 RTT 你优化不动（光速+距离），能动的只有**步数**：

- **批量（batching）**：N 个请求并成一个往返。DB 的 N+1 查询（循环里逐条 SELECT）改成 IN 一次查询；RPC 的逐条推送改成攒批（11 章 client-streaming）；LLM 的 continuous batching（03 章）——同一个思想的三次落地。
- **流水线（pipelining）**：不等回应就发下一个（Redis pipeline：10 条命令 1 个 RTT 发完，而非 10 个 RTT；TCP 滑动窗口本质也是流水线）。注意与并发的区别：流水线保序，并发乱序。
- **预取（prefetch）**：猜到下一步要什么，提前去拿。CPU 硬件预取器（03 章）、HTTP/2 服务器推送（已弃）、数据库预读——共同点是"用带宽换延迟"（带宽便宜，RTT 贵）。
- **本地缓存**：把上一次往返的结果留在进程内，下次零往返。成本是失效一致性（缓存多久的权衡），收益是把 100ns~100ms 的访问降到 ~100ns 内存速度（03 章表）。

**案例：KV cache 就是"预取/缓存"思想在推理里的化身**。Transformer 自回归生成第 t 个 token 时需要全部前文 t-1 个位置的 K/V——朴素做法每步重算全部历史（往返=重算整个前缀）；KV cache 把历史 K/V 存下来，每步只算新 token 的 K/V（**一次增量、零重算**）：

```
 朴素生成（无缓存）                     KV cache（预取/缓存）
 第 t 步：算 K/V(1..t-1) ← 重算！       第 t 步：只算 K/V(t)，查表其余
 第 t+1 步：算 K/V(1..t) ← 又重算！     第 t+1 步：只算 K/V(t+1)，追加进表
 每步代价 O(t)   →  总代价 O(n²)        每步代价 O(1) → 总代价 O(n)
```

代价是显存（随上下文线性增长：7B 模型 fp16 每万 token 约数 GB——03/05 章的位宽账直接可用），收益是延迟从 O(上下文长度) 降到 O(1)。**PagedAttention 进一步**把 KV cache 当虚拟内存分页管理（OS 系列 05 篇思想的 GPU 版），碎片率从 60-80% 降到 <4%（vLLM 论文，Kwon et al. 2023）——网络课的"缓存/预取"与 OS 课的"分页"在推理引擎里会师。

## 7. 跨地域部署决策：把计算放到离用户最近的地方

决策树（从上往下走，命中即停）：

```
 请求能否容忍 >150ms 延迟？ ──是──► 单区域部署（最简单）
        │否
 请求是读为主、数据可缓存/可复制？ ──是──► 边缘/CDN + 多区域读副本
        │否
 写为主且强一致？ ──是──► 单主区域 + 就近接入转发（Anycast 终结连接，写回主区域）
        │否（可牺牲一致性）
 最终一致多活（CRDT/冲突解决）── 复杂度最高，仅巨头核心业务用
```

典型 LLM API 的形态（10 章 Anycast 的回收）：边缘就近终结 TLS/TCP（握手快），请求转发到少数几个大区域集群（GPU 集中管理便宜），流式响应原路返回（首 token 延迟取决于模型集群位置——所以"区域选择"是用户可见的配置项）。**经验做法**：跨区域部署前先做"延迟预算审计"——把一个请求的关键路径按 6 节四件工具过一遍，往往发现"搬到边缘"的收益远小于"少两次跨区域往返"；多区域是最后手段，不是第一步。

## 常见误区

1. **"带宽大 = 传得快"**：小文件传输的耗时被 RTT 主导（握手+往返），100Mbps 与 10Gbps 传一个 10KB 文件几乎无差（1 RTT 就完事）。提升"小包延迟"靠就近（10 章）与长连接复用（07/08 章），不靠加带宽。
2. **"并行度 = 机器数，加机器线性加速"**：Amdahl 数值表面前不成立；p=0.9 时 100 台只有 9 倍。先审计串行比例与共享瓶颈，再谈扩容（3 节三类约束过一遍）。
3. **"延迟优化 = 优化代码"**：03 章的内存墙、07 章的慢启动、本章的 RTT——大量延迟是"物理与协议"给的，代码层优化在错误的分母上白费劲。先拆账（1 节三刀），再选工具。
4. **"缓存是万能的"**：缓存的隐性成本=一致性维护+失效风暴（热点 key 失效瞬间打穿源站）+内存预算；KV cache 显示"缓存思想"要配套"淘汰与分页"（PagedAttention）才完整。无失效策略的缓存是事故预定。
5. **"跨机房复制 = 高可用，值得马上做"**：强一致跨机房写延迟 ≥ 2×RTT（3 节②的账），同步复制把最慢副本变成你的写延迟；多数业务该用"同城强一致 + 异地异步灾备"，跨洲强一致多活是极少数业务的需求。
6. **"数字表会过时，不用背"**：数字会微调，**数量级关系十年不变**（L1 比内存快两个数量级、网络比内存慢三个数量级以上）——背的是数量级与梯度，不是精确值；拿到新机器用 06 章的 ping、本篇的 `curl -w` 花 5 分钟重新标定一遍即可。

## 本篇小结

- 延迟数字表是优化方向的分母：内存 100ns / 同城 1ms / 跨洲 150-300ms / HTTPS 握手 2×RTT；先拆"计算/网络/磁盘"三份账再动手（经验做法）。
- BDP = 带宽×RTT；窗口 < BDP 时吞吐 = 窗口/RTT 与带宽无关——跨地域慢先对 BDP 账，看 cwnd/rwnd 再谈扩带宽；"速率×延迟=在途量"的管道思维适用于 MQ/流水线/爬虫等一切场景。
- 加机器无效的三类约束：串行依赖（延迟看关键路径）、一致性往返（跨洲强一致写 ≥ 2×RTT）、共享瓶颈（先拆共享点）。
- Amdahl：S(n)=1/((1-p)+p/n)，上限 1/(1-p)；p=0.95 → ∞ 台也只有 20 倍；先提 p（批量化）再加 n；Gustafson 是吞吐视角的补集。
- 会用数字表做算题：HTTPS 首字节 ≈ 3 RTT（DNS 缓存命中 + TLS1.3），TLS1.2 跨洲变 4 RTT——每项协议优化都能在账单上找到位置；Little's Law L=λ×W 把连接池/worker 的 sizing 从拍脑袋变成乘法（与性能工程 01 篇互通）。
- RTT 敏感设计四件套：批量/流水线/预取/本地缓存；KV cache = 预取思想 + 分页管理（PagedAttention）在推理引擎的会师。
- 跨地域决策树：能容忍 → 单区域；读多 → 边缘+副本；强一致写 → 单主+就近接入（Anycast 终结）；先做延迟预算审计，多区域是最后手段。

## 练习

1. 用 1 节数字表心算：一个页面加载需要 1 次 DNS（未缓存）、1 次 TCP+TLS 握手（TLS1.3）、1 次 HTTP 请求，服务器在 150ms RTT 外——首个字节大约多少 ms 之后到达？换 HTTP/3 的 1-RTT 握手（QUIC+TLS 合一，DNS 仍需一次往返）能省多少？
2. 算 BDP：你的 WSL2 到 `223.5.5.5` 的 RTT（06 章 ping 实测 ~15ms）× 你家/办公室出口带宽（假设 300Mbps）——在途数据多少 KB？TCP 窗口至少要多大？用 `ss -tin` 观察一次真实下载的 cwnd 与 send 速率对照。
3. 对一个 p=0.8 的任务画 Amdahl 表（n=2/8/32/∞），并计算"把 p 提到 0.95（n=8）"与"保持 p=0.8 加到 n=64"哪个收益大——用数字回答"先提 p 再加 n"。
4. 拆账实验：用 `curl -w` 的计时变量（`time_namelookup/time_connect/time_appconnect/time_starttransfer`）请求一个 HTTPS API，把总延迟切成 DNS/TCP/TLS/首字节四段，指出最大一段该用本章哪个工具箱（就近/复用/批量/缓存）。
5. 用 Little's Law 反推你手头一个服务的并发槽：取它的目标 QPS 与实测 P50 延迟（没有真实服务就用 5 节例二的数字），算稳态并发 L；再故意把"响应时间"换成 P99 重算一次，解释"按 P99 做 sizing"比"按平均"安全在哪。
6. 估算你常用的 7B 模型在 fp16 下的 KV cache 显存（每 token = 2×层数×上下文×头数×头维×2 字节；查模型 config 的 num_layers/num_heads/head_dim），算出 32K 上下文一张 24GB 卡能放几个并发会话——把 6 节的"缓存收益与预算"算成具体数字。
7. 给 3 节的下单算题补一问：若风控 RPC 需要两次调用（串行），总延迟变多少？若把两次调用合并成一次批量接口（1 个 RTT），又省多少？画出前后两条时间线（比例尺 10ms/格），标出"串行依赖"被消掉的部分。
