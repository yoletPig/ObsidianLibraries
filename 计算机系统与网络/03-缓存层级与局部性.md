# 03 - 缓存层级与局部性

## 本篇目标

- 建立存储金字塔的量级直觉：寄存器/L1/L2/L3/内存/SSD/网络的延迟数字表，并知道这些数字的来源与用法。
- 理解缓存的组织方式：64 字节缓存行、直接映射/组相联、写回与写通策略，能手工推演一次访存是否命中。
- 做两个决定性实验：行优先 vs 列优先遍历矩阵（实测 23 倍差距）、伪共享（实测 8 倍差距），把"局部性"从口号变成数字。
- 把缓存层级的结论接到模型推理上：解释"权重加载是带宽受限"这句话的算术。

前置：01 章（ISA 与内存层次的位置）；操作系统系列 04 篇（虚拟地址）有助理解，不强求。

## 1. 存储金字塔：一张必须刻进脑子的延迟表

CPU 快、内存慢，且差距每十年更糟一点——处理器-内存性能鸿沟（P&H 第 1 章"great idea: memory hierarchy"的出发点）。解法是用多级缓存把"热数据"搬到离计算单元越来越近的地方：

```
        ┌───────────────┐
        │   寄存器        │  ~0.3 ns（1 周期内，编译器直接命名访问）
      ┌─┴───────────────┴─┐
      │  L1 d/i 缓存 32~64KB │  ~1 ns（约 4 周期）
    ┌─┴─────────────────────┴─┐
    │  L2 缓存 256KB~2MB/核    │  ~4 ns（约 14 周期）
  ┌─┴───────────────────────────┴─┐
  │  L3 缓存 8~64MB（全核共享）      │  ~15~40 ns（约 40~100 周期）
┌─┴─────────────────────────────────┴─┐
│  主内存（DRAM）GB 级                  │  ~100 ns（约 300 周期！）
├──────────────────────────────────────┤
│  NVMe SSD                            │  ~20~100 µs（比内存慢千倍）
├──────────────────────────────────────┤
│  网络往返（同城 ~1ms / 跨洲 ~100ms+）  │  ~1e6~1e8 ns
└──────────────────────────────────────┘
```

数字的量级与出处：L1 约 4 周期、L2 约 12 周期、L3 约 40+ 周期、内存约 100ns 级，来自 Intel SDM Vol.3 第 11 章（缓存结构）与各家 Optimization Manual 的实测表；"1ns/L1、100ns/内存、SSD 微秒、跨洲 RTT 150ms"这组跨层数字来自 Jeff Dean 的著名清单《Latency Numbers Every Programmer Should Know》（2009，Dean/LAB；常以可视化卡片流传）。**注意看梯度**：L1→内存差 **两个数量级**，内存→网络差 **三到六个数量级**——这正是本篇与 06 章共享的底层逻辑：**每一层的"下一层"都贵得多，所以每一层的优化主题都是"少去下一层"**。

本机实测锚点（`lscpu | grep -i cache`）：

```
L1d cache:   384 KiB (8 instances)     # 8 个 P/E 核各 48KB
L1i cache:   256 KiB (8 instances)
L2 cache:    10 MiB (8 instances)      # 每核 1.25MB
L3 cache:    20 MiB (1 instance)       # 全核共享
```

## 2. 缓存行：64 字节是缓存世界的"原子"

CPU 与缓存之间**不以字节为单位搬运，而以缓存行（cache line）为单位**：x86-64 与绝大多数现代 CPU 是 **64 字节**（Intel SDM Vol.1 11.4；部分 ARM 服务器核是 128 字节——**ARM 注**：Apple M 系列与部分 ARMv8.5+ 核用 128B 行，写可移植代码时 `alignas(64)` 常改用 128 保险）。一次未命中，硬件把整个 64 字节搬进缓存——这是**空间局部性**被硬件直接兑现：你访问了 `a[0]`，`a[1]~a[15]`（int 数组）已经在缓存里等着了。

缓存的查找问题：内存地址 48 位，缓存只有几 MB，怎么知道"这个地址的数据在不在缓存里"？把地址切成三段（CSAPP 6.4）：

```
 48 位物理/虚拟地址：
 ┌─────────────┬──────────────┬─────────┐
 │   tag 标记   │  set index 组号│ offset  │
 │（高位，比对） │（中间，选组）   │（低 6 位）│
 └─────────────┴──────────────┴─────────┘
 查找流程：用 index 选中一组 → 组内每路并行比对 tag → 命中则按 offset 取字节
```

**直接映射**（每組 1 路）：每个内存块只能去唯一一组，规则简单、查找快，但**冲突缺失**致命——`a[0]` 与 `a[N]` 若 index 相同就永远互相踢，"打架"的数组轮流把对方赶出去。**组相联**（每組 N 路）：一组容纳 N 个候选，`a[0]` 与 `a[N]` 可以共存。现实配置是折中：**L1 通常 8 路 / L2 16 路 / L3 11~16 路**（Intel SDM Vol.3 表 11-x）。概念对照表（CSAPP 6.4.3）：

| 缺失类型 | 原因 | 典型场景 |
| --- | --- | --- |
| 冷缺失（compulsory） | 数据第一次被访问 | 程序启动 |
| 容量缺失（capacity） | 工作集 > 缓存容量 | 大矩阵遍历（本篇 5 节） |
| 冲突缺失（conflict） | index 打架但缓存未满 | 直接映射/低相联下的步长恰好是缓存大小倍数 |
| 一致性缺失（coherence） | 多核同步缓存行 | 伪共享（本篇 6 节） |

**写策略**：写命中时，**写回（write-back）**只改缓存、打上脏位（dirty），被逐出时才刷回内存——省带宽，是 CPU 缓存的标准做法；**写通（write-through）**每次写都同步到下级——简单、一致性好，用于个别场景（如某些 GPU L2 配置、网络网卡的描述符缓存）。写未命中时通常配合**写分配（write-allocate）**：先把行搬进来再改——所以"逐字节填充大数组"实际产生的是读+写双倍流量，这是 `memset` 比 `=` 快的部分原因（用非临时指令绕开分配是另一个高级话题）。

## 3. 缓存命中率的简化模型：AMAT

评估任何访存行为，用平均访存时间（AMAT）一个公式就够：

```
AMAT = T_hit + miss_rate × miss_penalty
```

直觉用量：L1 命中 4 周期，未命中去 L2 再花 14，AMAT = 4 + miss_rate×10；若 miss_rate 从 5% 降到 0.1%，AMAT 从 4.5 降到 4.01——**命中率在 90% 区间内的改善几乎无感，在 99%→99.9% 区间的改善决定生死**，因为 miss_penalty 是几十上百周期。这就是为什么性能工程系列里 cache-misses 计数器比"命中率百分比"更值得盯（perf stat 的 `LLC-load-misses` 直接对应 03 篇的方法论）。

**经验做法**：判断一段代码"该不该担心缓存"，先估算工作集大小——一次遍历接触的不重复字节数。工作集 ≪ L2（MB 级）：随便写都快；工作集 ≫ L3：访问模式决定一切（顺序流 vs 乱序跳跃，差距可达 5~10 倍）。5 节实验会验证。

## 4. 局部性：唯一需要背的缓存原则

- **时间局部性**：刚被访问的数据很快会再被访问（循环变量、热点对象）→ 缓存天然照顾。
- **空间局部性**：被访问地址附近的数据很快会被访问（顺序数组、结构体字段连用）→ 64B 行预取兑现。

由此推出代码层的三条铁律（CSAPP 6.2 "编程者能做的，就是写局部性好的代码"）：

1. **按内存布局顺序访问**（多维数组按最内层维度的步进方向遍历——C 是行优先，5 节实测）；
2. **内层循环紧凑、步长尽量为 1**（链表遍历的每个节点跳跃是空间局部性杀手）；
3. **热点数据结构紧凑**（把一起访问的字段放一起；`struct of arrays vs array of structs` 的取舍本质是"哪个维度有空间局部性"）。

现代硬件还在此之上叠了**硬件预取器**（检测顺序/固定步长流并提前搬运，Intel SDM Vol.1 11.5.4）——所以顺序流甚至能在内存延迟面前跑出接近 L3 的有效延迟；但**指针追逐（链表/树）没有稳定步长，预取器无能为力**，这就是为什么 B 树为缓存友好转成了 B+ 树+大节点（每节点恰好多页，配 OS 系列 08 篇）。

## 5. 实验：行优先 vs 列优先，实测 23 倍

```c
// loc2.c —— 同样的计算量，只换访问方向
#include <stdio.h>
#include <time.h>
#include <stdlib.h>
#define N 4096
static int *a;
double now(){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);return t.tv_sec+t.tv_nsec/1e9;}
int main(){
    a = malloc((size_t)N*N*sizeof(int));
    for(size_t i=0;i<(size_t)N*N;i++) a[i]=1;          // 防止全零被特殊对待
    volatile long s; double t0,t1;
    t0=now();
    s=0; for(int i=0;i<N;i++) for(int j=0;j<N;j++) s+=a[i*N+j];   // 行优先：j 内层连续
    t1=now(); printf("row-major: %.5f s (sum=%ld)\n", t1-t0, s);
    t0=now();
    s=0; for(int j=0;j<N;j++) for(int i=0;i<N;i++) s+=a[i*N+j];   // 列优先：i 内层步进 N*4B
    t1=now(); printf("col-major: %.5f s (sum=%ld)\n", t1-t0, s);
    return 0;
}
```

```bash
$ gcc -O2 loc2.c -o loc2 && ./loc2 && ./loc2
row-major: 0.00554 s (sum=16777216)
col-major: 0.12918 s (sum=16777216)
row-major: 0.00560 s (sum=16777216)
col-major: 0.13105 s (sum=16777216)
```

**同样的指令数、同样的数据量，23 倍差距。** 逐层解释（对照 2 节的三段式地址）：行优先时，内层 j 每次步进 4 字节，一行 4096×4B=16KB——正好逐行灌满缓存行，64 个元素才产生一次未命中，且硬件预取器能稳定预测这个流。列优先时，内层 i 每次步进 4096×4B=16KB——**每次访问都落在不同缓存行、不同页**，64 个元素分别占 64 行；总流量虽相同，但每次未命中都要等约 100ns 的内存延迟且预取器无法形成流，于是时间从"带宽限"变成"延迟限"。对 Python 学习者的映射：NumPy 里 `a[:, i]` 慢于 `a[i, :]`（默认 C 序）、`pandas.iterrows()` 慢于向量化，底层都是同一个行优先/列优先问题。

## 6. 实验：伪共享，多线程的性能隐形杀手

多核各自有 L1/L2，**缓存一致性协议（MESI）保证同一缓存行在多核间只有一份"已修改"副本**。于是出现反直觉现象：两个线程写两个**毫不相干**的变量，只要它们住在同一个 64 字节行里，这一行就在两核之间来回"弹跳"（每次写都要先把行拉到自己核上），像被共享了一样——**伪共享（false sharing）**（CSAPP 6.13 习题背景；Intel Optimization Manual 专门有一节）。

```c
// fs5.c —— 4 线程各写各的原子计数器，唯一区别是内存布局
#include <stdio.h>
#include <pthread.h>
#include <time.h>
#define NT 4
#define ITER 50000000L
double now(){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);return t.tv_sec+t.tv_nsec/1e9;}
struct packed { volatile long v[NT]; };                        // 4 个计数器挤一行
struct padded { volatile long v; long pad[7]; } __attribute__((aligned(64)));
static struct packed P;                                        // 全部在同一缓存行
static struct padded Q[NT];                                    // 每个独占一行
static void *wpack(void*p){long i=(long)p;for(long k=0;k<ITER;k++) __sync_fetch_and_add(&P.v[i],1);return 0;}
static void *wpad (void*p){long i=(long)p;for(long k=0;k<ITER;k++) __sync_fetch_and_add(&Q[i].v,1);return 0;}
int main(){ printf("packed line base: %p, padded[0]: %p, padded[1]: %p\n",
        (void*)&P, (void*)&Q[0], (void*)&Q[1]);
    double t0,t1; pthread_t t[NT];
    t0=now(); for(long i=0;i<NT;i++) pthread_create(&t[i],0,wpack,(void*)i);
    for(int i=0;i<NT;i++) pthread_join(t[i],0); t1=now();
    printf("4 atomic counters, same 64B line : %.3f s\n", t1-t0);
    t0=now(); for(long i=0;i<NT;i++) pthread_create(&t[i],0,wpad,(void*)i);
    for(int i=0;i<NT;i++) pthread_join(t[i],0); t1=now();
    printf("4 atomic counters, one line each : %.3f s\n", t1-t0);
    return 0;
}
```

```bash
$ gcc -O2 fs5.c -o fs5 -pthread && taskset -c 0-3 ./fs5
packed line base: 0x5fa161c36180, padded[0]: 0x5fa161c36080, padded[1]: 0x5fa161c360c0
4 atomic counters, same 64B line : 2.004 s
4 atomic counters, one line each : 0.248 s          # 8 倍！
```

（先核对布局：`padded[0]` 与 `padded[1]` 恰好差 0x40=64 字节——对齐生效，两组唯一的区别就是布局。）没有锁、没有竞态、逻辑完全独立，8 倍差距全部来自 MESI 弹跳。生产环境的惯犯：线程局部统计计数器数组（`stats[thread_id]`，连续排列）、一个结构体里相邻的"各线程写"字段、`std::atomic` 标志挨着数据。**经验做法**：多线程各自写的可变数据，一律 `alignas(64)`（C++）/`__attribute__((aligned(64)))`（C）隔离；Python 里 GIL 挡住了大部分，但 Cython/C 扩展与多进程共享内存（OS 系列 10 篇）时同坑。排查工具：`perf c2c`（性能工程系列 03 篇的延伸，WSL2 上 PMU 受限时不可用，真机可用）。

## 7. 为什么这决定模型推理速度

把 1~6 节的结论直接算到推理上（与模型性能优化系列 Stage 4/5 呼应）：

- **单 token 生成是带宽受限的**：7B 参数 fp16 ≈ 14GB 权重，每生成一个 token 都要把全部权重读一遍。本机内存带宽约 50GB/s（双通道 DDR4 量级），14GB/50GB/s ≈ **0.28 秒/token 是物理下限**——此时 GPU/CPU 算力大量闲置，卡在 1 节表里的"内存→计算单元"这一段。这解释了为什么"核更多"不等于"推理更快"（12 章从 RTT 角度再讲一遍）。
- **Batch 增大摊薄权重读取**：batch=32 时，同一遍权重读取服务 32 个请求，算术强度（每字节权重支撑的计算次数）提高 32 倍——吞吐暴涨而单 token 延迟几乎不变，这是 vLLM/SGLang Continuous Batching 收益的硬件根源（模型性能优化 Stage 5）。
- **KV cache 是 03 章思想的应用**：已生成 token 的 K/V 不再重算，本质是"时间局部性的人工兑现"；其显存占用随上下文线性增长，管理它就是 04 篇分页思想的 GPU 版（OS 系列 05 篇 ↔ PagedAttention）。
- **量化为什么有效**：fp16→int4 把权重流量砍 4 倍，带宽受限场景吞吐近乎线性提升——05 章讲数字表示后这个账会更清楚。

## 常见误区

1. **"L3 大 = 快"**：容量只是下限，访问模式才是主导。20MB L3 上乱序访问大数组照样比顺序流慢数倍（预取器失效）；看性能先看访问模式，再看容量。
2. **"加了缓存行对齐就一定更快"**：对齐隔离只对"多核各自频繁写"的字段有效；给只读数据加 padding 反而浪费缓存容量。先确认存在伪共享（性能特征：加线程反而变慢），再动手。
3. **"写通/写回只是名词"**：写回策略意味着"写内存"是异步的、按行批量刷的——这直接解释了 OS 系列 08 篇的页缓存回写行为（LRU+脏页批量刷盘）为什么长那样：CPU 缓存与页缓存是同一思想在两级硬件上的两次实现。
4. **"Python 里讨论缓存没意义"**：NumPy/pandas 的每一行向量化代码最终落在 C 的访存模式上；`for` 循环里逐元素 `df.iloc[i,j]` 与 `.values` 切片后整体算，差距常是 10~100 倍，其中很大一部分就是本篇的访存模式差异。
5. **"并行就能绕开内存墙"**：所有核共享同一条内存总线（和同一个 L3 的带宽）。8 核各自顺序读不同数组可能已经把带宽吃满，此时加核只增加排队——1 节表里的"内存 100ns"是所有核分摊的预算。

## 本篇小结

- 延迟梯度：L1 ~1ns → L2 ~4ns → L3 ~15-40ns → 内存 ~100ns → SSD 微秒级 → 网络毫秒级（Jeff Dean 数字表 / Intel SDM Vol.3）；每层的优化主题都是"少去下一层"。
- 64B 缓存行是搬运原子；地址切 tag/index/offset，直接映射有冲突缺失，组相联是现实折中；写回+写分配是 CPU 缓存标配。
- AMAT = T_hit + miss_rate × miss_penalty；命中率 99%→99.9% 的改善远大于 90%→95%——盯 miss 数而不是命中率。
- 局部性三条铁律：按布局顺序访问、内层步长为 1、热点数据紧凑；行优先 vs 列优先实测 23 倍，链表/树是预取器盲区。
- 伪共享：无关变量同住 64B 行 → MESI 弹跳，实测 8 倍；各线程独写数据用 aligned(64) 隔离（经验做法）。
- 推理速度的物理账：14GB 权重 / 50GB/s ≈ 0.28s/token 下限；batch 摊薄、KV cache 保时间局部性、量化砍流量——全是本篇三条原理的应用。

4. 写一个遍历 `int a[10000]` 的循环，分别用步长 1 和步长 16（`i+=16`），用 `perf stat -e cache-misses,instructions`（若 WSL2 不可用则用计时法）观察两条曲线，解释为什么步长 16 的总时间可能反而与步长 1 相近（提示：64B 行含 16 个 int）。
