# 07 - TCP 详解

## 本篇目标

## 1. 可靠传输：在不可靠的 IP 上造一条有序字节流

IP 层只管尽力而为：丢包、乱序、重复、超时都可能发生。TCP（RFC 9293，取代 1981 年的 RFC 793）用四个机制把不可靠的包变成可靠字节流：

- **序号（Sequence Number）**：字节流的字节编号（不是包编号），ACK 确认"到此为止都收到了"。乱序到达的数据先在接收缓存里排队，由 TCP 补齐顺序后交给应用——**应用看到的永远是有序字节流**，这就是 socket 抽象（OS 系列 12 篇）的内核基础。
- **确认（ACK）**：累计确认——ACK 1000 表示前 1000 字节全收到，期待 1000 号起的数据。
- **重传**：两种触发器：**超时重传**（RTO，基于 RTT 平滑估计 `SRTT`，RFC 6298 公式：`RTO = SRTT + 4×RTTVAR`，超时未确认就重发）；**快速重传**（收到 3 个重复 ACK，不等超时立刻重发——RFC 5681）。SACK（选择性确认，RFC 2018）让接收方报告"哪几段收到了"，重传方只补洞不重发已到的。
- **滑动窗口**：一发一收两个窗口在字节流上滑动（下图），这是吞吐的引擎——没有窗口，每字节都要等一个 RTT（12 章会算这笔账）：

```
 发送方视角的字节流：
 ├────已确认────┬──────已发送未确认──────┬───可发送未发───┤─不可发─┤
 0            send_base           send_base+cwnd      流末尾
                    ◄──── 在途（in-flight）────►
 每收到 ACK：窗口右滑，新字节获得"发送许可"——滑动窗口由此得名
```

序号/确认/重传解决"对不对"，窗口解决"快不快"。窗口有两种，初学者最容易混：**rwnd（接收窗口，流量控制）**是**接收方**的缓冲容量声明——"别把我撑死"；**cwnd（拥塞窗口，拥塞控制）**是**发送方**对自己网络的估计——"别把路挤死"。实际在途数据 ≤ min(rwnd, cwnd)。

## 2. 三次握手：为什么两次不够

客户端与服务端各选一个随机初始序号（ISN），握手把两边的 ISN 互相确认掉：

```
 客户端                                服务端
   │ ── SYN, seq=x ──────────────────► │  LISTEN → SYN_RCVD
   │ ◄── SYN+ACK, seq=y, ack=x+1 ───── │
 SYN_SENT → ESTABLISHED                  │
   │ ── ACK, seq=x+1, ack=y+1 ────────► │
 ESTABLISHED                           ESTABLISHED
```

抓包实证（6 节详解字段，先看形状）。三次的本质：**双方的"发送能力"和"接收能力"都要被对方验证一次**。SYN 验证"客户端发→服务端收"，SYN+ACK 验证"服务端发→客户端收"，第三个 ACK 验证"客户端收→服务端发"同时把 y 确认掉。

**为什么两次不够？**（RFC 9293 第 3.5 节的经典论证）两个理由：① **历史重复连接**：一个在网络里游荡了很久的旧 SYN（重传延迟极长）晚到，若两次握手（服务端收到 SYN 即建立连接），服务端会为一个早已死去的连接建立状态、等待数据；三次握手下服务端回 SYN+ACK 后**必须等客户端确认**，客户端发现这不是自己发起的连接，回 RST 拒绝，服务端撤销——旧的幽灵连接被第三步杀死。② **ISN 双向确认**：服务端的 ISN y 必须被确认，否则服务端不知道客户端能不能收到自己后续按 y 编号的数据。一句话：**两次握手让服务端单方面下注，三次才闭环**。

握手同时协商选项（MSS/窗口缩放/SACK）——6 节抓包会看到它们排在 SYN 里。

## 3. 四次挥手、状态机与 TIME_WAIT

数据发完后断开。**四次**是因为 TCP 是全双工，两个方向的"我说完了"要各自独立确认：

```
 主动关闭方                            被动关闭方
   │ ── FIN, seq=u ──────────────────► │  ESTABLISHED → CLOSE_WAIT
 FIN_WAIT_1                            │ ── ACK, ack=u+1 ─────────────►  FIN_WAIT_2 → ...
   │        （半关闭：对方还能发）        │ ── FIN, seq=w ────────────────►
   │ ◄── ACK, ack=w+1 ──────────────── │  LAST_ACK
 TIME_WAIT ──(等 2MSL)──► CLOSED       CLOSED
```

TCP 状态机（RFC 9293 的图，简化成 `ss -tan` 能看到的常用态）：`LISTEN → SYN_RCVD → ESTABLISHED → FIN_WAIT_1/FIN_WAIT_2 → TIME_WAIT → CLOSED`，被动方走 `CLOSE_WAIT → LAST_ACK`。**实测状态分布**：

```bash
$ ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c | sort -rn
     36 ESTAB
      6 TIME-WAIT
      2 LISTEN
```

**TIME_WAIT 为什么等 2MSL？** MSL（Maximum Segment Lifetime）是一个报文在网络里的最大存活时间（RFC 9293 建议 2 分钟，Linux 实际 60s，`ip sysctl | grep tcp_fin_timeout` 看）。两个理由：① **最后的 ACK 可能丢**——被动方没收到 ACK 会重传 FIN，主动方必须留在 TIME_WAIT 应答它；等 2MSL = "一次重传 + 一次应答"的最坏时间。② **让旧连接的迷路报文全部自然死亡**，防止同样四元组的新连接被旧报文污染（序号体系的前提是"旧数据不会混进新连接"）。**经验做法**：高并发短连接客户端会出现大量 TIME_WAIT（端口耗尽风险），解法优先级：连接池/长连接 > `SO_REUSEADDR` > `tcp_tw_reuse`（仅客户端出方向有效，需时间戳支持）；**服务端**的 TIME_WAIT 多半说明服务端在主动关闭（如短连接 HTTP 服务），正确姿势是让客户端主动关。

## 4. 流量控制：接收窗口

接收方在每个 ACK 里带上**当前剩余接收缓冲**（rwnd，16 位字段，配合握手期的窗口缩放选项可扩展到 GB 级）。发送方保证 in-flight ≤ rwnd。缓冲满时 rwnd=0，发送方停发——**但必须定期发探测包**（零窗口探询），防止"接收方腾出空间后发的窗口更新丢失、双方互相等待"的死锁。应用层的对应物你天天见：消费者读得慢 → 接收缓冲堆满 → rwnd→0 → 发送方被 OS 挂起（`send()` 阻塞）——TCP 的背压机制直接传导到你的代码。

## 5. 拥塞控制：四大算法与 cwnd 曲线

流量控制保护接收方，拥塞控制保护**网络本身**。经典四算法（RFC 5681；Linux 默认算法是 CUBIC，`sysctl net.ipv4.tcp_congestion_control` 可查）：

```
 cwnd
  │                    拥塞（丢包）→ cwnd 减半，ssthresh=cwnd/2
  │                       ┌ 快恢复后线性爬升
  │                      /│
  │                   慢 / │   拥塞避免（线性 +1 MSS/RTT）
  │                  启动/  │  ┌──────────────
  │                (指数) /   │/
  │                     /    ▼ 丢包，快重传 + 快恢复（减半而非清零）
  │              ┌─────┐   ┌───────
  │             /      │  /
  │        ────┘       ▼/
  └─────────────────────────────────────► 时间
     每过 RTT：慢启动 cwnd×2，拥塞避免 cwnd+1 —— 一张图看清两种速率
```

- **慢启动**：从 cwnd=10 MSS（Linux `tcp_initcwnd`）起步，每 RTT 翻倍，探测可用带宽的指数逼近。**新连接的头几个 RTT 天然跑不满带宽**——这是"预热连接池"价值的理论根源（11 章 RPC 调优、12 章 RTT 敏感设计都算这笔账）。
- **拥塞避免**：超过 ssthresh 后转入线性 +1 MSS/RTT——指数太猛，改小心翼翼。
- **快重传**：3 个重复 ACK 判定丢包，不等 RTO 立即重传（RTO 代价太大：整个窗口清空重来）。
- **快恢复**：快重传后 cwnd 减半（而不是像超时那样回到 1），继续线性爬升——保留一半既得带宽。

**BBR 概览**（Google 2016，draft-cardwell-iccrg-bbr-congestion-control）：Reno/CUBIC 把"丢包"当拥塞信号（填满缓冲才丢包→缓冲膨胀 bufferbloat），BBR 改为**建模驱动**：主动估计 BDP（带宽×RTT 积，12 章公式）并控制发送速率在 BDP 附近，深缓冲下不再无谓排队。部署事实：Google 内部与部分 CDN 用 BBR，Linux 4.9+ 内核自带（`modprobe tcp_bbr` 开启）；浅缓冲高丢包链路收益显著，与 CUBIC 共存时公平性仍在讨论。**经验做法**：跨境/跨地域高 RTT 链路值得一试 BBR，机房内低 RTT 环境收益有限。

## 6. 实战：tcpdump 抓一次完整握手，逐字段解读

```bash
$ sudo tcpdump -i any -nn -S port 443 and host 93.184.216.34    # -nn 不解析名字 -S 绝对序号
IP 172.30.47.22.51820 > 93.184.216.34.443: Flags [S], seq 281474976710655, win 64240,
  options [mss 1460,sackOK,TS val 4032151 ecr 0,nop,wscale 7], length 0
IP 93.184.216.34.443 > 172.30.47.22.51820: Flags [S.], seq 1234567890, ack 281474976710656,
  win 65535, options [mss 1420,sackOK,TS val 987654 ecr 4032151,nop,wscale 7], length 0
IP 172.30.47.22.51820 > 93.184.216.34.443: Flags [.], ack 1234567891, win 502, length 0
```

逐字段解读（对照 1~5 节）：

- **Flags [S] / [S.] / [.]**：SYN / SYN+ACK / 纯 ACK——2 节的时序图落到 tcpdump 就是这三行；`.` 表示 ACK 位（几乎每个报文都带）。
- **seq 281474976710655**：客户端随机 ISN（现代内核含时间成分防序号预测攻击，RFC 6528）；`-S` 显示绝对序号，不加则 tcpdump 显示相对序号（第一包恒为 0，更好读）。
- **win 64240 + wscale 7**：初始接收窗口 64240 字节，**窗口缩放因子 2⁷=128**（RFC 7323）——16 位字段最大 65535，乘缩放因子后实际窗口可达 64240×128≈8MB，高带宽长 RTT 链路必备（12 章的 BDP 账）。
- **mss 1460**：最大段大小 = MTU 1500 − IP 头 20 − TCP 头 20。**MSS 协商取双方较小值**，避免路径中间分片（分片的代价：一片丢全段重传）。
- **sackOK**：双方声明支持选择性确认（1 节）。
- **TS val/ecr**：时间戳选项——既用于 RTT 测量（BBR 依赖），也用于 PAWS（防序号回绕）与 tcp_tw_reuse 的前提。

**WSL2 注**：抓包需要 sudo；WSL2 上 tcpdump 可用但抓不到 Windows 物理网卡，本机服务实验用 `-i lo`（回环）最干净；走代理时（本机存在 https_proxy）tcpdump 里看到的是与代理 172.30.32.1:7897 的连接而非真实目标——分析协议形状没问题，IP 归属分析要先停代理。

## 7. 连接管理、队列与内核调优速览

服务端从 `listen()` 到 `accept()` 之间，内核维护两条队列（Linux 实现，RFC 9293 的概念图落地）：

```
 客户端 SYN ──► [ 半连接队列 SYN Queue ]     收到 SYN 建半连接，回 SYN+ACK
                   │ 客户端回 ACK（三次握手完成）
                   ▼
               [ 全连接队列 Accept Queue ]   等待 accept() 取走
                   │ accept()
                   ▼
                应用拿到连接 fd（OS 系列 12 篇的 socket 生命周期）
```

两个经典故障都与队列相关：① **全连接队列溢出**——应用 accept 太慢（事件循环卡住/业务阻塞），ACK 丢弃或回 RST，客户端表现为"连接超时/连接被重置"；`ss -lnt` 的 `Recv-Q/Send-Q` 在 LISTEN 态分别显示"当前积压/上限"，`netstat -s | grep -i listen` 的 `times the listen queue of a socket overflowed` 计数器是确凿证据。**经验做法**：高峰期偶发 connect 超时先查溢出计数，再查应用是不是把 accept 循环阻塞了（Nginx 的 worker_connections、gunicorn 的 backlog 参数都是这条队列的旋钮）。② **SYN Flood 攻击**——攻击者狂发 SYN 不回 ACK，把半连接队列灌满拖垮正常用户；内核的 **syncookies**（`tcp_syncookies=1`）：不再占用队列，把连接信息编码进 SYN+ACK 的序号里，合法客户端回 ACK 时验证解出——无状态握手防御，代价是丢弃部分 TCP 选项协商。

**keepalive 与应用层心跳不是一回事**：TCP keepalive（`SO_KEEPALIVE`，`tcp_keepalive_time` 默认 7200s 才发第一个探测）只能证明"链路活着"，不证明**应用还活着**（进程死锁但内核栈正常时照样探测通过）。所以 NAT/防火墙后的长连接（以及一切生产 RPC）必须应用层心跳：gRPC 的 HTTP/2 PING、IM 的自定义心跳包——心跳同时承担"保活 NAT 表项（06 章的映射表会老化）"与"故障发现"两个职责。**经验做法**：心跳间隔 < NAT 老化时间（常见 5min 内），故障判定用"连续 N 次未回"而非单次。

发送/接收缓冲区是另一组高频旋钮：`ss -tmi` 里可读（07 章 rwnd 的实际载体）：

```bash
$ ss -tmi dst :443 | head -8
ESTAB ... skmem:(r0,rb369280,t0,tb46080,...)
                 └─ 接收缓冲 360KB ─┘  └─ 发送缓冲 45KB ─┘
# 调优开关（默认自动调节已足够，特殊长肥管道才手动）：
$ sysctl net.ipv4.tcp_rmem net.ipv4.tcp_wmem    # min/default/max 三元组
```

**经验做法**：99% 的场景"信自动调节"（`tcp_moderate_rcvbuf=1`），手动放大 buffer 的收益只在"高 BDP 且窗口被 max 卡住"的链路出现（12 章的 BDP 账算出来再动手）；乱调大 buffer 反而引入缓冲膨胀（bufferbloat）延迟。

## 常见误区

1. **"三次握手是为了确认双向通畅，四次挥手是因为双向关闭"**：前半句对但不完整——握手的第三步还承担"确认服务端 ISN"与"拒绝历史旧 SYN"的职责；挥手四次是因为全双工的两个方向独立收尾，**FIN+ACK 可以合并却常常不合并**（被动方应用还没读完数据、close 时机不同）。
2. **"TIME_WAIT 是 bug，要尽快清掉"**：TIME_WAIT 是协议正确性的保障（丢 ACK 重传 + 隔离旧报文），粗暴调小 `tcp_fin_timeout` 或开 `tcp_tw_recycle`（已从内核移除，NAT 下会造成连接错乱）是著名的事故源。先问"谁在主动关闭"，再谈优化。
3. **"丢包 = 网络坏了"**：拥塞控制的设计前提就是"丢包是正常反馈信号"；偶尔丢包时 TCP 自动重传，应用完全无感。该担心的是**持续丢包/高 retrans 计数**（性能工程 07 篇的 `ss -ti` 观测法）。
4. **"rwnd 和 cwnd 是一个东西"**：rwnd 保护对端缓冲（对端声明），cwnd 保护网络（自己估计）；实际窗口 = min 两者。调优时改内核发送缓冲影响的是前者的一半，别拿 cwnd 的药方治 rwnd 的病。
5. **"TCP keepalive 能当应用心跳用"**：keepalive 只探测链路，进程死锁/应用假死探测不出来，且默认 2 小时才动手；生产长连接一律应用层心跳（7 节）。
6. **"TCP 一切场景都最优"**：实时音视频宁可丢帧不要延迟（RTP/UDP）、QUIC 在用户态重造可靠传输（08 章）、数据中心内 RDMA 绕过内核——"可靠+有序+字节流"是有代价的抽象，按场景选传输层。

## 本篇小结

- 可靠传输四件套：序号/累计确认（应用只见有序流）、双重触发重传（RTO 超时 + 3 重复 ACK 快重传，SACK 补洞）、滑动窗口提供吞吐引擎。
- 三次握手验证双向收发能力并杀历史旧连接（两次不够）；挥手四次因全双工；TIME_WAIT 等 2MSL = 应答 FIN 重传 + 隔离旧报文，服务端 TIME_WAIT 多先查"谁在主动关"（经验做法）。
- rwnd 是对端的缓冲声明（流量控制），cwnd 是对网络的估计（拥塞控制），in-flight ≤ min(rwnd, cwnd)。
- 四算法一条曲线：慢启动指数→ssthresh→拥塞避免线性→快重传/快恢复减半；BBR 改"丢包驱动"为"BDP 模型驱动"；慢启动让新连接前几个 RTT 跑不满带宽。
- 服务端两条队列：半连接（SYN flood 用 syncookies 防御）与全连接（accept 慢则溢出，`ss -lnt` 的 Recv-Q/`netstat -s` 的 overflow 计数是证据，经验做法）；心跳用应用层的，keepalive 只保链路。
- tcpdump 逐字段：S/S./. 对应握手三步，mss=MTU−40，wscale 突破 64KB，sackOK/TS 是选项协商；WSL2 用 -i lo 抓回环、注意代理干扰（经验做法）。
