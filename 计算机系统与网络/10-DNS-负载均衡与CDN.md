# 10 - DNS、负载均衡与 CDN

## 本篇目标

- 走通一次完整的 DNS 解析（递归 vs 迭代），把"浏览器输入域名到拿到 IP"画成时序图并说清每一步。
- 认全 A/AAAA/CNAME/TXT/NS/TTL 等记录类型，用 dig 实测读懂答案区的每一行。
- 分清负载均衡的三个层次：DNS 轮询/GSLB、四层（LVS）、七层（Nginx），以及健康检查与会话保持的常见做法。
- 理解 CDN 的边缘缓存/回源/命中率模型，并用 Anycast 解释"大模型 API 为什么就近接入"。

前置：06 章（IP 与路由）；07/08 章（TCP/HTTP）在负载均衡处引用。

## 1. DNS：分布式数据库的设计课

DNS（Domain Name System，RFC 1034/1035）解决"人记不住 IP"的问题，但它的真正价值是**一个可扩展分布式系统的教科书实现**：分层命名空间（host → domain → TLD → root）、分散权威（每个域自己管自己的记录）、逐层缓存（解析器与浏览器/OS 各层都有缓存）、最终一致性（TTL 控制变更生效时间）。你后面学分布式系统时的"分区+复制+缓存+TTL"，DNS 全都先示范过一遍。

域名层级自右向左：`www.example.com.` 末尾的 `.` 是根，`com` 是顶级域（TLD），`example.com` 是权威域，`www` 是主机记录。每一级的 NS 记录指向"谁掌管这一级的下一级"。

## 2. 解析全流程：递归 vs 迭代

两种角色先分清：**递归解析器**（resolver，替你跑完全程的那种——运营商 DNS、`8.8.8.8`、你 WSL2 里的 `172.30.32.1`）与**权威服务器**（authoritative，真正持有某域记录的——`ns1.a.shifen.com` 掌管 baidu.com）。"递归"指解析器对客户端承诺查到为止；"迭代"指解析器对权威服务器逐步问路：

```
 浏览器/OS 缓存？ ──有──► 直接用（未到 TTL）
      │无
      ▼
 [1] 客户端 ──递归查询──► 本地解析器 172.30.32.1（本机 /etc/resolv.conf 实测值）
      │                     │ 缓存有？有则直接回
      │                     │无，迭代查询：
      │                     ├──► 根服务器："谁管 com？" → 返回 com 的 NS 列表
      │                     ├──► com TLD 服务器："谁管 example.com？" → 返回其 NS
      │                     └──► example.com 权威服务器："www 的 A 记录？" → 93.184.216.34
      │◄── 答案 + TTL（解析器缓存一份）────┘
      ▼
 [2] 拿到 IP，开始 TCP/TLS（07/09 章）
```

**递归 vs 迭代**一句话：客户端→解析器是递归（"帮我查到底"），解析器→各级权威是迭代（"一步步问路"）。**缓存生效于每一层**：浏览器缓存→OS 缓存（Linux 无系统级 DNS 缓存，靠 nscd/systemd-resolved）→解析器缓存→各级响应里的 TTL 决定存多久。所以你改了一条 DNS 记录，全球生效要等**最长的未过期 TTL**——生产变更先把 TTL 调短再改，是标准做法（**经验做法**）。

## 3. 记录类型与 dig 实测

| 类型 | 含义 | 典型用法 |
| --- | --- | --- |
| A / AAAA | 域名→IPv4 / IPv6 | 基本盘 |
| CNAME | 域名→域名（别名） | CDN 接入、统一入口 |
| TXT | 任意文本 | 域名验证、SPF/DKIM 反垃圾邮件 |
| NS | 本域的权威服务器 | 委派 |
| MX | 邮件交换 | 邮件路由 |
| SOA | 域的元数据（主从、序列号、TTL） | 区域传输/调试 |

```bash
$ dig +noall +answer www.baidu.com
www.baidu.com.      0   IN  CNAME  www.a.shifen.com.
www.a.shifen.com.   0   IN  A      111.45.11.5
www.a.shifen.com.   0   IN  A      183.240.99.224
```

逐列读：`www.baidu.com` 先是 **CNAME 指向 `www.a.shifen.com`**（百度的 CDN/调度名），再解析出**两个 A 记录**——这就是最朴素的 DNS 负载均衡：一个域名吐多 IP，客户端选一个。TTL 为 0 表示权威服务器要求"不许缓存"（调度器要实时控制流量，10 分钟后再查可能给你完全不同的一组 IP——因为它是按你**来源 IP 的地理位置**返回的，这就是 5 节的 GSLB）。

**dig +trace 实测**（复现 2 节的迭代全程；WSL2 注：若运营商拦截 UDP 53 的转发，+trace 可能卡在某一步，改用公共解析器 `dig @223.5.5.5` 对照）：

```bash
$ dig +trace www.example.com | tail -20
.            518400  IN  NS  a.root-servers.net.        ← 根的 NS 名单
;; Received 1093 bytes from 172.30.32.1#53(172.30.32.1) in 0 ms
com.           172800 IN NS a.gtld-servers.net.         ← 问根：com 由谁管
;; Received 1169 bytes from 198.41.0.4#53(a.root-servers.net) in 60 ms
example.com.   172800 IN NS a.iana-servers.net.         ← 问 TLD：example 由谁管
;; Received 865 bytes from 192.5.6.30#53(a.gtld-servers.net) in 150 ms
www.example.com. 86400 IN A 93.184.216.34              ← 问权威：答案！
;; Received 87 bytes from 199.43.135.53#53(a.iana-servers.net) in 80 ms
```

每一段 dig 输出自动展示"上一级告诉我的下一级 NS"，与 2 节时序图一一对上。**经验做法**：`dig +trace` 是排查"我改了 DNS 为什么没生效"的第一工具——它能看出卡在哪一级（本地缓存？TLD？还是权威记录本身）；日常快速验证用 `dig @8.8.8.8 +short 域名` 直接问指定解析器。

**亲手看一次 DNS 报文**（DNS 是明文 UDP 53，2 节的全部概念都能在字节里指认）：

```bash
$ sudo tcpdump -i any -nn port 53 &      # 终端 A 抓包
$ dig @172.30.32.1 www.qq.com +short     # 终端 B 触发查询
IP 172.30.47.22.51234 > 172.30.32.1.53: 40213+ A? www.qq.com. (30)
IP 172.30.32.1.53 > 172.30.47.22.51234: 40213* 3/0/0 CNAME ..., A 120.233.51.33, A ... (117)
     └ 事务号 40213 匹配请求响应 ┘ └ flags: qr/rd/ra、答案 3 条 ┘
```

要点：**事务 ID（40213）**配对请求与响应（DNS 劫持攻击就是抢答伪造的 ID）；`A?` 是问题段；`3/0/0` = 3 条答案/0 权威/0 附加。因为明文，运营商可以插广告（历史真实案例），于是有了 **DoH/DoT**（DNS over HTTPS/TLS，RFC 8484/7858）把查询塞进加密信道——浏览器已默认启用 DoH，本系列抓包实验若"抓不到 53 端口流量"多半是浏览器走了 DoH（**WSL2 注**：curl/系统解析仍走 53，不影响实验）。

## 4. DNS 在负载均衡中的角色：GSLB 与权重

DNS 天然是"流量入口的第一级调度器"：

- **多 A 记录轮询**：一个域名多个 IP，简单分散流量；缺点是不知道各 IP 的健康/负载，且 DNS 缓存让摘除慢。
- **GSLB（全局服务器负载均衡）/地理 DNS**：权威服务器按**查询来源 IP**（或 EDNS Client Subnet 传来的用户网段）返回就近机房 IP——3 节里 baidu 的 shifen 调度就是它。分运营商（电信用户回电信机房）与分地域（北美用户回美西）两种粒度。
- **权重调度**：同名多 IP 配不同权重做灰度/机房导流；配合短 TTL 做故障切换（TTL 30s 意味着最坏 30s+客户端缓存延迟生效）。

一个把这些旋钮串起来的故障切换算题（面试常考的"机房挂了多久切走"）：假设 A 机房宕机，你的 DNS 权威记录 TTL=60s、故障检测+记录变更耗时 30s，客户端解析器缓存还剩最长 60s——**最坏 60+30+60=150s 后流量才完全离开故障机房**；如果前面还有 CDN/网关层自己的 DNS 缓存与 keep-alive 长连接（07 章的已建连接不会因 DNS 变化而断），恢复时间还要再叠加。这组数字解释了两件事：为什么关键服务要在 LB 层（秒级健康检查摘除，5 节）而不是 DNS 层做故障切换；为什么"改 DNS"永远是最后手段而非第一反应。

DNS 调度的局限（记住这三条，架构讨论不吃亏）：**粒度粗**（不知道每台服务器实时负载）、**生效慢**（缓存 TTL，客户端还会无视 TTL 自行缓存）、**看不见 TCP 层**（返回了 IP 不代表连接会成功）。所以生产架构里 DNS 只做"粗调度"，细活交给 5 节的 LB 层。

## 5. 四层 vs 七层负载均衡：LVS 与 Nginx

| 维度 | 四层（L4，传输层） | 七层（L7，应用层） |
| --- | --- | --- |
| 决策依据 | IP + 端口（不看内容） | HTTP 路径/Host/Cookie/头 |
| 代表实现 | LVS（Linux 内核 IPVS，章文嵩 1998）、云 SLB 的四层监听 | Nginx/HAProxy、云 SLB 的 HTTP 监听 |
| 性能 | 极高（内核态/NAT 或 DR 模式，单机千万级 PPS） | 高但需解析协议（万级~十万级 QPS/节点） |
| 能力 | 只能转发 | 改写/压缩/限流/灰度/会话保持/压缩 |
| 典型位置 | 入口第一跳（扛流量） | L4 之后（做业务路由） |

LVS 的三种转发模式一句话区分：**NAT**（改写 IP 转发，进出都经过 LB，瓶颈在 LB）、**DR**（直接路由：LB 只改 MAC，真实服务器直接回客户端，出流量绕开 LB，性能最好）、**TUN**（IP 隧道，跨机房可用）。三种模式的取舍本质是"谁改写哪层地址"（对照 06 章：NAT 动 IP+端口、DR 只动 MAC、TUN 加一层 IP 头）——回包路径决定性能上限，DR/TUN 让回包绕开 LB，代价是后端机必须配置 VIP 且抑制 ARP（经典运维考点）。DR 模式的回包路径（为什么性能好）：

```
 客户端 ──► LB(只改目的MAC) ──► 真实服务器( seeing 目的IP=VIP，处理)
                                      │
        客户端 ◄──────────────────────┘ 直接回包，不经过 LB
                     ▲ 出方向流量完全不占 LB 带宽 —— LB 只剩"进方向"压力
```

大型站点标准拓扑：**DNS/GSLB（粗）→ L4/LVS（扛量）→ L7/Nginx（精细路由）→ 服务集群**，每层各管一段。为什么有了 L7 还要 L4？——SSL 卸载、抗 SYN flood、把百万级连接先在四层摊开，七层节点就不用扛原始洪流。

**健康检查**：L7 用 HTTP 探针（GET /healthz 返回 200 才算活，可深查依赖）；L4 用 TCP 探测（能建连就算活，浅但快）。摘除节奏与探测周期/连续失败阈值相关——**经验做法**：健康检查超时+阈值 ≈ 5~15s 完成摘除，低于这个值要么误摘（抖动）要么摘太慢（用户踩雷）。

**会话保持**（同一个用户总打到同一台后端）：① **源 IP 哈希**——简单，但 06 章 NAT 的坑在此引爆：同一出口 IP 后的成百上千用户全部挤到同一台后端（负载失衡）；② **Cookie 插入**——LB 往响应塞一个会话 cookie，下次请求带上就回同一台（准确但依赖应用层）；③ **一致性哈希**——扩缩容时只迁移少量会话（分布式缓存的标配思想）。LLM 网关的会话粘性还有个特殊需求：KV cache 在哪台实例上，后续请求最好也去哪台（重算 KV 的代价远大于转发），这是 12 章预取/亲和性话题的服务端版本。

## 6. CDN：把内容搬到离用户 10ms 的地方

**原理一句话**：在各地边缘节点（POP，Point of Presence）缓存源站内容的副本，用户请求被 DNS/GSLB 调度到最近边缘，未命中再**回源**（回 origin 拉取）。静态资源（图片/JS/CSS/模型权重分发）命中率是生命线：

```
 命中率 H 与源站压力：源站流量 = 总流量 × (1-H)
 H=0.95 → 源站只需扛 5% 的请求；
 回源请求的带宽/延迟成本远高于边缘命中（跨骨干网 RTT）
```

CDN 的三板斧：① **缓存**（按 Cache-Control/ETag 语义，08 章的规则在边缘执行）；② **回源合并**（同一文件的并发未命中只回源一次，其他等待——request coalescing）；③ **预取/预热**（大活动前主动把内容推到边缘）。动态内容不走缓存但可走**动态加速**（边缘与源站间走优化的私有骨干线路，绕开公网拥塞——本质是把 06 章的"路径质量"问题用工程手段解决）。模型分发的现实案例：Hugging Face 的模型文件走 CDN 分发，国内镜像站本质是"自建回源 CDN"。

**缓存键（Cache Key）与命中率**：CDN 判定"同一个请求"依据的是缓存键——默认通常是"域名+完整 URL"（忽略大部分查询串之外的头/cookie；可配置）。两个工程后果：① URL 上带随机参数（时间戳、签名 nonce）会把同一资源炸成无数个键，命中率归零——**经验做法**：静态资源 URL 参数只保留真正影响内容的（版本号），监控/营销参数走 cookie 或前端埋点；② 不同用户差异化内容（登录态个性化页面）要么干脆 no-cache，要么按"缓存键变体"（Vary 头，08 章）拆分。观察一张 CDN 命中与否的免费探针（**经验做法**）：

```bash
$ curl -sI https://some-cdn.example/app.js | grep -iE 'cache|x-cache|age|cf-'
X-Cache: HIT            # HIT=边缘命中 / MISS=回源 / BYPASS=策略跳过
Age: 84231              # 副本已在边缘存活 84231 秒
CF-Cache-Status: HIT    # Cloudflare 系的同类字段
```

再往下是**边缘计算**（Cloudflare Workers、边缘函数）：把 JS/WASM 推到边缘节点执行，"计算也就近"——适合鉴权、A/B、重写这类轻逻辑，不适合重计算（边缘机器贵且少）。CDN 的演进方向一句话：从"缓存的仓库"走向"分布式计算的终端"。

## 7. Anycast：一个 IP，全球多站点

普通单播（unicast）：一个 IP 一台机器。**Anycast**：同一个 IP 从**多个地理位置**的站点同时向 BGP 宣告（06 章 BGP 的实际应用），路由协议自动把用户的连接送**网络拓扑上最近**的那个站点：

```
 用户 A（上海）──┐
                ├── 同一 IP 203.0.113.7 ──► BGP 路由表选择"最短 AS 路径"
 用户 B（柏林）──┘          → A 到亚洲站点，B 到欧洲站点（无 DNS 参与的理由）
```

为什么大模型 API（OpenAI/Anthropic 及国内厂商）都在用 Anycast：① **TCP 就近终结**——三次握手与 TLS 握手（07/09 章）都发生在用户与**最近边缘**之间，RTT 从 150ms 降到 20ms，握手延迟立减一个量级；② **故障切换自动**——某站点宕机撤回宣告，BGP 自动改路，无需 DNS TTL 等待；③ **抗 DDoS**——攻击流量被 BGP 分散到全球各站点吸收。代价：站点间无状态共享（连接只属于某站点）、排障时"同一个 IP 各地看到不同行为"。Anycast 与 GSLB 的分工：Anycast 靠路由就近（网络层最优，可能非地理最优），GSLB 靠 DNS 调度（可控粒度细）；大型服务常两者混用。

## 常见误区

1. **"ping 域名得到的 IP 就是服务器 IP"**：那是调度链的产物（GSLB/CDN/Anycast 决定的边缘节点）；同一域名不同地区解析结果不同（3 节 baidu 实测两 IP 即是），拿它做白名单/防火墙规则会翻车。
2. **"改了 DNS 立即生效"**：生效时间 = 旧记录剩余 TTL + 各级缓存（本地解析器可能无视短 TTL 强缓存）；变更前调低 TTL 是唯一可控手段（**经验做法**：提前 24h 把 TTL 调到 60s）。
3. **"负载均衡 = Nginx"**：Nginx 只是七层一员；流量入口的完整层次是 DNS→L4→L7，每层解决不同问题（扛量 vs 精细路由）。面试题"如何设计支撑 10 万 QPS 的入口"要按层次答，不要只报菜名。
4. **"源 IP 哈希就能做会话保持"**：NAT 环境下同源 IP = 一群用户（06 章），哈希后负载严重倾斜；且后端扩缩容会重排哈希。要粘性选 cookie 或一致性哈希。
5. **"CDN 只能加速静态内容"**：动态加速（私有骨干）、API 边缘化（边缘函数）、安全防护（边缘 WAF/DDoS 清洗）都是 CDN 现代业务；"是否可缓存"只是它的一条特性轴。

## 本篇小结

- DNS 是分布式系统范本：分层命名+权威分散+逐层缓存+TTL 一致性；递归（客户端↔解析器）与迭代（解析器↔权威）是两种承诺。
- dig 实测：CNAME→A 链（baidu/shifen）、多 A 记录即朴素 LB、TTL 0=不许缓存；+trace 逐级复现"根→TLD→权威"问路；tcpdump 看 UDP 53 明文报文（事务 ID 配对请求响应），DoH/DoT 是明文的解药。
- DNS 调度粗而慢（无实时负载、缓存延迟、不知 TCP 层），只做第一级：GSLB 地理调度 + 权重灰度；细活交给 LB 层。
- L4（LVS：NAT/DR/TUN 三模式的取舍在"谁改写哪层地址"，IP+端口、内核态扛量）与 L7（Nginx，解析 HTTP 做业务路由）互补成标准拓扑；健康检查 5-15s 摘除（经验做法）；会话保持慎用源 IP 哈希（NAT 坑），优选 cookie/一致性哈希。
- CDN 三板斧：边缘缓存（源站压力 = (1-H)）、回源合并、预热；缓存键设计决定命中率（随机参数毁一切，经验做法）；动态内容走私有骨干加速。
- Anycast：同一 IP 多地 BGP 宣告，TCP/TLS 就近终结 + 自动故障切换 + 抗 DDoS；大模型 API 用它把握手 RTT 从跨洲降到同城量级。

## 练习

1. 用 `dig +trace qq.com`（或 baidu.com）截取"根→TLD→权威"三段输出，画出与 2 节对应的时序图，标出每一步问的是哪一级服务器、返回的是什么类型记录。
2. 解释 3 节实测里 `www.baidu.com` 的 TTL 为什么是 0，结合 4 节 GSLB 原理说明"如果 TTL 是 86400 会出什么问题"。
3. 用 `dig @223.5.5.5 +short your-domain` 与 `dig @8.8.8.8 +short your-domain` 对比同一域名在两个解析器的答案差异（若你有自己的域名）；没有则对 `www.qq.com` 在两地 VPN/不同网络环境下试，体会地理调度的存在。
4. 设计题：一个全球 LLM API 服务，要求"用户连接延迟 < 50ms、单站点故障 1 分钟内切换、支持按机房灰度"。给出 DNS/GSLB、Anycast、L4/L7 各自承担的职责与切换时限估算（提示：Anycast 撤宣告 vs DNS TTL）。
5. 在本机跑 `sudo tcpdump -nn port 53 &` 然后 `curl -s http://www.qq.com -o /dev/null`，抓到 DNS 查询报文：抄出事务 ID、问题段与答案条数（A? 与 3/0/0 形状），对照 3 节的 dig 结果验证一致性；再让浏览器访问同一域名，观察 53 端口是否安静（DoH 已接管？）。
6. 任选一个你常用的 CDN 站点，`curl -sI` 连续请求同一静态资源 3 次，读出 X-Cache/CF-Cache-Status/Age 的变化（MISS→HIT、Age 递增），写两句话解释这次"回源→命中"的过程。
