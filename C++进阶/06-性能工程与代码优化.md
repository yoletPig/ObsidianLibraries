## 1. 编译器优化清单与验证手段

GCC/Clang 在 `-O2` 常开的优化里，对日常代码影响最大的四个：

| 优化 | 做什么 | 怎么验证 |
| --- | --- | --- |
| 内联（inlining） | 函数体替换调用，解锁后续一切跨函数优化 | Godbolt 看调用指令是否消失；`-finline-functions`（-O3 自动） |
| LICM（循环不变量外提） | 把循环内不变的计算搬到循环外 | `-fopt-info-all` 或看汇编位置 |
| 自动向量化 | 循环变 SIMD（第 03 章详述） | `-fopt-info-vec-optimized` |
| 死代码消除（DCE） | 删除无副作用计算 | 本章第 2 节的"0.0001 ms 惨案" |

**Godbolt（godbolt.org）是读懂优化器的第一工具**：左边贴代码右边出汇编，切换 `-O0/-O2/-O3` 与编译器版本，看 `call` 消失（内联）、`vaddps` 出现（向量化）。示例——一个 4 行函数在 `-O0` 下是 30 行汇编 + 3 次 `call`，`-O2` 后被整体折叠成一条 `ret`（常量折叠 + 内联）；这种"眼见为实"比任何文档都快。

`-fopt-info` 家族（GCC）：

```bash
g++ -O3 -fopt-info-vec-optimized -c foo.cpp    # 只报告成功的向量化
g++ -O3 -fopt-info-vec-missed     -c foo.cpp   # 只报告失败与原因（第 03 章见过）
g++ -O3 -fopt-info-all           -c foo.cpp   # 全部优化动作（内联、外提……）
```

输出直接指到行号与原因，例如 `foo.cpp:12:9: optimized: loop vectorized (80.0%)`；missed 信息甚至会说 `not vectorized: unsuitable data stride`。**把 missed 报告当 TODO 清单读**是编译器优化的最短学习路径（经验做法）。

## 2. 防止优化掉基准代码：DoNotOptimize 规范写法

先看一个真实事故——第 05 章 spin 基准的初版里有一个纯递增循环：

```cpp
long c = 0;
for (long i = 0; i < 10'000'000; ++i) ++c;    // 本想测 1000 万次递增
return c;
```

实测输出是 **0.0001 ms**——优化器把整个循环折叠成 `c = 10'000'000`（常量折叠），我们测到的是"函数调用开销"。基准代码的第一铁律：**被测计算必须有可观察的副作用**。规范写法（Google Benchmark 的 `DoNotOptimize` 同款）：

```cpp
// donotopt.cpp
#include <chrono>
#include <cstdint>
#include <iostream>

// 1) 阻止结果被丢弃：把值通过内联汇编"交给"编译器看不见的地方
template <typename T>
inline void DoNotOptimize(T const& value) {
    asm volatile("" : : "r,m"(value) : "memory");
}
// 2) 阻止"循环体没被改过所以不用重算"：标记内存可能被外部改动
template <typename T>
inline void ClobberMemory() {
    asm volatile("" : : : "memory");
}

int main() {
    volatile long sink = 0;                        // 也可以用 volatile 落点
    auto t0 = std::chrono::steady_clock::now();
    long c = 0;
    for (long i = 0; i < 10'000'000; ++i) c += i;
    auto t1 = std::chrono::steady_clock::now();
    DoNotOptimize(c);                              // 结果被"消费"，循环不能删
    sink += c;
    std::cout << "1 亿次累加: "
              << std::chrono::duration<double, std::milli>(t1 - t0).count() << " ms\n";
}
```

```bash
g++ -std=c++20 -O2 donotopt.cpp -o donotopt && ./donotopt
# 输出：1 亿次累加: 3.87731 ms
```

三条防线（经验做法）：输入用 `DoNotOptimize` 递给被测函数（防止常量折叠）；结果 `DoNotOptimize` 或写进 `volatile`/全局；被测循环内有函数调用时，让函数定义对优化器不可见（单独编译单元 / `noinline`）。严肃基准直接用 Google Benchmark 或 nanobench，它们的计时统计（中位数、误差、循环展开控制）比自己写靠谱得多。

## 3. 数据布局优化：SoA vs AoS 实测

缓存行 64 字节（《计算机系统与网络》03）。遍历 400 万个粒子、只更新 `x/y` 两个分量：

```cpp
// soa.cpp —— AoS（数组结构体）vs SoA（结构体数组）
#include <chrono>
#include <iostream>
#include <vector>

struct ParticleAoS { float x, y, z, vx, vy, vz; float pad[10]; };   // 64B/粒子，只用到 1/3 字段
struct ParticlesSoA {
    std::vector<float> x, y, z, vx, vy, vz;
    explicit ParticlesSoA(size_t n) : x(n), y(n), z(n), vx(n), vy(n), vz(n) {}
};

int main() {
    const size_t N = 1 << 22;                       // 4M 粒子
    std::vector<ParticleAoS> aos(N);
    ParticlesSoA soa(N);
    for (size_t i = 0; i < N; ++i) { aos[i].vx = soa.vx[i] = 1.0f * i; aos[i].vy = soa.vy[i] = 0.5f; }
    using clk = std::chrono::steady_clock;
    auto t0 = clk::now();
    for (size_t i = 0; i < N; ++i) { aos[i].x += aos[i].vx * 0.016f; aos[i].y += aos[i].vy * 0.016f; }
    auto t1 = clk::now();
    for (size_t i = 0; i < N; ++i) { soa.x[i] += soa.vx[i] * 0.016f; soa.y[i] += soa.vy[i] * 0.016f; }
    auto t2 = clk::now();
    std::cout << "AoS 更新两分量: " << std::chrono::duration<double, std::milli>(t1 - t0).count() << " ms\n";
    std::cout << "SoA 更新两分量: " << std::chrono::duration<double, std::milli>(t2 - t1).count() << " ms\n";
}
```

```bash
g++ -std=c++20 -O2 soa.cpp -o soa && ./soa && ./soa
# 输出（i5-12600K 实测两次）：
# AoS 更新两分量: 16.133 ms
# SoA 更新两分量: 3.0885 ms
# AoS 更新两分量: 17.376 ms
# SoA 更新两分量: 3.0818 ms
```

**5 倍差距**，来自两个叠加效应：AoS 每粒子 64 字节而只用 16 字节，带宽与缓存利用率打 25 折；SoA 的连续 float 数组还能被自动向量化（`-fopt-info` 会告诉你 AoS 版没向量化）。SoA 的代价是"一个实体的字段散在各数组"——增删实体要同步搬多个数组。决策口诀（经验做法）：**整批遍历同字段 → SoA；总是整体访问单个实体 → AoS；两者都要 → AoS 里再做热/冷字段分离**（高频字段排前面、低频大字段挪到旁路数组或指针）。

## 4. 减少虚函数开销：final、devirtualization 与 variant 分派

虚调用本身不贵（一次间接跳转，几周期），贵的三件事是：**阻碍内联**（后续优化全灭）、**分支预测失败**（目标频繁变化时）、**指针追逐**（对象散布堆上，每跳一页缓存）。

**第一层：给 devirtualization 创造条件。** 编译器看到静态类型确定或 `final` 时，虚调用被直接改成直调/内联：

```cpp
struct Base  { virtual double area() const; virtual ~Base() = default; };
struct Circle final : Base {          // final：没有进一步派生 → 编译器可去虚化
    double r;
    double area() const override { return 3.141592653589 * r * r; }
};
double f(const Circle& c) { return c.area(); }   // Circle 是 final：直接内联，无虚表查找
```

**第二层：`std::variant` 闭集分派。** 类型集合在编译期已知（AST 节点、指令类型、推理引擎的算子闭集）时，`variant` 把"虚表 + 指针追逐"换成"连续内存 + switch"。但要诚实：**分支可预测时两者接近**——先看"对象连续 vs 散布"的真实对比：

```cpp
// varv.cpp —— variant（连续存储） vs 虚函数（指针乱序，模拟真实堆布局）
#include <algorithm>
#include <chrono>
#include <iostream>
#include <memory>
#include <numeric>
#include <random>
#include <variant>
#include <vector>

struct Circle { double r; };
struct Rect   { double w, h; double pad; };

struct ShapeV { virtual double area() const = 0; virtual ~ShapeV() = default; };
struct CircleV final : ShapeV { double r; explicit CircleV(double rr):r(rr){}
                               double area() const override { return 3.141592653589*r*r; } };
struct RectV   final : ShapeV { double w, h; explicit RectV(double ww,double hh):w(ww),h(hh){}
                               double area() const override { return w*h; } };

int main() {
    const int N = 10'000'000;
    std::vector<std::variant<Circle, Rect>> vs; vs.reserve(N);      // 连续：每个 32B
    std::vector<std::unique_ptr<ShapeV>>     vp; vp.reserve(N);     // 每元素一个堆对象
    for (int i = 0; i < N; ++i) {
        if (i % 2) { vs.emplace_back(Circle{1.0}); vp.push_back(std::make_unique<CircleV>(1.0)); }
        else       { vs.emplace_back(Rect{2.0,3.0,0}); vp.push_back(std::make_unique<RectV>(2.0,3.0)); }
    }
    {   // 打乱 unique_ptr 的指向顺序：模拟对象散布在堆各处
        std::vector<int> order(N); std::iota(order.begin(), order.end(), 0);
        std::mt19937 g(42); std::shuffle(order.begin(), order.end(), g);
        std::vector<std::unique_ptr<ShapeV>> shuffled(N);
        for (int i = 0; i < N; ++i) shuffled[i] = std::move(vp[order[i]]);
        vp = std::move(shuffled);
    }
    using clk = std::chrono::steady_clock;
    double s1 = 0, s2 = 0;
    auto t0 = clk::now();
    for (auto& v : vs) s1 += std::visit([](const auto& s) {
        using T = std::decay_t<decltype(s)>;
        if constexpr (std::is_same_v<T, Circle>) return 3.141592653589*s.r*s.r;
        else return s.w*s.h;
    }, v);
    auto t1 = clk::now();
    for (auto& p : vp) s2 += p->area();
    auto t2 = clk::now();
    std::cout << "variant(连续存储): " << std::chrono::duration<double,std::milli>(t1-t0).count() << " ms\n";
    std::cout << "虚函数(指针乱序)  : " << std::chrono::duration<double,std::milli>(t2-t1).count() << " ms\n";
}
```

```bash
g++ -std=c++20 -O2 varv.cpp -o varv && ./varv && ./varv
# 输出（i5-12600K 实测两次）：
# variant(连续存储): 23.7626 ms
# 虚函数(指针乱序)  : 191.662 ms
# variant(连续存储): 23.825 ms
# 虚函数(指针乱序)  : 192.056 ms
```

**8 倍**。但注意公平：如果指针不乱序（分配恰好连续、可预取），本机测得两者都是 ~24ms 几乎打平。所以结论要说准（经验做法）：**variant 的收益主要来自"数据连续 + 类型闭集"，而不只是"没有虚表"；分支高度可预测的小对象虚调用并不慢**。开集扩展（插件注册新类型）必须虚函数；闭集大批量遍历选 variant/SoA 化。

## 5. 字符串处理优化：string_view 与 SBO

两个事实打底：**`std::string` 的拷贝必然可能分配堆**；**libc++/libstdc++ 有 SBO（Small Buffer Optimization，也常写 SSO）**——短字符串（libstdc++ 15 字节、libc++ 22 字节）直接存在对象内部，零堆分配。

工程清单：

- **函数参数与解析路径用 `std::string_view`**（C++17）：只持有"指针 + 长度"，切分/比较零拷贝。JSON 解析器（第 12 章）的键值全是 `string_view` 指向原文，这是它快的第一支柱。
- **`substr` 的成本差一个量级**：`std::string::substr` 拷贝（分配），`string_view::substr` 只是两个整数运算。
- **拼接用 `reserve` + `append`**，或 `std::format`（C++20，第 07 章）；`a + b + c` 连锁会产生临时对象链。
- **SBO 意味着"小字符串并不慢"**：别为十几字节的路径写 `string_view` 优化到牺牲清晰度；热点在"长字符串的切分与传递"。
- **`string_view` 不拥有内存**：悬空 view 是 C++17 后最常见的新坑（见本章误区）。

## 6. allocator 概念与 arena 分配器

`std::allocator` 把 new/delete 抽象成可替换的"内存策略"。推理引擎的高频模式：**每一步推理要分配大量小对象（张量描述符、节点、临时缓冲），用完一次性丢弃**。逐个 new/delete 的代价 = 分配器锁 + 元数据 + 缓存不友好；arena 一次拿一大块、指针一拨就算分配：

```cpp
// arena.cpp —— new/delete vs 最小 arena：200 万个 16 字节节点
#include <chrono>
#include <cstddef>
#include <iostream>
#include <memory>
#include <new>
#include <vector>

class Arena {
public:
    explicit Arena(size_t chunk) : buf_(::operator new(chunk)), cap_(chunk), used_(0) {}
    ~Arena() { ::operator delete(buf_); }
    void* allocate(size_t n, size_t align = 16) {
        uintptr_t base = reinterpret_cast<uintptr_t>(buf_) + used_;
        base = (base + align - 1) & ~(uintptr_t)(align - 1);       // 对齐
        used_ = base - reinterpret_cast<uintptr_t>(buf_) + n;
        return reinterpret_cast<void*>(base);
    }
    void reset() noexcept { used_ = 0; }                           // 整批回收：一行
private:
    void* buf_; size_t cap_, used_;
};

struct Node { int a, b, c, d; };

int main() {
    const int N = 2'000'000;
    using clk = std::chrono::steady_clock;
    double s = 0;
    auto t0 = clk::now();
    {
        std::vector<std::unique_ptr<Node>> v; v.reserve(N);        // 每节点一次堆分配
        for (int i = 0; i < N; ++i) v.push_back(std::make_unique<Node>(Node{1,2,3,4}));
        for (auto& p : v) s += p->a + p->b;
    }                                                              // 析构：200 万次 free
    auto t1 = clk::now();
    {
        Arena ar(N * sizeof(Node) + 4096);
        std::vector<Node*> v; v.reserve(N);
        for (int i = 0; i < N; ++i) v.push_back(static_cast<Node*>(ar.allocate(sizeof(Node))));
        for (auto p : v) s += p->a + p->b;
    }                                                              // 析构：一次 free
    auto t2 = clk::now();
    std::cout << "new/delete: " << std::chrono::duration<double,std::milli>(t1-t0).count() << " ms\n";
    std::cout << "arena      : " << std::chrono::duration<double,std::milli>(t2-t1).count() << " ms\n";
    std::cout << "(校验 " << s << ")\n";
}
```

```bash
g++ -std=c++20 -O2 arena.cpp -o arena && ./arena && ./arena
# 输出（i5-12600K 实测两次）：
# new/delete: 58.6728 ms
# arena      : 12.261 ms
# new/delete: 52.9778 ms
# arena      : 11.6708 ms
```

**约 4.6 倍**，且 arena 附赠三样好处：内存连续（缓存友好）、整批回收（析构函数都不用跑，POD 情况）、无锁（每帧/每请求一个 arena，天然线程隔离）。标准库的对应物是 **C++17 的 `std::pmr`**（`std::pmr::monotonic_buffer_resource` 就是生产级 arena，`pmr::vector`/`pmr::string` 直接换底）——新代码优先 pmr，别重复造轮子（经验做法）。llama.cpp 的计算图与 PyTorch C++ 层的 memory pool 是同一思想的两个工业级实现。arena 的限制也要记牢：**不能单独释放某个对象**；对象生命周期必须"同生共死"。

## 7. 剖析驱动：perf 火焰图读 C++ 栈

衔接《Linux 性能工程》03/10。C++ 侧两个前置：**编译要带 `-g`，并加 `-fno-omit-frame-pointer`**（否则帧指针被优化掉，栈回溯靠 DWARF 慢十倍）；Release 也可以带 `-g`（调试信息不进指令流，不影响性能）。

```bash
g++ -std=c++20 -O2 -g -fno-omit-frame-pointer app.cpp -o app
perf record -F 99 -g -- ./app                 # 99Hz 采样调用栈
perf script | ./stackcollapse-perf.pl | ./flamegraph.pl > flame.svg   # 火焰图（FlameGraph 工具集）
```

火焰图的读法（自上而下是调用方向，宽度是 CPU 时间占比）：**看最宽的"平顶"**——平顶 = 自身耗时大（值得优化）；宽而不平的塔 = 调用链深但每层不热（先看顶部）。C++ 特有注意事项：模板实例化让符号名巨长（`std::vector<xxx>::push_back` 全展开），火焰图先用 `c++filt` 或让脚本折叠模板参数；动态库符号读不到时确认没 `strip`。另一个利器是 `perf annotate`（对着汇编标采样热点）——SIMD 章验证"这行循环到底没向量化"时，`perf annotate` 里看到的是 `vaddps` 还是标量 `addss` 一目了然。

## 常见误区

1. **基准被优化器删掉**（第 2 节的 0.0001ms）：结果必须被消费。这是所有微基准错误里最隐蔽的。
2. **拿 Debug 构建的数字做决策**：Debug 比 Release 慢一个数量级（第 01 章 fib 实验 11 倍），所有性能结论必须来自 `-O2` 及以上的构建。
3. **SoA 全盘推广**：频繁随机访问单个实体的代码（哈希表、图）SoA 反而更慢（多次缓存行）；先确认访问模式再动布局。
4. **`string_view` 悬空**：view 指向临时 `std::string`、`substr` 后源被释放、函数返回局部 view——三大悬空现场。规则：**view 的寿命 ≤ 源数据的寿命**，跨作用域持有就拷成 `std::string`。
5. **arena 忘记对齐或越界**：教学版 arena 不检查剩余空间（真实版要查），`align` 处理错会导致 `movaps` 段错误（第 03 章）——分配器是"性能与正确性交界处"，优先用 `std::pmr`。
6. **只看平均延迟**：火焰图给出的是分布，P99 尾延迟常由另一条冷路径贡献；剖析与优化都要分桶看（衔接《Linux 性能工程》的延迟分析）。

## 本篇小结

- 验证先行：`-fopt-info` 家族报告成功/失败与原因；Godbolt 看汇编验证内联与向量化；`perf annotate` 对汇编标热点。
- 基准规范：`DoNotOptimize`/消费结果防 DCE，`-g -fno-omit-frame-pointer` 建 Release 才有可剖析的栈。
- 数据布局：SoA vs AoS 实测 5x，口诀"整批遍历用 SoA、整体访问用 AoS、热冷字段分离居中"。
- 去虚化：`final` 让编译器直调；variant 收益来自"连续 + 闭集"，实测指针乱序时 8 倍、可预取时打平——诚实归因。
- 字符串：`string_view` 零拷贝切分，SBO 保短字符串无分配；警惕悬空。
- allocator：arena/pmr 把"百万级小对象"从 53ms 干到 12ms（4.6x），整批回收 + 连续内存是推理引擎的标配思路。

2. 给第 6 节 Arena 补上"空间不足返回 nullptr"与 `reset()` 复用，改造成"每轮推理开始 reset、结束整块释放"的形状，测量 1000 轮循环的总耗时变化。
3. 用 Godbolt 对比 `struct Circle final` 与不带 `final` 的 `area()` 调用汇编，指出去虚化发生的位置。
4. 用 `perf record -g` 剖析第 12 章的 JSON 解析器，找出最宽平顶；对照 `-fopt-info-vec` 报告，提出一个优化假设并用数字验证或证伪它。
5. 写一个"热冷字段分离"实验：`Entity { Transform t; std::string name; }` 拆成 `vector<Transform>` + `vector<string>` 两个数组，测遍历全部 Transform 的速度变化，并说明什么情况下不值得拆。
