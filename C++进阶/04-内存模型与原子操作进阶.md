# 04 - 内存模型与原子操作进阶

## 本篇目标

- 给出数据竞争的**标准定义**，理解"竞争 = 未定义行为"而不是"结果不确定"。
- 逐个理解六种 `memory_order` 的语义与适用场景，能对每一处原子操作说出"为什么是这个序"。
- 用 release-acquire 配对实验 + TSan 验证正确的同步，看懂 happens-before 关系图。
- 认识 ABA 问题与带版本号解法；复现并修复伪共享（衔接《计算机系统与网络》03 的缓存行概念）。

前置：《C++》系列 12（并发编程）——本篇默认你会用 `std::thread`、`std::mutex`、`std::atomic` 的基本 API。

## 1. 数据竞争的严格定义

《C++》系列 12 说"两个线程同时写同一个变量是数据竞争"，标准里的定义更精确（[intro.races]，N4861 §6.9.2）：

> 两个**冲突动作**（conflicting actions）指：访问同一内存位置、至少一个是写。若它们**发生在不同线程**（或同一线程内不按程序序），且**没有先后关系（happens-before）**，则程序包含数据竞争。**含数据竞争的 C++ 程序（用非原子操作时）是未定义行为**——不是"结果可能是旧值"，是标准不再保证任何事。

三个关键词逐个过：

- **同一内存位置**：一个 `int` 是一个位置；一个 `struct {int a; int b;}` 是两个位置（成员各自独立），但位域可能共享位置。
- **happens-before**：同步建立的"可见性边"。有这条边，一个线程的写对另一个线程的读**保证可见且有序**；没有这条边，硬件/优化器可以乱序、缓存、复用寄存器，读到的可以是任何历史值甚至"既新又旧"的混合。
- **UB 的含义**：编译器有权假设无竞争，据此把看似无关的代码重排/删除。下面这个例子（标准 [intro.progress] 相关讨论的常见教学变体）在 `-O2` 下可能死循环：

```cpp
// spin_ub.cpp —— 演示：非原子忙等可能被优化成死循环（UB 的实际危害）
#include <thread>
bool ready = false;                 // 非原子！
int  data  = 0;

void producer() { data = 42; ready = true; }   // 两行写
void consumer() { while (!ready) {} std::cout << data << '\n'; }
// 优化器假设无竞争 → consumer 里 ready 不会"自己变 true" → 循环体可能被提升成 while(true){}
```

修法不是加锁（这里没有临界区），而是把 `ready` 换成 `std::atomic<bool>` 并选对内存序——这就是接下来两节的内容。

## 2. 六种 memory_order 逐个语义

`memory_order` 控制的是"这条原子操作周围的其他访存可以乱序到什么程度"。六种按强度排列：

| memory_order | 语义 | 典型场景 |
| --- | --- | --- |
| `relaxed` | 只保证本操作原子，**不约束**其他访存的顺序 | 计数器（统计）、无同步意义的标志 |
| `acquire` | 本读之后的其他访存**不得上移**到它之前；能看见配对 release 之前的所有写 | 消费者读标志/游标 |
| `release` | 本写之前的其他访存**不得下移**到它之后；写入对配对 acquire 可见 | 生产者写完数据后置标志 |
| `acq_rel` | 对一个读-改-写操作同时施加 acquire + release | CAS/`fetch_add` 既是读又是写时 |
| `seq_cst` | acquire + release，**且所有 seq_cst 操作构成全序**（默认值） | 多变量同步、不想想清楚时 |
| `consume` | 理论上的"依赖序 acquire"；**实践中被实现为 acquire**，标准委员会建议别用（[atomics.order] 明确鼓励改为 acquire） | 几乎没有（历史遗留） |

记忆骨架（经验做法）：**"release 发布，acquire 接收"是一对；`fetch_*`/CAS 这类读改写用 `acq_rel`；纯计数用 `relaxed`；拿不准用 `seq_cst`（默认），先对再快**。`consume` 只在两个地方还会遇到：旧代码和面试题。

默认值陷阱：`store(v)` 不写内存序就是 `seq_cst`，在某些架构（尤其 ARM）上比 `release` 贵——但**贵的不是 store 本身，是它要求的全序栅栏**。所以"先写对（seq_cst），剖析证明热点后再收紧"是可行路径。

## 3. release-acquire 配对实验

经典的"生产者写数据 → 消费者看标志再读数据"：

```cpp
// ra_pair.cpp —— release-acquire 正确配对
#include <atomic>
#include <cassert>
#include <iostream>
#include <thread>

std::atomic<bool> ready{false};
int payload = 0;                              // 普通变量，靠 atomic 建立可见性

void producer() {
    payload = 42;                             // (1) 普通写
    ready.store(true, std::memory_order_release);   // (2) release：之前的写(1)不许下沉到它之后
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) {}  // (3) acquire：之后的读不许上移到它之前
    assert(payload == 42);                    // (4) 保证看到 42——(2)与(3)配对建立 happens-before
}

int main() {
    std::thread t1(producer), t2(consumer);
    t1.join(); t2.join();
    std::cout << "payload = " << payload << '\n';
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra -pthread ra_pair.cpp -o ra_pair && ./ra_pair
# 输出：payload = 42
```

**验证工具 TSan**（ThreadSanitizer）能把"有没有竞争"从猜变成查。故意把 `acquire/release` 都改成 `relaxed`，让 (1)(4) 失去同步边：

```text
$ g++ -std=c++20 -O1 -g -fsanitize=thread -pthread ra_bad.cpp -o ra_bad && ./ra_bad
==================
WARNING: ThreadSanitizer: data race (pid=12345)
  Read of size 4 at 0x7ffc... by thread T2:
    #0 consumer() ra_bad.cpp:14 (ra_bad+0x...)
  Previous write of size 4 at 0x7ffc... by thread T1:
    #1 producer() ra_bad.cpp:9 (ra_bad+0x...)
...
SUMMARY: ThreadSanitizer: data race ra_bad.cpp:9 in producer()
==================
```

TSan 报出 `data race`——尽管程序"看起来"能跑对（assert 大多数时候不炸）。规则：**`relaxed` 只保证"读到的是某个原子写过的值"，不保证"读到的是最新的一次写"，更不传递其他变量的可见性**。改回 release/acquire 再跑 TSan，输出干净。TSan 只能在"竞争被实际触发"时报告，是检测器不是证明器；无竞争的正确性要靠第 4 节的推理。

## 4. happens-before 关系图解

happens-before（先行发生）是上述一切的形式化骨架。三种边（[intro.races]/13-15）：

```
1. 程序序（sequenced-before）：单线程内，按语句顺序。
2. 同步（synchronizes-with）：配对的 release 写 → acquire 读。
3. happens-before = 1、2 的传递闭包。
```

把第 3 节的实验画成图：

```
producer 线程                                consumer 线程
─────────────                                ─────────────
payload = 42  ──sequenced-before──┐
                                  │
ready.store(release) ─────────────┼──synchronizes-with────→ ready.load(acquire)
                                  │                            │
                                  │                    sequenced-before
                                  │                            ↓
                                  └───happens-before──→   读 payload（看到 42）
```

顺带把其他同步点映射进来，建立全局地图：`mutex.unlock() → 后续 lock()` 是 synchronizes-with；`thread t(f)` 的构造 happens-before `f` 的执行，`t.join()` 的返回 happens-after `f` 的全部动作；`std::atomic` 的 RMW 读到的是"最新值链"上的值（[intro.races]/20 的 read-modify-write 特殊规则）。**竞争的定义 = 冲突动作间没有 happens-before 边**——检查并发代码就是画这张图，画不出边的全都有问题。

## 5. ABA 问题：值一样，世界已经变了

CAS 的语义是"期望值等于当前值才写"。但"值相等"不等于"没被改过"：

```
时刻 1：线程 A 读到指针 p（指向节点 X）
时刻 2：线程 B 把 X 弹出，free 掉，后来又 push 回一个"恰好地址还是 X"的新节点
时刻 3：线程 A CAS(p, X, ...) —— 成功！但 X 已经不是当年那个 X
```

无锁栈/队列在内存可复用时都会踩到。最常用的解法是**带版本号的 CAS**：把"指针 + 计数器"打包成一个 128 位值，每次修改计数器 +1，A/B 两次操作即使地址相同、版本号也不同：

```cpp
// aba.cpp —— 版本号化解 ABA（教学版：单机 128 位 CAS）
#include <atomic>
#include <cstdint>
#include <iostream>

struct Tagged {          // 64 位指针 + 16 位版本号，打进 80 位；x86-64 可用 __int128 做一次 CAS
    std::uint64_t ptr;
    std::uint16_t ver;
};
static_assert(sizeof(Tagged) <= 16);

struct Slot { Tagged t; };
struct AtomicTagged {
    // 生产实现：x86-64 用 cmpxchg16b（lock cmpxchg16b）；这里用 std::atomic<Tagged> 示意
    std::atomic<Tagged> a{{0, 0}};
    bool cas(Tagged expect, Tagged next) {
        return a.compare_exchange_strong(expect, next);
    }
};

int main() {
    AtomicTagged s;
    Tagged cur = s.a.load();
    Tagged next{cur.ptr + 8, static_cast<std::uint16_t>(cur.ver + 1)};  // 每次改动版本号变
    bool ok = s.cas(cur, next);
    std::cout << "CAS " << (ok ? "成功" : "失败")
              << "，ver: " << cur.ver << " -> " << next.ver << '\n';
}
```

```bash
g++ -std=c++20 -O2 aba.cpp -o aba && ./aba
# 输出：CAS 成功，ver: 0 -> 1
```

另外两条路：**延迟回收**（hazard pointer/epoch，见第 05 章——节点退出链表后不 free，等所有读者确认不再引用再回收，"地址复用"就无从发生）；**干脆不回收**（epoll 式：节点从池里借、用完还池，池内存永不 free，ABA 退化为"值相同即可"）。标准库实践：`std::shared_ptr` 原子操作有引用计数兜底，但慢；C++20 的 `std::atomic<std::shared_ptr<T>>` 与 `atomic_ref` 提供了更直接的方案。

## 6. 伪共享实测：alignas(64) 填充

《计算机系统与网络》03 讲过缓存行（64 字节）与 MESI：**缓存一致性以缓存行为单位**。两个线程各自写两个"逻辑无关"的变量，若它们落在同一条缓存行上，每次写都让对方的缓存行失效——这就是伪共享（false sharing）：

```cpp
// falsesharing.cpp —— 两个线程各写各的计数器
#include <atomic>
#include <chrono>
#include <iostream>
#include <thread>
#include <vector>

struct CountersBad  { std::atomic<long> a; std::atomic<long> b; };   // 16 字节：同一条缓存行
struct CountersGood { alignas(64) std::atomic<long> a;
                      alignas(64) std::atomic<long> b; };            // 各占一条缓存行

template <typename C>
void run(const char* name) {
    C c{}; c.a = 0; c.b = 0;
    std::vector<std::thread> ts;
    auto t0 = std::chrono::steady_clock::now();
    ts.emplace_back([&]{ for (long i = 0; i < 50'000'000; ++i) c.a.fetch_add(1, std::memory_order_relaxed); });
    ts.emplace_back([&]{ for (long i = 0; i < 50'000'000; ++i) c.b.fetch_add(1, std::memory_order_relaxed); });
    for (auto& t : ts) t.join();
    auto t1 = std::chrono::steady_clock::now();
    std::cout << name << ": " << std::chrono::duration<double, std::milli>(t1 - t0).count()
              << " ms  (a+b=" << (c.a.load() + c.b.load()) << ")\n";
}

int main() { run<CountersBad>("伪共享     "); run<CountersGood>("缓存行隔离 "); }
```

```bash
g++ -std=c++20 -O2 -pthread falsesharing.cpp -o falsesharing && ./falsesharing && ./falsesharing
# 输出（i5-12600K 实测两次）：
# 伪共享     : 904.404 ms  (a+b=100000000)
# 缓存行隔离 : 246.061 ms  (a+b=100000000)
# 伪共享     : 855.977 ms  (a+b=100000000)
# 缓存行隔离 : 246.061 → 213.85 ms（第二次）
```

隔离后快 **3.7 倍**——没有改任何逻辑，只把两个变量分开 64 字节。诊断工具：`perf c2c`（cache-to-cache 冲突检测，见《Linux 性能工程》10）或看 `perf stat -e cache-misses` 的异常比例。工程规则（经验做法）：**被不同线程高频写的变量，一个变量一条缓存行**：`alignas(64)`，或 `std::hardware_destructive_interference_size`（C++17，GCC 需手动 `__GCC_DESTRUCTIVE_SIZE`，值即 64）。注意方向别搞反：**被同一线程一起读的一组变量反而要挤在一条行内**。

## 7. std::atomic 正确用法清单

- **能不用就不用**：复合逻辑（两个变量的不变式）用 `mutex`；单变量计数/标志/游标才轮到 atomic（见《C++》系列 12 的选择标准）。
- **内存序按"最小够用"标理由**：每个 `atomic` 操作旁边写注释说明选它的原因；写不出理由就用默认 `seq_cst`（经验做法）。
- **RMW 一律 `acq_rel`** 起步：`fetch_add`/`compare_exchange` 本身既读又写，单边序（只 release 或只 acquire）语义不完整。
- **CAS 循环用 `compare_exchange_weak`**：允许伪失败、循环里自动重试；只在"不循环、单次尝试"时用 strong。
- **别用 atomic 数组解决伪共享后忘对齐**：`std::atomic<T>` 的对齐跟随 `T`，热数组手动 `alignas(64)`。
- **`volatile` 不是 atomic**：`volatile` 只禁止编译器优化访存，不提供原子性、不建立 happens-before（[intro.progress] 与 cppreference 明确区分）；把 `volatile int` 当线程标志是经典错误。
- **验证**：并发代码合入前跑 TSan（CI 里固定跑），性能敏感路径用 `perf c2c`/false-sharing 检查。

## 常见误区

1. **把数据竞争理解成"读到的值可能旧"**：UB 意味着优化器可以基于"无竞争"假设删掉整段逻辑（第 1 节的死循环就是实证），不是"偶尔读到旧值"那么温和。
2. **relaxed 当"更快版 seq_cst"随便用**：`relaxed` 不传递任何可见性，两个 relaxed 变量之间没有顺序；只有"计数、不参与同步"的场合才能用它。
3. **以为 `release` store 会让数据立刻对其他线程可见**：可见性只在**配对的 acquire 读到这个 store 的值**时才沿边传播；没人 acquire，什么也不保证。
4. **`compare_exchange_strong` 忘了它会改写 `expected`**：失败时 `expected` 被更新为当前值，循环写法必须接着用这个新值，否则白转。
5. **伪共享只想到 atomic 数组**：两个非原子变量被不同线程写同样是伪共享（顺便还是 UB）；`alignas(64)` 对两者都需要。
6. **用 `std::atomic<double>`/结构体当万能药**：`atomic<T>` 要求 T 可平凡拷贝才基本可用，大结构体会退化成内部锁（`is_lock_free()` 为 false），性能不升反降；先用 `atomic<T*>` 指向不可变对象（copy-on-write 思想）。

## 本篇小结

- 数据竞争的标准定义：不同线程的冲突动作 + 无 happens-before → UB；后果包括死循环、被删除的代码，不只是"旧值"。
- 六种内存序记骨架：release 发布 / acquire 接收、RMW 用 acq_rel、计数 relaxed、默认 seq_cst、consume 别用。
- happens-before = 程序序 + 同步边的传递闭包；检查并发代码 = 画图找缺失的边；TSan 能查实际触发的竞争。
- ABA 用版本号 CAS、延迟回收或对象池解决；伪共享用 `alignas(64)` 隔离，实测 3.7x。
- atomic 清单：先锁后原子、内存序写理由、CAS 用 weak + 接住 expected、volatile 不是 atomic。
