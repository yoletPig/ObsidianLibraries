# 02 - 模板深水区

## 本篇目标

- 理解 SFINAE 的原理与两个经典形态（`enable_if`、`void_t`），能读懂标准库与推理引擎源码里的这类代码。
- 掌握 C++17 `if constexpr` 对标签分发的替代，以及变参模板的两种展开写法与折叠表达式。
- 说清"模板为什么放头文件"、显式实例化何时有用。
- 用 C++20 concepts 重写约束，并用实验对比两种写法的报错长度。

前置：《C++》系列 09（函数模板）、10（类模板）。

## 1. SFINAE：替换失败不是错误

模板实例化时，编译器把实参代入模板参数。**代入失败（substitution failure）本身不算错误，只是把这个候选从重载集里剔除**——这就是 SFINAE（Substitution Failure Is Not An Error），出处：C++ 标准 [temp.deduct]/8（N4861 及以后）；系统论述见《C++ Templates》第 2 版 Vandevoorde/Josuttis/Gregor，第 8 章。

它最有名的应用是"按类型性质选择重载"：

```cpp
// sfinae.cpp —— 同名函数只对特定类型可用
#include <iostream>
#include <type_traits>

// std::enable_if_t<条件, 类型>：条件为真时是 int，为假时没有 ::type 成员 → 代入失败 → 剔除
template <typename T, std::enable_if_t<std::is_integral_v<T>, int> = 0>
long double to_long_double(T v) { return v; }             // 只接受整型

template <typename T, std::enable_if_t<std::is_floating_point_v<T>, int> = 0>
long double to_long_double(T v) { return v; }             // 只接受浮点

int main() {
    std::cout << to_long_double(7) << '\n';        // 命中整型版
    std::cout << to_long_double(0.25) << '\n';     // 命中浮点版
    // to_long_double("x")   // 编译错误：两个重载都被剔除，无候选
}
```

```bash
g++ -std=c++20 -Wall -Wextra sfinae.cpp -o sfinae && ./sfinae
# 输出：
# 7
# 0.25
```

读法：`enable_if_t<cond, int> = 0` 是一个**默认为 0 的哑模板参数**。cond 为假时 `enable_if_t` 没有 `type` 成员，代入失败，该重载消失。注意条件必须依赖模板参数 `T`——写死 `std::enable_if_t<true, int> = 0` 没有约束力。

## 2. void_t 惯用法：探测"有没有这个成员"

SFINAE 的第二个经典形态：用 `std::void_t<...>`（C++17，[meta.transform]）把任意类型序列映射成 `void`，从而在"类型"里做**表达式是否合法**的探测：

```cpp
// void_t.cpp —— 编译期探测：T 有没有 begin()？
#include <iostream>
#include <string>
#include <type_traits>
#include <vector>

template <typename, typename = void>
struct has_begin : std::false_type {};                 // 主模板：默认没有

template <typename T>
struct has_begin<T, std::void_t<decltype(std::declval<T&>().begin())>>
    : std::true_type {};                               // 偏特化：begin() 合法才参与匹配

int main() {
    static_assert(has_begin<std::vector<int>>::value); // 有
    static_assert(has_begin<std::string>::value);      // 有
    static_assert(!has_begin<int>::value);             // 没有
    std::cout << "编译期探测全部成立\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra void_t.cpp -o void_t && ./void_t
# 输出：编译期探测全部成立
```

读法：`decltype(std::declval<T&>().begin())` 只有在 `begin()` 表达式合法时才能推出类型；不合法 → 代入失败 → 偏特化被剔除 → 落回主模板 `false_type`。这个惯用法有一个著名的历史坑：早期标准对"别名模板里的依赖类型是否参与替换"规定不明，导致主流编译器上 `void_t` 时灵时不灵，最终由 **CWG 1558** 澄清（别名模板中未使用的模板参数也会触发替换），`std::void_t` 才成为可靠惯用法——在 cppreference 的 void_t 页面能看到这段历史。想探测的成员换成 `.size()`、`.value_type` 都行，一个模式打天下。

## 3. if constexpr：两代写法对比

SFINAE 可读性差。C++17 的 `if constexpr` 把"编译期分支"直接还给语言，**不成立的分支直接丢弃（不实例化）**。对比同一个问题："整型输出整数、浮点输出浮点、其他输出类型名"。

C++14 时代的标签分发（tag dispatch）写法：

```cpp
// C++14：三个辅助函数靠重载决议挑一个，可读性差
template <typename T>
std::string describe_impl(const T& v, std::true_type)  { return "整数: " + std::to_string(v); }
template <typename T>
std::string describe_impl(const T& v, std::false_type) { return "浮点: " + std::to_string(v); }
template <typename T>
std::string describe(const T& v) {
    return describe_impl(v, std::is_integral<T>{});
}
```

C++17 写法（真实运行验证）：

```cpp
// ifconstexpr.cpp
#include <iostream>
#include <string>
#include <type_traits>

template <typename T>
std::string describe(const T& v) {
    if constexpr (std::is_integral_v<T>)
        return "整数: " + std::to_string(v);          // 非 T 为整型时，这行整体不参与编译
    else if constexpr (std::is_floating_point_v<T>)
        return "浮点: " + std::to_string(v);
    else
        return "其他类型";                             // 兜底分支让 else 链闭合，任何 T 都有一条路
}

int main() {
    std::cout << describe(42) << " | " << describe(3.5) << " | " << describe("hi") << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra ifconstexpr.cpp -o ifconstexpr && ./ifconstexpr
# 输出：整数: 42 | 浮点: 3.500000 | 其他类型
```

三个要点：丢弃的分支**不参与实例化**，所以分支里可以放"对当前 T 非法"的代码（这是它替代 SFINAE 的根本原因）；`else if constexpr` 链最后必须有非 constexpr 兜底，否则所有条件都不满足的 T 会让函数体没有 return；`if constexpr` 不影响**重载决议**——它不能让某个函数"对某 T 不存在"，需要那种效果时（比如从重载集里剔除）仍用 SFINAE/concepts（出处：[stmt.if]/2，《Effective Modern C++》条款 27 对 tag dispatch 有系统讨论）。

## 4. 变参模板：包展开与递归展开

模板参数包 `typename... Args` 是"零个或多个类型"的编译期列表。展开有两种写法，都认识才能读别人的代码。

### 4.1 递归展开（C++11 时代的经典）

```cpp
void print_rec() {}                                    // 递归基：包空了
template <typename T, typename... Rest>
void print_rec(const T& first, const Rest&... rest) {
    std::cout << first << ' ';
    print_rec(rest...);                                // 每层剥掉一个，剩 n-1 个
}
// print_rec(1, 2.5, "three")  实例化链：print_rec(int,double,const char(&)[6]) → print_rec(double,...) → print_rec(const char(&)[6]) → print_rec()
```

### 4.2 折叠表达式（C++17，一次实例化搞定）

```cpp
template <typename... Args>
void print_fold(const Args&... args) {
    ((std::cout << args << ' '), ...);                 // 一元右折叠：对包里每个元素做逗号表达式
    std::cout << '\n';
}
// 四种形态：(init op ... op pack) / (... op pack) / (pack op ... op init) / (pack op ...)——见 cppreference "fold expression"
```

```bash
# 两种写法输出一致：
# 1 2.5 three
# 1 2.5 three x
```

折叠表达式支持 `+ - * / % ^ & | << >> && || , < > <= >= == !=`。常用的还有求和 `(args + ... + 0)`（带初值，防空包对 `+` 非法）、逻辑与 `(std::is_arithmetic_v<Args> && ...)`。经验做法：**新代码用折叠表达式，递归展开只在"需要按序/带索引"时用**（比如逐层传 `std::index_sequence`）。

## 5. CTAD：让编译器替你写 `<T>`

C++17 的类模板实参推导（Class Template Argument Deduction）让 `std::pair`、`std::vector`、锁这些"构造函数里已带类型信息"的模板免写尖括号：

```cpp
#include <mutex>
#include <vector>
std::pair p(1, 2.0);            // pair<int, double>，从构造函数实参推
std::vector v{1, 2, 3};         // vector<int>（initializer_list 构造函数优先）
std::mutex m;
std::lock_guard lg(m);          // C++17 前要写 lock_guard<std::mutex>，C++17 起免写
```

推导不到时写**推导指引**（deduction guide）教编译器：

```cpp
template <typename T> struct Wrapper { T v; Wrapper(T); };
Wrapper(const char*) -> Wrapper<std::string>;   // Wrapper("hi") 推成 Wrapper<std::string>
```

CTAD 与模板实参推导的规则细节在《C++ Templates》第 2 版第 15 章；日常记住：构造函数能推出全部参数 → 免写；推不出或语义需要转换 → 写指引。

## 6. 模板代码组织：为什么模板放头文件

普通函数可以"头文件声明 + cpp 定义"，模板不行——**实例化发生在编译消费者翻译单元的时刻，编译器必须当场看到完整定义**才能生成代码。于是有两种组织法：

```cpp
// 法一（99% 的情况）：全放头文件。代价：改一个字符，所有消费者重编
template <typename T>
struct Buffer { T data[16]; size_t n = 0; void push(T v) { data[n++] = v; } };

// 法二：定义放 cpp，在 cpp 里显式实例化，头文件里声明
// buffer.h:
//     template <typename T> struct Buffer { ... 声明 + 仅声明 push ... };
//     extern template class Buffer<float>;   // 阻止消费者隐式实例化
// buffer.cpp:
//     template class Buffer<float>;          // 显式实例化：只在这里生成一份代码
//     template class Buffer<double>;
```

显式实例化（`extern template` + `template class X<T>;`）的两个收益：**编译防火墙**（消费者看不到定义也能用，修改 .cpp 不触发消费者重编）和**编译时间/代码体积控制**（同一实例只生成一份）。出处：标准 [temp.explicit]；《C++ Templates》第 14 章。经验做法：**对外接口固定的泛型库（如推理框架的 `Tensor<float/double/int8>`）用显式实例化，把 C++20 的支持类型列成白名单**——llama.cpp 系的量化模板正是这么干的。

## 7. concepts：约束终于长在语言里

C++20 concepts（[temp.concepts]；主要提案 P0734）把 SFINAE 的"能不能代换"升级成"满不满足概念"，并直接改善报错。先看探测型 concept 的写法：

```cpp
#include <concepts>

template <typename T>
concept HasBegin = requires(T& t) {
    t.begin();                                   // 要求表达式合法
    { t.begin() } -> std::input_or_output_iterator; // 且返回类型满足迭代器概念
};

template <HasBegin C>          // 用在类型参数位置
void serialize(const C& c) { /* ... */ }

// 等价的形式三：requires 子句放后面，可表达更复杂条件
template <typename T>
    requires std::integral<T> || std::floating_point<T>
T twice(T v) { return v * 2; }
```

`requires` 表达式还能写多条要求：`requires(T a, T b) { a + b; a == b; typename T::value_type; }`（表达式合法 + 存在嵌套类型）。

### 报错长度对比实验

同一个错误调用（给算术函数传 `std::complex<double>`），两种写法在 g++ 11 下的真实报错：

```cpp
// conc.cpp —— 有 concept
#include <concepts>
#include <complex>
template <typename T> requires std::integral<T>
T twice(T v) { return v * 2; }
int main() { return static_cast<int>(twice(std::complex<double>{1,0}).real()); }
```

```text
$ g++ -std=c++20 conc.cpp -o conc 2>&1 | wc -l      # 报错 16 行
conc.cpp:5:43: error: no matching function for call to ‘twice(std::complex<double>)’
conc.cpp:4:3: note: candidate: ‘template<class T>  requires  integral<T> T twice(T)’
    4 | T twice(T v) { return v * 2; }
      |   ^~~~~
```

```cpp
// conc2.cpp —— 无 concept（约束体现在函数体内部表达式的合法性上）
#include <complex>
template <typename T>
T twice(T v) { return v * 2; }
int main() { return static_cast<int>(twice(std::complex<double>{1,0}).real()); }
```

```text
$ g++ -std=c++20 conc2.cpp -o conc2 2>&1 | wc -l    # 报错 29 行
conc2.cpp:3:25: error: no match for ‘operator*’ (operand types are ‘std::complex<double>’ and ‘int’)
...  接着罗列 std::complex 里一长串 operator* 重载候选 ...
```

调用栈越深，无 concept 的报错膨胀得越恐怖（每一层实例化都会被展开复述）。概念版直接告诉调用者"你给的类型不满足 integral"，这正是读大型模板报错时最想要的语义层信息。注意本实验里 16 行中还有大半是上下文行；`requires` 未满足的原因在 gcc 11 的显示还比较简略，gcc 13+ 会进一步指出"哪一个子要求失败"。

## 常见误区

1. **以为 `if constexpr` 能替代一切 SFINAE**：它丢弃的是"分支体"，不是"重载候选"。想让某重载对某类型不存在（从而被其他重载接住），还是要 concept/enable_if。
2. **在 `if constexpr` 分支里写当前 T 非法、又忘了分支会被丢弃的时机**：丢弃发生在实例化时，非依赖代码的语法错误（如拼错关键字）仍会在模板定义解析时报。
3. **折叠表达式对空包**：`(args + ...)` 空包非法（`std::cout << pack` 这类逗号折叠空包为合法空语句）；求和记得写 `(args + ... + 0)`。
4. **模板递归深度爆掉**：深度嵌套的元程序（如编译期生成 1 万个 case）会撞 `-ftemplate-depth` 上限（默认 900），报错是一屏" instantiation depth exceeded"。先怀疑有没有设计成线性递归。
5. **头文件里的模板用到 static 变量/匿名命名空间**：每个翻译单元各一份，行为分裂。需要共享状态时显式设计（传参、`std::atomic` 单例），不要靠模板内 static。
6. **对 `std::vector<bool>` 这类特化想当然**：库里的偏特化可能改变语义（vector<bool> 不是 bool 数组），写模板代码时对标准库特化保持警觉。

## 本篇小结

- SFINAE：代入失败只是剔除候选，`enable_if` 控制重载可用性，`void_t` 探测成员表达式合法性（CWG 1558 后成为可靠惯用法）。
- `if constexpr` 在实例化期丢弃分支，可读性完胜标签分发，但不改变重载决议。
- 变参模板：递归展开是历史写法，折叠表达式 `(pack op ...)` 是 C++17 后的日常；CTAD + 推导指引消掉尖括号。
- 模板定义必须在实例化点可见 → 放头文件；接口固定时用 `extern template`/显式实例化换编译时间与体积。
- concepts 把约束语义化，报错从 29 行降到 16 行，且说的是人话；新代码优先 concepts。
