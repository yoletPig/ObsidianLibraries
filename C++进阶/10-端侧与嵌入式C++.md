# 10 - 端侧与嵌入式 C++

## 本篇目标

- 列出端侧环境的约束清单，建立"桌面 C++ 直觉"到"端侧 C++ 直觉"的转换。
- 掌握 `-fno-exceptions -fno-rtti` 下的错误处理风格（错误码/expected）。
- 会用 `objdump -h` 规划静态内存（.text/.data/.bss），用 `-fstack-usage` 估算栈，实现池分配器。
- 走通交叉编译最小流程与 CMake toolchain 文件，认识 RK3588 用户态接入 NPU 的 rknn_api 骨架（衔接《模型性能优化》Stage 4）。

范围说明：本章的"端侧"覆盖两个层次——**MCU 裸机/RTOS**（KB 级，禁异常是刚需）与 **ARM Linux SoC（RK3588）**（MB 级，异常可用但仍受内存/功耗约束）。两者共用的工程习惯是本章主线，差异处分别标注。

## 1. 端侧约束清单

| 约束 | MCU（如 STM32，Cortex-M4） | ARM Linux SoC（RK3588） | 对代码风格的影响 |
| --- | --- | --- | --- |
| 内存 | RAM 几十 KB–几 MB，Flash 同量级 | 几 GB，但与其他进程共享 | 禁止运行期无界分配；静态规划 |
| 异常/RTTI | 通常 `-fno-exceptions -fno-rtti`（异常展开表占 Flash，实时性不可控） | 可用，但实时路径仍避免 | 错误码/expected 为主 |
| 实时性 | 硬实时（中断响应 μs 级） | 软实时（帧率/延迟预算） | 无锁 SPSC（第 05 章）、预算内完成 |
| 栈 | 几 KB 固定，溢出 = 硬故障 | 8MB 默认但线程多时要规划 | `-fstack-usage` 预估 |
| 看门狗 | 必配，喂狗是代码结构的一部分 | 进程级 health check | 第 6 节 |
| 电源 | μA 级功耗预算 | W 级但受热限制 | NPU/DSP offload |

桌面习惯里三件"免费"的事在端侧都是事故源：**异常**（栈展开要几百 KB 代码与不可预测延迟）、**堆碎片**（长期运行的 malloc/free 使碎片化，最终 OOM）、**无界容器**（`push_back` 到内存耗尽）。本章其余部分就是给这三件事换工具。

## 2. 禁用异常与 RTTI 的代码风格

```bash
g++ -std=c++20 -Os -fno-exceptions -fno-rtti mem.cpp -o mem   # 嵌入式常见编译配置
```

`-fno-exceptions` 下 `throw` 直接变 `std::terminate`；`-fno-rtti` 禁掉 `dynamic_cast`/`typeid`（省虚表扩展与类型元数据）。STL 不会编译失败（`vector::push_back` 分配失败时内部 throw 退化成 abort），但**依赖异常做错误流的设计全部失效**，替代风格：

```cpp
// errstyle.cpp —— 错误码 + expected 的无异常风格（已验证编译）
#include <cstdio>
#include <expected>      // MCU 上没有 libstdc++ expected 时用 tl::expected（header-only，无异常模式可用）

enum class Status : int { OK = 0, BufTooSmall, InvalidArg, Timeout };

// 风格一：错误码出参（无堆、最省，C 兼容）
Status fill_buffer(std::uint8_t* dst, std::size_t cap, const std::uint8_t* src, std::size_t n, std::size_t* written) {
    if (!dst || !src || !written) return Status::InvalidArg;
    if (n > cap) return Status::BufTooSmall;    // 不抛，返回错误码
    for (std::size_t i = 0; i < n; ++i) dst[i] = src[i];
    *written = n;
    return Status::OK;
}

// 风格二：expected（有值或错误，调用方可链式；第 07 章）
std::expected<int, Status> parse_len(const std::uint8_t* p, std::size_t n) {
    if (n < 4) return std::unexpected(Status::InvalidArg);
    return static_cast<int>((p[0] << 24) | (p[1] << 16) | (p[2] << 8) | p[3]);
}

int main() {
    std::uint8_t buf[8] = {};
    std::size_t w = 0;
    if (Status s = fill_buffer(buf, sizeof buf, buf + 4, 2, &w); s != Status::OK) {
        std::printf("失败: %d\n", static_cast<int>(s));   // 嵌入式的"异常处理"就是分支
    }
    auto len = parse_len(buf, sizeof buf);
    std::printf("len=%d\n", len.value_or(-1));
}
```

```bash
g++ -std=c++20 -Os -fno-exceptions -fno-rtti -Wall -Wextra errstyle.cpp -o errstyle && ./errstyle
# 输出：
# len=131072
```

经验做法：**MCU 层 API 用错误码（C 兼容、可预测栈上布局），中间业务层用 expected 串链**；`-fno-rtti` 后需要"类型分发"的地方用 tag/variant（第 06 章）替代 `dynamic_cast`。注意 `std::expected` 的 `value()` 在无值时抛异常——无异常环境下用 `value_or`/`operator*`（先判 `has_value`）。

## 3. 静态内存规划：链接脚本与 .bss/.data

ELF 可执行/固件的内存画像由段构成（衔接《计算机系统与网络》01）：

| 段 | 内容 | 占 Flash | 占 RAM | 注意 |
| --- | --- | --- | --- | --- |
| `.text` | 代码、字面量池 | 是 | 否（从 Flash 直接执行/XIP） | `-Os` 瘦身主战场 |
| `.rodata` | 常量、字符串 | 是 | 否（或映射） | 模型权重放这里（或独立分区） |
| `.data` | 有初值全局/静态 | 是（存初值） | 是（运行时） | **双倍计费** |
| `.bss` | 零初始化全局/静态 | 否 | 是 | 文件小≠内存小，最易翻车 |

实测（本机 g++ 11，验证过的例子）：

```cpp
// mem.cpp
#include <cstdint>
std::uint8_t big_bss[64 * 1024];                    // 零初始化 → .bss
std::uint8_t big_data[8 * 1024] = {1, 2, 3};        // 有初值 → .data
const std::uint8_t ro[4 * 1024] = {7};              // 常量 → .rodata
int main() { return big_bss[0] + big_data[0] + ro[0]; }
```

```bash
g++ -std=c++20 -Os mem.cpp -o mem && objdump -h mem | grep -E "\.text|\.data |\.bss|\.rodata"
# 输出：
#   13 .text         00000109  ...    265 字节代码
#   15 .rodata       00000004  ...    （ro 的内容被优化进指令流，段剩 4 字节）
#   22 .data         00002020  ...    8208 字节（8KB 数组 + 杂项）
#   23 .bss          00010020  ...    65568 字节（64KB 数组 + 杂项）——Flash 里不存在！
```

`.bss` 的 64KB 在二进制文件里只占段头几个字节，**烧录文件大小毫无变化，运行内存实打实多吃 64KB**——"固件下进去了但跑不起来"的第一大原因。工具链：`size mem`（GNU size 工具汇总 text/data/bss 三列）、`nm --size-sort -S mem | tail`（按大小排符号，找内存大户）。**链接脚本（linker script，.ld 文件）**定义这些段落到物理地址的映射（MCU：`.text` @FLASH、`.data` 初值 @FLASH + 运行 @RAM、`.bss` @RAM，启动代码把 .data 从 Flash 拷到 RAM、清零 .bss）；规划 RAM 的流程 = 列出所有全局/静态缓冲（模型输入输出、DMA 缓冲、栈、堆）→ 每项注明尺寸 → 与 RAM 预算核对。经验做法：**所有大缓冲用固定长度数组 + `static_assert(sizeof)` 记录在案，禁止"先 new 了再说"**。

## 4. 内存受限下的容器选择

### 4.1 vector 的正确打开方式

`std::vector` 在端侧可用，但必须**确定容量上限**：

```cpp
std::vector<Sample> ring;
ring.reserve(kMaxSamples);          // 预留：一次分配，杜绝扩容搬移
ring.resize(kMaxSamples);           // 或 resize 后用下标，容量恒定
shrink_to_fit();                    // 收缩（实现相关，微弱）
```

每次扩容是"分配 + 搬移 + 释放"，在内存紧张的堆里既慢又加剧碎片；**预留后的 vector 退化为定长数组语义**，大部分场景够用。彻底杜绝堆的方式见 4.2。

### 4.2 固定容量环形缓冲

《C++》系列 13 写过线程安全加锁版，第 05 章写过无锁 SPSC 版；嵌入式场景（无多线程竞争、无堆）最简版本：

```cpp
// ringbuf.hpp —— 定长环形缓冲：无堆、无锁（单读者单写者时）
#pragma once
#include <array>
#include <cstddef>

template <typename T, std::size_t N>
class RingBuffer {
    static_assert((N & (N - 1)) == 0, "N 必须是 2 的幂");
public:
    bool push(const T& v) {
        if (full()) return false;
        slots_[head_ & MASK] = v;
        ++head_;
        return true;
    }
    bool pop(T& out) {
        if (empty()) return false;
        out = slots_[tail_ & MASK];
        ++tail_;
        return true;
    }
    bool empty() const { return head_ == tail_; }
    bool full()  const { return head_ - tail_ == N; }
    std::size_t size() const { return head_ - tail_; }   // 无符号回绕
private:
    static constexpr std::size_t MASK = N - 1;
    std::array<T, N> slots_{};                            // 静态内联存储，零堆分配
    std::size_t head_ = 0, tail_ = 0;                     // 同线程访问时裸 size_t 即可
};
```

内存 = `N * sizeof(T)`，编译期确定，可直接 `static_assert` 进内存规划表。跨中断/线程时换第 05 章 SPSC（原子游标 + 内存序）。

### 4.3 池分配器完整实现

"对象数量已知、频繁创建销毁"（消息、任务块、网络包）用**定长块池**：分配 O(1)、无碎片、无锁竞争（每池单线程或加锁）：

```cpp
// pool.hpp —— 固定容量对象池（free list 实现）
#pragma once
#include <array>
#include <cstddef>

template <typename T, std::size_t N>
class ObjectPool {
    static_assert(N > 0);
public:
    ObjectPool() {
        for (std::size_t i = 0; i + 1 < N; ++i)
            free_[i].next = &free_[i + 1];      // 把所有块串成空闲链表
        free_[N - 1].next = nullptr;
        head_ = &free_[0];
    }
    T* acquire() {                              // O(1)；无异常环境返回 nullptr 表示耗尽
        if (!head_) return nullptr;
        Slot* s = head_;
        head_ = s->next;
        return &s->storage;
    }
    void release(T* p) {                        // O(1)；不调用析构（POD/消息体场景）
        Slot* s = reinterpret_cast<Slot*>(p);
        s->next = head_;
        head_ = s;
    }
    static constexpr std::size_t capacity() { return N; }
private:
    union Slot {                                // 空闲时当链表节点用，占用时当 T
        Slot* next;
        T storage;                              // storage 保证对齐与尺寸
        Slot() {}
        ~Slot() {}
    };
    Slot free_[N];
    Slot* head_ = nullptr;
};
```

要点：`union Slot` 让"空闲链表指针"与"对象存储"共用内存（free list 的标准技巧）；`acquire/release` 都是几次指针操作，时序确定——**实时性比平均速度重要时，池 > malloc**。用完池再往上是"整块 arena + reset"（第 06 章，每帧重置式）。`new`/`delete`、`malloc/free` 在 MCU 上的定位：**只在启动阶段用（构造静态结构），运行期禁用**（经验做法，MISRA/汽车行业惯例一致）。

## 5. 栈大小估算：-fstack-usage

栈溢出在 MCU 上是静默的硬故障（踩到别的内存，行为诡异），必须提前算。GCC 的 `-fstack-usage` 给每个函数生成 `.su` 文件：

```cpp
// su.cpp
int leaf(int a, int b) { int buf[16]; for (int i = 0; i < 16; ++i) buf[i] = a + b + i; return buf[15]; }
int big(int n)  { int buf[512]; for (int i = 0; i < 512; ++i) buf[i] = n + i; return leaf(buf[0], buf[511]); }
int main()      { return big(1); }
```

```bash
g++ -std=c++20 -Os -fstack-usage su.cpp && cat su.su
# 输出（真实）：
# su.cpp:1:5:int leaf(int, int)	96	static
# su.cpp:2:5:int big(int)	2080	static
# su.cpp:3:5:int main()	8	static
```

每行 = 函数自身栈用量（字节）；`big` 的 2080 = 512×4 的缓冲 + 帧开销。**总栈 = 调用链上各函数之和**（叶子路径）。三个工程工具：链最深路径的分析器（`puncover`、`stack_analyzer` 等读 ELF 自动算）；递归函数在端侧基本禁用（栈不可预测，改显式栈）；RTOS 里每线程栈独立配额（FreeRTOS `uxTaskGetStackHighWaterMark` 运行期校准）。经验做法：**估算值 × 1.5 起配，跑真实负载后用 high-water mark 收紧**。

## 6. 看门狗与喂狗模式

看门狗（watchdog）是"不喂就复位"的硬件倒计时，端侧可用性方案的最后防线。设计要点：

- **喂狗的不是定时器中断，而是主循环/工作线程**：中断里喂狗 = 中断活着但主逻辑死了照样不复位，防不住真正的卡死。MCU 模式：主循环每轮喂一次，轮内做"各任务心跳检查"。
- **多任务用"逻辑与"喂狗**：每个关键任务置自己的心跳位/时间戳，监控点检查全部新鲜才喂（FreeRTOS 的 task watchdog、Linux 的 systemd watchdog 同思想）。
- **喂狗节奏与最坏路径预算绑定**：把最慢一轮的执行时间（含最坏分支）测出来，超时时间 > 2× 最坏值；宁可偶尔复位，不可饿死不喂。
- Linux 侧（RK3588）：`systemd` 的 `WatchdogSec=` + 服务内定期 `sd_notify WATCHDOG=1`；推理进程在"帧处理循环"里喂，处理阻塞（NPU 超时、解码卡死）时由 systemd 拉起服务。

```cpp
// 伪码：逻辑与喂狗骨架
bool all_alive() {
    return now() - last_audio_heartbeat < 50ms
        && now() - last_infer_heartbeat < 500ms
        && npu_last_status_ok;
}
while (running) {
    step_audio(); step_infer(); step_ui();
    if (all_alive()) wdt_feed();          // 全部健康才喂
    else { log_fault(); wdt_feed_later_or_reboot(); }
}
```

## 7. 交叉编译与 CMake toolchain 文件

在 x86 开发机给 ARM 目标编译。工具链命名：`arm-none-eabi-gcc`（裸机/RTOS，无 OS 依赖，newlib 库）、`aarch64-linux-gnu-gcc`（ARM Linux，glibc）。RK3588 是后者（8 核 Cortex-A76/A55，跑 Debian/Android）；MCU（如 Cortex-M4）是前者。本机验证流程（未安装工具链时的安装与最小验证）：

```bash
sudo apt install gcc-arm-none-eabi          # MCU 交叉链
sudo apt install gcc-aarch64-linux-gnu      # ARM Linux 交叉链

# 最小验证：交叉编译 hello 并确认产物架构
cat > hello.c <<'EOF'
#include <stdio.h>
int main(void) { printf("hello cross\n"); return 0; }
EOF
aarch64-linux-gnu-gcc hello.c -o hello
file hello
# 输出：hello: ELF 64-bit LSB executable, ARM aarch64, ... dynamically linked
aarch64-linux-gnu-objdump -d hello | head    # 反汇编看到 aarch64 指令
# 传到目标板运行：scp hello board:~/ && ./hello
```

CMake 的跨平台支持点是 **toolchain 文件**（`-DCMAKE_TOOLCHAIN_FILE=...`，必须在首次 configure 给出）：

```cmake
# arm64.cmake —— aarch64-linux-gnu 交叉工具链
set(CMAKE_SYSTEM_NAME Linux)          # 目标系统（Generic = 裸机）
set(CMAKE_SYSTEM_PROCESSOR aarch64)
set(CMAKE_C_COMPILER   aarch64-linux-gnu-gcc)
set(CMAKE_CXX_COMPILER aarch64-linux-gnu-g++)
set(CMAKE_FIND_ROOT_PATH /usr/aarch64-linux-gnu)   # 库/头文件搜索根
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)       # 程序用宿主的
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)        # 库只找目标的
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
```

```bash
cmake -S . -B build-arm -DCMAKE_TOOLCHAIN_FILE=arm64.cmake -DCMAKE_BUILD_TYPE=Release
cmake --build build-arm
file build-arm/app      # 确认 aarch64
```

裸机工程额外需要 `CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY`（不允许试编可执行——没有标准库入口）与供应商链接脚本（`-T xxx.ld`）。**宿主机与交叉构建目录必须分开**（build / build-arm），toolchain 文件只影响新 configure（第 01 章"源码与构建分离"的直接延伸）。

## 8. RK3588 用户态接入 NPU：rknn_api 骨架

衔接《模型性能优化》Stage 4。RK3588 内置 6 TOPS NPU（3 核），用户态通过 **rknn-toolkit2（PC 上把模型转 .rknn）+ rknn runtime（板端 C API）**接入。板端 C 代码骨架（rknn_api.h，librknnrt.so）：

```cpp
// rknn_skel.cpp —— RKNN 推理最小骨架（编译：g++ ... -lrknnrt，在 RK3588 板上）
#include <rknn_api.h>
#include <cstdio>
#include <vector>

int main() {
    // 1) 加载 .rknn 模型（PC 端 rknn-toolkit2 从 ONNX 转出）
    FILE* f = fopen("model.rknn", "rb");
    fseek(f, 0, SEEK_END); long size = ftell(f); fseek(f, 0, SEEK_SET);
    std::vector<char> model(size);
    fread(model.data(), 1, size, f);
    fclose(f);

    // 2) 初始化 context（可指定 NPU 核心掩码）
    rknn_context ctx;
    if (rknn_init(&ctx, model.data(), size, 0, nullptr) != RKNN_SUCC) {
        std::printf("rknn_init 失败\n"); return 1;
    }

    // 3) 查询输入/输出张量属性（布局 NCHW/NHWC、量化类型）
    rknn_tensor_attr in_attr, out_attr;
    in_attr.index = 0;
    rknn_query(ctx, RKNN_QUERY_IN_ATTR, &in_attr, sizeof(in_attr));
    out_attr.index = 0;
    rknn_query(ctx, RKNN_QUERY_OUT_ATTR, &out_attr, sizeof(out_attr));

    // 4) 准备输入（NHWC uint8 量化场景直接喂；浮点模型喂 float32）
    std::vector<std::uint8_t> input(in_attr.size_with_stride);
    // ... 填充预处理后的图像数据（第 03 章 NEON 可用在 resize/normalize）...

    // 5) 设置输入 → 推理 → 取输出
    rknn_input in{};
    in.index = 0; in.type = RKNN_TENSOR_UINT8;
    in.fmt = RKNN_TENSOR_NHWC; in.buf = input.data(); in.size = input.size();
    rknn_inputs_set(ctx, 1, &in);
    if (rknn_run(ctx, nullptr) != RKNN_SUCC) { /* 错误处理：错误码风格 */ }

    std::vector<std::uint8_t> output(out_attr.size);
    rknn_output out{};
    out.index = 0; out.is_prealloc = 1; out.buf = output.data(); out.size = output.size();
    rknn_outputs_get(ctx, 1, &out, nullptr);   // 输出拷到预分配缓冲（零堆分配）

    // 6) 后处理（decode/softmax）+ 释放
    rknn_outputs_release(ctx, 1, &out);
    rknn_destroy(ctx);
    return 0;
}
```

读骨架能看出的工程要点：**输入输出的内存由调用方管理**（`is_prealloc` + 预分配 vector，符合本章"运行期禁堆"纪律）；量化模型喂 uint8（第 3 步查询决定），预处理与后处理都在 CPU 上（NEON 的地盘，第 03 章）；多核用 `RKNN_NPU_CORE_0_1_2` 掩码或三 context 并行。错过的细节（量化尺度 `zp/scale` 的反量化、零拷贝 API `rknn_create_mem`）在 Stage 4 展开。

## 常见误区

1. **`.bss` 大数组以为"不占空间"**：文件小、运行内存大（第 3 节实测 64KB），MCU 上直接链接失败或运行崩溃。内存规划表里它算满额。
2. **`-fno-exceptions` 下照写依赖异常的代码**：`throw` 编译成 `terminate`，`expected::value()` 无值时也是抛（退化 abort）。所有错误路径走错误码/`value_or`。
3. **运行期 malloc/free 撒着用**：碎片化让"总空闲充足却分不出连续块"。启动期一次性分配 + 池/arena。
4. **栈按"够用就行"拍脑袋**：`-fstack-usage` 逐函数给数，链最深路径求和 × 1.5；递归与 `alloca` 禁用。
5. **中断里喂狗 / 中断里做重活**：前者防不住主逻辑卡死，后者破坏实时性。喂狗放主循环 + 心跳聚合；重活放任务/线程。
6. **在 PC 上测完性能直接报给端侧**：交叉编译优化级别、缓存大小（RK3588 无 AVX，只有 NEON）、内存带宽都不同。性能数字必须在目标板上测（第 03 章的跨平台派发同理）。

## 本篇小结

- 端侧约束 = MB 级内存 + 无异常 + 实时性 + 看门狗；桌面三件套（异常/无界堆/无界容器）全部换装。
- 无异常风格：底层错误码 + 业务层 expected；`-fno-rtti` 用 variant/tag 替代 dynamic_cast。
- 静态内存：`.bss` 只占 RAM 不占 Flash（实测 64KB 数组），`objdump -h`/`size`/`nm --size-sort` 三件套规划；链接脚本映射段到物理地址。
- 容器：vector 必须 reserve 定容；定长环形缓冲与 union 槽位池分配器都是 O(1)、零堆；`new` 只在启动期。
- 栈：`-fstack-usage` 逐函数量化（leaf 96B / big 2080B 实测），最深链 × 1.5 起配。
- 交叉编译：toolchain 文件四行 + FIND_ROOT 三规则；RK3588 用 rknn_api 的预分配输入输出骨架接 NPU。
