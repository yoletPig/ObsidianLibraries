## 1. 锁的代价：什么时候不可接受

先实测三种互斥手段的真实成本（单线程、临界区只有 `++c`）：

```cpp
// lockcost.cpp —— 单线程空临界区成本
#include <chrono>
#include <iostream>
#include <mutex>

class Spinlock {
    std::atomic_flag f = ATOMIC_FLAG_INIT;
public:
    void lock()   { while (f.test_and_set(std::memory_order_acquire))
                        { while (f.test(std::memory_order_relaxed)) {} } }  // 先纺线再争
    void unlock() { f.clear(std::memory_order_release); }
};

int main() {
    const long ITERS = 10'000'000;
    using clk = std::chrono::steady_clock;
    long c = 0;
    auto t0 = clk::now();
    { std::mutex m; for (long i = 0; i < ITERS; ++i) { std::lock_guard<std::mutex> g(m); ++c; } }
    auto t1 = clk::now();
    { Spinlock s; for (long i = 0; i < ITERS; ++i) { std::lock_guard<Spinlock> g(s); ++c; } }
    auto t2 = clk::now();
    std::cout << "mutex    : " << std::chrono::duration<double, std::milli>(t1 - t0).count()
              << " ms\n";
    std::cout << "spinlock : " << std::chrono::duration<double, std::milli>(t2 - t1).count()
              << " ms\n";
}
```

```bash
g++ -std=c++20 -O2 -pthread lockcost.cpp -o lockcost && ./lockcost && ./lockcost
# 输出（i5-12600K 实测两次）：
# mutex    : 25.2451 ms        → 每次 lock/unlock ≈ 2.5 ns
# spinlock : 56.2891 ms        → ≈ 5.6 ns（atomic RMW 全栅栏反而更贵）
# mutex    : 24.987 ms
# spinlock : 59.0186 ms
```

反直觉但真实：**无争抢时 libstdc++ 的 mutex 走 futex 快路径（用户态一条原子交换），比朴素自旋锁还快**。所以"锁很贵"的直觉只对了一半。再看 4 线程争抢同一把锁（每线程 5M 次 `lock_guard` + `++v`）：

```text
4 线程争抢 mutex    : 854-868 ms   （含 futex 睡眠/唤醒的系统调用）
4 线程争抢 spinlock : 1301-1332 ms （缓存行在 4 个核之间弹跳，纺线烧满 CPU）
4 线程 atomic fetch_add(同一变量, relaxed): 220-238 ms
```

结论（实测得出，不是背书）：**锁的真正代价来自"争抢"而非"加锁"**。临界区极短（几十纳秒）且争抢激烈时，锁的睡眠/唤醒开销才不可接受——这正是无锁队列的用武之地：**生产者-消费者之间只有一个指针游标，没有临界区可言**。反过来，临界区里有任何实际工作（查表、拷贝、计算），锁的开销立刻摊薄到可忽略。

## 2. 无锁 SPSC 环形队列：逐行讲内存序

先立定义（[intro.progress] 的惯用归纳）：**无锁（lock-free）** = 任意时刻停下所有线程，至少有一个能取得进展（个别线程卡住不拖累全局）；**有界等待**更进一步。SPSC（Single-Producer Single-Consumer）是唯一容易做对的无锁结构：**每个游标只有一个写者、一个读者**，这把同步需求压到最低——一处 release/acquire 配对。

完整实现（已在真实环境编译运行验证）：

```cpp
// spsc_queue.h —— 无锁 SPSC 环形队列（rigtorp/SPSCQueue 同款思想的教学简化版）
#pragma once
#include <atomic>
#include <cstddef>
#include <new>
#include <type_traits>

constexpr size_t next_pow2(size_t v) noexcept {
    size_t p = 1;
    while (p < v) p <<= 1;
    return p;
}

template <typename T>
class SpscQueue {
    static_assert(std::is_nothrow_move_constructible_v<T> ||
                  std::is_nothrow_copy_constructible_v<T>,
                  "T 必须可 noexcept 拷贝或移动，保证队列不变量不被异常破坏");
public:
    explicit SpscQueue(size_t capacity)
        : capacity_(next_pow2(capacity)),
          slots_(static_cast<Slot*>(::operator new(sizeof(Slot) * capacity_))) {}
    ~SpscQueue() { T t; while (pop(t)) {} ::operator delete(slots_); }

    SpscQueue(const SpscQueue&) = delete;
    SpscQueue& operator=(const SpscQueue&) = delete;

    // 【仅允许唯一生产者线程调用】
    bool push(const T& v) {
        const size_t head = head_.load(std::memory_order_relaxed); // 只被生产者写，读到的是自己刚写的
        const size_t tail = tail_.load(std::memory_order_acquire); // 读消费者进度：要看到消费者 release 的“已腾出”
        if (head - tail == capacity_) return false;                // 差值即元素个数（无符号回绕自动取模）
        ::new (static_cast<void*>(&slots_[idx(head)].storage)) T(v);
        head_.store(head + 1, std::memory_order_release);          // 发布新元素给消费者
        return true;
    }

    // 【仅允许唯一消费者线程调用】
    bool pop(T& out) {
        const size_t tail = tail_.load(std::memory_order_relaxed); // 只被消费者写
        const size_t head = head_.load(std::memory_order_acquire); // 读生产者进度：要看到 release 的新元素
        if (tail == head) return false;                            // 空
        T* p = static_cast<T*>(static_cast<void*>(&slots_[idx(tail)].storage));
        out = std::move(*p);
        p->~T();
        tail_.store(tail + 1, std::memory_order_release);          // 发布“槽位已腾出”给生产者
        return true;
    }

private:
    struct Slot {
        // 教学版直接用槽位存储做同步；rigtorp 版每个槽位多一个 seq 序号字段，
        // 用于支持 MPMC 化与更细的就绪标记——这里靠“唯一读者/唯一写者”前提省掉
        typename std::aligned_storage_t<sizeof(T), alignof(T)>::type storage;
    };
    size_t idx(size_t i) const noexcept { return i & (capacity_ - 1); } // 位与代替取模（容量 2 的幂）

    const size_t capacity_;
    Slot* slots_;
    alignas(64) std::atomic<size_t> head_{0}; // 生产者游标：生产者 store / 消费者 load，独占缓存行
    alignas(64) std::atomic<size_t> tail_{0}; // 消费者游标：消费者 store / 生产者 load，独占缓存行
};
```

内存序逐处复盘（配合第 04 章的 happens-before 图）：

| 位置 | 内存序 | 为什么 |
| --- | --- | --- |
| `push` 读 `head_` | relaxed | 本线程是唯一写者，读到的是自己写的值，无同步需求 |
| `push` 读 `tail_` | acquire | 要“看见”消费者 release 的腾出动作，确认槽位可覆写 |
| `push` 写 `head_` | release | **发布**：placement new 写入的 `T` 对消费者可见的前置条件 |
| `pop` 读 `tail_` | relaxed | 同 push/head 的镜像 |
| `pop` 读 `head_` | acquire | 要“看见”生产者发布的新元素 |
| `pop` 写 `tail_` | release | 发布“已取走”，让生产者能覆写该槽位 |
| 两个游标 `alignas(64)` | — | 伪共享隔离（第 04 章），否则一读一写在同一行互相弹 |

测试（生产者推 1..1000000，消费者求和核对）：

```cpp
// spsc_test.cpp
#include "spsc_queue.h"
#include <cstdio>
#include <thread>

int main() {
    const size_t N = 1'000'000;
    SpscQueue<int> q(1024);
    std::thread consumer([&] {
        int v; unsigned long long s = 0, got = 0;
        while (got < N)
            while (q.pop(v)) { s += static_cast<unsigned long long>(v); ++got; }
        std::printf("sum=%llu count=%llu\n", s, got);
    });
    for (size_t i = 1; i <= N; ++i) { while (!q.push(static_cast<int>(i))) {} }
    consumer.join();
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra -pthread spsc_test.cpp -o spsc_test && ./spsc_test
# 输出：sum=500000500000 count=1000000     # 与等差数列公式 1000000*1000001/2 一致
```

注意两个设计取舍：**满/空时返回 false 而不是阻塞**（把"等待策略"留给调用方——音频线程 `while(!push)` 忙等、控制线程挂条件变量，队列本身保持无锁）；**容量取 2 的幂**，用位与代替取模。rigtorp/SPSCQueue 在此基础上加了缓存行预取与 per-slot seq，folly 版还支持批量推拉，思想同源。

## 3. MPSC 概览：多个生产者怎么办

SPSC 的极限场景之外，更多是 MPSC（多生产者单消费者：日志聚合、GPU 命令队列）与 MPMC（线程池任务队列）。生产者多于一个后，`head_` 变成多个写者——单一 release/acquire 不再够，典型做法：

- **CAS 竞争游标**（`compare_exchange_weak` 抢占 head）+ **两阶段提交**：先 CAS 占坑，写完数据再把"就绪序号"发布，消费者只能消费连续就绪区间（folly::MPMCQueue、moodycamel::ConcurrentQueue 的思路）。
- **每生产者一条 SPSC 队列**，消费者轮询（round-robin）多条 SPSC——把 MPMC 问题降维成已解决的 SPSC 问题。实现简单、无 CAS 风暴，代价是消费者公平性需要自己调度。经验做法：**生产者数固定且不大时，先选这条**。

MPSC/MPMC 的实现复杂度跨过 SPSC 一个数量级，几乎总是应该直接用 folly/moodycamel/boost::lockfree，而不是手写（经验做法，见第 6 节的"该不该"）。

## 4. Hazard Pointer：为什么无锁回收内存难

SPSC 队列的内存是预分配环形数组，没有回收问题。但无锁**栈/链表**（如 Treiber stack）把节点 new/delete 混进并发路径，立刻撞上难题：

```
线程 A 读到节点 X 的指针，还没来得及解引用
线程 B 把 X 从栈上摘除并 delete
线程 A 解引用 X —— use-after-free
```

难点在于：A 持有的只是"一个副本"，B 无法知道"还有人要读"。经典方案 **Hazard Pointer（危险指针）**：

1. 每个读者线程有若干"危险指针"槽（公开可见的原子槽位）。
2. 读者解引用前，先把指针副本发布到自己的 hazard 槽，再回头验证节点还在链上（否则重来）。
3. 删除者把节点挂到"待删清单"，**只有当任何 hazard 槽都不再指向它**时才真正 free。

验证-发布之间存在竞争窗口，所以要"发布 → 复查 → 不在则重试"的两步协议。Michael 2004 的论文（Hazard Pointers: Safe Memory Reclamation）是原始出处；C++ 上的成熟实现见 folly 的 `hazard` 模块。替代思路 **Epoch-Based Reclamation（EBR）**：读者进入临界区登记"epoch"，回收者等全局 epoch 推进（所有读者都离开旧 epoch）后整批回收——检查 O(1)，代价是回收有延迟。

## 5. RCU 概念：读侧几乎零开销

RCU（Read-Copy-Update，Linux 内核大规模使用）把上述思想推到极致，服务"读多写极少"的数据（路由表、配置）：

- **读者**：进_rcu → 读指针副本 → 用 → 出_rcu。全程**无原子操作、无锁、无内存写**（编译器屏障级别）。
- **写者**：复制一份新结构 → 在副本上修改 → 原子地替换根指针 → 等"宽限期"（grace period，所有旧读者离开）→ 释放旧副本。

读者完全不感知写者的存在，读路径开销接近零；代价由写者承担（复制 + 等待 + 写多时副本爆炸）。与 Hazard Pointer 的关系：都是"延迟回收"，RCU 把"谁还在读"的判定从逐指针验证变成全局 epoch 推进。C++ 用户态可参考 liburcu（Userspace RCU）。经验做法：**配置/参数表这类"分钟级才改一次、纳秒级读一次"的数据，RCU 或 `shared_ptr` 原子交换（copy-on-write）都远好于读写锁**。

## 6. 无锁不等于更快：CAS 重试风暴实测

最常见的迷信："锁有系统调用开销，无锁一定快"。用计数器做反例——三种实现完成同样的"4 线程各 1000 万次 +1"：

```cpp
// castorm.cpp —— CAS 重试风暴 vs fetch_add vs mutex
#include <atomic>
#include <chrono>
#include <iostream>
#include <mutex>
#include <thread>
#include <vector>

template <typename F>
void bench(const char* name, F&& f) {
    auto t0 = std::chrono::steady_clock::now();
    f();
    auto t1 = std::chrono::steady_clock::now();
    std::cout << name << ": " << std::chrono::duration<double, std::milli>(t1 - t0).count() << " ms\n";
}

int main() {
    const int N = 4;
    const long ITER = 10'000'000;
    bench("mutex 加锁++   ", [=]{
        long v = 0; std::mutex m;
        std::vector<std::thread> ts;
        for (int i = 0; i < N; ++i) ts.emplace_back([&]{ for (long j = 0; j < ITER; ++j) { std::lock_guard<std::mutex> g(m); ++v; } });
        for (auto& t : ts) t.join();
        (void)v;
    });
    bench("atomic fetch_add", [=]{
        std::atomic<long> v{0};
        std::vector<std::thread> ts;
        for (int i = 0; i < N; ++i) ts.emplace_back([&]{ for (long j = 0; j < ITER; ++j) v.fetch_add(1, std::memory_order_relaxed); });
        for (auto& t : ts) t.join();
    });
    bench("CAS 循环++    ", [=]{
        std::atomic<long> v{0};
        std::vector<std::thread> ts;
        for (int i = 0; i < N; ++i) ts.emplace_back([&]{
            for (long j = 0; j < ITER; ++j) {
                long cur = v.load(std::memory_order_relaxed);
                while (!v.compare_exchange_weak(cur, cur + 1, std::memory_order_relaxed)) {}
            }
        });
        for (auto& t : ts) t.join();
    });
}
```

```bash
g++ -std=c++20 -O2 -pthread castorm.cpp -o castorm && ./castorm && ./castorm
# 输出（i5-12600K 实测两次）：
# mutex 加锁++   : 1642.6 ms
# atomic fetch_add: 454.813 ms
# CAS 循环++    : 829.961 ms
# mutex 加锁++   : 1714.51 ms
# atomic fetch_add: 451.71 ms
# CAS 循环++    : 879.939 ms
```

读数：CAS 循环比 `fetch_add` 慢一倍。原因——`fetch_add` 是硬件原子的读改写（x86 上 `lock xadd`，一条指令成功）；CAS 循环在 4 线程争抢同一缓存行时**反复冲突重试**，每次失败都要重新 load 再交换，还制造额外的缓存一致性流量。"手写的乐观并发"在没有硬件原子原语支持时就是这个下场。真正的教训不是"CAS 不行"，而是：

1. **有硬件原子原语（fetch_add/fetch_or/…）就别手搓 CAS 循环**；
2. **争抢的根源是"共享写热点"，解法是消除热点而不是换同步原语**（分片计数再汇总、每线程局部缓冲）；
3. 无锁结构赢在"临界区为零 + 无系统调用"，不是赢在"用了 atomic"。

## 7. 什么时候该用无锁（经验做法）

按可维护性与收益排序的决策阶梯：

1. **默认：`std::mutex` + RAII 锁**。临界区 ≥ 1μs 或每秒次数 < 10 万，锁的成本根本测不出来；可读性、可调试性（死锁能 dump 栈，无锁只能看汇编）完胜。
2. **单变量协调：atomic 标志/游标/计数**。这不算"无锁编程"，是标准工具（《C++》系列 12）。
3. **生产者-消费者管线：无锁 SPSC 队列**。音频采集→推理、采样→渲染这类"每几十微秒过一小块数据"的固定管线，SPSC 是收益最确定的无锁结构（rigtorp/SPSCQueue 可直接用）。
4. **其余无锁结构（栈/哈希/MPMC）：直接用 folly/boost::lockfree/moodycamel，不要手写**。内存回收（Hazard Pointer/EBR）与 ABA 的坑在第 4 节已经看到，手写正确的工程量以月计。

**99% 的场景应该用锁 + 少量原子变量；剩下的 1% 里，SPSC 队列又占大头**——这是并发工程里少有的可以放心说的经验法则。

## 常见误区

1. **以为无锁 = 不用锁 = 快**：第 6 节实测 CAS 循环慢 fetch_add 一倍。无锁的收益来自结构设计，不是原子原语的堆砌。
2. **SPSC 队列被两个线程 push**：SPSC 的全部正确性建立在"游标单写者"上，生产者多一个，队列立刻变成未定义行为。用 `static_assert`/类型系统外的纪律（命名、断言、文档）守住这个前提。
3. **在无锁代码里调用可能异常的代码**：placement new 后 `T` 的拷贝构造抛异常，游标已推进，队列状态损坏。这就是实现里 `static_assert` 要求 `noexcept` 构造的原因。
4. **忙等不用 `pause`/让出**：`while (!push(v)) {}` 在单核或超线程上空转会拖死伙伴线程。生产环境要么挂 `std::this_thread::yield()`，要么限制重试次数后退避（经验做法）。
5. **用 `volatile` 写无锁**：第 04 章讲过，volatile 无原子性无内存序，无锁代码里它唯一的用途是 MMIO（嵌入式），不是线程同步。
6. **忘测消费者追不上生产者的"满"路径**：环形队列的满/空边界是竞争高发区，测试必须同时覆盖"队列空转"与"队列打满"两种稳态。

## 本篇小结

- 锁的真实代价 = 争抢成本：无争抢 mutex ≈ 2.5ns（futex 快路径），4 线程争抢短临界区时 mutex/自旋锁都跌进 850-1330ms 量级而原子游标 220ms——短临界区高争抢才需要无锁。
- SPSC 环形队列是无锁入门标准案例：游标单写者 + 一对 release/acquire 发布 + alignas(64) 防伪共享 + 容量 2 的幂；满/空返回 bool 把等待策略留给调用方。
- MPSC 优先"每生产者一条 SPSC + 消费者轮询"；MPMC 直接用 folly/moodycamel。
- 无锁内存回收难在"删除者不知道有没有读者"：Hazard Pointer 逐指针验证、EBR/RCU 用全局 epoch 延迟回收；读多写少用 RCU/copy-on-write。
- CAS 重试风暴实测（830ms vs fetch_add 452ms）证明无锁不等于更快；99% 用锁 + 少量原子，1% 里优先 SPSC。
