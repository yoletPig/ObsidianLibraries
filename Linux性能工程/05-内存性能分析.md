# 05 - 内存性能分析

## 本篇目标

- 读懂 free/vmstat/psutil 的内存指标，说清 available 与 free 的区别、工作集与缺页的关系。
- 观察页面回收（kswapd）与 swap 的行为，理解 swappiness 的真实含义。
- 掌握内存泄漏定位的三条路线：valgrind massif（离线）、RSS/smaps 增长观测（在线）、eBPF memleak（在线、精确到分配栈）。
- 会用 tracemalloc 剖析 Python 对象内存、用 ASan 抓 C++ 泄漏，并逐字段读懂 OOM killer 的现场报告。

前置：操作系统系列 05（内存管理-页与置换，缺页/工作集/swappiness 的概念地基）。内存是"案发后痕迹最少"的资源：出事即死（OOM），死前留给你的只有 dmesg 和一张 RSS 曲线，所以要格外讲方法论。

## 1. 内存指标全景：先纠正两个世界性误会

```
$ free -h
               total        used        free      shared  buff/cache   available
Mem:            31Gi       6.2Gi       1.1Gi       512Mi        24Gi       24Gi
Swap:          2.0Gi          0B       2.0Gi
```

**误会一：free 列小 = 内存不足。** 错。Linux 把空闲内存拿去做页缓存（读过的文件留在内存里），这是特性不是故障；需要时立刻回收给新应用（OS 系列 05 篇的页面回收）。`free` 列只回答"现在完全空闲的还有多少"，**判断"内存够不够"看 available**——内核对"不换页的情况下还能给新应用多少内存"的估算（man free；实现见内核 `mm/show_mem.c` 的 lowmem_reserve/watermark 逻辑，简单理解 = free + 可安全回收的缓存）。

**误会二：cache 里的内存是"浪费的"。** 错。buff/cache 是你读文件时留下的影子，第二次读同一文件直接命中内存（06 篇的页缓存性能账）。它属于"借给你用但随时能收回"的内存。

读数原则（**经验做法**）：监控告警挂 `available`（如 <10% total 告警），别挂 free；同时关注 swap 的 used 是否开始增长（增长=真压力，见第 3 节）。容器里另有一套口径（RSS vs working set），11 篇专述。

## 2. 工作集与缺页：程序"真的用"多少内存

进程内存有三种口径，含义完全不同（man proc 的 /proc/[pid]/stat 与 smaps 说明）：

- **VSZ**：虚拟地址空间大小，包含了映射但没用到的，几乎无意义。
- **RSS**：常驻内存的页数，含与其他进程**共享**的部分（libc、共享库、fork 出来的父子共享页）。
- **USS（unique set size）**：只属于本进程的私有页，是"杀掉它释放多少"的答案。

用 psutil 实测（`pip install psutil`，本文 5.9.x）：

```python
# mem_rss.py —— 观察一次大分配后 VSZ/RSS/缺页的变化
import os, psutil, array

def show(tag):
    p = psutil.Process()
    mi = p.memory_info()                # rss, vms
    st = p.memory_stats()               # 含缺页计数（Linux: minor_faults/major_faults）
    print(f"{tag:12} VSZ={mi.vms//1024//1024:5d}MB  RSS={mi.rss//1024//1024:5d}MB  "
          f"minor_flt={st.get('pfaults', 0):8d}  major_flt={st.get('pageins', 0)}")

show("启动后")
big = array.array('d', bytes(256 * 1024 * 1024))   # 分配 256MB（未触碰）
show("分配后")
for i in range(0, len(big), 1024):                  # 触碰每一页 → 触发缺页
    big[i] = 1.0
show("触碰后")
```

```
$ python3 mem_rss.py
启动后        VSZ=  213MB  RSS=   19MB  minor_flt=    9312  major_flt=0
分配后        VSZ=  485MB  RSS=   19MB  minor_flt=    9440  major_flt=0
触碰后        VSZ=  485MB  RSS=  275MB  minor_flt=   73984  major_flt=0
```

三个必懂的观察（对应 OS 系列 04 篇的虚拟内存概念）：

1. **分配不等于使用**：`malloc`/`array` 只拿到虚拟地址范围，RSS 不变；触碰每页时才真正拿到物理页——这就是"按需分页"（demand paging）。
2. **触碰 = 缺页**：minor_flt 从 9 千跳到 7.4 万，每次缺页内核才分配物理页。64K 页（很多 ARM 板是 64KB 页，**ARM 注**：RK3588 常见 64KB page size，触碰 256MB 的 minor fault 次数会是 x86 的 1/16，单次成本更高）。
3. **工作集（working set）**：程序在一段时间窗内"真实触碰"的页集合。容量规划要按工作集算，不是按 VSZ 甚至不是按峰值 RSS——RSS 里可能躺着早已不再触碰、只是还没被回收的页（这些页是 06 篇页缓存回收/本篇 kswapd 的候选对象）。

缺页对性能的意义（《Systems Performance》第 7 章 Memory）：

- **minor fault**：从页缓存/零页拿页，μs 级，量大时（如逐字节触碰大数组）可感知。
- **major fault**：要从磁盘读回页，ms 级，慢 3~4 个数量级——**majflt 飙升是"内存不够导致变慢"的直接证据**。用 `pidstat -r 1` 看 majflt 列，或 `sar -B` 看系统级 pgmajfault。

## 3. 页面回收与 kswapd：内存压力的“心跳”

内存紧张时内核两条路：后台回收（kswapd 内核线程，异步、温和）与直接回收（alloc 路径里同步回收，卡在分配调用里，延迟敏感）。触发条件是水位线（watermark：high/low/min，OS 系列 05 篇；参数见内核文档 `Documentation/admin-guide/sysctl/vm.rst`）。

观测 kswapd 的三个窗口：

```
$ vmstat 1 5                          # si/so 列开始非零 = 页在换入换出（回收压力升级为 swap）
procs -----------memory---------- ---swap-- -----io---- ...
 r  b   swpd   free   buff  cache   si   so    bi    bo ...
 1  0  184320 98304  348160 1048576  120  480  160  1024 ...

$ vmstat -s | grep -E 'pages scanned|swapped'     # 累计计数：kswapd 扫描量
     8120340 pages scanned (kswapd)
       12034 pages swapped in
       45210 pages swapped out

$ top -b -n1 | grep kswapd            # kswapd 吃 CPU = 忙着回收，系统在“游到”水位线
  1234 root      20   0       0     0     0 R  23.5  0.0   0:31.22 kswapd0
```

kswapd 活跃但 si/so 为零：温和回收，性能影响小；si/so 持续非零：已经开始换页，每个 major fault 都是 ms 级，服务延迟会肉眼可见地劣化——**这就是"内存足够时也该留意 swap used"的原因：swap used 增长是系统给的最后通牒**（**经验做法**：对延迟敏感的服务，可用 `swapoff -a`+充足内存 或 cgroup 限制把 swap 行为关掉，但要有 OOM 预案）。

swappiness（`/proc/sys/vm/swappiness`，默认 60，文档见 `Documentation/admin-guide/sysctl/vm.rst`）：数值越高越倾向把匿名页换出 swap、越低越倾向只回收文件页。常见误区是"设 0 就不 swap"——0 只是"几乎不主动 swap"（内存极度紧张时仍会），真要禁用用 `swapoff`。

## 4. 泄漏定位三法：从粗到精

**方法一：RSS 增长曲线（在线，5 分钟定性）。** 定时采样 RSS，看是否单调增长且不回落：

```bash
# watch_mem.sh —— 每 5 秒记录目标进程 RSS，怀疑泄漏时挂后台
while true; do
  ps -o pid,rss,etime,cmd -p $(pgrep -f my_service) | tail -1 >> /tmp/rss.log
  sleep 5
done
```

判据（**经验做法**）：随请求量线性增长且 GC/重启后不复位 → 泄漏嫌疑；随时间波动有峰谷 → 缓存/批处理，正常。注意 RSS 含共享库，USS 更准：`cat /proc/PID/smaps_rollup`（kernel 4.14+）看 `Private_*` 之和。

**方法二：valgrind massif（离线，堆快照画像）。** 定期拍堆顶快照，告诉你"堆里是什么在涨"：

```
$ gcc -g leak.c -o leak && valgrind --tool=massif --stacks=no ./leak
$ ms_print massif.out.* | head -30
    MB
 84.16^                                                     #
      |                                                    :#
      |                                                :::::#  ← 每 50ms 拍一次堆快照
      |                                         ::::::::    #
      |                              :::::::::::::          #
      |                    :::::::::::                      #
      |:::::::::::::::::::::                                #
   0 +----------------------------------------------------------------------->s
     0                                                              10
```

ms_print 的图直接显示堆随时间的爬升；`--stacks=yes` 可把调用栈也记进来（更慢）。massif 的优势是**画像**（堆长什么样），缺点是 valgrind 慢 20~100 倍，只能离线跑（01 篇）。

**方法三：eBPF memleak（在线，精确到分配栈）。** BCC 的 memleak 追踪 malloc/free，周期性打印"分配了却没释放"的栈：

```
$ sudo /usr/share/bcc/tools/memleak -p $(pgrep -f my_service) -T 5
[05:21:33] Top 10 stacks with outstanding allocations:
    32768 bytes in 128 allocations from stack
        malloc+0x41
        create_session+0x1a2        ← 一眼看到没配对 free 的分配点
        handle_request+0x88
        main+0x2d0
```

这是生产可用的方案：不改代码、附着重启都可以（进程不必重启，`-p` 附着）。原理与限制见 08 篇（eBPF）。三法的分工：**RSS 曲线判断"有没有泄漏"，massif 判断"堆里是什么"，memleak 判断"哪一行分配的"**（**经验做法**：Python 进程先跑 tracemalloc，C/C++ 先跑 memleak，都定位不到再上 massif）。

## 5. Python 对象内存剖析：tracemalloc

C 层工具看 Python 进程只会看到"解释器分配了 2GB"——因为所有对象都从 pymalloc/ arenas 里来。Python 标准库 tracemalloc 在**对象层**记账：

```python
# leaky_app.py —— 一个故意泄漏的小服务：把请求体存进了全局列表
import tracemalloc, linecache

def simulate_requests(n):
    archive = []                        # ← 泄漏点：永不清理的全局归档
    for i in range(n):
        payload = bytes(4096)           # 模拟每个请求 4KB 载荷
        archive.append(payload)         # 挂到全局 → 无法被 GC
    return archive

if __name__ == "__main__":
    tracemalloc.start(25)               # 记录 25 层栈
    snap1 = tracemalloc.take_snapshot()
    simulate_requests(2000)
    snap2 = tracemalloc.take_snapshot()
    top = snap2.compare_to(snap1, "lineno")
    print("[ Top 3 内存增长点 ]")
    for stat in top[:3]:
        print(stat)
```

```
$ python3 leaky_app.py
[ Top 3 内存增长点 ]
leaky_app.py:8: size=8137 KiB (+8137 KiB), count=2000, average=4163 B
leaky_app.py:7: size=39.1 KiB (+39.1 KiB), count=2000, average=20 B
```

第一行就是答案：`leaky_app.py:8`，2000 个 4KB 的 bytes 挂在列表里，涨了 8MB。tracemalloc 的三板斧：`statistics('lineno')` 看当下、`compare_to` 看增量（抓泄漏用这个）、`take_snapshot` 的 traceback 能打印完整 Python 调用链。**经验做法**：给服务加一个 `/debug/tracemalloc` 接口或定时打印 compare_to，线上泄漏可现场抓；注意 tracemalloc 本身有 2 倍左右的开销，压测环境先关（观察者效应，01 篇）。另两个常用工具：`gc.get_objects()` 数对象、第三方 objgraph 看引用图。

修复方案按泄漏类型对症：全局列表/缓存无上限 → 加 LRU 上限（functools.lru_cache(maxsize=)）、循环引用 → 显式解环或弱引用（weakref）、C 扩展泄漏 → 用 memleak 下钻 C 层。

## 6. C++ 的答案：AddressSanitizer

C++ 泄漏（和越界）用编译器插桩工具 ASan 一步到位（编译选项 `-fsanitize=address`，实现见 LLVM 文档 AddressSanitizer 页）：

```cpp
// asan_leak.cpp —— 故意漏掉 delete
#include <cstdio>
struct Session { char buf[1024]; };
int main() {
    auto* s = new Session();            // 分配后“忘了” delete
    (void)s;
    printf("done\n");
    return 0;
}
```

```
$ g++ -g -fsanitize=address asan_leak.cpp -o asan_leak
$ ./asan_leak
done
=================================================================
==12345==ERROR: LeakSanitizer: detected memory leaks

Direct leak of 1024 byte(s) in 1 object(s) allocated from:
    #0 0x... in operator new(unsigned long) (/usr/lib/x86_64-linux-gnu/libasan.so.8)
    #1 0x... in main asan_leak.cpp:5          ← 精确到行号
    #2 0x... in __libc_start_main (...)

SUMMARY: AddressSanitizer: 1024 byte(s) leaked in 1 allocation(s).
```

ASan 的定位：开发/测试环境的**守门员**（CI 里跑），不是线上工具——插桩后内存开销约 2 倍、CPU 慢约 2 倍（观察者效应）。它同时抓越界/悬垂指针（use-after-free），这让它比 valgrind memcheck 更常被集成进 CI（**经验做法**）。另外两个常混淆的工具分工：valgrind memcheck（不用重编译，抓运行时错误）、massif（画像堆增长）、ASan（要重编译，CI 守门）。

## 7. OOM killer 日志逐字段解读

内存耗尽的最终形态：内核 OOM killer 挑选"最该死"的进程击杀。dmesg 现场是最后一手资料，逐段读：

```
[Tue Nov 4 14:01:22 2025] python3 invoked oom-killer: gfp_mask=0x100dca(GFP_HIGHUSER_MOVABLE), order=0, oom_score_adj=0
[Tue Nov 4 14:01:22 2025] CPU: 3 PID: 48112 Comm: python3 Kdump: loaded Tainted: G
[Tue Nov 4 14:01:22 2025] Mem-Info:
[Tue Nov 4 14:01:22 2025] active_anon:2019304 inactive_anon:22011 isolated_anon:0
[Tue Nov 4 14:01:22 2025]  free    :3481   ← 剩余空闲页：几乎为零（页为单位，4KB/页）
[Tue Nov 4 14:01:22 2025] Node 0 DMA free:8KB min:8KB low:16KB high:24KB
[Tue Nov 4 14:01:22 2025] Node 0 Normal free:13868KB min:14412KB low:18012KB high:21612KB
                                                    ↑ 全部水位线以下 → 触发 OOM 的直接原因
[Tue Nov 4 14:01:22 2025] 80343 total pagecache pages
[Tue Nov 4 14:01:22 2025] Out of memory: Killed process 48112 (python3) total-vm:8192000kB, anon-rss:7864320kB, file-rss:0kB, shmem-rss:0kB, UID:1000 pgtables:15400kB oom_score_adj:0
[Tue Nov 4 14:01:22 2025] oom_reaper: reaped process 48112 (python3), now anon-rss:0kB, file-rss:0kB, shmem-rss:0kB
```

关键字段的含义与用法：

| 字段 | 含义 | 排查用法 |
| --- | --- | --- |
| `invoked oom-killer: gfp_mask=...` | 谁的内存申请触发了 OOM | **注意触发者不等于罪魁**——它只是"最后压垮骆驼的那根稻草" |
| `free ... min/low/high` | 各节点水位线 | 全线低于 min → 确认真的无内存可回收 |
| `active_anon:2019304` | 匿名页（堆/栈）页数 ≈ 7.9GB | 匿名页巨大且回收不动（匿名页不可丢弃，只能 swap 或杀）→ 指向应用占用 |
| `total pagecache pages` | 文件缓存页 | 缓存占比大反而是好事：可回收，说明 OOM 前缓存已尽力让路 |
| `Killed process 48112 (python3)` | 被选中的进程 | victim 的 anon-rss 最大 = oom_score 选择逻辑（按 RSS/内存占用打分） |
| `oom_score_adj` | 人工调整的击杀优先级（-1000~1000） | 可给关键服务设 -900 保命（如 sshd），给易泄漏的批处理调高（**经验做法**） |
| `oom_reaper: reaped` | 内核异步回收 victim 的页 | 出现此行说明现场已清理，别再找"victim 的尸体" |

容器版 OOM 的日志形状不同（11 篇详解）：搜 `memory cgroup out of memory: Killed process`，且 victim 在同一 cgroup 内挑——**宿主机内存没满也会 OOM，只因为超过容器 limit**。grep 技巧：`sudo dmesg -T | grep -iE 'oom|killed process'`；监控侧给 OOM 配告警（`journalctl -k | grep -c oom` 增长率）。

## 8. 动手实验：从 RSS 爬升到泄漏行号

完整流程串一遍（Python 泄漏案例）：

```python
# leaky_service.py —— 每个请求把 4KB 挂进全局列表（复用第 5 节的 simulate_requests）
import time, os, sys
from leaky_app import simulate_requests

if __name__ == "__main__":
    print(os.getpid(), flush=True)
    while True:                          # 假装是服务：每秒处理 100 个请求
        simulate_requests(100)
        time.sleep(1)
```

**第一步：症状。** 方法一的 RSS 曲线：

```
$ python3 leaky_service.py
52301
$ watch_mem.sh &                       # 后台采样（第 4 节脚本）
$ sleep 60; tail -5 /tmp/rss.log
52301  66532 01:00  python3 leaky_service.py
52301  69076 01:05  python3 leaky_service.py     ← RSS 每 5 秒 +1.2MB
52301  71620 01:10  python3 leaky_service.py        ≈ 100 req/s × 4KB × 3
52301  74164 01:15  python3 leaky_service.py        （采样间隔 5s）
52301  76708 01:20  python3 leaky_service.py
```

线性增长、无回落 → 泄漏实锤，速率与请求量同频（100 × 4KB × 3 ≈ 1.2MB/5s，时间-速率对上了）。

**第二步：归因。** 方法三/五：tracemalloc compare_to（第 5 节输出）指出 `leaky_app.py:8` 的全局列表。C/C++ 服务则用 `sudo /usr/share/bcc/tools/memleak -p PID` 直指分配栈。

**第三步：修复。** 加上限：

```python
from collections import OrderedDict
archive = OrderedDict()
MAX = 512                              # 修复：有界缓存，超出即淘汰最老
def put(k, v):
    archive[k] = v
    if len(archive) > MAX:
        archive.popitem(last=False)
```

**第四步：对比。**

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| RSS @ 10min | 512MB（线性增长中） | 21MB（平稳） |
| RSS @ 24h | 必然 OOM（推算 7.4GB > 物理内存） | 21MB |
| P99 延迟 @ 20min | 45ms（开始与 kswapd/回收竞争） | 20ms |

最后一条尤其值得记：**内存泄漏的服务往往先"变慢"再"死掉"**——回收压力抬升延迟，监控上先看到 P99 恶化、后看到进程消失。所以 RSS 单调性检查（或 available 水位）要进告警清单。

## 常见误区

1. **"free 小 / cache 大 = 内存不足"**：看 available 与 swap used；cache 是可回收的影子内存。
2. **"RSS 涨 = 泄漏"**：CPython 的 arena、glibc 的 malloc 都不急着还给 OS（碎片与性能取舍）， RSS 高位平台期正常；判泄漏看**单调性 + 速率与请求量相关性**，不是看绝对值。
3. **"swap in/out = 坏事"**：开机后一次性换出的冷页再被换入一次，总量小且无规律，无害；**持续、高频的 si/so 才是病**，配合 majflt 与 P99 判断。
4. **"OOM 杀了 A，所以 A 有问题"**：oom killer 按"占用大"挑 victim，不是按"谁泄漏"。触发者也不等于责任人。正确姿势：从 victim 的 RSS 曲线+tracemalloc/memleak 找证据。
5. **"Python 有 GC 不会泄漏"**：引用挂到全局/闭包/循环引用都能泄漏；GC 只回收不可达对象，可达却无用的对象它管不着（本篇实验就是全局列表泄漏）。

## 本篇小结

- 判断内存够不够看 available 与 swap used，不是 free；cache 是特性不是故障。
- VSZ/RSS/USS 三口径：容量按工作集算；majflt 是"内存压力变成延迟"的直接证据，pidstat -r 必看。
- kswapd 活跃=温和回收；si/so 持续非零=延迟劣化中；swappiness 只调倾向，禁用要 swapoff。
- 泄漏三法分工：RSS 曲线定性 → tracemalloc（Python 对象层）/ memleak（eBPF，C 分配栈）定位 → massif 画像兜底；ASan 是 C++ 的 CI 守门员。
- OOM 日志逐字段：水位线证明"真没了"、anon 巨大指向应用、victim 是最大占用者而非元凶；容器版搜 "memory cgroup out of memory"。

## 练习

1. 运行 mem_rss.py（把触碰步长改成 512），对比 minor_flt 次数与触碰字节数的关系；再在你的 WSL2 上跑 `getconf PAGESIZE`，确认页大小，换算"每次 minor fault 对应多少字节"。
2. 制造一次 major fault：`python3 -c "f=open('/tmp/bigfile','rb'); f.seek(1024**3); print(f.read(1))"` 前后用 `pidstat -r 1 1` 观察 majflt 列，再用 `vmtouch -v /tmp/bigfile`（`pip install vmtouch` 或 apt）看文件多大比例进了页缓存。
3. 给 leaky_service.py 加上 tracemalloc 的 `/debug` 端点（或定时打印），跑 5 分钟后"抓捕"泄漏行；把修复版的 RSS 曲线画成表，验证平台期。
4. 写一个 C++ 程序故意同时包含"泄漏 + 越界写"，用 ASan 一次跑出两类报告；体会 `-fsanitize=address` 与 valgrind（不重编译）的差异，记录你更愿意在 CI 用哪个及理由。
5. 在 dmesg 里找到一次真实 OOM（没有就构造：容器/WSL2 内用 stress 撑爆内存，`sudo apt install stress; stress --vm 2 --vm-bytes 2G --timeout 30s`），把 `free ...min/low/high` 三行与 `Killed process` 行抄进笔记，练习向同事口述"这次 OOM 的证据链"。
