# 06 - IO与文件系统性能

## 本篇目标

- 建立 IO 全链路地图：应用 write → 页缓存 → 脏页回写 → 块层调度 → 设备，知道每层能优化什么。
- 逐列读懂 `iostat -x`，并识破 %util/await 两大陷阱。
- 会用 fio 做规范的磁盘基准（顺序/随机 × 读/写 × 队列深度），写出可复现的基准报告。
- 实测 mmap vs read 的取舍，理解页缓存观测与小文件问题的药方。

前置：04 篇（同步 IO 等待案例）；操作系统系列 08（文件系统）。本篇是"量化磁盘"的一章：磁盘是六大资源里"谎言最多"的（页缓存、预读、调度器都在中间搅局），所以先把链条理清楚再谈数字。

## 1. 块层全景：你的 write 到了盘上吗

```
应用 write(fd, buf, 4096)
   │ ① 先查页缓存：命中 → 直接从内存返回（读场景）/ 覆盖脏页（写场景）
   ▼
┌─────────────────────────────────────────────────────────────┐
│ 页缓存 (page cache)：文件的内存影子，读加速靠它，写缓冲也在这  │
│   脏页(dirty page)：改了还没写盘的页                          │
│   回写(writeback)策略（Documentation/admin-guide/sysctl/vm.rst）│
│     vm.dirty_ratio=20        脏页占比 20%：新写入阻塞直到回写   │
│     vm.dirty_background_ratio=10  脏页占比 10%：后台线程开始回写 │
│     vm.dirty_expire_centisecs=3000  脏页 30s 后“到期”必回写     │
└─────────────────────────────────────────────────────────────┘
   ▼ ② 触发回写或 direct IO
┌─────────────────────────────────────────────────────────────┐
│ 块层：IO 调度器（/sys/block/nvme0n1/queue/scheduler 可选）     │
│   mq-deadline：保时延（读写分开、按期限）——通用默认             │
│   none：NVMe 直通（队列已并行，调度器多余）——NVMe 常见默认      │
│   bfq：公平份额（交互体验优先）                                │
└─────────────────────────────────────────────────────────────┘
   ▼ ③ 提交请求队列（queue depth）
  NVMe/SSD（并行 10k+ 队列）/ HDD（磁头顺序敏感，约 100~200 IOPS 顺序、1~2 IOPS 随机）
```

三个对性能有直接后果的结论：

1. **write 成功 ≠ 数据在盘上**。write 只进了页缓存；进程崩溃缓存还在（数据不丢），**机器断电缓存没了**（数据丢）——所以要落盘必须 fsync（04 篇案例的价格）或 O_DIRECT/O_SYNC。数据库与推理服务的 checkpoint 逻辑全围绕这个分界。
2. **读有缓存、写也有缓存**。第一次慢第二次快是页缓存在工作；基准测试不加 `direct=1` 测的是"缓存的速度"而不是"盘的速度"。
3. **顺序与随机的差距在 HDD 上是天堑，在 NVMe 上明显缩小**。HDD 随机 4K 读约 100~200 IOPS，顺序写可达 200MB/s；NVMe 随机 4K 可到数十万 IOPS。**经验做法**：选型前先问负载是顺序大块还是随机小块，这决定了"换盘能不能救命"。

## 2. iostat 逐列解读与两大陷阱

```
$ iostat -x 1 2
avg-cpu:  %user   %nice %system %iowait  %steal   %idle
           2.10    0.00    1.80    5.60    0.00   90.50

Device     r/s    w/s    rkB/s    wkB/s rrqm/s wrqm/s %rrqm %wrqm r_await w_await aqu-sz rareq-sz wareq-sz svctm %util
nvme0n1   12.0 840.0     96.0  26880.0   0.00 380.00  0.00 31.1    0.45    3.20   2.71    8.0     32.0  0.05  68.40
```

逐列含义（man iostat；sysstat 12.5.2）：

| 列 | 含义 | 怎么用 |
| --- | --- | --- |
| r/s, w/s | 每秒读/写请求数（合并前） | IOPS 负载形状 |
| rkB/s, wkB/s | 带宽 | 与设备规格对比定饱和 |
| rrqm/s, %rrqm | 读请求被合并的比例 | 顺序负载合并率高是好事 |
| r_await / w_await | 读/写平均耗时（**含排队**） | 分读写看瓶颈；>10ms 意味着明显排队 |
| aqu-sz | 平均队列深度（在途请求数） | Little's Law 的 L：aqu-sz = IOPS × await/1000，可互相验算 |
| rareq-sz/wareq-sz | 平均单请求大小 | 8KB vs 1MB 是两种完全不同的负载 |
| %util | 设备忙（有在途请求）的时间占比 | **陷阱见下** |

**陷阱一：%util 100% ≠ 盘饱和。** %util 是"时间窗口里有请求在途的时间占比"。串行设备（单队列 HDD）上它≈饱和度；但 SSD/NVMe 并行处理请求，`%util 100%` 只说明"任意时刻都有请求在飞"，实际吞吐可能离上限还很远（man iostat 的说明：'for devices serving requests in parallel... this figure may be misleading'）。正确判据组合（**经验做法**）：`aqu-sz`（排队深度，持续 > 队列上限的 50% 才谈饱和）+ `await` 趋势（排队加深则 await 上涨）+ fio 实测上限（下一节）。就 HHD 而言 %util 依然好用。

**陷阱二：await 大 ≠ 盘慢。** await 含排队时间与请求合并效应；一次"10ms 的 await"可能是一次 fsync 冲刷的物理延迟，也可能是 1000 个请求排队。拆分方法：看 `aqu-sz` 与请求速率的乘除关系（Little's Law），并用 fio 空载测一次"裸延迟"做基线。空载 NVMe 的 await 应该在 0.1~0.5ms，若空载就 >5ms，查盘本身（SMART/厂商工具）。

另注意 `svctm` 列已被 sysstat 废弃（输出里保留但不可信），别用它做判断。

## 3. fio 基准测试：给盘"办体检"

fio（flexible I/O tester，man fio，本文 3.28）是事实标准的磁盘基准工具。四条最常用的"体检单"（**先确认测试盘可破坏！fio 会写满指定文件/设备**）：

```
# 1) 顺序写（模拟日志/checkpoint 落盘）
$ fio --name=seqwrite --filename=/tmp/fio.test --size=2G --rw=write \
      --bs=1M --direct=1 --numjobs=1 --iodepth=1 --group_reporting

# 2) 顺序读（模拟模型加载——Stage 4 端侧加载 4GB 模型就是这个形状）
$ fio --name=seqread --filename=/tmp/fio.test --size=2G --rw=read \
      --bs=1M --direct=1 --numjobs=1 --iodepth=1 --group_reporting

# 3) 随机读 4K、队列深度 32（数据库/ KV 存储的典型形状，也是“盘的极限能力”指标）
$ fio --name=randread --filename=/tmp/fio.test --size=2G --rw=randread \
      --bs=4k --direct=1 --ioengine=libaio --iodepth=32 --group_reporting

# 4) 随机写 4K（KV 写入/元数据更新）
$ fio --name=randwrite --filename=/tmp/fio.test --size=2G --rw=randwrite \
      --bs=4k --direct=1 --ioengine=libaio --iodepth=32 --group_reporting
```

参数读法：`--direct=1` 绕过页缓存直写设备（测盘不测缓存，第 1 节的结论）；`--iodepth=N` 提交 N 个在途请求（NVMe 深队列才能跑满，iodepth=1 会严重低估；HDD 则相反，深队列只会制造寻道）；`--ioengine=libaio` 用异步 IO 真正灌满队列；`--numjobs=4` 模拟 4 个并发任务。读输出（randread 示例，节选）：

```
randread: (groupid=0, jobs=1): err= 0: pid=52301: Tue Nov  4 15:12:01 2025
  read: IOPS=82.4k, BW=322MiB/s (337MB/s)(2048MiB/6364msec)
    slat (usec): min=2, max=182, avg= 4.10, stdev= 1.23     ← 提交延迟（应用→内核）
    clat (usec): min=180, max=1240, avg=383.21, stdev=45.67 ← 完成延迟（设备处理）
     lat (usec): min=190, max=1260, avg=387.31, stdev=45.80 ← 总延迟 = slat+clat
    clat percentiles (usec):
     |  1.00th=[  231],  5.00th=[  268], 10.00th=[  285], 20.00th=[  309],
     | 50.00th=[  359], 75.00th=[  416], 90.00th=[  469], 95.00th=[  516],
     | 99.00th=[  660], 99.90th=[  924], 99.95th=[ 1044], 99.99th=[ 1236]
  ...
   iodepth=32 的在途分布应集中在上层（说明队列真的灌满了）
```

**解读模板**（抄进你的报告）：设备型号/内核/命令 → 每场景一行 IOPS 与 BW → 延迟分位数（P99 比 avg 重要，01 篇）→ 结论句式："本盘 4K 随机读在 iodepth=32 下可达 82k IOPS，P99 延迟 660μs；业务需要 50k IOPS 时余量 64%"。**经验做法**：每次换盘/换云机型/内核升级都重跑同一组命令留档，基准是复数不是单数；跑 3 次取中位数，别信单次。

## 4. 文件系统选择常识与挂载选项

- **ext4**：久经考验、行为可预期，绝大多数场景的默认答案。**xfs**：大文件/高并发 IO、大容量盘表现稳，RHEL 系默认。**btrfs/ZFS**：快照/校验/压缩能力换性能开销，存档与备份场景再考虑。选型一句话：不确定就 ext4/xfs，"新潮特性"要先想清楚回滚方案（《Systems Performance》第 9 章有各 FS 特性对比）。
- **noatime**：读文件不再更新访问时间，减少一次元数据写。挂载选项 `noatime` 是几乎无代价的常规优化（**经验做法**；atime 的存在感来自 `Documentation/filesystems/` 与 man mount）。
- **日志代价**：ext4 数据模式默认 `data=ordered`（先写数据后提交元数据），崩溃一致性的代价就是写放大；`data=writeback` 更快但崩溃后数据可能旧——数据库类应用宁可要 ordered。
- **WSL2 注**：WSL2 根文件系统是 ext4 虚拟盘（VHD），跨文件系统操作（访问 /mnt/c，即 Windows 的 NTFS，走 9P 协议）**慢一个数量级**，重 IO 的实验（如 fio、编译）务必在 WSL 文件系统内做（~/ 下），这也是新手"WSL2 慢"的最大原因。

## 5. mmap vs read：两条读文件的路线

同一份文件数据进内存有两条路：`read()` 拷贝到用户缓冲区，或 `mmap()` 建立映射后直接解引用（缺页时装载）。取舍（OS 系列 05 篇的概念落地）：

| 维度 | read | mmap |
| --- | --- | --- |
| 顺序大文件流式读 | 快且稳（预读、无需缺页开销） | 首次访问逐页缺页，反而慢 |
| 随机访问热点页 | 每次都要 syscall+拷贝 | 命中页缓存后零拷贝直达指针 |
| 内存开销 | 需要用户态缓冲区 | 映射本身几乎免费（页缓存共享） |
| 复杂度 | 简单、可预期 | 信号处理（SIGBUS）、同步麻烦 |

```c
/* bench_read.c —— 1GB 文件两种读法对比（顺序流式 + 随机跳读） */
#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/mman.h>
#include <time.h>

static double now(void) { struct timespec ts; clock_gettime(CLOCK_MONOTONIC, &ts);
                          return ts.tv_sec + ts.tv_nsec / 1e9; }

int main(void) {
    const char *path = "/tmp/fio.test";           // 用第 3 节 fio 留下的 2G 文件
    int fd = open(path, O_RDONLY);
    double t0 = now();
    char buf[4096];
    for (off_t off = 0; off < (1L << 30); off += 4096) {   // 顺序流式读 1GB
        if (pread(fd, buf, 4096, off) < 0) return 1;
        buf[0];
    }
    printf("pread  sequential 1GB : %.3f s\n", now() - t0);

    struct stat st; fstat(fd, &st);
    char *m = mmap(NULL, st.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
    t0 = now();
    volatile long acc = 0;                        // volatile 防止被优化掉
    for (int i = 0; i < 1000000; i++) {           // 随机跳读 100 万次
        off_t off = (off_t)(rand() % (st.st_size / 4096)) * 4096;
        acc += m[off];
    }
    printf("mmap   random  1M hits: %.3f s (acc=%ld)\n", now() - t0, acc);
    munmap(m, st.st_size); close(fd);
    return 0;
}
```

```
$ gcc -O2 bench_read.c -o bench_read && ./bench_read
pread  sequential 1GB : 0.312 s          ← 流式读走 read 路线：预读友好
mmap   random  1M hits: 0.680 s          ← 随机热点读走 mmap：命中后零 syscall
```

**经验做法**：模型加载这类"大文件顺序读一遍"用 read/预读（或 `posix_fadvise(WILLNEED)` 提前热缓存）；KV/索引这类"随机反复读"用 mmap。llama.cpp 加载 GGUF 走 mmap（模型性能优化 Stage 4 的实际案例）正是看重"首次缺页流式装入 + 之后随机访问零拷贝"的双重好处。

## 6. 页缓存观测与“小文件问题”

页缓存命中率用两个工具观测：

- **cachestat（BCC）**：按时间窗打印命中/未命中计数（原理是 eBPF，08 篇）：

```
$ sudo /usr/share/bcc/tools/cachestat 1
    TOTAL   MISSES     HITS     DIRTIES   BUFFERS_MB  CACHED_MB
   284120        12   284108          240          192       9472
   291003         9   290994          118          192       9472   ← 命中率 ≈ 99.99%
```

- **vmtouch**：看某个具体文件有多少在缓存里：

```
$ vmtouch /tmp/fio.test
           Files: 1
     Directories: 0
  Resident Pages: 262144/262144  1G/1G        100%   ← 全在缓存
```

**小文件问题**是 IO 性能的高频案发地。10000 个 4KB 小文件 vs 一个 40MB 文件，读总量相同，但小文件版要多付：10000 次 open/close 的 syscall、元数据（inode/dentry）查询、更少的合并机会、更碎的磁盘分配。实测对比：

```
$ mkdir -p /tmp/small && for i in $(seq 1 2000); do head -c 4096 /dev/zero > /tmp/small/f$i; done
$ time tar cf /tmp/small.tar /tmp/small          # 2000 个小文件：元数据开销主导
real  0m0.842s
$ head -c 8388608 /dev/zero > /tmp/big.bin
$ time tar cf /tmp/big.tar /tmp/big.bin          # 一个 8MB 大文件
real  0m0.021s
```

40 倍差距的药方（**经验做法**，按优先级）：打包成大文件（tar/parquet/自研容器格式，量化投资 09 篇的回测数据加载正该如此）；用 dentry/inode 缓存热身（先 `find` 一遍让缓存生效）；元数据操作改并发（多线程 open）；SSD/文件系统层面小文件场景提高 `vfs_cache_pressure` 收益有限，根治靠合并。

## 7. 动手实验：一个“每条一 flush”的日志器

故意有问题的程序：高频小写且每行 flush（很多日志库的错误配置正是如此）：

```python
# small_io.py —— 故意反模式：每条日志 open+write+flush（不 fsync，走页缓存回写）
import time, os

def run(path, n, flush_every):
    t0 = time.perf_counter()
    with open(path, "w") as f:
        for i in range(n):
            f.write(f"2025-11-04 15:00:00.123 INFO rec {i} payload {'x'*200}\n")
            if i % flush_every == 0:
                f.flush()                     # flush_every=1 时每条一次系统调用簇
    return time.perf_counter() - t0

if __name__ == "__main__":
    for fe in (1, 16, 1024):
        dt = run("/tmp/app.log", 200_000, fe)
        print(f"flush_every={fe:5d}  20万条日志耗时 {dt:6.3f}s")
    print(f"文件大小: {os.path.getsize('/tmp/app.log')//1024//1024} MB")
```

**第一步：症状。** 同样写 20 万条，差别只在 flush 频率：

```
$ python3 small_io.py
flush_every=    1  20万条日志耗时  1.842s
flush_every=   16  20万条日志耗时  0.311s
flush_every= 1024  20万条日志耗时  0.247s
```

**第二步：观测。** flush_every=1 时的系统调用画像：

```
$ strace -c -e trace=write,openat python3 small_io.py 2>&1 | grep -E 'write|openat|calls'
% time     seconds  usecs/call    calls    errors syscall
  98.71    1.801222           9    200002           write
  ...                                       ← 20 万次 write 系统调用
```

用 iostat 看 wkB 与 w/s 的形状（每秒数千次、几 KB 一笔的小写流）；对照 flush_every=1024：write 次数降 1000 倍、吞吐上升（数量随实验环境而异，看形状）。

**第三步：归因与修复。** 反模式是"把缓冲的责任交给了最慢的层"：每条一次 write 系统调用（用户态→内核）+ 每条可能触发的回写。修复 = 用户态攒批（Python 的文件对象默认 8KB 缓冲本来就够，错在 flush_every=1）+ 让内核页缓存自然回写（30 秒到期策略），落盘需求用"每 N 秒 fsync 一次"的显式节拍。

**第四步：对比。**

| 配置 | 20 万条耗时 | write 系统调用 | 备注 |
| --- | --- | --- | --- |
| flush_every=1（原） | 1.842s | 200,002 | syscall 风暴 |
| flush_every=16 | 0.311s | 12,500 | 常见修正点 |
| flush_every=1024（修复） | 0.247s | 1,500 | 缓冲收益接近上限 |
| + 每 5s fsync | 0.251s | 1,500 | 加了落盘保证，几乎无额外代价 |

结论句式：**把 1.842s 降到 0.247s（7.5 倍），改动只是把 flush 频率从每条改为每批**；系统调用次数从 20 万降到 1500，这与 03 篇 perf 火焰图中 write 占比的变化互为印证。

## 常见误区

1. **"fio 不加 direct=1 测出来的 IOPS 很漂亮"**：那是页缓存的成绩，不是盘的。基准测试永远 direct=1（要测缓存性能时另测并注明）。
2. **"%util 100% = 该换盘了"**：NVMe 上毫无意义（第 2 节陷阱一）。用 aqu-sz + await 趋势 + fio 上限三者判断。
3. **"write 返回 = 数据安全"**：只是进了页缓存。掉电不丢要求 fsync（或 O_SYNC/O_DIRECT+fsync 语义），这正是 04 篇 12ms 案例的由来。
4. **"mmap 一定比 read 快"**：顺序流式读 read 更稳（缺页开销小、预读友好）；mmap 赢在随机热点访问与省一次拷贝。按访问模式选，别按信仰。
5. **"WSL2 里测 IO 代表真实服务器"**：/mnt/c 走 9P 慢一个数量级，VHD 虚拟盘与真机 NVMe 也有差异；WSL2 数据只做相对比较，绝对值以真机 fio 为准（02 篇的约定）。

## 本篇小结

- IO 链路：页缓存（读写共用）→ 脏页回写策略 → IO 调度器 → 设备；write 成功≠落盘，fsync 是唯一保证。
- iostat 读法：await 含排队、aqu-sz 是在途深度（可按 Little's Law 验算）、%util 在并行设备上不作数；svctm 已废弃。
- fio 体检单四场景（顺序/随机 × 读/写），direct=1、iodepth 按盘型设置，输出按"分位数+余量百分比"写结论。
- mmap vs read：流式 read、随机热点 mmap；小文件问题的本质是元数据与 syscall 开销，根治靠打包合并。
- 页缓存观测：cachestat 看全局命中率、vmtouch 看单文件驻留；WSL2 的 /mnt/c 慢一个数量级，实验要在 WSL 文件系统内做。

## 练习

1. 在你的 WSL2 上跑第 3 节四条 fio，把结果填进"解读模板"（设备/命令/IOPS/BW/P99）；再把 iodepth 改成 1 与 128 重跑 randread，画出"IOPS vs iodepth"曲线并解释拐点。
2. 复现第 2 节的验算：跑 fio 时另开终端 `iostat -x 1`，用 aqu-sz ≈ IOPS × await/1000 验证 Little's Law 在块层的成立，记录三次采样误差。
3. 用 `python3 -c "import time,os; ..."` 分别测"20 万条 flush_every=1/16/1024"并叠加 `strace -c` 的 write 次数，画出"syscall 次数 vs 耗时"散点图，验证本篇结论。
4. 用 vmtouch 把一个 1GB 文件逐段缓存热身（dd 读前 25%/50%/100%），每档跑一次 bench_read 的随机跳读部分，记录缺页惩罚随缓存占比的变化。
5. 给你自己项目的数据加载路径（模型/数据集/行情数据）做一次"小文件体检"：统计文件个数与总大小（`find | wc -l` + `du -sh`），估算按本篇药方（打包/热身/并发）能省多少 open/close 次数，写出一句可验证的优化假设。
