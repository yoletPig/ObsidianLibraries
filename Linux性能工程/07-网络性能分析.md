# 07 - 网络性能分析

## 本篇目标

- 按链路/主机/应用三层组织网络观测，知道每层的工具与问题清单。
- 逐列读懂 `ss -tin` 与 `netstat -s`，能从重传率、队列溢出计数器判断问题性质。
- 用 tcpdump 抓一个 HTTP 请求的完整时序，把延迟分解为 RTT、服务端处理、传输三段。
- 走通丢包排查路径（ethtool -S / netstat -s / softnet_stat），理解内核收包路径与 socket 缓冲区调优的位置。

前置：操作系统系列 12（网络栈与 socket）；本篇与 04 篇互补——网络等待是最常见的 off-CPU 来源。

## 1. 网络分层观测：每层只回答自己那部分

```
┌──────────────────────────────────────────────────────────────────────┐
│ 应用层    延迟的"用户感知"部分：请求处理、序列化、连接池                │
│           工具：应用日志、分布式追踪（11 篇）、pprof                    │
├──────────────────────────────────────────────────────────────────────┤
│ 主机层    内核协议栈与 socket：重传、缓冲区、队列溢出、软中断           │
│           工具：ss / netstat -s / /proc/net/softnet_stat / perf       │
├──────────────────────────────────────────────────────────────────────┤
│ 链路层    网卡与线缆：错包、速率协商、丢包、带宽                        │
│           工具：ethtool / ethtool -S / ip -s link / iperf3             │
└──────────────────────────────────────────────────────────────────────┘
   分诊规则：iperf3 打满带宽后应用还慢 → 看主机层；主机层计数器干净 → 看链路层
```

一条总原则（《Systems Performance》第 10 章 Networking）：**先确定"网络慢"是带宽问题、延迟问题还是丢包问题**——三者症状相似，药方毫无关系。带宽问题用 iperf3 证伪（第 5 节），延迟问题用 RTT 分解（第 4 节），丢包问题顺着计数器查（第 6 节）。

## 2. ss：socket 的体检报告

ss 是 netstat 的现代替代（iproute2，man ss）。看 TCP 连接的完整状态：

```
$ ss -tinm dst 10.0.0.5:8000
State  Recv-Q Send-Q Local Address:Port  Peer Address:Port  Process
ESTAB  0      42832  192.168.1.10:52322 10.0.0.5:8000
       cubic wsize:1024000 ... rtt:24.5/12.3 ... send 33.5Mbps ... unacked:31 retrans:0/3 ...
       rcv_space:29200 notsent:42832 minrtt:18.2
```

逐项读法（man ss；TCP 状态机见 OS 系列 12 篇）：

| 字段 | 含义 | 信号 |
| --- | --- | --- |
| Recv-Q (ESTAB) | 应用还没 read() 走的字节数 | 持续 > 0：应用读得慢（处理不过来），不是网络慢 |
| Send-Q / notsent | 还没被对端 ACK 的发送字节 | 打满发送缓冲：对端收不动或带宽不足 |
| rtt/rttvar | 平滑 RTT/其波动 | rttvar 大 = 抖动大（拥塞/路由漂移） |
| minrtt | 历史最小 RTT | ≈物理 RTT 下限，是"理想值"参照 |
| retrans | 重传计数（当前/累计） | 增长 = 丢包在发生，直接进入第 6 节 |
| cwnd / send | 拥塞窗口 / 估算发送速率 | cwnd 长不大 = 拥塞；send 远低于带宽 = 有瓶颈 |

`ss -s` 给全景汇总：

```
$ ss -s
TCP:   128 (estab 96, closed 12, orphaned 0, timewait 8)
Transport Total IP IPv6
*         245   -  12
RAW   0   UDP  14   TCP  128   INET  142   FRAG 0
```

timewait 多不是病（OS 12 篇），**estab 数 × 平均缓冲用量**才和内存（05 篇）挂钩：每个 TCP 缓冲最大可到 rmem_max（默认 212KB 级），1 万连接全满时仅缓冲就 2GB——这就是第 7 节要调缓冲区的现实理由。

`netstat -s`（= `ss -s` 的详细版）是协议栈计数器的宝库，先背三个高频问题计数器：

```
$ netstat -s | grep -iE 'retrans|overflow|prune|backlog'
    1244 segments retransmitted              ← 重传总量（除以 segments sent 得重传率，>0.5% 要查）
    3 times the listen queue of a socket overflowed
    3 SYNs to LISTEN sockets dropped          ← accept 队列溢出：应用 accept() 太慢（12 篇 backlog）
    58 packet receive errors                  ← UDP 侧：缓冲区不足丢包
    1244 TCP pruned ...                       ← 接收缓冲告急，内核丢弃 ooo 队列
```

**经验做法**：把上面四个计数器的增长率进监控（11 篇），它们各自的药方完全不同——重传查链路、listen overflow 查 accept 速度与 somaxconn、receive errors 查 UDP 缓冲。

## 3. tcpdump：抓一个 HTTP 请求的完整时序

tcpdump（4.99，man tcpdump）看的是"线上真实发生的每一帧"。三个常用姿势：

```
$ sudo tcpdump -i any -nn 'tcp port 8000' -c 20        # 实时看（-nn 不解析名字，快）
$ sudo tcpdump -i any -nn 'tcp port 8000' -w req.pcap  # 存盘后用 Wireshark 分析
$ sudo tcpdump -r req.pcap -ttt -nn 'tcp' | head       # -ttt：打印相邻帧的时间增量
```

抓一次完整 HTTP 请求（对本地一个 FastAPI/简单 server 发一条 curl），时序与延迟分解：

```
$ sudo tcpdump -i lo -nn -ttt 'tcp port 8000'
   00:00.000000 IP 127.0.0.1.52322 > 127.0.0.1.8000: Flags [S], seq 123456    ① SYN
   00:00.000042 IP 127.0.0.1.8000 > 127.0.0.1.52322: Flags [S.], seq 654321   ② SYN-ACK (+42μs)
   00:00.000065 IP 127.0.0.1.52322 > 127.0.0.1.8000: Flags [.], ack 1         ③ ACK（握手完成）
   00:00.000089 IP 127.0.0.1.52322 > 127.0.0.1.8000: Flags [P.], seq 1:118    ④ HTTP 请求发出
   00:02.412300 IP 127.0.0.1.8000 > 127.0.0.1.52322: Flags [P.], seq 1:1421   ⑤ 响应头返回 (+2412ms!)
   00:02.412455 IP 127.0.0.1.52322 > 127.0.0.1.8000: Flags [.], ack 1421
```

延迟分解法（**经验做法**，对线上抓包同样适用）：

```
①→③  握手 = 1.5 × RTT          → 这段大 = 网络物理距离/丢包重传 SYN
③→④  几乎瞬时（同机）
④→⑤  服务端处理时间 = ⑤ − ④ − RTT（响应第一个字节的传输）→ 这段大 = 服务器慢（04/10 篇的领地）
⑤→⑥  数据传输 = 响应体大小 ÷ 带宽 + RTT → 这段大 = 带宽或窗口问题（第 7 节）
```

把一次 curl 的 2.4 秒总延迟分解后：握手 0.04ms（本机）、服务端处理 2.41ms、传输 0.01ms——**慢的是服务端，网络是无辜的**。反过来若 ④→⑤ 只有 2ms 而 ①→③ 有 200ms，该查的是跨机房距离/丢包/连接复用（每次新建连接都付 1.5×RTT 的握手税，这就是连接池存在的理由）。**经验做法**：抓包时固定用 `-nn` 与 `-ttt`，分析保存的 pcap；线上抓包加 `-c` 限量，避免写爆磁盘。

## 4. iperf3：带宽的证伪实验

"网络是不是瓶颈"先测带宽上限（iperf3 3.9，man iperf3）：

```
$ iperf3 -s                          # 服务端（另一台机器/或 WSL2 里的另一进程）
$ iperf3 -c 192.168.1.20 -t 10       # 客户端：10 秒 TCP 测试
- - - - - - - - - - - - - - - - - - - - - - - - -
[ ID] Interval           Transfer     Bitrate         Retr
[  5]   0.00-10.00  sec  1.09 GBytes   938 Mbits/sec    0 sender
[  5]   0.00-10.04  sec  1.09 GBytes   935 Mbits/sec          receiver

$ iperf3 -c 192.168.1.20 -t 10 -P 4  # 4 并行流：单流跑不满时验多流
$ iperf3 -c 192.168.1.20 -t 10 -R    # -R 反向（收方向）
$ iperf3 -c 192.168.1.20 -u -b 1G    # UDP：看丢包率与抖动（jitter）
```

读法：Retr（重传次数）>0 说明带宽测试本身就在丢包；单流速率低但 -P 4 后线性增长 = 单 TCP 流受窗口/RTT 限制（带宽时延积 BDP 大的长肥管道，第 7 节的缓冲区调优正是解药）；UDP 模式下 `lost/total datagram` 直接给出丢包率。**WSL2 注**：WSL2 走 NAT 虚拟网络，与宿主机互测的数字是虚拟链路成绩，判断"真实机房带宽"要在真实主机间测；本机回环（127.0.0.1）测的是 CPU 而非网络。

## 5. 内核收包路径概览：丢包藏在哪一环

一个包从网卡到应用的旅程（内核文档 `Documentation/networking/`，napi 部分见 `Documentation/networking/napi.rst`）：

```
  网卡收包 → DMA 写入环形缓冲(ring buffer, ethtool -g 看大小)
     ↓ 硬中断(通知"有包了")
  软中断 NET_RX（/proc/net/softnet_stat）→ GRO 合并 → 协议栈(IP→TCP)
     ↓ 放入 socket 接收缓冲 (rmem)
  应用 read()/epoll 就绪
     ↑ 任何一环满了都会丢包，且各有专属计数器：
  ring buffer 满 → ethtool -S 的 rx_fifo_errors / rx_missed_errors
  softirq 处理不过来(time squeeze) → softnet_stat 第 3 列
  socket 缓冲满 → netstat -s 的 "pruned"/UDP "packet receive errors"
  accept 队列满 → "listen queue overflowed"（第 2 节）
```

`/proc/net/softnet_stat` 每行是一个 CPU 的计数（十六进制）：第 1 列处理包数，第 2 列因时间片用尽被丢的包（time squeeze 时也会丢），第 3 列 time squeeze 次数：

```
$ awk '{printf "cpu%-3d packets=%d dropped=%d squeeze=%d\n", NR-1, strtonum("0x"$1), strtonum("0x"$2), strtonum("0x"$3)}' /proc/net/softnet_stat
cpu0   packets=8123341 dropped=0        squeeze=214
cpu1   packets=8201934 dropped=0        squeeze=2190   ← squeeze 大：该 CPU 收包软中断过忙
```

**经验做法**：丢包排查固定路径——`ethtool -S` 找硬件侧丢 → softnet_stat 找 CPU 侧丢 → netstat -s 找协议栈侧丢。三处全干净还慢，回头查应用层（Recv-Q 堆积）。**WSL2 注**：WSL2 的虚拟网卡（eth0，由 Hyper-V 虚拟交换机提供）没有完整硬件计数器，`ethtool -S` 输出很少甚至为空，丢包定位主要靠 netstat -s 与 softnet_stat；真机（含 RK3588 的板载网卡）才有完整的 ethtool -S。

## 6. 丢包排查实战：一条路径走到底

制造一次可观测的拥塞（在 WSL2 或任何 Linux 上）：

```
$ # 用一个监听后故意不 accept 的“堵门”进程，制造 listen 队列溢出
$ python3 -c "
import socket, time
s = socket.socket(); s.bind(('127.0.0.1', 9000))
s.listen(2)                        # backlog 故意设成 2
time.sleep(30)                     # 期间完全不 accept
" &
$ # 另开终端，快速发起 10 个连接：
$ for i in $(seq 10); do (echo > /dev/tcp/127.0.0.1/9000) 2>/dev/null & done
$ sleep 1; netstat -s | grep -iE 'overflow|dropped'
    7 times the listen queue of a socket overflowed
    7 SYNs to LISTEN sockets dropped       ← 7 个 SYN 被“堵门”进程弄丢
```

这类丢包的修复链：应用 accept 不够快（单线程 accept → 多 worker）→ `net.core.somaxconn` 与应用 listen backlog 对齐（man tcp(7)，OS 12 篇的 backlog 语义）→ 前置 LB 摊平突发。对照第 5 节的表格，每种丢包有自己的修法——**丢包不是一种病，是一族病，先定位是哪一环**。

## 7. socket 缓冲区调优：长肥管道的解药

TCP 吞吐的物理上限由 BDP（带宽时延积）决定：要跑满带宽，**在途未确认数据 ≥ 带宽 × RTT**。1Gbps × 100ms 的跨机房链路 BDP = 12.5MB——若 socket 缓冲只有默认上限（net.ipv4.tcp_rmem 第三列，常见 6MB），单流跑不满，iperf3 单流低、多流高的症状由此而来。

```
$ sysctl net.ipv4.tcp_rmem net.ipv4.tcp_wmem net.core.rmem_max
net.ipv4.tcp_rmem = 4096        131072  6291456      ← 最小/默认/最大接收缓冲
net.ipv4.tcp_wmem = 4096        16384   4194304
net.core.rmem_max = 212992                      ← 应用 setsockopt 的硬上限
```

调优原则（man tcp(7)；内核文档 `Documentation/networking/ip-sysctl.rst`）：

1. **内核自动调优已足够好**（tcp_rmem 的最大值管住 autotuning 的上限），要做的是**把 max 抬到 ≥ BDP**：`sudo sysctl -w net.ipv4.tcp_rmem="4096 131072 33554432"`（32MB），rmem_max 同步抬（否则应用显式设置的缓冲被截断）。
2. **只调服务所在方向**：收大流量调 rmem，发大流量调 wmem；无脑全调大会增加每连接内存基数（ss -s 的缓冲账）。
3. **短连接服务先看握手与 accept**（第 6 节），缓冲区调优救不了 listen 队列溢出。

**经验做法**：跨机房大流量传输（模型分发、数据同步）前，先算 BDP 再对缓冲区，一次 sysctl 换来翻倍吞吐；机房内 RTT <1ms 时默认值几乎总是够的，别乱调。

## 8. 动手实验：分解一次“诡异的 100ms”

症状设定：跨机房调用 P99 抖到 100ms+，均值正常。用本篇工具把 100ms 拆开归因。

**第一步：ss 看连接质量。** 高峰期采样：

```
$ ss -tin dst 10.0.0.5:8000 | grep -E 'rtt|retrans' | head -3
 cubic wsize:... rtt:24.5/18.2 ... retrans:2/141 ...      ← rttvar 18ms：抖动大
 cubic wsize:... rtt:88.4/40.1 ... retrans:0/142 ...      ← 峰值时 rtt 飙到 88ms
```

**第二步：ping 分离"网络抖"与"服务端抖"。** 同一时刻对目标 IP 裸 ping：

```
$ ping -c 10 10.0.0.5 | tail -2
--- 10.0.0.5 ping statistics ---
10 packets transmitted, 10 received, 0% packet loss, time 9058ms
rtt min/avg/max/mdev = 22.1/23.8/25.0/0.6 ms    ← 网络层稳定 23.8ms、零丢包
```

网络稳如老狗但 TCP 层 rtt 到 88ms → **多出来的 60ms 不是路慢，是"包到了但没被及时 ACK"**——典型是服务端接收路径堵（第 5 节的 softirq/sk_buff）或服务端处理慢导致接收窗口满。

**第三步：tcpdump 定位"包在哪边等待"。** 抓双向时序（关键看 ACK 与数据的间隙）：

```
$ sudo tcpdump -i any -nn -ttt 'host 10.0.0.5 and port 8000' -c 40 | head -8
   00:00.000000 IP client.52322 > 10.0.0.5.8000: Flags [P.], seq 1:1049    ← 请求发出
   00:00.000421 IP 10.0.0.5.8000 > client.52322: Flags [.], ack 1049       ← 0.4ms 就 ACK：链路与对端内核都正常
   00:00.000444 IP client.52322 > 10.0.0.5.8000: Flags [P.], seq 1049:2097 ← 第二段请求体
   00:00.098120 IP 10.0.0.5.8000 > client.52322: Flags [P.], seq 1:987     ← 98ms 后才有响应数据！
```

ACK 0.4ms 回来（对端内核健康），数据 98ms 才出现（对端应用慢）——**延迟在对端应用里**，与网络无关。转去对端用 04 篇（off-CPU）或 10 篇（应用剖析）收网。**经验做法**：tcpdump 里"ACK 快、数据慢"是应用慢的指纹；"连 ACK 都慢"才是网络/对端内核的问题。这个"RTT 分解"的思路可以推广：任何端到端延迟，先分解再归因，永远别拿总延迟直接下结论。

第四步：对比验证。服务端修复（例如把同步 DB 查询改异步，04 篇手法）后，同口径复测：P99 100ms → 26ms（23.8ms RTT + 2ms 处理），rttvar 从 40ms 回到 1.2ms，retrans 增速归零——三个指标同时收敛才叫修复完成。

## 常见误区

1. **"Recv-Q 大 = 网络堵"**：ESTAB 状态的 Recv-Q 是"应用还没读"的字节，堵的是应用；网络堵的信号是重传、rttvar、Send-Q。
2. **"timewait 堆积要赶紧修"**：短连接服务的正常现象（OS 12 篇），除非耗尽端口/内存才需要处理；真正的病是"为什么每请求都新建连接"。
3. **"ping 快 = 网络没问题"**：ping 只证明 ICMP 路径，TCP 丢包（被中间设备限速/丢）与对端接收路径堵都不体现在 ping 上；第 8 节实验展示了"ping 稳但业务慢"的真实分解。
4. **"缓冲区调大总没错"**：大缓冲 = 大 BDP 缓存 = 更长的队延迟（bufferbloat），且每连接内存基数上升；按 BDP 算，不拍脑袋。
5. **"WSL2 网络数字可作容量依据"**：NAT 虚拟链路 + 缺失的 ethtool -S，只适合学工具；容量结论必须来自真实网卡环境。

## 本篇小结

- 网络观测三层：应用（追踪/日志）→ 主机（ss/netstat -s/softnet_stat）→ 链路（ethtool/iperf3）；先分清带宽/延迟/丢包三类病。
- ss -tin 的 Recv-Q 指向应用、retrans/rttvar 指向网络质量；netstat -s 四大计数器（重传/overflow/prune/UDP errors）各有专属药方。
- tcpdump -ttt 时序 + RTT 分解：握手=1.5×RTT、ACK 快数据慢=对端应用慢、连 ACK 都慢=网络/内核收包问题。
- 收包路径五道闸（ring buffer/softirq/socket 缓冲/accept 队列/应用读取），每道闸有专属计数器，丢包排查按 ethtool -S → softnet_stat → netstat -s 走。
- 缓冲区调优按 BDP：跨机房长肥管道抬 tcp_rmem 的 max；机房内默认值即可；WSL2 数字只做相对比较。

## 练习

1. 对本机 127.0.0.1 的任一服务跑第 3 节的 tcpdump 抓包，把一个 HTTP 请求的 ⑤−④ 差值（服务端处理时间）与 curl 的 `-w 'time_starttransfer=%{time_starttransfer}\n'` 输出对照，验证两种测量的一致性。
2. 复现第 6 节的 listen 队列溢出实验，把 backlog 依次设为 2/64/1024（`s.listen(n)`），记录 "SYNs to LISTEN sockets dropped" 的增长，画出"backlog vs 丢包数"关系。
