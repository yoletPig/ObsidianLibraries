## 1. cProfile：先找热点再动手

`cProfile`（标准库，确定性剖析器）统计每个函数的调用次数与耗时。工作流三步：跑剖析 → 按 `cumtime/tottime` 排序看热点 → 只优化头部：

```python
"""profile_demo.py：一个有"隐藏热点"的文本处理函数。"""
import time

def slow_transform(words: list[str]) -> list[str]:
    out = []
    for w in words:
        out.append(w.strip().lower().replace("-", "_"))
    return out

def build_report(n: int) -> str:
    words = [f"Word-{i}" for i in range(n)]
    parts = []
    for _ in range(10):                    # 外层循环放大热点
        parts.extend(slow_transform(words))
    return " ".join(parts)                 # ★ 反例伏笔：第 3 节改为 += 拼接看差异

if __name__ == "__main__":
    import cProfile, pstats, io
    pr = cProfile.Profile()
    pr.enable()
    build_report(200_000)
    pr.disable()
    buf = io.StringIO()
    ps = pstats.Stats(pr, stream=buf).sort_stats("cumulative")   # 按累计耗时排序
    ps.print_stats(8)                                            # 只看前 8 行
    print(buf.getvalue())
```

输出节选（数字因机器而异，比例关系稳定）：

```text
         Ordered by: cumulative time
   ncalls  tottime  percall  cumtime  percall filename:lineno(function)
        1    0.031    0.031    2.855    2.855 profile_demo.py:12(build_report)
  2000000    1.913    0.000    2.517    0.000 profile_demo.py:5(slow_transform)
  6000000    0.604    0.000    0.604    0.000 {built-in method builtins.isinstance}
  ...
```

读法（《Fluent Python》第 21 章同款工作流）：

- **tottime**：函数自身耗时（不含子调用）——找"哪段代码本身慢"；
- **cumtime**：含所有子调用——找"哪条调用链慢"；
- **ncalls** 惊人的行（如上面的 200 万次）通常是算法层 bug：该缓存没缓存、该合并没合并。

**经验做法**：剖析要在**接近生产的输入规模**下跑（小输入的热点分布会骗人）；cProfile 本身有开销（每函数调用都记录），它回答"谁最慢"，不回答"到底多快"——后者交给 timeit（第 2 节）。命令行更省事：`python -m cProfile -s cumulative script.py`；只想要一行结论可用 `time -p` 配合（不剖析、纯墙钟）。

热点定位到**具体某一行**用 line_profiler（第三方，`uv add --dev line_profiler`）：

```python
# @profile 装饰目标函数后：kernprof -l -v profile_demo.py
Line #      Hits         Time  Per Hit   % Time  Line Contents
     5                                           def slow_transform(words):
     6         1         42.0     42.0      0.1      out = []
     7   2000000    1204431.0      0.6     71.2      for w in words:
     8   2000000     484110.0      0.2     28.7          out.append(w.strip().lower().replace("-", "_"))
```

71% 的时间在 for 循环本身——提示**用向量化/批量操作替代逐元素 Python 循环**（推导式、`str.translate`、pandas/numpy）。

## 2. timeit 微基准规范

手工 `time.time()` 计时的坑：单次运行受系统抖动影响、没有考虑"第一次运行有冷启动"、精确度不足。`timeit`（标准库）的规范做法：**多次重复取最优 + 关闭 GC + 自动选择循环次数**（官方文档 timeit 模块）：

```python
>>> import timeit
>>> timeit.timeit("'-'.join(str(n) for n in range(100))", number=10000)
0.1352...
>>> timeit.timeit("'-'.join(map(str, range(100)))", number=10000)
0.0961...                      # map 版更快（循环在 C 层）
>>> timeit.repeat(..., repeat=5, number=10000)   # 重复 5 轮，取最小值（min 才代表真实能力）
```

规范四条（经验做法）：

1. **测"微操作"**（一个函数、一个表达式），别测整个程序——timeit 回答"这个改法快不快"，cProfile 回答"该不该改"；
2. **取 repeat 的最小值**而不是平均值——最小值受系统干扰最小，最接近代码真实速度；
3. **警惕常量折叠与作用域差异**：`timeit` 默认在隔离命名空间执行，`setup` 参数负责准备数据；函数里的全局变量访问比局部慢（第 3 节实测），timeit 语句与真实代码的上下文要一致；
4. **验证差异显著性**：差异 < 5% 的"优化"大概率是噪声，不值得改代码。

内存视角用标准库 `tracemalloc`（0 篇 01 章埋的种子）：

```python
import tracemalloc
tracemalloc.start()
data = [x * x for x in range(10_000_000)]
current, peak = tracemalloc.get_traced_memory()
print(f"峰值 {peak / 1e6:.0f} MB")            # 约 400+ MB（int 对象+列表）
tracemalloc.stop()
```

## 3. 常见优化手段：实测收益

下面每个手段都给出**可运行的对照实验**——数字是你自己机器上的判决，不是我的结论。

**手段一：字符串拼接用 join，不用 +=**。`+=` 每次都可能创建新字符串对象（str 不可变，01 篇），O(n²) 风险；`join` 一次分配：

```python
import timeit
setup = "parts = ['word-%d' % i for i in range(10_000)]"
t1 = timeit.timeit('s = "";  \nfor p in parts: s += p', setup, number=100)
t2 = timeit.timeit('s = "".join(parts)', setup, number=100)
print(f"+= 拼接: {t1:.3f}s   join: {t2:.3f}s")
# 典型：+= 1.9s   join 0.02s —— 两个数量级，注意 CPython 对 += 有优化，仍不可靠（列表+join 才稳）
```

**手段二：局部变量缓存全局/属性查找**。全局查找走字典（01 篇 LEGB），属性查找走 MRO——循环体内把它们绑成局部变量：

```python
import timeit
setup = """
values = list(range(10_000))
out = []
"""
t1 = timeit.timeit("for v in values: out.append(v)", setup, number=100)
t2 = timeit.timeit("""
append = out.append                 # 方法查找提出来（绑定方法）
for v in values: append(v)
""", setup, number=100)
print(f"属性查找: {t1:.3f}s   局部缓存: {t2:.3f}s")
# 典型：0.42s vs 0.33s —— ~20% 收益；代价是可读性，热点确认后才值得
```

**手段三：`__slots__` 省内存提速实例创建**。默认实例属性存 `__dict__`（01 篇），`__slots__` 用固定槽位替代——内存省、创建快，但**不能再动态加属性**（06 篇 dataclass 的 `slots=True` 即此机制，3.10+）：

```python
import tracemalloc, time

class PointDict:
    def __init__(self, x, y): self.x, self.y = x, y

class PointSlots:
    __slots__ = ("x", "y")
    def __init__(self, x, y): self.x, self.y = x, y

tracemalloc.start()
pts = [PointDict(i, i) for i in range(1_000_000)]
print(f"dict 实例 峰值: {tracemalloc.get_traced_memory()[1]/1e6:.0f} MB")   # 典型 ~160MB
tracemalloc.stop(); tracemalloc.start()
pts = [PointSlots(i, i) for i in range(1_000_000)]
print(f"slots 实例 峰值: {tracemalloc.get_traced_memory()[1]/1e6:.0f} MB")  # 典型 ~76MB
# 经验做法：百万级小对象（图节点、token、消息体）值得 slots；业务对象不必
```

**手段四：生成器替代中间列表**（04 篇实测的回归测试）：一次性流水线（读→过滤→聚合）内存 O(1)；需要多次遍历/随机访问才物化。

**手段五：换对数据结构**（收益常排第一）：`set`/`dict` 成员判断 O(1) vs `list` O(n)；`collections.deque` 两端操作 O(1) vs `list.pop(0)` O(n)；`functools.lru_cache` 消灭重复计算：

```python
import timeit
setup = "data = list(range(100_000)); s = set(data)"
print(timeit.timeit("99_999 in data", setup, number=100))   # list: 每次都扫
print(timeit.timeit("99_999 in s",    setup, number=100))   # set: 恒定哈希查找
# 典型：list 0.9s vs set 0.000003s —— 判断"在不在"永远先想 set/dict
```

## 4. PyPy / Cython / Rust 扩展概览

纯 Python 优化到头（热点确认、算法正确、数据结构合适）仍不够时，三条升级路线：

| 路线 | 是什么 | 何时考虑 | 代价 |
| --- | --- | --- | --- |
| **PyPy** | 替代解释器（JIT 编译） | 纯 Python 长跑 CPU 任务，懒得改代码 | 启动慢、部分 C 扩展兼容问题、GIL 仍在 |
| **Cython** | Python 超集编译为 C，可加静态类型 | 数值循环、已有 C 库胶水 | 需要构建链、代码侵入 |
| **Rust 扩展**（pyo3/maturin，pydantic-core/vLLM 部分内核即此路线） | 原生扩展，释放 GIL 并行 | 热点模块重写、追求极致 | 开发成本最高，需 Rust 工具链 |

判据链条（07 篇决策树的性能分支）：**cProfile 确认热点在 Python 字节码 → 算法/数据结构无解 → numpy 等向量化库能否覆盖 → 不行再 Cython/Rust**。注意"热点在 C 层"时（numpy 大矩阵）三者都帮不上忙，问题变成并行化（07 篇）。

**经验做法**：给优化加"护栏"——优化前先建立**基准测试**（pytest-benchmark 或 timeit 脚本入库），改完跑对比；**优化只改热点，不顺手重构**（否则 benchmark 报告说不清哪来的收益）；收益 < 10% 且代码变难读的优化直接放弃。

## 5. 何时优化（经验做法）

优化纪律三条（Donald Knuth 的 "premature optimization is the root of all evil" 是行业共识，但常被误读——完整的观点是"**在关键路径上**过早优化是万恶之源"，不是"永远不优化"）：

1. **先对，再快**：正确性测试通过之前谈性能是负资产；剖析驱动的优化发生在"功能稳定后、发布前"；
2. **度量优先**：没有 cProfile/基准数据支持的"我觉得这里慢"一律不成立（本篇第一句话的执行版）；
3. **热点集中度检查**：80/20 规律——多数程序 80% 时间花在 20% 代码上，优化前 3 个热点函数通常就到顶了；改完重新剖析，**验证收益**，没有收益就回滚。

**反面清单**：为 1000 次调用的函数做 slots；把清晰代码改成一行推导式只为省 2%；在没测过 IO 占比的服务里并行化 CPU 段（07 篇）；用 `+=` 拼 10 个字符串的"优化"（可读性损失换不来可测收益）。**正面模板**：上线前跑一次 `python -m cProfile -s cumulative` → 头部三个函数逐一确认"能缓存吗？能批量吗？能换结构吗？" → 每项改动配基准数据进 PR。

## 常见陷阱

**陷阱一：用 cProfile 的数字当最终耗时**——剖析器自身开销让绝对值失真；配对用法：cProfile 找热点 + timeit 出可信数字。

**陷阱二：timeit 的语句与真实代码上下文不一致**——测的是全局变量访问、真实路径是局部变量（反之亦然），结论失真；`setup` 尽量模拟真实上下文。

**陷阱三：微基准结论直接外推**——`join` 在"字符串数多、单个短"时优势最大，10 个长字符串 `+=` 无所谓；任何优化的适用范围跟着实验条件走，写进注释。

**陷阱四：`__slots__` 破坏动态性而不自知**——加了 slots 的类不能随便加属性、与某些序列化/依赖注入库冲突（它们靠 `__dict__`）；给第三方可能继承你的类的**公共基类**加 slots 前想清楚。

**陷阱五：优化了非热点**——把 2% 的函数快了 3 倍，整体没变化；每次优化前重看 cProfile 头部，确认这个函数的 cumtime 占比值得动手。

## 本篇小结

- 工作流：**cProfile 找热点（cumtime/tottime/ncalls 三看）→ line_profiler 拆到行 → timeit 验证改法 → tracemalloc 看内存**；
- timeit 规范：微操作、repeat 取 min、setup 模拟真实上下文、差异 <5% 视为噪声；
- 实测收益榜：set/dict 成员判断（数量级）> join 拼接（数量级）> slots 内存（~50%）> 局部变量缓存（~20%）> 生成器省内存（O(n)→O(1)）；
- 升级路线：PyPy（不改码）→ Cython（数值循环）→ Rust 扩展（极致热点，pydantic-core/vLLM 路线）；前提都是"热点在 Python 字节码"；
- 纪律：先对再快、度量优先、只改热点、每次优化配基准数据——没有数据的"优化"是风险不是收益。
