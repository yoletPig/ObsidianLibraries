# 03 - 装饰器

## 本篇目标

1. 理解装饰器的本质——**语法糖**：`@dec` 就是 `f = dec(f)`，装饰发生在 `def` 执行的那一刻；
2. 手写无参与**带参**装饰器，说清 `functools.wraps` 为什么必须存在；
3. 掌握类装饰器、多层装饰器的应用顺序，能从下到上手工展开等价代码；
4. 落地四个生产级模式：计时、重试、缓存、**工具注册器（Agent 工具注册模式）**。

## 1. 装饰器是语法糖：@dec 就是 f = dec(f)

装饰器只是一个**接受函数、返回函数**的 callable（PEP 318，Python 2.4 引入）。`@` 符号没有任何魔法，它只是把"包一层再重新绑定同名"这个动作写成了显式标记。**装饰在 `def` 语句执行时立即发生**——模块导入时就跑完了，不是等第一次调用才包装（这是常见的理解偏差，后面 3.2 节用它解释带参装饰器）。

```python
def shout(func):                     # 装饰器：普通的高阶函数
    def wrapper():
        return func().upper() + "!"
    return wrapper

@shout                               # 语法糖
def hello():
    return "hello"

# 等价于（手动展开）：
# def hello(): return "hello"
# hello = shout(hello)

>>> hello()
'HELLO!'
>>> hello.__name__                   # 注意：名字已经变成 wrapper（3.2 节修复）
'wrapper'
```

因为"函数可以作为参数和返回值"（02 篇一等公民），这个模式顺理成章。装饰器的价值在于**把横切逻辑（计时、日志、重试、校验）从业务函数中剥离**，一处定义、处处复用——与《Fluent Python》第 9 章的定位一致。

## 2. 手写无参装饰器：functools.wraps 为什么必须有

上一节的 `hello.__name__` 变成了 `'wrapper'`——包装函数**覆盖了原函数的元数据**（`__name__`、`__doc__`、`__module__`、`__qualname__`、`__wrapped__` 等），会破坏调试（栈跟踪里全是 wrapper）、文档生成、内省（02 篇第 5 节的工具全失灵）。`functools.wraps` 就是官方给的修复器（文档：functools → wraps），它把这些元数据从原函数复制到包装函数上：

```python
import functools
import time

def timed(func):
    """计时装饰器：打印函数执行耗时。"""
    @functools.wraps(func)                    # ✅ 必须有：复制元数据
    def wrapper(*args, **kwargs):             # 收集任意参数（02 篇转发模式）
        t0 = time.perf_counter()              # perf_counter：单调高精度计时
        try:
            return func(*args, **kwargs)      # 转发并保留返回值
        finally:
            dt = time.perf_counter() - t0
            print(f"{func.__name__} 耗时 {dt*1000:.3f} ms")
    return wrapper

@timed
def fib(n: int) -> int:
    """递归斐波那契。"""
    return n if n < 2 else fib(n - 1) + fib(n - 2)

>>> fib(10)
fib 耗时 0.012 ms
55
>>> fib.__name__                    # 修复后仍是 fib
'fib'
>>> fib.__doc__
'递归斐波那契。'
```

不加 `@functools.wraps` 的实际代价，除了元数据丢失，还有一个隐蔽 bug：**装饰器叠加后 `__wrapped__` 链断裂**——`inspect.signature` 靠 `__wrapped__` 沿链找到原始签名，链条断了签名显示的就是 `(*args, **kwargs)`。**经验做法**：把 `@functools.wraps(func)` 当作写装饰器的肌肉记忆，和 `def wrapper` 连着背。

## 3. 带参装饰器：多一层"装饰器工厂"

`@timed` 是把函数交给装饰器；而 `@retry(times=3)` 里 `retry(times=3)` **先执行**，返回的结果才是装饰器。也就是说：**带参装饰器 = 装饰器工厂**（接收参数、返回装饰器），装饰发生时机不变（def 时）。三层嵌套的分工要分清：

```python
import functools
import random
import time

def retry(times, delay=0.1, exceptions=(Exception,)):
    """带参装饰器：失败重试 times 次，指数退避。只处理指定异常。"""
    def decorator(func):                          # 第二层：真正的装饰器
        @functools.wraps(func)
        def wrapper(*args, **kwargs):             # 第三层：包装执行逻辑
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except exceptions as exc:         # 只捕获声明的异常族
                    if attempt == times:
                        raise                     # 最后一次：抛出，不吞错
                    backoff = delay * (2 ** (attempt - 1))   # 指数退避
                    print(f"[retry] {func.__name__} 第{attempt}次失败: {exc!r}，"
                          f"{backoff:.2f}s 后重试")
                    time.sleep(backoff)
        return wrapper
    return decorator

@retry(times=3, exceptions=(ConnectionError,))
def fetch(url):
    if random.random() < 0.7:
        raise ConnectionError(f"{url} 连接失败")
    return f"<data from {url}>"

>>> fetch("https://api.example.com/v1/users")
[retry] fetch 第1次失败: ConnectionError('https://api.example.com/v1/users 连接失败')，0.10s 后重试
[retry] fetch 第2次失败: ConnectionError('...')，0.20s 后重试
'<data from https://api.example.com/v1/users>'
```

逐层读法（务必在脑内展开一遍）：

1. `@retry(times=3, ...)` → 先调用 `retry(times=3, ...)`，得到 `decorator`；
2. `def fetch` 执行时 → `fetch = decorator(fetch)`，得到 `wrapper`；
3. 之后每次 `fetch(...)` 实际调用 `wrapper(...)`。

记忆口诀：**@ 后面的表达式"先求值，再把结果当装饰器用"**。写错层的典型症状是 `TypeError: 'function' object is not callable`——说明把"装饰器"当成了"装饰器工厂"。

## 4. 类装饰器与装饰器的执行时机

**类装饰器**：装饰器只要求"可调用"，类也可以——`@myclass` 就是 `X = myclass(X)`，类本身可调用（调用即实例化，01 篇）。适合"想给被装饰对象保存状态/挂方法"的场合。经典用法是**给类注入方法或记录类清单**（与 11 篇元类自动注册呼应）：

```python
def register(cls):
    """类装饰器：登记到全局注册表，并给类加一个 label 属性。"""
    REGISTRY[cls.__name__.lower()] = cls
    cls.label = cls.__name__
    return cls

REGISTRY = {}

@register
class JSONExporter:
    def export(self): return "{}"

@register
class CSVExporter:
    def export(self): return "a,b,c"

>>> list(REGISTRY)
['jsonexporter', 'csvexporter']
>>> JSONExporter().label
'JSONExporter'
```

**执行时机验证**——装饰在 def/导入时执行，包装逻辑在调用时执行，两者千万不要混淆：

```python
def trace(tag):
    print(f"① 工厂执行: {tag}")       # def 装饰时打印
    def decorator(func):
        print(f"② 装饰器执行: {func.__name__}")
        @functools.wraps(func)
        def wrapper(*a, **kw):
            print(f"③ wrapper 执行")   # 每次调用打印
            return func(*a, **kw)
        return wrapper
    return decorator

@trace("demo")                        # 模块导入时立刻打印 ①②
def demo(): pass

demo()                                # 只打印 ③
demo()                                # 又打印 ③（①② 不会再来）
```

这也解释了一个重要推论：**装饰器里的代码影响导入速度**——在装饰器体（工厂层）里做重活（读配置、连网络）会拖慢每次 import；**经验做法**：工厂层只做轻量的参数校验与闭包绑定，重活放到 wrapper 里或惰性初始化。

## 5. 多层装饰器：从下到上包装

多个装饰器叠加时，**从下到上（从里到外）依次应用**，即最靠近 `def` 的最先包装、也最贴近原函数：

```python
@A
@B
def f(): ...

# 完全等价于：f = A(B(f))
# 执行流：调用 f() → A 的 wrapper → B 的 wrapper → 原函数
```

用两个计时/日志装饰器实测顺序：

```python
import functools

def tag(name):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*a, **kw):
            print(f"{name}: 进入")
            result = func(*a, **kw)
            print(f"{name}: 退出")
            return result
        return wrapper
    return decorator

@tag("外层A")
@tag("内层B")
def work():
    print("  原函数执行")

>>> work()
外层A: 进入
内层B: 进入
  原函数执行
内层B: 退出
外层A: 退出
```

**经验做法**：有语义顺序要求的组合要留心——典型如 `@app.route("/")` 与缓存装饰器同用时，**缓存应更靠近原函数**（`@route` 在上、`@cache` 在下），让路由逻辑先处理再查缓存；重试装饰器同理一般放最里层。顺序错了不是报错，而是静默改变语义，靠评审清单兜底（14 篇）。

## 6. 实战：缓存与注册器（Agent 工具注册模式）

**缓存装饰器**——自己实现一遍，就懂 `functools.lru_cache` 的内核了（生产直接用标准库，这里为了看清机制）：

```python
import functools

def cache(func):
    _store: dict = {}                     # 闭包保存缓存（02 篇状态）
    @functools.wraps(func)
    def wrapper(*args):
        if args not in _store:            # 未命中才计算
            _store[args] = func(*args)
        return _store[args]
    wrapper.cache_clear = _store.clear    # 挂上管理接口
    wrapper.cache = _store                # 暴露给测试
    return wrapper

@cache
def slow_square(n):
    time.sleep(0.1)
    return n * n

>>> slow_square(4)                        # 第一次：慢
16
>>> slow_square(4)                        # 第二次：命中
16
```

标准库方案 `@functools.lru_cache(maxsize=128)` 支持容量上限与 LRU 淘汰（文档：functools），加 `maxsize=None` 即无界缓存。**注意**：lru_cache 缓存键是参数——方法上慎用（会把 `self` 连同实例一起缓存，造成实例泄漏 + 无法感知实例状态变化），这是《Fluent Python》第 9 章明确警示的点。

**工具注册器**——Agent 开发中"把函数注册成 LLM 工具"的模式，是 02 篇内省 + 本篇装饰器的合体，也是 LangChain/各类 Agent 框架 `@tool` 的最小原理：

```python
import inspect

TOOLBOX: dict[str, dict] = {}

def tool(name=None, description=None):
    """注册器：把函数登记进 TOOLBOX，并生成 LLM 可读的元数据。"""
    def decorator(func):
        key = name or func.__name__                # 默认用函数名
        TOOLBOX[key] = {
            "func": func,
            "description": description or (func.__doc__ or "").strip(),
            "schema": {                            # 由签名自动推导（02 篇）
                pname: (p.annotation.__name__ if p.annotation is not p.empty
                        else "string")
                for pname, p in inspect.signature(func).parameters.items()
            },
        }
        return func                                # 注意：这里原样返回 func，不包装！
    return decorator

@tool(description="按城市查询天气")
def get_weather(city: str, days: int = 3):
    """返回未来 days 天的天气。"""
    return f"{city} 未来 {days} 天：晴"

>>> TOOLBOX["get_weather"]["schema"]
{'city': 'str', 'days': 'int'}
>>> TOOLBOX["get_weather"]["func"]("北京")         # 运行时由 Agent 调度器取出并调用
'北京 未来 3 天：晴'
```

两个设计细节值得咀嚼：① 注册器**原样返回 func**——注册是副作用，函数本体行为不变，这是"注册型装饰器"与"包装型装饰器"的分水岭；② 12 篇的 `importlib` 插件系统会把"模块导入即注册"补完——插件模块被 import 的那一刻，所有 `@tool` 自动进入 TOOLBOX。

## 常见陷阱

**陷阱一：忘写 `functools.wraps`**——`__name__` 变 `wrapper`、文档丢失、`inspect.signature` 失真。修复：每写一个 `def wrapper` 就跟一个 `@functools.wraps(func)`。

**陷阱二：装饰器写成了工厂**——`@mydecorator()` 和 `@mydecorator` 只有一个是对的。若装饰器需要参数就实现成三层工厂；若不需要参数就直接一层，混用时会 `TypeError`。

**陷阱三：在 wrapper 里丢了返回值**——`func(*args, **kwargs)` 执行了但忘了 `return`，所有被装饰函数都悄悄返回 `None`：

```python
def bad_log(func):
    def wrapper(*a, **kw):
        print("before")
        func(*a, **kw)          # ❌ 返回值被吞
    return wrapper
```

**陷阱四：装饰 async 函数的装饰器里用了同步 wrapper**——`async def` 被普通函数包装后，返回的是 coroutine 对象而不是结果，调用方 `await` 的行为会被破坏。正确形态是 `def wrapper` 内 `async def inner` 并返回 `inner(*args, **kwargs)`，或直接写 `functools.wraps` 修饰的 `async def wrapper`（09/10 篇有完整范例）。

**陷阱五：装饰器状态共享**——工厂层的可变对象被所有"同工厂、不同函数"的装饰结果共享（比如同一 `retry` 参数生成的两个装饰器共享计数器），需要按函数隔离状态时应把状态放进闭包（每次 `decorator(func)` 调用新建）或挂在 `wrapper` 属性上。

## 本篇小结

- 装饰器 = 高阶函数 + `@` 语法糖，`@dec` 即 `f = dec(f)`，**装饰发生在 def/导入时**，包装逻辑在调用时；
- 无参装饰器三件套：`def wrapper(*args, **kwargs)` 收集参数、`return func(*args, **kwargs)` 转发并保留返回值、`@functools.wraps(func)` 修复元数据；
- 带参装饰器是**装饰器工厂**（三层：收参 → 装饰 → 包装），`@` 后表达式先求值；
- 类装饰器适合注入方法/登记类；多层装饰器**从下到上**包装，有语义依赖时顺序要刻意安排；
- 注册器模式（原样返回 func + 副作用注册）是 Agent 工具系统与插件框架的地基，11 篇元类会给出类级的另一种实现。
