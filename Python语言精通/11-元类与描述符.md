# 11 - 元类与描述符

## 本篇目标

1. 画出**属性查找顺序**的完整规则（实例 dict → 类 MRO → 描述符/钩子），解释 `__getattr__`/`__getattribute__`/`__setattr__` 的分工；
2. 理解**描述符协议**：`@property` 的本质，会手写数据校验描述符；
3. 会用 `type` 动态创建类，理解**元类**如何在类创建时介入（字段注册/自动注册——SQLAlchemy/pydantic 的原理）；
4. 建立"什么时候不该用"的判断力（经验做法）。

## 1. 属性查找顺序与 MRO

读属性 `obj.attr` 时，解释器的查找链（官方文档 Data Model → customizing attribute access，《Fluent Python》第 22 章有完整图）：

```text
obj.attr 的查找顺序（data descriptor 参与在类层）：
1. 类及基类的 MRO 中找 data descriptor（定义了 __set__ 或 __delete__ 的）→ 命中即用
2. 实例的 __dict__                        → 命中即用
3. 类及基类的 MRO 中找 非 data descriptor / 普通类属性     → 命中即用
4. 都没有 → 调 __getattr__(self, name)（若定义）→ 否则 AttributeError
```

**MRO（Method Resolution Order）**是"沿继承链查找的线性顺序"，由 C3 线性化算法计算（Python 2.3 起固定，见官方文档 Python Tutorial 9.5 与 PEP 253 的背景材料），保证：子类先于父类、父类保持声明顺序、单调性（不会跳序）。菱形继承是理解 MRO 的钥匙：

```python
class A:
    def who(self): return "A"
class B(A):
    def who(self): return "B"
class C(A):
    def who(self): return "C"
class D(B, C):        # 菱形：D → B → C → A
    pass

>>> D.__mro__
(<class 'D'>, <class 'B'>, <class 'C'>, <class 'A'>, <class 'object'>)
>>> D().who()         # MRO 上第一个有 who 的：B
'B'
```

为什么不是 A 先于 C？C3 要保证**父类相对顺序**（声明 `class D(B, C)`，则 B 系全部排在 C 系前面）且每个类只出现一次。`super()` 也不是"调父类"，而是**沿 MRO 找下一个**——协作式多重继承（mixin）的基础：

```python
class LoggedMixin:
    def who(self):
        return "L(" + super().who() + ")"   # super 沿 MRO 找下一个，不是"父类"
class Base:
    def who(self): return "Base"
class Service(LoggedMixin, Base):
    pass

>>> Service().who()          # MRO: Service → LoggedMixin → Base
'L(Base)'
```

**钩子三兄弟**的分工（Data Model 文档）：

- `__getattribute__(self, name)`：**所有**属性读取的必经之路（先于上面整个查找链执行，默认实现就是那张查找图）。重写它等于接管一切属性访问，极易递归（内部必须用 `super().__getattribute__` 或 `object.__getattribute__`）；
- `__getattr__(self, name)`：**只在常规查找失败后**才被调用的兜底钩子。安全的"懒加载/代理/动态属性"入口；
- `__setattr__(self, name, value)`：所有赋值的必经之路（默认写入 `__dict__` 或触发 data descriptor 的 `__set__`）。

```python
class LazyAPI:
    """__getattr__ 兜底：访问未定义属性时转发到远程 API（懒加载）。"""
    def __init__(self, prefix: str):
        self.prefix = prefix
        self._cache: dict[str, str] = {}
    def __getattr__(self, name: str):          # 只有 self.attr 找不到才进来
        if name.startswith("_"):
            raise AttributeError(name)         # 内部属性别劫持
        print(f"  [fetch] {self.prefix}.{name}")
        self._cache[name] = f"<{self.prefix}.{name} 响应>"   # 写缓存（会触发 __setattr__）
        return self._cache[name]

>>> api = LazyAPI("users")
>>> api.get_profile                 # __dict__ 里没有 → __getattr__ 兜底
  [fetch] users.get_profile
'<users.get_profile 响应>'
>>> api.get_profile                 # 已缓存？不——缓存写入实例 __dict__ 后，第二次走常规查找
'<users.get_profile 响应>'
```

注意最后两行的微妙之处：**`__getattr__` 里 `self._cache[...] = ...` 把名字写进了实例 `__dict__`，于是下次读取走常规路径不再进钩子**——这是懒加载自动"固化"的标准手法。

## 2. 描述符协议：@property 的本质

**描述符**：定义了 `__get__`/`__set__`/`__delete__` 之一、且**放在类的层级**的对象——它把"某个属性的所有读写"接管走。`@property` 就是一个内置的 data descriptor（Data Model 文档 → descriptors；PEP 252）：

```python
>>> class Temp:
...     @property
...     def celsius(self): return self._c
...     @celsius.setter
...     def celsius(self, v): self._c = v
>>> p = property(Temp.celsius.fget, Temp.celsius.fset)
>>> type(Temp.celsius)          # property 是描述符对象本身
<class 'property'>
>>> Temp.celsius                # 挂在类上（不是实例上！）
<property object at 0x...>
```

手写一遍等价物，彻底看穿 `property` 的马甲：

```python
class Celsius:                        # data descriptor：定义了 __get__ 和 __set__
    def __set_name__(self, owner, name):      # 3.6+：类创建时自动告知"我被命名为 celsius"
        self.public = name
        self.private = "_" + name
    def __get__(self, obj, objtype=None):
        if obj is None:               # 通过类访问（Temp.celsius）时 obj 为 None
            return self
        return getattr(obj, self.private)
    def __set__(self, obj, value):
        if not -273.15 <= value:
            raise ValueError(f"{self.public} 低于绝对零度")
        setattr(obj, self.private, value)

class Temp:
    celsius = Celsius()               # ★ 描述符必须是类属性
    def __init__(self, c): self.celsius = c    # 这行赋值走 Celsius.__set__

>>> t = Temp(25)
>>> t.celsius                         # 走 Celsius.__get__
25
>>> t.celsius = -300
Traceback (most recent call last):
  ...
ValueError: celsius 低于绝对零度
```

关键分类（《Fluent Python》第 23 章）：**data descriptor**（有 `__set__`）**优先于实例 `__dict__`**；**non-data descriptor**（只有 `__get__`，如函数、classmethod、staticmethod）**被实例 `__dict__` 遮蔽**。这解释了两个日常现象：① 实例属性遮不住 `property`（数据校验永远生效）；② **方法其实是 non-data descriptor**——`obj.method` 返回的是绑定方法（`__get__(obj)` 的产物），这就是"函数存在类里、调用时自动绑定 self"的机制。

## 3. 数据校验描述符实战

描述符最大的工程价值：**校验逻辑写一次，声明式复用**——这就是 pydantic/attrs/SQLAlchemy 字段的实现内核：

```python
class Typed:
    """类型校验描述符（基类）。"""
    expected_type: type = object
    def __set_name__(self, owner, name):
        self.name = name                       # 记住字段名（报错信息用）
    def __get__(self, obj, objtype=None):
        if obj is None: return self
        return obj.__dict__[self.name]         # 数据其实存在实例 __dict__
    def __set__(self, obj, value):
        if not isinstance(value, self.expected_type):
            raise TypeError(f"{owner.__name__}.{self.name} 期望 "
                            f"{self.expected_type.__name__}, 得到 {type(value).__name__}")
        obj.__dict__[self.name] = value

class IntField(Typed):
    expected_type = int
    def __init__(self, min=None, max=None):    # 参数化：声明时可以带约束
        self.min, self.max = min, max
    def __set__(self, obj, value):
        super().__set__(obj, value)            # 先过类型关
        if self.min is not None and value < self.min:
            raise ValueError(f"{self.name} 不能小于 {self.min}")
        obj.__dict__[self.name] = value

class StrField(Typed):
    expected_type = str

class AgentConfig:
    """声明式配置类：字段=描述符实例。"""
    max_turns = IntField(min=1, max=100)
    model = StrField()
    def __init__(self, model: str, max_turns: int):
        self.model = model                     # 触发 StrField.__set__
        self.max_turns = max_turns             # 触发 IntField.__set__

>>> cfg = AgentConfig("gpt-4o", 20)
>>> cfg.model
'gpt-4o'
>>> cfg.max_turns = 0
Traceback (most recent call last):
  ...
ValueError: max_turns 不能小于 1
>>> cfg.max_turns = "20"
Traceback (most recent call last):
  ...
TypeError: AgentConfig.max_turns 期望 int, 得到 str
```

对照 06 篇：`dataclass` 生成的是"方法级"样板（init/repr/eq），描述符生成的是"属性级"行为（校验/转换/依赖追踪）；pydantic v2 的 `Field(ge=1, le=100)` 与这里 `IntField(min=1, max=100)` 形状几乎一致——差别只在它用元类+`__set_name__` 收集字段再批量生成校验代码（下一步）。

## 4. type 动态创建类与元类

**类也是对象**（01 篇"一切皆对象"的最后一环）：`class` 语句的幕后是——**调用元类（默认 `type`）创建类对象**。`type(name, bases, namespace)` 三参数形式可以直接手工建类：

```python
>>> Dog = type("Dog", (object,), {"sound": "汪", "bark": lambda self: self.sound * 2})
>>> Dog
<class 'Dog'>
>>> Dog().bark()
'汪汪'
>>> Dog.__mro__
(<class 'Dog'>, <class 'object'>)
```

等价于 `class Dog: sound = "汪"` 加一个方法。**元类**则是"类的类"：`class Foo(metaclass=Meta)` 中，`Meta.__new__`/`__init__` 接管"类对象被创建"这件事，拿到三件套（名字、基类、命名空间）后可以为所欲为——扫描命名空间、注册类、改写方法、注入属性。时机上：**元类在 `class` 语句执行时运行（导入时），实例创建时不再介入**。

**元类自动注册模式**（03 篇类装饰器注册的类级版本；插件框架与 ORM 的共同祖先）：

```python
import abc

class PluginMeta(abc.ABCMeta):            # 元类：所有 Plugin 子类创建时自动登记
    registry: dict[str, type] = {}
    def __new__(mcls, name, bases, namespace, **kw):
        cls = super().__new__(mcls, name, bases, namespace, **kw)
        if bases:                          # 跳过抽象基类自己
            key = namespace.get("name", name.lower())
            mcls.registry[key] = cls       # ★ 副作用：注册（导入即注册，12 篇接续）
        return cls

class Plugin(abc.ABC, metaclass=PluginMeta):
    name: str = ""
    @abc.abstractmethod
    def run(self, payload: dict) -> dict: ...

class SearchPlugin(Plugin):
    name = "search"
    def run(self, payload): return {"results": [...]}

class TranslatePlugin(Plugin):
    name = "translate"
    def run(self, payload): return {"text": "..."}

>>> PluginMeta.registry
{'search': <class 'SearchPlugin'>, 'translate': <class 'TranslatePlugin'>}
>>> PluginMeta.registry["search"]().run({})
{'results': [...]}
```

**ORM 字段注册模式**（SQLAlchemy declarative / 老 pydantic v1 的原理）：

```python
class Field:
    def __init__(self, column_type: str, primary_key: bool = False):
        self.column_type, self.primary_key = column_type, primary_key

class ModelMeta(type):
    def __new__(mcls, name, bases, namespace):
        if bases:                               # 跳过 Model 基类
            columns = {k: v for k, v in namespace.items() if isinstance(v, Field)}
            if not columns:
                raise TypeError(f"{name} 没有定义任何字段")
            namespace["_columns"] = columns     # ★ 收集字段表，顺手注入类属性
            namespace["_table"] = name.lower()  # ★ 约定：表名 = 类名小写
        return super().__new__(mcls, name, bases, namespace)

class Model(metaclass=ModelMeta):
    def save_sql(self) -> str:
        cols = ", ".join(self._columns)
        return f"INSERT INTO {self._table} ({cols}) VALUES ({', ?'*len(self._columns)})"

class User(Model):
    id = Field("INTEGER", primary_key=True)
    name = Field("TEXT")
    email = Field("TEXT")

>>> User._columns, User._table
({'id': <Field ...>, 'name': <Field ...>, 'email': <Field ...>}, 'user')
>>> User(1, "a", "b").save_sql()
'INSERT INTO user (id, name, email) VALUES (?, ?, ?)'
```

`type` 在这里只做了一件事：**在类定义的那一刻**扫描"哪些类属性是 Field 实例"，汇成表并注入 `_columns`——之后所有实例共享。pydantic v2 的提速秘诀就是把这类"元类期收集"换成编译期生成校验函数（`pydantic-core`，Rust），但**收集字段、由声明生成行为**的架构骨架与上面 20 行同构。

## 5. 什么时候不该用（经验做法）

元类与 `__getattribute__` 是 Python 里"最重的锤子"（官方文档 Data Model 原话："99% of users should never think about this"——绝大多数用户永远不需要考虑元类；Tim Peters 的名言"如果你不确定是否需要元类，你就不需要"）。决策清单：

- **能用 `__init__`/`__getattr__`/描述符/类装饰器解决的，不要上元类**。03 篇的注册器装饰器能覆盖大部分"自动注册"需求且更可读；`__init_subclass__`（3.6+，Data Model 文档）是元类最常见用途的**官方平替**——父类里定义，子类创建时收到回调，无需 metaclass 参数：

```python
class Plugin:
    registry: dict[str, type] = {}
    def __init_subclass__(cls, **kw):       # ★ 元类的 99% 需求，一行替代
        super().__init_subclass__(**kw)
        Plugin.registry[getattr(cls, "name", cls.__name__.lower())] = cls
```

- **`__getattribute__` 几乎永远不该手写**——它接管所有属性访问，性能与正确性双杀；`__getattr__`（失败兜底）能满足的都不该碰它；
- **读框架源码是"必须懂"的场景**：pydantic（BaseModel 的元类收集字段）、SQLAlchemy（declarative）、Django ORM（ModelBase）、vLLM 的模型/配置注册（11 篇是模型性能优化系列 Stage 5 的门票）、各类 ABC/Protocol 底层（`abc.ABCMeta` 就是元类）。**懂 ≠ 写**：读懂它们，自己的代码用轻量替代；
- 真需要元类时（类级协议强制、全命名空间扫描、修改类的继承结构），写清注释说明"为什么类装饰器/`__init_subclass__` 不够"。

## 常见陷阱

**陷阱一：重写 `__getattribute__` 不调 super**——无限递归（`self.attr` 在钩子里又触发钩子）；必须 `super().__getattribute__(name)` 起手，且考虑性能（每次访问都过一遍你的代码）。

**陷阱二：`__getattr__` 里访问 `self.xxx` 未定义属性又触发自己**——递归到 `RecursionError`；内部一律用 `object.__getattribute__(self, "_cache")` 或在 `__init__` 就初始化缓存，并对 `"_xxx"` 前缀直接抛 AttributeError。

**陷阱三：描述符定义在实例上**——描述符协议只对**类属性**生效（解释器只在类/MRO 上找描述符）；`self.field = Typed()` 是普通对象，`__get__` 不会被调。

**陷阱四：元类冲突**——`class C(A, B)` 而 A、B 的元类不是同一个（且互不为基）→ `metaclass conflict`；修法是让它们共享一个共同元类（如都基于 `abc.ABCMeta`）。

**陷阱五：把"需要运行时才知道"的逻辑塞进元类**——元类只在导入时跑一次，它不知道将来的实例；实例级状态用 `__init__`/描述符，类级静态信息才归元类管。

## 本篇小结

- 属性读取链：`__getattribute__` 总入口 → data descriptor（类 MRO）→ 实例 `__dict__` → 非 data descriptor/类属性 → `__getattr__` 兜底；MRO 是 C3 线性化的继承查找序，`super()` 是"沿 MRO 下一个"；
- 描述符 = 挂在类上接管某属性读写的对象；`@property`/方法/classmethod 全是描述符；data 优先于实例 dict（校验不可绕），non-data 可被遮蔽（绑定方法的由来）；
- 校验描述符（`__set_name__` + `__set__`）是声明式校验的内核，pydantic/attrs 字段的骨架；
- `type(name, bases, ns)` 手工建类；元类在 class 语句时接管"类的创建"，用于字段收集与自动注册（ORM/pydantic/vLLM 注册原理）；
- 99% 场景用 `__init_subclass__`/类装饰器替代元类；`__getattribute__` 慎碰；读懂框架源码是本篇的主要收益。
