## 1. 迭代协议：for 循环的幕后

官方术语表（Glossary → iterator）定义：**可迭代对象（iterable）**是实现了 `__iter__`、能返回迭代器的对象；**迭代器（iterator）**是实现了 `__next__`（无值可给时抛 `StopIteration`）**且** `__iter__` 返回自身的对象。`for x in obj` 的幕后流程是：

1. 调用 `iter(obj)` → 即调用 `obj.__iter__()`，拿到迭代器；
2. 循环调用 `next(it)` → 即 `it.__next__()`，取下一个值；
3. 捕获 `StopIteration`，**正常结束循环**（对 for 来说不是错误）。

用代码等价展开一个 for 循环：

```python
>>> nums = [10, 20, 30]
>>> it = iter(nums)          # ① 获取迭代器（list 是 iterable，不是 iterator）
>>> it
<list_iterator object at 0x...>
>>> next(it)                 # ② 逐个取值
10
>>> next(it)
20
>>> next(it)
30
>>> next(it)                 # ③ 耗尽
Traceback (most recent call last):
  ...
StopIteration
```

**iterable 与 iterator 是两个角色**（《Fluent Python》第 12 章反复强调）：iterable 可以反复创建新迭代器（每个 for 循环各拿一个），iterator 是一次性的"取值游标"。所以 `list` 是 iterable 不是 iterator；`zip`、`map`、`enumerate`、文件对象则直接是 iterator（耗尽即空，二次遍历为空）：

```python
>>> nums = [1, 2, 3]
>>> for x in nums: pass
>>> for x in nums: pass          # list 可反复遍历
>>> z = zip(nums, "abc")
>>> list(z)
[(1, 'a'), (2, 'b'), (3, 'c')]
>>> list(z)                      # zip 是 iterator：已耗尽
[]
```

自己实现一个满足协议的类——"倒计时"：

```python
class Countdown:
    """可迭代对象：每次 iter() 给一个独立的新迭代器。"""
    def __init__(self, start):
        self.start = start

    def __iter__(self):
        return CountdownIterator(self.start)   # 关键：返回新迭代器

class CountdownIterator:
    """迭代器：有游标状态，一次性。"""
    def __init__(self, n):
        self.n = n
    def __iter__(self):
        return self                            # 迭代器返回自身
    def __next__(self):
        if self.n <= 0:
            raise StopIteration                # 协议约定的结束信号
        self.n -= 1
        return self.n + 1

>>> for x in Countdown(3):        # 可以反复 for：每次拿新迭代器
...     print(x, end=" ")
3 2 1
>>> for x in Countdown(3):
...     print(x, end=" ")
3 2 1
```

## 2. 生成器函数：yield 的暂停与恢复

**生成器函数**：函数体内出现 `yield`，这个函数就不再是普通函数——调用它**不执行函数体**，而是立刻返回一个生成器对象（生成器既是 iterator 也是 iterable，`__iter__` 返回自身）。`yield` 的语义是**暂停并交出一个值，下次 `next` 从暂停点恢复**（官方文档：Python Language Reference → 6.2.8 Yield expressions）。

逐步图解执行流（用打印标注，左边是调用轨迹，右边是解释器视角）：

```python
def gen():
    print("  A: 函数体开始")
    yield 1                  # 暂停点 1
    print("  B: 恢复执行")
    yield 2                  # 暂停点 2
    print("  C: 函数体结束")

>>> g = gen()                # ★ 不打印任何东西！只创建生成器对象
>>> next(g)
  A: 函数体开始              # 第一次 next 才开始执行
1                            # 停在 yield 1，交出 1
>>> next(g)
  B: 恢复执行                # 从 yield 1 的下一句继续
2                            # 停在 yield 2，交出 2
>>> next(g)
  C: 函数体结束              # 执行到末尾
Traceback (most recent call last):
  ...
StopIteration                # 函数返回即迭代结束
```

执行轨迹总结：`gen()` → 创建（不执行）；`next()` → 执行到下一个 yield 暂停；yield 值成为本次 next 的返回值；再 next → 从暂停点恢复；函数体执行完毕 → `StopIteration`。**生成器的局部变量、执行位置全部被解释器保存在生成器对象里**——这就是为什么 `c1 = counter(); c2 = counter()` 两个生成器互不干扰（对比 02 篇闭包：都是"函数 + 环境"的打包，只是恢复机制不同）。

生成器表达式（genexp）是生成器函数的快捷写法，语法同列表推导但用圆括号：

```python
>>> squares = (x * x for x in range(3))   # 不立即计算！
>>> squares
<generator object <genexpr> at 0x...>
>>> next(squares)
0
>>> sum(x * x for x in range(3))          # 函数唯一参数时可省一层括号
5
```

**给生成器喂数据**：`yield` 不只交出值，还能**接收**值——`val = yield x` 中，调用方用 `g.send(v)` 恢复执行，`v` 就是 `val` 的取值（首次必须 `next(g)` 先推进到第一个 yield）：

```python
def running_total():
    total = 0
    while True:
        x = yield total          # 交出 total，等待外界喂数据
        total += x

>>> r = running_total()
>>> next(r)                      # 预激活：推进到第一个 yield
0
>>> r.send(10)                   # 10 赋给 x，循环回到 yield
10
>>> r.send(5)
15
```

有状态的"喂入式"生成器，就是 2001 年 PEP 342 之后 Python 协程的原始形态——第 5 节展开这段历史。

## 3. yield from：委托子生成器

`yield from iterable` 把迭代工作**委托**给子可迭代对象：外层生成器逐个透传子生成器的值，直到子生成器耗尽。等价于一层透明的"管道"：

```python
def inner():
    yield 1
    yield 2
    return "inner done"          # 生成器可以有返回值，放在 StopIteration 里

def outer():
    result = yield from inner()  # 透传 inner 的所有 yield 值
    print(f"  子生成器返回值: {result}")   # return 值通过 yield from 的"表达式值"拿到
    yield 3

>>> list(outer())
  子生成器返回值: inner done
[1, 2, 3]
```

`yield from` 不只是语法捷径：它还建立了**双向通道**（外层 `send` 的值透传给子生成器、异常也透传），这正是它后来被用来实现协程嵌套的原因。但要注意 Python 3.10 起 `yield` 已从**基于生成器的协程**（`@types.coroutine`/`@asyncio.coroutine`）中移除，`async/await` 全面接管（PEP 476 之后的演进：PEP 492 引入 async/await，PEP 525 异步生成器）——**新代码的协程一律写 async/await，yield from 只在"纯迭代委托"场景使用**：

```python
def flatten(nested):
    """递归展平：yield from 最自然的用法。"""
    for item in nested:
        if isinstance(item, list):
            yield from flatten(item)     # 委托给子生成器
        else:
            yield item

>>> list(flatten([1, [2, [3, 4], 5], 6]))
[1, 2, 3, 4, 5, 6]
```

## 4. 惰性求值省内存：实测

生成器逐个产出、用完即弃，**不在内存中持有整个序列**。对比"一亿个数的平方和"两种写法（Windows/Linux 均可复现，数值因机器而异，量级关系稳定）：

```python
import sys
import time

n = 100_000_000

t0 = time.perf_counter()
total_list = sum([x * x for x in range(n)])       # ① 列表推导：先造整表
t_list = time.perf_counter() - t0

t0 = time.perf_counter()
total_gen = sum(x * x for x in range(n))          # ② 生成器：边产边算
t_gen = time.perf_counter() - t0

assert total_list == total_gen
print(f"列表推导: {t_list:.2f}s")                  # 例如 4.8s
print(f"生成器:   {t_gen:.2f}s")                   # 例如 5.1s（耗时接近，见下）

size_list = sys.getsizeof([x for x in range(10_000_000)])
size_gen = sys.getsizeof(x for x in range(10_000_000))
print(f"列表对象: {size_list / 1e6:.0f} MB")       # 例如 89 MB（随元素数线性增长）
print(f"生成器对象: {size_gen} B")                 # 208 B（固定大小！）
```

实测结论（数字因机器而异，关系恒定）：**内存差距是数量级的**——列表随元素数线性增长，生成器恒定约 200 字节（只存当前状态）；**耗时接近甚至生成器略慢**（逐项函数调用开销），因为瓶颈是求和本身。所以选型准则是：**需要反复访问/切片/len → 列表；一次性流水线（读大文件、过滤、转换、求和）→ 生成器**。文件处理是天然范例：

```python
def error_lines(path):
    """逐行流式处理：无论 1GB 还是 100GB 的日志，内存占用恒定。"""
    with open(path, encoding="utf-8") as f:
        for line in f:                 # 文件对象本身就是惰性迭代器
            if "ERROR" in line:
                yield line.strip()

# 经验做法：把"读→过滤→转换→聚合"写成生成器管道，每段职责单一，内存 O(1)
```

## 5. 生成器与协程：一段历史

理解这段历史，才能明白 asyncio 的术语从哪来（09 篇将接续这个话题）：

1. **PEP 255（Python 2.2）**：引入生成器，`yield` 只用于产出值；
2. **PEP 342（Python 2.5）**：`yield` 变成表达式（`x = yield v`），新增 `send()`/`throw()`/`close()`——生成器可以**被外界喂数据、被驱动**，"生成器协程"诞生；
3. **PEP 380（Python 3.3）**：`yield from` 支持**子生成器委托**，协程可以嵌套等待；
4. **PEP 492（Python 3.5）**：`async def`/`await` 原生协程成为一等语法，`await` 在机制上是 `yield from` 的受控特化；
5. **Python 3.8**：`@asyncio.coroutine` 弃用；**3.10**：`@asyncio.coroutine` 移除、生成器协程谢幕；**3.11**：`asend`/`athrow`/`aclose` 支撑的异步生成器成熟（PEP 525，3.6 引入）。

也就是说：**今天 asyncio 的事件循环，驱动协程的底层机制与驱动生成器同源——都是"暂停于一个 yield 点、保存现场、可恢复"**。09 篇会用这个视角讲 `await`：它就是协程版的 `next(g)`。

`itertools` 精选——官方文档自称"gem"，与生成器组合构成声明式流水线：

```python
>>> import itertools as it
>>> list(it.islice((x * x for x in it.count()), 5))   # count: 无限流 + islice 截断
[0, 1, 4, 9, 16]
>>> list(it.chain([1, 2], [3], (4, 5)))               # 串联多个可迭代对象
[1, 2, 3, 4, 5]
>>> list(it.pairwise("ABCD"))                          # 3.10+
[('A', 'B'), ('B', 'C'), ('C', 'D')]
>>> list(it.groupby(["a1", "a2", "b1"], key=lambda s: s[0]))
[('a', <itertools._grouper>), ('b', <itertools._grouper>)]   # 注意：需先按 key 排序
>>> dict(it.zip_longest("abc", "xyz12", fillvalue="?"))
{'a': 'x', 'b': 'y', 'c': 'z', '?': '2'}               # 演示用；更常见于对齐序列
```

**经验做法**：`groupby` 前必须先按 key `sorted`（文档原话 "generally, the iterable needs to already be sorted on the same key"）；无限迭代器（`count`/`cycle`/`repeat`）务必配合 `islice`/`takewhile` 设终止条件，否则死循环。

## 常见陷阱

**陷阱一：生成器是一次性的**——耗尽后再遍历得到空，且**不报错**：

```python
>>> g = (x for x in [1, 2, 3])
>>> sum(g)
6
>>> sum(g)          # 静默返回 0！排查难点就在"不报错"
0
```

**陷阱二：生成器"惰性"到调用时才求值**——捕获循环变量（late binding，02 篇）在生成器里同样存在且更隐蔽：

```python
>>> funcs = [lambda: i for i in range(3)]      # 列表推导立即执行
>>> gens = [(lambda: i) for i in range(3)]     # 同上
>>> g2 = (i for i in range(3))                 # 生成器：i 到 next 时才绑定
>>> list(g2)
[0, 1, 2]                                      # genexp 每次推进按当前迭代取值，安全
```

真正的雷是 genexp 捕获**外部**变量：`x = 1; g = (x for _ in range(3)); x = 99; list(g)` → `[99, 99, 99]`（首个值取定义时的 x，其后取当前值——CPython 行为，勿依赖，避免写法即可）。

**陷阱三：生成器里抛异常被静默吞掉**——`for x in g` 中生成器内部异常会传播出来，但若生成器函数用 `try/finally` 管理资源而迭代方提前 `break`，要靠 `close()`（触发 `GeneratorExit`）走 finally 清理；`with` 块写在生成器里时，**确保生成器被耗尽或显式 close**，否则资源释放推迟到 GC（承接 01 篇：CPython 引用计数通常很快，但 PyPy/跨引用循环不保证）。

**陷阱四：在生成器函数中 return 值却想拿到它**——`return v` 的值只在 `StopIteration.value`/`yield from` 表达式里可见，普通 `for` 循环拿不到；需要"迭代 + 结果"两个产物时用自定义类或让调用方显式处理。

**陷阱五：把 map/zip 当列表用**——它们是 iterator，`len()`、索引、二次遍历都会翻车；需要列表特性时 `list(...)` 物化（并想清楚内存代价，回到第 4 节的选型准则）。

## 本篇小结

- 迭代协议：`iter()` 取迭代器、`next()` 取值、`StopIteration` 结束；**iterable 可反复产迭代器，iterator 是一次性游标**；
- 生成器函数遇 `yield` 暂停交值、恢复续跑，`gen()` 不执行函数体；`send` 可喂数据（协程的雏形）；
- `yield from` 委托子生成器并透传双向通道；新协程一律 async/await（3.10 起生成器协程已移除）；
- 惰性求值省的是**内存**不是时间：一次性流水线用生成器（内存 O(1)），需要反复访问就物化成列表；
- 生成器是 asyncio 的直系祖先：`await` 与 `next(g)` 同源（暂停-恢复机制），09 篇正式展开。
