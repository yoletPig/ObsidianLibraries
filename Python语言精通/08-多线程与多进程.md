## 1. threading 基础：Thread 与生命周期

线程是最小的 OS 调度单位。`threading.Thread(target=fn, args=(...))` 创建线程，`start()` 才真正启动（直接 `run()` 只是普通函数调用，不会并发）：

```python
import threading
import time

def worker(task_id: int) -> None:
    print(f"[{task_id}] 开始, 线程名: {threading.current_thread().name}")
    time.sleep(0.1)                  # 模拟 IO 等待（07 篇：此时释放 GIL）
    print(f"[{task_id}] 结束")

t1 = threading.Thread(target=worker, args=(1,), name="worker-1")
t2 = threading.Thread(target=worker, args=(2,), name="worker-2")

t1.start()
t2.start()
t1.join()          # 等待 t1 结束（不 join 则主线程不等）
t2.join()
print("全部完成")
```

典型输出（交错顺序每次运行可能不同——这正是并发的本性）：

```text
[1] 开始, 线程名: worker-1
[2] 开始, 线程名: worker-2
[1] 结束
[2] 结束
全部完成
```

要点：`daemon=True` 的守护线程随主进程退出被强杀（**不做清理**，不适合管资源）；线程间**共享同一个进程的内存**——这是它快的一面，也是一切竞态的根源。线程局部变量 `threading.local()` 让每个线程各存一份（典型用途：DB 连接 per-thread），需要跨函数传递"线程私有状态"时用它。

## 2. 锁家族与竞态：银行账户实测

**竞态条件（race condition）**：结果取决于线程交错时序的错误。用最经典的银行账户复现（07 篇练习 3 的正式版）：

```python
"""bank_race.py：两个线程同时存款，总额不该丢，但丢了。"""
import threading

class Account:
    def __init__(self, balance: int):
        self.balance = balance
        self.lock = threading.Lock()

    def deposit_unsafe(self, amount: int) -> None:
        # 复合操作：读 → 加 → 写，三步之间可被切换（GIL 只保证单条字节码原子）
        b = self.balance          # ① 读
        b += amount               # ② 算
        self.balance = b          # ③ 写

    def deposit_safe(self, amount: int) -> None:
        with self.lock:           # 临界区：同一时刻只有一个线程进入（05 篇 with 锁）
            b = self.balance
            b += amount
            self.balance = b

if __name__ == "__main__":
    # ---------- 无锁：实测丢失更新 ----------
    acc = Account(0)
    threads = [threading.Thread(target=lambda: [acc.deposit_unsafe(1) for _ in range(100_000)])
               for _ in range(4)]
    for t in threads: t.start()
    for t in threads: t.join()
    print(f"无锁:   balance = {acc.balance} (期望 400000)")   # 典型 25 万上下，每次不同

    # ---------- 有锁 ----------
    acc2 = Account(0)
    threads = [threading.Thread(target=lambda: [acc2.deposit_safe(1) for _ in range(100_000)])
               for _ in range(4)]
    for t in threads: t.start()
    for t in threads: t.join()
    print(f"有锁:   balance = {acc2.balance} (期望 400000)")  # 恒为 400000
```

典型输出：

```text
无锁:   balance = 231437 (期望 400000)
有锁:   balance = 400000 (期望 400000)
```

丢失更新的机理：线程 A 读到 100，还没写回就被切到线程 B 也读到 100，两者各写回 101——两次存款只生效一次。**锁保证的是"临界区互斥"**，而正确性要求你先圈对临界区（读-改-写必须整体在锁内）。

锁家族速查（文档：threading）：

- **`Lock`**：基础互斥锁，不可重入。谁加锁谁释放，重复 acquire 死锁自己；
- **`RLock`**：可重入锁——同一线程可多次 acquire（计数释放），适合"持锁方法调用另一个持锁方法"（递归或类内部组合）；
- **`Semaphore(n)`**：计数信号量，最多 n 个线程同时进入——限制并发连接数的标准件；
- **`Condition`**：等待/通知原语（`wait()`/`notify()`/`notify_all()`）——生产者消费者、线程间状态同步的地基（`queue.Queue` 内部就是它）；
- **`Event`**：布尔开关，`set()`/`wait()`——"准备好了吗"型一次性通知。

```python
import threading

sem = threading.Semaphore(3)         # 最多 3 个并发

def limited(task_id):
    with sem:                        # 第 4 个线程在此排队
        print(f"任务 {task_id} 获得许可")

# RLock 场景：内部方法也要加锁
class SafeList:
    def __init__(self):
        self._items = []
        self._lock = threading.RLock()      # 用 Lock 会死锁：append 调 size 都持锁
    def append(self, x):
        with self._lock:
            self._items.append(x)
    def size(self):
        with self._lock:
            return len(self._items)
    def append_and_report(self, x):
        with self._lock:                    # 外层已持 RLock，内层可重入
            self.append(x)
            return self.size()
```

## 3. queue.Queue：生产者消费者标准解法

**`queue.Queue` 是线程安全的队列**（内部用 Condition 实现），自带阻塞语义：`put()` 满了阻塞、`get()` 空了阻塞。它让你**不碰锁就能写出线程安全的生产者消费者**——共享状态被封装在队列内部：

```python
import queue
import threading
import time

def producer(q: queue.Queue, n: int) -> None:
    for i in range(n):
        time.sleep(0.01)
        q.put(f"任务-{i}")            # 队列有界(maxsize)时：满则阻塞，天然限流
    q.put(None)                       # 结束哨兵

def consumer(q: queue.Queue, name: str) -> None:
    while True:
        item = q.get()                # 空则阻塞，不空转
        if item is None:              # 哨兵：收工（一个消费者一个哨兵）
            q.task_done()
            break
        print(f"  {name} 处理 {item}")
        time.sleep(0.03)              # 模拟处理耗时
        q.task_done()                 # 告知完成（配合 join 统计）

q: queue.Queue = queue.Queue(maxsize=10)
threads = [threading.Thread(target=producer, args=(q, 6)),
           threading.Thread(target=consumer, args=(q, "C1"), daemon=True),
           threading.Thread(target=consumer, args=(q, "C2"), daemon=True)]
for t in threads: t.start()
q.join()                              # 等所有 task_done
q.put(None); q.put(None)              # 再发两个哨兵放倒两个消费者
for t in threads: t.join()
print("全部处理完毕")
```

**经验做法**：线程间传数据用 Queue，**不要**用 list/dict + 自己加锁（容易圈错临界区）；有界队列（maxsize）是天然的背压机制——生产过快时生产者被阻塞，内存不爆。多进程对应物是 `multiprocessing.Queue`（第 4 节）。

## 4. multiprocessing：绕开 GIL 的代价与规则

每个子进程有**独立的解释器与 GIL**（07 篇 CPU 密集的正解），代价是：进程启动慢、**数据不共享**——传参和返回值都要经过**序列化（pickle）**跨进程传输。

```python
"""mp_demo.py"""
import multiprocessing as mp

def square(n: int) -> int:
    return n * n

if __name__ == "__main__":            # ★ 必须有：spawn 方式子进程会重新 import 本模块
    # ---------- Process 手工管理 ----------
    p = mp.Process(target=square, args=(8,))
    p.start()
    p.join()

    # ---------- Pool 进程池（日常主力）----------
    with mp.Pool(processes=4) as pool:
        print(pool.map(square, range(10)))          # 并行 map
        print(pool.apply_async(square, (99,)).get())  # 单个异步任务

    # ---------- 进程间通信：Queue / Pipe ----------
    q = mp.Queue()
    p2 = mp.Process(target=lambda qq: qq.put("来自子进程"), args=(q,))
    p2.start()
    print(q.get())
    p2.join()
```

输出：

```text
[0, 1, 4, 9, 16, 25, 36, 49, 64, 81]
9801
来自子进程
```

三条铁律：

1. **`if __name__ == "__main__":` 必须有**。Windows/macOS（3.8+ 默认）spawn 方式启动子进程时会**重新 import 主模块**，没有保护就无限创建进程；Linux 默认 fork（子进程复制父进程内存，不重跑 import），但为可移植性也一律写保护。3.14 起 Linux 默认也改为 forkserver/spawn 系（PEP 保留意见详见官方 changelog，趋势是更安全）；
2. **能 pickle 才能传**：args/返回值/Queue 里的对象都要可 pickle（01 篇的对象模型）。**lambda、嵌套函数、局部函数、打开的文件句柄、数据库连接、torch 的部分大对象（建议专用的共享机制）不可 pickle**，报错形如 `PicklingError: Can't pickle <function <lambda>...`。报错的正解是把函数提到模块顶层；
3. **进程间不共享内存**：子进程里改一个全局变量，父进程看不见。真要共享用 `mp.Value`/`mp.Array`（配合锁）或 Manager，但优先想"能不能只用 Queue 传消息"——**共享内存是万恶之源，消息传递是正道**。

```python
def process_data(df_chunk):            # ❌ 若 df_chunk 在主进程的函数里闭包创建
    ...
# ✅ 正解：把"创建数据"也放进子进程，或只传可 pickle 的引用（文件路径/URI）
```

**经验做法**：进程池任务粒度要"粗"——每次跨进程传输都有 pickle 成本，传 1 万个小任务不如传 100 个大块（分块 map）；GPU 训练场景的多进程数据加载（DataLoader num_workers）正是"队列传索引、子进程自己读数据"的同一思想。

## 5. concurrent.futures：统一接口

`ThreadPoolExecutor` 与 `ProcessPoolExecutor` 提供**完全一致的 API**（文档：concurrent.futures），换并发模型只改一行构造参数——工程上应默认用它而不是裸 Thread/Pool：

```python
import time
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor, as_completed

def fetch(url_id: int) -> str:
    time.sleep(0.1)                   # 模拟 IO
    return f"resp-{url_id}"

def main() -> None:
    # IO 密集：线程池
    with ThreadPoolExecutor(max_workers=5) as ex:
        futs = {ex.submit(fetch, i): i for i in range(5)}   # submit 立即返回 Future
        for fut in as_completed(futs):                      # 谁先完成先处理谁
            print(futs[fut], "->", fut.result())            # result() 取值（会重新抛异常）

    # CPU 密集：只换一行 → 进程池
    with ProcessPoolExecutor(max_workers=4) as ex:
        results = list(ex.map(lambda n: n * n, range(5)))   # 注意 lambda 的 pickle 限制（见下）

main()
```

要点：

- **`Future`** 是"未来才有值的票据"：`result(timeout=...)` 阻塞取值并**重新抛出工作线程的异常**（异常不会静默丢）、`add_done_callback` 挂完成回调；
- `as_completed(futs)` 按**完成顺序**迭代；`ex.map(fn, seq)` 按**提交顺序**返回；
- `ProcessPoolExecutor` 走 spawn 语义，**同样受 pickle 限制**——`ex.map(lambda ...)` 会炸（lambda 不可 pickle），需改用模块顶层函数（`functools.partial` 也只 pickle 到"部分应用一个顶层函数"的程度）；
- 3.9+ 的 `ThreadPoolExecutor(max_workers=None)` 默认 `min(32, cpu+4)`（官方文档默认值），进程池默认 CPU 核数。

**经验做法**：所有"批量并发"代码统一写成 executor 风格；需求升级到 asyncio 时，10 篇的 `loop.run_in_executor` 能让同一批函数无缝过渡。

## 常见陷阱

**陷阱一：临界区圈错**——只把"写"放进锁里、把"读"放外面（本节银行账户：读-改-写三步必须整体在锁内）；或两个锁的加锁顺序不一致导致死锁（约定全局加锁顺序，或用 `lock.acquire(timeout=)` + 放弃重试）。

**陷阱二：`t.run()` 而不是 `t.start()`**——没有并发，纯串行，还以为多线程生效了。

**陷阱三：lambda/闭包传给进程池**——`PicklingError`；函数必须定义在模块顶层。同样，`mp.Queue` 在 `with Pool` 的 initializer 之外被父子进程乱用会出诡异死锁，进程间队列只在主进程创建、传给子进程。

**陷阱四：daemon 线程里管资源**——主进程退出守护线程被硬杀，文件缓冲丢失、锁没释放；资源清理逻辑放非守护线程或主线程（05 篇 with 纪律）。

**陷阱五：用 time.sleep 轮询代替 Condition/Queue**——`while not ready: time.sleep(0.01)` 既浪费又不精确；等条件用 `Condition.wait()` / `Event.wait()` / `Queue.get()`（阻塞、被通知时才醒）。

## 本篇小结

- `Thread`/`start`/`join` 是骨架；线程共享内存——**竞态来自"读-改-写"被切断**，银行账户实测丢失更新；
- 锁家族：`Lock`（互斥）、`RLock`（可重入）、`Semaphore`（限并发）、`Condition`/`Event`（等待通知）；临界区要圈对、加锁顺序要一致；
- `queue.Queue` 是线程间通信标准件：阻塞语义 + task_done/join + 有界背压，**共享状态封装在队列里**；
- 多进程绕开 GIL：`if __name__ == "__main__"` 保护、一切跨进程皆 pickle、不共享内存传消息不共享状态；
- `concurrent.futures` 统一线程/进程池接口，`Future.result` 会重抛异常、`as_completed` 按完成序——**工程默认写法**。
