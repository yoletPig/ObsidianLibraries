## 1. with 的原理：__enter__ 与 __exit__

`with expr as x:` 的幕后流程（官方文档：Python Language Reference → 3.10 with statement；PEP 343 引入）：

1. 求值 `expr`，调用其 `__enter__()`，返回值绑定给 `x`；
2. 执行 with 块内的语句；
3. **无论块内是否抛异常**，都调用 `__exit__(exc_type, exc_value, traceback)`：
   - 正常结束 → 三个参数都是 `None`；
   - 有异常 → 传入异常三元组，`__exit__` 处理完后异常**继续向外传播**（除非返回 True，见第 3 节）。

用 try/finally 手工等价展开，理解就到位了：

```python
# with f = open(...): 的等价物（简化示意，真实 open 语义见文档）
f = open("data.txt", encoding="utf-8")
try:
    data = f.read()
finally:
    f.close()          # 无论读写是否抛异常，close 一定执行
```

自己实现一个最典型的——计时器：

```python
import time

class Timer:
    """with Timer() as t: ... 之后 t.elapsed 可读。"""
    def __enter__(self):
        self.start = time.perf_counter()
        return self                       # 绑定给 as 后面的名字
    def __exit__(self, exc_type, exc_value, traceback):
        self.elapsed = time.perf_counter() - self.start
        return False                      # 不吞异常：异常照常传播
    def __repr__(self):
        return f"<Timer elapsed={self.elapsed:.4f}s>"

>>> with Timer() as t:
...     sum(range(1_000_000))
...     print(f"耗时 {t.elapsed:.4f}s")   # 注意：此刻 elapsed 还没定稿（__exit__ 未跑）
... # __exit__ 在块结束后才执行，elapsed 在此定稿
耗时 0.0183s
>>> t.elapsed                             # 离开 with 后读取才准确
0.019124
```

细节对照：`as` 绑定的是 `__enter__` 的**返回值**（不是表达式本身）；`__exit__` 返回 `False`（或 None）表示"不处理异常"。注意上面块内读 `t.elapsed` 是早于 `__exit__` 的——所以计时器的读取习惯放在 with 块**之外**。

## 2. contextlib.contextmanager：生成器写法

`@contextlib.contextmanager`（标准库 contextlib 模块）让你用一个**生成器函数**替代两个方法：`yield` 之前的代码是 `__enter__`，之后的是 `__exit__`，yield 的值绑定给 `as`：

```python
import contextlib
import time

@contextlib.contextmanager
def timer(label):
    start = time.perf_counter()          # --- __enter__ 部分 ---
    try:
        yield start                      # ← 块体在此执行；yield 值给 as
    finally:                             # --- __exit__ 部分 ---
        print(f"[{label}] {time.perf_counter() - start:.4f}s")

>>> with timer("sum"):
...     sum(range(1_000_000))
[sum] 0.0189s
```

`try/finally` 不是装饰——**必须写**：如果块内抛异常，异常会在 `yield` 处重新抛出，没有 finally 清理代码就跳过了。这等价于类写法里 `__exit__` 中做清理。

两种写法的取舍（《Fluent Python》第 15 章观点）：

- **`contextmanager`**：简单资源、一次性逻辑，代码量少、局部性好；缺点是**一个类只能干一件事的状态复用**不如类方便（生成器是一次性的，不能复用同一 manager 实例——每次 with 都要重新调用工厂函数）；
- **类实现**：需要状态、可复用实例（如连接池对象既做上下文管理器又做普通对象）、复杂清理逻辑时用类。

**经验做法**：库代码暴露给别人的 API 用类实现（可复用、可继承、可文档化），脚本内部的小工具用 `contextmanager` 快速完成。

`contextlib` 还有几个常用件：`closing(obj)` 给只有 `close()` 的对象补 with 支持；`suppress(*exc)` 有意忽略特定异常（比裸 try/except 意图清晰）；`redirect_stdout/stderr` 重定向输出；`nullcontext` 占位（"可能有上下文也可能没有"的统一接口）。

```python
>>> import contextlib, os
>>> with contextlib.suppress(FileNotFoundError):   # 明确表达"没有就算了"
...     os.remove("/tmp/不存在的文件.txt")
```

## 3. 异常抑制与清理顺序

**`__exit__` 返回 True 的含义是"我已处理，别再传播"**。这是官方文档明文规定的行为，也是 `contextlib.suppress` 的实现原理。三种情形对比：

```python
class Absorb:
    def __enter__(self): return self
    def __exit__(self, *exc): return True        # 吞掉一切异常

class Propagate:
    def __enter__(self): return self
    def __exit__(self, *exc): return False       # 放行异常（默认行为）

>>> with Absorb():
...     raise ValueError("消失")
>>> print("继续执行")                             # 异常被吞，程序活着
继续执行
>>> with Propagate():
...     raise ValueError("向上传播")
Traceback (most recent call last):
  ...
ValueError: 向上传播
```

**经验做法**：除非极个别场景（如 `suppress(FileNotFoundError)` 这种"预期的、无害的异常"），`__exit__` 一律返回 `False`——无差别吞异常是事故之源（14 篇陷阱清单里的"异常吞掉"）。要抑制就**精确指定异常类型**。

**嵌套的清理顺序是 LIFO（后进先出）**——with 块可以叠着写，`__exit__` 按 `__enter__` 的逆序执行，像剥洋葱：

```python
import contextlib

@contextlib.contextmanager
def step(name):
    print(f"  enter {name}")
    try:
        yield
    finally:
        print(f"  exit  {name}")

>>> with step("A"), step("B"), step("C"):    # Python 3.1+ 可逗号并列
...     print("  body")
  enter A
  enter B
  enter C
  body
  exit  C        # 逆序！最后进入的最先退出
  exit  B
  exit  A
```

这个顺序是有讲究的：典型如 `with lock, conn:` ——先释放锁还是先关连接？LIFO 保证**申请顺序与释放顺序严格相反**，与 `__init__`/`__del__`、栈帧退出的直觉一致。即使块中抛异常，每个已进入的 `__exit__` 也会按序执行完。这也是"锁的正确用法"（第 6 节）的根基。

## 4. ExitStack：不定数量的资源

编译期不知道要开几个文件/锁几个资源时，`contextlib.ExitStack` 把"栈"交给运行时管理（官方文档：contextlib → ExitStack）：

```python
import contextlib

def merge_logs(paths, output):
    """打开 N 个日志合并写入：数量运行时才知道。"""
    with contextlib.ExitStack() as stack, open(output, "w") as out:
        files = [stack.enter_context(open(p, encoding="utf-8")) for p in paths]
        for f in files:
            for line in f:
                out.write(line)
    # 离开 with 时：先关 output，再按逆序关 files
```

`ExitStack` 的三种常用动作：`enter_context(cm)` 压入并返回结果；`callback(fn, *args)` 注册任意清理回调（不需要上下文管理器时用）；`pop_all()` 把已压入的资源**转移**到新栈——实现"提交或回滚"语义的标准手法：

```python
def update_configs(paths):
    """全部解析成功才落盘；任何一步失败，已打开/已修改全部回滚。"""
    with contextlib.ExitStack() as stack:
        stack.callback(print, "rollback: 恢复快照")     # 默认回调（失败路径走）
        data = {}
        for p in paths:
            with open(p) as f:
                data[p] = f.read()
        success = stack.pop_all()          # 校验通过：把清理动作转到新栈
        # ... 落盘成功后 success.close() 才真正"提交"
```

**经验做法**：资源获取路径上"半途失败要回滚"的逻辑，用 `ExitStack` + `pop_all` 比手写嵌套 try/finally 清晰得多；Agent/服务代码里动态申请的锁、连接、临时文件，都适合交给 ExitStack 统一收口。

## 5. 实战：临时目录 / 数据库事务 / 锁

**临时目录**——块结束自动删除，永不遗留垃圾（标准库 tempfile）：

```python
import contextlib
import shutil
import tempfile

@contextlib.contextmanager
def temp_workspace():
    d = tempfile.mkdtemp(prefix="pycourse_")
    try:
        yield d
    finally:
        shutil.rmtree(d, ignore_errors=True)

>>> import os
>>> with temp_workspace() as ws:
...     open(os.path.join(ws, "a.txt"), "w").write("hi")
...     print(os.listdir(ws))
['a.txt']
>>> os.path.exists(ws)          # 块外已删除
False
```

**数据库事务**——`__enter__` 开启事务，正常退出提交、异常回滚（以 sqlite3 为例，标准库自带该语义）：

```python
import sqlite3

def transfer(conn, from_id, to_id, amount):
    try:
        with conn:                                    # sqlite3.Connection 的 with：事务
            conn.execute("UPDATE accounts SET balance = balance - ? WHERE id = ?",
                         (amount, from_id))
            conn.execute("UPDATE accounts SET balance = balance + ? WHERE id = ?",
                         (amount, to_id))
    except Exception:
        print("回滚：转账未生效")                      # with 内异常 → 自动 ROLLBACK
        raise
    else:
        print("提交成功")                              # 无异常 → 自动 COMMIT

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE accounts (id INTEGER PRIMARY KEY, balance INT)")
conn.executemany("INSERT INTO accounts VALUES (?, ?)", [(1, 100), (2, 0)])
>>> transfer(conn, 1, 2, 30)
提交成功
>>> conn.execute("SELECT id, balance FROM accounts").fetchall()
[(1, 70), (2, 30)]
```

**锁的正确用法**——**永远用 `with lock:`，不要手动 acquire/release**（08 篇展开线程细节，这里先立规矩）：

```python
import threading

lock = threading.Lock()
counter = 0

def unsafe():
    global counter
    counter += 1                       # ❌ 复合操作非原子（08 篇实测竞态）

def safe():
    global counter
    with lock:                         # ✅ 异常也会释放锁，绝不死锁在手里
        counter += 1
```

手动 `acquire()` 后若中间抛异常且没有 finally `release()`，锁被永久持有——整个程序随后在所有 `acquire` 上卡死。`with` 把释放交给 `__exit__`，异常路径也安全。

## 常见陷阱

**陷阱一：把 `with` 写成 `with open(a), open(b) as f`**——只有最后一个有 `as` 绑定。多资源就多逗号或用 ExitStack：

```python
with open("a.txt") as fa, open("b.txt") as fb:   # ✅ 每个资源独立 as
    ...
```

**陷阱二：`@contextmanager` 装饰的生成器没有 try/finally**——块内抛异常时清理被跳过：

```python
@contextlib.contextmanager
def bad_lock(lock):
    lock.acquire()
    yield                 # ❌ 块内异常 → release 永远不执行 → 后续全部死锁
    lock.release()
```

**陷阱三：`__exit__` 里 return True 吞掉所有异常**（第 3 节）——"莫名丢失错误"的经典来源；要用 `contextlib.suppress(具体异常)` 表达意图。

**陷阱四：finally 中 return/raise 覆盖真实异常**——`__exit__`（或 finally）里主动 `raise`/`return` 会**顶掉**正在传播的原异常，堆栈里看不到真相；清理代码只做清理，想附加信息用 `raise NewError(...) from exc`（14 篇详解）。

**陷阱五：在 `__exit__` 里引用可能已失效的资源**——比如清理顺序错了（先关 conn 再关依赖 conn 的游标）。记住 LIFO，把依赖关系安排成"后申请的依赖先申请的"。

## 本篇小结

- `with` = `__enter__`（返回值给 as）+ `__exit__`（必被调用，LIFO 逆序，参数是异常三元组）；
- `@contextmanager`：yield 前是进入、后是清理，**清理必须放 try/finally**；简单逻辑用它，可复用/带状态用类；
- `__exit__` 返回 True 抑制异常——默认返回 False；抑制必须精确到异常类型（`suppress`）；
- 嵌套清理 LIFO；不定数量资源用 `ExitStack`（`enter_context`/`callback`/`pop_all` 提交-回滚）；
- 实战铁律：文件/锁/事务/临时目录，**一律 with**；锁尤其如此——`with lock:` 是异常安全的唯一简单写法。
