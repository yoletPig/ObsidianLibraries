# 14 - 常见陷阱与代码规范

## 本篇目标

1. 建立**十大陷阱清单**：每条给出反例 + 正确写法，作为评审时的速查表；
2. 掌握 **PEP 8 关键条目**的判断标准（为什么，而不只是"是什么"）；
3. 搭起 **ruff + black 工具链**：让机器管格式与低级错误，人管设计；
4. 拿走一份可直接落地的**代码评审清单模板**。

## 1. 十大陷阱清单

**陷阱一：可变默认参数**（02 篇）。默认值 def 时求值一次：

```python
def add_item(item, items=[]):        # ❌ 跨调用共享同一列表
    items.append(item); return items
def add_item(item, items=None):      # ✅ 哨兵 None
    if items is None: items = []
    items.append(item); return items
```

**陷阱二：`is` 与 `==` 混用**（01 篇）。`is` 只用于单例（`is None`）：

```python
if x is "hello": ...     # ❌ SyntaxWarning，且行为依赖驻留细节
if x == "hello": ...     # ✅ 值比较
```

**陷阱三：闭包 late binding**（02/04 篇）。闭包调用时才读变量：

```python
callbacks = [lambda: i for i in range(3)]       # ❌ 全是 2
callbacks = [lambda i=i: i for i in range(3)]   # ✅ 默认参数固化
```

**陷阱四：可变对象做默认 dict/set 状态**（02 篇变体）——`self.data` 直接引用外部可变对象、类属性当实例属性共享：

```python
class Counter:
    counts = {}                    # ❌ 类属性：所有实例共享一个 dict
    def add(self, k): self.counts[k] = self.counts.get(k, 0) + 1
class Counter:
    def __init__(self):            # ✅ 实例属性在 __init__ 建
        self.counts = {}
    def add(self, k): self.counts[k] = self.counts.get(k, 0) + 1
```

**陷阱五：异常吞掉**。静默 except 让故障不可见：

```python
try:
    save(data)
except Exception:               # ❌ 出错无声无息，排障地狱
    pass
try:
    save(data)
except OSError as exc:          # ✅ 精确类型 + 记录 + 决策（重试/上报/降级）
    logger.error("保存失败: %s", exc)
    raise
```

**陷阱六：裸 except 与过宽捕获**（陷阱五的孪生）。`except:` 连 `KeyboardInterrupt`/`SystemExit`（BaseException）一起抓，Ctrl+C 都停不下来；永远 `except SpecificError:`，兜底也只 `except Exception:`。

**陷阱七：finally（或 `__exit__`）中 return/raise**（05 篇）。清理路径的 return 会**顶掉**正在传播的异常，真相消失：

```python
try:
    risky()
finally:
    return "ok"        # ❌ risky() 的异常被无声丢弃
try:
    risky()
finally:
    cleanup()          # ✅ 清理只做清理；异常继续传播
```

**陷阱八：循环变量泄漏**。Python 的 for 变量在循环外存活（3.0 起列表推导有自己的作用域，但普通 for 不会）：

```python
for i in range(10): ...
print(i)               # 9 —— 泄漏！后续代码误用 i 的隐患
# ✅ 复用变量名前重新赋值；或把循环体包成函数（局部作用域隔离）
```

**陷阱九：深浅拷贝混淆**（01 篇）。`list(x)`/`dict(x)`/`.copy()` 只复制一层：

```python
backup = config.copy()                    # ❌ 嵌套 dict 仍共享
backup = copy.deepcopy(config)            # ✅ 嵌套可变结构用深拷贝
```

**陷阱十：编码问题**。读写文件不声明编码（Windows 默认 GBK，Linux UTF-8，跨平台炸）：

```python
open("data.txt", "w").write(s)                    # ❌ 编码看平台脸色
open("data.txt", "w", encoding="utf-8").write(s)  # ✅ 显式声明（PEP 597 已加入检查工具）
```

## 2. PEP 8 关键条目：背后的理由

PEP 8（官方风格指南）不是审美偏好吗——多数条目背后有工程理由，记住理由才能灵活判断：

- **4 空格缩进，不用 Tab**：跨编辑器/工具链唯一安全的公因数；
- **一行 ≤ 79 字符（文档 72）**：代码评审并排 diff、终端、日志可读；团队可用 88（black 默认）或 100，**关键是全仓库一致**；
- **顶层函数与类空 2 行、类内方法空 1 行**：视觉上划分逻辑块，diff 噪声小；
- **命名**：`snake_case` 函数/变量、`PascalCase` 类、`UPPER_CASE` 常量、`_leading_underscore` 内部——命名是最低成本的文档；**不要自定义影子名**（`l`/`O`/`I` 单字符、与内置同名 `list = []`）；
- **导入三段式 + 显式导入**（12 篇）：标准库/第三方/本地分段，禁 `from x import *`（污染命名空间、静态分析失效）；
- **比较 None 用 is/is not**（01 篇）；**不要用 `== True`**，写 `if flag:`——显式优于隐晦（Python 之禅，`import this`）；
- **异常消息带上下文**：`raise ValueError(f"max_turns 需为正数, 得到 {v}")` 而非裸 `raise ValueError("invalid")`；
- **函数名动词开头**（`load_config`/`validate_user`）配合类型注解（06 篇）构成"自解释 API"。

PEP 8 自己都说："A style guide is about consistency... know when to be inconsistent"——**一致性 > 教条**，团队有既定风格就跟随团队。

## 3. 工具链：ruff + black

现代分工（《Fluent Python》倡导的理念落地）：**机器管格式与低级错误（linter/formatter），人管设计与命名**。当前事实标准组合：

- **black**：无争议格式化（"the uncompromising formatter"，格式没有讨论空间）；
- **ruff**（Rust 实现，一个工具替代 flake8/isort/pyupgrade 等几十个）：查 bug 隐患（bugbear 规则）、排序 import、升级过时语法（06 篇 UP 规则）。

```bash
uv add --dev ruff black            # uv 系列 02 篇的 dev 依赖
black src/ tests/                  # 格式化（无脑执行）
ruff check src/ tests/             # 静态检查
ruff check --fix src/              # 自动修复（未使用 import、import 排序等）
ruff format src/                   # ruff 自带 formatter 也可替代 black（二选一）
```

`pyproject.toml` 配置（全部工具认 PEP 621 标准，12 篇）：

```toml
[tool.ruff]
line-length = 100
target-version = "py310"           # 06 篇约定的 3.10+

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP", "SIM"]   # 风格/错误/import/bugbear/过时语法/简化
# B006 可变默认参数、E711 is 与 == 比较、F401 未使用导入——前两节的陷阱全部机器化

[tool.black]
line-length = 100
```

**经验做法**：规则要在 **pre-commit hook + CI** 双保险强制（提交前本地挡一道、流水线再挡一道），"能被机器发现的问题绝不留给人眼"；规则集宁可从严起步再豁免，`# noqa: B006` 豁免必须带原因注释。

## 4. 代码评审清单模板

可复制到团队 PR 模板（分五区，融合本系列全部章节的要点）：

```markdown
## 正确性
- [ ] 无可变默认参数（B006；02 篇）
- [ ] 循环内创建的 lambda/闭包/Task 已固化变量（02/09 篇 late binding）
- [ ] 生成器/迭代器未被二次消费（04 篇）；map/zip 需要列表特性时已 list()
- [ ] 资源全部走 with（文件/锁/连接/事务，05 篇）；@contextmanager 有 try/finally
- [ ] 异常处理：精确类型、不裸 except、不吞 CancelledError（05/09 篇）、清理路径无 return
- [ ] 深浅拷贝语义正确（01 篇）；文件读写显式 encoding

## 并发（07-10 篇）
- [ ] CPU/IO 密集判断与并发模型匹配（线程/进程/协程）
- [ ] 共享可变状态有保护（线程锁 / asyncio.Lock），跨 await 的临界区圈对了
- [ ] asyncio：无同步阻塞调用（requests/time.sleep）、Task 引用已保存、超时与取消路径完整
- [ ] 多进程入口有 if __name__ == "__main__"，跨进程数据可 pickle

## 可维护性
- [ ] 类型注解完整，mypy 通过（06 篇）；公共函数有 docstring（02 篇）
- [ ] 装饰器已用 functools.wraps（03 篇）；描述符/元类使用有正当理由（11 篇）
- [ ] 无循环导入、无标准库 shadowing（12 篇）；__init__.py 保持薄

## 性能（13 篇）
- [ ] 优化改动附基准数据（timeit repeat 取 min）；只改热点
- [ ] 成员判断用 set/dict；字符串拼接用 join；大规模小对象考虑 slots

## 提交卫生
- [ ] black/ruff 全绿（CI 强制）；命名符合 PEP 8；无调试残留（print/breakpoint）
- [ ] 新增依赖已 uv add 并提交 uv.lock（uv 系列 03 篇）
```

**经验做法**：评审关注**正确性与设计**，格式问题全部让机器挡在门外——如果评审还在讨论缩进，说明工具链没配好；清单不是背的，是"过一遍打钩"的检查表，漏掉的高频项应转化为 lint 规则（工具化一条，清单就少一条）。

## 5. 十大陷阱的"机器化"对照表

最后把陷阱清单与工具规则对上号——**能自动拦截的绝靠自觉**：

| 陷阱 | 拦截手段 |
| --- | --- |
| 可变默认参数 | ruff `B006`（flake8-bugbear） |
| is/== 混用 | ruff `E711`/`E712`；`F632`（is 与字面量） |
| 异常吞掉/裸 except | ruff `E722`（裸 except）、`BLE001`（过宽捕获） |
| 未使用 import/变量 | ruff `F401`/`F841` |
| 过时 typing 语法 | ruff `UP` 系列（pyupgrade） |
| 编码未声明 | PEP 597 检查（`-X warn_default_encoding` / 工具插件） |
| import 排序/顺序 | ruff `I`（isort 规则） |
| 格式 | black / ruff format |
| 循环导入 | ruff `TID` 规则 + mypy；架构靠 12 篇依赖方向纪律 |
| late binding 闭包 | 尚无通用 lint——**评审清单人工把关**（这也是为什么清单不能全废） |

结论很清楚：**工具能兜住 8/10，剩下的是设计判断**（闭包语义、拷贝深度、并发正确性），这正是"人管设计"的那部分，也是本系列 01–13 篇存在的意义。

## 常见陷阱（meta：关于"防陷阱"本身的陷阱）

**陷阱一：把清单当知识而不当流程**——"我知道可变默认参数"和"每次评审真打钩"是两回事；把清单放进 PR 模板、把规则装进 CI，流程才生效。

**陷阱二：规则越多越好**——ruff 全规则开会淹没真问题；按 select 渐进启用，噪音大的规则（如 `SIM` 的部分）评估后再留。

**陷阱三：豁免（noqa）不带注释**——`# noqa` 扫得到但没人记得为什么；格式 `# noqa: B006  # JSON Schema 生成器需要原样列表`，评审时一眼可判。

**陷阱四：用 formatter 的输出质疑 formatter**——black 的哲学是"接受它的格式"（ debates 时间成本远大于审美损失）；真不满意可以整体换 ruff format/black 风格参数，但仓库内保持唯一。

**陷阱五：只靠机器，忘了机器兜不住的部分**——并发正确性、异常策略、API 设计、命名质量；评审时按第 4 节"人区"逐项过，这是清单存在的意义。

## 本篇小结

- 十大陷阱每条都是"反例一眼认出、正解一行写出"：可变默认参数、is/==、late binding、类属性共享、异常吞掉、裸 except、finally return、循环变量泄漏、深浅拷贝、编码；
- PEP 8 记理由不记条文：一致性优先，命名是最便宜的文档；
- 工具链 ruff + black（或 ruff format）：机器挡格式与低级错误（B006/E711/E722/UP/I...），pre-commit + CI 双保险；
- 评审清单五区（正确性/并发/可维护性/性能/提交卫生）可直接落地；机器能拦 8/10 陷阱，剩下靠人管设计；
- 本系列至此闭环：对象模型 → 函数与装饰器 → 协议与抽象 → 并发三件套 → 元类/import/性能 → 陷阱与规范——**从"会写 Python"到"精通 Python"的差别，就在于这些层是否真正长进肌肉**。
