# 04 - 复制

## 本篇目标

- 掌握三种复制模式：主从（同步/半同步/异步）、多主、无主，并能说出各自的故障语义。
- 系统分析复制滞后引发的三类问题（读己之写/单调读/一致前缀读）与对应修复手段。
- 推导无主复制的 Quorum 交集条件 W+R>N，理解读修复与反熵如何最终收敛。
- 手写一个带故障切换的主从复制模拟，亲眼看到"异步复制 + 主宕机"的数据丢失。

## 1. 为什么要复制：三件事

复制（replication）= 在多台机器上保留同一份数据的副本。动机有三（DDIA 第 5 章开篇）：

1. **数据离用户更近**（地理复制，降低读延迟）。
2. **部分机器故障时系统仍可用**（冗余，提高可用性）。
3. **读请求分摊到多副本**（提高读吞吐，第 01 章 x 轴）。

副本一多，核心难题立刻出现：**怎么让 N 个副本保持一致**。一切方案都是对"写操作如何在副本间传播"的回答。三大变量：谁接收写（单主/多主/无主）、什么时候确认（同步/半同步/异步）、冲突怎么办（修主/合并）。

## 2. 主从复制：同步、半同步、异步

主从复制（leader-based replication，也叫 master/slave、primary/secondary）的分工：**主副本**（leader）接收全部写，把变更记入日志（binlog/WAL），从副本（follower）消费日志追平；**读**可以走主也可以走从（读写分离）。

按"主副本何时向客户端确认"，分三档：

| 模式 | 确认时机 | 主宕机时 | 延迟 | 现实代表 |
| --- | --- | --- | --- | --- |
| 完全同步 | 等**全部**从副本落盘确认 | 最少丢数据 | 最高；任何一个从挂了，写全停 | 几乎没人用（可用性太差） |
| **半同步** | 等**一个**从确认 + 主自己落盘 | 最多丢 0 条（那一个从有全量） | 中 | MySQL semi-sync、Raft 日志提交（等多数派） |
| 完全异步 | 主自己落盘即返回 | 可能丢已确认写 | 最低 | MySQL 默认异步、Redis 主从、PG 流复制默认 |

推导半同步为什么是"甜点"：设主副本 + n 个从。完全同步的写延迟 = max(所有副本的网络+落盘)，可用性 = 所有从都活着；异步的丢数据窗口 = 主宕机瞬间未传输的日志。半同步只要求"有一个从跟上了"，主宕机后可以无损切换到它——**用一个从的延迟代价，买断了"确认过的写不丢"**。Raft 的"提交需多数派日志匹配"（第 05 章）本质是半同步思想的多数派版：3 副本半同步等 1 个从 ≈ 等 2 个节点确认（含主）。

故障切换（failover）的完整流程与三个坑：

1. **检测**：主超时（02 章：超时≠死亡，误判是常态）。
2. **选举/提升**：选新主。坑一——**数据丢失**：异步复制下旧主有未同步的写，切换后丢失。
3. **重配置**：客户端与剩余从感知新主。坑二——**脑裂（split brain）**：旧主没死透（只是 GC 停顿），与新主同时接收写；必须用**纪元/ fencing token** 强制旧主下台（第 11 章租约）。坑三——**风暴**：新主切换瞬间大量写涌入 + 所有从重建同步。

## 3. 复制滞后：三类问题与修复

异步复制下，从副本落后主副本若干毫秒到若干秒，这段时间内读到旧值（复制滞后，replication lag）。三个经典场景（DDIA 第 5.2 节；第 03 章已提，这里给完整对策）：

```
读己之写违反：                       单调读违反：
 用户: 写头像(x) → 主               用户: 读(x) → 主副本 → 看到 v2
 随后: 读头像 → 从(还停在 v1)        随后: 读(y) → 从副本 → 只到 v1（倒流）
 一句话：自己写的看不见               一句话：越读越旧

一致前缀读违反（分片版）：
 分片1: 帖子"P"（复制慢）   分片2: 回复"R"（复制快）
 用户先看到 R（回复），后看到 P（帖子）→ 因果乱序
```

修复手段（都是"弱一致系统上做会话保证"的路由层技巧，经验做法）：

- **读己之写**：写后 N 秒内该用户的读强制走主；或客户端记录最后写入时间戳，从副本滞后于该戳就换副本/等待。
- **单调读**：按用户 ID 粘住同一副本（同一从）或记录"该副本已服务到的水位"。
- **一致前缀读**：把因果相关对象放同一分片（第 06 章的分区设计题），或由中件层校验版本顺序。
- **降低滞后本身**：从副本并行应用日志（MySQL 5.7+ 的多线程复制）、写操作分组提交、监控 `Seconds_Behind_Master` 并告警。

## 4. 多主复制：冲突是常态

多主（multi-leader）：多个副本都接收写，互相复制。动机：跨数据中心（每个机房一个主，本地写低延迟）、离线操作（手机端本地库是"主"，联网时同步）、协作编辑（Google Docs）。

代价：**同样的数据可能被两个主同时改**（写冲突）。经典例子：两个机房同时把某商品标题改成不同值。冲突处理策略：

1. **避免冲突**（最好）：把同一记录的"所有权"固定给某个主（如按用户分区），从根上让两个主不写同一行（经验做法优先级最高）。
2. **LWW（last-write-wins）**：带时间戳比较，新的赢。简单，但丢数据（先到的写被静默覆盖），且依赖 02 章"不可靠的物理时钟"。
3. **保留所有版本，应用层合并**：用版本向量（02 章）识别并发写，交给应用决定怎么合（Dynamo 的兄弟值 sibling，CouchDB 的冲突文档）。
4. **CRDT（收敛数据类型）**：为"加法计数器""集合""序"等特定结构设计可交换的合并算子，数学上保证收敛（Shapiro et al., *Conflict-free Replicated Data Types*, SSS 2011）。
5. **自动解决算法**：操作转换 OT（Google Docs 文本）等。

## 5. 无主复制：Quorum 读写与修复

无主（leaderless，Dynamo 风格，出处：DeCandia et al., *Dynamo: Amazon's Highly Available Key-value Store*, SOSP 2007）：**没有主副本**，写发给任意副本集合，读也发给多个副本比版本。

参数 N = 副本总数，W = 写成功的副本数，R = 读需要的副本数（N=3, W=2, R=2 是常见起步）。

**Quorum 交集推导**（必须会证明）：

- 读到至少一个"最新写入"的条件：**W + R > N**。证明：写集合大小 W，读集合大小 R，两者都在 N 个副本中；若 W + R > N，则 |写∩读| ≥ W + R - N ≥ 1，读集合至少含一个写成功的副本 → 只要该副本保留"最新"值即可读到。
- 保证写入成功的交集（防两个并发写都"成功"却互不知晓）：**W > N/2**，即写集合过半（两个过半集合必相交，同 Raft 多数派逻辑）。
- 极端取值：W=1, R=N → 写快读慢（Dynamo 可配置）；W=N, R=1 → 读强写慢；W+R>N 只保证"读到至少一份最新副本"，**不等于线性一致**（DDIA 第 5.3 节明确指出：quorum 不是万能，时序交错下仍可能读到旧值，比如写还没开始读就完成了的场景）。

读后写、写前读的版本管理靠**向量时钟**（02 章）：并发写产生 sibling，读时合并。两个收敛机制：

- **读修复（read repair）**：读时发现某副本版本旧，顺手把新值写回去。
- **反熵（anti-entropy / hinted handoff）**：后台进程比对副本间差异（Merkle 树高效比对，Cassandra 实现），慢慢补齐——这是"最终一致"里"最终"的执行者。

```python
# leaderless_quorum.py —— 无主复制的 Quorum 读、读写修复与反熵
import asyncio, random

class DynamoNode:
    def __init__(self, name):
        self.name = name
        self.data = {}           # key -> (value, version向量简化为单调版本号)
        self.online = True

class DynamoCluster:
    def __init__(self, n=3):
        self.nodes = [DynamoNode(f"N{i}") for i in range(n)]
        self.N, self.W, self.R = n, n // 2 + 1, n // 2 + 1

    def _alive(self):
        return [x for x in self.nodes if x.online]

    async def put(self, key, value):
        """写：向 W 个活副本写（Dynamo 实际按 preference list 选，这里简化为随机）"""
        targets = random.sample(self._alive(), min(self.W, len(self._alive())))
        ver = max((v for x in self.nodes for _, v in x.data.get(key, [(None, 0)])),
                  default=0) + 1
        for t in targets:
            await asyncio.sleep(random.uniform(0.005, 0.02))   # 网络延迟
            t.data[key] = (value, ver)
        return ver

    async def get(self, key):
        """读：向 R 个副本读，取版本最高者；顺便做读修复"""
        targets = random.sample(self._alive(), min(self.R, len(self._alive())))
        results = []
        for t in targets:
            await asyncio.sleep(random.uniform(0.005, 0.02))
            if key in t.data:
                results.append((t, t.data[key]))
        if not results:
            return None
        best_node, (best_val, best_ver) = max(results, key=lambda p: p[1][1])
        # ---- 读修复：把落后副本补到最新（异步，不阻塞读）----
        for node in targets:
            if key not in node.data or node.data[key][1] < best_ver:
                node.data[key] = (best_val, best_ver)
                print(f"  [读修复] {node.name} 补齐 {key}={best_val}@v{best_ver}")
        return best_val, best_ver

    async def anti_entropy(self):
        """后台反熵：两两比对，落后者补齐（真实系统用 Merkle 树，这里直接全量）"""
        changed = 0
        for key in {k for x in self.nodes for k in x.data}:
            versions = [(x, x.data.get(key)) for x in self.nodes if key in x.data]
            _, (val, ver) = max(versions, key=lambda p: p[1][1])
            for node, pair in versions:
                if pair[1] < ver:
                    node.data[key] = (val, ver)
                    changed += 1
        return changed

async def main():
    random.seed(7)
    c = DynamoCluster()
    # 场景1：一个副本掉线时写入（W=2 仍成功），恢复后靠读修复/反熵追平
    c.nodes[2].online = False
    ver = await c.put("sku:1", "99元")
    print(f"写成功 v{ver}（副本2 掉线，只写到 2 个副本）")
    c.nodes[2].online = True
    val, v = await c.get("sku:1")
    print(f"quorum 读: {val}@v{v}")

    # 场景2：掉线副本上根本没有该数据 —— 反熵把它补齐
    print("反熵修复数:", await c.anti_entropy())
    print("副本2 现在的数据:", c.nodes[2].data)

asyncio.run(main())
```

## 6. 手写主从复制 + 故障切换

把第 2 节的模式写成可运行代码，重点观察**异步复制下主宕机的丢数据**与**纪元号防脑裂**：

```python
# master_slave.py —— 主从复制：同步/半同步/异步 + 宕机切换 + 纪元防脑裂
import asyncio, random

class Replica:
    def __init__(self, name, epoch=-1):
        self.name = name
        self.data = {}
        self.log = []                 # 已应用的操作日志
        self.online = True
        self.epoch = epoch            # 纪元：第几任主（fencing token 的雏形）

    def __repr__(self):
        return f"{self.name}(epoch={self.epoch}, data={self.data})"

class Cluster:
    def __init__(self, mode="async"):
        self.mode = mode              # "sync" / "semi" / "async"
        self.nodes = [Replica("M"), Replica("F1"), Replica("F2")]
        self.leader = self.nodes[0]
        self.epoch = 0

    async def write(self, key, value):
        """主副本写，按模式决定等谁；返回成功与否"""
        self.leader.data[key] = value
        self.leader.log.append(("W", key, value, self.epoch))
        acks = 1
        tasks = [asyncio.create_task(self._replicate(f, key, value))
                 for f in self.nodes if f is not self.leader and f.online]
        results = await asyncio.gather(*tasks, return_exceptions=True)
        acks += sum(1 for r in results if r is True)
        if self.mode == "sync" and acks < len(self.nodes):
            raise RuntimeError("完全同步：有从副本未确认，写失败（可用性差）")
        if self.mode == "semi" and acks < 2:
            raise RuntimeError("半同步：无任何从副本确认，写失败")
        return True                   # 异步模式：主落盘即成功（可能丢数据）

    async def _replicate(self, f, key, value):
        await asyncio.sleep(random.uniform(0.01, 0.08))   # 复制延迟（异步的丢数据窗口）
        f.data[key] = value
        f.log.append(("W", key, value, self.epoch))
        return True

    async def failover(self):
        """主宕机 → 提升'日志最长'的从为新主，纪元+1"""
        self.epoch += 1
        self.leader.online = False                      # 旧主"死"了（可能只是 GC 停顿）
        alive = [x for x in self.nodes if x.online]
        new_leader = max(alive, key=lambda x: len(x.log))  # 选日志最长的从（数据最全）
        new_leader.epoch = self.epoch
        old, self.leader = self.leader, new_leader
        # 纪元防脑裂：旧主若'复活'，其纪号已落后，写操作会被拒绝（见 guarded_write）
        return old, new_leader

    async def guarded_write(self, key, value, claimed_epoch):
        """带纪元检查的写：旧主复活后携带旧纪元来写 → 拒绝（fencing）"""
        if claimed_epoch < self.epoch:
            raise PermissionError(f"纪元过期({claimed_epoch}<{self.epoch})，拒绝旧主写入")
        return await self.write(key, value)

async def main():
    random.seed(3)
    for mode in ("sync", "semi", "async"):
        c = Cluster(mode)
        await c.write("k", mode + "-v1")          # 正常写
        await asyncio.sleep(0.1)                  # 等异步复制传播
        old, new = await c.failover()
        lost = set(old.data.items()) - set(new.data.items())
        print(f"[{mode}] 切换 {old.name}->{new.name}，旧主独有数据(即丢失): {dict(lost) or '无'}")
        # 旧主复活试图继续写（脑裂场景）
        try:
            await c.guarded_write("k", "ghost-write", claimed_epoch=old.epoch)
        except PermissionError as e:
            print(f"[{mode}] 脑裂防护: {e}")

asyncio.run(main())
```

运行会看到：sync 模式旧主与从完全一致（不丢）；async 模式旧主有未复制的独有数据——**这些已确认写入在切换后直接消失**，这就是异步复制丢失数据的全过程。而 guarded_write 展示的纪元检查，就是 Raft 任期（term）做同类防护的雏形。

## 常见误区

1. **"读写分离能提升写性能"**：不能。所有写仍走主（单主架构），读写分离只扩读吞吐；写瓶颈要靠分区（第 06 章）或换无主/多主。
2. **"半同步复制 = 数据零丢失"**：MySQL 半同步在"等待 ACK 超时"时会自动降级回异步（rpl_semi_sync_master_timeout），降级瞬间等于异步——所谓零丢失只在"降级未发生"的时间窗内成立。要无丢失得靠多数派共识（Raft/Paxos 系存储）。
3. **"Quorum 配置了就是强一致"**：W+R>N 只保证读到"至少一份最新"，不保证读到的是**这份**（并发交错、sibling 合并都可能给出旧序结果）。DDIA 第 5 章给了具体反例；要线性一致还得加读时读修复强制 + 写前读确认（Dynamo 的做法）或干脆用共识系统。
4. **"故障切换是瞬间且无损的"**：切换全程（检测超时 + 选举 + 客户端重连）通常秒级，期间服务降级；异步复制还有丢数据窗口。可用性目标（几个 9）要按"切换时间 × 频率"核算，而不是假设永远不切。
5. **"LWW 是无害的冲突解决"**：它按墙钟时间戳丢写，而墙钟恰恰不可靠（02 章）。两个并发写里"先执行"的那个可能因为时钟慢被判旧而消失——计数器、余额类数据用 LWW 会直接丢更新，CRDT 或应用层合并才是正解。

## 本篇小结

- 复制的三个动机（就近/冗余/读扩展）与一个核心难题（写传播）；同步/半同步/异步的取舍 = 数据安全 ↔ 延迟与可用性。
- 半同步是工程甜点；Raft 多数派提交是其多数派版；故障切换三坑：丢数据、脑裂（用纪元/fencing 防）、切换风暴。
- 复制滞后三类问题各有路由层解法；优先做会话保证而不是上强一致（经验做法）。
- 多主的本质是"引入冲突"，最好的处理是避免（所有权分区），其次 CRDT/应用层合并，LWW 会静默丢数据。
- 无主复制：W+R>N 保证读到最新副本（可推导），W>N/2 保证写集合相交；读修复 + 反熵负责最终收敛；Quorum ≠ 线性一致。
- 手写模拟确认了两个关键事实：异步复制丢数据是机制性的，纪元检查能挡住脑裂写。
