# 01 - 为什么要分布式

## 本篇目标

- 用具体的物理数字回答"为什么单机终会不够"：CPU、内存、磁盘、网络各自的天花板在哪里。
- 掌握扩展性立方（Scalability Cube，AKF）的 x/y/z 三轴，能对任意系统说出它该往哪个轴扩。
- 理解共享 nothing（shared-nothing）架构为什么是分布式的默认形态。
- 算清分布式的三笔代价账（部分失败、不可靠网络、无全局时钟），建立"能单机就单机"的工程直觉。

## 1. 单机的物理极限：天花板是拿数字写出来的

"单机不够了"不是玄学，是几个物理量到达上限后的必然。先看一台 2024 年前后典型服务器（双路 x86，如 2×32 核）大致能到哪（数量级参考：各厂商公开规格，如 Intel Xeon 8480+ / AMD EPYC 9554，NVMe 盘公开标称值）：

| 资源 | 单机典型上限 | 量级参考 | 到顶后意味着什么 |
| --- | --- | --- | --- |
| CPU | ~128 物理核 / 256 线程 | 单核吞吐有能耗墙（主频 2004 年后基本停在 3~4 GHz） | CPU 密集任务并发度封顶 |
| 内存 | 几 TB（DIMM 插槽与寻址位宽决定） | 8~12 TB 已是高端双路机器顶配 | 放不下的数据必须落盘或外移 |
| 磁盘 | 容量可堆到 PB 级（多盘），但**随机 IOPS 有墙**：SATA SSD ~10 万，NVMe ~100 万（公开标称） | 顺序写 NVMe ~7 GB/s | 每秒请求数超过 IOPS 就开始排队 |
| 网络 | 单口 100 Gbps（RoCE/IB 更高） | 一台机器网卡带宽 ~12.5 GB/s | 数据进出量超带宽，延迟上升 |
| 单点可靠性 | 1 台机器年可用性撑死 99.9%（经验值） | 一年 ~8.7 小时不可用 | 软硬件故障 = 服务全停 |

几个关键的不对称性（这些数字决定架构，值得背下来）：

- **内存随机访问 ~100 ns vs 磁盘随机访问 ~100 μs vs 网络同机房往返 ~0.5 ms**：跨一次网络的代价是内存的 5000 倍（数量级参考：Jeff Dean 2009 年在 LADIS 的演讲《Buildings, Badges, and Big Data》给出的延迟数字表，业内通用）。所以分布式设计的第一直觉是**少跨网络**，而不是"反正集群大随便跨"。
- **单核性能停滞**：CPU 主频在上世纪末至 2004 年随摩尔定律狂飙，此后转为主要靠堆核（Herb Sutter 2005 年著名文章《The Free Lunch Is Over》即宣告此事）。**横向扩核就是最朴素的分布式前奏**。
- **故障率随规模线性增长**：集群里跑 1 万块硬盘，即使单盘年故障率只有 1%，平均每天也有 ~2.7 块盘要坏（巴氏聚类结论：故障是常态不是例外，见 *A View of Cloud Computing*, Communications of the ACM 2010）。

一个直观的演算：假设你的推理服务单机每秒能处理 200 个请求，业务峰值 2 万 QPS——从第一天起你就需要至少 100 台机器，这不是"优化单机"能解决的。再看训练：一个 175B 参数的模型，fp16 权重就要 350 GB，**任何单卡（即使 80 GB 的 A100/H100）都放不下**，多卡多机不是选择题（数据点：GPT-3 论文 *Language Models are Few-Shot Learners*, Brown et al., 2020，明确记载其使用数千 GPU 训练）。

```python
# limits_demo.py —— 亲手感受"单机极限"的两个具体例子
import time

def memory_ceiling_demo():
    """演示内存天花板：申请超过物理内存+swap 的内存会发生什么"""
    # 经验做法：先用 /proc/meminfo 看可用内存，再决定测试规模，避免真把机器 OOM
    with open("/proc/meminfo") as f:
        for line in f:
            if line.startswith(("MemTotal", "MemAvailable", "SwapTotal")):
                print(line.strip())
    # 在 WSL2/容器里谨慎执行大分配，OOM killer 会杀掉进程（OS 系列第 5 篇讲过）

def latency_ladder_demo():
    """延迟阶梯：为什么'跨网络一次'在架构里是大事件"""
    # 数量级参考（同机房）：内存 100ns / SSD 随机读 100us / 网络往返 500us
    steps = [
        ("内存随机访问", 100e-9),
        ("NVMe 随机读", 100e-6),
        ("同机房网络往返", 0.5e-3),
        ("跨机房网络往返", 30e-3),   # 例如北京-上海 ~30ms 光速+设备延迟
    ]
    base = steps[0][1]
    for name, t in steps:
        print(f"{name:<14} {t*1e3:>8.3f} ms   = 内存访问的 {t/base:>8,.0f} 倍")

if __name__ == "__main__":
    latency_ladder_demo()
    # memory_ceiling_demo()  # 需要看内存上限时再打开
```

## 2. 扩展性立方：给"怎么扩"建坐标系

Martin Abbott 与 Michael Fisher 在《Scalability Rules》（中译《架构即未来》）里把扩展方案总结为三条轴，业内常称 **AKF 立方**（AKF Partners 是该公司名）：

```
                  z 轴：按数据分片（查询路由）
                        ▲
                        │
                        │
                        │
  y 轴：按功能拆分 ─────►●───────────► x 轴：克隆（复制/负载均衡）
 （服务化/微服务）      原点：单体
```

- **x 轴——克隆**：跑 N 个一模一样的实例，前面放负载均衡。最简单，数据库只读副本也算 x 轴（读请求摊开）。天花板：**写**还是要落到同一个库；实例间共享同一份有状态数据时，缓存一致性、会话粘滞都是坑。
- **y 轴——按功能拆**：把单体拆成"订单服务/库存服务/支付服务"。每个服务可以独立扩、独立故障。天花板：数据量大的那张表仍然是一个库的瓶颈；服务间调用把一次请求变成一串网络跳。
- **z 轴——按数据分片**：把数据切开（按用户 ID、按地区），每个分片跑一套完整的 x/y 结构。这是唯一能同时解决"请求多"和"数据大"的轴，代价是分片路由、跨片查询、再平衡（第 06 章专讲）。

经验做法：扩容决策沿"x → y → z"顺序考虑。x 轴成本最低（无业务改造）；y 轴是组织与代码结构的重构；z 轴是数据层的伤筋动骨，不到数据/写入量顶不住不上 z。很多公司的演进史就是这三个字母的先后出场顺序。

举三个对号入座的例子：

1. 无状态推理服务加副本 → 纯 x 轴（Stage 7 里 Ray Serve 的 replicas 就是干这个）。
2. 把"模型推理/图片处理/风控校验"拆成独立服务 → y 轴。
3. 用户表按 user_id 哈希切 16 片、每个用户永远落在同一片 → z 轴。

```python
# scaling_cube.py —— 用一个"计数器服务"演示三条轴的区别
import threading
from collections import defaultdict

class Monolith:
    """原点：单体。所有请求打一个实例，一把锁（等价于单库单表）"""
    def __init__(self):
        self.counts = defaultdict(int)
        self.lock = threading.Lock()          # 并发上限 = 锁的吞吐（OS 11 篇的老朋友）

    def handle(self, user, action):
        with self.lock:
            self.counts[action] += 1
            return self.counts[action]

class XAxis:
    """x 轴：N 个相同实例轮询。吞吐×N，但'写同一个状态'依然要共享存储（这里略去）"""
    def __init__(self, n=4):
        self.replicas = [Monolith() for _ in range(n)]
        self.rr = 0
        self.lock = threading.Lock()

    def handle(self, user, action):
        with self.lock:                        # 轮询选副本（真实系统由负载均衡做）
            r = self.replicas[self.rr % len(self.replicas)]
            self.rr += 1
        return r.handle(user, action)

class ZAxis:
    """z 轴：按 user 分片。同一个 user 永远命中同一片 → 无共享状态、无锁竞争"""
    def __init__(self, n=4):
        self.shards = [Monolith() for _ in range(n)]

    def handle(self, user, action):
        shard = hash(user) % len(self.shards)  # 哈希路由（第 06 章会升级成一致性哈希）
        return self.shards[shard].handle(user, action)

if __name__ == "__main__":
    m, x, z = Monolith(), XAxis(), ZAxis()
    print("单体:", [m.handle("u1", "click") for _ in range(3)])
    print("x轴:", [x.handle("u1", "click") for _ in range(3)])   # 注意：分散到 4 个副本，每副本各自计数
    print("z轴:", [z.handle("u1", "click") for _ in range(3)])   # 同一 user 路由固定，计数连续
```

注意上面输出里的微妙差别：x 轴分散后"同一用户的连续计数"不再连续（每个副本一份状态）——**x 轴扩的是无状态吞吐，扩不了有状态一致性**；z 轴把"同一用户"钉在同一片上，状态自然连续。这个差别是第 04 章复制、第 06 章分区的全部动机。

## 3. 共享 nothing：分布式的默认形态

按"节点之间共享什么"，系统分三档：

| 架构 | 共享什么 | 优点 | 死穴 |
| --- | --- | --- | --- |
| 共享内存（shared-memory） | 多核共享内存 | 硬件保证一致 | 只有一台机器，回到第 1 节的天花板 |
| 共享磁盘（shared-disk） | 节点共享存储（如 Oracle RAC、共享 NAS） | 节点无状态可加 | 存储层锁与带宽成瓶颈，规模上限低 |
| **共享 nothing（shared-nothing）** | 什么都不共享：CPU/内存/磁盘各自独立，只靠网络消息通信 | 可扩展性最强，故障域隔离最好 | 一切问题都变成"消息与一致性"问题 |

DDIA 第二部分开篇的定义：shared-nothing（又称无共享架构）中，每台机器独立拥有内存与磁盘，节点间仅通过网络传递消息（DDIA 第 1、2 章）。**共享 nothing 是几乎所有大规模系统的最终形态**：Kafka 的 broker、Redis Cluster 的分片、Cassandra 的节点、PyTorch DDP 的多机训练进程，本质都是"各自管好自己的一亩三分地，靠网络说话"。

为什么它赢？因为共享内存/共享磁盘架构里，"共享"本身就是瓶颈与单点：所有节点抢同一把存储层的锁、同一条总线；而 shared-nothing 把资源切干净了，扩展变成"再加一个独立节点"。代价则是本系列后面 12 章要处理的一切——**共享没有了，一致性只能靠消息协议重建**。

## 4. 分布式的代价：三笔必须付的账

好处不是免费的。分布式系统从此背上三笔永久的账（DDIA 第 8 章系统总结了前两笔；第三笔出自 Lamport 对分布式时间的经典论述，下一章展开）：

**账一：部分失败（partial failure）**。单机系统里程序要么崩溃要么活着，失败是"全或无"；分布式系统里最常见的状态是**一部分活了、一部分死了，而你分不清哪部分**。协调者发出请求后收不到回复，可能是对方崩了、可能是网络断了、可能是对方慢——它无法区分，只能猜（这个"无法区分崩溃与失联"的问题在 FLP 论文里被形式化：*Impossibility of Distributed Consensus with One Faulty Process*, Fischer, Lynch, Paterson, 1985）。

**账二：不可靠网络**。消息可能丢、延迟任意大、乱序到达。你在代码里写 `send()` 成功，只代表"塞进了本机内核缓冲区"，不代表对方收到了（第 02 章会证明：这是分布式一切协议复杂性的根源）。

**账三：无全局时钟**。没有任何办法让两台机器对"现在几点"达成完全一致（物理极限：光速 + 时钟晶振误差 + NTP 校正的不可控偏移）。"A 先于 B 发生"这种单机上显而易见的判断，在分布式里需要专门机制来定义（第 02 章的 Lamport 时钟就是为此而生）。

```python
# partial_failure.py —— 部分失败现场：请求超时后，你连对方死没死都不知道
import asyncio, random

class Node:
    def __init__(self, name, alive=True):
        self.name, self.alive = name, alive

async def unreliable_call(node: Node, timeout: float = 0.2):
    """向 node 发请求。三种结局：正常返回 / 超时（可能对方活着只是慢）/ 明确拒绝（连接失败）"""
    if random.random() < 0.3:                       # 模拟 30% 概率网络丢包或节点失联
        await asyncio.sleep(timeout + 1)            # 让调用方超时
    if not node.alive:
        raise ConnectionError(f"{node.name} 明确不可达")   # 这是最"幸运"的失败：至少你知道它死了
    await asyncio.sleep(random.uniform(0.01, 0.15)) # 正常网络延迟
    return f"{node.name} 回复 OK"

async def main():
    random.seed(42)
    a = Node("节点A", alive=True)
    for i in range(5):
        try:
            # 经验做法：永远给网络调用设超时；没超时的调用是在"赌对方还活着"
            print(i, await asyncio.wait_for(unreliable_call(a), timeout=0.2))
        except asyncio.TimeoutError:
            # 关键：超时后请求的真实结局有三种——没到达 / 到了没执行 / 执行了但回复丢了
            # 调用方无法区分，这直接导致第 08/09 章的幂等与重试问题
            print(i, "超时：A 到底执行了没有？不知道。")
        except ConnectionError as e:
            print(i, e)

asyncio.run(main())
```

## 5. 单机最优原则：能单机就单机

把前面四节合起来，得到本系列第一条工程铁律：

> **经验做法：如果一个系统在可预见范围内单机能扛住，就坚决不要上分布式。** 每引入一个跨进程边界，就引入一次网络失败的可能、一个需要同步的副本、一类新的 bug。

判断"要不要分布式"的四个硬问题（任何一个是"是"才值得上）：

1. **数据**会不会超单机内存/磁盘上限（或随机 IOPS 顶不住）？
2. **吞吐**会不会超单机 CPU/网络上限（x 轴加副本也解决不了写瓶颈）？
3. **可用性**要求是否高于单机能给的（要求 99.95% 以上，就必须多机冗余）？
4. **物理距离**是否要求就近服务（多地部署本身强制分布式）？

反例（现实里很多人一开始就冲分布式）：个人博客上一个 Redis；内网工具链用一个 3 副本的 etcd 存配置却从没考虑过 etcd 自己的运维成本；千行代码的爬虫用上 Celery + Redis + 三个 worker。这些场景单进程/单机 + 定时备份更可靠也更便宜。SQLite 的作者长期论证"大多数网站数据库用 SQLite 就够"（*SQLite: The World's Most Widely Used Database* 相关访谈与文档《Appropriate Uses For SQLite》），说的就是这件事。

正例（不得不分布式的）：vLLM 推理服务多副本（x 轴）、一个亿级用户的 feed 存储（z 轴）、LLM 多机训练（模型放不下，物理强制）。

## 常见误区

1. **"分布式系统 = 性能更好"**：恰恰相反，跨网络一次的代价是内存访问的几千倍。分布式买到的是**扩展性与可用性**，常常以牺牲单次请求延迟为代价。单机不够时先问：是无状态吞吐不够（x 轴就能解决）还是数据/写瓶颈（才需要分区）？
2. **"加机器就能线性扩展"**：x 轴对有状态服务无效（见第 2 节代码输出），z 轴有再平衡与跨片查询成本，共享点（分布式锁、单一协调者）会先于数据成为瓶颈。扩展性要用 AKF 三轴具体分析，不存在"集群大了自然就快"。
3. **"部分失败是罕见场景，先不考虑"**：在千台规模集群里，任何时刻都有节点在坏（第 1 节的巴氏聚类）。生产分布式代码里，每一个远程调用都要回答"对方没回怎么办"——这不是防御式编程的加分题，是及格线。
4. **"我们的内网很可靠，网络问题可以忽略"**：数据中心网络的设计目标是"高可用"不是"完全可靠"：交换机升级、光纤被挖断、网卡驱动 bug、TCP 缓冲区打满造成的"伪死连接"都真实存在。Google 的 Jupiter 网络、AWS 的历史故障报告都把网络分区列为常态事件（DDIA 第 8 章《不可靠的网络》一节有系统论述）。
5. **"微服务拆得越细越分布式越先进"**：y 轴拆分的单位是"独立演进的组织边界"，不是"类的个数"。把单体拆成 50 个服务，换来的是 50 份部署/监控/一致性难题（分布式的三笔账各付 50 次）。拆分粒度跟团队规模走（经验做法：一个服务一个团队养得起为止，参考康威定律，《人月神话》Brooks, 1975 中组织结构与系统结构的对应关系）。

## 本篇小结

- 单机天花板的三个硬数字：单核性能早已停滞、内存带宽/容量有限、随机 IOPS 与网卡带宽有物理墙；LLM 训练从第一天起就跨过全部天花板。
- 扩展性立方三轴：x 克隆（治无状态吞吐）、y 按功能拆（治组织复杂度）、z 按数据分片（治数据与写瓶颈）；决策顺序经验做法是 x → y → z。
- shared-nothing 是大规模系统的默认形态：扩展性最好、故障域最隔离，代价是一切变成消息与一致性问题。
- 分布式三笔账：部分失败（分不清对方死活）、不可靠网络（发送成功≠送达）、无全局时钟（"谁先发生"需要专门定义）——后面每一章都在还这三笔账的利息。
- 单机最优原则：能单机就单机，上分布式前过四个硬问题（数据/吞吐/可用性/距离）。
