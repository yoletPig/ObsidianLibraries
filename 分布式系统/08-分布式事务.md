## 1. 问题定义：原子提交跨了机器

第 07 章留的问题：一个事务要写两个分片（甚至两种存储），怎么保证"要么都提交、要么都不提交"？单机靠 undo log + 一个锁管理器闭环；跨机后，**决定"提交"的瞬间必须所有参与者都同意**，而这个决定过程本身可能被故障打断——这就是**原子提交问题（atomic commit）**。

关键约束（回忆 02 章）：协调者发出"提交"决定后收不到某参与者确认，它**无法区分**"对方死了"与"网络断了"；而参与者在等决定时也**无法自作主张**（自己提交了，协调者那边可能已决定中止）——双方都卡在"必须等对方"上。2PC 是这个困境下的最优工程解，但不是完美解。

## 2. 2PC：流程与故障走查

**两阶段提交（Two-Phase Commit，Jim Gray 1978 年《Notes on Data Base Operating Systems》中形式化）**：

```
阶段一（表决/准备）                          阶段二（决定/提交）
协调者 ── PREPARE ──► 参与者A               协调者 ── COMMIT ──► A（应用提交）
协调者 ── PREPARE ──► 参与者B               协调者 ── COMMIT ──► B
          A 落盘 redo/undo，锁住资源
          A 回 YES（此后只能听候发落）
          B 回 YES
协调者收到全部YES → 本地落盘"决定提交"
```

规则要点：参与者回 YES 后进入**不确定态（in-doubt）**——不能再自行提交或中止，必须死等协调者的第二阶段指令；协调者落盘决定后（write-ahead），无论发生什么都要把决定送达所有参与者。

**故障逐一走查**（面试核心题，每一条都要能推）：

| 故障点 | 后果 | 恢复动作 |
| --- | --- | --- |
| 参与者在 PREPARE 前崩 | 协调者收不齐 YES → 决定 ABORT | 参与者重启后收到/查出 ABORT，无副作用 |
| 参与者回 YES 后、收到 COMMIT 前崩 | 该参与者卡在不确定态；协调者若活着会重发 COMMIT | 参与者重启后**必须问协调者**（不能自决），期间其锁被占用 |
| **协调者在收到全部 YES 前崩** | 参与者等不到决定，但大家还都没提交 → 安全超时后统一 ABORT | 参与者自行中止（因为没人收到过"决定提交"） |
| **协调者在落盘决定后、发完 COMMIT 前崩** | 最坏情形：参与者不知道全局决定是提交还是中止，**全部卡死** | 参与者重启后只能阻塞等待协调者恢复；协调者从磁盘决定记录恢复后重发 |
| 网络分区：协调者与部分参与者失联 | 同上——失联的参与者卡在不确定态 | 分区恢复后重发决定 |

第 4 行是 2PC 的命门：**协调者单点 + 参与者阻塞**。协调者崩了，参与者既不能提交也不能中止（都可能违反原子性），资源锁全程持有，下游全堵。这就是"2PC 时代码可用、故障时阻塞"的精确含义。

```python
# two_pc.py —— 2PC 模拟：正常路径 + 协调者"落盘决定后"宕机的阻塞现场
import asyncio

class Participant:
    def __init__(self, name, fail_after_yes=False):
        self.name, self.fail = name, fail_after_yes
        self.state = "init"          # init / prepared / committed / aborted / in_doubt
        self.locked = False

    async def prepare(self):
        # 模拟业务校验 + 写 redo/undo + 锁资源
        self.locked = True
        self.state = "prepared"
        return "YES"

    async def commit(self):
        if self.state == "in_doubt":
            self.state = "committed"
            self.locked = False
            return f"{self.name} 恢复后提交"
        self.state = "committed"; self.locked = False
        return f"{self.name} 提交"

    async def abort(self):
        self.state = "aborted"; self.locked = False
        return f"{self.name} 中止"

class Coordinator:
    def __init__(self, parts):
        self.parts = parts
        self.decision_disk = None     # "落盘"的决定记录（持久化点）

    async def run(self, coord_dies_after_decision=False):
        # ---- 阶段一 ----
        votes = []
        for p in self.parts:
            votes.append(await p.prepare())
            if p.fail:
                return "参与者故障 → 协调者决定 ABORT（安全）"
        if all(v == "YES" for v in votes):
            self.decision_disk = "COMMIT"          # 写决定到磁盘（持久点）
            print("  协调者: 落盘决定=COMMIT")
            if coord_dies_after_decision:
                await asyncio.sleep(0.05)
                print("  协调者: 宕机（决定已落盘但未送达）")
                return "所有参与者卡死在 in_doubt，锁不释放，等待协调者恢复"
            results = [await p.commit() for p in self.parts]
            return " → ".join(results)
        self.decision_disk = "ABORT"
        return " → ".join([await p.abort() for p in self.parts])

async def main():
    print("== 场景1: 正常 ==")
    print(" ", await Coordinator([Participant("A"), Participant("B")]).run())
    print("== 场景2: 参与者在准备前死 ==")
    print(" ", await Coordinator([Participant("A", fail_after_yes=True), Participant("B")]).run())
    print("== 场景3: 协调者落盘决定后宕机 ==")
    parts = [Participant("A"), Participant("B")]
    r = await Coordinator(parts).run(coord_dies_after_decision=True)
    print(" ", r)
    print("  参与者状态:", [(p.name, p.state) for p in parts], "← 锁仍被持有")

asyncio.run(main())
```

2PC 与 Raft 的关系值得点破：**2PC 解决"一次事务跨多方"的原子性，Raft 解决"一份日志跨副本"的复制一致性**，两者正交。etcd 的事务（txn）是 Raft 上的单键空间原子操作，MySQL XA 才是 2PC。把 Raft 叫"分布式事务"是常见口误。

## 3. 3PC 为什么没人用

三阶段提交（Three-Phase Commit，Skeleton of idea 出现于 1980 年代）在 PREPARE 与 COMMIT 之间插入 **PreCommit** 阶段，并引入超时：参与者若在 PreCommit 后失联，超时后**自行提交**（因为"能到 PreCommit 说明大家都同意过"）。

理论目标：消除 2PC 的阻塞（协调者死了参与者也能自己决定）。但前提是**网络延迟有上界 + 时钟可靠**——正是 02 章证伪的两个假设。分区场景下，被隔离的一组参与者可能超时后自行提交，而协调者侧决定的是 ABORT → **原子性被破坏**。结论（DDIA 第 9 章明确表述）：3PC 在非拜占庭异步网络下既不完美也不实用；工程界要么用 2PC + 共识化协调者（协调者本身跑在 Raft 上，如 TiDB 的 TiKV 事务协调、 Spanner 的 Paxos group），要么换 Saga 类最终一致方案。

## 4. Saga：长事务的补偿之路

**Saga**（Garcia-Molina & Salem, *Sagas*, SIGMOD 1987；微服务语境的复兴见 Chris Richardson《微服务架构设计模式》第 4 章）：把大事务拆成 **T1 → T2 → ... → Tn** 的本地事务序列，每个 Ti 配一个补偿事务 Ci（语义上"撤销 Ti 的业务效果"，不是数据库回滚）。任何一步失败，**反向执行已完成步骤的补偿**：T1 T2 T3 失败 → 执行 C2 C1。

```
订票案例：订机票 → 订酒店 → 扣款
 正常:  T1订机票✓ → T2订酒店✓ → T3扣款✓ → 完成
 失败:  T1订机票✓ → T2订酒店✓ → T3扣款✗(余额不足)
        → C2退酒店 → C1退机票 → 用户收到"预订失败"
```

补偿不是回滚的三个不同点：补偿**发布新的可见状态**（机票先显示"已订"再变"已退"，其他事务可能看到中间态）；补偿本身也可能失败（需要重试到成功，所以**补偿必须设计成可重试的幂等操作**）；没有隔离性（Saga 之间可能交错，需要业务层防脏读——如"已订未付款"状态让其他流程不可见）。

编排（orchestration）与协同（choreography）两种实现：

- **编排式**：中央协调器驱动每一步（代码直观、可观测；协调器本身要高可用——用状态机 + 持久化进度实现，别把协调器做成另一个 2PC 协调者）。
- **协同式**：每步完成后发事件，下游订阅（无中心、松耦合；流程散落在各服务里，链路长后不可维护）。经验做法：步骤 ≤ 3 用协同式，更多用编排式。

```python
# saga_ticket.py —— 订票 Saga：正向流程 + 反向补偿 + 补偿失败的幂等重试
import asyncio

class BookingSaga:
    def __init__(self):
        self.done = []            # 已完成的正向步骤（用于反向补偿）
        self.log = []

    async def step(self, name, forward, compensate):
        try:
            await forward()
            self.done.append((name, compensate))
            self.log.append(f"T:{name} ✓")
            return True
        except Exception as e:
            self.log.append(f"T:{name} ✗ ({e})")
            return False

    async def run(self):
        async def book_flight():
            await asyncio.sleep(0.01); print("  已订机票")
        async def cancel_flight():
            print("  已退机票（补偿，可重试）")
        async def book_hotel():
            await asyncio.sleep(0.01); print("  已订酒店")
        async def cancel_hotel():
            print("  已退酒店（补偿，可重试）")
        async def charge():
            raise RuntimeError("余额不足")     # 最后一步失败

        ok1 = await self.step("订机票", book_flight, cancel_flight)
        ok2 = await self.step("订酒店", book_hotel, cancel_hotel) if ok1 else False
        ok3 = await self.step("扣款", charge, None) if ok2 else False
        if not ok3:
            for name, comp in reversed(self.done):     # 反向补偿
                await comp()
        print("  流程:", " → ".join(self.log))

asyncio.run(BookingSaga().run())
```

## 5. TCC 与消息最终一致

**TCC（Try-Confirm-Cancel）**：业务层的"准 2PC"。每个参与方实现三个接口：Try 预留资源（冻结额度而非扣款）、Confirm 确认（真正扣）、Cancel 释放预留。TCC 的本质是把"数据库锁资源"提前到"业务预留资源"，第二阶段不再碰底层事务，因此协调器崩溃时业务状态自洽（预留要么 Confirm 要么 Cancel，都有幂等接口兜底）。代价：**每个参与方要写三个接口且全部幂等**，侵入性大（支付/资金类业务愿意付这个代价）。

**本地消息表 / Outbox 模式**（最常用的最终一致落地，经验做法首选）：跨服务写操作拆成"本地事务 + 事件投递"：

1. 业务写与"待发消息"记录在**同一个本地事务**里落库（原子性由单机事务保证）。
2. 后台轮询（或 binlog 订阅，如 Canal/Debezium）把待发消息投到 MQ，成功后标记已发。
3. 消费方幂等处理（第 09 章幂等键）。

它把"分布式事务"降级为"本地事务 + 至少一次投递 + 幂等消费"，没有跨库锁、没有协调者单点，唯一代价是**消费方短暂可见延迟**——大多数业务完全可接受。Kafka 的事务（transactional producer，read-process-write 原子性）是此思路在流处理侧的对应物，但覆盖面不同（见 09 章）。

## 6. 选型决策表

| 方案 | 一致性 | 阻塞/单点 | 侵入性 | 适用 |
| --- | --- | --- | --- | --- |
| 2PC/XA | 强（原子性） | 协调者宕机参与者阻塞 | 低（协议级） | 短事务、参与方少、同公司基础设施 |
| 3PC | 理论强 | 网络分区下破坏原子性 | — | **不用于生产** |
| Saga | 最终一致（有中间态） | 无（补偿幂等重试） | 中（写补偿） | 长流程、跨服务、可接受中间态（订票/订单履约） |
| TCC | 准强一致（业务预留） | 无（Confirm/Cancel 幂等） | 高（三接口） | 资金/库存等不容忍中间脏数据的短流程 |
| Outbox+MQ | 最终一致 | 无 | 低（一张表+轮询） | 微服务间状态同步的事实标准 |

## 常见误区

1. **"用了 Raft/etcd 就不需要 2PC"**：Raft 保证**一份日志**在副本间一致；"一个操作横跨两个系统"的原子性它管不着。跨系统原子性要么 2PC、要么 Saga/Outbox 拆解。
2. **"Saga 的补偿 = 数据库回滚"**：补偿是新的业务操作（退票单），会被其他事务看见；且补偿自身必须幂等可重试。把补偿当"撤销历史"会导致中间态被下游消费后无法收拾。
3. **"TCC 的 Try 失败就不用 Cancel"**：Try 超时时**不知道**对方是否已预留成功，必须照样发 Cancel（幂等），否则留下幽灵冻结额度。TCC 的正确性全靠幂等，这是它侵入性高的根源。
4. **"Outbox 会不会丢消息/重复消息"**：会重复（至少一次投递），不会丢（同事务落库）。正确姿势是消费端按消息 ID 幂等去重，而不是给投递加"恰好一次"的执念。
5. **"2PC 性能差所以直接淘汰"**：2PC 的可用性差（阻塞）与延迟高（两轮 RTT + 锁持有期）是真的；但在**短事务、参与方稳定、同栈管理**的场景（如同一厂商数据库集群、X AU 内部），XA 依然是省心选择。选型看故障容忍度，不看流行度。

## 本篇小结

- 跨机原子提交的困境来自"决定点与执行点分离 + 网络不可靠"；2PC 用准备阶段 + 落盘决定给出了工程最优，代价是协调者宕机后参与者阻塞。
- 2PC 五种故障走查中，"协调者落盘决定后宕机"是命门；3PC 想靠超时自救，却把原子性押在不可靠的网络与时钟上，被实践淘汰。
- Saga 用"本地事务序列 + 反向补偿"换取无阻塞长流程；补偿必须幂等、可重试、可被看见（与回滚的三点区别）。
- TCC 把锁资源业务化（预留），适合资金类短流程；Outbox + 至少一次投递 + 幂等消费是微服务最终一致的事实标准。
- 选型口诀（经验做法）：强一致短事务 2PC、资金预留 TCC、长流程 Saga、服务间解耦 Outbox。
