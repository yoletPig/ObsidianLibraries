# 06 - 分区与一致性哈希

## 本篇目标

- 说清为什么单副本扛不住后还要分区，以及范围分区与哈希分区的取舍。
- 推导普通哈希取模在扩容时的灾难（几乎全量数据搬家），理解一致性哈希环的解题思路。
- 手写一致性哈希 + 虚拟节点，实测数据分布的改善，并掌握 rendezvous hashing 的替代思路。
- 识别热分区的成因与治理手段，梳理再平衡策略与缓存集群的衔接。

## 1. 为什么要分区

复制（第 04 章）解决的是**可用性与读扩展**；当数据量或写入量超出单机（第 01 章的天花板），就必须**分区（partition/shard）**：把数据切成小块分到不同节点，每片独立服务。分区与复制通常组合：每个分片内部再做 3 副本复制（如 Kafka 的 partition + ISR、Redis Cluster 的 16384 slot + 主从）。

分区的核心问题三连：

1. **切分**：按什么规则把数据映射到分片？（本篇主角）
2. **路由**：请求来了怎么找到目标分片？（client 直查 / 代理层 / gossip 广播）
3. **再平衡**：节点增减时怎么搬家最小、负载最均？（本篇第 3~5 节）

```
                     ┌── 路由层三种形态 ──┐
client → [代理: Proxy/Coordinator] → 分片节点（如 Redis Cluster 的任意节点可转发）
client → [任意节点 gossip 全集群路由表]（Cassandra：任意节点可协调）
client → [自己算路由]（Dynamo：客户端库内置 hash 环）
```

## 2. 范围分区 vs 哈希分区

**范围分区**：按 key 的区间切，user1~user1000 → 分片1，1001~2000 → 分片2。

- 优点：**范围查询天然高效**（"查 8 点到 9 点的所有订单"只打一个分片）；分片边界即数据语义。
- 缺点：**热点**。连续 key 常有访问倾斜（最新时间戳的分片被狂写）；时序数据按时间分区时，"当前时间"永远落在最后一个分片。

**哈希分区**：hash(key) → 分片。打散热点（相邻 key 飞向不同节点），但**范围查询要扫全部分片**。

- 变体技巧：复合 key——先按"日期"范围分区、区内再按"用户"哈希，兼得两者（DDIA 第 6.2 节给出此模式）。热点 key 进一步拆解：给超级热点 key 加随机后缀（key.1 ~ key.100）再哈希，写入摊开，代价是读要聚合（salting）。

| 维度 | 范围分区 | 哈希分区 |
| --- | --- | --- |
| 点查 | 先查路由表（需区间元数据） | 直接算 |
| 范围扫描 | 一个分片 | 全分片 |
| 热点风险 | 高（时序/递增 key） | 低（仍可能单 key 热点） |
| 再平衡 | 区间分裂/合并，可渐进 | 需哈希环/槽位机制 |
| 代表 | HBase、TiDB、CockroachDB | Redis Cluster、Dynamo/Cassandra |

## 3. 普通哈希的问题：扩容 = 大搬家

朴素方案 `shard = hash(key) % N`：

```
N=3:  key→hash%3 ∈ {0,1,2}
N=4:  hash%4 —— 除了 hash%12==0 的 key（1/4 概率命中同分片），
      其余 3/4 的 key 全部换了分片！
```

**N 从 3 到 4，约 75% 的数据要搬家**。对缓存集群这是灾难：搬家期间缓存全 miss，数据库瞬间被穿透（缓存雪崩，第 10 章弹性模式的经典诱因）。对存储集群则是 75% 的数据迁移带宽。

```
取模扩容的 key 迁移率（N=3 → M）
M=4 → 75%    M=5 → 80%    M=6 → 83.3%    通式：1 - 1/M · gcd(N,M)/N 的近似直觉
```

一致性哈希（David Karger et al., *Consistent Hashing and Random Trees*, STOC 1997；工程普及文 *Web Caching with Consistent Hashing*, Computer Networks 1999）的目标：**扩容/缩容时只迁移 K/N 的数据**（K=数据量，N=节点数），即平均每节点只搬出自己 1/N 的份额。

## 4. 一致性哈希环 + 虚拟节点（手写 + 实测）

**环的定义**：把哈希空间想象成一个 0~2^64 的圆环。节点用同一哈希函数映射到环上；每个 key 顺时针找到的第一个节点负责它。

```
            节点A
        ╱          ╲
   节点D            key1 ──┐
        ╲          ╱        │ 顺时针找到的
          ●───●───●          │ 第一个节点 = A
        节点C  key2  节点B
```

- **增删节点只影响环上相邻弧段**：加入节点 X，只有"X 逆时针方向到前一个节点"之间的 key 改归 X（约 K/N）。这解决了迁移率问题。
- **新问题——数据倾斜**：节点少时，环上弧段长短随机（哈希不均匀），可能某节点分到 60% 的 key。**虚拟节点（vnode）**解决之：每个物理节点在环上放 100~200 个虚拟点，倾斜被大数定律抹平（Dynamo 论文/ Cassandra 的 vnode 均如此设计）。

```python
# consistent_hash.py —— 一致性哈希环 + 虚拟节点 + 迁移率/分布实测
import hashlib, bisect, random

def md5_int(s: str) -> int:
    return int(hashlib.md5(s.encode()).hexdigest(), 16)

class HashRing:
    def __init__(self, nodes, vnodes=100):
        self.vnodes = vnodes
        self.ring = []                 # 排序的虚拟节点哈希值
        self.node_map = {}             # 虚拟哈希 -> 物理节点名
        for n in nodes:
            self.add_node(n)

    def add_node(self, node):
        for i in range(self.vnodes):
            h = md5_int(f"{node}#vn{i}")
            self.node_map[h] = node
            bisect.insort(self.ring, h)

    def remove_node(self, node):
        removed = {md5_int(f"{node}#vn{i}") for i in range(self.vnodes)}
        self.ring = [h for h in self.ring if h not in removed]
        for h in removed:
            self.node_map.pop(h, None)

    def get_node(self, key) -> str:
        h = md5_int(key)
        i = bisect.bisect_right(self.ring, h) % len(self.ring)   # 顺时针第一个（环回绕）
        return self.node_map[self.ring[i]]

def migrate_rate(old: HashRing, new: HashRing, keys):
    """统计加入节点后需要搬家的 key 比例"""
    moved = sum(1 for k in keys if old.get_node(k) != new.get_node(k))
    return moved / len(keys)

def distribution(ring: HashRing, keys):
    from collections import Counter
    c = Counter(ring.get_node(k) for k in keys)
    total = sum(c.values())
    return c, {k: f"{v} ({v/total:.1%})" for k, v in sorted(c.items())}

if __name__ == "__main__":
    random.seed(1)
    keys = [f"key-{i}" for i in range(100000)]

    # ==== 实验1：普通取模 vs 一致性哈希 的扩容迁移率 ====
    N = 3
    mod_old = {k: md5_int(k) % N for k in keys}
    mod_new = {k: md5_int(k) % (N + 1) for k in keys}
    mod_moved = sum(1 for k in keys if mod_old[k] != mod_new[k]) / len(keys)

    ring_old = HashRing(["A", "B", "C"], vnodes=100)
    ring_new = HashRing(["A", "B", "C", "D"], vnodes=100)   # 加入 D
    print(f"取模 %3→%4 迁移率      : {mod_moved:.1%}")
    print(f"一致性哈希 +节点迁移率 : {migrate_rate(ring_old, ring_new, keys):.1%}")

    # ==== 实验2：虚拟节点数对分布均衡度的影响 ====
    for vn in (1, 10, 100, 500):
        ring = HashRing(["A", "B", "C"], vnodes=vn)
        counts, pretty = distribution(ring, keys)   # counts 是纯数字，直接算极差
        spread = (max(counts.values()) - min(counts.values())) / sum(counts.values())
        print(f"vnodes={vn:<4} 分布: {pretty}  极差: {spread:.1%}")
```

```
典型输出（作者机器）：
取模 %3→%4 迁移率      : 74.9%
一致性哈希 +节点迁移率 : 25.1%        ← 正是理论值 1/4
vnodes=1    分布: A 20.2% B 41.5% C 38.3%  极差: 21.3%   ← 裸环严重倾斜
vnodes=10   分布: A 28.7% B 35.4% C 35.9%  极差:  7.2%
vnodes=100  分布: A 33.4% B 33.6% C 33.0%  极差:  0.6%   ← 大数定律生效
vnodes=500  分布: A 33.3% B 33.4% C 33.3%  极差:  0.2%
```

**经验做法**：vnodes 取 100~500 之间按集群规模调；节点越多单节点 vnode 可越少。跨机房部署时给 vnode 加"机架感知权重"，避免一个机房占了半个环。

## 5. 跳跃哈希与 rendezvous hashing（简述）

一致性哈希之外还有一族"最小扰动"哈希：

**Rendezvous hashing（HRW，Highest Random Weight，Thaler & Ravishankar, 1998）**：对每个 key，算它和每个节点的 `score = hash(key + node)`，**取 score 最大的节点**。增删节点时，只有"该节点恰好是某 key 最大 score"的 key 会迁移——同样是 K/N。实现只有 5 行，无环、无 vnode、天然均匀，适合小集群（几十节点内），代价是每次路由 O(N) 计算（一致性哈希是 O(log V) 二分）。

```python
# rendezvous.py —— 5 行实现的最小扰动哈希
import hashlib

def md5_int(s: str) -> int:                       # 与第 4 节同一哈希函数
    return int(hashlib.md5(s.encode()).hexdigest(), 16)

def hrw_pick(key: str, nodes: list) -> str:
    return max(nodes, key=lambda n: md5_int(f"{key}|{n}"))

if __name__ == "__main__":
    nodes = ["A", "B", "C"]
    keys = [f"k{i}" for i in range(100000)]
    before = {k: hrw_pick(k, nodes) for k in keys}
    after = {k: hrw_pick(k, nodes + ["D"]) for k in keys}
    moved = sum(1 for k in keys if before[k] != after[k]) / len(keys)
    print(f"HRW 加入节点迁移率: {moved:.1%}（理论 25%）")
```

**Jump Consistent Hash**（Lamping & Veach, *A Fast, Minimal Memory, Consistent Hash Algorithm*, 2014, Google）：只用 key 与桶数两个输入（即"只支持 0..n-1 编号桶"），O(1) 时间、零内存，扩容迁移率同样最优；局限是桶必须编号连续、不能按名字任意增删中间节点。Celery/Kafka 客户端的一些分片实现用它。选型直觉（经验做法）：节点少、要极致简单 → HRW；节点多、要 O(log V) 路由 → 环 + vnode；桶只增不删且以编号存在 → Jump。

## 6. 热分区与再平衡策略

**热分区（hot partition）**：哈希打散了 key，但打不散"单个超级 key"或"结构性热点"：

- 明星效应：某网红/爆品/热搜的 key QPS 独占 50%。
- 时序写入：日志按时间分区，"当前小时"分片独扛写入。
- 机器人：某客户端循环刷同一资源。

治理手段（经验做法，按代价从低到高）：

1. **热点 key 加盐**：`key#1..#16` 写入 16 个子分片，读时聚合（适合计数器类可加数据）。
2. **本地缓存/副本读**：热点分片在每个节点放一份只读缓存，挡掉大部分读。
3. **拆分分片**：把热分片一分为二迁到更多节点（范围分区天然支持；哈希分区靠 vnode 上下线实现同效果）。
4. **限流 + 排队**：接受热点存在，用第 10 章的限流器保护分片自身不倒。

**再平衡策略**：节点增减后数据怎么挪？三种思路（DDIA 第 6.5 节）：

| 策略 | 做法 | 问题 |
| --- | --- | --- |
| hash%N 取模 | 节点数变则几乎全量搬 | 已淘汰 |
| 固定槽位 | 预设远多于节点的槽（Redis Cluster 16384 slot），槽在节点间搬 | 槽粒度决定迁移粒度；slot 数固定不可超 |
| 一致性哈希环 | 虚拟节点在物理节点间重新分配 | 分布靠 vnode 数量调 |

公平再平衡的目标：**每个节点负责 ~K/N 且迁移量最小**。Redis Cluster 的做法值得记住：slot 是搬运单位，16384 个 slot 平均分给 N 个主节点，扩容时用 `CLUSTER ADDSLOTS` + 在线 MIGRATE 逐 key 搬，期间该 slot 请求被 ASK 重定向。

## 7. 与缓存集群的衔接

一致性哈希最经典的落地是**分布式缓存**（memcached 集群、Redis Cluster 客户端分片模式）。三个工程要点：

1. **迁移窗口防雪崩**：扩容瞬间被搬走的 key 全部 miss，回源流量可能压垮数据库。经验做法：扩容选低峰、逐 vnode 灰度（搬一段预热一段）、客户端对 miss 加"防击穿单飞"（singleflight，同一 key 并发回源只放一个请求过去）。
2. **客户端路由 vs 代理路由**：客户端内置哈希环（少一跳，但升级客户端才能改拓扑）vs 中间代理（如 Codis/Twemproxy，拓扑对应用透明，多一跳延迟）。
3. **与复制组合**：分片只解决容量，每个分片仍需主从复制保可用（Redis Cluster：16384 slot × 主从）。分片+复制+路由三件套齐了，才是一个完整的分布式存储骨架——第 12 章的四个案例全是这三件套的不同组合。

## 常见误区

1. **"一致性哈希 = 完全均匀"**：裸环（无 vnode）在节点少时倾斜可达 20%+ 极差（实验 2 的 vnodes=1）；均匀性是买虚拟节点与哈希函数质量（md5/xxhash 而非内置 hash()——Python 的 `hash()` 对字符串有随机盐，跨进程不稳定，这是实验代码用 md5 的原因）换来的。
2. **"迁移率 1/N 是精确保证"**：1/N 是期望值；单次扩容实测会围绕它波动（实验输出 25.1%）。且"只迁 1/N"不等于"零成本"——迁移期间路由表切换、双写/双读的过渡协议仍有大量工程细节。
3. **"哈希分区就不能范围查询"**：可以付代价做——广播查询（Map-Reduce 式并行扫所有分片再归并），或用复合 key 设计（日期范围分区+区内哈希）。选择前先看业务查询形状，别被"哈希分区"四个字吓退。
4. **"分区数越多越好"**：每分片有固定开销（元数据、心跳、快照、后台线程）；几千个几乎空的小分片会拖垮协调层与运维。经验做法：单分片承载 1~10 GB / 数万 QPS 量级起步，按增长预留但不过度细分。
5. **"加了 vnode 热点 key 就不怕了"**：vnode 平滑的是**节点间**分布；单个超热 key 还是整片落在同一个分片上。热点 key 必须单独治理（加盐/本地缓存/限流），两者不是一回事。

## 本篇小结

- 分区解决容量与写扩展，与复制正交组合；路由三形态（代理/节点转发/客户端）各有延迟与拓扑灵活性取舍。
- 范围分区利于范围扫描但热点风险高；哈希分区打散热点但范围查询要跨片；复合 key 与加盐是两把常用手术刀。
- 取模扩容迁移 1-1/M 的数据，一致性哈希只迁 K/N；倾斜靠 vnode 大数定律抹平（实测极差从 21% 压到 0.6%）。
- HRW 五行实现、天然均匀、O(N) 路由，小集群好选择；Jump 哈希零内存适合编号桶。
- 热分区与节点倾斜是两个问题：vnode 治后者，加盐/缓存/限流治前者；再平衡首选"固定槽位/一致性哈希"两种最小迁移方案。
- 缓存集群落地三件事：迁移窗口防雪崩、路由位置选择、分片+复制+路由组合成完整骨架。
