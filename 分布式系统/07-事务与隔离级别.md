- 复现三类并发异常（脏读/不可重复读/幻读），配时序图，建立"异常 × 隔离级别"的完整映射。

## 1. ACID 逐项辨析

ACID 是 Härder 与 Reuter 1983 年提出的缩写（*Principles of Transaction-Oriented Database Recovery*, ACM Computing Surveys）。四个字母的实际工程含义远比口号复杂：

- **A（Atomicity，原子性）**："要么全做要么全不做"。实现靠 **undo log / 回滚段**：事务中断时把已做的改动撤销。注意与"隔离性"无关——它是"失败时的行为契约"。另一个常见混淆：ACID 的原子性与"原子操作"（如 CPU 的原子指令，OS 11 篇）不是一回事：前者是"全有或全无的多步组合"，后者是"不可分割的单步"。
- **C（Consistency，一致性）**：最含糊的一个——指"事务把数据库从一个合法状态带到另一个合法状态"（应用层不变量，如"转账前后总额不变"）。**C 主要靠应用保证**，A/I/D 只是提供工具。这也是为什么 CAP 的 C（线性一致）与 ACID 的 C 毫无关系——同名不同物。
- **I（Isolation，隔离性）**：并发事务互不干扰。**它是一个谱系**（第 3 节），从"互相看不见任何中间态"（串行化）到"几乎随便看"（读未提交），成本差一个数量级。SQL 标准定义了四级，见第 2 节。
- **D（Durability，持久性）**：提交了就不能丢。实现靠 **WAL（预写日志）+ fsync**：提交先落日志盘，数据页可以后写（OS 08 篇崩溃一致性的延续）。分布式里 D 变得更微妙——单机落盘成功≠副本已同步（第 04 章半同步的动机）。

```python
# acid_durability.py —— 持久性的最小实验：fsync 的代价与"不 fsync 的丢失窗口"
import os, time

def durability_bench(path="/tmp/wal_demo.log", n=1000):
    # 1) 写但不同步：数据在内核 page cache，机器断电即丢（应用崩溃不丢，因为内核还活着）
    t0 = time.monotonic()
    with open(path, "w") as f:
        for i in range(n):
            f.write(f"tx-{i}\n")
    t_write = time.monotonic() - t0

    # 2) 每条都 fsync：强制落盘，崩溃（连断电）都不丢，但每条付出一次磁盘寻道/刷盘
    t0 = time.monotonic()
    with open(path, "w") as f:
        for i in range(n):
            f.write(f"tx-{i}\n")
            f.flush()
            os.fsync(f.fileno())          # 真正的持久点（D 的实现代价）
    t_fsync = time.monotonic() - t0
    print(f"写{n}条: 无fsync {t_write*1000:.1f} ms | 每条fsync {t_fsync*1000:.1f} ms "
          f"(x{t_fsync/max(t_write,1e-9):.0f})")
    print("结论：D 不是免费的 —— 数据库的 group commit、WAL 都是给 fsync 省钱的设计")

if __name__ == "__main__":
    durability_bench()
```

## 2. SQL 隔离级别与三类异常

并发事务的读写在无隔离时互相踩踏。三个经典异常（时序图里 T1/T2 是并发事务，x 初始 0）：

```
脏读（读到别人未提交的数据）：
 T1: BEGIN; x = x + 10;      （还没提交）
 T2:            read(x) → 10  ← 读到未提交值；若 T1 回滚，T2 基于幻影数据行动
 T1: ROLLBACK;

不可重复读（同一事务两次读同一行，值变了）：
 T1: read(x) → 0;  ...其他事...
 T2:            x = x + 10; COMMIT;
 T1:                              read(x) → 10  ← 同一事务内两次读不一致

幻读（同一事务两次按同一条件查询，行数变了）：
 T1: SELECT COUNT(*) WHERE age>18 → 100
 T2:                 INSERT 一条 age=20 的行; COMMIT;
 T1:                                 SELECT COUNT(*) WHERE age>18 → 101 ← 多出"幽灵行"
```

脏读 vs 不可重复读的区别一句话：前者读到**未提交**的中间态，后者读到**已提交**的新值但破坏了自己事务内的视图一致性。幻读与不可重复读的区别：后者针对**同一行**的值变化，前者针对**满足条件的行集合**变化。

SQL-92 标准定义的四级隔离（完整理论见 Berenson et al., *A Critique of ANSI SQL Isolation Levels*, SIGMOD 1995——这篇论文指出 ANSI 标准定义的漏洞并补充了更多异常）：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现手段 |
| --- | --- | --- | --- | --- |
| 读未提交（RU） | 可能 | 可能 | 可能 | 什么都不做 |
| 读已提交（RC） | 不可能 | 可能 | 可能 | 行锁 / MVCC 每语句快照 |
| 可重复读（RR） | 不可能 | 不可能 | 标准说可能* | MVCC 每事务快照 |
| 串行化（SER） | 不可能 | 不可能 | 不可能 | 2PL / SSI |

*注：标准把 RR 定义为"不许不可重复读"，幻读在 RR 是否被禁止存在数据库实现差异：**PostgreSQL 的 RR（快照隔离）会出幻读（写偏斜异常），MySQL InnoDB 的 RR 用间隙锁（next-key locking）基本挡住了幻读**。面试说"RR 是否有幻阅读实现"比背标准分更准。

## 3. 两阶段锁（2PL）

实现串行化的经典方案：**两阶段锁（Two-Phase Locking）**（起源：Gray et al. 1970 年代 System R；教材定义见任何数据库系统教科书）：

1. **增长阶段**：事务按需获取锁（读锁/写锁），不释放。
2. **收缩阶段**：一旦释放任何锁，就**不能再获取新锁**。

"两阶段"的必要性：若允许"用完即放、用时再取"，两个事务可以交错成"读到对方回滚前的中间态"——收缩阶段禁止新锁，保证了一个事务持有的所有锁存在重叠区间，从而可串行化。

代价与死结：

- **性能**：读读不冲突但读写全冲突，热点行上事务排队，吞吐暴跌。
- **死锁**：T1 锁 A 等 B，T2 锁 B 等 A。数据库靠死锁检测（等待图找环）或超时打破，牺牲一个事务回滚。
- **2PL 是悲观并发控制**：冲突概率高时它反而好（冲突都在锁上排队，没有白干的回滚）；冲突少时 MVCC 更好（读者永不阻塞）。

```python
# two_phase_lock.py —— 用一把锁模拟 2PL 的事务分组，演示"提前放锁"导致的脏序列
import threading, time

class TwoPhaseLockDB:
    def __init__(self):
        self.grow = threading.Lock()   # 简化：用一把事务级锁模拟"增长阶段持锁"
        self.data = {"x": 0}

    def tx_correct(self):
        """正确 2PL：增长阶段拿住锁做完所有事，最后统一释放（收缩=释放点）"""
        with self.grow:                          # 增长阶段
            self.data["x"] += 10
            time.sleep(0.05)                     # 模拟事务内其他工作
            v1 = self.data["x"]                  # 整个事务持锁 → 其他事务看不到中间态
            self.data["x"] += 5
            return v1, self.data["x"]            # 收缩阶段（with 退出统一放锁）

def demo_early_release():
    """反例：提前放锁再取锁（违反两阶段），会让别人读到中间态"""
    db = TwoPhaseLockDB()
    def bad_tx():
        with db.grow:
            db.data["x"] += 10
        # ↑ 在这里提前释放（收缩），又去取新锁 → 违反两阶段
        time.sleep(0.05)      # 这个空窗让 T2 挤进来读
        with db.grow:
            db.data["x"] += 5
    t = threading.Thread(target=bad_tx); t.start()
    time.sleep(0.01)
    print("中间态被读到:", db.data["x"])   # 可能输出 10（未提交的中间值）
    t.join()

if __name__ == "__main__":
    print("正确2PL结果:", TwoPhaseLockDB().tx_correct())
    demo_early_release()
```

## 4. 快照隔离（SI）与可串行化快照隔离（SSI）

**多版本并发控制（MVCC）+ 快照隔离**：每行保留多个版本；事务开始时拍一个快照，**整个事务读这个一致的旧快照**，写依然加锁。效果：

- 读不加锁、不阻塞写；写不阻塞读 → 并发性能远好于 2PL。
- 天然消灭脏读（快照里只有已提交版本）与不可重复读（快照固定）。
- 但引入新异常：**写偏斜（write skew）**——两个事务各写不相关的行，但都依赖对方会改变的前提。经典例：值班系统要求"至少一名医生在线"，T1 看到 Alice 在 → 删除 Bob；T2 同时看到 Bob 在 → 删除 Alice；结果无人值班，但两者无写冲突（写的行不同），快照隔离放行。**这是 SI 不是可串行化的证据**（Fekete et al., *Proving Snapshot Isolation Serializable...* 相关论文序列，以及 Cahill et al. 2008 的 SSI 论文）。

**可串行化快照隔离（SSI）**（Cahill, Röhm, Fekete, *Serializable Isolation for Snapshot Databases*, SIGMOD 2008，PostgreSQL 9.1 起采用）：在 SI 基础上检测两个危险模式，发现就中止其中一个事务：

1. **读写依赖环**：T1 读的行被 T2 修改并提交（T1 的决策依据失效），且形成依赖环。
2. **谓词写偏斜**：T1 的读取影响了 T2 的写入判断且交织成环（用范围锁/SIREAD 锁标记"我读过这个范围"）。

取舍（经验做法）：SSI 冲突检测的误报会多回滚一些事务，适合**冲突率低**的 OLTP 负载；冲突极高（同一行狂竞争）的负载，悲观 2PL 或干脆上队列串行化反而稳。PostgreSQL 的 `SERIALIZABLE` 就是 SSI，用它时应用要准备重试逻辑（错误码 40001）。

## 5. 分布式事务的难点

单机事务靠"一个锁管理器 + 一个日志"闭环。数据一分区（第 06 章），一个事务的读写可能横跨多个分片甚至多种存储，难点全部来自"没有单一闭环"：

1. **原子提交问题**：多个分片要"全提交或全中止"，但协调者自己也可能崩——这就是第 08 章 2PC 要解决的问题（两将军问题的近亲）。
2. **跨节点锁与死锁**：死锁检测需要全局等待图，分区各自检测看不到跨片环。Spanner/Percolator 等用全局时间戳排序 + 等待超时兜底。
3. **隔离级别跨节点语义**：快照要"全局一致"（所有分片同一版本线），需要全局时钟（Spanner TrueTime）或 HLC（CockroachDB），否则分片间快照错位又出跨片异常。
4. **性能悬崖**：跨片事务的延迟 = 最慢分片的延迟；可用性 = 所有参与分片的可用性之积（3 个 99.9% 的分片串一个事务 → 99.7%）。

一句话方向（经验做法）：**能设计成单分片事务就单分片**（分区 key 选得好，80% 事务只碰一个分片，如按 user_id 分区后用户事务天然单片）；跨片事务是奢侈品，用前先想清楚第 08 章的补偿方案。

## 常见误区

1. **"隔离级别越高一定越好"**：隔离级别是性能与正确性的标价交换。把全站默认 RR/SERIALIZABLE 会牺牲一个数量级吞吐；正确姿势是按业务分级——余额/库存串行化或乐观重试，展示类数据 RC 足够（经验做法）。
2. **"MVCC 解决了幻读"**：MVCC 只保证"读快照"的一致性；写-写冲突与写偏斜照样存在。SI 有写偏斜，PostgreSQL RR 下 SELECT 看不到新行但随后写入可能制造依赖环——需要 SSI 才堵上。
3. **"ACID 的 C 与 CAP 的 C 是一回事"**：完全不同。ACID-C 是应用不变量，CAP-C 是线性一致。混淆会直接导致架构评审中说外行话。
4. **"自动提交就是事务"**：`autocommit=1` 下每条语句一个事务，多条语句之间没有隔离保证。需要"多次读保持一致视图"时必须显式开事务（BEGIN/COMMIT），否则 RR/RC 都救不了你。
5. **"死锁了数据库会自动优化掉"**：数据库只会检测并**牺牲**一个事务（回滚报错），你的代码要处理死锁异常并重试。无重试逻辑的死锁处理等于"偶尔随机失败"。

## 本篇小结

- ACID 各有实现支撑：A 靠 undo、I 靠锁/MVCC、D 靠 WAL+fsync，C 靠应用；fsync 是持久性的物理代价。
- 三类异常（脏读/不可重复读/幻读）+ 写偏斜构成"异常清单"，与四级隔离级别一一对应；RR 是否有幻阅读实现（PG 出、MySQL 基本不出）。
- 2PL 串行化但吞吐差、有死锁；MVCC/SI 读性能好但有写偏斜；SSI 在 SI 上加危险结构检测，兼顾大部分正确性与性能。
- 分布式事务 = 原子提交 + 全局隔离 + 性能悬崖三个新难题；首选把事务设计进单分片。
- 异常 × 级别 × 实现的映射表是本章的随身工具，第 08 章把"原子提交"单独拉出来讲。
