# 09 - 消息队列

## 本篇目标

- 说清消息队列的三大价值（解耦/削峰/异步）与它们的代价（一致性与复杂度）。
- 精确定义 at-most-once / at-least-once / exactly-once 三种投递语义，理解"exactly-once 是端到端性质"。
- 掌握重复消费的必然性与幂等设计，写出幂等键消费案例代码。
- 对比 Kafka/RabbitMQ/Redis Stream 的事实性差异，设计死信队列与重试策略（退避+抖动）。

## 1. 为什么需要 MQ：三个价值与一张账单

消息队列（MQ）在"生产者"与"消费者"之间插入一个持久化的中转站，买到三样东西：

1. **解耦**：生产者不需要知道消费者是谁、在不在线。下单服务发一条"订单已创建"，库存/积分/短信各自订阅——加订阅者不用改下单代码。
2. **削峰**：瞬时 10 万 QPS 写入，消费端按自己节奏 2 万 QPS 处理，MQ 的日志当蓄水池。背压（backpressure）由"队列长度"显式表达。
3. **异步**：主流程只做必须同步的事（扣款），慢活（发短信、发券）进队列，接口响应时间从串行求和变成主干耗时。

账单（为什么不是免费午餐）：

- **一致性变弱**：主库提交与下游处理之间有时间差（第 08 章 Outbox 的可见延迟）。
- **排障变难**：一次业务动作散落在生产者/MQ/消费者三处日志，需要消息 ID 串链。
- **MQ 本身成为要运维的分布式系统**：它自己有副本、有分区、有脑裂风险——你是把可靠性外包给了另一个系统。

## 2. 投递语义：三种承诺的真实含义

设一条消息从生产者发出到消费者处理完成，中间任何一环（发送、存储、消费确认）都可能失败重试：

| 语义 | 含义 | 实现方式 | 现实性 |
| --- | --- | --- | --- |
| at-most-once | 至多一次：可能丢，绝不重 | 发完即忘；消费前先 ack | 可靠性最差，适合日志/指标类可丢数据 |
| at-least-once | 至少一次：绝不丢，可能重 | 消费**成功后**再 ack；失败重投 | **主流 MQ 的默认承诺**（Kafka/RabbitMQ/RocketMQ） |
| exactly-once | 恰好一次：不丢不重 | 见下文——单靠 MQ 做不到 | 只能在"端到端"意义上逼近 |

**核心论断：exactly-once 是端到端性质，不是 MQ 单方面能给的**（DDIA 第 11 章《Exactly-once 处理》一节的中心观点；Kafka 的事务与幂等生产者也只覆盖 produce→consume 的特定链路，参见 Kafka KIP-98/KIP-129 文档）。推导：消费者处理消息分两步——"改数据库"与"确认（ack）"，两步无法原子（不同系统）。若先改库后 ack，ack 前崩溃 → 重投 → 处理两次；若先 ack 后改库，ack 后崩溃 → 消息丢失。**无论 MQ 怎么实现，只要"处理"与"确认"是两个系统，重或丢必居其一**。出路：让"处理两次"无害（幂等），或把处理与提交放进同一事务边界（Kafka Streams 的 consume-transform-produce 事务、Flink 的两阶段提交 sink）——即端到端协议，而非 MQ 魔法。

```python
# delivery_semantics.py —— 三种语义在"消费者崩溃"下的行为差异
import asyncio, random

class Broker:
    def __init__(self):
        self.queue = []
        self.inflight = {}            # 已投递未确认（重投候选）

    def produce(self, msg): self.queue.append(msg)

    def fetch(self, cid):
        if self.queue:
            m = self.queue.pop(0)
            self.inflight[cid] = m
            return m
        return None

    def ack(self, cid, ok=True):
        m = self.inflight.pop(cid, None)
        if not ok and m: self.queue.append(m)     # nack → 重投（at-least-once 的根）

async def consumer(broker, mode, processed, cid="c1"):
    """mode: at_most_once / at_least_once / idempotent"""
    while True:
        msg = broker.fetch(cid)
        if msg is None:
            break
        try:
            if mode == "at_most_once":
                broker.ack(cid)                    # 先确认再处理：崩溃则消息丢
                if random.random() < 0.3: raise RuntimeError("处理崩溃")
                processed.append(msg)
            elif mode == "at_least_once":
                processed.append(msg)              # 先处理再确认：崩溃则重投（可能重复）
                if random.random() < 0.3: raise RuntimeError("ack 前崩溃")
                broker.ack(cid)
            else:                                  # 幂等消费：重复处理被去重
                if msg in processed:               # 真实系统用消息ID+去重表，此处简化
                    print(f"  [幂等] {msg} 已处理过，跳过")
                else:
                    processed.append(msg)
                broker.ack(cid)
        except RuntimeError:
            await asyncio.sleep(0.01)              # 重试/重投

async def main():
    random.seed(5)
    for mode in ("at_most_once", "at_least_once", "idempotent"):
        b = Broker()
        for i in range(5): b.produce(f"m{i}")
        processed = []
        await consumer(b, mode, processed)
        print(f"{mode:<14} 处理结果: {processed}")

asyncio.run(main())
```

## 3. 重复消费与幂等设计

既然 at-least-once 必然带来重复（网络超时导致生产者重发、消费者 ack 丢失导致重投），**幂等（idempotency）就是必答题**。常用幂等手段（按数据库能力从弱到强）：

1. **唯一约束兜底**：把业务唯一键（订单号/流水号）建成唯一索引，重复插入直接冲突报错——最后一道防线，任何方案都建议加（经验做法）。
2. **幂等键 + 去重表**：消费前查"已处理消息表"（消息 ID 为主键），用**同一事务**完成"插入去重记录 + 业务处理"；表冲突即视为重复，跳过。
3. **条件更新（乐观幂等）**：`UPDATE account SET balance = balance - 100 WHERE id=1 AND version=7`——version 不匹配说明已处理过，天然幂等且并发安全。
4. **状态机幂等**：操作只允许合法状态迁移（`待支付→已支付`），重复请求落在非法迁移上被拒绝。
5. **Redis SETNX 短期去重**：轻量但不可靠（Redis 与 DB 非原子），只能当第一道过滤，不能当正确性保证。

```python
# idempotent_consumer.py —— 幂等键消费：去重表与业务处理同事务
import sqlite3, asyncio

db = sqlite3.connect(":memory:", check_same_thread=False)
db.execute("CREATE TABLE orders (order_id TEXT PRIMARY KEY, amount INT)")
db.execute("CREATE TABLE inbox_dedup (msg_id TEXT PRIMARY KEY, processed_at REAL)")
db.commit()

async def consume(msg_id: str, order_id: str, amount: int):
    """处理一条'创建订单'消息：去重与业务写入在同一个本地事务（关键！）"""
    cur = db.cursor()
    try:
        cur.execute("BEGIN")
        cur.execute("INSERT INTO inbox_dedup (msg_id, processed_at) VALUES (?, strftime('%s','now'))",
                    (msg_id,))
        cur.execute("INSERT INTO orders (order_id, amount) VALUES (?, ?)", (order_id, amount))
        db.commit()
        return f"{msg_id}: 处理成功"
    except sqlite3.IntegrityError:
        db.rollback()
        # 消息ID冲突 → 该消息处理过（或正被处理）；业务唯一键冲突同理
        return f"{msg_id}: 重复消息，幂等跳过"

async def main():
    # 同一条消息因网络重试被投递 3 次（at-least-once 的日常）
    results = await asyncio.gather(*[consume("msg-1", "ORD-88", 200) for _ in range(3)])
    print("\n".join(results))
    n = db.execute("SELECT COUNT(*) FROM orders").fetchone()[0]
    print(f"订单表行数: {n}（重投 3 次只建 1 单 → 幂等成立）")

asyncio.run(main())
```

注意实现细节：去重插入与业务写入必须**同一事务**——分开写（先记去重再做事，或先做事再记）都会在崩溃点留出"记了没做/做了没记"的窗口，回到 exactly-once 困境。

## 4. Kafka / RabbitMQ / Redis Stream 事实性对比

| 维度 | Kafka | RabbitMQ | Redis Stream |
| --- | --- | --- | --- |
| 模型 | 持久化日志（分区），消费位图偏移 | 队列，消费确认后删除 | 内存日志（可持久化），消费者组 |
| 消息保留 | 按时间/容量保留（消费后仍在） | ack 后即删 | 按 MAXLEN 修剪 |
| 重放历史 | 天然支持（重置 offset） | 不支持（已删） | 支持（按 ID 范围） |
| 吞吐量级 | 单集群百万级 msg/s（顺序写磁盘+零拷贝） | 万~十万级 msg/s | 十万级（受内存与单线程限制） |
| 路由能力 | 弱（按 key 分区，主题为粒度） | 强（exchange 直连/主题/头路由） | 弱（按 stream 分） |
| 延迟 | 毫秒~十毫秒级（批量攒批） | 亚毫秒~毫秒级 | 亚毫秒级 |
| 事务 | produce 幂等 + 事务（跨分区原子写） | publisher confirm + 消费 ack | 无事务（有单命令原子性） |
| 典型场景 | 日志管道、事件溯源、流处理输入 | 复杂路由、任务队列、低延迟 RPC 异步 | 轻量队列、已有 Redis 技术栈 |

事实依据：Kafka 设计文档《Kafka: a Distributed Messaging System for Log Processing》（Kreps et al., NetDB 2011）确立"日志即队列"模型；RabbitMQ 基于 AMQP 0-9-1 规范；Redis Stream 自 Redis 5.0（2018）引入，`XADD/XREADGROUP/XACK`。选型一句话（经验做法）：**重吞吐重回放选 Kafka，重路由重延迟选 RabbitMQ，重简单已有 Redis 选 Stream**。

## 5. 死信队列与重试策略

消费者处理失败怎么办？直接 requeue 会形成毒丸循环（一条坏消息卡死整个分区）。标准做法：

```
主队列 → 消费失败(可重试错误) → 重试队列(带延迟) → N 次后 → 死信队列(DLQ) → 人工/兜底任务
                                    ↑ 延迟用多级队列实现（retry-5s / retry-30s / retry-5m）
```

- **死信队列（DLQ）**：重试耗尽的消息的收容所；DLQ 必须有监控告警，进 DLQ = "系统承认处理不了，需要人介入"。
- **错误分类决定策略**：可重试错误（网络抖动、下游暂时 5xx）走重试；不可重试错误（参数错、业务规则拒绝）**直接进 DLQ**，重试是浪费。
- **重试策略**：指数退避 + 抖动（第 10 章详述，这里先记住结论：`delay = base * 2^attempt + random(0, jitter)`），且**重试次数有限**（3~5 次）。

```python
# retry_dlq.py —— 指数退避 + 抖动的重试，耗尽后进死信队列
import asyncio, random, time

async def process_with_retry(msg, max_attempts=4, base=0.05, jitter=0.02):
    dlq = []
    for attempt in range(1, max_attempts + 1):
        try:
            if msg == "poison" and attempt < 3:      # 毒丸消息：前两次必失败
                raise ConnectionError("下游暂时不可用")
            if msg == "bad-msg":                     # 不可重试错误：直接 DLQ
                raise ValueError("参数非法，重试无意义")
            return f"{msg} ✓(第{attempt}次)"
        except ConnectionError:                       # 可重试 → 退避+抖动
            delay = base * (2 ** (attempt - 1)) + random.uniform(0, jitter)
            print(f"  {msg}: 第{attempt}次失败，{delay*1000:.0f}ms 后重试")
            await asyncio.sleep(delay)
        except ValueError:                            # 不可重试 → 立即死信
            dlq.append((msg, "non-retryable"))
            return f"{msg} → 直接进 DLQ（业务错误）"
    dlq.append((msg, "retries-exhausted"))
    print(f"  {msg}: 重试耗尽 → 死信队列")
    return f"{msg} → DLQ"

async def main():
    random.seed(0)
    for m in ("good-msg", "flaky-msg", "poison", "bad-msg"):
        print(await process_with_retry(m))

asyncio.run(main())
```

## 常见误区

1. **"Kafka 开了事务就是 exactly-once"**：Kafka 事务覆盖的是"consume-process-produce"闭环且消费端要配 `read_committed`；你的处理里若还写了外部数据库，那一步不在事务里——外部副作用依然要幂等。别把产品营销词当成系统性质。
2. **"消息不会丢"**：任何 MQ 在"生产者不等确认""broker 未刷盘""消费者先 ack 后处理"三种配置下都会丢。可靠性是配置与协议的结果：生产端 acks=all/confirm、broker 刷盘策略、消费端手动 ack，三处都要对。
3. **"重试越多越可靠"**：无退避的密集重试会把刚恢复的下游再次打垮（重试风暴，第 10 章）；重试要**有限次数 + 退避抖动 + 区分错误类型**。毒丸消息进 DLQ 是正确行为，不是失败。
4. **"队列堆积是 MQ 的问题"**：堆积是消费能力的账单，MQ 只是显式化了它。治理手段是扩消费者（注意分区数限制并行度上限——Kafka 消费者数 ≤ 分区数）、优化处理耗时、或降级非关键消费。
5. **"消息顺序无关紧要"**：跨分区的消息无全局顺序；同 key 消息才保序（Kafka 按 key 哈希到分区）。"先创建后更新同一实体"的业务必须用同一 key，否则乱序处理会以旧覆新（配合版本号防御）。

## 本篇小结

- MQ 买来解耦/削峰/异步，付出一致性延迟、排障链路、额外一个分布式系统的运维账单。
- at-least-once 是主流默认；exactly-once 只能端到端达成——"处理与确认跨系统"这个结构决定了必须幂等。
- 幂等五件套：唯一约束兜底、去重表同事务、条件更新、状态机、（不可靠的）Redis 去重；核心纪律是**去重记录与业务写入同事务**。
- Kafka=日志+重放+高吞吐，RabbitMQ=路由+低延迟，Redis Stream=轻量即用；按吞吐/路由/栈现状选，不按潮流选。
- 重试必须分类：可重试错误走退避+抖动+有限次数，不可重试直接 DLQ；DLQ 要有告警与人工兜底流程。
