# 07 - 集成测试与外部依赖：边界层又稳又快

## 本篇目标

1. 会判断一条测试属于单元还是集成，并据此选择替身策略；
2. 掌握数据库测试三种隔离法：事务回滚、独立 schema、内存库（及内存库与真库的差异清单）；
3. 会用 respx/responses 打桩 HTTP 依赖，理解"contract 测试"补齐打桩的信任缺口；
4. 建立稳定性问题清单：sleep、端口冲突、时区、代理——每个有解法。

## 1. 单元 vs 集成：边界判断

上三章默认"依赖都替身化了"——那是单元测试。**集成测试**回答另一类问题：*各部分拼起来，真实边界真的对得上吗？*（01 篇 Testing Trophy 里它当主力的原因。）

判断一条测试属于哪层，看两个问题：

1. **有没有真实 I/O？**（真数据库、真 HTTP 栈、真文件系统、真子进程）——有，就是集成；
2. **有没有跨模块的真实协作？**（不是 mock 出来的协作）——有，也归集成。

由此得出替身策略表：

| 依赖 | 单元层 | 集成层 |
| --- | --- | --- |
| 数据库 | Fake 仓库（04 篇） | 事务回滚 / 独立 schema（本章 2 节） |
| HTTP API | respx/responses 打桩 | 本地假服务端 / contract 测试（本章 3 节） |
| 文件系统 | tmp_path 注入 | tmp_path（本身就是真实 FS，算轻量集成） |
| 时间 | fake clock / freezegun | 真时钟（避免测时间本身） |
| 子进程 | mock `subprocess.run` | 真跑短命令（`echo`/`python -c`） |

**经验做法**：单元层的集成替身（Fake/打桩）负责"逻辑分支全覆盖"，集成层只负责"真契约验证"——每类外部依赖通常只需要 5~20 条集成用例，多了说明业务逻辑漏到了边界层。

## 2. 数据库测试：三种隔离法

数据测试的核心矛盾：**既要真库的语义，又要测试间的完全隔离**。三种隔离法按优先级：

**方法一：事务回滚（首选）。** 每个测试在事务里跑，结束回滚——快（无建库开销）、绝对干净（失败也回滚）：

```python
# conftest.py
import sqlite3, pytest

@pytest.fixture
def db():
    """事务回滚型 fixture：每个测试拿到干净库，失败也不留痕。"""
    conn = sqlite3.connect(":memory:", isolation_level=None)
    conn.execute("BEGIN")
    conn.execute("CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT UNIQUE)")
    yield conn
    conn.rollback()
    conn.close()
```

```python
# test_db.py
def test_insert(db):
    db.execute("INSERT INTO users (name) VALUES ('alice')")
    assert db.execute("SELECT count(*) FROM users").fetchone()[0] == 1

def test_unique_violation(db):
    db.execute("INSERT INTO users (name) VALUES ('alice')")
    import pytest, sqlite3
    with pytest.raises(sqlite3.IntegrityError):
        db.execute("INSERT INTO users (name) VALUES ('alice')")
    assert db.execute("SELECT count(*) FROM users").fetchone()[0] == 1  # 上个测试没泄漏
```

对 PostgreSQL/MySQL 同构：`BEGIN` → 测试 → `ROLLBACK`；被测代码自己 `COMMIT` 时改用"每测试独立 schema/库"（方法二）。注意 fixture 里的 `isolation_level=None` 让 Python 驱动交出自动事务管理——否则驱动的隐式 commit 会让回滚失效，这是事务回滚法最常见的翻车点。

**方法二：每测试独立 schema。** 重但彻底：session 级 fixture 持连接池，function 级 fixture `CREATE SCHEMA test_$UUID` + 跑迁移，teardown `DROP SCHEMA`。适合"被测代码必须 commit"或要验证迁移脚本本身的场景：

```python
# 独立 schema 型 fixture（PostgreSQL 方言，骨架）
import uuid

@pytest.fixture
def pg_schema(pg_pool):                       # pg_pool: session 级连接池
    name = f"t_{uuid.uuid4().hex[:10]}"       # ⭐ 名字随机化，并行也不撞
    with pg_pool.connection() as conn:
        conn.execute(f'CREATE SCHEMA "{name}"')
        conn.execute(f'SET search_path TO "{name}"')
        run_migrations(conn)                  # 每个测试一张全新表结构
        yield conn
        conn.execute(f'DROP SCHEMA "{name}" CASCADE')   # teardown 兜底清理
```

代价是每个测试多付一次迁移时间（几十毫秒到秒级），所以它通常只挂在 `-m integration` 层（02 篇的标记选择 + 08 篇分层策略）。

**方法三：内存 SQLite（sqlite:///:memory:）。** 最快，但**与真库有真实语义差异**——实测两条：

```python
# 差异一（实测）：SQLite 对列类型宽容，字符串能进 INTEGER 列
conn.execute("CREATE TABLE t (n INTEGER)")
conn.execute("INSERT INTO t VALUES ('abc')")     # 不报错！
# 查询结果: ('abc', 'text')   # PostgreSQL 会直接 raise
```

差异清单（写库测试前过一遍）：类型强制度（上例）、并发写锁行为（文件库才有，`:memory:` 没有）、方言函数（`GROUP_CONCAT`/`ON CONFLICT` 细节/`RETURNING` 支持度）、事务隔离级别。**经验做法**：用内存 SQLite 测"业务 SQL 逻辑"，但**每类查询至少一条用例在真库跑**（testcontainers 或 CI 服务容器，见 4 节）——两层的分工是"逻辑"与"方言"。

## 3. HTTP 依赖：打桩与 contract 测试

**打桩（单元/集成层皆宜）。** httpx 生态用 respx（requests 用 responses），语法同构：

```python
# test_http.py
import httpx, pytest, respx

def fetch_base(url: str) -> str:
    r = httpx.get(url)
    r.raise_for_status()
    return r.json()["base"]

@respx.mock(base_url="https://api.example.com")
def test_fetch_base(respx_mock):
    respx_mock.get("/v1/base").respond(json={"base": "CNY"}, status_code=200)
    assert fetch_base("https://api.example.com/v1/base") == "CNY"
    assert respx_mock.calls.call_count == 1     # 请求确实发出且只发一次

@respx.mock(base_url="https://api.example.com")
def test_fetch_500_raises(respx_mock):
    respx_mock.get("/v1/base").respond(status_code=500)
    with pytest.raises(httpx.HTTPStatusError):
        fetch_base("https://api.example.com/v1/base")
```

打桩能测全状态机（200/404/429/超时），但**它验证不了"对方真长这样"**——桩里的 JSON 形状是你抄的文档，接口一改，桩照常绿。这就是**contract 测试**要补的缺口：让桩与真服务端共享同一段"契约"（OpenAPI schema、或你定义的请求/响应快照），CI 里用真服务端（或其官方 sandbox）跑一遍契约用例，两边谁违约谁红。

轻量形态：**本地假服务端**——pytest fixture 里起一个真实 HTTP server（`http.server`/`uvicorn`），业务代码发真 HTTP 请求，但打到 127.0.0.1。它比打桩多覆盖一层真实协议栈（编码、header、重定向），比打真外网稳定得多：

```python
# tests/integration/conftest.py —— 本地假服务端 fixture（实测通过）
import http.server, json, threading
import pytest

@pytest.fixture
def fake_api():
    class H(http.server.BaseHTTPRequestHandler):
        def do_GET(self):
            body = json.dumps({"path": self.path}).encode()
            self.send_response(200)
            self.send_header("Content-Type", "application/json")
            self.end_headers()
            self.wfile.write(body)
        def log_message(self, *a): pass         # 静默访问日志
    srv = http.server.ThreadingHTTPServer(("127.0.0.1", 0), H)  # 端口 0 随机分配
    threading.Thread(target=srv.serve_forever, daemon=True).start()
    yield f"http://127.0.0.1:{srv.server_address[1]}"
    srv.shutdown()                              # teardown：进程内关闭，不占端口

def test_fetch_base_via_real_stack(fake_api):
    import httpx
    assert httpx.get(fake_api + "/v1/base").json()["path"] == "/v1/base"
```

注意 fixture 里三件小事都做对了：端口交给内核分配（第 6 节清单二）、线程设 daemon、`shutdown()` 保证重复运行不积累监听 socket——集成 fixture 的"干净退出"与"干净进入"同样重要。

## 4. testcontainers 思想概览

"真库语义"与"环境干净"可以兼得：**testcontainers**（Python 包 `testcontainers`，思想同源 Java 生态）在测试会话里**编程式拉起一次性的 Docker 容器**（PostgreSQL、Redis、Kafka……），跑完销毁：

```python
# 思想示意（真实 API 以 testcontainers 文档为准）
from testcontainers.postgres import PostgresContainer

@pytest.fixture(scope="session")
def pg():
    with PostgresContainer("postgres:16") as p:
        yield p.get_connection_url()   # 随机端口的真实 Postgres
```

三个关键词：**session 级**（容器启动秒级~十秒级，不要 function 级）、**随机端口**（容器自己分配，杜绝冲突）、**一次性**（每次 CI 任务全新实例，无状态污染）。成本是 CI 必须有 Docker；没有 Docker 的环境退化路径：CI 服务容器（GitHub Actions `services:` 字段，08 篇 yaml 里给全）或内存库+真库抽样。

## 5. 文件系统与子进程：真实边界，最小暴露

**文件系统**：文件操作是真行为（编码、权限、换行符），用**真实文件系统 + tmp_path**（03 篇），不用 mock `open`——mock 文件的测试等于宣布"我不测编码问题"。子目录资源随测试自动清理，Windows/WSL 差异也顺手覆盖（换行符 `\r\n` 是经典翻车点，`Path.write_text` 的 `newline` 参数要显式）。

**子进程**：真跑可以，但三件事必须做——用 `sys.executable`（CI 上没有 `python` 别名）、超时必填（`subprocess.run(..., timeout=30)`，防挂死拖死整条流水线）、输出用 `capture_output=True` 断言而非人眼。命令本身做成参数注入，测试里替换成无害命令（`echo`/`python -c 'print(1)'`），只有一两条"真命令"用例留给 CI。

## 6. 稳定性问题清单：每个配解法

集成测试 flaky 的四大来源，逐条给解法（本系列写作过程中实际撞上的一条也在列）：

1. **sleep 等待**。`time.sleep(2)` 等"慢的东西"：CI 机器慢时 2 秒不够就 flaky，改成轮询——`for _ in range(50): if 条件: break; time.sleep(0.1)`，或更优：把"等"改成"事件"（fakes 事件、队列 `get(timeout=)`、asyncio 的 `Event`）。原则：**测结果，不测时机**；
2. **端口冲突**。写死 8000/8080 在并行 CI 上必撞。解法：`bind(("127.0.0.1", 0))` 让内核随机分配（实测一次拿到 56595），再从 `getsockname()[1]` 读回真端口传给被测代码——"端口可注入"因此成为被测代码的隐性要求；
3. **环境泄漏**。实测案例：本系列写作时跑 httpx 测试，shell 里的 `ALL_PROXY` 让 respx 全绿用例直接 `ImportError: Using SOCKS proxy`。代理变量（`HTTP(S)_PROXY`/`ALL_PROXY`）、语言区（`LANG`）、时区（`TZ`）都会改变行为。解法：测试进程统一 `monkeypatch.delenv`（或 CI 步骤 `env -i`/显式覆盖）+ 关键测试显式 `monkeypatch.setenv("TZ", "UTC")`；时区相关断言一律用 aware datetime；
4. **外部状态残留**。测试写了固定路径（`/tmp/shared.json`）或固定 docker 容器名。解法：一切"名字"经 tmp_path/UUID 生成，CI 每任务全新环境；同名容器的 stale 残留用 session 级 teardown 兜底清理。

**经验做法**：任何"本地稳、CI 挂"或"单跑绿、全量红"的测试，先查清单四条再查代码——九成命中其中之一。

## 常见误区

**误区一：全量用内存 SQLite 却以为测了数据库。** 方言差异（类型/锁/函数）一条都没被覆盖。分层补真库用例，或接受"数据库层风险另账管理"并写进 README。

**误区二：打桩即集成测试。** respx 全绿 ≠ 对接没问题，它只证明"你的代码按你理解的契约工作"。契约测试/真服务端抽样必须存在。

**误区三：共享数据库实例但不做隔离。** 测试间靠"执行顺序"维持数据成立（A 建的数据 B 用），并行跑立刻散架。隔离三法选一个，别选第四种"小心点"。

**误区四：容器当轻量资源。** function 级拉容器把套件拖到十分钟级。session 级 + 随机端口 + 数据事务隔离的组合才是正解。

**误区五：为稳定性加 try/except 吞断言。** flaky 的正确处理是**根因修复**（本节清单）或显式隔离（08 篇的 quarantine 机制），吞掉的断言等于删掉的测试。

## 本篇小结

- 单元/集成的判定看真实 I/O 与真实协作；替身策略按"单元测逻辑分支、集成测真契约"分工，集成用例贵精不贵多；
- 数据库隔离三法：事务回滚（首选，注意驱动隐式 commit）、独立 schema（必须 commit 时）、内存 SQLite（测逻辑不测方言，类型宽容度是实测坑）；
- HTTP 打桩（respx/responses）覆盖状态机，contract 测试/本地假服务端补"对方真长这样"的验证；
- testcontainers = session 级一次性容器 + 随机端口，CI 无 Docker 时退化到 services 容器；
- 文件与子进程用真实资源但最小暴露：tmp_path、`sys.executable`、超时必填；
- 稳定性四清单：sleep→轮询/事件、端口→内核分配、环境泄漏→显式 env 控制、状态残留→UUID 化——flaky 先查清单。

## 练习

1. 把事务回滚 fixture 从 `:memory:` 改成临时文件库（tmp_path），并解释为什么两个测试之间依然互不可见；故意去掉 `isolation_level=None` 复现"回滚失效"，记录现象。
2. 为 `fetch_base` 补三条 respx 用例：429（带 `Retry-After` header）、超时（`respx_mock.route(...).mock(side_effect=httpx.ConnectTimeout)`）、响应体缺 `base` 字段。
3. 写一个"本地假服务端"fixture（`http.server` 起 127.0.0.1:0），让 `fetch_base` 走真 HTTP 栈通过，并说明它比 respx 多验证了什么。
4. 给一个你自己的库写 testcontainers 版 session fixture（或退化版：CI `services:` 里的真 Postgres），跑通"迁移脚本幂等"用例。
5. 制造一个 flaky 测试（固定端口 + sleep），按第 6 节清单逐条修复，写出修复前后各连续运行 10 次的结果对比。
