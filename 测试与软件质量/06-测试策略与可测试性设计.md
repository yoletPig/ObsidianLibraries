# 06 - 测试策略与可测试性设计：改代码之前先改"可测性"

## 本篇目标

1. 认识三种不可测代码的病灶（隐藏依赖/静态调用/God 对象），理解 Feathers 的 seam 概念；
2. 会用最简依赖注入（构造函数注入）与端口-适配器，让测试从"设计要求"变成"设计副产品"；
3. 掌握遗留代码加测试的套路：characterization 测试先行，再重构；
4. 学会 Builder/Object Mother 两种测试数据构造法，并对"测试代码要不要 DRY"建立立场。

## 1. 不好测的代码长什么样

测试写不动，九成不是测试的问题，是代码的问题。三种病灶：

**病灶一：隐藏依赖——依赖在函数体内自建。**

```python
# before.py：症状现场
import sqlite3, smtplib

def send_welcome(user_id: int) -> bool:
    conn = sqlite3.connect("prod.db")           # ❌ 每次自建连接
    row = conn.execute("SELECT email FROM users WHERE id=?", (user_id,)).fetchone()
    s = smtplib.SMTP("smtp.corp.internal")      # ❌ 硬编码内网 SMTP
    s.sendmail("noreply@corp", row[0], "welcome!")
    s.quit()
    return True
```

想测它就必须连真库、真 SMTP。Michael Feathers 在《Working Effectively with Legacy Code》（2004）把这类问题统一到一个概念下——**接缝（seam）**：*程序中一个可以改变行为、而无需在现场编辑代码的点*。`sqlite3.connect(...)` 这个调用点没有任何 seam（改它就得编辑函数）；而如果连接从外面传进来，参数列表就是一条天然的 **object seam**（利用多态在调用点替换实现）。

**病灶二：静态调用/模块级副作用。** `from config import SETTINGS` 后直接 `SETTINGS.timeout`——import 期就固化了值；`utils.now()` 这类模块函数在模块命名空间里被"死绑"。它们都是 Feathers 说的** link seam 缺失**形态：没有可以替换的间接层。（04 篇 patch 现场四的"值拷贝"就是它的测试侧症状。）

**病灶三：God 对象。** 一个类管配置、管数据库、管业务、管输出——测试它的任何方法都要先"拖起整个世界"。判定标准很朴素：**构造这个对象需要几个真实依赖？** 答案大于 3，测试就写不动了。God 对象的修法不是"学更多 mock 技巧"，而是拆职责——把"读配置的"和"用配置的"分开。

## 2. 依赖注入的最简形式：构造函数注入

不必上框架。Python 里依赖注入的最简形式就是把依赖放进构造函数签名：

```python
# after.py：seam 提取后的形态
from typing import Protocol

class Mailer(Protocol):
    def send(self, to: str, body: str) -> None: ...

class UserSource(Protocol):
    def email_of(self, user_id: int) -> str: ...

class WelcomeService:
    def __init__(self, users: UserSource, mailer: Mailer):
        self._users, self._mailer = users, mailer    # 依赖从外面进来

    def send_welcome(self, user_id: int) -> bool:
        self._mailer.send(self._users.email_of(user_id), "welcome!")
        return True
```

三个要点：① `Protocol`（结构化类型）做接口——Python 不需要显式继承，Fake 天然满足 Protocol，静态检查器还帮你把关（09 篇的类型检查由此顺带测了"Fake 是否守约"）；② 默认值兜底的写法（`def __init__(self, users=None): users = users or DbUserSource()`）对**渐进改造**友好，但会把产品路径和测试路径混在一起，团队大了以后推荐"组合根"集中装配（main 里 new 真实现，测试里 new Fake）；③ 03 篇的 fixture 组合与这里是同一件事的两面：产品代码的依赖注入让测试 fixture 有地方插手。

改造后的测试（实测通过）：

```python
def test_welcome_sent_to_user_email():
    users, mailer = FakeUsers({7: "a@corp"}), FakeMailer()
    assert WelcomeService(users, mailer).send_welcome(7) is True
    assert mailer.sent == [("a@corp", "welcome!")]
```

## 3. 端口-适配器：测试的第二份收益

上节的 `Mailer`/`UserSource` 就是端口（Port，你定义的接口），`SmtpMailer`/`FakeMailer` 是适配器（Adapter，各实现一个）。Hexagonal Architecture（Alistair Cockburn，2005 提出）的本意是隔离领域与外部系统，**从测试视角看它给了三份具体收益**：

1. **切替真假实现**：同一份业务测试，插 `FakeMailer` 跑单元层（毫秒级），插 `SmtpMailer + respx` 跑集成层（07 篇）——04 篇的 Fake 仓库靠这个结构落地；
2. **接口即契约文档**：新同事读 `Mailer` 三行 Protocol 就知道边界在哪，不用读 SMTP 细节；
3. **架构演化有轨道**：换邮件服务商 = 写一个新适配器，业务测试一行不改——测试在替你验证"换皮没伤芯"。

**经验做法**：端口的粒度按"业务语言"切（`send_welcome`、`charge`），不按技术名词切（`execute_sql`、`http_post`）——前者让 Fake 表达业务行为，后者只是把 HTTP mock 换了个地方。

## 4. 遗留代码加测试：characterization 先行

给无测试的老代码动手前，第一件事不是重构，是 Feathers 的两步套路：

**第一步：characterization 测试（特征测试/刻画测试）——把现状钉死，哪怕现状看起来是错的。** 目的不是判断对错，是**锁定行为**，保证重构不改变它：

```python
# legacy.py：折扣规则已经没人说得清，先别猜，先钉死
def apply_discount(price: float, vip: bool) -> float:
    d = 0.0
    if price > 100: d += 0.1
    if vip: d += 0.2
    if price > 100 and vip: d += 0.05
    return round(price * (1 - d), 2)
```

用真实输出写测试（边界值成对出现：`100` 与 `100.01`）：

```python
# test_characterization.py —— 值全部来自当前实现的实测输出
import pytest
from legacy import apply_discount

@pytest.mark.parametrize("price, vip, want", [
    (50.0, False, 50.0),
    (150.0, False, 135.0),
    (80.0, True, 64.0),
    (150.0, True, 97.5),      # 注意：折扣叠加 = 1-(0.1+0.2+0.05) = 0.65
    (100.0, True, 80.0),      # 边界：100 不触发 price>100
    (100.01, True, 65.01),    # 边界：刚过线
])
def test_current_behavior(price, vip, want):
    assert apply_discount(price, vip) == want
```

写 characterization 测试的省力技巧（Feathers 书中同款思路）：不确定行为的分支，先跑一遍拿到真值再填表——测试内容是"现状快照"，不是"你的期望"。所以它红的时候，说明**你改了行为**，而不是"测试写错"。

**第二步：在这个安全网下重构。** 把隐晦的三段折扣条件改成显式规则表：

```python
# refactored.py
def apply_discount(price: float, vip: bool) -> float:
    rate = 1.0
    if price > 100:
        rate -= 0.10
    if vip:
        rate -= 0.20
    if price > 100 and vip:
        rate -= 0.05          # ⚠️ characterization 测试已锁定：叠加规则保持原样
    return round(price * rate, 2)

# 产品需求方看到规则表后确认"叠加"本意是 0.35 封顶——那是下一次变更，
# 先改测试（新期望）再改代码，永远不裸奔。
```

对 `test_characterization.py` 跑一遍，全绿，重构完成。**顺序纪律**：characterization → 重构（测试不动）→ 确认绿 → 若要"改行为"，先改测试再改代码。跳过第一步的重构，等于蒙眼拆弹。

## 5. 测试数据构造：Object Mother 与 Builder

测试一多，`User("alice", 30, False, "a@corp", None, [])` 这种位置参数地雷遍地开花——读测试的人根本不知道第 3 个 False 是什么。两种解法：

**Object Mother**（Meszaros《xUnit Test Patterns》命名）：一个对象工厂，提供**预制的具名对象**：

```python
# tests/factories.py
def make_admin_user() -> User:
    return User(name="admin-alice", age=35, admin=True, email="a@corp")

def make_minor_user() -> User:
    return User(name="bob", age=17, admin=False)
```

优点是意图清晰（`make_minor_user()` 自解释）；缺点是**参数组合爆炸**——"17 岁的 admin"怎么办？再加一个 `make_minor_admin_user()` 就开始失控。

**Builder**：默认值齐全 + 链式覆盖，测试只写差异：

```python
# tests/builders.py
class UserBuilder:
    """默认值齐全的构造器：测试只写差异。"""
    def __init__(self):
        self._u = User(name="alice", age=30, admin=False, email="a@corp")
    def named(self, name): self._u.name = name; return self
    def aged(self, age): self._u.age = age; return self
    def as_admin(self): self._u.admin = True; return self
    def build(self) -> User: return self._u

def test_minor_cannot_buy():
    assert not UserBuilder().aged(17).build().admin

def test_admin_can_delete():
    assert UserBuilder().as_admin().build().admin
```

**经验做法**：简单场景 Object Mother 够用；一旦出现"要微调 Mother 产物的第二个字段"，立刻升级 Builder；两者可以合体（Mother 内部用 Builder：`make_admin_user = lambda: UserBuilder().as_admin().build()`）。03 篇的工厂 fixture 是同一思想在 fixture 侧的形态，习惯上把 Builder 挂进 fixture：`def make_user(): return UserBuilder().build()`。

## 6. 测试代码的质量：DRY 到什么程度

测试代码也是代码，但**DRY 的度量衡不同**。产品代码里重复是坏味道；测试代码里，**可读性优先级高于去重**——Sandi Metz 的名言在这里完全适用："duplication is far cheaper than the wrong abstraction"（错误的抽象比重复昂贵得多）。测试代码里的"错误抽象"长这样：

```python
# ❌ 过度 DRY：断言被抽象进了循环 + 数据表 + 隐式约定
CASES = [(t_input, t_expect, t_setup), ...]
def test_all():
    for inp, exp, setup in CASES:
        result = run_pipeline(inp, setup)
        assert normalize(result) == normalize(exp)
```

一个用例失败，你得同时读懂循环、normalize 的语义、setup 的隐式约定——测试的"自解释"（01 篇 FIRST）荡然无存。**经验做法**的三条线：

1. **setup/teardown 层大胆 DRY**（fixture/Builder 就是干这个的）——它们重复的是机械劳动；
2. **断言与业务步骤适度重复**：每个测试函数肉眼可读，从上到下就是一段行为描述，不为省三行代码抽 helper；
3. 抽象的唯一正当理由：**同一个知识出现在 ≥3 个测试且语义完全一致**（比如"合法配置的标准样例"），抽成具名常量/函数，并给足文档字符串。

Feathers 在《Working Effectively with Legacy Code》里的相关提醒同样适用于测试代码：修改测试的结构时，先有测试保护（哪怕是最基本的 smoke 级），再动手。

## 常见误区

**误区一：为了"可测试"把所有私有方法都提为公开。** 可测试性改造的对象是**依赖的方向**（外部的依赖进来），不是访问修饰符。测试经公开接口+Fake 依赖进行，私有细节留给重构自由。

**误区二：DI 框架先于需要。** Python 项目里手写构造函数注入 + 组合根覆盖 95% 场景；上依赖注入容器之前，先确认不是 God 对象问题。

**误区三：characterization 测试永久化。** 它是脚手架：重构完成后，把"现状快照"逐步改写为"业务期望"（或确认现状即期望后改名归档）。永久留一堆"锁死怪行为"的测试，会把坏行为升格为规格。

**误区四：Builder 万能。** 只有两个字段、无可选差异的值对象，直接字面量更清楚；Builder 的价值随字段数与组合需求增长，小对象别过度设计。

**误区五：测试代码不 review。** 测试是团队资产，同样会腐烂：魔法数、复制粘贴的 setup、失效后无人认领的 skip——测试代码进同一个 code review 流程（08 篇的门禁清单里加一条）。

## 本篇小结

- 三种不可测病灶：函数体内自建依赖（隐藏依赖）、导入期绑定的静态值（静态调用）、构造即拖起全世界（God 对象）；
- seam（Feathers）：能在不编辑现场的前提下改变行为的点；构造函数注入是最简 object seam，Protocol 定义端口；
- 端口-适配器的测试收益：真假实现可切替、接口即契约、换适配器不伤业务测试；
- 遗留代码两步走：characterization 测试锁死现状（值来自实测）→ 安全网下重构；改行为时先改测试；
- 数据构造：Object Mother 管具名预制，Builder 管增量差异，两者可合体挂进 fixture；
- 测试代码的 DRY 边界：setup 层大胆去重，断言层宁可重复，Metz 的"错误抽象比重复贵"是准绳。
