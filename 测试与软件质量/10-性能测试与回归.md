# 10 - 性能测试与回归：慢也是 bug

## 本篇目标

1. 建立"性能回归也是缺陷"的意识，理解基准测试为什么必须讲纪律；
2. 掌握 timeit 的正确用法，能解释"测出来忽高忽低"的全部常见原因；
3. 会用 pytest-benchmark 把性能基线挂进测试套件，防止优化成果被回退；
4. 认识微基准的陷阱（死代码消除/常量折叠/分支预测）与内存回归（tracemalloc），并知道 C++ 侧的 Google Benchmark 怎么用。

## 1. 功能对了但慢了也是 bug

"性能回归算不算 bug"在工程上不需要讨论——用户用脚投票：接口从 80ms 涨到 800ms，就是线上事故。性能问题的特殊之处只在于**它悄悄发生**：每一次看似无害的重构、每一次"顺手加个日志"、每一版依赖升级，都可能让热点路径慢 10%。功能测试对此全绿——因为断言里没有时间。

所以性能测试的目标从来不是"测一次有多快"，而是**把速度变成受版本管理守护的属性**：有一个基线，有一个能对比基线的机制，有一个人人看得到的回归警报。本章 3 节的 pytest-benchmark 就是这三件事的最小实现。

**先分清两类测量**：剖析（profiling，回答"慢在哪"，Python 语言精通 13 篇的 cProfile/line_profiler 是主角）与基准（benchmarking，回答"有多慢/变快变慢了"，本章主角）。两件事互相成就：先剖析找到热点，优化后用基准守住战果。

## 2. 基准测试纪律：为什么测出来忽高忽低

先看一个"不讲纪律"的现场（实测）：

```python
import timeit

code = "sum(range(1000))"
for n in (1, 10, 1000):
    ts = timeit.repeat(stmt=code, number=n, repeat=5)
    per_call = [t / n * 1e6 for t in ts]          # 换算成微秒/次
    print(f"number={n:>5}: 单次 {min(per_call):7.2f} ~ {max(per_call):7.2f} µs，"
          f"波动 {100*(max(per_call)-min(per_call))/min(per_call):5.1f}%")
```

```
number=    1: 单次    5.00 ~    6.70 µs，波动  34.0%
number=   10: 单次    5.05 ~    5.14 µs，波动   1.8%
number= 1000: 单次    5.01 ~    5.16 µs，波动   2.9%
```

同样一段代码，`number=1` 时波动 34%，`number=10` 就收敛到 2% 以内——**测量的固定开销（计时器精度、解释器调度）被摊薄了**。这就是 timeit 官方文档强调 `number` 要够大的原因：让被测代码的耗时远大于测量噪声。`timeit.repeat` 取 **min** 作报告值（而不是平均）也是同理：min 最接近"机器无干扰时的真实能力"，均值会被各种干扰拉高。

忽高忽低的完整原因清单（排查基准不稳定的第一个表）：

| 噪声源 | 机理 | 对策 |
| --- | --- | --- |
| CPU 频率调节 | 省电模式降频、睿频未热身 | 预热跑若干轮再测；笔记本插电、关闭省电 |
| 其他进程 | 后台编译/杀毒/浏览器抢核 | 关后台；CI 用独占 runner |
| 缓存冷热 | 冷缓存首轮偏慢 | 多轮 repeat，取 min |
| GC | 分配多时触发回收抖动 | `gc.disable()` 包住计时区（timeit 默认已关） |
| 数据太贴近 | 常量折叠/过小输入 | 见第 4 节；输入要"真实规模" |
| WSL2 特有 | 宿主机调度、时钟漂移 | 加大 repeat 次数；重要结论换原生 Linux 复测 |

**纪律总结**（timeit 原则）：预热 → 多次 repeat → 每次跑够 `number` → 报告 min → 同机同环境对比。基准的价值在**对比**，一切换环境的绝对数字都不可比。

## 3. pytest-benchmark：把基线挂进测试套件

pytest-benchmark 让"性能用例"长得和普通测试一样，产出实测报告：

```python
# bench_demo.py
def sum_squares(n: int) -> int:
    return sum(i * i for i in range(n))
```

```python
# test_bench.py
from bench_demo import sum_squares

def test_sum_squares_1000(benchmark):
    result = benchmark(sum_squares, 1000)   # 被测函数经 fixture 包装执行
    assert result == 332833500              # 功能断言照常写
```

```
$ pytest test_bench.py
--------------------------------------------------- benchmark: 1 tests ---------------------------------------------------
Name (time in us)             Min       Max     Mean  StdDev   Median     IQR   Outliers  OPS (Kops/s)  Rounds  Iterations
--------------------------------------------------------------------------------------------------------------------------
test_sum_squares_1000     24.8998  320.7996  28.2835  6.5302  26.4999  0.5998  2317;5320       35.3563   34483           1
--------------------------------------------------------------------------------------------------------------------------
```

它自动完成纪律清单：预热、自适应轮数（Rounds 34483）、统计与离群点标注。**防回退的两步**：

1. **存基线**：`pytest --benchmark-autosave`（结果进 `.benchmarks/`，随仓库管理或只存 CI 机器）；
2. **对比门禁**：`pytest --benchmark-compare=0001 --benchmark-compare-fail=min:20%`——本轮 min 比基线慢超 20% 即红。把它挂进 nightly（08 篇分层：PR 不跑基准，因为 CI 机器噪声大，nightly 固定 runner 上跑对比才可靠）。

**经验做法**：性能用例的输入规模要"真实业务规模"（排序 1 万元素而不是 10 个），规模写在测试名里（`test_sum_squares_1000`）——小输入测的是框架开销，大输入才是业务性能；同一基线只跟同机同环境的数据比，跨机器比较没有意义。

## 4. 微基准陷阱：你以为在测 A，其实在测 B

微基准（测一个函数/几行代码）有四个经典陷阱，前两个 Python/C++ 通用：

**陷阱一：常量折叠——测的是空循环。** Python 编译器会把字面量表达式在编译期算掉（实测，41 倍差距）：

```
>>> timeit.timeit("2**31", number=1_000_000)        # 4.29 ns/op，编译期已折叠
>>> timeit.timeit("x**31", setup="x=2", number=1_000_000)   # 176.57 ns/op，真实计算
```

对策：被测表达式里**永远有来自 runtime 的变量**（`setup=`/fixture 注入），杜绝纯字面量。C++ 侧对应的陷阱是**死代码消除**：结果没被使用的计算会被编译器整个删掉，`-O2` 下你可能测了个寂寞——对策是 `benchmark::DoNotOptimize(result)`（第 6 节）阻止优化器丢掉结果。

**陷阱二：分支预测预热。** 处理"几乎全 False"分支的循环，CPU 分支预测器在长跑中命中率远高于冷启动——同样代码，"先跑一万次再测"与"上来就测"能差出数倍。对策：预热（pytest-benchmark 自动做；手写 timeit 用 repeat 的前几轮当预热，报告取 min）。

**陷阱三：测的是分配不是算法。** 在循环里 `new`/复制大对象的"算法对比"，比的其实是内存分配器。对策：把分配挪出被测区，或分别测"纯计算"与"分配+计算"两个版本，别混。

**陷阱四：优化把瓶颈挪走了。** 你测了 `list.append` 快了 30%，但真实瓶颈在别处（剖析数据说了算）。微基准只回答"这个点快没快"，不回答"这个点重不重要"——**先剖析后优化**（Python 语言精通 13 篇），否则优化得再漂亮也是负资产。

## 5. 内存回归：tracemalloc 断言上限

内存回归的常见形态：批处理任务从 500MB 涨到 5GB，OOM 容器被杀——同样没有功能测试能拦。Python 标准库 tracemalloc 能把"峰值内存"变成可断言的量：

```python
# test_memory.py
import tracemalloc

def build_report(n: int) -> list[str]:
    rows = []
    for i in range(n):
        rows.append(f"row-{i}: " + "x" * 40)
    return rows

def test_report_peak_memory():
    tracemalloc.start()
    data = build_report(50_000)
    _, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    assert peak < 6 * 1024 * 1024        # 实测峰值 ~5.4MB：上限留 10% 余量
```

要点：**上限 = 实测值 × (1 + 合理余量)**，别拍脑袋定 2 倍（挡不住缓慢劣化）也别 5%（噪声误杀）；阈值随合法需求变化时显式更新并写明理由（issue 链接）。更进一步可用 `tracemalloc.take_snapshot()` 对比两个时间点的分配栈，直接定位"谁多分了"（Python 语言精通 13 篇有完整剖析流程）。C++ 侧对应 valgrind massif 或 Sanitizer 的 allocator 统计，通常进 nightly 而不是 PR 门禁。

## 6. C++ 用 Google Benchmark

C++ 侧的等价物是 Google Benchmark（pytest-benchmark 的很多设计就源自它）：

```cpp
// bench_sum.cpp
#include <benchmark/benchmark.h>
#include <numeric>
#include <vector>

static long long sum_squares(const std::vector<int>& v) {
    long long s = 0;
    for (int x : v) s += (long long)x * x;
    return s;
}

static void BM_SumSquares(benchmark::State& state) {
    std::vector<int> v(1000);
    std::iota(v.begin(), v.end(), 1);        // 夹具构造放循环外
    for (auto _ : state) {
        long long r = sum_squares(v);
        benchmark::DoNotOptimize(r);          // ⭐ 防死代码消除
        benchmark::ClobberMemory();           // 防编译器重排"合并"多轮计算
    }
}
BENCHMARK(BM_SumSquares);
BENCHMARK_MAIN();
```

```
$ cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build
$ ./build/bench_sum
--------------------------------------------------------
Benchmark              Time             CPU   Iterations
--------------------------------------------------------
BM_SumSquares        421 ns          419 ns      1663042
```

四个关键点：① `DoNotOptimize`/`ClobberMemory` 是反死代码消除的标准组合（陷阱一的 C++ 解法）；② **对比模式**把两个实现挂进同一二进制跑出相对差（`BENCHMARK(BM_v1); BENCHMARK(BM_v2);` 同理，或多参数 `BENCHMARK(BM)->Arg(1000)->Arg(10000)` 扫规模曲线），`compare.py` 工具可对两次保存的结果输出增减百分比；③ Time 与 CPU 两列：差异大说明有 I/O 或睡眠混入；④ 迭代数由库自适应决定，等价于 pytest-benchmark 的 Rounds。与 CI 的接线同 3 节：nightly 固定 runner、保存 JSON、对比阈值门禁。

## 常见误区

**误区一：在 CI 的共享机器上跑性能门禁。** 虚拟化/抢占让 20% 的回归淹没在噪声里。基准要么 nightly 固定 runner，要么接受"CI 上只测相对趋势"（同轮内两实现对比）。

**误区二：均值当结论。** 均值被离群点污染（pytest-benchmark 表里 Max 320µs 对 Min 25µs，均值 28 毫无意义）；报告与对比一律用 min 或 median（官方默认对比 min）。

**误区三：优化前不建基线。** "重构完快了 30%"——跟什么比？没有基线的优化故事无法验证。先 `--benchmark-autosave`，再动手。

**误区四：微基准规模失真。** 用 10 个元素测排序选型；分支预测、缓存行、内联策略在小输入上的行为与生产规模完全不同。输入规模对齐生产 P99。

**误区五：内存阈值拍脑袋。** 不量实测就定"不超 100MB"，要么太松（挡不住劣化）要么太紧（天天误报）。阈值=实测×1.1 起步，随需求演进显式调整。

## 本篇小结

- 性能回归是缺陷：需要基线、对比机制、回归警报三件套；剖析与基准各答一个问题；
- timeit 纪律：预热、多次 repeat、number 够大（实测 34%→2% 的波动差）、报告 min、同环境对比；噪声六源清单是排查表；
- pytest-benchmark：`benchmark` fixture + `--benchmark-autosave/--benchmark-compare-fail=min:20%` 挂 nightly 防回退；输入规模对齐真实业务；
- 微基准四陷阱：常量折叠/死代码消除（变量注入、DoNotOptimize）、分支预测预热（预热+min）、分配混入、瓶颈错位（先剖析）；
- 内存回归：tracemalloc 峰值断言（阈值=实测×1.1），snapshot 对比定位分配点；
- C++ 侧 Google Benchmark：夹具在循环外、`DoNotOptimize`+`ClobberMemory`、对比模式与 JSON 门禁同 Python 思路。
