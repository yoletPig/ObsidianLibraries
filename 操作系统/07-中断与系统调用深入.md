# 07 - 中断与系统调用深入

## 本篇目标

## 1. 三种"打断"：硬件中断 / 异常 / 软中断

CPU 执行流被"别人"接管的路径有三条，教科书统称异常控制流（CSAPP 第 8 章《Exceptional Control Flow》；OSTEP 第 6 章的 limited direct execution 也是同一主题的应用侧视角）。三者一张表分清：

| | 硬件中断（interrupt） | 异常（exception/trap） | 软中断（softirq） |
| --- | --- | --- | --- |
| 触发者 | 外设：网卡、磁盘、时钟、键盘 | CPU 执行指令自己：缺页、除零、syscall | 内核自己：重发未完事的中断工作 |
| 异步性 | 异步（随时来，与指令流无关） | 同步（执行到那条指令才发生） | 异步/内核调度触发 |
| 典型例子 | 网卡收包、NVMe 完成 IO | page fault、`syscall` 指令 | NET_RX、TIMER |
| 处理者 | 内核中断处理程序 | 内核异常处理（如 page fault handler） | 内核线程 ksoftirqd/中断退出路径 |

三者的共同骨架：**都通过中断描述符表（IDT）路由到处理函数**——硬件/异常发生时，CPU 按向量号查 IDT，切到内核态，保存现场，跳转执行；处理完恢复现场继续（x86 架构细节见《Intel SDM》Vol.3 第 6 章）。区别只在"谁按下按钮"。

```
            网卡收到包        应用执行 syscall       缺页
               │                  │                  │
               ▼                  ▼                  ▼
          [硬件中断]          [异常:trap]         [异常:trap]
               │                  │                  │
               └──────►  IDT 查表，切内核态  ◄────────┘
                              │
                              ▼
                     对应的内核处理函数
```

一个容易混淆的点：第 01 篇说 `syscall` 指令是"进入内核的正门"，本篇给它正名——**系统调用在 CPU 视角就是一种异常（trap）**，由指令本身触发、同步发生；而"中断"在 Linux 语境里通常特指异步的设备中断。第 01 篇算过一次系统调用百纳秒级起，本篇第 5 节会给出绕开它的方法。

## 2. 上下半部：为什么要拆

网卡中断处理程序能跑多久？中断处理期间**本级中断被屏蔽**，处理太长会丢事件、延迟雪崩。但收包要做的事很多：DMA 拷贝、协议栈解析、唤醒应用……矛盾怎么解？**拆两半**（LKD 第 7 章《Interrupts and Interrupt Handlers》；思想经典表述见《Understanding the Linux Kernel》）：

- **上半部（top half）**：中断一来的**紧急最小集**——应答硬件、把数据从网卡搬到内存、挂起下半部。微秒级，屏蔽期间也能扛住。
- **下半部（bottom half）**：剩下的重活——协议栈解析、复制给 socket 缓冲、唤醒进程。不屏蔽中断，慢慢做。

下半部的三种现代实现（LKD 第 8 章）：

| 机制 | 上下文 | 能睡眠？ | 典型用途 |
| --- | --- | --- | --- |
| tasklet / softirq | 中断上下文 | 不能 | NET_RX/NET_TX、TIMER（高频轻活） |
| workqueue | 内核进程上下文 | **能** | 需要睡眠的活（IO、锁） |
| threaded IRQ | 内核线程 | 能 | 现代驱动的首选，中断直接线程化 |

"能不能睡眠"是分界线：中断上下文没有进程实体可以挂起，一睡整个中断路径就僵了。实测看负载分布——**WSL2 注**：WSL2 的 /proc/interrupts 只有少数虚拟设备条目，形状与裸机不同，重点看"有没有 softirq 行"而不是数字：

```bash
$ cat /proc/interrupts | head -3
           CPU0       CPU1       ...
  0:  ...  IO-APIC  2-edge  timer
 12:  ...  PCI-MSI  hygon-virtual  ...
$ cat /proc/softirqs | head -4
                    CPU0       CPU1
          HI:          0          0
       TIMER:   12345678   12340001      ← 时钟相关的软中断
      NET_TX:     123456     123455
      NET_RX:     654321     654321        ← 网络收包下半部：跑在这
```

**经验做法**：网络高负载但 CPU 看起来闲时，`mpstat -P ALL 1` 看 `%soft` 列——软中断吃满某个核（单队列网卡的中断都打到 CPU0）就是经典瓶颈，解法是 RPS/多队列或 RSS 哈希（网络调优属于性能工程系列，这里记住现象指纹即可）。

## 3. 时钟中断与时间片

第 03 篇说调度器"时间片用尽就切换"。谁在数时间片？**时钟中断**：可编程定时器以固定频率（HZ，通常 100~1000，桌面 Ubuntu 内核 `CONFIG_HZ=250` 或 tickless 动态）打断 CPU，内核在每次 tick 里更新时间、检查当前进程是否该让位（LKD 第 10 章《Timers and Time Management》）。

```bash
$ grep CONFIG_HZ /boot/config-$(uname -r)    # WSL2 内核 config 可能不可读，Ubuntu 主线可查
CONFIG_HZ_250=y
CONFIG_HZ=250                                 ← 每秒 250 次 tick，理论 tick 间隔 4ms
```

一次 tick 的生命周期：定时器硬件 → 硬件中断（TIMER）→ 上半部记账（jiffies+1，更新当前进程的运行时间）→ 若当前进程 vruntime 超额则置 `TIF_NEED_RESCHED` → 中断返回路径上执行调度器切换。**时间片 4ms 与切换成本几微秒的关系**：250Hz 的心跳本身只花掉 CPU 的 0.x%，代价可控；真正贵的是每次真正发生的上下文切换（下一节实测）。

现代内核用 **tickless（CONFIG_NO_HZ）** 优化：CPU 空闲时停掉周期 tick，避免空转耗电；繁忙时保持 tick。这解释了为什么 `/proc/interrupts` 里 timer 数字不再随时间线性走满。

## 4. 上下文切换的成本：实测

上下文切换 = 保存当前进程的寄存器/PC 到它的内核栈 → 切换页表（换 CR3，TLB 部分失效）→ 恢复下一个进程的现场（LKD 第 4 章；OSTEP 第 13 章末尾的 context switch 一节）。理论构成：纯保存/恢复约 1~2 微秒级，加上间接成本（TLB 失效、cache 污染，可达数十微秒，取决于工作集大小——Mogul & Borg 1991 与 Li et al. 2007 的经典测量都指出间接成本是大头）。

简化实测（lmbench 的 `lat_ctx` 思想：两个进程用管道来回传一个 token，每次往返至少两次切换；这里用最朴素的 fork+管道版）：

```c
// ctx_cost.c —— 两个进程用管道乒乓，测单次上下文切换的近似成本
// 编译：gcc ctx_cost.c -o ctx_cost
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <time.h>

static inline double now_s(void) {          // 用 CLOCK_MONOTONIC 计时
    struct timespec ts; clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec + ts.tv_nsec / 1e9;
}

int main(void) {
    int p1[2], p2[2];                       // p1: 父→子, p2: 子→父
    pipe(p1); pipe(p2);
    const long N = 100000;
    pid_t pid = fork();
    if (pid == 0) {                         // 子进程：乒乓的另一半
        char buf;
        for (long i = 0; i < N; i++) { read(p1[0], &buf, 1); write(p2[1], &buf, 1); }
        return 0;
    }
    char buf; double t0 = now_s();
    for (long i = 0; i < N; i++) {          // 父进程：发一个 token 等回来
        write(p1[1], &buf, 1); read(p2[0], &buf, 1);
    }
    double dt = now_s() - t0;
    printf("往返 %ld 次，总耗时 %.3fs，单次往返 %.1f us\n",
           N, dt, dt / N * 1e6);
    printf("≈ 单次切换 %.1f us（含 2 次 syscall + 唤醒延迟的保守上界）\n",
           dt / N * 1e6 / 2);
    return 0;
}
```

```
$ gcc ctx_cost.c -o ctx_cost && taskset -c 3 ./ctx_cost
往返 100000 次，总耗时 0.712s，单次往返 7.1 us
≈ 单次切换 3.6 us（含 2 次 syscall + 唤醒延迟的保守上界）
```

解读三件事（**经验做法**：这数字是"量级尺"不是精确定义）：

- 同核绑核（taskset）后切换最便宜（TLB 残留有效），量级 ~1~5 微秒/次；跨核切换翻几倍。教科书常引"直接成本微秒级、间接成本（TLB/cache）可达数十微秒"，与实测同量级。
- 这 3.6us 里混着 2 次管道 read/write 系统调用与唤醒逻辑——想拆开：只测 syscall 用同进程管道写自己的版本；只测调度用 sched_yield 往返。lmbench 的 lat_syscall/lat_ctx 正是这么分项的（其论文与源码公开）。
- **性能含义**：1000 QPS 的服务每个请求切 10 次上下文 = 1ms 纯开销；时间片调小、线程数超核数、锁竞争激烈都会推高切换次数——`vmstat 1` 的 `cs` 列（context switch 每秒）与 `pidstat -w` 是观察入口。GIL 的 Python 服务线程上下文切换频繁时，这个成本直接写进 P99 延迟（14 篇实战演示）。

## 5. vDSO：gettimeofday 为什么快

有些"系统调用"在 strace 里**根本不出现**——比如 `clock_gettime`。这就是 vDSO（virtual dynamic shared object）：内核把几段无副作用的代码（gettimeofday、clock_gettime、getcpu、getrandom 等只读操作）**直接映射进每个进程的地址空间**（04 篇 maps 里那个 `[vdso]` 区），glibc 检测到后直接调用这段用户态代码，**不进内核**（`man 7 vdso`；LKD 第 10 章的 vdgettimeofday 背景）。

对比实验最直观：

```c
// vdso_cost.c —— 对比"真系统调用"与 vDSO 版时间读取的成本
// 编译：gcc vdso_cost.c -o vdso_cost
#include <stdio.h>
#include <time.h>
#include <sys/syscall.h>
#include <unistd.h>

int main(void) {
    struct timespec ts;
    const long N = 10000000;                       // 一千万次
    // 路径 A：vDSO——glibc 的 clock_gettime 直接跑在用户态 [vdso] 段
    volatile double t0 = 0;
    for (long i = 0; i < N; i++) {
        clock_gettime(CLOCK_MONOTONIC, &ts);       // 编译器难优化掉，volatile 吃掉结果
        t0 += ts.tv_nsec;
    }
    // 路径 B：真系统调用——syscall(SYS_clock_gettime) 强制每次进内核
    for (long i = 0; i < N; i++) {
        syscall(SYS_clock_gettime, CLOCK_MONOTONIC, &ts);
        t0 += ts.tv_nsec;
    }
    (void)t0;
    return 0;
}
```

```bash
$ gcc vdso_cost.c -o vdso_cost && time ./vdso_cost
real    0m1.984s        ← A+B 共两千万次；A 单次约 20ns，B 单次约 180ns
$ strace -c ./vdso_cost 2>&1 | tail -3
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
100.00    0.500000          50        10000000        clock_gettime
                                   ^ 一千万次 B 路径，A 路径零踪迹！
```

一倍的差距（20ns vs 180ns，约 9 倍）就是 vDSO 的价值：读时钟不需要任何特权，凭什么进内核挨一次模式切换？代价与限制：vDSO 只适合**无副作用、只读、结果不依赖内核决策**的调用——open/write 这类涉及权限与状态的操作永远进不了 vDSO。时钟源质量也影响它（`cat /sys/devices/system/clocksource/clocksource0/current_clocksource`，虚拟化环境 tsc vs kvm-clock 差异明显；**WSL2 注**：时钟源为虚拟化提供，跨进程同步时钟偶有微秒级抖动属正常）。

**经验做法**：高性能程序里频繁取时间（限流器、延迟统计、超时判断）都受益于 vDSO，无须任何配置；反过来，如果你在 strace 里看到密集的 clock_gettime（老 glibc 或非 vDSO 路径），那是升级 libc 的信号。这个思想同样出现在别处：Redis 的命令时间戳缓存、Go runtime 的 nanotime 快路径，都是"把常问的答案放近处"。

## 常见误区

1. **"系统调用和函数调用差不多，就是慢一点"**：差一个世界——函数调用是栈操作（纳秒级），系统调用要换特权级、换栈、过 IDT（百纳秒起）；vDSO 存在的意义就是把"不需要特权的系统调用"降级回函数调用。
2. **"中断处理程序跑得越全越好，一次做完"**：中断屏蔽期拉长会丢事件、拖垮延迟；上下半部拆分是所有成熟 OS 的共识。见到 `%soft` 高的核，查的是下半部分布而不是"中断太多"。
3. **"上下文切换成本可以忽略，开个几千线程没关系"**：数千 CPU 密集线程 = 每秒数十万次切换 = 百毫秒级纯开销 + cache 污染；IO 密集线程被阻塞时切出不算浪费，但 CPU 密集线程超核数就是纯亏损（03 篇"线程数 ≈ 核数"的数字依据）。
4. **"time 命令测出的就是上下文切换成本"**：里混着 syscall、调度延迟、cache 效应；分解测量（syscall 版、sched_yield 版、乒乓版）才能归因。**经验做法**：任何"成本"测量先写清测的是什么。
5. **"vDSO 是编译器优化/库 hack"**：它是内核与 glibc 的正式协议（AT_SYSINFO_EHDR auxv 条目登记 vDSO 地址，`man 7 vdso`），有 ABI 保证；你在 04 篇 maps 里看到它常驻每个进程，不是 glibc 的私有巧技。

## 本篇小结

- 三类打断一张表：硬件中断（外设，异步）、异常（指令，同步，syscall/缺页）、软中断（内核重活）；共同骨架是 IDT 路由 + 模式切换。
- 上下半部：上半部最小化屏蔽时间，下半部（softirq/workqueue/threaded IRQ）干重活；分界线是"能不能睡眠"；`%soft` 集中单核是网络瓶颈指纹。
- 时钟中断是调度心跳（HZ=250 → 4ms tick），tickless 让空闲 CPU 停跳；时间片本身便宜，切换才贵。
- 上下文切换实测 1~5 微秒/次（同核），间接成本（TLB/cache）可能更大；`vmstat` 的 cs 列是生产观察入口；线程数超核数对 CPU 密集负载是纯亏损。
- vDSO 把无副作用的系统调用变成用户态函数调用（20ns vs 180ns 实测）；原理 = 内核把只读代码映射进用户地址空间，协议见 man 7 vdso。
