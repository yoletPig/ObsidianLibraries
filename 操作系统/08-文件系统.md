## 1. VFS 抽象层：四个对象

Linux 支持 ext4、xfs、btrfs、NFS（网络）、procfs（/proc）……几十种"文件系统"，但应用只见得到一套 `open/read/write/close`。中间的翻译官就是 VFS（Virtual File System，LKD 第 12 章《The Virtual Filesystem》）。VFS 定义四个核心对象，磁盘上的具体文件系统负责实现它们：

```
                 应用 open("/home/yyl/model.bin")
                          │
   ┌──────────────────────▼───────────────────────┐
   │                VFS 通用接口                    │
   │  superblock ←→ inode ←→ dentry ←→ file        │
   └───┬──────────┬──────────┬──────────┬──────────┘
       ▼          ▼          ▼          ▼
   ext4 实现   ext4 实现   dcache     进程打开文件表
 (xfs/btrfs/procfs 各自实现同一套 operation 结构体)
```

| VFS 对象 | 一句话 | 关键内容 | 主要系统调用 |
| --- | --- | --- | --- |
| superblock | 这个文件系统的"身份证" | 类型、块大小、已用/空闲计数 | mount 时读入 |
| inode | 一个文件的全部元数据 | 大小、权限、时间戳、数据块指针 | stat |
| dentry | 路径中的一个分量 | 名字 → inode 的映射（缓存于内存 dcache） | 路径解析（open 每一层都要查） |
| file | 一次**打开**的会话 | 当前偏移量、打开模式、操作函数表 | read/write/lseek |

`file` 与 `inode` 的分离是面试与实战双高频：**fd 指向的是"打开会话"（file），不是文件本身（inode）**——同一个文件被打开两次得到两个 fd、两套独立的偏移量（下文硬链接实验会用到 fd→inode 的链条）。VFS 的价值还有一条性能线：**dcache**（dentry 缓存）让 `open("/a/b/c")` 的三层路径解析不用每次都摸磁盘；`find /` 快，是因为 dcache 记住了整棵树。

## 2. inode 与 dentry：stat 实测

**inode = 文件的身份证**：权限、属主、大小、三个时间戳、链接计数、数据块指针——**唯独不包括名字**。名字是 dentry（目录项）的事：**目录的本质是"文件名 → inode 号"的映射表**，也是普通文件（LKD 第 12 章；`man 7 inode`）。用 stat 亲眼看（`man 2 stat`）：

```bash
$ echo "hello" > note.txt
$ stat note.txt
  File: note.txt
  Size: 6          Blocks: 8          IO Block: 4096   regular file
Device: 820h/2080d Inode: 524339      Links: 1
Access: (0644/-rw-r--r--)  Uid: ( 1000/   yyl)   Gid: ( 1000/   yyl)
Modify: 2026-11-08 10:12:33.000000000 +0800
Change: 2026-11-08 10:12:33.000000000 +0800
 Birth: 2026-11-08 10:12:33.000000000 +0800
$ ls -li note.txt            # -i 直接显示 inode 号
524339 -rw-r--r-- 1 yyl yyl 6 Nov  8 10:12 note.txt
```

三个时间戳的语义（`man 7 inode` 的"File timestamps"节，面试常考）：**atime** 最后读、**mtime** 内容最后改、**ctime** inode 元数据最后改（改权限/改名/改内容都会动 ctime——它不是 creation time，Birth 才是）。IO Block 4096 就是 04 篇的页大小在文件系统的镜像；Size 6 但 Blocks 8（8×512B = 4KB）——**哪怕 1 字节的文件也要占一个整块**，文件系统内部碎片的第一个例子。

"删除文件"的真相由两个数字共同决定：**Links（硬链接计数）**和**打开它的 fd 数**。`unlink` 只删一个名字、把 Links 减一；计数归零且无人持有 fd 时才真正释放数据块（POSIX unlink 语义，`man 2 unlink`）。于是有著名技巧：**程序还在写的 log 文件，用 `rm` 删掉不会释放磁盘**（fd 还开着，inode 还活着），`df` 看到空间没回来，`lsof | grep deleted` 能找到"幽灵文件"——**经验做法**：清理大日志前先 `truncate` 或重启服务，而不是裸 `rm`。

## 3. ext4 布局概览：superblock/inode表/块位图

把磁盘看成块（4KB）的数组，ext4 的组织方式（参照《Linux 内核设计与实现》第 13 章与内核文档 Documentation/filesystems/ext4/，不抠位级细节，建立账本直觉）：

```
┌───────────── 磁盘 ─────────────┐
│ ┌──── 块组 0 ────────────────┐ │
│ │ superblock  ← 文件系统级账本头 │ │
│ │ 组描述符表                   │ │
│ │ 块位图   ← 哪些数据块空闲     │ │
│ │ inode位图 ← 哪些inode空闲    │ │
│ │ inode表  ← 所有inode的实体   │ │
│ │ 数据块   ← 文件内容本体       │ │
│ └────────────────────────────┘ │
│ ┌──── 块组 1（同样结构，无superblock或备份）─┐ │
│ └────────────────────────────┘ │
│ ... 块组 N ...                  │
└─────────────────────────────────┘
```

- **superblock**：文件系统总账——块总数/空闲数、块大小、状态。挂载时第一个读它，坏了整个文件系统失忆（所以 ext4 在多个块组存备份）。
- **块位图/ inode 位图**：一串 bit，每个 bit 对应一个块/inode 是否占用。分配新块就是"找 0 再置 1"。
- **inode 表**：inode 实体数组。**inode 数量在格式化时就定死**——`df -i` 看到的 IUse 就是它的水位。海量小文件场景（几千万图片/切片）磁盘没满但 inode 耗尽，报 `No space left on device`——**经验做法**：创建失败先 `df -h` 再 `df -i`，第二个才是老手动作。
- **目录也是文件**，内容是"名字→inode"的表项。`ls` 遍历目录 = 读这张表；`stat` 按名字找文件 = 先在 dcache 查路径，miss 则逐层读目录块。

ext4 相对 ext2/3 的两大进化（与性能直接相关）：**extent（区段）**代替"块指针数组"——大文件不再需要百万级指针，一个 extent 记录"起点+连续长度"，1GB 连续文件只需要几十个 extent；**延迟分配（delayed allocation）**——写数据先攒在 page cache，等内核决定物理位置时一次性给连续块（减少外部碎片、提高顺序写比例，05 篇页 cache 的续篇）。

```bash
$ dumpe2fs -h /dev/sdX 2>/dev/null | head -12     # 需要 root 与具体设备名；WSL2 内的 ext4 虚拟盘可用 df 查看类型
$ df -T .                                          # 看当前目录所在文件系统类型
Filesystem     Type 1K-blocks      Used Available Use% Mounted on
/dev/sdc       ext4 263174212 155360048  94489636  63% /
```

**WSL2 注**：WSL2 的根文件系统是虚拟磁盘（VHD）上的 ext4，`dumpe2fs` 需要找到对应虚拟块设备；Windows 侧的 /mnt/c 则是 9P 协议透传（性能差一个量级，编译/训练数据务必放 WSL 文件系统内——这条是 WSL2 第一性能铁律）。

## 4. 日志文件系统思想：crash consistency

一次"写文件"其实要动多处：inode、数据块、目录、位图。写到一半断电，磁盘上的账本就自相矛盾（数据写了 inode 没记、目录指了个半截文件）——这是 **crash consistency 问题**（OSTEP 的持久化篇整卷讲它，第 40 章《Crash Consistency: FSCK and Journaling》是标准参考；想读原始研究："All File Systems Are Not Created Equal" (OSDI'14) 对 ext4 的 fsync 语义做过实证）。

日志（journal）的解法，思想与数据库 WAL（write-ahead log）完全一致：

```
1. 日志写入：把"打算做的全部修改"先顺序写到日志区，fsync 落盘
2. 提交点：  写入一个 commit 记录（此刻起这批修改"已定"）
3. 检查点：  择机把修改真正写回原位置
4. 崩溃恢复：重启时扫日志——commit 完整的重放（redo），不完整的丢弃
```

三种日志模式（ext4 默认 ordered）：**journal**（数据+元数据全进日志，最安全最慢）、**ordered**（元数据进日志，数据先于元数据落盘，默认）、**writeback**（只日志元数据，最快，崩溃后旧数据风险）。fsync 在这套机制里的位置：`write()` 只保证数据进了 page cache（05 篇），**掉电可能全丢**；`fsync(fd)` 才逼内核把该文件的数据（和 ext4 ordered 模式下随后的元数据）真正落盘（`man 2 fsync`）。代价实测：

```bash
$ time dd if=/dev/zero of=/tmp/a bs=1M count=512 oflag=dsync   # 每块都 fsync
512+0 records in
real    0m7.823s        ← 约 65 MB/s
$ time dd if=/dev/zero of=/tmp/b bs=1M count=512               # 直写 page cache
real    0m0.412s        ← 约 1.2 GB/s，差 20 倍
```

差出来的 7 秒全是"等磁盘确认"的时间。**经验做法**：数据库/训练 checkpoint/任何"不能丢"的落盘必须 fsync（或 O_DSYNC），但要**批量 fsync**（一次刷大批数据）而不是每条数据刷一次——LevelDB/RocksDB 的 WAL 批量提交、PyTorch 保存 checkpoint 后立即 fsync 都是同一工程判断。反过来，日志、指标这类"丢了能忍"的数据永远不要 fsync。

## 5. 硬链接 vs 软链接：实测演示

两条完全不同的"另一个名字"：

```bash
$ echo "content" > real.txt
$ ln real.txt hard.txt          # 硬链接：同一个 inode 的第二个名字
$ ln -s real.txt soft.txt       # 软链接（符号链接）：一个存路径的独立文件
$ ls -li
total 12
524402 -rw-r--r-- 2 yyl yyl 8 Nov  8 10:30 hard.txt     ← Links=2，inode 与 real 相同
524403 lrwxrwxrwx 1 yyl yyl 8 Nov  8 10:30 soft.txt     ← l 开头，独立 inode，大小=路径长度
524401 -rw-r--r-- 1 yyl yyl 8 Nov  8 10:30 real.txt     ← Links=1？不，注意 hard 与 real 同号
```

细看：hard.txt 与 real.txt 的 **inode 号相同（524402...以实际输出为准）且 Links 计数为 2**——它们就是同一个文件的两个名字；soft.txt 有独立 inode，内容只是字符串 `real.txt`。做破坏实验看语义差异：

```bash
$ rm real.txt && ls -li && cat hard.txt && cat soft.txt
524402 -rw-r--r-- 1 yyl yyl 8 ... hard.txt     ← Links 从 2 变 1：数据还活着
524403 lrwxrwxrwx 1 yyl yyl 8 ... soft.txt
content                                        ← 硬链接完好（inode 还在）
cat: soft.txt: No such file or directory       ← 软链接悬空（dangling symlink）
```

| | 硬链接 | 软链接 |
| --- | --- | --- |
| 本质 | 同一 inode 的别名（Links 计数） | 独立 inode，内容为目标**路径** |
| 跨文件系统 | 不行（inode 号只在单个 fs 内有意义） | 可以 |
| 链接目录 | 不行（防环，仅 root 的 . / .. 例外） | 可以 |
| 目标删除后 | 数据完好（计数减到 0 才释放） | 悬空，访问报 ENOENT |
| 大小/成本 | 零额外空间 | 存路径字符串的极小文件 |

工程落点（**经验做法**）：硬链接用于"同一份数据多处可见"——Git 的对象库、cp 的 `-al` 秒拷、模型文件的 checkpoint 复用；软链接用于"可变的指向"——`/usr/bin/python3 → python3.10`、虚拟环境切换、配置文件指向当前版本。注意 Python 里 `os.path.exists` 对悬空链接返回 False，`os.path.lexists` 才如实报告链接本身存在——写部署脚本时的经典坑。

## 6. 一切皆文件：/proc /dev /sys

Unix 的设计信条（源自 Thompson/Ritchie 的原始论文思想，"everything is a file"）：**把所有资源都暴露成可 read/write 的文件，一套 API（open/read/write/ioctl）通吃**。Linux 严格贯彻：

- **/proc**：内核状态的伪文件系统（procfs，`man 5 proc`）。`/proc/self/maps`（04 篇）、`/proc/cpuinfo`、`/proc/meminfo`、`/proc/loadavg`——本系列一直在"读文件"读内核。
- **/sys**：设备与内核参数的结构化视图（sysfs）。`/sys/class/block/`、`/sys/devices/system/cpu/`。
- **/dev**：设备文件。`/dev/null`（写入即丢弃）、`/dev/zero`（无限 0）、`/dev/random`；块设备 `/dev/sda`。

伪文件的特殊性：它们**不存在于磁盘**，读它时内核现场生成内容。验证一下"读 /proc 就是调内核代码"：

```python
# proc_demo.py —— 伪文件系统实测：读 = 触发内核计算
import os, time

f1 = os.stat("/proc/self/status")
time.sleep(0.1)                        # 期间程序自己分配点内存
x = [0] * 10_000_000
st = os.stat(f"/proc/{os.getpid()}/status")
print(f"status 的 inode Size: {f1.st_size} -> {st.st_size}")   # 大小会变！
print("VmRSS:", [l for l in open("/proc/self/status") if "VmRSS" in l][0].strip())
print("loadavg:", open("/proc/loadavg").read().strip())
```

```
$ python3 proc_demo.py
status 的 inode Size: 0 -> 0
VmRSS: 41228 kB                        ← 文件"大小"是 0，内容却真实可读
loadavg: 1.23 0.87 0.65 2/812 24601
```

伪文件 stat 出来的 size 是 0（它们没有静态内容），`cat` 却能读到数据——因为 read 时内核现场调用生成函数。这就是 VFS 抽象的威力：**应用不需要知道对面是真磁盘还是一段内核函数**。对算法工程师，/proc 是最顺手的 OS 可观测层：02 篇看状态、04 篇看 maps、05 篇看 meminfo、13 篇看 cgroup（/proc/self/cgroup）——"cat 一下"贯穿全系列。

## 常见误区

1. **"文件名是文件的一部分"**：名字属于目录（dentry），内容与元数据属于 inode。改名（mv 同盘）只是改目录表项，inode 号不变——这也是 `mv` 通常瞬间完成的原因。
2. **"write 返回成功 = 数据安全落盘"**：只进了 page cache；掉电/崩溃的账要 fsync 来兜底。测试环境"从没丢过数据"不能证明写入路径正确（crash 一致性只有在崩溃实验里才显形）。
3. **"硬链接只是复制了一份文件"**：零复制，同一 inode。相反，软链接才"复制了名字"；判断标准永远是 inode 号（`ls -i`）。
4. **"磁盘满才会 No space left on device"**：inode 耗尽同样报这个错（`df -i`）；另一个同错场景是文件系统只读（dmesg 查 I/O error/只读挂载）。
5. **"读 /proc 与读普通文件没区别，随便高频轮询"**：每次读都触发内核现场计算（procfs 的 show 回调），高频轮询 VmStatus 等文件有可测开销；监控程序应控制采样频率（**经验做法**：1s 级足够，100ms 级轮询 /proc 本身会成为负载）。

## 本篇小结

- VFS 四对象：superblock（文件系统账本）、inode（文件元数据）、dentry（名字→inode，内存缓存 dcache）、file（打开会话，fd 指向它）。
- inode 没有名字；删除 = unlink 名字、Links 减 1、归零且无 fd 才释放；"rm 掉还在写的日志不释放空间"由这条规则解释（lsof | grep deleted）。
- ext4 = 块组（superblock/位图/inode 表/数据块）+ extent（连续区段）+ 延迟分配；海量小文件先查 `df -i`。
- 崩溃一致性由日志解决：先写日志（含 commit 记录）再检查点，恢复时重放；fsync 是把 page cache 兑现成持久性的唯一手段，批量刷才是工程正解（经验做法）。
- 硬链接同 inode 跨不了 fs，软链接存路径可悬空；/proc /sys /dev 是内核现场生成内容的伪文件——"一切皆文件"让 OS 可观测性统一在 cat 与 read 里。
