## 1. malloc/free 如何工作：brk/mmap 之上有分配器

`malloc` 不是系统调用，是 libc 里的库函数。它和内核的分工（CSAPP 第 9.9 节的分配器模型；Linux 实现细节见 glibc malloc 内部文档，`man 3 malloc` 与 mallopt(3)）：

```
你的代码:  p = malloc(64);
   │
   ▼
libc 分配器（ptmalloc）：小块走"自己的仓库" —— 从已拿到的内存里切一块，改空闲链表
   │ 仓库空了/请求超大（≥128KB，M_MMAP_THRESHOLD 可调）
   ▼
内核系统调用:  brk() 推高堆顶  |  mmap() 匿名映射新区域（05 篇讲过）
```

验证：同一程序里先要小块、再要大块，strace 一眼看穿两层：

```c
// alloc_trace.c —— 小块走 brk/堆，大块走 mmap
// 编译：gcc alloc_trace.c -o alloc_trace
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    void *small = malloc(64);            // 小块：分配器从堆里切
    void *big   = malloc(256 * 1024);    // 256KB ≥ 128KB 阈值：直接 mmap
    printf("small=%p big=%p\n", small, big);
    free(small); free(big);
    return 0;
}
```

```bash
$ gcc alloc_trace.c -o alloc_trace && strace -e trace=brk,mmap,munmap ./alloc_trace 2>&1 | grep -v "ld\|libc\|ENOENT" | head -6
brk(NULL)                               = 0x5a1e...
mmap(NULL, 266240, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) = 0x7f...
small=0x5a1e...d2a0 big=0x7f2c...6010
munmap(0x7f2c...6010, 266240)           = 0
```

`malloc(64)` 在系统调用层**没有任何痕迹**（分配器自给自足），`malloc(256*1024)` 则直接多出一条 `mmap`。这个分层解释了大量现象：小块分配快（用户态链表操作，几十纳秒）；大块走 mmap（进内核，微秒级）但 free 时立即归还系统（munmap）；**128KB 阈值是可调的性能旋钮**（mallopt 的 M_MMAP_THRESHOLD，glibc 还有动态调整逻辑）。

分配器内部如何记账？把空闲内存组织成链表（free list），分配时找一块够大的切下。最简单的两种策略（OSTEP 第 17 章《Free-Space Management》）：

- **first-fit**：从链表头找第一块够大的。快，但低地址端容易剩下一堆小碎屑。
- **best-fit**：找能装下的最小块。浪费少，但每次要扫全表，且会攒下大量"刚好差一点"的残余小块。

分配时还要"顺手"记下块大小（通常放在块头 header 里，CSAPP 第 9.9 节的隐式空闲链表正是这么设计的），free 才知道还多少。

## 2. 内存碎片：内部与外部（配 mini allocator）

**内部碎片**：给你的块比你要求的大（header、对齐、大小类取整），浪费在块里面。**外部碎片**：空闲内存总量够，但被切成不连续的小块，找不到一块连续的够用的。

```c
// mini_malloc.c —— 60 行的 first-fit 分配器：看懂碎片从哪来
// 编译：gcc mini_malloc.c -o mini_malloc
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <stdint.h>

typedef struct block {                  // 每块开头的 header：大小 + 在用标志
    size_t size; int used;
    struct block *next;
} block_t;

static block_t *heap_head = NULL;       // 空闲链表的头

void *my_malloc(size_t size) {
    size = (size + 15) & ~15UL;         // 16 字节对齐：自身就会造成内部碎片
    for (block_t *b = heap_head; b; b = b->next) {      // first-fit 扫描
        if (!b->used && b->size >= size) {
            if (b->size >= size + sizeof(block_t) + 32) {   // 够大就切分
                block_t *rest = (block_t *)((char *)b + sizeof(block_t) + size);
                rest->size = b->size - size - sizeof(block_t);
                rest->used = 0; rest->next = b->next;
                b->next = rest; b->size = size;
            }
            b->used = 1;
            return (char *)b + sizeof(block_t);   // 返回 header 之后的地址
        }
    }
    // 没找到：sbrk 向内核要新内存，挂到链表尾
    block_t *b = sbrk(sizeof(block_t) + size);
    if (b == (void *)-1) return NULL;             // OOM
    b->size = size; b->used = 1; b->next = NULL;
    if (!heap_head) heap_head = b;
    else { block_t *t = heap_head; while (t->next) t = t->next; t->next = b; }
    return (char *)b + sizeof(block_t);
}

void my_free(void *p) {
    if (!p) return;
    block_t *b = (block_t *)((char *)p - sizeof(block_t));   // 沿 header 拿回大小
    b->used = 0;                                   // 本版不做相邻合并，故意留坑
}

int main(void) {
    void *a = my_malloc(100), *b = my_malloc(100), *c = my_malloc(100);
    my_free(b);                                    // 中间空出 100B 洞
    void *d = my_malloc(200);                      // 洞不够，first-fit 只能要新内存
    printf("a=%p b=%p c=%p d=%p\n", a, b, c, d);
    printf("b 被释放留下的洞：%p（大小 100，装不下 d 的 200）\n", b);
    return 0;
}
```

```
$ gcc mini_malloc.c -o mini_malloc && ./mini_malloc
a=0x55f4...d2b0 b=0x55f4...d360 c=0x55f4...d410 d=0x55f4...d4c0
b 被释放留下的洞：0x55f4...d360（大小 100，装不下 d 的 200）
```

d 没有复用 b 的洞——**外部碎片**诞生：总空闲量够（100），但最大连续块不够（100 < 200）。真实分配器还做**合并**（free 时把相邻空闲块并起来）和**分离适配**（按大小分桶的空闲链表，CSAPP 第 9.9 节的 malloc lab 就教到这），但碎片的根源已经在这 60 行里了。**经验做法**：长时间运行的服务出现 RSS 涨了不回，第一嫌疑是碎片（释放的块太小、位置不连续，合并不了还给内核），第二才是泄漏——两者现象相似，工具能区分（见第 5 节）。

## 3. tcmalloc/jemalloc 设计思想概览

ptmalloc（glibc 默认）诞生于单核时代，多核多线程下有两个先天短板：**所有线程抢同一堆的锁**（arena 数量有限），**锁内操作链表在 NUMA 上跨节点访存**。两个现代分配器给出同一思想的两种实现（Tcmalloc 论文：Sanfilippo/Google per-thread cache 设计；jemalloc 设计文档：Evans, "A Scalable Concurrent malloc Implementation for FreeBSD"）：

- **线程缓存（thread cache / tcache）**：每个线程私有一组小对象缓存，分配/释放小块完全无锁、访问全在本地——大并发的第一加速器。攒多了再批量归还中心区。
- **大小类（size class）**：不按任意字节切，而是按固定档位（8B、16B、32B…2MB），同档位对象复用。牺牲一点内部碎片，换来 O(1) 定位与极低的合并需求。
- **arena 分区**：中心内存划成多个 arena（按 NUMA 节点对齐），线程绑定各自的 arena，减少跨节点流量与锁竞争。
- **页级管理**： jemalloc/tcmalloc 都把内存当"页（4KB）+ span/chunk"管理，大对象直接页分配、small object 从页里切。

```
线程 A ──► [tcache A] ──归还──► ┌ arena 0 (numa node 0) ┐
线程 B ──► [tcache B] ──归还──► │  size class 8/16/32...  │──不够──► mmap/brk
线程 C ──► [tcache C] ──归还──► └ arena 1 (numa node 1) ┘
```

什么时候值得换（**经验做法**，可查证的方法是压测对比）：多线程高频小对象（请求处理、KV cache 管理）用 jemalloc/tcmalloc 常有 10%~30% 吞吐提升；单线程或分配不频繁的场景收益接近零。在推理服务里验证极简单：`LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2 ./server` 前后各跑一遍基准——不写一行代码。

## 4. Python 的内存管理：pymalloc/arena

CPython 有自己的三层分配体系（依据：CPython 源码 Modules/obmalloc.c 的注释与官方 Dev Guide "Memory Management"）：

```
第 3 层  Python 对象（PyObject）
第 2 层  pymalloc：≤512B 的对象 → pool(4KB) 切成固定 block；同类 block 组成 usedpool
第 1 层  C malloc（glibc）：>512B 的对象直接走它 → 再下面才是 brk/mmap（本篇第 1 节）
```

- **≤512 字节**的小对象（绝大多数 PyObject：小整数、短字符串、元组）由 pymalloc 管理：arena(256KB) → pool(4KB) → block（与对象大小匹配的固定档位）。释放的 block 回池复用，**不归还 C 层**。
- **>512 字节**直接 malloc——这就是"大对象特殊"的原因：它绕过对象池，直接暴露在 glibc 分配器的碎片逻辑下。NumPy 数组的数据区、大字节串、模型 tensor 都在这里。
- **arena 整体归还的苛刻条件**：一个 arena 里所有 pool 全空才能还给 OS。而小对象散布在不同 arena 时"某个 pool 总有活着的对象"——**这就是 Python 常见现象"内存涨了不回"的主因**（不是泄漏，是池化+arena 碎片），官方文档 "Memory Management" 明确记载此行为。

实测三层结构的行为：

```python
# pymalloc_demo.py —— 小对象进池、大对象走 C 层、池不轻易还债
import os, tracemalloc

def rss():                                   # 读本进程 RSS（04 篇的 RES）
    with open(f"/proc/{os.getpid()}/status") as f:
        for line in f:
            if line.startswith("VmRSS"):
                return int(line.split()[1])

tracemalloc.start()
base = rss()
small = [str(i) for i in range(500_000)]     # 50 万个小字符串 → pymalloc
print(f"小对象: tracemalloc={tracemalloc.get_traced_memory()[0]//1024}KB, "
      f"RSS增幅={rss()-base}KB")
del small                                    # 全部释放：引用清零
print(f"del后   : tracemalloc={tracemalloc.get_traced_memory()[0]//1024}KB, "
      f"RSS增幅={rss()-base}KB")              # Python 视角已释放；RSS 看实现心情

big = bytearray(256 * 1024 * 1024)           # 256MB 大对象 → 直接 malloc→mmap
print(f"大对象: RSS增幅={rss()-base}KB")
del big
print(f"del后   : RSS增幅={rss()-base}KB")   # 大块通常立即还给 OS（munmap）
```

```
$ python3 pymalloc_demo.py
小对象: tracemalloc=49220KB, RSS增幅=64116KB
del后   : tracemalloc=0KB, RSS增幅=61892KB      ← Python 层清零，RSS 几乎不回（池保留）
大对象: RSS增幅=324092KB
del后   : RSS增幅=62132KB                        ← 256MB 立刻归还（回到基线附近）
```

这正是"为什么 Python 服务 RSS 会虚高、为什么重启比修内存有效"的底层答案。**经验做法**：排查 Python 内存先用 tracemalloc 看对象层（是代码漏了引用），再看 RSS-对象层的差值（是 pymalloc/arena 持有还是 C 扩展泄漏）；PyTorch 场景还要加一层 `torch.cuda.memory_reserved` 的显存池，原理同构。

## 5. 内存泄漏排查思路

一套由粗到细的通用流程（C 与 Python 各有工具，思想共用；**经验做法**——先确认"泄漏的是哪一层"再选工具）：

1. **现象确认**：RSS 随时间/请求量单调增长且不回。`ps -o rss,vsz -p PID` 每分钟采样，或 `pidstat -r -p PID 60`。注意区分：VIRT 涨不叫泄漏（05 篇），RSS 涨才查。
2. **分界定位**：`cat /proc/PID/smaps_rollup` 看 Anonymous（新分配）与 Shared（映射共享库）哪边在涨。Anonymous 涨 → 堆/大对象问题；FilePmdMapped/Shared 涨 → mmap/页 cache 行为。
3. **C/C++ 层定罪**：valgrind memcheck（`valgrind --leak-check=full ./prog`，慢 10 倍但精确到行）；常驻服务用 AddressSanitizer（`gcc -fsanitize=address`，运行时拦截）；分配热点用 heap profiler（`gperftools` 的 pprof / jemalloc 的 prof）。
4. **Python 层定罪**：tracemalloc 快照 diff（下面代码）；`gc` 模块查引用环；第三方扩展（NumPy/CUDA）的泄漏要用 `CUDA-MEMCHECK`/`compute-sanitizer` 或 py-spy dump。
5. **长跑服务**：压测 + 灰度观察曲线；区分"泄漏"与"碎片虚高"——重启后 RSS 立即回落的模式更支持碎片（第 2 节），对象数不降的才支持泄漏。

```python
# leak_check.py —— tracemalloc 快照 diff：定位"谁在涨"
import tracemalloc, linecache

tracemalloc.start(10)                       # 保存 10 层栈
snaps = []
for step in range(3):
    leaks = [bytearray(1024) for _ in range(1000)]   # 模拟泄漏：列表一直追加
    snaps.append(tracemalloc.take_snapshot())
    if step == 2:
        top = snaps[2].compare_to(snaps[0], "lineno")
        for stat in top[:2]:
            print(f"{stat.size_diff//1024:6d}KB  {stat.traceback.format()[0]}")
```

```
$ python3 leak_check.py
  2969KB  leak_check.py:6: <module>          ← 每轮 +1000 个 1KB，元凶是这行的列表
```

## 常见误区

1. **"malloc(100) 就精确拿到 100 字节"**：至少 112+（对齐与 header），大块可能按大小类取整到 256KB 级页。别拿 malloc 返回值当内存审计依据。
2. **"free 之后内存就还给 OS 了"**：小块进分配器空闲链表复用，RSS 不变是**正常且正确**的；只有大块（mmap 路径）和触发 trim 时机才归还。用 RSS 判断"free 有没有生效"会冤枉代码。
3. **"Python 没有内存问题，有 GC"**：GC 管引用回收，不管池归还（arena 保留）与 C 扩展的泄漏；`del` 之后 RSS 不降多半不是 bug，是池设计。判断泄漏要看对象层（tracemalloc），不是 RSS。
4. **"碎片和泄漏是一回事"**：碎片是"空了但没合并/没归还"，泄漏是"没空"。前者换分配器（jemalloc）或改分配模式可能解决，后者必须改代码——处置完全不同。
5. **"128KB 阈值是官方钦定的最优"**：它是 glibc 的默认值（历史经验值），glibc 自己还会动态调整它；把 mallopt 调优当玄学抄配置不如压测验证（**经验做法**）。

## 本篇小结

- malloc 是"库的仓库管理"叠在"内核的批发"（brk/mmap）上：小块用户态链表直达，≥128KB 直接 mmap；strace 一看便知两层边界。
- 分配策略 first-fit 快、best-fit 省，共同制造外部碎片；块内对齐与 header 制造内部碎片；合并与分桶是对抗碎片的两大武器。
- tcmalloc/jemalloc 的三板斧：线程缓存（无锁）、大小类（O(1)）、arena（NUMA 友好）；LD_PRELOAD 十分钟完成 A/B 验证（**经验做法**）。
- CPython 三层：pymalloc 池（≤512B）、C malloc（大对象）、arena 归还门槛高——"RSS 涨不回"多为池化行为；大对象直通 mmap 所以立还。
- 排查漏-碎之争：RSS 曲线 → smaps_rollup 分界 → C 用 valgrind/ASan、Python 用 tracemalloc diff；先定位层再选工具。
