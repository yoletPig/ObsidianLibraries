## 1. 综合解剖：观察一个 Python 训练进程

先造一个"像模像样"的训练进程（加载-训练-保存三阶段，不需要真实框架，纯标准库模拟）：

```python
# train_sim.py —— 模拟训练进程：加载(读大文件) → 训练(CPU+子进程) → 保存(写盘)
import os, time, sys, resource

def rss_kb():
    with open(f"/proc/{os.getpid()}/status") as f:          # 04 篇：读 VmRSS
        for line in f:
            if line.startswith("VmRSS"):
                return int(line.split()[1])

def log(tag):
    r = resource.getrusage(resource.RUSAGE_SELF)            # 05 篇：缺页计数
    print(f"[{time.strftime('%H:%M:%S')}] {tag:6} rss={rss_kb():7d}KB "
          f"minflt={r.ru_minflt:7d} majflt={r.ru_majflt:4d}", flush=True)

print(f"PID={os.getpid()}，3 秒后开始（趁现在去 top/strace 挂上观察）", flush=True)
time.sleep(3)

log("启动")
weights = bytearray(150 * 1024 * 1024)                       # ① 加载权重 150MB
for i in range(0, len(weights), 4096):
    weights[i] = i & 0xFF                                    # 触摸每页 → 按需调页
log("加载后")

for step in range(4):                                        # ② 训练：纯 CPU 循环
    t0 = time.perf_counter()
    acc = 0
    for i in range(0, len(weights), 1024):
        acc += weights[i]
    log(f"step{step} {time.perf_counter()-t0:.3f}s")

if "--fork" in sys.argv:                                     # ③ fork 一个子进程碰权重
    pid = os.fork()                                          # 02 篇：COW 复制
    if pid == 0:
        for i in range(0, len(weights), 4096):               # 子进程写 → 触发 COW 缺页
            weights[i] = 2
        os._exit(0)
    os.waitpid(pid, 0)
    log("fork+写后")

with open("/tmp/ckpt.bin", "wb") as f:                       # ④ 保存 checkpoint
    f.write(weights)
    f.flush(); os.fsync(f.fileno())                          # 08 篇：fsync 兑现持久性
log("保存后")
```

观察流程分四步走（**经验做法**：先看账本再下结论，每一步都对应前文的一个概念）：

```bash
$ python3 train_sim.py --fork
PID=25301，3 秒后开始（趁现在去 top/strace 挂上观察）
[10:00:03] 启动   rss=  11232KB minflt=   4123 majflt=   0
[10:00:04] 加载后 rss=163404KB minflt=  40778 majflt=   0   ← 150MB 匿名内存：写一页分配一页
[10:00:06] step0 0.142s rss=163404KB minflt=  40782 ...
[10:00:09] fork+写后 rss=313572KB minflt=  81771             ← COW 触发：子进程写，父进程 RSS 涨
[10:00:10] 保存后 rss=313572KB ...                            ← fsync 不涨 RSS，涨的是磁盘
```

对照观察工具箱（每个命令的原理都在前文）：

```bash
$ strace -c -f python3 train_sim.py          # ① 系统调用账单：openat/mmap/write/fork/clone 各多少次
$ ps -o pid,rss,vsz,stat,wchan:20 -p <PID>   # ② 状态与等待点（wchan：睡在哪个内核函数）
$ cat /proc/<PID>/status | grep -E "VmRSS|Threads|voluntary"   # ③ 内存/线程/切换计数
$ top -p <PID>                               # ④ CPU 与 RES 的实时形状
$ cat /proc/<PID>/smaps_rollup               # ⑤ 内存构成：Anonymous(权重) vs Shared(库)
```

读数要点（把这五条练成条件反射）：**minflt 大涨 = 分配/换页活动**（加载后 +3.6 万次缺页，全是"写一页分配一页"的 minor）；**fork 后 RSS 涨一倍 = COW 触发**（子进程写页时复制，父进程看的 RSS 含共享页——严格说此时两进程各持一半页，`smaps_rollup` 的 Rss 求和会大于物理总量，这是共享页会计的经典坑）；**majflt=0 = 文件都在 page cache**；CPU 时间应≈纯循环时间，若明显大于，查缺页与调度（voluntary_ctxt_switches 列）。

## 2. 实验：fork 的真实开销

02 篇说"COW 让 fork 便宜"，现在量化。测三个东西：fork 一个 150MB 进程的成本、fork+exec 的成本、以及"父进程内存越大 fork 越慢吗"：

```python
# fork_cost.py —— 用进程自身测 fork/fork+exec 开销
import os, time, subprocess, sys

blob = bytearray(int(sys.argv[1]) * 1024 * 1024) if len(sys.argv) > 1 else bytearray(0)
for i in range(0, len(blob), 4096): blob[i] = 1        # 触摸：确保真实分配

N = 200
t0 = time.perf_counter()
for _ in range(N):
    pid = os.fork()                                    # 纯 fork：COW 复制页表
    if pid == 0:
        os._exit(0)                                    # 子进程立刻退出
    os.waitpid(pid, 0)
t1 = time.perf_counter() - t0
print(f"父进程RSS={os.stat('/proc/self/statm').st_size and ''}"
      f"纯fork: {t1/N*1e3:.3f} ms/次")

t0 = time.perf_counter()
for _ in range(N):
    subprocess.run(["/bin/true"], check=False)         # fork + exec + 回收
t1 = time.perf_counter() - t0
print(f"fork+exec(/bin/true): {t1/N*1e3:.3f} ms/次")
```

```
$ python3 fork_cost.py 150
纯fork: 0.812 ms/次                  ← 150MB 进程：复制页表而已（几万条 PTE）
fork+exec(/bin/true): 2.945 ms/次    ← 多了：execve 重建地址空间 + 加载器 + 动态链接（01 篇）
$ python3 fork_cost.py 800           # 把父进程换成 800MB 再测
纯fork: 3.966 ms/次                  ← 页表按内存大小线性增长（多级页表条目更多）
```

结论三连：fork 是**毫秒级**（不是纳秒级）、成本与父进程内存**正相关**（复制页表）、fork+exec 比 fork 贵 3~4 倍（地址空间重建 + 动态链接）。工程落点：高频起子进程的服务（每个请求 fork 一个 worker）在 10ms 延迟预算里 3ms 交给 fork+exec 不可接受——用进程池（预先 fork）或线程；数据加载器（PyTorch DataLoader num_workers）每个 epoch 不重建 worker 也是这个原因。**经验做法**：`strace -c` 里 clone 出现频率高，先问"能不能池化"。

## 3. 实验：观察缺页的发生现场

05 篇讲了缺页的类型，这里看"发生的那一瞬"：用 `/proc/pid/pagemap` 不可行（WSL2 权限），改用两个可复现的视角——minflt 时间线 + mmap 文件映射的 major fault 制造（先清缓存让文件出内存，需 root 且**只对 /tmp 小文件做**）：

```python
# fault_timeline.py —— 每秒打印缺页计数，观察"哪一步在缺页"
import os, time, resource, mmap

def faults():
    r = resource.getrusage(resource.RUSAGE_SELF)
    return r.ru_minflt, r.ru_majflt

m0, M0 = faults()
data = bytearray(64 * 1024 * 1024)          # 64MB 匿名内存
m1, _ = faults()
print(f"分配64MB后     minflt +{m1-m0}")    # 预期 0：还没写！
for i in range(0, len(data), 4096):
    data[i] = 1                             # 逐页写
m2, _ = faults()
print(f"逐页写后       minflt +{m2-m1}")    # 预期 ≈ 16K：每页一次（零页升级）
del data
f = open("/tmp/bigfile", "rb")              # 04/05 篇造的 200MB 文件
mm = mmap.mmap(f.fileno(), 0, prot=mmap.PROT_READ)
m3, M3 = faults()
mm[::4096].count(b"")                       # 逐页摸文件映射
m4, M4 = faults()
print(f"mmap逐页摸后   minflt +{m4-m3}  majflt +{M4-M3}")   # minor（cache命中）
```

```
$ python3 fault_timeline.py
分配64MB后     minflt +0
逐页写后       minflt +16384            ← 64MB/4KB = 16384 页，一次不多一次不少
mmap逐页摸后   minflt +51200  majflt +0  ← 文件页在 cache：minor；清 cache 后 majflt 会显形
```

三个数对上三课：**分配不等于分配落地**（bytearray(64MB) 零缺页——虚拟内存只是登记，04 篇误区 2 的实证）；**写才触发**（16384 次缺页 = 按需调页把零页换成真页）；**mmap 的访问是缺页驱动**（每次首次访问一页 = 一次 minor，这就是"mmap 读大文件首遍慢、二遍快"的机制）。观察生产进程：`pidstat -r -p PID 1` 的 majflt/s 列持续 >10 就该查内存压力（05 篇工作集）。

## 4. 实验：GIL 与线程调度（ps -T）

02 篇说"GIL 下 CPU 密集线程不并行"，10 篇说"线程是调度单位"。合起来实测：4 个纯 CPU 线程 vs 4 个进程，看 CPU 时间去向与线程的调度形态：

```python
# gil_demo.py —— GIL 实测：4 线程 vs 4 进程的墙钟时间与 CPU 时间
import threading, multiprocessing, time, os, resource

def burn(n=8_000_000):
    x = 0
    for i in range(n): x += i * i            # 纯 Python 计算：吃 GIL

def run_threads():
    ts = [threading.Thread(target=burn) for _ in range(4)]
    t0 = time.perf_counter()
    [t.start() for t in ts]; [t.join() for t in ts]
    return time.perf_counter() - t0

def run_procs():
    ps = [multiprocessing.Process(target=burn) for _ in range(4)]
    t0 = time.perf_counter()
    [p.start() for p in ps]; [p.join() for p in ps]
    return time.perf_counter() - t0

if __name__ == "__main__":
    burn()                                    # 预热
    single = time.perf_counter(); burn(); single = time.perf_counter() - single
    print(f"单线程基准: {single:.2f}s")
    print(f"4 线程(GIL): {run_threads():.2f}s   ← 没变快（甚至更慢：GIL 竞争开销）")
    print(f"4 进程    : {run_procs():.2f}s   ← 接近 4 倍加速（真并行）")
```

```
$ python3 gil_demo.py
单线程基准: 0.42s
4 线程(GIL): 1.85s   ← 没变快（甚至更慢：GIL 竞争开销）
4 进程    : 0.49s    ← 接近 4 倍加速（真并行）
```

用 OS 工具看线程的调度形态（`ps -T`：每线程一行，02 篇的 SPID）：

```bash
$ python3 -c "import threading,time; [threading.Thread(target=lambda: time.sleep(30)).start() for _ in range(4)]; time.sleep(30)" &
$ ps -T -p $(pgrep -f 'time.sleep(30)') -o spid,stat,pcpu,comm
   SPID STAT %CPU COMMAND
  25404 Ssl   0.0 python3
  25405 S     0.0 python3        ← 5 个线程全部 S（睡眠）：sleep 不占 CPU
  25406 S     0.0 python3
$ cat /proc/<pid>/status | grep -E "Threads|voluntary|nonvoluntary"
Threads:  5
voluntary_ctxt_switches:  3120       ← GIL 让出/等待引发的自愿切换
nonvoluntary_ctxt_switches: 15       ← 时间片用尽的非自愿切换
```

两个可迁移的判读经验（**经验做法**）：**voluntary 高 = 在等东西**（GIL/IO/锁——推理服务的典型形态，正常）；**nonvoluntary 高 = CPU 抢不到**（线程数超核数或优先级低——该减线程或调 nice，03/07 篇）。看 Python 进程在干嘛的另一条路是 py-spy（采样 profiler，直接读线程栈，不需要插桩）——OS 层面它是把 /proc/pid/task 的线程逐个 ptrace，本质还是本系列的工具。

## 5. 实验：容器资源限制下的训练进程

13 篇的 cgroup 实验在"训练任务"上走一遍完整闭环（docker 可用则一条命令，cgroup 原生则三行文件）：

```bash
$ docker run --rm --cpus=0.5 --memory=300m python:3.11-slim \

t0 = time.perf_counter(); x = 0
for i in range(30_000_000): x += i
print(f'{time.perf_counter()-t0:.2f}s')"  ← 同样的循环，0.5 核下时间约翻倍
2.86s                                     ← throttle：不是被杀，是被扣速
```

```bash
# 方式二：原生 cgroup v2（无 docker 也行，13 篇的步骤）
$ sudo mkdir /sys/fs/cgroup/train
$ echo "+cpu +memory" | sudo tee /sys/fs/cgroup/train/cgroup.subtree_control
$ echo "100000 50000" | sudo tee /sys/fs/cgroup/train/cpu.max
$ echo "300M"          | sudo tee /sys/fs/cgroup/train/memory.max
$ echo $$ | sudo tee /sys/fs/cgroup/train/cgroup.procs   # 把当前 shell 放进去（注意：整个 shell 都受限）
$ python3 train_sim.py                                     # 观察各阶段变慢与 OOM 风险
```

读数与迁移（**经验做法**）：训练/推理任务入容器前先测**真实工作集**（05 篇：RSS 峰值 + 20% 余量），memory.max 给少了 OOM 杀训练（半天白跑），给多了浪费配额；CPU 配额低于核数会拉长墙钟时间但不影响正确性（throttle 是慢不是错）；显存限制不在 cgroup 管辖（cgroup 管不了 GPU），CUDA 侧要用 MPS/时间片或 MIG——这是容器跑 GPU 的特殊一章（模型性能优化 Stage 7 的部署实践与此衔接）。

## 常见误区

1. **"观察工具链要装很多组件"**：strace/ps/top//proc/pidstat 全在最小 Ubuntu 里；perf/py-spy 是增强不是门槛。先把 /proc 读熟，比任何监控面板都接近真相。
2. **"RSS 涨 = 泄漏"**：06 篇的池化、05 篇的 page cache、04 篇的 VIRT 增长都会伪装成泄漏；先用 smaps_rollup 分层再定罪。
3. **"minflt 大 = 出问题了"**：分配型 minor 是正常机制（本章第 1 节加载权重 +3.6 万次）；只有 majflt 或缺页伴随 CPU 空转（抖动）才是警报。
4. **"容器里测的性能 = 宿主机性能"**：throttle、CPU 配额、cgroup 内存压力都会改写结果；压测前先 `cat /sys/fs/cgroup/cpu.max` 确认自己戴了几道枷锁（13 篇）。
5. **"OS 知识面试完就没用了"**：本章五组实验就是日常：训练慢先看 CPU 形态（调度）、内存涨先看缺页与分配器、服务抖先看 IO 状态（D 状态）、部署挂先看 cgroup 配额——OS 是生产排障的第一现场。

## 本篇小结

- 一套"OS 眼睛"流程：strace 看系统调用账单 → /proc/status 看 RSS/线程/切换 → smaps_rollup 看内存构成 → pidstat 看缺页与切换速率 → cgroup 看配额枷锁；每一步对应前文一个概念。
- fork 实测：纯 fork 毫秒级且随父进程内存线性涨（页表复制），fork+exec 贵 3~4 倍（动态链接）；高频起进程要池化。
- 缺页实测：分配零缺页、写才触发（16384 页一次不差）、mmap 访问缺页驱动；majflt 持续 >10/s 是内存压力指纹。
- GIL 实测：4 线程不快反慢（GIL 竞争）、4 进程真并行；voluntary 切换高 = 在等，nonvoluntary 高 = 抢不到——ps -T 与 ctxt_switches 是线程体检表。
- 容器实验闭环：CPU 超限 throttle（慢）、内存超限 OOM（死）；训练入容器先量工作集再定 memory.max；GPU 不归 cgroup 管。
- 30 题清单覆盖进程/内存/中断/并发/网络五域；答题心法 = 本质 + 机制 + 项目场景。
