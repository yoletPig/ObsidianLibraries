## 1. 页表与多级页表：为什么 48 位要四级

第 04 篇说"MMU 查页表把虚拟页号换成物理帧号"。单级页表的账很吓人：x86-64 常用 48 位虚拟地址、4KB 页 → 页内偏移 12 位、页号 36 位 → 每个进程的页表要 2^36 个 PTE；PTE 8 字节 → **每进程 512GB 页表**。比物理内存本身还大，显然不能这么存。

多级页表的解法：**把页号切段，逐级索引，没有用到的高位部分整棵子树不建**（OSTEP 第 20 章《Smaller Page Tables》；CSAPP 第 9.3 节用 32 位例子推演同一思想）。x86-64 Linux 标准四级（新内核支持五级 la57）：

```
48 位虚拟地址：[47:39] [38:30] [29:21] [20:12] [11:0]
                 PGD     PUD     PMD     PTE   页内偏移
                  9bit    9bit    9bit    9bit   12bit
                  │       │       │       │
 CR3 ─► PGD表(512项) ► PUD表 ► PMD表 ► PTE表 ─► 物理帧号 + 偏移
```

每级表恰好 512 项 × 8 字节 = 4KB，正好占一个页框，方便分配和回收。省内存的关键：**大多数进程根本用不满 47 位空间**——堆、栈、库中间都是大空洞，页表只需覆盖实际映射的区域，空洞部分各级表项直接为空、不建下级表。一个只映射 100MB 的进程，页表总量是几十 KB 量级，而不是 512GB。**代价**：一次访存最多查 4 次表（内存里），TLB 的价值因此更大（04 篇的账在这里兑现）。

Linux 给每个进程一套独立页表（`task_struct` 里的 `mm->pgd`，02 篇档案表的 mm 栏）；上下文切换时换 CR3 寄存器指向新进程的页表根——这也是进程切换比线程切换贵的根本原因：**换 CR3 后 TLB 大量失效**（内核用 PCID/ASID 技巧缓解，07 篇讲切换成本时回收这个话题）。

## 2. 页面置换算法：FIFO / LRU / Clock

物理内存满了、还要调页进来，就有人要被换出去（或直接丢弃干净页）。算法只关心一件事：**猜谁不会再被用**（OSTEP 第 22 章《Beyond Physical Memory: Policies》）。用 Python 写一个统一的模拟器，输入访问序列，输出缺页次数：

```python
# paging_sim.py —— FIFO / LRU / Clock(二次机会) 页面置换模拟器
def simulate(policy, refs, frames):
    """refs: 页访问序列; frames: 页框数; 返回 (缺页次数, 每步是否缺页)"""
    mem, faults, trace = [], 0, []
    if policy == "FIFO":                          # 先进先出：只记到来顺序
        from collections import deque
        order = deque()
        for r in refs:
            if r not in mem:
                faults += 1; trace.append(1)
                if len(mem) == frames:
                    old = order.popleft(); mem.remove(old)
                mem.append(r); order.append(r)
            else: trace.append(0)
    elif policy == "LRU":                         # 最久未使用：按最近访问时间淘汰
        last = {}
        for t, r in enumerate(refs):
            if r not in mem:
                faults += 1; trace.append(1)
                if len(mem) == frames:
                    victim = min(mem, key=lambda p: last[p])
                    mem.remove(victim)
                mem.append(r)
            else: trace.append(0)
            last[r] = t
    elif policy == "CLOCK":                       # 二次机会：近似 LRU，只多用 1 个引用位
        refbit, hand = {}, 0
        for r in refs:
            if r in mem:
                refbit[r] = 1; trace.append(0); continue
            faults += 1; trace.append(1)
            if len(mem) == frames:
                while refbit[mem[hand]] == 1:     # 扫描：引用位 1 → 清零跳过
                    refbit[mem[hand]] = 0
                    hand = (hand + 1) % frames
                victim = mem[hand]                # 指针停下的第一个 0 页被淘汰
                mem[hand] = r
                hand = (hand + 1) % frames
            else:
                mem.append(r)
            refbit[r] = 0
    return faults, trace

if __name__ == "__main__":
    refs = [1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5]   # 经典 Belady 序列
    for f in (3, 4):
        row = [f"{p}: {simulate(p, refs, f)[0]:2d} 次缺页" for p in ("FIFO", "LRU", "CLOCK")]
        print(f"页框={f}  " + "   ".join(row))
```

```
$ python3 paging_sim.py
页框=3  FIFO:  9 次缺页   LRU: 10 次缺页   CLOCK: 10 次缺页
页框=4  FIFO: 10 次缺页   LRU:  8 次缺页   CLOCK:  8 次缺页
```

三个必读结论：

- **FIFO 的 Belady 异常**：页框从 3 加到 4，缺页反而从 9 升到 10（这就是上面的经典序列，OSTEP 第 22 章引用的 Belady 1966 实验）。FIFO 与"程序将来用不用"毫无关联，加内存都可能更糟——面试常客。
- **LRU 看过去猜未来**："很久没用 ⇒ 大概不会再用"，对局部性敏感的负载效果好；理论最优是"淘汰将来最久不用"的 OPT 算法（需要预知未来，仅作标尺，OSTEP 第 22 章用它给所有实际算法定上限）。
- **Clock 是 LRU 的工程替身**：真硬件不提供"访问时间戳"，只提供 PTE 里的一个引用位（访问置 1）。Clock/二次机会用"引用位 0 就淘汰、1 就清零再给一次机会"模拟 LRU，成本 O(1) 摊还。**Linux 实际用的 active/inactive 双链表 + 引用位，思想同源**（LKD 第 16 章《The Page Cache and Page Writeback》；近年多代 LRU gen LRU 是其演进）。**经验做法**：面试答"页面置换"时先讲 LRU 原理，再补一句"硬件只有引用位，所以实际系统都是 Clock 近似"，立刻显出工程味。

## 3. 缺页率与工作集：Belady 之外的故事

**工作集（working set）**：进程在时间窗 T 内实际访问的页的集合（Denning 1968 的经典模型，OSTEP 第 23 章的 locality 引用）。它决定缺页率曲线的形状：

```
缺页率
  │＼
  │  ＼
  │    ＼___                          ← 分配页数 >> 工作集：缺页率≈0，再多给也没用
  │        ＼＼
  │           ＼＿ 崖壁区              ← 分配页数 ≈ 工作集：抖动（thrashing）
  │                ＼                  系统忙于换页，CPU 几乎不干活
  └──────────────────────► 分配给进程的页数
```

这解释了两个日常现象：**内存刚好不够时性能不是线性下降而是断崖**（工作集装不下，狂换页）；**CPU 利用率突然掉到近零、磁盘 IO 打满**是抖动的指纹（`vmstat` 看 `si/so` 列持续非零、`%idle` 高——**经验做法**：先查抖动再查代码）。推理服务的镜像知识：KV cache 的显存工作集超过显存就会疯狂换页（Stage 3 的统一内存实验就是这个曲线）。

## 4. Linux 的内存回收：swappiness 与 OOM killer（实测）

Linux 的内存压力反应链（LKD 第 12、16 章；`man proc` 的 /proc/sys/vm 节）：

```
内存紧张
  → 1. 回收 page cache（干净页直接丢，脏页写回）     ← 无感知
  → 2. 按 swappiness 权衡：回收匿名页（换出到 swap） vs 文件页
  → 3. 还不够 → 触发 OOM killer：挑"最该死"的进程杀之
```

**swappiness**（0~100，默认 60）：数值越大越倾向把匿名页换出到 swap，越小越倾向保留匿名页、只回收文件页。实测：

```bash
$ cat /proc/sys/vm/swappiness
60
$ sudo sysctl vm.swappiness=10        # 常见调法：服务器少换页
vm.swappiness = 10
$ free -h
              total        used        free      shared  buff/cache   available
Mem:           15Gi       3.1Gi       1.2Gi       384Mi        11Gi        12Gi
Swap:         2.0Gi          0B       2.0Gi          ← WSL2 默认也给 swap（.wslconfig 可调）
```

经验定位（**经验做法**）：数据库/推理服务这类"匿名页就是命根子"的负载调低（10 左右）；桌面/大 cache 场景保持默认。看现场的三件套：`free -h`（available 才是"还能分多少"）、`vmstat 1`（si/so 换页流量）、`ps -eo pid,rss,comm --sort=-rss | head`（谁在吃）。

**OOM killer**：所有路都走不通时的最后一刀。选择标准是 oom_score（`/proc/PID/oom_score`，约等于 badness：占用大 + 不重要者优先，可手工调 `/proc/PID/oom_score_adj` ±1000 免死/必死）。被杀进程的死状是 `Killed`（信号 9, SIGKILL——10 篇讲信号时回收），dmesg 留下完整案发现场：

```
$ dmesg | grep -i "killed process" | tail -2
[86210.441] Out of memory: Killed process 24311 (python3) total-vm:9134204kB,
anon-rss:8204112kB, file-rss:2048kB, shmem-rss:0kB, UID:1000 pgtables:16892kB
oom_score_adj:0
```

读这条日志的方法：`anon-rss` 是它自己的匿名内存（真凶），`total-vm` 是虚拟地址空间（大不一定是罪），`oom_score_adj:0` 是没做保护。**经验做法**：跑大模型推理前，给关键进程设 `echo -500 > /proc/$$/oom_score_adj` 保命，并确保监控里盯 available 内存而不是 free（cache 占的 free 是健康不是病）。**WSL2 注**：WSL2 的内存上限在 `.wslconfig` 的 `memory=` 配置；超限表现是 VM 内 OOM killer 动手或 Windows 侧报错，dmesg 同样可查。

## 5. mmap：文件映射与匿名映射

mmap 把"一段虚拟地址"和"一个文件（或一块匿名内存）"接起来（`man 2 mmap`；OSTEP 第 23 章的 mmap I/O 一节）。第一次访问那页地址才真正分配/读入（demand paging），major/minor fault 由内核悄悄处理。两种用法一张表：

| | 文件映射 | 匿名映射（MAP_ANONYMOUS） |
| --- | --- | --- |
| 后备 | 磁盘上的文件 | 无（swap/物理内存） |
| 典型用途 | 读模型权重、共享库、共享内存文件 | malloc 大块、线程栈、CUDA host pinned 类比 |
| 优点 | 免 read 拷贝、页 cache 直接共享、按需调入 | 惰性分配、大块不占堆 |
| 缺点 | 缺页开销在访问路径上（抖动敏感） | 仍受物理内存约束 |

```c
// mmap_demo.c —— 文件映射读大文件：逐页访问，观察 major/minor 缺页
// 编译：gcc mmap_demo.c -o mmap_demo
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/mman.h>
#include <sys/stat.h>

int main(void) {
    const char *path = "/tmp/bigfile";           // 04 篇练习造的 200MB 文件
    int fd = open(path, O_RDONLY);
    struct stat st; fstat(fd, &st);

    char *p = mmap(NULL, st.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }

    volatile long sum = 0;                        // volatile 防止编译器把读优化掉
    for (size_t i = 0; i < st.st_size; i += 4096) // 每页读 1 字节 → 每页一次缺页
        sum += p[i];

    printf("sum=%ld\n", sum);
    munmap(p, st.st_size); close(fd);
    return 0;
}
```

```bash
$ /usr/bin/time -v ./mmap_demo 2>&1 | grep -E "Minor|Major|Maximum resident"
        Minor (reclaiming a frame) page faults: 20489    ← 每页一次 minor（页在 cache）
        Major (requiring I/O) page faults:     0         ← 文件已在 page cache 里
        Maximum resident set size (kbytes):    4816     ← 程序自己只用了 4.8MB！
```

最后那行是 mmap 的灵魂：**RSS 只有几 MB，却"读"完了 200MB**——数据住在 page cache，通过映射直接访问，`read()` 那种"从内核拷到用户缓冲区"的复制整个消失了（零拷贝视角，10 篇 IPC 对比时会再次用到）。llama.cpp 默认 `mmap` 加载 GGUF 权重、多进程共享同一份模型页，正是这个机制的直接应用（Stage 4 对接）。什么时候不用 mmap：随机访问小文件（read 更简单）、需要稳定延迟的实时路径（缺页抖动不可控）。

## 常见误区

1. **"swap 关了就万事大吉"**：关 swap 后内存回收只剩 page cache 一条路，匿名页一旦分配就钉死，OOM 更早到来；swappiness=0 也不是"不换页"，而是"万不得已才换"（语义见内核文档 Documentation/admin-guide/sysctl/vm.rst）。
2. **"free 显示 free 很少 = 内存不够"**：Linux 把空闲内存拿去当 page cache，free 少是设计使然；看 available 列。**这条是新手性能误判第一名**。
3. **"LRU 是 Linux 的页面置换算法"**：LRU 是思想，Linux 用双链表(active/inactive)+引用位的近似实现，从未真做过 O(n) 时间戳扫描；面试时答"近似 LRU"才准确。
4. **"mmap 一定比 read 快"**：顺序读一次的场景 read 走预读（readahead）可能更稳；mmap 的优势在重复访问、共享、零拷贝场景。**经验做法**：大文件反复读用 mmap，一次性顺序读 read 足够。
5. **"OOM killer 杀内存最大的进程"**：粗略如此，但实际按 oom_badness 综合评分（RSS 换算 + oom_score_adj 调整），大 RSS 但 adj=-500 的进程可以豁免。生产服务必须主动设置保护而不是赌评分。

## 本篇小结

- 多级页表用"稀疏不建子树"把每进程页表从 512GB 压到几十 KB 级；代价是 TLB miss 的查表次数增加——内存账与性能账永远一起算。
- 置换算法的谱系：FIFO（Belady 异常）→ LRU（局部性好但硬件不友好）→ Clock/引用位近似；Linux 用 active/inactive 双链表落地，gen LRU 是现代演进。
- 工作集决定缺页率曲线：内存恰好不足时是断崖不是斜坡；`vmstat` 的 si/so + 低 CPU 是抖动指纹。
- 内存压力反应链：回收 cache → swap → OOM killer；free 看 available、OOM 现场 dmesg 找 anon-rss、关键进程设 oom_score_adj 保命（**经验做法**）。
- mmap 文件映射 = 零拷贝 + 页级共享（llama.cpp 加载权重的原理）；匿名映射 = 大块惰性分配（malloc 大对象的后台）。
