## 1. 管道：匿名与命名

**匿名管道**是 shell 里竖线的实体（`man 2 pipe`）：一个单向字节流，带两个 fd——`pipefd[0]` 读端、`pipefd[1]` 写端。它的亲缘限制是刻在创建方式里的：由父进程 pipe() 创建后经 fork 继承，**没有亲缘关系的进程拿不到它**。看 shell 怎么把 `ls | grep os` 接起来：

```c
// pipe_shell.c —— 手工实现 ls | grep os：pipe + fork ×2 + dup2
// 编译：gcc pipe_shell.c -o pipe_shell && ./pipe_shell
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    int p[2];
    if (pipe(p) < 0) { perror("pipe"); return 1; }   // p[0] 读端, p[1] 写端

    pid_t c1 = fork();
    if (c1 == 0) {                    // 左命令 ls
        dup2(p[1], STDOUT_FILENO);    // 把 stdout 接到管道写端（覆盖 fd 1）
        close(p[0]); close(p[1]);     // 多余的原始 fd 关掉
        execlp("ls", "ls", (char *)NULL);
    }
    pid_t c2 = fork();
    if (c2 == 0) {                    // 右命令 grep os
        dup2(p[0], STDIN_FILENO);     // 把 stdin 接到管道读端
        close(p[0]); close(p[1]);
        execlp("grep", "grep", "os", (char *)NULL);
    }
    close(p[0]); close(p[1]);         // 父进程两边都不用，必须关！
    waitpid(c1, NULL, 0); waitpid(c2, NULL, 0);
    return 0;
}
```

```
$ ./pipe_shell | head -4
操作系统.md
process.md
pytorch.md
queue.md
```

（本目录恰好有这些文件名含 os 的文件。）图示数据流与两个易错点：

```
   ls ──stdout──► [管道内核缓冲 64KB] ──stdin──► grep
                  ▲
   陷阱1: 父进程不关 p[0]/p[1] → grep 永远等不到 EOF（写端还有人）
   陷阱2: 缓冲区满(64KB)时写端阻塞 → 两端不读完会互相卡死（死锁形状）
```

**命名管道（FIFO）**（`man 3 mkfifo`）突破亲缘限制：mkfifo 在文件系统里立一个特殊文件，任何进程按文件名 open 它。实测：

```bash
$ mkfifo /tmp/myfifo
$ echo "通过fifo" > /tmp/myfifo &     # 写端（阻塞直到有读者）
$ cat /tmp/myfifo                     # 读端
通过fifo
$ ls -l /tmp/myfifo
prw-r--r-- 1 yyl yyl 0 ... /tmp/myfifo    ← p 开头：FIFO 文件
```

管道的本质限制：**字节流、无消息边界**（两条 echo 可能被一次 cat 读出——08 篇的"字节流无结构"在 IPC 里的镜像）、单向、缓冲有限。工程用法（**经验做法**）：进程间"触发/通知/日志接力"用管道顺手；要传结构化消息请看第 3、4 节。

## 2. 信号：kill -l、处理函数、可重入陷阱

**信号（signal）是内核发给进程的异步通知**（`man 7 signal`）：软件中断（07 篇的"打断"家族在进程层面的投影）。发信人可以是内核（段错误→SIGSEGV、Ctrl-C→SIGINT、子进程退出→SIGCHLD）、也可以是别的进程（kill 命令）。信号生命周期三步：**产生（pending）→ 阻塞（block，挂着不递送）→ 递送（deliver，执行默认动作或处理函数）**。

先看全景：

```bash
$ kill -l
 1) SIGHUP	 2) SIGINT	 3) SIGQUIT	 4) SIGILL	 5) SIGTRAP
 6) SIGABRT	 7) SIGBUS	 8) SIGFPE	 9) SIGKILL	10) SIGUSR1
...
15) SIGTERM	17) SIGCHLD	...
```

必须认识的六个：SIGKILL(9)/SIGSTOP **不可捕获不可忽略**（内核保留的最终手段）；SIGTERM(15)"请你退出"（kill 默认发它，优雅退出靠捕获它做清理）；SIGINT(2) Ctrl-C；SIGCHLD(17) 子进程退出（02 篇收尸的正牌触发器）；SIGSEGV(11) 段错误。进程对大多数信号可选三种处置：默认动作、忽略、或注册处理函数（`sigaction`，`man 2 sigaction`——比老的 signal() 可靠）：

```c
// signal_demo.c —— 优雅退出：捕获 SIGTERM/SIGINT 做清理
// 编译：gcc signal_demo.c -o signal_demo && ./signal_demo &
#include <stdio.h>
#include <signal.h>
#include <unistd.h>
#include <string.h>

static volatile sig_atomic_t stop_flag = 0;   // 关键：sig_atomic_t + volatile

void on_term(int sig) {                        // 处理函数：能做的事极少
    stop_flag = 1;                             // 只设置标志，不做 IO/加锁/ malloc
    write(STDOUT_FILENO, "收到退出信号，清理中...\n", 26);  // write 是异步信号安全的
}

int main(void) {
    struct sigaction sa = {0};
    sa.sa_handler = on_term;
    sigemptyset(&sa.sa_mask);
    sigaction(SIGTERM, &sa, NULL);
    sigaction(SIGINT, &sa, NULL);
    while (!stop_flag)
        pause();                               // 睡着等信号
    printf("正常退出（这里放关闭连接/落盘等清理）\n");
    return 0;
}
```

```bash
$ gcc signal_demo.c -o signal_demo && ./signal_demo &
$ kill -TERM %1
收到退出信号，清理中...
正常退出（这里放关闭连接/落盘等清理）
$ kill -9 <另一个程序的pid>     # SIGKILL：无法捕获，进程当场消失，清理代码没机会跑
```

**可重入陷阱**是本节的深水区：处理函数可能在**任意一条指令之间**插入主程序（比如主程序正在 malloc 到一半），所以处理函数里调用 malloc/printf/锁都可能撞上"函数没跑完就被自己再次进入"——不可重入。规则（`man 7 signal-safety`，POSIX 列出了异步信号安全函数白名单）：

- 处理函数里**只允许**：设置 `volatile sig_atomic_t` 标志、调用白名单函数（write、_exit 等）；
- 复杂清理全部放到主循环里根据标志执行（上面代码的结构正是"标志 + 主循环"模式）；
- Python 的信号处理是同一个问题的温柔版：CPython 把 Python 级 handler 排队到主线程的字节码间隙执行，所以 handler 里可以写 Python，但**只有主线程收信号**且可能延迟到下一个字节码——信号安全在两种语言里都要刻意设计。

**经验做法**：推理服务/Agent 进程必须捕获 SIGTERM 做"断开新请求、排空旧请求、落盘状态"的优雅退出——K8s 滚动更新发的是 SIGTERM，你的清理代码只有 `terminationGracePeriodSeconds` 的宽限；赌 SIGKILL 会给你几毫秒的人，都会在下次 OOM 时丢数据。

## 3. 消息队列、共享内存、信号量：三种 System V IPC

`ipcs` 命令背后的一族机制（`man 7 sysvipc`）。先各自 30 秒画像，再用一道拷贝账本对比：

**消息队列**：内核维护的消息链表，收发按消息（有类型/边界）：

```c
// mq_demo.c —— System V 消息队列（实际项目多用 POSIX mq_open，思想相同）
// 编译：gcc mq_demo.c -o mq_demo
#include <stdio.h>
#include <string.h>
#include <sys/ipc.h>
#include <sys/msg.h>

struct msgbuf { long mtype; char text[64]; };   // mtype 是消息类型（优先级用）

int main(void) {
    key_t key = ftok("/tmp", 'A');              // 路径+字符 → 生成 key
    int qid = msgget(key, IPC_CREAT | 0666);
    struct msgbuf m = {1, "hello from queue"};
    msgsnd(qid, &m, strlen(m.text) + 1, 0);     // 发送（拷贝进内核）
    struct msgbuf r;
    msgrcv(qid, &r, sizeof(r.text), 1, 0);      // 接收（拷贝出内核）
    printf("收到: %s\n", r.text);
    msgctl(qid, IPC_RMID, NULL);                // 删除队列
    return 0;
}
```

**共享内存 + 信号量**：最快的一条路。shmget 申请一块物理内存映射进**多个进程的地址空间**，读写就是普通指针访问——零拷贝。但"同一时刻谁能写"没人管，必须配信号量（semget）做互斥/计数：

```c
// shm_demo.c —— 共享内存 + 信号量：写进程与读进程共享一块内存
// 编译：gcc shm_demo.c -o shm_demo
#include <stdio.h>
#include <string.h>
#include <sys/ipc.h>
#include <sys/shm.h>
#include <sys/sem.h>
#include <unistd.h>
#include <sys/wait.h>

union semun { int val; };
static void sem_op(int id, int val) {          // P(-1)/V(+1) 一步封装
    struct sembuf sb = { .sem_num = 0, .sem_op = val };
    semop(id, &sb, 1);
}

int main(void) {
    key_t key = ftok("/tmp", 'B');
    int shmid = shmget(key, 4096, IPC_CREAT | 0666);
    char *shm = shmat(shmid, NULL, 0);          // 映射进本进程地址空间
    int semid = semget(key, 1, IPC_CREAT | 0666);
    semctl(semid, 0, SETVAL, (union semun){.val = 0});   // 初始 0：无数据可读

    if (fork() == 0) {                          // 子进程：读者
        sem_op(semid, -1);                      // P：等"数据就绪"
        printf("读者收到: %s\n", shm);
        return 0;
    }
    strcpy(shm, "zero-copy data via shm");      // 父进程：写者，直接写内存
    sem_op(semid, +1);                          // V：通知读者
    wait(NULL);
    shmdt(shm); shmctl(shmid, IPC_RMID, NULL); semctl(semid, 0, IPC_RMID);
    return 0;
}
```

```
$ gcc shm_demo.c -o shm_demo && ./shm_demo
读者收到: zero-copy data via shm
```

现在算那笔拷贝账（这是"为什么共享内存最快"的定量答案，管道/队列每走一次要 2 次内核↔用户拷贝）：

```
管道/消息队列:  写进程 → 拷贝1 → 内核缓冲 → 拷贝2 → 读进程     （2 次拷贝 + 2 次系统调用）
共享内存:       写进程 ──同一段物理内存──► 读进程              （0 次拷贝 + 0 次系统调用）
```

```
$ ipcs -m        ← 实测查看系统中活着的共享内存段
------ Shared Memory Segments --------
key        shmid      owner      perms      bytes      nattch     status
```

（大模型推理的镜像知识：多进程共享模型权重、KV cache 传输、CUDA 的 IPC 显存句柄，全是"共享内存+同步原语"思想的硬件版；Python 的 `multiprocessing.shared_memory` 是 System V 的现代封装。）代价也要认清：共享内存**没有任何边界和同步**，布局、同步、生命周期全靠用户自己——最快 = 最不省心。**经验做法**：大数据高频传输用共享内存，控制/通知用信号量或小消息队列，"数据走快车道、信令走可靠车道"是标准分工。

## 4. socket 本地通信：AF_UNIX

socket 家族不止是网络工具（12 篇专题）：`AF_UNIX`（本地）socket 在同一台机器上提供全双工字节流/数据报，支持双向、面向连接、可传 fd（SCM_RIGHTS 附属数据，这是其他 IPC 给不了的能力）：

```c
// unix_socket_server.c —— AF_UNIX 流式 socket：进程间可靠的会话通道
// 编译：gcc unix_socket_server.c -o unix_socket_server && ./unix_socket_server &
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <sys/socket.h>
#include <sys/un.h>

int main(void) {
    int sfd = socket(AF_UNIX, SOCK_STREAM, 0);
    struct sockaddr_un addr = {0};
    addr.sun_family = AF_UNIX;
    strncpy(addr.sun_path, "/tmp/demo.sock", sizeof(addr.sun_path) - 1);
    unlink("/tmp/demo.sock");                       // 旧的先删（socket 文件残留问题）
    bind(sfd, (struct sockaddr *)&addr, sizeof(addr));
    listen(sfd, 5);

    int cfd = accept(sfd, NULL, NULL);              // 等一个连接
    char buf[128];
    ssize_t n = read(cfd, buf, sizeof(buf) - 1);
    buf[n] = 0;
    printf("server 收到: %s\n", buf);
    write(cfd, "ack", 3);
    close(cfd); close(sfd); unlink("/tmp/demo.sock");
    return 0;
}
```

```bash
$ python3 -c "
import socket
s = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)   # Python 客户端连它
s.connect('/tmp/demo.sock')
s.sendall(b'hello via unix socket')
print('server 回复:', s.recv(3).decode())"
server 收到: hello via unix socket
server 回复: ack
```

AF_UNIX vs 管道/共享内存的定位：**会话式**（有连接、双向、有关闭语义）、**可靠有序**、可被 epoll 管理（09 篇的事件模型直接适用）。Docker 的 `/var/run/docker.sock`、推理服务与本地客户端的通信、systemd 的 socket 激活，都是它的地盘；相比 TCP 127.0.0.1 省掉完整网络栈（无路由/无校验和），延迟更低且天然有文件权限做访问控制。

## 5. 选型对比表

六种 IPC 一张表定选型（依据各 man 手册与《Linux 系统编程》Robert Love 第 5 章的横向对比，量级数据为常见经验值）：

| 机制 | 数据形态 | 方向 | 拷贝次数 | 关系要求 | 典型场景 |
| --- | --- | --- | --- | --- | --- |
| 匿名管道 | 字节流 | 单向 | 2 | 亲缘 | shell 管道、父子通知 |
| 命名管道 | 字节流 | 单向 | 2 | 无（文件权限） | 简单跨进程接力 |
| 消息队列 | 离散消息 | 双向（多条队列） | 2 | 无（key） | 小消息、需边界 |
| 共享内存 | 任意（自定协议） | 双向 | **0** | 无（需自行同步） | 大数据高频（权重/KV cache） |
| 信号 | 无数据（一个编号） | 单向 | - | 无 | 生命周期管理（kill/SIGTERM） |
| AF_UNIX socket | 字节流/数据报 | 双向 | 2 | 无（文件权限） | 会话式通信、传 fd、C/S 本地协议 |

选型口诀（**经验做法**）：**管数据量，也管关系**——传大块高频数据选共享内存（配信号量）；要消息边界选消息队列；要会话与双向选 AF_UNIX；只发通知选信号；父子进程顺手用管道。多网卡多机？那不叫 IPC，叫网络编程（12 篇）。

## 常见误区

1. **"管道可以当消息队列用"**：管道是无边界的字节流，两条消息可能黏在一次 read 里（与 12 篇 TCP 粘包同源）；需要边界自己加长度前缀，或改用消息队列/数据报 socket。
2. **"信号处理函数里可以随意调用库函数"**：malloc/printf/锁都可能死锁或破坏堆（不可重入）；只设 sig_atomic_t 标志 + 白名单函数是铁律（man 7 signal-safety）。
3. **"共享内存最快所以全用共享内存"**：它把同步、边界、生命周期全甩给你；小数据低频场景，消息队列/AF_UNIX 的省心完胜零拷贝的收益——性能优化只优化账本上真实的大头。
4. **"kill -9 是清理进程的标准流程"**：SIGKILL 绕过一切清理逻辑，会留下半写文件、锁、共享内存残骸；标准流程是先 SIGTERM 等待，超时才 SIGKILL（K8s/Kill 全家桶都这么设计）。
5. **"System V IPC 资源会随进程退出自动回收"**：不会！消息队列/共享内存/信号量在 `ipcs` 里一直活着直到显式 IPC_RMID 或重启——调试留下的共享内存段会悄悄吃内存（`ipcrm` 手动清理，**经验做法**：IPC 代码必配清理路径与 atexit）。

## 本篇小结

- 管道 = 单向字节流（匿名靠亲缘、命名靠文件系统）；shell 竖线的实体是 pipe+dup2+fork；读不到 EOF 的第一嫌疑是写端 fd 没关干净。
- 信号是异步通知：SIGTERM 捕获优雅退出、SIGKILL/ SIGSTOP 不可捕获；处理函数只设标志调白名单（可重入铁律，man 7 signal-safety）。
- 三种 SysV IPC：消息队列有边界（2 次拷贝）、共享内存零拷贝但裸奔（配信号量）、信号量是同步原语不是数据通道；零拷贝账本是"共享内存最快"的全部答案。
- AF_UNIX socket：本机会话式通道，双向可靠、可传 fd、可进 epoll；docker.sock 是它的名片。
- 选型按"数据形态 × 关系 × 性能需求"三轴走，没有万能 IPC；SysV IPC 资源生命周期独立于进程，用完必须显式回收。
