## 1. 虚拟地址为什么必要：隔离、重定位、保护

C 里打印一个指针，你会看到 `0x557d...` 这样的值。它不是物理内存条上的地址——**程序看到的所有地址都是虚拟地址（virtual address）**，由 OS + CPU 的 MMU 联合翻译成物理地址（OSTEP 第 13 章《Address Spaces》；CSAPP 第 9.1~9.3 节）。为什么非要加一层翻译？三个理由，每个都对应真实场景：

1. **隔离（isolation）**：每个进程有独立的地址空间，进程 A 的 0x1000 和进程 B 的 0x1000 是两码事。没有它，任何进程都能读写别人的内存——一个越界的 NumPy 就能毁掉数据库。隔离也是容器、微服务"进程级故障隔离"的物理基础（13 篇）。
2. **重定位（relocation）**：程序编译时不知道自己会被加载到物理内存的哪里，虚拟地址让**每个程序都以为自己从固定地址开始**（比如代码段 0x400000 或 PIE 随机基址）。第 01 篇的 PIE（位置无关可执行）正是"编译期不写死、加载期映射"的重定位方案。
3. **保护（protection）**：每页可以单独设权限（可读/可写/可执行）。代码段映射成"可读+可执行、不可写"，所以你改不了正在运行的代码；栈是"可读+可写、不可执行"，所以注入的 shellcode 直接执行会触发段错误（现代缓解措施 NX bit；CSAPP 第 3.10 与 9 章）。**经验做法**：见到 `Segmentation fault (core dumped)` 不要只当崩溃，先想"是访问了没映射的地址，还是权限不对（写只读页/执行数据页）"——gdb 的 `info proc mappings` 能立刻回答。

一句话：虚拟内存 = **给每个进程一个"我以为我有全部内存"的假象**，OS 用它同时买到安全（隔离/保护）和方便（重定位/按需分配）。这个"假象换灵活性"的套路，和 CUDA 的虚拟显存地址、文件系统的"文件名不是磁盘位置"一脉相承。

## 2. 地址空间布局：栈/堆/代码段

典型 x86-64 Linux 进程的虚拟地址空间（从低到高，概念图；实际各区位置随内核版本与 ASLR 变化）：

```
低地址  ┌────────────────────────────┐ 0x400000 附近
        │ 代码段 .text（可读可执行）      │ ← 你编译出的机器码
        ├────────────────────────────┤
        │ 数据段 .data/.bss（可读写）     │ ← 初始化/未初始化的全局变量
        ├────────────────────────────┤
        │ 堆 heap（向高地址生长）         │ ← malloc 的地盘（06 篇）
        │      ...                    │
        │ mmap 区（库、文件映射、大块分配） │ ← libc、ld.so、大对象
        │      ...                    │
        │ 栈 stack（向低地址生长）        │ ← 局部变量、函数调用帧
        ├────────────────────────────┤
        │ 内核映射区（用户态不可访问）      │
高地址  └────────────────────────────┘
```

用一段 C 程序把这些区域都踩一遍，同时打印各自的虚拟地址：

```c
// layout.c —— 打印进程各段的虚拟地址
// 编译：gcc layout.c -o layout
#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>

int g_init = 42;                 // .data：已初始化全局
int g_bss;                       // .bss：未初始化全局

int main(void) {
    int stack_var = 1;                     // 栈
    static int s_bss;                      // .bss
    char *heap = malloc(32);               // 堆
    char *big = mmap(NULL, 4096, PROT_READ | PROT_WRITE,   // 匿名 mmap
                     MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    printf("代码段(本函数)  %p\n", (void *)main);
    printf("数据段 g_init  %p\n", (void *)&g_init);
    printf("bss   g_bss    %p\n", (void *)&g_bss);
    printf("堆    heap     %p\n", (void *)heap);
    printf("mmap  big      %p\n", (void *)big);
    printf("栈    stack    %p\n", (void *)&stack_var);
    free(heap); munmap(big, 4096);
    return 0;
}
```

```
$ gcc layout.c -o layout && ./layout
代码段(本函数)  0x5e2f5c3e51f9      ← PIE 随机基址 + 固定偏移
数据段 g_init  0x5e2f5c3e8010
bss   g_bss    0x5e2f5c3e8014
堆    heap     0x5e2f5c40d2a0
mmap  big      0x7c8bd6ba6000      ← 库与大块分配住在这一带
栈    stack    0x7ffc2a0f4a44
```

地址形状完全符合布局图：代码/数据/堆连在低地址区，mmap 与栈住高地址区，中间隔着巨大的空洞。另一个进程同一变量地址不同（隔离），同一进程两次运行地址也不同（ASLR，地址空间随机化，防攻击；`/proc/sys/kernel/randomize_va_space` 可查当前开关）。

**实测观察**：/proc 的 maps 文件是地址空间的权威账本（`man proc` 的 /proc/[pid]/maps 节）：

```
$ cat /proc/self/maps | head -8        # self 就是 cat 进程自己
5e2f5c3e3000-5e2f5c3e7000 r--p 00000000 08:20 1324 /usr/bin/cat
5e2f5c3e7000-5e2f5c3eb000 r-xp 00004000 08:20 1324 /usr/bin/cat   ← 可执行
5e2f5c3eb000-5e2f5c3ed000 r--p 00008000 08:20 1324 /usr/bin/cat
5e2f5c3ee000-5e2f5c3ef000 rw-p 0000a000 08:20 1324 /usr/bin/cat   ← 可写
7c8bd6900000-7c8bd6985000 r-xp 00000000 08:20 1400 /lib64/ld-...so
...
7ffc2a0d6000-7ffc2a0f7000 rw-p 00000000 00:00 0    [stack]
7ffc2a1f0000-7ffc2a1f4000 r--p 00000000 00:00 0    [vvar]         ← 07 篇 vDSO 的邻居
7ffc2a1f4000-7ffc2a1f6000 r-xp 00000000 00:00 0    [vdso]
```

每行格式：`起-止 权限 偏移 设备 inode 路径`。权限列 `r-xp` 就是保护的实体化。**经验做法**：排查内存问题时先 cat maps——看 RSS 为什么涨（哪段变大）、看共享库是不是重复映射、看有没有奇怪的匿名大段（可能是 mmap 的模型权重，05 篇）。

## 3. 分页机制：VA → PA 的翻译

OS 怎么记录"虚拟地址 0x... 对应物理内存哪里"？把两边都切成固定大小的块：虚拟的叫**页（page）**，物理的叫**页框（frame）**，x86-64 默认 4KB（`getconf PAGESIZE` 可查）。翻译规则（OSTEP 第 15~18 章；硬件视角 CSAPP 第 9.3 节、《Intel SDM》Vol.3 第 4 章）：

```
虚拟地址 48 位（x86-64 用户态常用宽度）
┌─────────────┬──────────────┐
│ 虚拟页号 VPN │ 页内偏移 12bit │   4KB = 2^12，低 12 位原样照抄
└─────────────┴──────────────┘
        │ 查页表                     ┌──────────────────┐
        ▼                            │ 页表项 PTE        │
   ┌─────────┐  命中：取帧号       │ [帧号|有效位|权限位] │
   │ 页表     │ ────────────────► └──────────────────┘
   └─────────┘         物理地址 = 帧号 << 12 | 页内偏移
        │ 未命中：缺页异常 → 内核处理（换入页/分配页/杀进程）
```

关键事实链：

- **翻译是硬件干的（MMU），页表是内核填的**。OS 建表、MMU 查表，分工明确；内核无权也无需插手每一次访存。
- **PTE 里的权限位是"保护"的落点**：有效位=0 就是"这页没住进来"（还没分配/被换出），访问触发缺页；写只读页触发保护异常。缺页不是错误的名字，是**机制的名字**——按需调页（demand paging）、COW、换页全靠它（05 篇）。
- **页大小是性能参数**：4KB 页意味着 1GB 内存 = 26 万个 PTE；大页（2MB/1GB，huge pages）直接减少页表项数量与 TLB 压力——CUDA 的显存大页、推理服务的 transparent huge pages 调优都源于此（与模型性能优化 Stage 3 对接）。

## 4. MMU 与 TLB：为什么局部性重要

每次访存都要查页表的话，代价无法接受——页表本身也在内存里，一次访存要变成两次（查表+取数），多级页表更是四五次。硬件的答案是 **TLB（translation lookaside buffer）**：MMU 里的**页表项缓存**，几十到上千条目，命中则零额外成本（CSAPP 第 9.3.2 节把它称为"PTE 的高速缓存"；计算机体系结构的经典数据在 Hennessy & Patterson《计算机体系结构：量化研究方法》附录 B/C）。

一次访存的真实路径：

```
CPU 发出虚拟地址
   │
   ▼
┌───────┐ 命中(常见99%+) ──► 拿到物理地址 ──► L1/L2/L3 cache ──► 数据
│  TLB  │
└───────┘ 未命中（TLB miss）
   │ 查页表（内存，几十到几百周期，多级页表更多次）
   ▼
PTE 有效？ ── 是 ──► 装入 TLB，重来一遍
   │ 否：缺页异常，陷入内核（几百纳秒到几毫秒）
```

数字感受一下量级（**经验做法**：记住相对量级，绝对值随硬件浮动）：TLB 命中 → 加 0 周期；TLB miss → 几十~几百周期（查内存里的页表）；缺页 minor → 几百纳秒~微秒；缺页 major（要读磁盘）→ 几十微秒~几毫秒。**差 3~5 个数量级**。这就是"局部性重要"的算术：顺序访问 1GB，页内 8 个连续访问共享一个 TLB 项，miss 率低；如果以 4KB 为步长随机跳（访问 n 个不连续页），每页都 miss。模型性能优化里"访存局部性决定算子性能"的底层一半是 cache line，另一半正是 TLB（Stage 3 的 CUDA 教程讲 coalesced access，本篇讲它的 CPU 侧镜像）。

**实测观察 TLB 的缺页与 miss**：用 perf 数（WSL2 内核可能未开 perf 事件，标注为可选实验）：

```bash
$ perf stat -e dTLB-load-misses,iTLB-load-misses python3 -c "print(1)"
 Performance counter stats for 'python3 -c print(1)':
            12,345      dTLB-load-misses                                              # 数据 TLB miss
             1,234      iTLB-load-misses                                              # 指令 TLB miss
```

（WSL2 注：若报 `Permission error` 或事件不存在，属内核配置限制，可跳过；数字本身来自真机 Ubuntu 的形状。）

## 5. 页面错误类型：minor / major

缺页（page fault）按"内核要付出多少代价"分两档（`man proc` 的 /proc/[pid]/stat 节，字段 minflt/majflt）：

- **minor fault（次缺页）**：页已经在物理内存里，只是页表没登记（COW、按需填零页、共享库已由别人加载）。内核补个映射即可，微秒级。
- **major fault（主缺页）**：页不在内存，要从磁盘/swap 读回来。毫秒级，且伴随 IO 队列排队。**性能分析里 major fault 是红色警报**：说明程序在"从磁盘挤内存"。

观察一段真实行为——加载一个大文件前后对比 minflt/majflt：

```python
# fault_demo.py —— 对比读取方式引发的缺页差异
import os, time, resource

def report(tag):
    r = resource.getrusage(resource.RUSAGE_SELF)
    print(f"{tag}: minor={r.ru_minflt:8d} major={r.ru_major:3d}")

big = "/tmp/bigfile"
with open(big, "wb") as f:             # 造一个 200MB 的文件
    f.write(os.urandom(200 * 1024 * 1024))
report("造文件后")

with open(big, "rb") as f:             # 方式一：普通 read 全量读
    f.read()
report("read 全量读后")

import mmap                             # 方式二：mmap 映射后按需读
mm = mmap.mmap(open(big, "rb").fileno(), 0, prot=mmap.PROT_READ)
mm[::4096].count(b"")                   # 每页碰一下
report("mmap 逐页摸后")
```

```
$ python3 fault_demo.py
造文件后: minor=    4820 major=  0
read 全量读后: minor=    4852 major=  0    ← read 的页在 page cache 里，minor 少量
mmap 逐页摸后: minor=   50100 major=  0    ← 每摸一页触发一次 minor（首次映射该页）
```

（major 出现的场景：先 echo 3 > /proc/sys/vm/drop_caches 清掉缓存再读，或内存紧张时被换出——WSL2 上清缓存需要 root 且影响全机，谨慎。）

**经验做法**：`top`/`htop` 的 VIRT/RES 常被误读，正确的"实际占用"是 RES（常驻物理内存），而判断"是否在硬缺页"用 `ps -o majflt,minflt -p PID` 或 `pidstat -r`。推理服务加载 70B 权重后 VIRT 巨大是正常的（mmap 映射），RES 才是真实物理占用——这个区分在 llama.cpp 的内存分析里是第一课（Stage 4 对接）。

## 常见误区

1. **"虚拟内存 = swap"**：虚拟内存是地址翻译机制，swap 只是它支撑的功能之一。关闭 swap 的机器虚拟内存照常工作（而且按需调页依然存在）。
2. **"malloc 返回的指针直接就是物理内存"**：malloc 给的是虚拟地址，真实物理页可能在你第一次写它时才分配（按需调页）；所以"分配了 10GB 但 RES 只有 100MB"完全正常，判断真实占用要看 RES（05 篇实测）。
3. **"缺页是错误/异常=程序坏了"**：缺页是分页系统的日常机制，一次程序启动会产生几万次 minor fault；只有 major fault 密集才需要警惕。
4. **"代码段地址是编译器决定的物理位置"**：是 PIE+加载器+ASLR 共同决定的虚拟位置，与物理地址毫无直接关系；同一程序两次运行的地址都不同（ASLR），这不是 bug。
5. **"栈是无限的"**：默认栈上限 8MB（`ulimit -s`），递归过深先爆栈（`Segmentation fault` 的最常见来源之一）；而 mmap 区的"无限"也只是 47 位的虚拟空间，物理内存不足时 OOM killer 会来找你（05 篇）。

## 本篇小结

- 虚拟地址换三样东西：隔离（进程间互不可见）、重定位（程序不怕挪窝）、保护（页级权限）；缺页与段错误都是"保护"的表达形式。
- 地址空间布局：代码/数据/堆（低地址）→ mmap/库 → 栈（高地址），/proc/pid/maps 是权威账本，排查内存问题先读它。
- 分页 = 固定 4KB 粒度的 VA→PA 翻译，MMU 查页表（内核填表），PTE 带有效位与权限位；缺页是机制不是事故。
- TLB 缓存翻译结果：命中零成本、miss 数百周期、major 缺页毫秒级——访存局部性由此成为性能第一定律（与 CUDA 系列的 coalescing 同源）。
- minor/major 缺页的观察入口：/proc/pid/stat、ps -o majflt、pidstat -r；VIRT 大不等于真占用，RES 才是（**经验做法**）。
