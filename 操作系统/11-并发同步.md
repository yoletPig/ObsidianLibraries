## 1. 竞态条件：两线程计数器反例实测

竞态条件（race condition）：**结果取决于线程交错顺序**的程序缺陷。触发它只需要一个计数器（OSTEP 第 26 章《Concurrency: An Introduction》的经典实验）：

```c
// race.c —— 两个线程各加 100 万次，结果却不对
// 编译：gcc race.c -o race -pthread
#include <stdio.h>
#include <pthread.h>

volatile long counter = 0;              // volatile 不解决竞态！只防编译器缓存

void *add_million(void *arg) {
    for (int i = 0; i < 1000000; i++)
        counter++;                      // 三步：读 → 加 → 写
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, add_million, NULL);
    pthread_create(&t2, NULL, add_million, NULL);
    pthread_join(t1, NULL); pthread_join(t2, NULL);
    printf("期望 2000000，实际 %ld\n", counter);
    return 0;
}
```

```
$ gcc race.c -o race -pthread && ./race
期望 2000000，实际 1157453
$ ./race
期望 2000000，实际 1077961
```

丢失更新的机制要用指令级视角看（`objdump -d race | grep -A3 add_million` 可自查）——`counter++` 编译成三条指令：

```
   mov  counter, %rax      ← 1. 读内存到寄存器
   add  $1, %rax           ← 2. 寄存器加 1
   mov  %rax, counter      ← 3. 写回内存
```

两个线程交错执行时：A 读到 5、B 读到 5、A 写 6、B 写 6——**两次加法生效一次**。交错发生在哪两条指令之间完全由调度决定（03 篇的时间片、07 篇的中断都可能插进来），所以结果是随机的、且和循环次数正相关（次数越多撞车概率越大）。两条重要推论：`volatile` 只保证"每次都真读内存"，不保证"读-改-写不可分割"，**它不是同步原语**（C++ 并发篇 12 章的结论在这里给出 OS 级解释）；测试通过不代表没竞态——只代表这次交错没踩中，这是并发 bug 的标准可怕之处。

## 2. 互斥锁的实现思想：从关中断到 CAS 自旋锁

临界区（critical section）问题：一段代码（访问 counter 的三条指令）同一时刻只能一个线程执行。解法按历史演进（OSTEP 第 28~30 章《Locks》；《The Art of Multiprocessor Programming》Herlihy & Shavit 是理论参考）：

**方案 1：关中断**（单核时代的正确答案）。进入临界区前关中断，退出再开——没有中断就没有调度，交错不可能发生。单核完美，多核失效（别的核上的线程根本不理你这颗核的中断），且用户态根本没权关中断——它只配当**内核内部**的手法（LKD 第 9 章的 spin_lock_irqsave 正是这个思想的现代残留）。

**方案 2：朴素锁变量**（看起来对，实际错）：

```c
while (lock == 1) ;   // 忙等：别人拿着就转圈
lock = 1;             // "抢锁"
/* 临界区 */
lock = 0;             // 释放
```

检查与设置是**两条指令**，交错照样发生：A 检查完 lock==0 还没写 1，B 检查也是 0，双双进入——锁形同虚设。**教训：判断+行动不是原子的**。

**方案 3：Peterson 算法**（1981，纯软件方案，两线程）：用 turn 与 flag[2] 两个变量的巧妙组合实现互斥（OSTEP 第 29 章有完整推导与正确性论证）。它在单核乱序之外的顺序机器上正确，但现代 CPU 的乱序执行/内存重排会让它失灵——它教育意义大于实用意义：**正确的并发原语需要硬件同步指令兜底**。

**方案 4：CAS 自旋锁**（现代方案的骨架）。硬件提供原子指令 x86 的 `lock cmpxchg`（比较并交换，CAS：如果变量等于期望值就换成新值并返回成功，否则失败——整个动作不可分割）。用它实现自旋锁：

```c
// spinlock.c —— 用 GCC 内建 CAS 实现自旋锁，验证正确性
// 编译：gcc spinlock.c -o spinlock -pthread
#include <stdio.h>
#include <pthread.h>
#include <stdatomic.h>

atomic_int lock = 0;                    // 0=空闲 1=持有

void acquire(void) {
    int expected = 0;
    // CAS：lock 还是 0 时换成 1；失败则 expected 被更新为当前值，继续转
    while (!atomic_compare_exchange_weak(&lock, &expected, 1)) {
        expected = 0;                   // 没抢到，带着新期望再转一圈
    }
}

void release(void) {
    atomic_store(&lock, 0);             // 释放：写 0 即可
}

atomic_long counter = 0;                // 受锁保护的计数器

void *worker(void *arg) {
    for (int i = 0; i < 1000000; i++) {
        acquire();
        counter++;                      // 临界区：这次不会再丢
        release();
    }
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, worker, NULL);
    pthread_create(&t2, NULL, worker, NULL);
    pthread_join(t1, NULL); pthread_join(t2, NULL);
    printf("期望 2000000，实际 %ld\n", (long)counter);
    return 0;
}
```

```
$ gcc spinlock.c -o spinlock -pthread && ./spinlock
期望 2000000，实际 2000000
```

自旋锁的适用边界：它**忙等烧 CPU**，适合临界区极短（纳秒~微秒级）、核数充足的场景；临界区长或线程数远超核数时，睡眠型锁（futex，第 6 节）才对。pthread_mutex 就是两者的合体——先自旋几圈，抢不到再睡（见第 6 节）。

## 3. 死锁：四条件与预防

死锁（deadlock）：一组线程互相等待对方手里的资源，全部永久卡死。四个**缺一不可**的条件（Coffman 1971 的经典表述；OSTEP 第 32 章《Common Concurrency Problems》）：

1. **互斥**：资源同一时刻只能一人持有（锁天生如此）；
2. **持有并等待**：拿着 A 还想要 B；
3. **不可抢占**：不能强行剥夺别人手里的锁；
4. **循环等待**：A 等 B 的、B 等 A 的，成环。

四个条件打断任何一个死锁就散架。工程上可行的两条（**经验做法**）：

- **全局加锁顺序**（打断条件 4）：所有代码按固定顺序拿锁（如按锁的地址排序、或按模块分层"先配置锁后数据锁"）。死锁预防的银弹没有，但顺序纪律覆盖 90% 场景。
- **一次性获取**（打断条件 2）：需要多把锁时用 `pthread_mutex_lock` 逐把拿会留窗口；C++ 用 `std::scoped_lock(a, b)`、或自己写 try-lock 回退，一次成套。

亲手造一个死锁，摸清它的现场：

```c
// deadlock.c —— 经典 AB-BA 死锁
// 编译：gcc deadlock.c -o deadlock -pthread    （运行后 Ctrl-C 结束）
#include <stdio.h>
#include <pthread.h>
#include <unistd.h>

pthread_mutex_t A = PTHREAD_MUTEX_INITIALIZER;
pthread_mutex_t B = PTHREAD_MUTEX_INITIALIZER;

void *t1_body(void *x) {                    // 线程 1：先 A 后 B
    pthread_mutex_lock(&A);
    sleep(1);                               // 制造窗口，保证交错
    pthread_mutex_lock(&B);                 // ← 永远卡在这
    printf("t1 拿到两把锁\n");
    return NULL;
}

void *t2_body(void *x) {                    // 线程 2：先 B 后 A（顺序相反！）
    pthread_mutex_lock(&B);
    sleep(1);
    pthread_mutex_lock(&A);                 // ← 永远卡在这
    printf("t2 拿到两把锁\n");
    return NULL;
}

int main(void) {
    pthread_t a, b;
    pthread_create(&a, NULL, t1_body, NULL);
    pthread_create(&b, NULL, t2_body, NULL);
    pthread_join(a, NULL); pthread_join(b, NULL);
    return 0;
}
```

```
$ gcc deadlock.c -o deadlock -pthread && ./deadlock &
$ ps -T -p $(pgrep deadlock)               # ps -T 看线程级状态（02 篇的工具）
   PID   SPID  STAT  COMMAND
  24770  24770  Ssl  ./deadlock
  24770  24771  Sl   ./deadlock
  24770  24772  Sl   ./deadlock        ← 两个线程 Sl：睡眠中，且永不醒
$ cat /proc/24770/task/24771/stack 2>/dev/null | head -2   # WSL2 需 root；看卡在哪个内核函数
[<0>] futex_wait_queue      ← 第 6 节的主角：睡在 futex 上等锁
```

诊断工具：gdb attach 后 `thread apply all bt` 看每个线程卡在哪把锁；生产环境用 `pstack`/`eu-stack` 采样对比两次调用栈是否纹丝不动。**经验做法**：疑死锁先看"是不是真的死锁"（状态 S 且 CPU 为 0 且永不结束），再用调用栈找出双方持锁顺序，把顺序统一即修复。

## 4. 条件变量：生产者消费者正确写法

互斥锁解决"互斥"，不解决"等待"——线程要等"队列非空"，转圈是浪费。条件变量（condition variable）是"**带着锁去睡觉、被叫醒时重新拿锁**"的机制（OSTEP 第 30 章《Condition Variables》）。生产者消费者的**标准写法**（谓词版，直接背下来）：

```c
// prodcons.c —— 生产者消费者：互斥锁 + 条件变量（正确版）
// 编译：gcc prodcons.c -o prodcons -pthread
#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>
#include <unistd.h>

#define QCAP 4
int queue[QCAP];                     // 简单循环队列
int head = 0, tail = 0, count = 0;
pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  not_empty = PTHREAD_COND_INITIALIZER;
pthread_cond_t  not_full  = PTHREAD_COND_INITIALIZER;
int done = 0;                        // 生产结束标志

void *producer(void *x) {
    for (int i = 1; i <= 10; i++) {
        pthread_mutex_lock(&mtx);
        while (count == QCAP)        // 队列满：等"非满"（必须 while 不是 if！）
            pthread_cond_wait(&not_full, &mtx);   // 睡前原子地释放锁
        queue[tail] = i; tail = (tail + 1) % QCAP; count++;
        printf("生产 %d\n", i);
        pthread_cond_signal(&not_empty);          // 唤醒一个等"非空"的消费者
        pthread_mutex_unlock(&mtx);
        usleep(100000);              // 生产得慢一点，好观察
    }
    pthread_mutex_lock(&mtx);
    done = 1;                        // 打完工卡（在锁内改共享状态）
    pthread_cond_broadcast(&not_empty);           // 广播：叫醒全部消费者去检查 done
    pthread_mutex_unlock(&mtx);
    return NULL;
}

void *consumer(void *x) {
    for (;;) {
        pthread_mutex_lock(&mtx);
        while (count == 0 && !done)  // 空且没收工：等"非空"
            pthread_cond_wait(&not_empty, &mtx);
        if (count == 0 && done) {    // 空 + 收工 = 真正的退出条件
            pthread_mutex_unlock(&mtx);
            return NULL;
        }
        int v = queue[head]; head = (head + 1) % QCAP; count--;
        printf("      消费 %d\n", v);
        pthread_cond_signal(&not_full);
        pthread_mutex_unlock(&mtx);
    }
}

int main(void) {
    pthread_t p, c1, c2;
    pthread_create(&p, NULL, producer, NULL);
    pthread_create(&c1, NULL, consumer, NULL);
    pthread_create(&c2, NULL, consumer, NULL);
    pthread_join(p, NULL); pthread_join(c1, NULL); pthread_join(c2, NULL);
    return 0;
}
```

```
$ gcc prodcons.c -o prodcons -pthread && ./prodcons | head -8
生产 1
      消费 1
生产 2
      消费 2
...
```

四个必守规矩（每条对应一颗真实的雷）：

1. **永远用 `while` 检查条件**，不用 if——`pthread_cond_wait` 被唤醒后条件可能已被别的线程改掉（**虚假唤醒**：OS 允许无通知醒来；且 signal 只保证"有希望"不保证"轮到你"）。
2. **wait 必须持有锁**进入——wait 内部"原子地：释放锁 + 睡眠"，醒来时自动重新持锁；这个原子性正是防止"检查条件与睡眠之间通知溜进来"的锁孔（C++ 并发篇的 wait(lock, pred) 是同一语义的库封装）。
3. **改共享状态必须在锁内**，signal 放锁内或锁尾皆可（现代实现放锁外略快，但状态变更本身绝不能在锁外）。
4. **退出条件要进谓词**（count==0 && !done）并用 broadcast 收尾——否则收工信号落在"正在睡"的消费者身上就成死锁。

## 5. 内存序常识：sequential consistency 语义

最后一层迷雾：为什么有了原子操作和锁，还会有"诡异结果"？因为**编译器和 CPU 都会重排指令**（乱序执行、写缓冲、缓存一致性延迟），单线程看不见的重排在多线程的观察下全都会显形。为讨论正确性，需要一个理想模型：**顺序一致性（sequential consistency, SC）**（Lamport 1979 的定义；C++ 并发篇 12 章提过的 memory_order 的地基）：

> 所有线程看到的**所有**线程的操作，按某个**统一的全局顺序**排列，且每个线程自己的操作顺序在这个全序中保持一致。

直觉版：就好像所有线程的操作被"洗进同一个牌堆"，任何人抽出来看都是同一种顺序。真实硬件的 x86 提供的是较强保证（TSO：store 不重排到 load 前，单靠 CAS/锁默认带 acquire/release 语义），ARM 则弱得多（各种重排都可能）——**写可移植并发代码的正确姿势是：要么全程用锁（锁的语义自动包含必要的内存屏障），要么用 C11/C++ 的默认顺序一致原子（seq_cst）**；显式 memory_order 的精细调优属于性能工程系列，本系列只需记住：**没有内存序意识时，不要手写无锁代码**（Herlihy & Shavit 的结论：无锁正确实现难度远超收益预期；**经验做法**：99% 的场景锁就够了，剩下 1% 先找现成的库）。

C11 的 `atomic_compare_exchange_weak`/`atomic_store` 未指定内存序时默认 `memory_order_seq_cst`——本篇第 2 节的自旋锁因此正确。这就是"sequential consistency 语义"在代码里的落点：**默认 seq_cst = 你按直觉想的顺序就是它执行的顺序**（在原子变量之间）。

## 6. futex 思想

收束到 Linux 的真实锁。futex（fast userspace mutex，`man 2 futex`）回答一个问题：** uncontended 的锁为什么要进内核？** 抢锁 99% 的时间是无人竞争的——进内核（系统调用 + 切换）纯属浪费。futex 的设计：

```
无竞争（快路径，99%+）:
    用户态 CAS 一把抢到锁 —— 全程不出内核，几十纳秒

有竞争（慢路径）:
    CAS 失败 → futex(WAIT) 系统调用：把自己挂到内核等待队列睡觉
释放时: futex(WAKE) 系统调用：叫醒一个等待者

pthread_mutex = 自旋一小段 + futex 睡眠的合体
```

这解释了三个此前悬而未决的现象：pthread_mutex 为什么"平时极快、竞争大时自动退化"；07 篇死锁现场栈里的 `futex_wait_queue`（睡在慢路径上）；Go/Java 的锁、Python GIL 底层（pthread_mutex）为何共享同一套设计。**fast path 用户态、slow path 内核态**——这个分层思想在 vDSO（07 篇：常问的答案放用户态）、epoll（09 篇：注册一次等多次）、io_uring 里反复出现，是内核设计的母题之一。

## 常见误区

1. **"volatile 能替代锁"**：volatile 只防编译器优化重读，不管原子性与可见性；race.c 加了 volatile 照样丢更新。原子性用 atomic/锁，可见性靠它们的内存序语义。
2. **"竞态测试通过就安全"**：交错是概率事件，测试只是采样；并发正确性靠推理（不变式）与工具（TSan：`gcc -fsanitize=thread`），不靠跑几次没炸。
3. **"自旋锁比互斥锁快，全用自旋锁"**：自旋锁在临界区长、线程多于核数时把 CPU 烧在转圈上（07 篇切换成本的反面教材）；pthread_mutex 的"自旋片刻再睡"才是默认正解。
4. **"条件变量用 if 检查就够了"**：虚假唤醒 + 多消费者抢跑会让 if 版漏判；while + 谓词是唯一安全写法。退出条件必须纳入谓词，否则收工时死锁。
5. **"死锁只在复杂的库代码里发生"**：AB-BA 四行代码就能造出来；跨模块调用（回调里再拿锁）是隐性加锁顺序破坏者。全局锁顺序文档化是团队纪律，不是可选风格（**经验做法**）。

## 本篇小结

- 竞态条件的物理本质：counter++ 是读-改-写三条指令，交错即丢更新；volatile 与此无关；测试通过 ≠ 无竞态。
- 锁的实现链：关中断（单核内核）→ 朴素锁变量（检查+设置不原子，错）→ Peterson（软件正确但怕重排）→ CAS 自旋锁（硬件原子指令兜底）；自旋锁适合短临界区。
- 死锁四条件（互斥/持有并等待/不可抢占/循环等待）缺一不可；工程预防 = 全局锁顺序 + 一次性成套获取；ps -T 与调用栈是现场工具。
- 生产者消费者四规矩：while 检查、wait 持锁、状态变更锁内、退出进谓词——每条对应虚假唤醒/通知丢失/竞态/死锁一颗雷。
- 顺序一致性 = 所有线程共享一个统一操作全序；默认 seq_cst 的原子与锁自动带对；无内存序意识不写无锁代码；futex = 快路径用户态 CAS + 慢路径内核睡眠，pthread_mutex 的真实结构。
