## 1. 进程是什么：task_struct 与进程描述符

第 01 篇说"进程是运行中的程序"。更准确的说法（OSTEP 第 4 章《Processes》）：**进程 = 受限直接执行的抽象 + 它的一整套状态**。内核用一个结构体给每个进程建档，Linux 里就是 `task_struct`（定义在 `include/linux/sched.h`；我们不读源码，只讲字段的意义，想翻的对照《Linux 内核设计与实现》第 3 章）。把它想象成一张员工档案：

| task_struct 字段 | 档案上的一栏 | 管什么 | 在哪观察 |
| --- | --- | --- | --- |
| `pid` / `tgid` | 工号 | pid 是"执行流"编号，tgid 是"进程"编号；主线程两者相同 | `getpid()`、`ps -e` |
| `state` | 在岗状态 | TASK_RUNNING / INTERRUPTIBLE / ... 见第 4 节状态机 | `/proc/PID/status` 的 State |
| `mm` | 记忆 | 内存描述符：页表根、地址空间布局；线程共享同一份 | `/proc/PID/maps`（04 篇） |
| `files` | 钥匙串 | 打开的文件描述符表 | `/proc/PID/fd/`（08 篇） |
| `thread_info` | 心跳 | CPU 上下文：寄存器、程序计数器，切换进程时保存/恢复的就是它 | 07 篇上下文切换 |
| `parent` / `children` | 家谱 | 父进程与子进程链表，wait/僵尸都绕不开它 | `ps -o ppid= -p PID` |
| `cred` | 胸卡 | 用户/组 ID、能力（capability），权限检查全查它 | `ps -o user= -p PID` |
| `sched_entity` | 考勤 | 调度信息：vruntime、权重，CFS 排队就靠它（03 篇） | `/proc/PID/sched` |
| `signal` / `sighand` | 呼机 | 信号处理表，kill 打过来落到这里（10 篇） | `/proc/PID/status` 的 Sig* 行 |

一句话记住档案哲学：**fork 复制档案，exec 换掉"记忆"，wait 是家长签字**。下面逐个落实。

## 2. fork/exec/wait：mini shell 的 C 实现

第 01 篇用 Python 演示过结构，现在用 C 写一遍才看得清语义。`fork()` 的奇特之处：**调用一次，返回两次**——父进程里返回子进程 PID，子进程里返回 0（OSTEP 第 5 章；`man 2 fork`）：

```c
// mini_shell.c —— 最小 shell：fork + execvp + waitpid
// 编译：gcc mini_shell.c -o mini_shell
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

#define MAXLINE 4096
#define MAXARGS 64

int main(void) {
    char line[MAXLINE];
    while (1) {
        printf("mysh> ");                       // 1. 提示符（记得冲缓冲区）
        fflush(stdout);
        if (!fgets(line, sizeof(line), stdin))  // 读到 EOF（Ctrl-D）退出
            break;
        line[strcspn(line, "\n")] = '\0';       // 去掉行尾换行
        if (line[0] == '\0') continue;
        if (strcmp(line, "exit") == 0) break;

        // 2. 简单分词（真实 shell 还要处理引号、管道、重定向）
        char *args[MAXARGS]; int argc = 0;
        for (char *p = strtok(line, " "); p; p = strtok(NULL, " "))
            args[argc++] = p;
        args[argc] = NULL;

        pid_t pid = fork();                     // 3. 复制进程
        if (pid < 0) { perror("fork"); continue; }
        if (pid == 0) {                         // —— 子进程分支 ——
            execvp(args[0], args);              // 4. 替换程序；成功则不再返回
            perror("execvp");                   // 失败才会执行到这里
            _exit(127);                         // 用 _exit 别用 exit：不冲刷父进程的缓冲区
        }
        int status;                             // —— 父进程分支 ——
        waitpid(pid, &status, 0);               // 5. 等待并回收（关键！不 wait 就有僵尸）
        if (WIFEXITED(status))
            printf("[退出码 %d]\n", WEXITSTATUS(status));
    }
    return 0;
}
```

```bash
$ gcc mini_shell.c -o mini_shell && ./mini_shell
mysh> echo hello
hello
[退出码 0]
mysh> ls no_such_file
ls: cannot access 'no_such_file': No such file or directory
[退出码 2]
mysh> exit
```

fork 的细节值得用一段代码钉死（面试高频）：

```c
// fork_basics.c —— fork 的三件套：返回值、写时复制、继承什么
#define _GNU_SOURCE
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int g = 100;                      // 全局变量

int main(void) {
    int local = 1;                // 栈上变量
    pid_t pid = fork();
    if (pid == 0) {               // 子进程
        g++; local++;
        printf("child:  pid=%d ppid=%d g=%d local=%d\n",
               getpid(), getppid(), g, local);
        return 0;                 // 子进程结束
    }
    wait(NULL);                   // 父进程回收
    printf("parent: pid=%d g=%d local=%d\n", getpid(), g, local);
    return 0;
}
```

```
$ gcc fork_basics.c -o fork_basics && ./fork_basics
child:  pid=23145 ppid=23144 g=101 local=2
parent: pid=23144 g=100 local=1
```

两个输出对不上号，正是设计使然：

- **fork 之后两份进程各改各的，互不可见**。现代 Linux 用**写时复制**（copy-on-write, COW）实现：fork 时不真的复制内存页，父子共享物理页并标记只读，谁写谁触发缺页、由内核复制那一页（OSTEP 第 15 章末尾；细节见 05 篇）。所以 fork 快、fork 大内存的进程也不怕（14 篇实测 fork 开销）。
- **子进程继承父进程打开的 fd、工作目录、环境变量、信号处理**（`man 2 fork` 的描述），所以 shell 里的 `> out.txt` 重定向才对子命令生效、log 才会写到同一个文件——线程与进程行为差异的很多"怪现象"根源都在继承规则。

## 3. 线程模型：用户级 vs 内核级

**线程 = 进程里的独立执行流**。教科书区分两种模型（OSTEP 第 26 章《Concurrency: An Introduction》开头；经典对照见 Silberschatz《Operating System Concepts》第 4 章）：

- **用户级线程（user-level threads, 多对一）**：线程库在用户态自己管理多个执行流，内核只看得见"一个进程"。切换极快（不进内核），但一个线程阻塞在系统调用上，**整个进程**都得跟着阻塞，也用不上多核。
- **内核级线程（kernel-level threads, 一对一）**：每个线程都是内核的调度对象（Linux 走的路）。阻塞一个不影响别人、能用满多核，代价是切换要进内核。

```
用户级线程（多对一）              内核级线程（一对一，Linux/goroutine的宿主）
┌──────────────┐                ┌──────────────┐
│ 线程库: T1 T2 │ ←内核看不见     │ T1 T2 T3     │ ←每个都映射一个内核线程
├──────────────┤                ├──────────────┤
│  进程地址空间  │                │  进程地址空间  │
└──────┬───────┘                └──────┬───────┘
       ▼ 1 个内核调度对象                ▼ N 个内核调度对象
   [ 内核进程 ]                    [内核线程][内核线程][内核线程]
```

Linux 的实现有个著名事实：**Linux 不区分进程和线程**，两者都是 `task`，只是创建参数不同（LKD 第 3 章）：

```c
// thread_vs_fork.c —— 同一个进程里开线程 vs 复制进程
// 编译：gcc thread_vs_fork.c -o thread_vs_fork -pthread
#include <stdio.h>
#include <unistd.h>
#include <pthread.h>
#include <sys/wait.h>

__thread int tls_var = 7;            // 线程局部存储（TLS）：每个线程一份

void *thread_main(void *arg) {
    tls_var = 8;
    printf("thread: pid=%d tid=%d tls_var=%d\n",
           getpid(), gettid(), tls_var);   // 注意：pid 相同！
    return NULL;
}

int main(void) {
    pthread_t t;
    pthread_create(&t, NULL, thread_main, NULL);
    pthread_join(t, NULL);
    printf("main  : pid=%d tls_var=%d\n", getpid(), tls_var);
    return 0;
}
```

```
$ gcc thread_vs_fork.c -o thread_vs_fork -pthread && ./thread_vs_fork
thread: pid=23901 tid=23902 tls_var=8
main  : pid=23901 tls_var=7
```

读三个信息：线程和主进程 `pid` 相同（同一个"进程"），`tid` 不同（内核眼里是不同调度单位）；`__thread` 修饰的 TLS 变量每个线程独立（8 vs 7）；底层 `pthread_create` 调用的正是 `clone(CLONE_VM|CLONE_FS|CLONE_FILES|...)`（`man 2 clone`）——**与 `fork` 共用同一套复制机制，只是少复制了 `mm` 等大头**，这就是"线程 = 共享资源的进程"的确切含义。

对照 Python：CPython 的 `threading` 建在 OS 线程（一对一线程）上，但解释器有全局锁 GIL，同一时刻只有一个线程执行 Python 字节码——所以 CPU 密集任务用 `threading` 不提速，要用 `multiprocessing`（多个进程）或把热点下沉到 C 扩展（NumPy/CUDA 在持锁外运行）。这也是推理服务普遍"多进程 + 进程内多线程"结构的原因（14 篇用 `ps -T` 实测线程与 GIL）。

**经验做法**：Go 语言的 goroutine 是"内核线程之上再虚拟的一层"（M:N 模型，多个 goroutine 复用少量内核线程）——你以后看到"协程比线程轻"的说法，本质就是用户级线程思想的现代复辟，代价是 runtime 要自己处理阻塞（netpoller）。Java 虚拟线程同理。

## 4. 进程状态机与 ps 实测

内核档案里 `state` 字段记录进程此刻在不在"能上 CPU"的状态。Linux 的主状态（LKD 第 3 章；`man proc` 的 /proc/PID/status 节）：

```
              fork() 创建
                 │
                 ▼
   ┌──── TASK_RUNNING (R) ────运行中或就绪排队────┐
   │             │ 时间片用尽/被抢占                │
   │             ▼                                │
   │      [ 等待 CPU 的就绪队列 ]                   │
   │                                              │
   ▼ 等待事件（read磁盘/网络/信号量）                 │
TASK_INTERRUPTIBLE (S)  可中断睡眠 ←── 事件到达 ────┘
TASK_UNINTERRUPTIBLE (D) 不可中断睡眠（通常在等 IO，kill 都杀不动）
   │
   ▼ exit() 退出
TASK_ZOMBIE (Z)  僵尸：等父进程 wait 收尸
TASK_STOPPED (T)  被 SIGSTOP/SIGTSTP 暂停（Ctrl-Z）
```

用 Python 造一个慢任务，观察它一生的状态变化：

```python
# state_demo.py —— 一个会经历 S/R/Z 三种状态的进程
import os, time

pid = os.fork()
if pid == 0:                     # 子进程：跑 10 秒
    time.sleep(10)               # sleep 是可中断睡眠 -> S
    os._exit(0)
# 父进程故意 sleep 12 秒再收尸：子进程最后 2 秒是 Z
time.sleep(2)
print(open(f"/proc/{pid}/status").read().split("State:")[1][:18])  # S sleeping
os.system(f"cat /proc/{pid}/status | head -3")                     # 现场打印
os.system(f"ps -o pid,stat,comm -p {pid}")                         # ps 视角
time.sleep(10)
os.waitpid(pid, 0)               # 收尸，Z 消失
```

```
$ python3 state_demo.py
   2 lines: S (sleeping) ...
    PID STAT COMM
  23999 S    python3
```

STAT 列的字母就是上图的缩写（`man ps` 的 PROCESS STATE CODES 节）：R 运行、S 可中断睡眠、D 不可中断睡眠、Z 僵尸、T 暂停。**性能分析里 S 和 D 的区别是关键线索**：CPU 空闲但系统卡，`ps` 看到成片 D 状态，说明瓶颈在磁盘/网络 IO 而不是 CPU——load average 里也计入 D 状态进程（所以"load 高但 CPU 低"通常在等 IO）。**WSL2 注**：WSL2 的磁盘是 9P 协议挂载的虚拟盘，跨文件系统 IO 偶发慢且伴随 D 状态，属已知特性，不是你程序的问题。

## 5. 僵尸与孤儿进程：实测演示

**僵尸（zombie）**：子进程已退出，退出状态还没被父进程收走，只剩一条 task_struct 档案挂着（OSTEP 第 5 章的 shell homework 专节）。**孤儿（orphan）**：父进程先死，子进程被 1 号进程（或 systemd 子进程）领养，领养者负责替它收尸。制造并观察两者：

```c
// zombie_orphan.c —— 左手制造僵尸，右手制造孤儿
// 编译：gcc zombie_orphan.c -o zombie_orphan
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    pid_t z = fork();
    if (z == 0) _exit(42);          // 子进程立刻退出：父进程(本进程)还没收尸
    sleep(1);                        // 窗口期：此刻 z 是僵尸
    char cmd[64];
    snprintf(cmd, sizeof(cmd), "ps -o pid,ppid,stat,comm -p %d", z);
    system(cmd);                     // 用 ps 亲眼确认 Z 状态
    printf("僵尸的退出码=%d\n", WEXITSTATUS(waitpid(z, NULL, 0)));  // 收尸

    pid_t o = fork();
    if (o == 0) {                    // 另一个子进程：活得比父进程久
        sleep(2);
        snprintf(cmd, sizeof(cmd),
                 "echo 孤儿的新爸爸 ppid=$(ps -o ppid= -p %d)", getpid());
        system(cmd);                 // 此时父进程已死，ppid 应变为 1 或 systemd 之类
        _exit(0);
    }
    sleep(1);                        // 父进程先撤，o 变孤儿
    return 0;
}
```

```
$ gcc zombie_orphan.c -o zombie_orphan && ./zombie_orphan
    PID    PPID STAT COMM
  24011   24010 Z+   zombie_orphan
僵尸的退出码=42
孤儿的新爸爸 ppid=2256     ← WSL2/systemd 担任 1 号进程角色，由它收尸
```

两条铁律由此而来：

1. **僵尸无害但占名额**：一个僵尸只占一个 PID 和一点内核内存；但如果服务长期 fork 短命子进程而不 wait（比如某些"简单粗暴"的推理框架调起外部工具），僵尸会越积越多直到 PID 耗尽。修法：父进程调用 `wait/waitpid`，或 `signal(SIGCHLD, SIG_IGN)`（内核代收），或用 `sigaction` 的 `SA_NOCLDWAIT`（`man 2 sigaction`）。
2. **孤儿是正常机制**：父进程死后子进程必须有人收尸，领养是内核自动做的，不是 bug。容器里 PID 1 的特殊性（要当所有孤儿的养父）正是 13 篇的主题。

**经验做法**：`ps aux | grep defunct` 是巡检僵尸的标准动作；看到僵尸先看它父进程是谁（PPID 列），修父进程的 wait 逻辑，而不是去 kill 僵尸（僵尸已经死了，杀不动）。

## 6. 进程 vs 线程：怎么选

把两者的核心差异压成一张表（依据：OSTEP 第 26 章、CSAPP 第 8.2/12 节）：

| 维度 | 进程 | 线程 |
| --- | --- | --- |
| 创建/销毁成本 | 高（复制页表、fd 表，COW 缓解） | 低（共享大部分资源） |
| 上下文切换成本 | 高（换页表，TLB 大概率被冲刷） | 低（同进程内换执行流，TLB 保得住） |
| 隔离性 | 强：一个崩不死全家 | 弱：一个线程越界写坏共享内存，整个进程完蛋 |
| 数据共享 | 要 IPC（10 篇：管道/共享内存/socket） | 直接读写全局变量（所以要同步，11 篇） |
| 故障半径 | 独立进程独立挂 | 共享进程生死 |
| 典型场景 | 隔离的组件（预处理/训练/服务），多租户，GIL 语言并行 | 推理引擎流水线，IO 并发，同一个模型的多路请求 |

对"算法工程师"这个目标画像，选型口诀（**经验做法**）：

- **用 Python 且 CPU 密集**（数据预处理、特征工程）→ 多进程 `multiprocessing`，因为 GIL；
- **引擎内部流水线**（C++ 推理框架、采集-推理-解码）→ 线程，共享模型权重省内存，切换快；
- **不信任的第三方模型/插件** → 进程隔离，崩了不能拖垮主服务；
- **多 GPU 训练/多副本推理服务** → 进程（每卡一进程是最省心的隔离单位，NCCL 生态也这么假设）。

## 常见误区

1. **"fork 会复制整个内存，进程越大 fork 越慢"**：有 COW 后 fork 主要是复制页表，微秒到毫秒级；真正慢的是 fork 后立即 exec 的路径要换掉整个地址空间。14 篇实测给出数字。
2. **"线程数越多越好"**：内核线程每个都是调度单位，超过核数的 CPU 密集线程只会增加上下文切换开销（07 篇实测成本）；IO 密集才靠更多线程掩盖等待。经验起点：CPU 密集 ≈ 核数，IO 密集按等待/计算比放大（**经验做法**）。
3. **"僵尸进程用 kill -9 就能清掉"**：僵尸已死，kill 发不进去；正确动作是让父进程 wait，或杀掉"卡住不收尸的父进程"让僵尸变孤儿被领养回收。
4. **"子进程一定共享父进程之后的修改"**：COW 之后完全分家；共享的只有显式建立的 IPC（10 篇）。拿"子进程改了全局变量父进程怎么没变"当 bug 报，是本系列最常收到的误解。
5. **"D 状态进程 CPU 占用低，说明不忙"**：D 是在等不可中断的 IO，load average 会计入它；"load 高、CPU 低"的第一反应是查 IO（`iostat`/`dmesg`），不是加机器。

## 本篇小结

- 进程的档案是 task_struct：pid/state/mm/files/cred/sched_entity 各管一摊，都能在 /proc/PID 下找到观察窗口；fork 复制档案、exec 换记忆、wait 是收尸。
- fork 一次返回两次；COW 让 fork 便宜；fd/环境/信号处理被继承，这是 shell 重定向与日志落地的根基。
- Linux 的线程就是共享资源的进程（clone 参数不同）；用户级线程快但阻塞传染，内核级线程能用满多核；GIL 让 Python 的 CPU 并行必须走多进程。
- 状态机 R/S/D/Z/T 中，S 与 D 的区分是 IO 排查的第一线索；僵尸要靠父进程 wait 回收，孤儿被 1 号进程领养是正常机制。
- 选型：隔离与故障半径看进程，共享与切换成本看线程；Python CPU 密集用多进程是 GIL 决定的（**经验做法**）。

## 练习

1. 跑通 mini_shell.c，然后扩展：支持 `cd`（提示：cd 必须由 shell 自己执行 `chdir`，想想为什么 fork 后做没用）；支持 `cmd &` 后台执行（父进程不 waitpid，观察僵尸如何产生）。
2. 把 fork_basics.c 里的 `wait(NULL)` 删掉，父进程 sleep 后退出，用 `ps aux | grep Z` 观察子进程的下场；再用 `ps -o ppid= -p <僵尸pid>` 找到新父亲，解释为什么它最终会消失。
3. 用 `ps -o pid,ppid,stat,comm -e | head -30` 找出你系统里 3 个 S 状态、1 个 R 状态的进程；对 S 的进程查 `/proc/PID/wchan`（内核等待函数名），说说它在等什么。
4. 写 C 程序：fork 一个子进程，父子各自向同一个文件（以追加模式打开）各写 1000 行，检查行数与交错情况；再把 fd 换成两个进程分别打开同一文件，对比差异，用"fork 继承 fd 表"解释结果。
5. 在 Python 里用 `multiprocessing` 起 4 个进程各做 1 秒纯 CPU 循环，用 `time.perf_counter()` 对比 `threading` 版本；再用 `ps -T -p <pid>` 数一数两种版本的线程数。把"GIL 下线程不并行于 CPU"变成你亲眼看过的现象。
