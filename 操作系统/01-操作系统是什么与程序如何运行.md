# 01 - 操作系统是什么与程序如何运行

## 本篇目标

- 用 OSTEP 的框架说出操作系统的三大职责：虚拟化、并发、持久化，并把它们和你将来会遇到的性能问题对上号。
- 走通一条完整的链路：从 `hello.c` 源码到屏幕上打出 "hello"，中间经过预处理、编译、汇编、链接、加载、执行六个站，每一站发生什么、谁负责。
- 理解系统调用的本质：`syscall` 指令、用户态与内核态的切换，并用 strace 亲眼看一个程序的每一次系统调用。
- 明白 shell 只是一个"循环调用 fork/exec/wait 的普通程序"，从第一天起就祛魅。

前置：会最基本的 Linux 命令行操作，能用 gcc 编译一个 C 文件（本篇会用到 Python 3.10+ 和 gcc，环境为 Ubuntu 22.04 / WSL2）。

## 1. 操作系统的三大职责：虚拟化、并发、持久化

教科书怎么定义操作系统？OS 提供一个标准教材式的回答（OSTEP 第 1、2 章）：操作系统是**把物理资源转化为通用、易用的虚拟资源**的系统软件。它站在硬件和你写的程序之间，干三件大事，这三件大事恰好对应 OSTEP 全书的三个部分，也对应本系列的三条主线：

```
                 ┌─────────────────────────────┐
                 │        应用程序们             │
                 │  python server   llamacpp    │
                 └──────┬──────────────┬────────┘
                        │  系统调用接口  │        ← 第 1/3/7 篇讲这条边界
                 ┌──────▼──────────────▼────────┐
                 │        操 作 系 统 内 核       │
                 │  虚拟化: CPU→进程 内存→地址空间 │
                 │  并发:   调度 同步 进程间通信   │
                 │  持久化: 文件系统 设备驱动      │
                 └──────┬──────────────┬────────┘
                        │   硬件指令    │
                 ┌──────▼──────────────▼────────┐
                 │   CPU  内存  磁盘  网卡  GPU   │
                 └──────────────────────────────┘
```

1. **虚拟化（virtualization）**：把一份物理 CPU 虚拟成"每个进程都独占一个 CPU"的假象（03 篇调度），把一块物理内存虚拟成"每个进程都有一个从 0 开始的完整地址空间"（04/05 篇虚拟内存）。你写 Python 时从来没操心过"这个变量的字节放在哪根内存条上"，就是虚拟化在替你操心。
2. **并发（concurrency）**：多个进程/线程同时跑、共享资源，就会有竞态、死锁、需要同步（02/10/11 篇）。C++ 并发篇讲的 mutex、条件变量，OS 层面有对应物（futex）。
3. **持久化（persistence）**：断电不丢的数据要靠文件系统与磁盘管理（08 篇）。模型权重文件怎么读出来的、`torch.save` 落盘时发生了什么，都归它管。

为什么要费劲虚拟化？三个理由（OSTEP 第 5 章与第 13 章）：**效率**（让多个程序分时复用 CPU，谁也别闲着）、**保护**（一个进程崩溃不能拖垮系统，写坏内存不能踩到内核）、**易用**（给你 `open()`/`malloc()` 这种干净抽象，而不是"往 0x00053f12 这个物理地址写"）。这套"物理资源 → 虚拟资源"的思路你其实已经见过：CUDA 的显存虚拟地址、PyTorch 的 Tensor 抽象，全是同一个设计哲学在不同层级的复现。

**经验做法**：排查性能问题时先问"这个问题落在三大职责的哪个区？"——CPU 忽高忽低看调度（03 篇），内存涨了不回看分配器与缺页（05/06 篇），接口偶发慢看 IO 路径（07/09 篇）。分类能让你少走一半弯路。

## 2. 从 hello.c 到进程：编译、链接、加载、执行全链路

先准备材料。这个程序我们后面几节会反复用：

```c
// hello.c
#include <stdio.h>

int main(void) {
    printf("hello, os\n");   // 别看只有一行，背后是一次系统调用
    return 0;
}
```

一条命令 `gcc hello.c -o hello` 似乎一步就完了，但它其实是四个阶段的流水线（CSAPP 第 1.2 节正是用这个例子开篇）。用 `-v` 参数可以看到每一步，我们拆开手动跑一遍：

```bash
$ gcc -E hello.c -o hello.i    # 1. 预处理：展开 #include，宏替换，得到纯 C
$ gcc -S hello.i -o hello.s    # 2. 编译：C 翻译成 x86-64 汇编
$ gcc -c hello.s -o hello.o    # 3. 汇编：汇编翻译成机器码，产出可重定位目标文件
$ gcc hello.o -o hello         # 4. 链接：把 hello.o 和 C 标准库拼成可执行文件
$ ./hello
hello, os
```

几个值得停下来看的点：

- 预处理产物 `hello.i` 有 800 多行——你只写了一行 `#include <stdio.h>`，它把整个头文件搬了进来。看看：`wc -l hello.i`。
- `hello.o` 还不是可执行文件，它里面的地址是"待定的"（所以叫**可重定位**），链接器（`ld`）负责填上最终的地址、把 `printf` 的实现从动态库 `libc.so.6` 里找出来。`printf` 不在你的程序里，在 libc 里：

```bash
$ ldd hello
        linux-vdso.so.1 (0x00007ffd...)          ← 第 07 篇的主角，先记住它是个"假"库
        libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f...)
        /lib64/ld-linux-x86-64.so.2 (0x00007f...)
```

- 可执行文件是 **ELF** 格式（Executable and Linkable Format），`file` 命令能看到它的身份：

```bash
$ file hello
hello: ELF 64-bit LSB pie executable, x86-64, dynamically linked,
interpreter /lib64/ld-linux-x86-64.so.2, for GNU/Linux 3.2.0, not stripped
```

注意 `pie executable`（位置无关可执行）和 `dynamically linked`（动态链接）两个词，04 篇讲地址空间时它们还会出现。

**链接完成之后程序还没运行**。你在 shell 里敲 `./hello`，真正开始跑前还有两步：

1. shell 调用 `fork()` 复制出子进程、再调用 `execve("./hello")` 把子进程的程序替换成 hello（02 篇手写这个过程）。
2. 内核的**加载器**（load_elf_binary，见 `man 5 elf`）读取 ELF 头，建立这个进程的虚拟地址空间：把代码段、数据段映射进内存，把动态链接器 `ld-linux-x86-64.so.2` 映射进来并先运行它，由它去加载 libc、完成符号重定位，最后才跳到 `_start` → `main`。

也就是说：**进程"出生"时的第一步不是你的 main，而是内核加载 + 动态链接器**。这也解释了一个日常现象——为什么 `python -c "print(1)"` 要几十毫秒而 `hello` 只要 1ms：加载的东西完全不是一个量级。

## 3. 系统调用的本质：syscall 指令与用户态/内核态切换

运行时那个 `printf("hello, os\n")` 到底发生了什么？`printf` 是库函数，它格式化字符串后调用 `write(1, buf, n)`——`write` 才是真正的**系统调用**（system call，OSTEP 第 4 章；`man 2 write`）。

系统调用为什么必须存在？因为 CPU 把指令分成了**特权级**：x86-64 用 Ring 3（用户态）和 Ring 0（内核态），Linux 只用这两个。普通程序跑在用户态，**无权**直接访问磁盘、网卡、别人的内存；这些事只能内核做。所以应用需要服务时，必须"举手"把 CPU 交给内核，这就是系统调用（CSAPP 第 8.1 节；架构细节见《Intel 64 and IA-32 Architectures Software Developer's Manual》Vol.3 第 5 章）。

x86-64 上这个过程由 `syscall` 指令完成（早期 32 位是 `int 0x80`）：

```c
// syscall_demo.c —— 不经由 libc 的 write，直接发起系统调用
#include <unistd.h>   // write 的声明；syscall 号见 man 2 syscall 的架构表

int main(void) {
    // x86-64 上 write 的系统调用号是 1（见 <sys/syscall.h> 的 SYS_write）
    const char msg[] = "hello via raw syscall\n";
    long ret = syscall(1 /* SYS_write */, 1 /* stdout */, msg, sizeof(msg) - 1);
    return (int)ret;
}
```

```bash
$ gcc syscall_demo.c -o syscall_demo && ./syscall_demo
hello via raw syscall
```

一次 `syscall` 指令背后发生的事（顺序是硬性的）：

```
用户态                          内核态
──────                         ──────
syscall 指令，传入系统调用号
   │
   ├─ CPU 切到 Ring 0，切换到内核栈
   ├─ 跳转到内核的系统调用入口（MSR 寄存器预先登记的地址）
   │                            ├─ 按系统调用号查 sys_call_table[]
   │                            ├─ 执行 sys_write（检查参数！地址是否合法）
   │                            └─ sysret 返回，切回用户态和用户栈
   ▼
拿到返回值（rax 寄存器），继续跑
```

成本视角（本系列的核心视角）：这次"举手"不是免费的——保存/恢复寄存器、换栈、TLB/缓存的局部性被打断，一次系统调用大致在**百纳秒到微秒量级**（《Systems Performance》Brendan Gregg 第 3 章给出的经验量级；**经验做法**：热路径上数系统调用次数而不是猜它们贵不贵）。看 07 篇我们会实际测它。

strace 是"数系统调用"的瑞士军刀（`man 1 strace`）。看 hello 的每一次系统调用：

```bash
$ strace ./hello
execve("./hello", ["./hello"], 0x7ffd... /* 26 vars */) = 0
brk(NULL)                               = 0x557d...
mmap(NULL, 8192, ..., PROT_READ|PROT_WRITE, ...) = 0x7f0c...
access("/etc/ld.so.preload", R_OK)      = -1 ENOENT (No such file or directory)
openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3
fstat(3, {st_mode=S_IFREG|0644, st_size=81894, ...}) = 0
mmap(NULL, 81894, ..., PROT_READ, MAP_PRIVATE, 3, 0) = 0x7f0c...
openat(AT_FDCWD, "/lib/x86_64-linux-gnu/libc.so.6", O_RDONLY|O_CLOEXEC) = 3
...                                    ← 动态链接器在加载 libc，十几条系统调用
write(1, "hello, os\n", 10)          = 10   ← 这才是 printf 的真身
exit_group(0)                           = ?
+++ exited with 0 +++
```

三行输出值得逐字读：

- `execve("./hello", ...) = 0`：第一个系统调用，把当前进程"变成" hello（返回 0 表示成功）。
- `-1 ENOENT`：系统调用失败长这样——返回 -1，errno 是 ENOENT（`man 3 errno`）。读 strace 时失败用负号标出，一眼可见。
- `write(1, "hello, os\n", 10) = 10`：写了 10 个字节到 fd 1（标准输出），返回 10。fd（文件描述符）这个概念 08 篇展开，现在只需记住 0/1/2 分别是标准输入/输出/错误。

再感受一下"量级"：`strace -c` 做统计：

```bash
$ strace -c ./hello
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 27.94    0.000832          12        68        65 openat
  6.77    0.000202           8        25            mprotect
  5.95    0.000177           8        22            fstat
 ...
------ ----------- ----------- --------- --------- ----------------
100.00    0.002978          11       271        66 total
```

**一个只打印一行的程序，产生约 270 次系统调用，其中 260+ 次来自动态链接**。这就是"系统调用不是免费的"最直观的证据，也是静态链接、预加载优化存在的理由。

**WSL2 注**：WSL2 是真 Linux 内核，strace 全部可用；但注意 WSL1 时代 strace 结果有差异，本文以 WSL2 为准。`uname -r` 里带 `microsoft-standard` 就说明你在 WSL2。

## 4. shell 如何工作

shell 听起来神秘，其实它就是一个死循环程序：**读一行 → 解析 → fork 一个子进程 → 子进程里 exec 你的命令 → 父进程 wait 等它结束**（OSTEP 第 5 章的 shell homework 正是这么引导的）。理解了这一点，你在 shell 里敲的每条命令都有了心智模型。

用 Python 写一个最小但结构完整的 shell（结构上与真实 shell 相同，只是没有 job control）：

```python
# mini_shell.py —— 最小 shell：读一行，fork+exec+wait
import os, sys

def main():
    while True:
        try:
            line = input("mysh> ")          # 1. 读命令行
        except EOFError:                     # Ctrl-D 退出
            print()
            break
        parts = line.split()
        if not parts:
            continue
        if parts[0] == "exit":
            break
        # 2. fork：复制出一个子进程（OS 的复制-粘贴进程魔法，02 篇深讲）
        pid = os.fork()
        if pid == 0:                         # 子进程走这条路
            # 3. exec：把子进程的程序替换成目标命令
            try:
                os.execvp(parts[0], parts)   # v: 参数列表, p: 按 PATH 搜索
            except FileNotFoundError:
                print(f"mysh: 未找到命令: {parts[0]}")
                os._exit(127)                # 惯例：命令不存在返回 127
        else:                                # 父进程（shell 本体）走这条路
            _, status = os.waitpid(pid, 0)   # 4. wait：等子进程结束并收尸
            code = os.waitstatus_to_exitcode(status)
            if code != 0:
                print(f"mysh: 命令退出码 {code}")

if __name__ == "__main__":
    main()
```

跑起来试试：

```
$ python3 mini_shell.py
mysh> echo hello
hello
mysh> ls /
bin  boot  dev  etc  home  ...
mysh> nvidia-smi
mysh: 未找到命令: nvidia-smi
mysh> exit
```

四件事值得对照真实 bash 深想一层：

1. **fork + exec 的两步分离不是历史包袱**：分离之后才有机会在"复制"和"替换"之间做手脚——输入输出重定向就是在 exec 前把子进程的 fd 1 指到文件（`dup2`），管道就是 exec 前把两个子进程的 fd 接起来（10 篇手写）。现代 Linux 还有 `posix_spawn`/`vfork` 这类合并优化（07 篇讲 fork 的成本时会回到这个话题）。
2. **PATH 搜索发生在 execvp 里**：`execvp` 逐个尝试 `$PATH` 里的目录，第一个成功的生效。`which python3` 告诉你会试中哪个——所以"明明装了却找不到命令"的第一排查动作就是 `which` 和 `echo $PATH`。
3. **退出码是进程间的约定语言**：0 成功、非 0 失败、127 找不到命令、128+N 被信号 N 杀死（`man bash` 的 EXIT STATUS 节）。`&&`、`||`、CI 的成败判定全建立在这个约定上。
4. **父进程必须 wait**：不 wait，退出的子进程会变成僵尸（02 篇实测）。真实的 bash 对"后台命令 + &"选择不立即 wait——这就埋下了僵尸进程的伏笔。

**经验做法**：以后遇到"shell 怪行为"（重定向顺序、后台任务、子 shell 继承了什么），别背规则，直接 `strace -f bash -c '你的命令'` 看它 fork/exec/dup2 的真实序列，一锤定音。

## 常见误区

1. **"gcc 一步到位，所以编译=编译"**：实际是预处理/编译/汇编/链接四步，报错信息会告诉你死在哪一步（`undefined reference` 是链接期，`expected ';'` 是编译期）。分阶段排查是基本功。
2. **"printf 是一个函数调用，没什么大不了"**：printf 是库函数，底层是 write 系统调用；而系统调用伴随用户态/内核态切换。把"库函数"与"系统调用"混为一谈，会让你在性能分析时数错对象（07 篇的 vDSO 更是把这条边界玩出了花）。
3. **"strace 很慢，只在调试崩溃时用"**：`strace -c` 的统计模式开销可控，平时就该用它回答"这个程序在忙什么"——它数的是程序与内核交互的总账，很多"玄学慢"就是某类系统调用暴增。
4. **"shell 是特殊进程，权限不一样"**：shell 和你的 Python 脚本地位完全平等，都是普通用户进程，只是它恰好会 fork/exec。你写的 mini_shell.py 就是证明。

## 本篇小结

- OS 三大职责 = 虚拟化（CPU→进程、内存→地址空间）、并发（同步与通信）、持久化（文件系统）；排查性能问题时先做这个分类（OSTEP 第 1-2 章）。
- `gcc hello.c` 背后是预处理→编译→汇编→链接四步，产物是 ELF；运行前还要经过 execve 与内核加载器、动态链接器的接力（CSAPP 第 1、7 章）。
- 系统调用是用户态进入内核态的唯一正门：`syscall` 指令换栈换特权级，成本百纳秒级起步；strace 是观察它的标准工具，一个 hello 约有 270 次系统调用、其中绝大多数来自动态链接。
- shell = 读入→fork→exec→wait 的普通程序；fork 与 exec 的分离正是重定向与管道的实现入口；退出码是进程间的约定语言。
