# 07 - 工作区利器

## 本篇目标

四个"进阶日常"场景的标准解法：改到一半被打断（stash）、多任务并行（worktree）、仓库套仓库（submodule/subtree）、巨型仓库（sparse-checkout）。每个工具对应一类真实痛点，先看痛点再学工具。

## 1. stash：紧急打断的"抽屉"

痛点：feature 改到一半，线上出 bug 需要立刻切回 main——**未提交的改动不能丢，但也没到能提交的状态**。

```bash
git stash                    # 改动（工作区+index）收进抽屉，工作区干净
git stash push -m "json 导出做到一半"     # 带说明的 stash（强烈建议）
git stash list               # stash@{0}、stash@{1}...（最新在最前）
git stash pop                # 取出最近一个并删除该条目
git stash apply stash@{2}    # 取出指定条目（保留条目）
git stash drop stash@{2}     # 丢弃指定条目
```

要点：

1. **stash 是栈不是分支**——没有消息的 stash 三天后就是"这堆改动是啥"的考古现场，`-m` 成本几乎为零；
2. stash 默认**不含未跟踪文件**（新文件）：`git stash -u` 连 untracked 一起收；
3. **pop 出来可能冲突**（目标分支上同名区域也变了）——按 03 篇冲突流程处理，stash 条目会保留到解决为止（pop 失败不清条目）；
4. stash 的本质：把改动提交成特殊 commit 存在 reflog 可达的 `refs/stash` 上——所以它同样是"对象库里的数据"，不神秘。

## 2. worktree：一个仓库，多个并行工作目录

痛点：比"切分支"更重的并行需求——feature 开发到一半，想**同时**另开一个目录跑 main 的服务/复现另一分支的 bug，而不想把 feature 的半成品 stash 起来。

```bash
git worktree add ../demo-hotfix main    # 把 main 检出到 ../demo-hotfix 目录
git worktree list                        # 列出所有工作树
git worktree remove ../demo-hotfix       # 用完移除
```

语义：多个目录共享**同一个仓库**（同一份对象库、同一批引用），各自有独立的工作区与 HEAD。对比三种并行方案的适用面：

| 方案 | 开销 | 适用 |
| --- | --- | --- |
| 切分支 | 快，但单目录单状态 | 串行切换的场景 |
| stash + 切分支 | 需要整理半成品 | 短暂打断 |
| worktree | 磁盘多一份工作区，仓库共享 | 真正的并行：边跑服务边改代码 |
| 再 clone 一份 | 全量对象库 ×2 | **没必要**（worktree 就是为此发明的，Git 2.5 起支持） |

注意：同一分支不能同时被两个 worktree 检出（引用一致性保护）。

## 3. submodule vs subtree：仓库嵌套的两条路

痛点：项目 A 依赖项目 B（公共库、第三方部署脚本），要"引用"而不是复制粘贴。

### submodule（独立仓库，指针引用）

```bash
git submodule add <url> libs/common    # 记录一个指针：B 仓库在特定 commit
git clone --recurse-submodules <url>   # 克隆时一并拉取子模块
git submodule update --init            # 老仓库补拉子模块
git submodule update --remote          # 更新子模块到其远程最新
```

模型：父仓库记录的是"**B 在 commit X 的状态**"（一个 gitlink 引用），B 的历史独立演进。

- **优点**：边界清晰（B 仍是独立仓库，有自己的 PR/版本）；
- **代价（著名的坑）**：clone 后是空目录要手动 init；父仓库里子模块"处于 detached HEAD"是常态；更新子模块需要"先进子模块提交、再回父仓库提交指针"两步——**流程繁琐但机械，照文档做即可**。

### subtree（把 B 的提交合并进 A 的历史）

```bash
git subtree add    --prefix=libs/common <url> main    # 并入
git subtree pull   --prefix=libs/common <url> main    # 同步
git subtree push   --prefix=libs/common <url> feature # 推回 B
```

- **优点**：A 的使用者**无感知**——clone 普通仓库即可，没有 submodule 的仪式；
- **代价**：A 的历史混入 B 的提交（历史膨胀）；推回 B 的操作较复杂。

**选择经验**：第三方库只想"用"→ subtree（对使用者零成本）；要"参与开发并保持独立发布"→ submodule。两者都不是日常刚需——**需要时回来查即可**。

## 4. sparse-checkout：巨型仓库只检出一角

痛点：monorepo 里你只需要 `services/pay/`，却被迫检出全部 10GB。

```bash
git clone --filter=blob:none <url>    # 部分克隆：先不下载文件内容（按需取）
git sparse-checkout set services/pay  # 只检出指定目录
git sparse-checkout disable           # 恢复全量
```

要点：`--filter=blob:none`（partial clone）让"没检出目录"的文件内容不占本地——浏览历史/切分支时才按需下载 blob；sparse-checkout 控制工作区范围。两者组合是大仓库名副其实的"按需加载"（Chromium、V8 等大型 monorepo 的官方文档都推荐此路径；Git 2.27+ 的 `sparse-checkout` 子命令取代了旧的 core.sparseCheckout 手工配置方式）。

## 5. clean：清掉未跟踪的杂物

```bash
git clean -n                # 预览（干跑，先看要删什么）
git clean -fd               # 删除未跟踪的文件与目录
git clean -fdX              # 只删被 .gitignore 忽略的（构建产物）
```

`clean` 是少数**没有撤销**的命令（未跟踪文件不在对象库里，reflog 管不着）——**先 `-n` 干跑永远是第一步**。
