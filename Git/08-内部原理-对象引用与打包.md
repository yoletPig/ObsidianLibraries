# 08 - 内部原理：对象、引用与打包

## 本篇目标

01 篇建立了对象模型的概念，本篇用**底层命令（plumbing）亲手验证它**，并补上最后两块拼图：引用的存储形态、以及仓库为什么会"自我整理"（packfile 与 gc）。学完本篇，`.git` 目录对你不再是黑盒。

## 1. 两层命令体系

| 层 | 名称 | 例子 | 面向 |
| --- | --- | --- | --- |
| 上层 | porcelain | `add/commit/log/switch` | 人类 |
| 底层 | plumbing | `cat-file/hash-object/ls-tree/rev-parse` | 脚本与"想懂原理的人" |

plumbing 命令稳定性承诺极高（porcelain 的输出格式甚至都偶有微调），是理解 Git 的 X 光机。

## 2. 亲手解剖：从一行文本到一个提交

```bash
mkdir gitlab && cd gitlab && git init -q
echo "hello" | git hash-object --stdin
# → ce013625030ba8dba906f756967f9e9ca394464a
```

`hash-object` 做的事：拼出对象头 `blob 6\0`，接上内容，算 SHA-1。**验证哈希只由内容决定**：

```bash
echo "hello" | git hash-object --stdin     # 再跑一次：完全相同的哈希
printf 'hello\n' | git hash-object --stdin # 注意换行差异 → 不同哈希
```

把这个 blob 真正写进对象库并验证存储位置（`-w` 才写盘）：

```bash
echo "hello" | git hash-object -w --stdin
find .git/objects -type f
# → .git/objects/ce/013625030ba8dba906f756967f9e9ca394464a
#    （前两位哈希做目录名，其余做文件名——松散对象 loose object，zlib 压缩存放）
```

手工搭一个提交（不经过 add/commit）：

```bash
tree=$(git mktree <<< "100644 blob ce013625030ba8dba906f756967f9e9ca394464a	a.txt")
commit=$(git commit-tree $tree -m "手工构造的提交")     # 无父提交（根提交）
git cat-file -p $commit        # tree/author/committer/message 都在
```

**所以 add/commit 的全部本质**：把工作区内容变成 blob → 组织成 tree → 打包成 commit 对象 → 把分支引用指向它。没有任何魔法。

## 3. 引用体系的完整目录

```bash
$ tree .git/refs -L 2     # 分支与标签都是文件
refs/heads/main           # 本地分支
refs/remotes/origin/main  # 远程跟踪引用（04 篇）
refs/tags/v1.0.0          # 标签
```

```bash
$ cat .git/HEAD           # HEAD 是"符号引用"：指向分支而非对象
ref: refs/heads/main
$ git rev-parse HEAD      # 解析成真正的 commit id
$ git symbolic-ref HEAD   # 查看符号指向（detach 后会报"不是符号引用"）
```

- 分支 = `refs/heads/` 下的 41 字节文件（03 篇"指针"的实物）；
- **tag 两种形态**：轻量标签 = 一个纯引用文件；附注标签（`git tag -a`）= 一个真正的 tag 对象（含打标者/日期/消息/GPG 签名，09 篇发版用它）；
- HEAD 在分离状态（detach）直接写着 commit id——"你不在任何分支上，提交将成孤儿"警告的逻辑来源。

## 4. packfile：仓库为什么不会无限膨胀

两个事实的矛盾：① 01 篇说 commit 是全量快照（应该很大）；② 实际 clone 很快、`.git` 不算大。答案是**打包与增量压缩**：

1. **松散对象会被打包**：`.git/objects/pack/*.pack`——gc（`git gc` 自动/手动触发）把大量松散对象压成 pack 文件 + 一个 `.idx` 索引；
2. **pack 内部做增量存储（delta）**：相似的 blob 只存一份全量 + 差异链。同文件的相邻版本 delta 极小——**"全量快照"的模型 + delta 存储 = 两全**（模型简单、存储紧凑）；
3. 触发时机：gc 自动（松散对象过多/定时）、网络传输前（推送/拉取按 pack 协议交换）。

```bash
git count-objects -v      # 松散/打包对象统计
git gc                    # 手动整理（打包+清理）
git verify-pack -v .git/objects/pack/*.idx | head   # 看 pack 内的对象与 delta 链
```

## 5. 排错时直接看仓库的诊断技巧

```bash
git fsck --full           # 完整性检查：孤儿对象、损坏对象全列出来（06 篇救数据的前置命令）
git cat-file -e <hash>    # 某对象是否还存在（exit code）
git log --walk-reflogs    # 用 log 的姿势读 reflog
```

## 6. SHA-1 与安全性的准确认知

常见问题："SHA-1 被攻破了，Git 安全吗？"准确回答（截至 Git 2.4x）：

1. Git 用的 SHA-1 已加入**碰撞检测加固**（SHA-1DC，检测到碰撞攻击构造即报错拒绝），实际构造 Git 对象的碰撞尚未被证实可行；
2. Git 2.29+ 支持 **SHA-256 仓库格式**（实验性，`git init --object-format=sha256`），迁移路径在逐步铺设但尚未默认；
3. 日常风险场景里，**"防止恶意构造碰撞"不是你该担心的**（需要攻击者对你推送内容做极其昂贵的工程）；完整性校验（意外损坏检测）SHA-1 依然胜任。
