# 10 - 高级主题与实战

## 本篇目标（Git 系列收官）

四个高级工具（bisect/hooks/LFS/rerere）+ 一套完整的急救命令卡 + 一个综合实战。学完本篇，你可以称得上"把 Git 讲得清楚、用得放心"。

## 1. bisect：二分定位"引入 bug 的提交"

痛点：`main` 上测试挂了，几百个提交，不知道哪次引入的。

```bash
git bisect start
git bisect bad                    # 当前位置是坏的
git bisect good v2.0.0            # 这个版本是好的 → 开始二分
# Git 检出中间提交 → 你运行测试 →
git bisect good                   # 这个提交是好的 → 继续二分（自动检出下一个中点）
git bisect bad
# ... O(log N) 步后输出："xxx is the first bad commit"
git bisect reset                  # 结束，回到原分支
```

自动化版（测试可脚本化时，一行定位）：

```bash
git bisect start HEAD v2.0.0
git bisect run ./run-tests.sh     # 脚本退出码 0=good 非0=bad，全自动二分
```

两个前提（02 篇埋的伏笔在此兑现）：**历史里每个提交都应可构建**；测试脚本对"该提交时的代码"有效。bisect 是"提交粒度纪律"的直接受益者——历史不可构建的仓库，二分无从谈起。

## 2. hooks：把规范固化到机器

钩子是 `.git/hooks/` 下的可执行脚本，在特定动作前后被 Git 调用。常用者：

| 钩子 | 触发时机 | 典型用途 |
| --- | --- | --- |
| `pre-commit` | commit 前 | 格式化检查、lint、拦截密钥（commit 大文件/疑似密钥即失败） |
| `commit-msg` | 提交消息写好后 | 校验 Conventional Commits 格式（09 篇规范的机器化） |
| `pre-push` | push 前 | 跑测试（别把红推上去） |
| `post-merge` | merge 后 | 自动重装依赖/更新子模块 |

示例：commit-msg 校验（任何 POSIX shell 都能写）：

```bash
#!/bin/sh
# .git/hooks/commit-msg — 校验 Conventional Commits
msg=$(cat "$1")
echo "$msg" | grep -qE '^(feat|fix|docs|refactor|test|chore|perf|build|ci)(\(.+\))?!?: .{1,72}' \
  || { echo "✗ 提交信息不符合规范: <type>(<scope>): <subject>"; exit 1; }
```

**两个工程事实**：

1. **`.git/hooks/` 不随 clone 传播**（安全考虑）——团队共享钩子的标准做法：钩子放仓库内（如 `scripts/hooks/`）+ `git config core.hooksPath scripts/hooks`（2.9+），或用 pre-commit（框架）等工具统一管理；
2. **钩子是"本地防线"不是"安全边界"**：`--no-verify` 可跳过——强制规范必须同时有服务端/CI 检查（09 篇的立场在此技术落地）。

## 3. Git LFS：大文件的正确通道

Git 对大二进制（模型权重、设计稿、数据集）天然低效：每次改动都存新对象，clone 全量拉取。**Git LFS**（Large File Storage，开源项目，GitHub/GitLab/Bitbucket 均支持）的方案：**仓库里存指针文件，真实文件放专用存储**：

```bash
git lfs install
git lfs track "*.safetensors" "*.psd"    # 生成/更新 .gitattributes（要提交！）
git add model.safetensors && git commit -m "feat: baseline 模型"
```

```text
version https://git-lfs.github.com/spec/v1
oid sha256:3f2a...       ← 仓库里存的只是这个指针
size 4059413561
```

- `.gitattributes` 记录 track 规则——**必须先 track 再 add**（后 track 不会自动转换已提交的大文件）；
- LFS 配额按流量/存储计费（各平台政策不同），超大模型考虑对象存储 + 下载脚本，而不是塞 LFS；
- 哪些文件适合 LFS 的判别：**大 + 二进制 + 会更新**。只 add 一次永不再改的大文件，直接入库也可接受（无 delta 增长的困扰）。

## 4. rerere：记住你解决过的冲突

```bash
git config --global rerere.enabled true   # Reuse Recorded Resolution
```

之后每次手工解决冲突都会被记录；同样的冲突再次出现（rebase 链上同一改动碰多次，是 rerere 的主场），Git 自动套用上次的解法，标成待确认。**长 rebases 与长期维护分支的福音**，零成本开启。

## 5. 急救命令卡（收藏页）

```markdown
【迷路了】
git status / git log --oneline --graph --all / git reflog

【改错了想反悔】
未 add        → git restore <file>
已 add        → git restore --staged <file>
刚 commit     → git commit --amend（未推送时）
已推送        → git revert <commit>
本地想回退    → git reset --soft|--mixed|--hard <commit>
rebase 乱了   → git rebase --abort；完成后发现错 → git reset --hard HEAD@{n}

【找不到东西】
删掉的分支    → git reflog 找 id → git branch <name> <id>
丢失的提交    → git fsck --lost-found
某个改动何时引入 → git log -S"关键代码" --oneline；git blame -L 10,20 <file>

【推送问题】
被拒          → git pull --rebase && git push
个人分支更新  → git push --force-with-lease
共享分支      → 永远不 force；回滚用 revert

【性能与仓库健康】
仓库过大      → git count-objects -vH；git gc
大文件        → git rev-list --objects --all | 按大小排序（配合 filter-repo 清历史）
```

## 6. 综合实战：一次完整的"个人开源贡献"

把全系列串成一条真实动线：

```bash
# ① 找到想改的开源仓库 → fork → clone 自己的 fork（04 篇）
git clone git@github.com:you/project.git && cd project
git remote add upstream https://github.com/org/project.git

# ② 同步上游 + 从最新切分支（04/03 篇）
git fetch upstream
git switch -c fix/doc-typos upstream/main

# ③ 开发：小步提交 + 规范消息（02/09 篇；钩子已由 core.hooksPath 启用）
git commit -m "docs: 修正安装文档中的命令拼写"

# ④ 上游有新提交 → 同步（05 篇：个人分支 rebase 安全）
git fetch upstream && git rebase upstream/main
git push --force-with-lease origin fix/doc-typos   # 已推送分支的规范更新方式

# ⑤ 发 PR → 评审意见 → 追加提交（或 rebase -i 整理）→ 合并 → 删分支（04/05 篇）
git switch main && git pull --rebase upstream main
git branch -d fix/doc-typos
```

每一步背后的原理都在前文——这就是本系列的教学目标：**不是背下这条动线，而是每一步都能说出"为什么"**。
