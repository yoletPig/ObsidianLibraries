# 04 - 远程协作

## 本篇目标

1. 理解远程引用的真相：**远程分支是"远程仓库上次联系时的快照"，不是实时状态**——这一条能解释 fetch/pull 的区别、推送被拒的原因、behind/ahead 的含义；
2. 掌握 clone/fetch/pull/push 的正确组合与各自的适用时机；
3. 建立协作的安全习惯：SSH 密钥、推送前检查、被拒后的正确反应。

## 1. 远程仓库与远程引用

远程仓库是另一份完整仓库（含全部对象图与分支），通常托管在 GitHub/GitLab/自建服务上。本地通过 `remote` 记住它的地址：

```bash
git remote -v                       # 列出远程（origin 是 clone 时自动命名的默认远程）
git remote add upstream <url>       # 常见第二远程：fork 工作流里的"上游官方仓库"
```

**关键事实**：`git clone` 后本地出现的 `origin/main` 这样的"远程分支"，是**远程跟踪引用（remote-tracking ref）**——存储在 `.git/refs/remotes/origin/` 下的本地指针，记录"**上次与 origin 通信时**，它的 main 在哪"。它不会自动更新，只有 fetch 才刷新。

这条事实的三个推论（背下来，能解开大部分初学者困惑）：

1. `git fetch` 只是**更新这些快照**（把 origin 的新对象下载下来），**不动你的任何分支**——所以 fetch 永远安全；
2. `git status` 显示的 "behind 3" 是"你的 main vs 本地缓存的 origin/main 快照"，**要 fetch 后才准**；
3. "同事刚 push 了代码我为什么看不到？"——你没 fetch，看到的只是旧快照。

## 2. 四个命令的分工

```
fetch   ：下载新对象 + 更新远程跟踪引用（只读操作，绝对安全）
pull    ：fetch + （merge 或 rebase）→ 同时更新你的分支（有动作，先想清楚）
push    ：把你的提交上传，并请求对方分支前移到你的提交（被拒条件见 §4）
clone   ：首次获取整个仓库（对象全量 + 建好 origin）
```

**推荐的日常节奏**（把"惊喜"从 pull 里拆出来）：

```bash
git fetch origin
git log HEAD..origin/main --oneline    # 先看：远程发生了什么
git log origin/main..HEAD --oneline    # 我有哪些没推的
git pull --rebase                      # 确认无碍再合入（用 rebase 避免无谓的 merge commit；02 篇的配置项）
```

直接 `git pull` 不是错——它只是把"看"和"合"两步合并，让你在合并发生前失去了检查的机会。

## 3. 推送被拒（rejected / non-fast-forward）：发生了什么

```
! [rejected]        main -> main (fetch first)
```

原因：**你要前移的远程分支上，有你本地没有的提交**（同事先推了）。Git 拒绝是保护机制——如果允许，同事的提交会凭空消失（他们的提交不在你父链条上，等于被你"覆盖"）。

正确反应（永远不是 `--force`）：

```bash
git pull --rebase          # 把你的提交摘下来，重放到远程最新之上，再推
git push
```

**关于 force push 的立场**：`--force-with-lease` 是带保险的强制推送（仅当远程引用仍是你 fetch 时的快照才执行，防止覆盖别人刚推的提交）。它**只允许用于"你确认独占的分支"**（如你个人的 PR 分支 rebase 后更新）——**对共享分支（main）强制推送属于团队纪律的重大事故**，需要流程审批的那种。

## 4. 认证：HTTPS vs SSH

| 方式 | 配置 | 适用 |
| --- | --- | --- |
| HTTPS + 凭据 | PAT（个人访问令牌）+ credential helper 缓存 | 简单快速；令牌比密码安全（可限权可吊销） |
| SSH 密钥 | `ssh-keygen -t ed25519` → 公钥贴到平台 → `git@...` 地址 | 日常开发推荐：免密、密钥不出本机 |

```bash
ssh-keygen -t ed25519 -C "you@example.com"
cat ~/.ssh/id_ed25519.pub        # 公钥添加到平台设置（私钥永远不离开本机）
ssh -T git@github.com            # 验证
```

安全纪律：**令牌/私钥只放本机安全位置，不进仓库**（02 篇 ignore 的极端重要性）、公钥可随意分享、换机器重新生成。

## 5. PR/MR 工作流（现代团队的事实标准）

```
1. 从 main 切 feature 分支（03 篇）
2. 开发 + 小步提交（02 篇粒度）
3. push 到远程同名分支（不是直接推 main！）
4. 发起 Pull Request / Merge Request：diff 可视化 + 代码评审 + CI 检查
5. 评审意见 → 分支上追加提交 → 自动更新 PR
6. 合并（平台提供三种方式，见下）→ 删分支
```

平台合并方式的选择（同一组提交，三种"合进 main"的形态）：

| 方式 | 形态 | 适用 |
| --- | --- | --- |
| Merge commit | 保留分支全部提交 + 一个合并节点 | 团队想保留完整过程 |
| Squash | 分支的 N 个提交压成 1 个 | 分支过程杂乱、main 历史要整洁（推荐搭配"分支内自由提交"） |
| Rebase merge | 提交逐个重放到 main 顶 | 想要线性历史又保留单个提交 |

**没有标准答案，但必须全团队统一**——三种混用且无约定，main 的历史语义会变得无法解读（09 篇协作规范把这项写进团队文档）。

## 6. 多远程场景：fork 工作流

开源贡献的标准形态（你无上游仓库的推送权）：

```bash
# fork 官方仓库 → clone 你的 fork（origin = 你的 fork）
git remote add upstream <官方仓库url>
git fetch upstream
git switch -c my-feature upstream/main    # 从上游最新切分支
# ...开发、push 到 origin（你的 fork）、向上游发 PR
git fetch upstream && git pull --rebase upstream main   # 同步上游进展
```
