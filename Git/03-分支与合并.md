# 03 - 分支与合并

## 本篇目标

1. 理解分支的物理本质：**41 字节的指针文件**——理解了它，"分支很重"的旧 VCS 直觉就能彻底扔掉；
2. 掌握三类合并（fast-forward、三方合并、冲突）的机制与处理；
3. 建立分支使用策略：什么时候开分支、分支活多久。

## 1. 分支的真相：一个可移动的指针

01 篇说过：分支只是指向某个 commit 的引用。物理形态是一个文本文件：

```bash
$ cat .git/refs/heads/main
e23ac9f...        # 一行 40 位哈希——这就是"main 分支"的全部
```

所以 Git 的分支操作便宜到离谱：

| 操作 | 旧式 VCS | Git |
| --- | --- | --- |
| 创建分支 | 复制整个目录树（秒~分钟级） | 写一个 41 字节文件（瞬时） |
| 切换分支 | 全量检出 | 更新 HEAD + 校验差异文件 |

心智模型更新：**main、feature-x 都只是同一张 commit 图上的两个游标**。"合并"不是"把数据搬来搬去"，而是"在图上找到共同祖先、算出合并结果、让指针前进"。

## 2. 开分支：标准动作

```bash
git switch -c feature/export-json    # 创建并切换（2.23+；旧写法 checkout -b）
git switch main                      # 切回
git branch -d feature/export-json    # 删除（已合并才允许；-D 强制）
git branch -a                        # 列出所有分支（含远程）
git branch --merged                  # 列出已并入当前分支的分支（清理前的检查）
```

### 分支策略的常识线

- **一个分支只承载一件事**（一个功能/一个修复）——"大杂烩分支"会让 review 与回滚都失效（02 篇提交粒度纪律的分支版）；
- **分支寿命越短越好**：分支活一周，与 main 的漂移就有一周，合并时冲突与风险随寿命**非线性增长**。行业趋势是"小步快合"（09 篇 trunk-based 讨论）；
- **分支名表达意图**：`feat/export-json`、`fix/1642-login-timeout`（带 issue 号）。

## 3. 合并的三种情形

### 3.1 fast-forward（快进）：最理想的情形

从 main 分出 feature 后 **main 没有新提交**，合并时只需要把 main 指针前移到 feature 的头：

```
合并前:  main ──┐
                ├── A ── B ── C  ← feature
合并后:  main ────────（指针直接前移）──→ C
```

```bash
git switch main && git merge feature/export-json
# 输出 "Fast-forward" 即此情形，不产生新 commit
```

### 3.2 三方合并（three-way）：分叉后的合流

main 与 feature 各自前进过 → Git 找到**共同祖先（merge base）**，三方对比（祖先 / 我 / 对方）合成一个**合并提交（merge commit，有两个父提交）**：

```
      A ── B ── D ── E      ← main
       \      \
        C ── F ────────── M ← 合并提交（父=D 和 F）
```

三方对比的意义：祖先告诉 Git"**谁改的**"——祖先中是 X、B 改成了 Y、D 没动 → 取 Y（无冲突）；两边都改了且改得不同 → 冲突。

### 3.3 冲突：不是错误，是"需要人决策"的信号

```
<<<<<<< HEAD
rate = 0.08          # main 上的改法
=======
rate = 0.1           # feature 上的改法
>>>>>>> feature/rate
```

处理流程（固定五步，照做即可）：

```bash
git merge feature/...          # 1. 冲突出现，Git 停在这里，等你
git status                     # 2. "both modified" 列出全部冲突文件
# 3. 逐个打开文件：<<<<<<< 到 >>>>>>> 之间选留/融合，删掉标记行
git add <已解决的文件>          # 4. 标记"此文件已解决"（add 进暂存区）
git commit                     # 5. 完成合并提交（默认消息已写好）
```

**要点**：

1. 冲突标记里的 `HEAD` 是"**你 merge 时所在的分支**"，下面是"被合入的分支"——先弄清方向再决策；
2. 中途想放弃整个合并：`git merge --abort`，一切如初（06 篇撤销体系的成员）；
3. **不是所有冲突都表现为冲突标记**：两边"同文件不同位置"的改动会静默合并——**语义冲突**（各自能编译、合在一起逻辑坏了）只有测试能兜住（09 篇 review 与 CI 的意义）。

## 4. merge 与 rebase 的路线之争（预告）

同样是"把 feature 的成果弄进 main"：

- **merge**：保留真实分叉历史，图上有分叉与合并节点；
- **rebase**：把 feature 的提交"摘下来重放"到 main 顶上，历史变成一条直线（代价：改写历史）。

两者的取舍、黄金法则与实操在 **05 篇**专门展开——本篇只需记住：团队必须**统一约定**用哪种（混用且无约定是冲突事故的主要来源）。

## 5. 场景速查

```bash
# 场景：feature 干到一半，main 有紧急修复要同步过来
git switch feature && git merge main      # 把 main 合进来（或 rebase，05 篇）

# 场景：看看这个分支相对 main 多了哪些提交
git log main..feature --oneline           # feature 有、main 没有
git log feature..main --oneline           # main 有、feature 没有（该不该同步的依据）

# 场景：找回刚删的分支
git reflog                                # 06 篇：指针移动日志里有它的 commit id
```
