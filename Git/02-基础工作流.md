# 02 - 基础工作流

## 本篇目标

把 01 篇的模型变成每天的手感：配置、提交循环、看历史、看差异、忽略文件，以及**提交粒度与提交信息的纪律**——后者决定了仓库两年后还有没有"可读的历史"。

## 1. 首次配置：三处身份与三个必设项

```bash
git config --global user.name  "你的名字"
git config --global user.email "you@example.com"   # 会写进每个 commit，公开仓库=公开信息
git config --global init.defaultBranch main        # 2.28+ 默认分支名（旧版默认 master）
```

三个强烈建议的补充：

```bash
git config --global pull.rebase false    # pull 时 merge 还是 rebase？显式声明，消除 2.27+ 的提示噪音
git config --global core.editor "code --wait"
git config --global credential.helper store   # 凭据缓存（HTTPS 场景）；更安全的选项见 04 篇 SSH
```

配置有三个作用域，**近的覆盖远的**：`system`（全机）→ `global`（用户 `~/.gitconfig`）→ `local`（仓库 `.git/config`）。查看生效值用 `git config --list --show-origin`，能直接看到每条来自哪个文件——排查"我的配置为什么没生效"的第一命令。

## 2. 日常循环：status → add → commit

```bash
git status                 # 永远的第一步：看两个区域的差集（01 篇）
git add app.py             # 暂存单个文件
git add -p                 # 交互式暂存：文件内的部分改动（hunk 级挑选，见 §4）
git commit -m "feat: 支持导出为 CSV"        # 完整提交
git commit --amend         # 补进暂存区的新改动 / 改上一条消息（改历史！仅限未推送，05 篇）
git log --oneline --graph --all   # 看历史：一行一提交 + 图 + 所有分支
```

`git add` 的三档粒度（从粗到细）：`add .`（全部）→ `add <file>`（整文件）→ `add -p`（改动块级挑选）。**日常默认第二档**，第一档仅用于确定没有杂物的场合——顺手 `add .` 把调试代码、密钥、临时文件提交进去，是事故与泄漏的常见入口（02 篇末的密钥事故处理见 06/10 篇）。

## 3. 看差异：diff 的三个基准

```bash
git diff                # 工作目录 vs 暂存区（"改了还没 add 的"）
git diff --staged       # 暂存区 vs HEAD（"add 了还没 commit 的"）
git diff HEAD           # 工作目录 vs HEAD（"所有未提交的改动"）
git diff main..feature  # 两个提交/分支之间的差异
```

与 01 篇的三区域一一对应。读 diff 输出的两个约定：`-` 开头是旧、`+` 开头是新；hunk 头 `@@ -10,7 +10,9 @@` 表示"旧文件第 10 行起 7 行，对应新文件第 10 行起 9 行"。

## 4. 提交粒度：一个 commit 一件事

**提交的单位不是"一天的活"，而是"一个可独立描述、可独立回滚的完整变更"**。粒度纪律：

1. **逻辑内聚**：修一个 bug 的代码 + 它的测试 = 一个 commit；顺手发现另一个问题？单独提交（`git add -p` 就是为此准备的）；
2. **编译可用**：任何 commit 单独 checkout 出来都应能构建/通过测试（bisect 10 篇依赖这条性质才能二分定位）；
3. **大小适中**：几百行的"重构+新功能"混在一个 commit，review 无法读、回滚无法精——拆。

## 5. 提交信息：为未来的自己与同事写

业界广泛采用的格式是 **Conventional Commits** 风格（09 篇展开）：`<type>: <摘要>`，正文说明**为什么**（what 看 diff 就知道，why 只有你知道）：

```text
feat: 导出模块支持 gzip 压缩

下游报表平台对大文件超时，需要可压缩的导出。
压缩放在加密之前（加密后的数据不可压缩）。
```

反面教材（真实的仓库里满是这样的）：`修改`、`fix bug`、`更新代码`、`1`。三个月后 `git log` 里它们等于噪声。

**写好消息的模板**：主题行 ≤ 50 字符、祈使句（"支持"不是"支持了"）、空一行、正文回答"为什么这么改、影响面、风险"。

## 6. .gitignore：让仓库只含有价值的东西

```gitignore
# 依赖与构建产物（可再生成的）
node_modules/
dist/
__pycache__/

# 本地环境与密钥（绝不入库）
.env
*.pem

# 编辑器与系统文件
.idea/
.DS_Store
```

三条关键纪律：

1. **先写 ignore 再开工**——等文件已被跟踪再加 ignore 不会生效（跟踪状态优先于 ignore 规则），要先 `git rm --cached <file>` 停止跟踪（06 篇详解这个"从仓库摘除但不删本地"的命令）；
2. **"能再生成的不入库"**：依赖目录、构建产物、虚拟环境——判断标准是"删掉后能否由仓库内容完整重建"；
3. **密钥入库 = 事故**：哪怕随后删除，历史里仍然存在（01 篇：commit 不可变），需要历史清除手术（10 篇 filter-repo）+ 立即换密钥。`uv.lock` 这类**锁文件则必须入库**（它锁定的是可复现的依赖图，见 uv 系列）。

## 7. 最小工作流检查清单

```markdown
□ 开工前 git status / git pull？
□ 改动前想好"这次提交要干什么"？
□ add 用文件粒度，杂物不进暂存区？
□ 提交信息讲清 why？
□ 推送前 log --oneline 扫一眼自己的历史？
```

## 自测

1. `git diff`、`git diff --staged`、`git diff HEAD` 分别对比哪两个区域？
2. 为什么 commit 要"编译可用"？哪条高级功能依赖这条性质？
3. 已跟踪的文件加了 ignore 规则却还在变更列表里——为什么？怎么修？
4. 为什么说"密钥入库后删除不算解决"？
