# 06 - 撤销的艺术

## 本篇目标

Git 的撤销命令之所以让人害怕，是因为它们同时管着**三个区域**（01 篇）的至少两个。本章把每个"后悔场景"映射到**唯一**正确的命令，并把 `reset` 的三种模式一次讲透；最后是全 Git 最重要的救命知识——**reflog**。

## 1. 撤销决策表（先背表，再懂原理）

| 场景 | 命令 | 动到什么 |
| --- | --- | --- |
| 工作区改动不要了（未 add） | `git restore <file>` | 工作区 |
| add 错了/暂存区想清空 | `git restore --staged <file>` | 仅 index |
| 最后一个提交消息写错（未推送） | `git commit --amend` | 新 commit 替换旧 |
| 提交漏了文件（未推送） | `git add <file>` + `git commit --amend` | 同上 |
| 想撤销**已推送**的提交 | `git revert <commit>` | 生成反向提交，安全 |
| 本地回退到某个提交 | `git reset --soft/--mixed/--hard` | 见 §3 |
| 从仓库里"摘除"已跟踪文件（保留本地） | `git rm --cached <file>` | 仅 index |
| 一切都乱了 | **`git reflog`** → `git reset --hard HEAD@{n}` | 见 §5 |

## 2. restore：两个区域各一个开关

Git 2.23 把老 `checkout` 的撤销职责拆给 `restore`，语义从此直白：

```bash
git restore <file>              # 工作区 ← index（丢弃工作区改动，index 不动）
git restore --staged <file>     # index ← HEAD（把文件移出暂存区，工作区不动）
git restore --source=<commit> <file>   # 从任意提交恢复文件内容（跨时间拷贝）
```

记忆法：restore 的意思是"**把某区域恢复成某来源的样子**"，`--staged`/`--source` 就是在指定"目标区域"与"来源"。

## 3. reset：三种模式，一个图讲清

`git reset <commit>` 把**当前分支指针**移到 `<commit>`，三种模式决定"工作区与 index 怎么处理"：

```
                 ┌─ --soft   ：只动 HEAD/分支指针（改动全保留在 index+工作区）
HEAD ← index ← 工作区
                 ├─ --mixed  （默认）：动指针 + 重置 index（改动保留在工作区，未暂存）
                 └─ --hard   ：三个全动（未提交的改动【永久】消失）
```

```bash
git reset --soft HEAD~1    # 提交做错了想重组：回到"已暂存未提交"状态
git reset --mixed HEAD~2   # 默认：两个提交撤销，改动留在工作区自己重新整理
git reset --hard abc123    # 彻底回到某状态 ⚠ 未提交改动不可恢复（reflog 只救已提交的）
```

**记忆锚点**：soft = 撤销提交动作，mixed = 撤销提交+暂存动作，hard = 连工作区一起抹平。**hard 是唯一真正丢数据的**，按下回车前问一遍"我有没有没提交的东西"。

## 4. revert：已共享历史的唯一合法撤销

`git revert <commit>` **不做删除**，而是生成一个"反向提交"（内容正好抵消目标提交），历史只增不减：

```
A ── B ── C ── D ── C'      C' = revert(C)：内容上是 C 的镜像
```

为什么已推送的提交必须用 revert 而不是 reset+force：

1. 共享历史被所有人本地持有——改写会制造 05 篇描述的平行历史灾难；
2. revert 保留了"曾经发生过、后来撤销了"的完整事实——审计友好；
3. revert 撤销**中间**的某个提交时若有冲突，同样按 03 篇流程解决。

团队实践：**main 上的回滚永远用 revert**（09 篇的发布回滚流程即基于此）。

## 5. reflog：Git 的黑匣子

**每个引用（含 HEAD）的每次移动都被记录**在 `.git/logs/` 里：

```bash
$ git reflog
a1b2c3d HEAD@{0}: commit: feat: xxx       ← 现在
e4f5g6h HEAD@{1}: rebase (finish)         ← 5 分钟前 rebase 完
i7j8k9l HEAD@{2}: rebase (start)          ← rebase 前
m0n1o2p HEAD@{3}: reset: moving to HEAD~1 ← 更早的一次 reset
...
```

"误 reset / 误 rebase / 删了分支 / amend 丢了改动"——全部有救：

```bash
git reflog                                   # 找到出事前的位置（HEAD@{n}）
git reset --hard HEAD@{3}                    # 整个仓库回到那时
# 或只救某个文件：
git restore --source=HEAD@{3} <file>
# 或救回被删分支：
git branch feature-rescued <那个commit id>
```

两个必须知道的边界：

1. **reflog 只救"进入过对象库的"东西**——`--hard` 时未提交的工作区改动从未成为对象，救不了（所以 02 篇要求勤提交小步提交）；
2. **reflog 是本地的、默认保留 90 天**（gc 后不可达对象默认 30 天清理，`gc.reflogExpire` 可配）——它是安全网不是保险箱，出了事**当天处理**。

## 6. 三个真实事故的处置剧本

**① 密钥提交了（已推送）**：立即作废密钥（比清历史更急）→ 历史清除（`git filter-repo` + force push，10 篇）→ 团队同步重新 clone。顺序不能反——历史清除只是"眼不见"，密钥作废才是止损。

**② reset --hard 丢了一堆未提交改动**：能试的绳索：IDE 本地历史（多数编辑器有）、`git fsck --lost-found`（若有 add 过则 blob 还在）。救回率不高——**这就是小步提交纪律存在的理由**。

**③ 合并了不该合并的分支（已推送）**：`git revert -m 1 <merge-commit>`（撤销合并提交需要 `-m` 指定保留哪条父线，这是 revert 的特例，文档有专述）。
