# 09 - 团队协作流程与规范

## 本篇目标

前 8 篇都是个人技艺；团队开发的难点在**约定**：分支怎么开、历史怎么整理、提交怎么写、评审怎么过。本章把可落地的约定讲透，并诚实讨论两个主流工作流的取舍——**没有最优工作流，只有与团队规模/发布节奏匹配的工作流**。

## 1. 两个主流工作流的取舍

### Feature Branch + PR（当前行业事实标准）

```
main（受保护）← PR ← feature/*（短命分支，1~3 天）
```

- **main 始终可发布**：受保护分支（禁止直推、强制 PR 评审 + CI 通过）；
- 每个变更有 review、有 CI、有归属（PR 号）；
- **分支短命是生命线**（03 篇的结论在团队维度的复述）：寿命长的 feature 分支 = 大爆炸合并 = review 无法读 + 冲突地狱。解法：功能拆薄（feature slicing）或用 feature flag 把"未完成"与"未发布"解耦（未完成的代码合入但被 flag 关闭）——这是 trunk-based 的思想来源。

### Trunk-Based Development（主干开发）

```
main（唯一长期分支）← 所有提交（小步直推或短命分支 <1 天）+ feature flags
```

- Google 等公司公开描述的工程实践；**全员基于主干**，用 flag 控制发布面，配合"发布即打 tag"；
- 优点：没有长分支、合并永不痛、发布与开发解耦；
- 前提：**成熟 CI/CD + 测试文化 + feature flag 基建**——没有这些前提的团队照搬，等于取消 review 直接裸奔。

### GitFlow 为什么渐被冷落（诚实陈述）

经典 GitFlow（develop/release/hotfix 多层分支，Vincent Driessen 2010 年提出）适合**多版本并行维护、发版周期长**的软件（如桌面软件、版本化交付）；作者本人后来也撰文指出：对持续部署的 Web 服务，它过重（多层分支的维护成本超过收益）。**选择依据是发布模式，不是时髦度**：SaaS/持续部署 → trunk 或轻量 feature branch；多版本交付 → 才考虑 GitFlow 类。

## 2. 分支命名与 main 的保护规则

```text
feat/export-json        fix/1642-login-timeout    chore/deps-bump
```

`main` 保护规则（平台设置）的标配：

- 禁止直接 push，只接受 PR 合并；
- 至少 1 个 approve + 状态检查（CI）通过才能合；
- 禁止 force push、禁止删除（06 篇黄金法则的制度化）。

## 3. 提交规范：Conventional Commits 落地

02 篇讲了个人的消息纪律；团队版加上**机器可解析**的诉求：

```text
<type>(<scope>): <subject>

[body]

[footer: BREAKING CHANGE / Closes #123]
```

- type 枚举：`feat`（新功能）/`fix`（修复）/`docs`/`refactor`/`test`/`chore`/`perf`/`build`/`ci`；
- **机器红利**：type → 自动生成 CHANGELOG；`BREAKING CHANGE:` footer 或 `!`（`feat!:`）→ 自动升级主版本号（语义化版本 SemVer：MAJOR.MINOR.PATCH 的变更判定可以完全自动化）；
- 主题行 ≤ 50 字符、祈使句、不加句号（02 篇模板的团队版）；
- 落地靠 **CI 检查**（commit-msg 校验钩子/平台检查），靠自觉的规范三个月后必然名存实亡（10 篇 hooks 实现校验）。

## 4. 代码评审：Reviewer 与 Author 的双向纪律

评审的意义排序：**知识共享 > 质量把关 > 风格统一**（风格交给格式化工具与 CI，人时不该花在缩进上）。

**Author 的义务**（评审成本由 PR 作者控制）：

1. **PR 小而聚焦**：≤ 400 行的 diff 评审质量显著更高（业界对评审效率的普遍经验值；Cisco 对大型 PR 的研究结论与之同向——大 PR 的缺陷检出率低）；过大就拆 PR；
2. PR 描述写清：做什么/为什么/怎么验证（测试证据贴出来）；
3. 评审意见处理后在对话里显式回应（"已改：xxx"），不留悬案。

**Reviewer 的义务**：

1. 及时（24h 内至少首轮反馈——评审瓶颈是阻塞整个团队的单点）；
2. 批评代码不批评人；意见分级：**[must] 必须改**（bug/安全/规范）与 **[nit] 建议改**（可自行取用）——不带级别的意见作者无法排序；
3. 有疑问先问再猜（"这里为什么锁两秒？"优于"这个锁不对"）；
4. **approve 不是免责**：合入后出问题，评审人与作者共同担责（这条写进团队文化比写进文档更有效）。

## 5. 版本与发布：tag 的正确用法

```bash
git tag -a v2.1.0 -m "发布 2.1.0：含导出模块"   # 附注标签：tag 对象（08 篇），发布标配
git push origin v2.1.0                          # tag 不随 push 自动上传
git tag -s v2.1.0 -m "..."                      # GPG 签名标签（验证发布者身份）
```

- **SemVer 语义**：破坏性变更 → MAJOR+1；向后兼容的新功能 → MINOR+1；修复 → PATCH+1。配合 Conventional Commits 可自动判定（§3）；
- 发布 = 从 main 打附注标签（+ CI 按标签构建产物）。**"从哪个 commit 发的版"永远可回答**——这是 tag 的第一价值。

## 6. 团队协作规范的最小模板（拿去改）

```markdown
# 协作规范 v1
- 分支：main 受保护；feature 分支 <1 周；命名 feat/fix/chore + 短语
- 提交：Conventional Commits；PR ≤ 400 行；描述含"怎么验证"
- 合并：squash merge（统一）；合并前 1 approve + CI 绿
- 评审：24h 首响；[must]/[nit] 分级
- 发布：main 打附注 tag vSemVer；从 tag 构建
- 历史改写：只允许个人未合入分支；main 只用 revert
```

**规范的生命周期**：写下来（不写=不存在）→ CI 固化（不固化=靠自觉）→ 每季度复盘修订（不变=会过时）。
