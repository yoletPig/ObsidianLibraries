# 08 - 权限与沙箱安全

## 本篇目标

1. 建立 Agent 权限模型的核心原则：**最小权限 + 能力分级 + 人审门 + 纵深防御**；
2. 掌握工具分级的实现方法；
3. 了解文件系统与网络层面的沙箱技术选项；
4. 理解"审计日志为什么是权限体系的一半"。

先立一个认知：**权限问题的本质不是"防模型学坏"，而是"防止错误被授权放大"**。即使模型完全不带恶意（07 篇的错误级联），一个拥有 `rm -rf` 能力的 Agent 也会因为一次误判造成灾难。权限系统是你的代码、不是模型，说了算的最后防线。

## 1. 四原则

### 原则一：最小权限（least privilege）

Agent 只应拿到**完成当前任务所需的最小能力集合**。落地为两条铁律：

1. **不注册的工具不存在**：模型无法调用没在工具注册表里的能力（03 篇）。给客服 Agent 挂上 `execute_sql` 再加限制，不如一开始就不挂；
2. **凭据也最小化**：Agent 使用的数据库账号应只读、限表、限行；API key 用 scope 最小的；**绝不把用户的完整凭据透传给 Agent 环境**。

### 原则二：能力分级（risk tiers）

按副作用把每个工具划入风险等级，**等级决定执行策略**：

| 等级 | 定义 | 例子 | 执行策略 |
| --- | --- | --- | --- |
| T0 只读 | 无副作用、不泄露敏感数据 | 查天气、读公开文件 | 自动放行 |
| T1 可逆写 | 可撤销的本地修改 | 新建草稿文件、写缓存 | 放行 + 记审计日志 |
| T2 敏感读 | 读隐私/凭据类数据 | 读用户通讯录、读 `.env` | 放行前脱敏或确认一次 |
| T3 不可逆/外发 | 删除、发送、支付、发布 | `rm`、发邮件、调用支付 API | **强制人审**，展示 diff/摘要 |

```python
from enum import Enum, auto
from dataclasses import dataclass

class Risk(Enum):
    T0_READ = auto()
    T1_REVERSIBLE_WRITE = auto()
    T2_SENSITIVE_READ = auto()
    T3_IRREVERSIBLE = auto()

@dataclass
class ToolSpec:
    fn: callable
    risk: Risk

POLICY = {
    Risk.T0_READ: "auto",
    Risk.T1_REVERSIBLE_WRITE: "auto_log",
    Risk.T2_SENSITIVE_READ: "confirm_once_per_session",
    Risk.T3_IRREVERSIBLE: "human_approval",
}

def gate(spec: ToolSpec, args: dict, session) -> bool:
    """执行前的权限门。返回 False 则拒绝执行。"""
    action = POLICY[spec.risk]
    if action == "auto":
        return True
    if action == "human_approval":
        # 展示将要做的事，等待人工批准（CLI 询问 / Web 确认按钮）
        return session.ask_human(
            f"请求执行【不可逆操作】{spec.fn.__name__}，参数：{args}\n批准？(y/N)"
        ).lower().startswith("y")
    return True  # 其余等级：放行，配合审计日志
```

### 原则三：人审门（human-in-the-loop, HITL）

T3 操作的审批界面要满足三条，否则审批形同虚设：

1. **展示具体 diff/参数**，不是"Agent 请求执行 tool_x"这种黑盒话术——人无法审批看不懂的东西；
2. **默认拒绝**（deny by default）：超时、用户离开都算拒绝；
3. **支持"本次会话内记住选择"与"永久规则"两级缓存**，否则审批疲劳会让用户无脑全点"是"（这是 HITL 系统的真实失败模式：审批疲劳 → 全部放行 → 权限系统名存实亡）。

### 原则四：纵深防御（defense in depth）

**不要把宝押在任何单层上**。提示词里的"请勿删除文件"会被注入攻破（09 篇）、会被模型"忘记"（07 篇）。层次应是：

```
提示词约束（软）→ 工具级校验（参数/schema）→ 权限门（分级/审批）
→ 沙箱（OS 级隔离）→ 审计与告警（事后可追责/可回滚）
```

每一层都假设上一层会被突破。其中**只有 OS 级沙箱和权限门是模型绕不过去的**——这两层是硬防线。

## 2. 沙箱：把"就算模型疯了也出不了笼子"落到实处

按成本从低到高的常见选项（同一系统可叠加多层）：

### 文件系统与进程层

- **专用工作目录**：Agent 只能在 `./workspace` 内读写；以该目录为 cwd 启动，配合路径校验（警惕 `../` 逃逸与符号链接）；
- **专用低权限账号**：Linux 下用 nobody 或专用用户跑 Agent 进程；不挂载敏感目录；
- **容器隔离**：Docker 容器 + 只读根文件系统 + `--cap-drop=ALL` + 限网络，是性价比很高的标准做法；
- **gVisor / Firecracker**：需要更强隔离（运行不可信代码、多租户）时的用户态内核/微虚拟机方案，Google App Engine 等生产系统的技术基础。

### 网络层

- **默认断网**：不需要网络的 Agent 直接禁网（容器 `--network none`），这是最有效的单条措施——既防数据外泄（exfiltration），也防注入攻击者远程回连；
- 需要网络时用**白名单代理**：只允许访问列出的域名（工具 API 端点），所有出站经代理校验。

### 代码执行类工具

Agent 经常需要"跑代码"工具（数据分析场景）。要点：

- 永远在沙箱内执行（容器/微虚拟机），限制 CPU/内存/时长/网络；
- 不要试图用"提示词 + 字符串黑名单"过滤危险代码——黑名单必然遗漏，这是业界共识；
- 成熟方案如各类沙箱运行时（例如 Anthropic 官方演示的容器化 code execution 工具、E2B 等第三方沙箱服务），选型以各自文档为准。

## 3. 审计日志：权限体系的另一半

没有审计的权限系统在出事后**无法回答"发生了什么"**。最小审计字段：

```json
{
  "ts": "2026-11-06T10:00:00Z",
  "session_id": "s-123",
  "tool": "delete_file",
  "args": {"path": "workspace/draft.txt"},
  "risk_tier": "T3",
  "approval": {"type": "human", "by": "user-alice", "decision": "allow"},
  "result": "success",
  "agent_step": 14
}
```

实践要点：追加写（append-only）、含审批记录、定期 review 异常模式（如某会话 T3 操作激增）、与回滚机制联动。

## 4. 提示词约束的正确位置

最后强调一次层次关系，因为它最容易被搞错：**提示词约束是第一道软防线，不是唯一防线**。

- 它值得写：告诉模型"执行删除前必须确认"能降低误操作概率、改善人审界面展示的内容；
- 它不可信：提示注入（09 篇）可以让模型"合法地"违反一切提示词约束；
- 所以：**安全判断必须放在模型之外的代码里**（gate 函数、沙箱），提示词只是体验层。
