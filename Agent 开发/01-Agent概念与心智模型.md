# 01 - Agent 概念与心智模型

## 本篇目标

读完本篇，你应该能回答三个问题：

1. Agent 和普通"调一次 LLM"有什么区别？
2. Agent 和工作流（workflow）有什么区别？什么时候该用哪个？
3. 一个 Agent 系统由哪几块组成？

先建立一个反直觉的认知：**Agent 不是更高级的聊天机器人，而是"让 LLM 参与控制流"的系统**。这个词目前没有统一标准定义，我们采用业界引用较多的一种描述。

## 1. 三个容易混淆的概念

### 聊天机器人（chatbot）

```
用户输入 → LLM → 文本输出
```

单轮或多轮对话，模型只产出**文字**。它不能查数据库、不能改文件、不能下单。所有"行动"都止步于文字。

### 工作流（workflow）

```
用户输入 → [步骤A] → [步骤B] → [步骤C] → 输出
              ↑ LLM      ↑ LLM
```

开发者**预先写死**了执行路径：先做什么、后做什么、失败怎么兜底。LLM 在其中扮演某些步骤（比如总结、分类、抽取），但**控制流是人写的代码决定的**。

Anthropic 在《Building Effective Agents》（2024 年 12 月）中把这类模式称为 workflows，并明确区分了 workflows 和 agents：

> Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage...

（翻译：工作流是 LLM 和工具通过**预定义代码路径**编排的系统；Agent 则是 LLM **动态决定自己的流程和工具使用**的系统。）

### Agent

```
用户输入 → LLM（思考：下一步干什么？）
              ↓ 选择工具并给出参数
           执行工具 → 把结果喂回 LLM
              ↑__________________|
           （循环，直到 LLM 认为任务完成）
```

关键区别只有一个：**下一步做什么由 LLM 在运行时决定，而不是由 if-else 写死**。LLM 从"被调用的函数"变成了"调用其他函数的主循环"。

## 2. 一句话定义与心智模型

一个可操作的定义（综合学界与工业界用法）：

> **Agent = LLM 作为决策核心 + 工具作为手脚 + 循环作为生命周期 + 反馈作为感知。**

把它想象成一个"戴着时钟的员工"：

| 人体类比 | Agent 组件 | 说明 |
| --- | --- | --- |
| 大脑 | LLM | 理解目标、拆解任务、决定下一步 |
| 手脚 | 工具（tools） | 搜索、读写文件、调 API、执行代码 |
| 眼睛 | 观测（observation） | 工具执行结果、报错信息，回喂给 LLM |
| 循环 | agent loop | 思考→行动→观测→再思考，直到完成 |
| 规章制度 | 权限与安全层 | 哪些事能做、哪些要人审批（见 08/09 篇） |
| 交接文档 | 记忆/上下文 | 记住做过什么（见 05 篇） |

## 3. 什么时候该用 Agent（什么时候不该）

Agent 的代价是明确的：**成本高**（多轮调用，token 翻倍增长）、**慢**（循环迭代）、**不可预测**（同一任务两次运行路径可能不同）、**难调试**（错误可能来自任何一次决策）。

所以判断标准不是"酷不酷"，而是：

**适合用 Agent 的场景特征：**

- 任务无法预先枚举步骤（"帮我调查这三个竞品的定价策略并写报告"——查什么、查几轮取决于中间结果）；
- 步骤数量大且存在分支（代码修复：可能改 1 个文件，也可能改 5 个）；
- 容忍一定的不确定性，且有**可验证的完成标准**（测试通过、文件存在、答案含引用）。

**不适合、应该用工作流甚至普通调用的场景：**

- 步骤固定（"把这段话翻译成英文再总结"）；
- 需要严格一致性和可审计的固定路径（金融对账、合规审查的固定流程）；
- 延迟敏感（Agent 的多轮循环天然慢）；
- 没有可验证的完成标准——Agent 不知道何时停，就会一直跑或提前放弃。

经验法则（来自 Anthropic 同文的建议精神）：**先用最简单的方案（单次调用 → 工作流），只有当简单方案确实解决不了时，才引入 Agent 的自主循环**。

## 4. Agent 系统的组成解剖

把任何 Agent 产品（Claude Code、ChatGPT 的工具使用、你自己的项目）拆开，都逃不出这六块：

```
┌─────────────────────────────────────────┐
│              Agent 运行时                │
│                                         │
│  ┌─────────┐    ┌──────────────────┐    │
│  │ 系统提示 │    │   对话/上下文状态  │    │
│  └─────────┘    └──────────────────┘    │
│                                         │
│  ┌────────────────────────────────┐     │
│  │        Agent Loop（主循环）      │     │
│  │  LLM → 工具选择 → 执行 → 回喂    │     │
│  └────────────────────────────────┘     │
│         │              │                │
│  ┌──────▼─────┐  ┌─────▼─────────┐      │
│  │ 工具注册表   │  │ 权限/安全检查  │      │
│  └────────────┘  └───────────────┘      │
└─────────────────────────────────────────┘
```

1. **系统提示（system prompt）**：角色、目标、约束、工具使用规范。
2. **工具注册表**：每个工具的名字、描述、参数 JSON Schema——LLM 靠这些描述来决定用不用、怎么用。
3. **主循环**：核心调度逻辑，02 篇手写一个。
4. **权限/安全层**：在工具真正执行前做检查（08 篇）。
5. **上下文状态**：对话历史 + 工具结果，需要管理长度（05 篇）。
6. **终止条件**：任务完成、达到步数上限、触发权限拒绝——**没有终止条件的 Agent 是定时炸弹**。

## 5. 常见误区

**误区一："Agent = 某个框架"。** LangChain、AutoGen、CrewAI 是封装了上述组件的库，不用框架完全可以从 200 行代码写出一个 Agent。理解原理比会用框架重要，这也是本系列先手写再谈框架的原因。

**误区二："Agent 越自主越强"。** 自主性是和能力验证、权限控制兑换来的。给 LLM 更多决策自由，同时必须给它更强的护栏，否则错误会复利放大（07 篇详述）。

**误区三："我的应用调了工具，所以是 Agent"。** 如果"先查库再回答"是代码写死的固定两步，那是工作流。判断标准回到控制流归谁。
