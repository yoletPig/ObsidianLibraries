# 12 - 进阶：长任务 Agent 与规划

> 进阶篇第 2 章。基础篇的 Agent 处理"几步能完成"的任务；本章处理**几十步、数小时、会失败、需要跨会话续做**的长任务。核心问题只有一个：**如何让 Agent 在任何一步断掉后都能继续，而不是从头再来**。

## 1. 长任务的三重放大效应

把 02 篇的 ReAct 循环直接跑长任务，会同时撞上三堵墙：

1. **误差放大**（07 篇错误级联）：步数 × 单步错误率。单步 2% 错误率，50 步任务的整体失败率 ≈ 1-0.98⁵⁰ ≈ 64%——**不做结构干预的长任务数学上必败**；
2. **上下文耗尽**：50 步的工具结果轻松超出任何窗口；
3. **中断不可避免**：进程崩溃、超时、人工审批挂起。没有持久化的 Agent，中断 = 全部重来。

对应的三个结构干预：**任务分解、计划外置、执行持久化**。

## 2. 任务分解：从目标到可验证的子任务

### 2.1 分解的两种主体

- **一次性分解（plan-then-execute）**：开始时 LLM 产出完整计划，随后逐项执行。适合结构清晰、少有意外的研究/写作类任务；
- **执行中再分解（hierarchical decomposition）**：主 Agent 执行中发现子问题复杂，动态拉起子 Agent 或展开子计划（06 篇 orchestrator 模式的规划化用法）。适合探索性任务——不看到中间结果无法制定后续计划。

经验法则：**计划只对"当前可预见范围"负责**。让 Agent 写 50 步的详细计划通常是浪费——第 10 步之后的世界基本会变。正确姿势是"粗粒度全局计划 + 细粒度滚动执行"。

### 2.2 好的子任务长什么样

一个可执行的子任务单元满足三条（与软件工程的 task slicing 同构）：

1. **单一交付物**：一个文件、一个函数、一份报告——能被明确检查"是否完成"；
2. **独立性**：重做这个子任务不需要重做其他已完成子任务（决定断点续做的成本）；
3. **小而完整**：预计 ≤ Agent 单次会话能可靠完成的规模（经验上 5~15 步）。

```text
❌ 坏分解："研究并实现用户系统"          —— 无法验证完成，跨度太大
❌ 坏分解："写 1 个函数"                —— 粒度过碎，编排开销 > 收益
✅ 好分解："实现 auth 模块的登录接口 + 单元测试（含密码哈希）"
```

### 2.3 分解质量的守门：交付物先行

让 Agent **先定义每个子任务的验收标准，再开始执行**。这条纪律来自 Anthropic《Building Effective Agents》的精神（把验证交给确定性检查）与 07 篇"可验证的完成标准"：验收标准写在计划里，执行时就能程序化判定（测试通过/文件存在/schema 校验），不需要模型"感觉做完了"。

## 3. 计划外置：一份可编辑的持久化文档

基础篇（05）的状态外置在长任务下升级为**计划文档（plan file）**模式：

```markdown
# PLAN.md（Agent 维护，人可随时查看/修改）
## 目标
把 /downloads 整理为分类目录并生成报告；不删除任何文件。

## 验收标准
- [ ] 无散落文件；- [ ] report.md 存在且计数正确；- [ ] 审计日志无 delete

## 子任务
- [x] 1. 扫描目录，产出文件清单（完成：137 个文件）
- [ ] 2. 设计分类方案 ← 当前步骤
- [ ] 3. 批量移动（分段执行，每段 ≤ 50 个文件）
- [ ] 4. 生成报告 + 自检三条验收标准

## 已知问题 / 教训
- 两个文件名含空格，move 工具已确认支持
```

设计要点：

1. **计划是 Agent 与人共享的界面**：人可以中途编辑 PLAN.md 修正方向（比对话打断更可靠），Agent 每个子任务开始前重读计划——这就是人审与方向控制在长任务中的落地形态；
2. **当前指针必须显式**（"← 当前步骤"）：会话重启后 Agent 第一件事是读计划找指针，而不是猜进度；
3. **教训区是 11 篇"负面清单回写"的任务内版本**：失败尝试的结论直接落在计划文档里，跨会话也在。

## 4. 执行持久化：checkpoint 与幂等重放

### 4.1 事件溯源式的执行日志

把 Agent 的每一步记为**不可变事件**（不是可变状态），这是数据库领域的 event sourcing 模式：

```python
@dataclass
class StepEvent:
    seq: int            # 单调递增
    step_type: str      # "llm_call" | "tool_result" | "approval" | "checkpoint"
    payload: dict
    ts: str

def resume_from_log(log: list[StepEvent]) -> AgentState:
    """崩溃后重放事件日志，恢复到崩溃前的确定状态。"""
    state = AgentState.initial()
    for ev in log:
        state = apply(state, ev)     # apply 必须是纯函数
    return state
```

重放能工作的前提是 **apply 是确定性的**：LLM 调用的输出作为事件存入日志（重放时直接读取，不重新调用模型——既省钱又保证一致）；只有工具执行这类外部作用需要**幂等**处理。

### 4.2 幂等性：重放安全的关键

工具设计成幂等（或可去重）的，重放才不会造成重复副作用：

- **客户端生成 idempotency key**：写操作带唯一键（如 `move_file` 记录 `(src, dst, task_id)`），重放时跳过已生效的操作（先检查目标是否已存在）；
- **状态检查式工具**：工具内部先查"是否已经做过"再做——`ensure_dir` 优于 `mkdir`（mkdir 已存在时报错，ensure 幂等）；
- **不可幂等的操作外提**：发邮件这类天然不可撤销的操作，放到"待审批队列"由人触发，而不是让 Agent 循环里直接执行（08 篇 T3 分级的长任务强化版）。

### 4.3 断点续做的完整流程

```text
崩溃/中断
  → 新会话启动，读取 PLAN.md（宏观位置）+ 事件日志（微观状态）
  → 重放恢复 state → 从最后一个 checkpoint 继续执行
  → 人改过 PLAN.md？以 PLAN.md 为准重新校准子任务边界
```

## 5. 长任务的失败模式（07 篇的进阶版）

| 模式 | 长任务特有表现 | 干预 |
| --- | --- | --- |
| 计划漂移 | 执行到中段，实际路径早已偏离计划，但计划文档未更新 | 每完成一个子任务强制更新 PLAN.md（作为子任务的完成动作之一） |
| 局部最优陷阱 | 在某个子任务里反复尝试同类方法（07 篇死循环的长任务版） | 子任务设步数预算；超预算则"带结论文档，请求重新规划" |
| 上下文世代退化 | 经多次摘要后，早期关键约束被压缩丢失（11 篇摘要损耗的累积） | 约束常驻系统提示/计划文档，不依赖对话历史保存 |
| 隐性完成感 | 模型把"大部分完成"当作"完成"，跳过验收 | 验收标准程序化检查；检查不过 = 子任务未完成 |

## 6. 一个完整的例子：跨会话的代码迁移任务

把"将 utils.py 拆分为包"作为长任务推演一遍：

1. **规划阶段**：Agent 读代码 → 产出 PLAN.md：目标、验收（全测试通过 + 无循环 import）、5 个子任务（每子任务 1~2 个模块 + 测试）；
2. **执行阶段**：逐子任务执行，每步事件入日志；每个子任务结束：跑全量测试（子任务级验收）→ 更新 PLAN.md 勾选 → checkpoint；
3. **中断**（如审批挂起）：状态在日志里，PLAN.md 指示进度；
4. **续做**：新会话读日志重放 → 从"子任务 3"继续；
5. **收尾**：整体验收 → 教训写入长期记忆（"此类迁移要先跑 import 图分析"）→ 生成变更报告。

注意每一步都有**可验证的完成定义**和**持久化锚点**——这就是长任务与"跑得久"的区别：**长任务不是跑更多步的短任务，而是另一类系统设计**。
