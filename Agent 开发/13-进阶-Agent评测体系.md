# 13 - 进阶：Agent 评测体系

> 进阶篇第 3 章。07 篇给了"20 个 case 的最小评测"；本章把它升级为**能支撑持续迭代的评测体系**：任务分层、LLM-as-judge 的偏差控制、回归防护、以及评测与生产的闭环。这是把 Agent 从"能跑"带到"敢改"的基础设施。

## 1. 为什么 Agent 评测比模型评测难一个量级

单轮模型评测（MMLU 式）是"输入→输出"的函数拟合检查；Agent 评测要面对：

1. **轨迹不确定**：同一任务两次运行的步数、路径、工具组合可能完全不同——不能按"标准答案的步骤"判分，只能按**结果与过程质量**判分；
2. **成败的中间态**：很多结果介于对错之间（报告对但引用错、代码能用但违反规范）——需要分级评分而非二值判定；
3. **环境依赖**：评测结果依赖工具实现、模型版本、甚至数据时间（搜索类 Agent 的评测集会过时）；
4. **非平稳目标**：上线的 Agent 面对的任务分布会漂移，静态评测集会逐渐失真。

所以 Agent 评测体系的设计目标不是"一个总分"，而是**一套能回答"这次改动让我在哪些能力上变好/变坏了"的诊断系统**。

## 2. 评测集的分层设计

按"测试金字塔"的思路给 Agent 任务分层（金字塔比喻在测试工程中由 Mike Cohn 提出，此处借用到 Agent 评测）：

```
        ┌──────────────┐
        │  端到端任务集  │  少而贵：完整真实任务，几十个
        ├──────────────┤
        │  能力维度集    │  中量：规划/工具选择/纠错/长上下文各几十个
        ├──────────────┤
        │  单元级用例    │  多而便宜：单个工具调用的参数正确性、格式遵循
        └──────────────┘
```

| 层 | 测什么 | 例子 | 判分方式 |
| --- | --- | --- | --- |
| 单元级 | 单步能力 | 给定邮件文本，选对工具并生成合法参数 | 程序化（schema 校验 + 断言） |
| 能力维度 | 单项智能 | 纠错能力：故意给错误的工具返回，看能否恢复 | 半程序化 + judge |
| 端到端 | 真实任务 | "调研竞品并产出报告" | rubric judge + 人工抽检 |

**每层各有用途**：单元级跑得最快、定位最准（改了工具描述后 30 秒知道参数生成有没有退化）；端到端最接近真实但归因最弱。**只跑端到端的团队，每次回归都像开盲盒**。

### 任务集的来源纪律

- 从**真实使用日志**里捞失败 case 改写成评测 case（最贴分布）；凭空编写的任务集会系统性偏离真实使用；
- 每个线上事故 → 归因 → 回填为一个评测 case（07 篇的"防回归"制度化）——评测集随事故单调增长，这是它最有价值的增长方式；
- **保持划分集（held-out）**：把评测集切成"开发集"（可反复看）与"封存集"（每月只跑一次）。反复对着同一个评测集调优，就是在对它过拟合（量化 05 篇的数据窥探，同一个道理）。

## 3. 判分器设计：程序化优先，judge 补位

### 3.1 判分优先级阶梯

1. **程序断言**（零成本、零偏差）：文件存在、JSON 合法、测试通过、输出包含要求的字段——**能程序判的绝不交给 judge**；
2. **rubric-based LLM judge**（有成本、有偏差、可覆盖开放维度）：按明确评分细则打分；
3. **人工评审**（最贵、最准）：只用于 judge 的校准与争议仲裁。

### 3.2 LLM-as-judge 的四个已知偏差与控制

LLM-as-judge 实用但有系统偏差（学界与业界均有实测，如 MT-Bench/Cheyney* 等研究揭示的 bias；控制手段是工程共识）：

| 偏差 | 表现 | 控制 |
| --- | --- | --- |
| 位置偏差 | 偏好先出现/后出现的答案 | 成对比较时**两个顺序各跑一次**取平均 |
| 自我偏好 | 偏好与 judge 同源的模型输出 | judge 模型与被测模型**异源**；至少知晓此偏差 |
| 冗长偏好 | 偏好更长的答案 | rubric 明确"长度不加分"；或先规定答案长度上限 |
| rubric 歧义 | 评分标准含糊 → judge 自由发挥 → 分数不可比 | rubric 用**行为化描述**："引用了具体数据=2 分；泛泛而谈=1 分" |

```python
JUDGE_PROMPT = """你是严格的评审。依据以下 rubric 给任务结果打分（1-5）。

Rubric：
- 5：完全满足全部要求，且有可验证的具体内容（引用了数据/给出了正确代码）
- 4：满足核心要求，个别次要缺失
- 3：核心要求部分满足，有明显缺口
- 2：方向正确但大量缺失
- 1：未满足或错误

任务：{task}
要求清单：{requirements}
实际结果：{output}

先逐条列出"要求 → 是否满足 + 证据"，再给总分。只依据要求清单评分，
不因长度、语气加分。输出 JSON：{{"evidence": [...], "score": n}}"""
```

要点：**先证据后分数**（强迫 judge 引用原文，减少凭印象）、**rubric 行为化**、**输出结构化**（可统计）。

### 3.3 judge 本身要被验证

上线 judge 前做一次**校准**：人工评 30~50 个结果，计算 judge 与人的**一致率/Spearman 相关**（经验阈值：与多数人评分的相关 ≥ 0.7 才可用作回归对比；绝对分数不重要，**相对变化可比**才是 judge 的核心价值）。judge 换版本同样要重新校准并回归旧集。

## 4. 指标体系：质量、成本、速度的三元组

| 维度 | 指标 | 说明 |
| --- | --- | --- |
| 质量 | 任务通过率、rubric 均分、**分能力通过率** | 分能力（工具选择/纠错/长上下文…）是诊断的钥匙 |
| 成本 | 平均 token/任务（分输入/输出）、工具调用次数 | 回归的另一半：质量持平成本翻倍也是退化 |
| 速度 | 端到端延迟 P50/P95、步数/任务 | P95 决定用户体验上限 |

三条分析纪律：

1. **任何改动同时看三元组**——"通过率 +2%、token +80%"可能是赚是亏，取决于任务价值密度；
2. **看分布不只看均值**：通过率从 80%→85% 如果是"难任务从 0 分变 5 分"，价值远大于简单任务上锦上添花——按任务难度分层看；
3. **CI 门禁化**：每次提示词/工具/模型改动自动跑单元级 + 能力维度集，质量或成本指标超出阈值即拦截合并（把评测变成像单测一样的 CI 环节）。

## 5. 与生产闭环：线上监控喂给评测

评测集会过时（§1.4），闭环做法：

1. **线上采样**：随机抽样生产轨迹（注意隐私脱敏）定期人工/judge 评分，与评测集分数对比——**评测分数高、线上分数低 = 评测集失真**，用线上样本增补评测集；
2. **失败信号自动入库**：用户显式纠正、重试、提前放弃等行为作为疑似失败 case 自动进入待标注队列；
3. **A/B 与流量灰度**：新版本 Agent 先灰度 5% 流量，用线上指标（完成率、人工接管率）验证后再放量——评测集只能保证"没变坏"，灰度保证"真实分布上确实变好"。

## 6. 最小可行体系（一周工作量）

按投入产出排序的实施清单：

```markdown
□ 单元级：每个工具 5~10 个参数生成用例（程序断言）—— 1 天
□ 能力维度：纠错 20 例 + 工具选择 20 例 —— 1~2 天
□ 端到端：20 个真实任务 + rubric 判分（judge 校准 30 例）—— 2 天
□ CI 接入 + 三元组指标报表 —— 1 天
□ 封存集切分（70/30），月度跑封存集 —— 半天
```
