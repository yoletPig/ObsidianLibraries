# 14 - 进阶：生产部署与可观测性

> 进阶篇第 4 章（Agent 系列完结篇）。评测体系（13 篇）解决"敢不敢改"，本章解决"上线后怎么活"：tracing、成本治理、可靠性降级、以及多租户下的安全隔离。这些是 90% 的教程不写、但生产事故 90% 发生在这里的地方。

## 1. 生产 Agent 与演示 Agent 的差异清单

| 维度 | 演示 | 生产 |
| --- | --- | --- |
| 失败处理 | 报错即止 | 降级、重试、部分结果返回 |
| 成本 | 不看 | 每 token 有预算与归属 |
| 调试 | print | 分布式 tracing，逐步回放 |
| 并发 | 单会话 | 多用户隔离、限流、排队 |
| 变更 | 手改提示词 | 版本化 + 灰度 + 回滚 |
| 数据 | 自己的 | 用户数据的隐私与留存合规 |

一条主线贯穿全章：**生产 Agent 的每一层都要"可解释、可限制、可回退"**。

## 2. 可观测性三支柱在 Agent 场景的落地

传统可观测性三支柱（metrics/logging/tracing，出自 CNCF 与 Control Theory 的工程共识）映射到 Agent：

### 2.1 Tracing：Agent 的第一等公民

Agent 的调试单位不是"请求"而是**轨迹（trace）**：一次任务 = 一次 trace，内含多个 LLM span 与工具 span，嵌套成树（多 Agent 时跨进程传播）。

```
trace_id: t-20261107-001 (任务: 整理下载目录)
├─ span: llm.step[1]      (model=gpt-x, in=2.1k tok, out=120 tok, 0.8s)
├─ span: tool.list_files  (args={dir}, 45ms, ok)
├─ span: llm.step[2]      (in=2.4k tok, out=200 tok)
├─ span: tool.move_file   (args={src,dst}, 12ms, ok)
├─ span: approval.delete  (human, waited 3m2s, DENIED)   ← 人审也进 trace
└─ span: llm.step[3]      (in=2.6k tok, out=150 tok, final)
```

实现要点：

1. **每步 LLM 调用记录完整输入输出**（含工具定义版本、提示词版本）——事后能精确重放任意一步。没有这个，13 篇的"线上采样评测"无从谈起；
2. **trace_id 透传到工具与子 Agent**：跨服务/子 Agent 场景沿用标准分布式追踪语义（W3C Trace Context 规范：`traceparent` 头传播 trace-id/parent-id）；
3. **prompt/工具定义打版本号**并记录在 span 属性里——"是提示词 v12 的锅还是 v13 的锅"必须有据可查。

### 2.2 Metrics：面向告警的指标

- **业务面**：任务完成率、人工接管率、验收不通过率（13 篇三元组的线上版）；
- **成本面**：token 消耗按 任务类型/用户/模型 维度分桶——成本告警比质量告警更早发现问题（token 突增常是死循环的先兆，07 篇问题 1 的生产形态）；
- **健康面**：各工具的延迟与错误率、LLM API 的限流率（429）、重试率。

### 2.3 Logging 与审计

08 篇的审计日志在这里扩展为生产规范：追加写、含审批记录、保留期与合规要求对齐（涉及用户数据的留存策略按所在司法辖区要求，如 GDPR 的数据最小化原则——**trace 里的完整用户输入往往不能永久留存**，需要脱敏或截断策略）。

## 3. 成本治理：从"按次计费"到"按价值记账"

1. **预算三层**：全局日预算（熔断）、按任务类型预算（超限降级到便宜模型）、按用户配额（防滥用）；
2. **级联模型路由（model cascading）**：简单步骤用小模型、关键决策用大模型——按"步骤价值"而不是"任务"选模型。这是推理成本优化的常见结构（业界统称 model routing / cascading，如早期 FrugalGPT 研究 Chen et al. 2023 系统化过）；
3. **缓存复用**：相同前缀（系统提示 + 工具定义）各家 API 普遍支持前缀缓存计费优惠；应用层再做任务级结果缓存（相同输入的任务直接复用轨迹）；
4. **成本异常 = 行为异常**：单任务成本超阈值自动终止并留 trace——它同时是成本控制和死循环熔断器。

## 4. 可靠性工程：重试、超时、降级的分型策略

不同失败类型，策略完全不同（盲目统一重试是事故放大器）：

| 失败类型 | 例子 | 策略 |
| --- | --- | --- |
| 瞬时错误 | 网络抖动、429 限流 | 指数退避重试 + jitter（AWS 架构博客的标准做法：Exponential Backoff And Jitter） |
| 永久错误 | 参数非法、权限不足 | 不重试，作为观测回喂模型自纠（03 篇） |
| 超时 | 工具卡死、LLM 慢 | 分层超时：单步 < 整任务 < 用户等待预算；超时后降级 |
| 内容级失败 | 模型输出无法解析、评分不达标 | 结构化重试（带错误反馈重生成 1~2 次），再失败降级 |

**降级阶梯**（从优到劣，提前定义好）：

```
正常执行 → 缓存/近似结果 → 简化版任务（如摘要代替全文分析）
→ 转人工队列 → 明确报错（附任务状态，用户可续做）
```

关键纪律：**降级是产品决策不是技术临时起意**——每个任务类型上线前必须写明降级阶梯，否则事故时现场发明。

## 5. 多租户与并发：隔离清单

1. **状态隔离**：每会话独立上下文存储（user_id + session_id 分区），串号（A 用户看到 B 的数据）是 Agent 产品最严重的事故类别之一；
2. **并发限制**：每用户并发任务数上限；全局并发保护下游（工具 API、数据库连接池）；
3. **权限的租户维度**：08 篇权限模型在多租户下升级——**凭据按租户代持（on-behalf-of）**，Agent 携带的是"某用户的受限委托凭据"，而不是服务级万能 key（09 篇 confused deputy 的租户版）；
4. **队列与排队反馈**：高峰期任务排队并给用户可见的排队状态，优于无声丢弃。

## 6. 变更管理与回滚

1. **提示词/工具定义/模型三者都做版本化**（12 篇 ADR 的运行时延续），一次发布只改一个变量——便于归因；
2. **灰度发布**：5% → 25% → 100%，每档看 13 篇线上指标 + 成本指标；
3. **一键回滚**：回滚 = 切回上一版本的提示词/模型配置（数据与状态层保持兼容——**状态 schema 变更要做前后兼容**，否则回滚会读不出旧状态）；
4. **影子运行（shadow mode）**：新版 Agent 与线上版并行处理相同输入但不对外输出，用真实流量免费获得对比评测。

## 7. 生产就绪检查清单

```markdown
□ 每步 LLM/工具调用都有 trace（含版本号），可重放任意一步？
□ 成本三层预算 + 异常熔断？
□ 失败分型策略表（瞬时/永久/超时/内容级）已写明？
□ 每个任务类型的降级阶梯已产品化定义？
□ 会话状态按租户隔离？凭据是用户级委托而非万能 key？
□ 提示词/模型版本化 + 灰度 + 一键回滚？状态 schema 前后兼容？
□ trace 中的用户数据有脱敏/留存策略？
□ 线上采样 → 评测集的闭环已运行？（13 篇）
```
